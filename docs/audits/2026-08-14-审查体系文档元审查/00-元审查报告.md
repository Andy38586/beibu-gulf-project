- **总数：35 个子 agent / 8 个专项窗口并行**。低于机械上限 Σmin(parts,6)=47（留汇总余量），高于串行 8（避免重蹈上次单 agent 1 小时的失败模式）。

- 代码范围预算（本仓库实测）：frontend/src 23,105 行（core 9,033 / business 4,864 / shared 3,600 / visualization 1,327 / types 1,195 / views 1,103 / stores 1,044 / services 597）、backend 6,098 行（含 flood-service）。每 agent 代码子集 ≤ 1 个模块，禁止全库通读。

### 3.2 负载均衡（用户关切：每 agent 相似数据量）
- 文档侧：每 slice 正文 131–518 行（合并后中位数 ~350）。
- 代码侧：按 00 §4 标准输入资产表映射 + 上述模块预算，每 agent 代码子集控制在 1 个模块内。
- 均衡判据：**slice 负载 = 正文行数 + 代码子集行数**，目标每 agent ≤ 1,000 行输入。
- 均衡性检查脚本：合并前 `[max/min]` 失衡比（专项8 3.8x）→ 合并后 ≤ 1.6x（§3.1 方案已达标，除两个 `*` 配重项）。

### 3.3 fail-fast（用户关切：不等待超时、失败即重派）
- **探活**：子 agent 启动后每 5 分钟报告进度（读文档完成 / 检查进行中 / 产出草稿）；**5 分钟无任何进度 → 立即 kill**，不等全局超时。
- **重派**：同一 slice 换 agent 重跑，最多 2 次；仍失败 → 降级为机械 grep 检查（本批次 `tools/audit-docs-check.mjs` + `audit-docs-deep.mjs` 即该降级形态）+ 主 agent 兜底复核。
- **源头防错**（减少失败概率）：
  1. 每 slice prompt **自包含**：指标编号清单 + 部分全文 + 代码路径 + 产出模板 11 字段全部内嵌，不依赖 agent 间通信；
  2. 明确「只读不改，禁止执行任何写操作」；
  3. 明确「不加载附录、不搜索『已修复』『已知』等字样」（防锚定，见 P2-3）；
  4. 产出模板机械可校验（编号/证据 file:line/等级三字段必填）。

### 3.4 1 小时窗口（用户关切：≤1h 且不过短）
- **窗口=60 分钟，硬上限**；下限 45 分钟（不足则判超时重派）。
- 时间分解：读文档 10min → 读代码子集 + 跑检查 20min → 证据核对 20min → 产出 10min。
- 可行性论证：每 agent 输入 ≤ 518 行文档 + ≤1 模块代码 + 指标 6–12 条（368/35），核对动作量级与 2026-08-12 批次单专项 2 文件的产出规模同量级。

### 3.5 发现质量（用户关切：最大化真实发现、最小化文档影响）
- **输入隔离**：子 agent 只见「指标 + 代码」，不见附录/判例/预期答案（00 §4 设计 + P2-3 强制条款）。
- **证据强制**：结论必须 file:line；无证据的观察不计入问题副本（0.6 格式约定）。
- **定级规则**：防御分支失效/量纲错误/除零兜底死代码 P1 起评（00 §1 特别约定）——机械检查无法自动覆盖，交由子 agent 判定。
- **主 agent 汇总**：35 份产出 → 去重（同根因跨 slice）、统一定级、按 00 §4 流转（问题副本 → 用户裁决 → 主台账）。
