## 一、定位与最终预期

**产品定位**：港口选址情景推演与多准则决策支持平台——不是"给政府做更准的选址系统"（做不到），
而是"快速探索'如果-那么'情景的决策研究工具"（政府没有的）：权重/假设可调、秒级重算、方法链可审计。

**最终预期（v4 形态）**：
- 五个业务模块闭环：选址（多准则+运河因子）、浸没风险（陆海 DEM 融合）、最短路径（可达性因子）、
  吞吐量预测（ARIMA+情景分档）、航线分析（密度叠加，降档）
- 情景推演核心交互：预测分档（看好/中立/看衰）→ 选址权重预设 → 双维矩阵输出
  （高适宜+高可达=即用型；高适宜+低可达=基建拉动型，联动最短路径算配套成本）
- 双后端 + PostGIS + 前端热插拔（见 §二/§五）
- 论文主线 = 核心三角（选址/浸没/最短路径）；预测/航线为支撑

**明确不做**：大屏数字孪生（动效>数据）、实时数据流（拿不到真实系统）、与政府精度竞争。

## 二、技术架构（已确认决策）

### 2.1 双后端 + PostGIS

| 层 | 职责 | 技术 |
|---|---|---|
| 业务系统层 | 认证/用户/方案收藏/编排/API 治理 | **NestJS**（DI/Guard/Interceptor/Swagger） |
| 计算引擎层 | 全部算法：ARIMA/连通性演算/最短路径/选址评分/航线叠加 | **FastAPI**（scipy/networkx/statsmodels/geopandas） |
| 数据层 | 空间数据存储与查询 | **PostGIS**（EPSG:4490 存储，pgRouting 待启用） |

- **不是纯 FastAPI**：职业目标（全栈、NestJS→Spring 迁移路径）+ 行业形态（业务平台+算法服务分离是智慧城市标配）+ 作品集叙事（Nest 展示企业级后端）。
- **双后端成本控制**：OpenAPI 契约先行（Nest Swagger + FastAPI 自动 OpenAPI 同源），CI 契约校验，一次性解决 b034 契约漂移。
- **栅格不入 PostGIS raster**：DEM（30m mosaic 777MB）保持文件 + GDAL/FastAPI 读取；PostGIS 管矢量/路由/拓扑。

### 2.2 隔离与替换（strangler，已确认）

```
backend/               老 Express —— 冻结保留（auth/plans/site-analysis/forecast/flood）
backend/nest/          v3 业务层（新建，逐步覆盖 Express 功能）
backend/algorithm-service/  FastAPI 演算服务（由 flood-service 演进，挂载全部算法）
docker-compose.v3.yml  v3 栈：postgis（已建）+ nest + fastapi（后续加入）
前端 services/adapters 按模块切换 baseURL（现有 api/online 双模式机制扩展）
新后端完善后全量替换：Nest:3000 / FastAPI:8000 / PG:5432
分支：experiment/v3-backend-migration（唯一 v3 分支，main 隔离不动）
```

### 2.3 存储坐标系（已确认）

**EPSG:4490（CGCS2000）**——与现有处理成果（filled_CGCS2000_int16.tif）一致；数据源为 4326，
二者在中国区域厘米级一致，入库直接赋值（项目尺度可接受）；前端展示层转 4326/3857。

总量 20.4GB（原始）；处理后 PostGIS 矢量入库约 100-200MB——小到中型，PostGIS 选择是**功能驱动**（pgRouting/空间 SQL/事务），面试口径如此。

### 3.2 处理流水线（全部可复现）

- GLO-30：19 瓦片 → `gdalwarp` 合并至 UTM48N（Int16/32767）→ `SAGA` 填洼（Wang&Liu, MINSLOPE 0.01）→ 重投影 4326+4490
- SRTM15+：`gdal_translate -projwin` 裁剪北部湾 bbox
- OSM：`pyosmium` 提取（路网/海岸线/水体，bbox 过滤）→ `ogr2ogr -spat` 裁剪
- 工具：GDAL（QGIS 3.44.12）/ SAGA / pyosmium 4.3.1 / Node 下载器（Range 续传+MD5 校验）

### 3.3 准确性保障

官方 MD5（OSM 首版损坏→重下通过）｜ 文件魔数（GeoTIFF/HDF5/PBF/ZIP）｜ 全量读取统计（SRTM15+ min/max 与元数据一致）｜ 语义范围检查（-121.6m 海底）｜ CRS/像元验证。

## 五、前端热插拔治理（先设计后实施）

**目标不是开源插件生态，而是"后来者能便捷管理"**：加一个地图功能=加一个模块，删一个=删一个模块；核心保持简短。

### 5.1 模块契约（v3 目标形态）

```
business/<module>/
├── manifest 条目（路由/导航/引擎，一处注册）     ← 已有，需自动化扩展
├── Page.vue + composables + constants            ← 已有
├── <module>Store.ts（自动注册/重置）              ← 待做：App.vue 遍历 manifest 批量 reset
└── 图层能力（renderer/adapter 注册）              ← 待做：图层 key 命名空间化（修 a066）
core/（核心，保持简短）
└── 地图渲染抽象 + BLM + GCS + 应用装配           ← 已有，目标是"不再随业务膨胀"
```

### 5.2 首批动作（阶段 2）

1. manifest 增加 store 声明字段 → App.vue 批量注册/重置（消除手工 resetStores）
2. 图层 key 加业务命名空间（修 a066，防模块间冲突）
3. 目录规范文档化（新增模块清单：要改哪几个文件）
4. 新老模块并存期：老选址保留代码与数据，路由让位给新模块（已确认不删除）
