## 一、多 Agent 接力协议（每个开工的 agent 必读）

任何 agent（或人）接手施工，按以下流程执行：

1. **读输入**：本文件全文 + 任务卡依赖的日志文件 + `docs/v3-发展路径-2026-08-14.md` §二/§四（若未读过）。
2. **认领任务**：在 §三 状态总表中找第一个 `pending` 且其依赖全部 `done` 的任务，把状态改为 `in-progress` 并注明接手者（agent 标识或会话名）。
3. **施工**：严格按 §四 任务卡的"动作"执行。**允许偏离，但必须在实施日志中记录偏离内容与理由**；禁止静默偏离。
4. **写日志**：完成后按 §六 模板在日志归档目录新建日志文件：`C:\Users\JionHappY\Desktop\_北部湾项目\文档\后端nest，pg，postGIS\`（**日志不进 git**，用户裁决 2026-09-01；状态总表的"完成日志"列即该目录下的文件名）。
5. **更新状态**：状态总表该行改为 `done` + 日志锚点 + 完成日期。若任务被阻塞，改为 `blocked` 并写明阻塞原因与解除条件（阻塞超 3 个任务时，停下来向用户汇报，不得绕过）。
6. **提交**：commit 格式遵循 03 §1.6（`<type>: 中文正文`，无括号 scope；`fix:`/`refactor:` 必须附测试）。文档类改动用 `docs:` 前缀。

**状态枚举**：`pending` / `in-progress`（+接手者）/ `done`（+日志锚点+日期）/ `blocked`（+原因）。
**单点维护**：任务状态只写在 §三 总表，任务卡内不得重复状态字段（防两处漂移，审查体系既有教训）。

### 1.1 编号声明

- 本档任务编号 `T<阶段>.<序号>` 是**施工编号**，用于任务引用与日志命名，与问题台账编号（`a/b/c/d/z`）是不同体系。
- 施工过程中发现的**问题**（bug、契约缺口、数据异常）不分配编号，记录在对应任务实施日志的"问题与测试固化"节；需要进入全项目台账的，经用户裁决后由用户分配正式编号（规则见 `docs/待解决问题.md` 头部）。

### 阶段 P1 NestJS 骨架与基础设施

> **Nest 评估结论（响应"Express 是否上 Nest"）**：**上，既定决策**（v3 §2.1：NestJS 业务层 + FastAPI 演算层 + PostGIS 数据层，strangler 逐模块替换；2026-08-14 用户确认）。支撑理由：职业路径（Nest→Spring 迁移叙事）、DI/Guard/Interceptor/OpenAPI 生态契合契约治理（b034 的 OpenAPI 契约先行方案依赖 Nest Swagger）。**控范围**：只做 auth/plans/favorites/数据读 API/OpenAPI，不做重编排、不引微服务通信框架。**不引入 ORM**：延续 ADR"不用 ORM"，用 `pg` 连接池 + 手写 SQL，repository 层封装（对齐"迁移时替换 repositories 层即可"的既有设计意图）。
