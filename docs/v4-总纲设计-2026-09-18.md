## 三、系统 R 详细设计 —— 请求归属重构（🔴 本版新增，最优先）

### 3.1 核心模型：三层分离

> **请求的"发起权"归面板，请求的"生命周期"归 store，渲染的"消费权"归页面。**

```
┌──────────────────────────────────────────────────────┐
│ ① 面板（发起点）                                       │
│    持有「参数」+「执行按钮」                            │
│    点击执行 → 调 taskStore.submit()，不自己 fetch      │
└────────────────────┬─────────────────────────────────┘
                     │ submit({ domain, params, route })
                     ▼
┌──────────────────────────────────────────────────────┐
│ ② taskStore（生命周期，唯一持有 AbortController）        │
│    - 调后端 POST /task 拿 taskId                        │
│    - 轮询 GET /task/:id 更新 progress                   │
│    - 完成/失败 → 结果 + 状态写 store                     │
│    - 页面卸载 / 面板拖走：不受影响                       │
└────────────────────┬─────────────────────────────────┘
                     │ taskStore.tasks[route]
                     ▼
┌──────────────────────────────────────────────────────┐
│ ③ 页面 + 结果面板（纯消费）                             │
│    订阅 store，拿 result → 调 renderer 渲染              │
│    不发请求、不持 AbortController                        │
└──────────────────────────────────────────────────────┘
```

### 3.2 🔴 关键技术变化：`AbortController` 搬家

|                          | 现状                                                                                            | 重构后                                               |
| ------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 谁持有 `AbortController` | **页面**（`FloodAnalysisPage.vue:277` `floodAdapter.getFloodAnalysis(waterLevel, { signal })`） | **taskStore**                                        |
| 页面卸载                 | `onUnmounted` → abort → **任务死**                                                              | 不受影响，任务继续                                   |
| 竞态守卫                 | 页面手写 `analysisSeq` 序号（`FloodAnalysisPage.vue:56`）                                       | taskStore 内置（按 `route` 分槽，`taskId` 天然去重） |

**顺带解决 R10**：手写 `analysisSeq` + `useLatestRequest` 的竞态守卫，收进 store 后用 `taskId` 天然去重
—— 新任务提交时，**同路由旧任务自动标记 `cancelled`**。竞态从"手工序号比对"升级为"状态机"。

### 3.3 composable 与 adapter 的处置

| 对象                                                                    | 现状                            | 重构后                                                           |
| ----------------------------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------- |
| `useForecastTimeseries` / `useForecastComparison` / `useOverviewCharts` | 自己调 `forecastAdapter` 发请求 | 只做**参数整理 + 订阅 store**；请求由 taskStore 完成             |
| `floodAdapter` / `forecastAdapter`                                      | 前端 ↔ 后端协议翻译层           | **保留**。调用点从 composable/页面移到 taskStore，**协议层不废** |
| `useRouteApi`（航线）                                                   | 面板内部自持                    | **保留**（已是正确形态），只需接上 taskStore                     |

### 3.4 边界：什么进 store，什么留页面

| 内容                                       | 归属          | 为什么                              |
| ------------------------------------------ | ------------- | ----------------------------------- |
| 参数（水位/起终点/指标）                   | 面板 `ref`    | 用户输入，面板自己的状态            |
| **请求 + AbortController + 竞态**          | **taskStore** | 生命周期必须脱离页面                |
| 结果数据                                   | taskStore     | 拖出/切换路由都要能拿到             |
| **渲染**（调 `businessLayerManager` 上图） | **页面**      | 依赖引擎实例，store 不能碰（I1/I2） |
| 视图状态（展开/折叠/选中）                 | 页面或面板    | 纯 UI                               |

> 🔑 **一句话**：**面板管"要什么"，store 管"跑到哪"，页面管"画出来"。**

> ⚠️ **必须写进文档的取舍**：**渲染不能进 store**（store 不能碰 renderer，违反 I1/I2）⇒
> **任务算完时若用户不在该路由，结果只能"存着"，不能渲染。**
> 这**正好符合口径 #8**（用户主动拖出才渲染）——**不是缺陷，是设计**。
> 结论：**运算可在后台，渲染必须在场。**

## 四、系统 B 详细设计 —— 后端异步任务能力

### 4.1 接口契约（新增）

```ts
// POST /nest-api/task           提交任务，立即返回
// 请求体：{ domain: 'flood'|'route'|'forecast', params: {...}, priority: 'high'|'normal' }
// 响应：  { taskId: string, status: 'pending'|'running', queuePosition: number, createdAt: number }

// GET  /nest-api/task/:id       查询任务
// 响应：  {
//   taskId, status: 'pending'|'running'|'retrying'|'done'|'failed'|'cancelled',
//   progress: number,             // 0~1，阶段进度（见 §4.4）
//   queuePosition?: number,       // pending 时的排队位次
//   retryCount?: number,          // 已重试次数（前端用于 toast）
//   result?: unknown,             // done 时存在
//   error?: { message: string },  // failed 时存在
//   startedAt, finishedAt
// }

// DELETE /nest-api/task/:id     取消任务
// 响应：  { taskId, status: 'cancelled' }
```

### 4.2 🔴 串行队列（口径 #24 + #23）

```
后端 task 注册表持有「执行队列」，并发上限 = 1（串行）

提交任务时按优先级入队（口径 #23）：
  priority='high'   → 插入队首（当前路由的任务）
  priority='normal' → 追加队尾（被拖入 dock 的后台任务）

场景：A 已拖入后台在跑 → 用户切到 B 操作 B 的面板
  ⇒ B 是当前路由（high）⇒ **B 插队到队首**
  ⇒ A 跑完 → B 开始（或若 B 提交时 A 还在跑，B 排队等 A）

「当前路由」由前端在 submit 时通过 priority 字段告知后端。
后端不判断"谁在前台"（它不知道用户在看哪个页面）—— 这是前端的知识。
```

| 参数         | 值                            | 说明                         |
| ------------ | ----------------------------- | ---------------------------- |
| 并发上限     | **1（串行）**                 | 口径 #24；防 1.6G 服务器 OOM |
| 队列长度上限 | 建议 8                        | 超出直接拒绝（防内存堆积）   |
| 优先级       | `high` 插队首 / `normal` 队尾 | 口径 #23                     |
| 排队状态     | `pending` + `queuePosition`   | 前端可显示"排队中"           |

> 🔴 **串行理由**：PostGIS 查询是 **CPU 密集型**（记忆铁律：_淹没裁剪是 CPU 型 ⇒ 拉 postgis 内存不会变快_）。
> 两任务并行会互相拖慢，甚至 OOM。串行 + 秒级任务 ⇒ 用户体感损失极小。

### 4.3 🔴 自动重试（口径 #21 + #25）

```
后端执行任务
  ├─ 尝试 1 失败 → 等 300ms  → 重试（status='retrying', retryCount=1）
  ├─ 尝试 2 失败 → 等 600ms  → 重试（retryCount=2）
  ├─ 尝试 3 失败 → 等 1200ms → 重试（retryCount=3）
  └─ 仍失败 → status='failed'，error.message='服务繁忙，请稍后重试'

退避：300 / 600 / 1200ms（指数退避，口径确认）
```

**🔑 展示语义 vs 执行语义解耦（口径 #22）**：

| 层                   | 职责                             |
| -------------------- | -------------------------------- |
| **执行语义**（后端） | 重试几次是内部自愈细节           |
| **展示语义**（前端） | 用户只需知道"在跑 / 成了 / 超时" |

> **这是好设计**：① 重试是后端自愈能力，暴露细节只造成困惑；② 用户对"第 2 次重试"无法做任何有意义操作。

**但重试期间必须有反馈**（否则用户以为卡死）⇒ 口径 #25：**走 toast**。

| 触发            | toast                                                   |
| --------------- | ------------------------------------------------------- |
| 进入 `retrying` | `showWarning('服务繁忙，正在重试…')`                    |
| 最终 `failed`   | `showError(null, { fallback: '任务超时，请稍后重试' })` |

> 🔴 **不得暴露"第几次重试"**（口径 #22）；toast 文案统一为"正在重试"。

### 4.4 进度语义（🔴 必须诚实：这是"阶段进度"不是"真百分比"）

| 阶段     | progress | 触发点            |
| -------- | -------- | ----------------- |
| 已提交   | 0.0      | `POST /task` 返回 |
| 排队中   | 0.0      | `pending`         |
| 查询中   | 0.15     | 进入 service      |
| 数据就绪 | 0.6      | repository 返回   |
| 转换完成 | 0.85     | 响应组装完成      |
| 完成     | 1.0      | 结果入注册表      |

> ⚠️ **不得宣称"真实进度条"**。PostGIS 查询无法上报内部进度，**只能是阶段级**。
> 前端 `0.15→0.6` 之间用"不确定态旋转"补足（§5.7）。

### 4.5 模块结构（对齐 `modules/<域>/` 惯例）

  controllers/task.controller.ts
  services/task.service.ts        # 提交/查询/取消 + 队列调度
  services/task-registry.ts       # 内存态 Map + TTL 清理

| -------- | ---------------------------------------------------------------------- |

### 4.6 与现有接口的关系

### 5.5 拖拽机制

**方案：Pointer Events（非 HTML5 DnD）**

| 方案               | 判定 | 理由                                      |
| ------------------ | ---- | ----------------------------------------- |
| HTML5 DnD          | ❌   | 幽灵图不可控、移动端差                    |
| **Pointer Events** | ✅   | 统一鼠标+触屏、`transform` 跟手、落点精确 |

```
idle ──pointerdown──▶ (待定) ──移动>4px──▶ dragging ──pointerup 命中 dock──▶ docking ──▶ docked
  ▲                      │                     │                                        │
  └──────────────────────┴─────────────────────┘  pointerup 未命中 / pointercancel       │
                                                                                          ▼
                                                                            任务跑完 → 绿/红环
```

| #   | 设计                                           | 原因                                     |
| --- | ---------------------------------------------- | ---------------------------------------- |
| 1   | **4px 阈值**                                   | 避免点按钮被识别为拖拽                   |
| 2   | **拖拽期脱离 PPS**                             | `left/top` 改 `transform: translate3d()` |
| 3   | **`GCSPanel` 加 `draggable` prop，默认 false** | 🔴 R1：公共组件，避免误伤全站            |
| 4   | **`elementFromPoint` 落点判定**                | 比矩形相交稳，天然处理遮挡               |
| 5   | 拖拽中 z-index → `--GCS-z-panel-float`(300)    | 不得高于 drawer(400)                     |
| 6   | `pointercancel` 必须回滚                       | 触屏中断（来电/手势）                    |
| 7   | `setPointerCapture`                            | 防拖出窗口丢 `pointermove`               |

## 九、系统 G 设计 —— 布局与响应式

### 9.1 🔴 地图容器 —— **保持全屏（本方案已作废，见 §〇.1）**

> **作废原因**：违反口径 #27「不能改布局」。**v4 保持 `UnifiedMap` 的 `position:absolute; inset:0` 不动。**

**实际方案**：dock 与堆叠槽位做成**绝对定位浮层**，叠在地图之上（复用现有 `--GCS-z-*` 刻度）。

```

v4 新增（仅加层，不改现有）：
  .app-content
    └─ TaskDockHost (absolute; bottom 上方; z-index:var(--GCS-z-nav))    ← 新增浮层
```

**好消息**：`UnifiedMap.vue:577-598` 的 `ResizeObserver` **已 observe 两个常驻容器**。
⇒ 因容器尺寸**不变**，引擎无需额外适配；`updateSize()` 逻辑**不需改动**。

## 附二、本档三个核心洞察（面试可讲）

1. **"做通一个就到处都通"为什么在本项目不成立** ——
   拖拽**机制**通用，但**请求归属**三页各异 ⇒ 卡点是架构一致性，不是 UI 通用性。**已用系统 R 解决。**

2. **"后台任务"不是被"慢"逼出来的，是被"跨路由保活"逼出来的** ——
   实测最慢接口 1.2s，本不需要重型队列。**这是用数据推翻假设的典型。**

3. **展示语义与执行语义解耦** ——
   后端重试 3 次是内部自愈，前端只需"在跑/成了/超时"。**用户对中间态无法做有意义操作 ⇒ 不该暴露。**
