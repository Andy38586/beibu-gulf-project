## 二、为什么是这个顺序（依赖论证）

1. **批次1 先行**：风险观察节明确"修复应以 a023（P0）为起点自上而下补全"。a023/a024/a025 动 `UnifiedMap.vue`/`BusinessLayerManager.ts` 销毁链，b035/b036/b037/b043 动登出重置链，同批避免反复触碰同一文件。
2. **批次2 在批次4 前**：z045（zod 运行时校验）要改 `useApiRequest`/`mapDataService`/`useBoundaryLayer`/`floodAdapter` 的 6 处 `as T` 边界——这些正是批次2 收口（z032/z063）动过的文件。先收口再校验，避免对同一函数改两遍。
3. **批次6 在批次4 后**：z058（CesiumRenderer 拆分）与 z042（去 @ts-nocheck）同文件，先补类型再拆分，拆分时类型不丢。
4. **批次7 殿后**：a028/c023/c024/z051/z052 大范围移动文件（usePortLayer 上提、建 index.ts 入口、navConfig 配置化），会改变前面批次方案里的 import 路径。放最后可让前面 6 批基于"最终文件布局"的上一版本实施，移动造成的破坏最小。
5. **批次8 收尾**：coverage 阈值（z057）与回归机制（z065）依赖前面批次修复后的基线，p3 硬化放最后。

## 三、边界红线（每批、每个 Part 必须遵守）

> 用户红线："**不要解决一个问题新增一堆问题**"。以下七条为硬约束，任何 Part 违反即视为失败：

1. **最小作用域**：只改目标函数/目标行，不做顺手重构；diff 中出现与目标无关的改动必须 revert。
2. **不加依赖**：不新增 npm 依赖，除非对应决策项（D-5 zod、D-17 Sentry、D-18 E2E 框架）经用户拍板。
3. **不动叙事文档**：不修改 `docs/开工前必读/项目根基.md` 等架构叙事文档，除非对应决策项明确批准。
4. **一个编号一个 commit**：每个编号独立 commit，**不 squash、不整理历史**（git 历史哲学红线：保留原始提交轨迹）。
5. **不删测试语义**：只允许补测试或修正测试断言，不允许删减现有断言来"让测试过"。
6. **每项修复后跑最小验证**：`npm run typecheck`（frontend）+ 该文件相关测试（`vitest run <相关测试文件>` / 后端 `node --test 相关文件`），通过才进入下一项。
7. **不在 Part 内扩大范围**：Part 描述里"明确不做 X"清单之外的任何疑似问题，只记录到批次日志的"顺带发现"节，不顺手修。

## 四、执行日志规范

- 每批一份日志：`logs/批次N-执行日志.md`（批次1 → `logs/批次1-生命周期销毁与重置链-执行日志.md`）。
- 每完成一个编号，追加一条（append-only，不覆盖）：
  ```
  ## YYYY-MM-DD HH:MM · 编号-标题 · ✅完成
  - 改动文件：A（file:line 摘要）、B
  - 验证：typecheck ✅ / vitest ✅（N passed）/ node --test ✅
  - 入档：已解决问题.md 补 solve:YYYYMMDD ✅
  - 顺带发现（不处理，仅记录）：...
  ```
- 未完成/阻塞的编号写 `⏸️阻塞` 并在该行注明原因（如"等待决策 D-x"）。
- 每批结束时，将批内全部 ✅ 编号从 `待解决问题-8.2审计专项.md` 删除，按原编号移入 `已解决问题.md`（补 `solve:YYYYMMDD`，遵守其入档质量门禁三问）。
