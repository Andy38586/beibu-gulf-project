## Part 2 · c026（P1）生产代码显式 any（8 处）

### 现状（审计 + 实码）
① `LayerControlPanel.vue:52-88` 4 处 `(l: any)`/`(e: any)`；② `WaterLevelProfilePanel.vue:192-195` 2 处 ECharts `formatter: (params: any)`；③ `MapRenderer.ts:169-180` 2 处 `handler: any`（MapRenderer 接口 :166-170 的 on/off 声明本身也是 `handler: any`，见实码 grep）。

### 目标改动
1. **`LayerControlPanel.vue`**：`(l: any)` → `(l: LayerEntry)`（已 import `LayerEntry` 类型则直接用；未 import 补 `import type { LayerEntry } from '@/types'`）；`(e: any)` → `(e: Event)`（DOM 事件）或 `(e: MouseEvent)`（点击）——实施时按实际用途判定。
2. **`WaterLevelProfilePanel.vue`**：`formatter: (params: any)` → `formatter: (params: CallbackDataParams)`（`import type { CallbackDataParams } from 'echarts/types/dist/shared'` 或 `echarts/types/src/util/types`——实施时以项目 echarts 版本类型路径为准；若无便捷路径，可用 `EChartsOption['tooltip']['formatter']` 参数类型推导）。
3. **`MapRenderer.ts:169-180`**：`handler: any` → `handler: EventListenerOrEventListenerObject`（与 :166 接口声明一致）；2 处实现若涉及事件对象消费，用 `CustomEvent<unknown>` 收窄。

### 为什么这么改 / 明确不改
- ③的接口声明（:166-170 on/off/emit）统一用 `EventListenerOrEventListenerObject`，与 DOM 惯例一致，不引第三方类型。
- **明确不改**：不重构 LayerControlPanel 的渲染逻辑；ECharts formatter 只改参数类型不改返回逻辑。

## Part 3 · c025（P1）App.vue provide/inject 字符串 key + ref 无类型

### 现状（实码核实）
`App.vue:24-28`：4 处 provide 用字符串 key；`ref(null)`（:21-22）类型为 `Ref<null>`，消费方期望 `Ref<Record<string, TypeSetting> | null>` / `Ref<Plan | null>`。

### 目标改动（`App.vue` + 类型文件）
1. 新建 `frontend/src/core/provideKeys.ts`（或就近 `types/`）：
```ts
import type { InjectionKey, Ref } from 'vue'
import type { Plan } from '@/types'          // 按实际类型路径
import type { TypeSettings } from '@/types'  // 按实际类型路径

export const RESTORE_PLAN_DATA_KEY: InjectionKey<Ref<Plan | null>> = Symbol('restorePlanData')
export const EDITING_PLAN_KEY: InjectionKey<Ref<Plan | null>> = Symbol('editingPlan')
export const UNIFIED_MAP_KEY: InjectionKey<Ref<{ getRenderer: () => unknown } | null>> = Symbol('unifiedMap')
export const MAP_STORE_KEY: InjectionKey<ReturnType<typeof useMapStore>> = Symbol('mapStore')
```
2. `App.vue`：
```ts
const restorePlanData = ref<Plan | null>(null)
const editingPlan = ref<Plan | null>(null)
provide(RESTORE_PLAN_DATA_KEY, restorePlanData)
...
```

3. 消费方（grep `inject('restorePlanData'` 等 4 处）改用 `inject(RESTORE_PLAN_DATA_KEY, null)` 或 `inject(RESTORE_PLAN_DATA_KEY)`。

### 为什么这么改 / 明确不改
- InjectionKey 让 key 拼写错误在编译期暴露；`ref<T|null>(null)` 让消费方不再手动断言。
- **明确不改**：不改 provide 的 value 语义（仍是同一 ref 实例）；`unifiedMap` 的 `getRenderer` 返回 `unknown` 保持现状（MapRenderer 类型在 z042 后收窄，本 Part 不联动）。

## Part 6 · b033（P0）淹没分析 API 类型契约断裂

### 现状（实码核实）
- 后端 `floodAnalysisController.js:210-217` 返回：`{ waterLevel, requestedWaterLevel, riskLevel, affectedFacilities, totalLoss }`。
- 前端 `FloodStatistics`（`types/business/base.ts:49-56`）：`{ totalArea, riskLevel, affectedCount, [key:string]: unknown }`——`totalArea`/`affectedCount` 后端不返回；`waterLevel`/`totalLoss` 只能经索引签名访问。
- 需在实施时 grep `FloodStatistics` 消费方（洪水页统计面板）确认 UI 依赖的字段。

### 目标改动（推荐：前端类型对齐后端响应）
1. `FloodStatistics` 按后端实际响应重定义（`types/business/base.ts`）：
```ts
export interface FloodStatistics {
  waterLevel: number          // 实际档位水位
  requestedWaterLevel: number // 请求水位
  riskLevel: string
  affectedFacilities: AffectedFacility[]
  totalLoss: number
}
```
2. grep 消费方：若洪水页 UI 用了 `totalArea`/`affectedCount`，则后端 `sendSuccess` 补算这两个字段（`assessDisaster` 返回里有面积/数量则直接带出，见 `floodService`）——**选择"后端补齐"而非前端删字段**，除非 UI 确实不用。
3. 配合 z045（Part 8）：为响应定义 zod schema，`z.infer` 推导类型（若 D-7=zod）。

### 为什么这么改 / 明确不改
- 审计建议二选一（前端对齐 or 后端补齐）；推荐"后端补齐 + 前端删索引签名"让契约**完全双向明确**，消除 `[key:string]: unknown` 逃生舱。
- **明确不改**：不改 `sendSuccess` 信封格式；不改 `assessDisaster` 业务算法。
