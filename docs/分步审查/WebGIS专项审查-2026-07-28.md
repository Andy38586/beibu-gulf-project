## 一、OpenLayers 使用

### 1.1 现状（落地位置）
- 唯一入口：`frontend/src/core/map/renderers/OLRenderer.js`，全项目**仅此一个文件** `import ... from 'ol/...'`（`:2-13`），引擎与业务隔离彻底。
- 地图初始化：`_initMap`（`:31-45`）`Map`/`View`，中心 `fromLonLat` 投影，zoom 6–20。
- 底图：天地图影像/矢量 `XYZ`（`OLRenderer.js:46-75`），`crossOrigin:'anonymous'`，支持 CORS。
- 图层：`addPointLayer` / `addPolygonLayer` / `addGeoJsonLayer` / `addHeatmapLayer`（`:110/:229/:301/:337`），`Heatmap` 来自 `ol/layer/Heatmap`。
- 点击拾取：`_setupClickHandler`（`:76-108`）`forEachFeatureAtPixel` + `layerFilter` 排除底图，按 `featureType` 派发 `click`。
- 视口裁剪（性能亮点）：要素 > `VIEWPORT_CULL_THRESHOLD`(1000) 走 `_addCulledPointLayer`（`:147-173`）R-tree（`spatialIndex.ts`），`moveend` 增量查询（`:186-202`）仅渲染视口内。
- 生命周期：`destroy()`（`:592-603`）`dispose()` + 清理裁剪索引与监听，无泄漏。

### 1.2 评价
封装、事件契约、性能裁剪均生产级；`pendingVisibility`（`MapRenderer.js:62-77`）解决"先 setVisible 后 addLayer"竞态，设计细腻。

### 1.3 真实问题
- 🟡 **颜色常量未集中（真违规）**：`_createPolygonStyle`（`:294`）与 `addGeoJsonLayer` 兜底（`:311-316`、`:443`）硬编码 `'rgba(77,171,247,0.15)'`。违反 `工程规范与性能参考.md` §5.4「禁止硬编码色值」及 `colors.ts` 集中规则（渲染层色值必须进 `src/shared/constants/colors.ts`）。应改为 `LAYER_DEFAULTS.*`。

### 1.4 已确认为 by-design（初稿曾误判，本版移除）
- 热力图 `addHeatmapLayer` 仅 2D：符合 `项目根基.md` §4.2 渲染器能力矩阵（热力图 OL✅ / Cesium❌），非缺陷。

## 二、Cesium 使用

### 2.1 现状（落地位置）
- 动态加载：`renderers/index.js:18-67` 首次切 3D 才注入 `Cesium.js`(~5.7MB) 并 `import('./CesiumRenderer')`，首屏零开销。
- 单例复用（最亮点）：`CesiumViewerManager`（`CesiumRenderer.js:26-194`）全局唯一 `Viewer`，`mount`/`unmount` 复用 DOM 与状态，离开 3D 路由仅 `unmount`（不销毁），并启动 **30s 空闲自动 `destroy()`**（`:147-163`）。
- 渲染器：`CesiumRenderer`（`:204-248`）首次创建 `_positionCamera` + 初始化底图；复用时 `mount` 到新容器并 `_enableCameraControls` 防交互失效。
- 相机：`_setupZoomLimits`（`:275-286`）100m–500km；`_setupCameraDebounce`（`:256-273`）300ms 防抖。
- 图层：点/面走 `Entity` API（`:375-471`），GeoJSON 走 `GeoJsonDataSource.load`（`:473-519`，幂等清除）。
- 水面（3D 专属）：`addWaterSurface` 用 **Primitive + PerInstanceColorAppearance**（`:720-763`），比 Entity 更适合大规模几何体。
- 相机同步：`_getCameraState`/`_setCameraState`（`:580-666`）center/height/pitch，height 钳制 200m–1,000,000m，pitch 强制 -90° 与 OL 对齐。

### 2.2 评价
单例 + 空闲销毁 + 复用挂载是内存管理最扎实部分；Primitive 用于水面、Entity 用于要素，API 选型合理。

### 2.3 真实问题
- 🔴 **3D 点图层无裁剪/LOD**：`addPointLayer`（`:375-420`）直接 `entities.add` 全量，无 rbush/聚合/视锥裁剪；而 OL 侧有视口裁剪（第一节）。同一份大数据 2D 流畅、3D 可能卡死，仅 `>1000` 告警（`:378`）不阻断。**此为真实性能缺口**（文档未宣称 3D 裁剪，故非误判）。

### 2.4 已确认为 by-design（初稿曾误判，本版移除）
- 热力图在 Cesium 不支持：符合 §4.2 能力矩阵（热力图 Cesium❌），且 flood 路由为 3D 不使用 heatmap，forecast 路由为 2D 使用 heatmap——实际不会触发。非缺陷。

## 三、图层管理

### 3.1 现状（落地位置）
- 抽象核心：`BusinessLayerManager`（`BusinessLayerManager.js`）业务只给 `{layerType,data,options}`，由 `LAYER_ADAPTERS`（`layerAdapters.js:13-78`）分派；Manager **不持有 renderer**，每次从 `mapStore.currentRenderer` 动态取（`:39-41`）。
- API：`register` / `updateData`（不改 visible，`:100-131`）/ `setVisible` / `remove` / `reapplyAll` / `has`。
- composable：`useBusinessLayers`（inject Manager）、`useLayerManager`（封装 `layerCatalog` 读取端）。
- 引擎切换重绘（关键验证）：`App.vue:99-106` 监听 `currentRenderer` 变化调 `reapplyAll(renderer)`，**已正确接通**——切 3D 后业务图层不会丢。

### 3.2 评价
Manager→Adapter→Renderer 三层分派是架构最成熟部分；catalog 只存元数据（key/label/visible），解耦干净。

### 3.3 初稿误判，本版移除
- ~~"双轨制/双路径不一致"~~：`项目根基.md` §4.3 + §6.3 + §11.3 明确区分——**基础底图**走 `UnifiedMap.setupLayers()` → `registerBaseLayer`/`_initBaseLayers()`；**业务图层**走 `BusinessLayerManager`。二者是"基础 vs 业务""写入端 vs 读取端"的刻意分离（§4.3 明文说明职责不重叠），**非缺陷**。初稿将其判为 P1 双轨制属误读文档。

### 3.4 真实（轻微）问题
- 🟢 **`geojson/points/polygon` 的 `update` 是删+加**：`layerAdapters.js:30-59` 每次 `updateData` 都 `removeLayer+addXXX`，无增量 diff。小数据无感，大数据有闪烁/GC 压力，可延后优化。
- 🟢 **doc 陈旧需同步**：`项目根基.md` §4.4 写"引擎切换会丢动态数据（切到 2D 不出现）"，但 `reapplyAll`（2026-07-28 加）已从 App 级 registry 重绘，**代码已优于文档描述**。建议更新 §4.4，避免误导后续维护者。

## 四、坐标转换

### 4.1 现状（落地位置）
- 约定：`types/crs.ts` 业务数据统一 **EPSG:4326 (WGS84)**；`LaxPoint` 兼容历史 `lon/longitude`（`crs.ts:34-41`）。
- OL：`fromLonLat`/`toLonLat`（`OLRenderer.js:4`）贯穿创建/点击/飞行；GeoJSON 读入 `featureProjection:'EPSG:3857'`（`:302-304`）。
- Cesium：`Cartesian3.fromDegrees`（`:389/:435/:722`）；点击 `Cartographic.fromCartesian`→经纬度（`:367-373`）。
- 归一化：`normalizePoint`（`crs.ts:54-72`）优先级 `lng>lon>longitude`，缺失回退 0 并 dev 告警；非默认 CRS（如 4490）仅 dev 告警。
- 区域校验：`BEIBU_GULF_BBOX` + `isInBeibuGulf`（`crs.ts:91-109`）越界过滤。
- 引擎同步：`zoom↔height` 经验公式（`config/map.js:59-80`）。

### 4.2 评价
双引擎对"业务坐标=4326"理解一致；字段归一化 + bbox 校验是务实入口防护；投影由各自引擎内部完成，避免手造投影 bug。

### 4.3 初稿误判，本版移除/降级
- ~~"无严格 4490→4326 变换 = 隐患"~~：`工程规范与性能参考.md` §4.2 明文——"北部湾区域横跨 108°E，处于 UTM 49N/50N 交界带；前端展示统一 WGS84(EPSG:4326)，投影由 OL/Cesium 内部处理"；技术栈表（项目根基 §1）也未列 proj4。此为**文档化简化**，对 web 展示平台合理，非 bug。面试如实讲"展示统一 4326，引擎内部投影"即可。
- `normalizePoint` 缺失值回退 0,0（`crs.ts:67-71`）：文档 §3.1 仅说 `normalizePoint` 归一化历史字段，**未 sanction 静默回退 (0,0)**。属防御性选择，降为 🟢 轻微建议：坏数据宜与 `isInBeibuGulf` 联动硬过滤而非渲染到 (0,0)。

### 4.4 真实（轻微）问题
- 🟢 **数据字段命名债**：`API契约文档.md` §790 `affectedFacilities` 仍用 `longitude/latitude` 全称（债务 D05，计划统一 `lng/lat`）。前端经 `normalizePoint` 已兼容，但需在后端/数据侧收口。

## 五、空间分析（核心修订章）

### 5.1 修订结论
初稿判"客户端空间分析能力为零 = 🔴 最大短板"。**此为误判**。依据文档：
- `API契约文档.md` §231：选址分析缓冲半径由**后端** `turf.buffer(..., {units:'kilometers'})` 计算；前端只传 `defaultRadius`（km）。
- `项目根基.md` §8.2 后端 services 含"**空间计算**"（选址评分 / 淹没模拟 / 预测计算）；`§1` 技术栈后端为 Node.js + Express。
- `工程规范与性能参考.md` §4.2 的 `turf.union/convex`、§6.2 的 `turf.union` 报错、§7.4 的 `turf.booleanPointInPolygon` git 示例，均以**后端服务**语境书写。

→ **几何运算（buffer / union / 点在多边形）刻意下沉后端 Node + Turf**，这是合理架构职责切分，前端负责渲染 + 空间索引 + 参数上传。前端"无几何分析"不是缺陷，而是设计意图。

### 5.2 真实缺口（文档-代码一致性）
- 🟡 **文档宣称前端 Turf.js 7，但代码无前端 turf**：
  - `项目根基.md` §1 技术栈列 "Turf.js 7" 为**前端**技术栈（与 OL/Cesium/ECharts 并列）；
  - `工程规范与性能参考.md` §三 `manualChunks` 预留 `if(id.includes('/@turf/')) return 'turf'`；
  - 同文档 §四 动态导入状态表写 "Turf.js | 按需 | ✅ 分析功能触发时才加载"。
  - 但实测：`package.json` **无 `@turf` 依赖**，`node_modules/@turf` 不存在，`frontend/src` **零 `turf` import**（仅 `types/*.ts` 注释引用）。
  - 即：文档声称前端 Turf "已按需接入 ✅"，与代码事实不符。前端实际的"空间"能力只有 `rbush` 宽相位裁剪（`spatialIndex.ts`，仅 OL 用）+ 坐标校验，无 turf 精确相位。
- 🟡 **前端两阶段过滤只实现一半**：`工程规范与性能参考.md` §4.2 示例的 "第一步 rbush BBox 过滤 → 第二步 turf.distance 精确计算" 是**前端**模式（配套 `spatialIndex.ts` 的 rbush）。当前仅 rbush 落地的宽相位，`turf.distance` 精确相位未实现（因无 turf 依赖）。
- 🟢 **`types/*.ts` 注释引用 turf 现为 aspirational**：`types/facility.ts:15`（"用于 turf.buffer 空间运算"）、`types/analysis.ts:18-19`（turf.union 坑）等，在前端无 turf 时属"计划性注释"，易误导维护者以为已实现——与 5.2 文档-代码不一致同源。

### 5.3 面试口径建议（如实）
- ✅ 正确表述："前端负责渲染 + rbush 视口裁剪 + 坐标归一化；几何运算（buffer/union/点在多边形）在后端 Node + Turf.js 完成，前端只上传分析参数、消费 GeoJSON 结果。"
- ⚠️ 勿讲成"前端用 Turf 做空间分析"——文档虽这么写，代码未落地，属"项目比人会说"风险（参见面试备战文档）。

### 5.4 可选修复（二选一，非紧急）
1. **落地前端 turf 最小集**：装 `@turf/distance` + `@turf/boolean-point-in-polygon`，实现 §4.2 的两阶段过滤（rbush + turf.distance）与/或 §7.4 的 `booleanPointInPolygon` 二次精确过滤，让文档"前端 Turf 按需加载"成真。
2. **降级文档**：将 `项目根基.md` §1 技术栈 "Turf.js 7" 标注为"后端技术栈"；§三/§四 的 `@turf` chunk 与"前端按需✅"改为"后端使用，前端不引入"，消除文档-代码不一致。

## 七、结论与优先级建议

**初稿误判已纠正**：热力图仅 2D、底图/业务双注册路径、无严格基准面变换——三者均为文档明文刻意设计，非缺陷，已从缺陷清单移除。

**真实待办（按优先级）**：
1. 🔴 **Cesium 点图层裁剪/LOD**（P1）：给 3D 点图层补 rbush/聚合/视锥裁剪，避免真实大数据 3D 卡死。
2. 🟡 **OLRenderer 硬编码色值集中到 `colors.ts`**（P1）：一处 `rgba(77,171,247,0.15)`，违反 §5.4 + colors.ts 规则。
3. 🟡 **对齐前端 Turf 文档-代码不一致**（P1/P2）：装 `@turf` 落地最小精确相位，或把文档 Turf 标注为后端技术栈。
4. 🟢 **文档同步**：更新 `项目根基.md` §4.4（引擎切换已不丢数据）；`types/*.ts` 的 turf 注释标明"后端/计划"。
5. 🟢 **`normalizePoint` 坏数据硬过滤** + `geojson/points` update 增量（均轻微，可延后）。

**强项（保留，对外可讲）**：双引擎隔离、Cesium 单例复用+空闲销毁、BusinessLayerManager+Adapter 抽象、引擎切换重绘、OL R-tree 视口裁剪、坐标归一化与 bbox 校验。
