### 2.2 维度详解

#### 2.2.1 技术栈健康度（18/20）
- ✅ Vue 3 `<script setup lang="ts">` + Pinia Setup Store 语法统一；`stores` / `services` / `types` 已全部 `.ts`（见 `项目根基.md §7.3`）。

- ✅ 已配置 `dependency-cruiser`（`.dependency-cruiser.cjs` 已改动）、ESLint、Prettier、CI 流水线（`.github/workflows/ci.yml`）。

- ✅ **Adapter 隔离**：`floodAdapter` 已成型（mock/api 切换点 `setDataSource`，`floodAdapter.ts:74`），业务层不感知数据来源。
- ✅ **Manager 单例 + 重绘缝合**：`App.vue:31` 创建 `BusinessLayerManager` 单例并 `provide`；`App.vue:99-106` 监听 `currentRenderer` 变化调用 `reapplyAll` 修复 D06（引擎切换后业务图层重绘）。
- ❌ 扣 6 分：仅 1 处跨层违规（A05，§2.4.1）；`E20` 状态直改；少量封装泄漏（§2.4.1 P3）。

#### 2.2.4 性能与可维护性（16/20）

### 2.4 Renderer / Manager / Store 职责评估

#### 2.4.1 Renderer（抽象合理 ✅）
- `MapRenderer.js`（抽象基类）：含真实共享逻辑——可见性挂起队列 `_pendingVisibility`、`EventTarget` 事件总线、`exportState/importState`（引擎切换相机+图层可见性序列化）、`flyTo` 目标归一化、`addHeatmapLayer`/`addWaterSurface` 等 2D/3D 能力按引擎降级（DEV warn + 返回 false）。**这不是"重复三件套"，而是实现侧的共享基类**；`types/renderer.ts` 是消费端契约，`.d.ts` 做桥接——分层合理，**且 `.js` 状态是 §7.3 的刻意决定**。
- `OLRenderer` / `CesiumRenderer` 已接入 `LAYER_DEFAULTS`（`OLRenderer.js:19` / `CesiumRenderer.js:23`），但 fallback 色仍有内联（见 §2.5 #5）。

#### 2.4.2 Manager（双端刻意设计 ✅，非债）
- **`BusinessLayerManager` = 写入端**（业务页面注册/更新/移除业务图层，`App.vue` 单例 provide）；**`useLayerManager` = 读取端**（Shared composable，封装 `mapStore.layerCatalog` 供 `LayerControlPanel` 消费）。`项目根基.md §4.3` 明确定义二者"操作同一数据源，职责不重叠"。**v1 所谓的'图层双轨制=最大扩展债'是误判，已撤回。**
- `reapplyAll`（`BusinessLayerManager.js:142`）在引擎切换后把 registry 中可见业务图层重绘到新 renderer，闭环了 D06。

#### 2.4.3 Store（职责清晰，少量取舍 ✅）
- 8 个业务 Store + 1 个工厂 `createPersistedState`（`gcsStore` 为协调器，互引合法，§2.2 规则4）。
- `mapStore` 累积 `analysisHandler` 职责是**已知设计取舍 A02**（业务通过 `registerAnalysisHandler` 注入而非 core 引 business），非缺陷。
- `E20`：`BusinessLayerManager.setVisible` 直改 `catalogEntry.visible`（`BusinessLayerManager.js:170`）与"用 action 改状态"约定不一致，属轻量一致性问题（§2.5）。
