## 三、分项审查

### 3.1 测试（24/50 ⭐⭐）

**现状 / 证据**
- 已配置 Vitest（`package.json` `test` / `test:watch`），`frontend/vitest.config.js` 启用 `jsdom` + `globals` + `coverage.provider:'v8'`。
- 现存 4 个测试文件，质量不低：
  - `core/map/__tests__/UnifiedMap.test.ts`（397 行，组件挂载 + 渲染器 mock + 2D/3D 切换 + 错误分支，最难的核心集成路径）
  - `core/map/renderers/__tests__/MapRenderer.interface.test.ts`
  - `shared/utils/__tests__/spatialIndex.test.ts`
  - `visualization/charts/composables/__tests__/useChartBase.test.ts`
- CI 中 `npm test` 会执行（`ci.yml`）。

**真实风险**
1. **覆盖率极低且分布畸形**：547 个前端文件仅 4 个测试，全部集中在 `core`。`services/adapters`（mock→API 切换的**架构核心边界**）、9 个 Pinia store、3 个业务模块、大量 composable 全部零测试。改 adapter/store 时 CI 不报警。
2. **覆盖率未设门槛**：`vitest.config.js` 开了 v8 coverage 但**没有 `lines`/`functions` 阈值**，CI 不强制，等于无质量闸门。
3. **无 E2E**：无 Playwright/Cypress，首屏加载、2D→3D 切换、登录态等关键路径无冒烟保障。
4. **后端零测试**（见 §四）：适配器 / 路由 / 服务层无单测，与前端同源问题。

**改进建议**
- P0：优先给 `forecastAdapter` / `floodAdapter` / `BusinessLayerManager` / 关键 store 补单测——这些是"架构契约边界"，守住即守住"mock→API 可替换"卖点。
- `vitest.config.js` 的 `coverage` 加阈值（核心模块 `lines: 60`），CI 上传报告。
- 后续引入 Playwright 做 1–2 条冒烟用例（首屏 + 切 3D）。

### 3.2 CI/CD（38/50 ⭐⭐⭐⭐）

**现状 / 证据**
- `.github/workflows/ci.yml` 流水线条理完整：`checkout → setup-node(22.x, cache npm) → npm ci → format:check → lint → cruise(dependency-cruiser) → typecheck(vue-tsc) → test → build`。
- `npm ci`（有 `package-lock.json`）保证可复现；Node 版本与 `engines` 对齐。
- 把 `dependency-cruiser` 架构契约纳入 CI——超出多数学生项目的亮点。

**真实风险**
1. **无覆盖率门禁**：`npm test` 不加阈值，测试形同"跑过即过"。
2. **`format:check` 范围过宽**：`prettier --check .` 默认覆盖全仓库 `.md`/`.json`/`.yaml`（含 12 个 docs），任一文档格式不合规即阻断 CI，且无根级 `.prettierignore`。
3. **无部署 / 预览**：流水线止步于 `build`，无产物上传、无 PR 预览、无 deploy job。
4. **小瑕疵**：无 `concurrency` 取消冗余运行；`.eslintcache` 未缓存（每次全量 lint）。
5. **⚠️ CI 健壮性隐患（高价值，初版未覆盖）**：`frontend/auto-imports.d.ts` 与 `frontend/components.d.ts` 为 untracked 且未进 `.gitignore`，却被 `frontend/tsconfig.app.json:33` 的 `include` 显式引用。CI 顺序中 `typecheck`(vue-tsc) 跑在 `vite`/`vitest` 生成这俩文件**之前** → 全新 clone 上文件不存在，vue-tsc 报缺失 / 全局类型丢失，CI 红。本地能过只是因为 dev server 已生成过。**建议二选一**：① 提交这两个 d.ts 进仓库（类型真相源，最稳）；② 加入 `.gitignore` 并在 `typecheck` 前预生成。

**改进建议**
- `format:check` 收窄为 `prettier --check "frontend/src" "docs"` 或加 `.prettierignore`。
- 加 coverage 阈值 + `actions/upload-artifact` 上传 `dist/`。
- 加 `concurrency: group: ci-${{ github.ref }}, cancel-in-progress: true`。
- **P1 优先处理 d.ts 托管**（见风险 5）。
- 补 deploy job（见 §3.6）。

### 3.3 Lint / 代码规范（30/50 ⭐⭐⭐）

**现状 / 证据**
- `eslint.config.js` 为现代化 **flat config**：`@eslint/js` + `eslint-plugin-vue` + `eslint-config-prettier` + `@typescript-eslint/parser`。
- 自定义规则极少（仅 `no-unused-vars` error + 关闭 `no-empty`/`no-useless-assignment`）。
- Prettier 配置完整（`.prettierrc`：no-semi / single-quote / printWidth 100 / lf）。
- 根级无 `.husky`，**未配置 pre-commit / lint-staged**——纯靠 CI 兜底。
- 正向实践：根 `.editorconfig` + 提交 `.vscode/settings.json`（`formatOnSave` + `source.fixAll.eslint`）、`.npmrc(engine-strict=true)` + `.nvmrc(22)` → 编辑器级一致性 + Node 版本硬锁（见 §五.3）。

**真实风险**
1. **未启用 `@typescript-eslint` 规则集**：只引入 *parser*，没有 `tseslint.configs.recommended`。TS 代码异味（悬空 Promise、`any` 滥用）Lint 不查。⚠️ **联动修正**：`项目根基.md` §7.3 规定"`any` 仅允许在 Vue emit 泛型 / 第三方库兼容，且**必须加注释**"。若盲目开 `no-explicit-any` 会**直接违反文档政策** → 启用 TS 规则时必须 `no-explicit-any: off` 或仅约束"无注释的 any"。
2. **Vue 仅 `flat/essential`**（最低档），未用 `flat/recommended`。
3. **无 `import/order`**：导入顺序靠人工，diff 噪声大。
4. **无 `no-console`**：源码检索 22 个文件直写 `console.*`。⚠️ **降级标注**：其中渲染器 DEV warn（`MapRenderer.js` 等 11 处）是文档化行为（§4.2/§11.7），**不可一刀切**。若启用 no-console，须 `['warn', { allow: ['warn','error'] }]` 并排除 DEV-warn 模式，引导其余业务日志走 `shared/utils/logger.js`。
5. **文档化约定未工具强制**（真实缺口）：Git 提交规范（`<type>(<scope>): <subject>`）、import 回溯 ≤2 层（§7.5）、barrel 导出禁令（§2.3）均无 ESLint/commitlint 强制，全靠人工自觉。

**改进建议**
- 引入 `@typescript-eslint` recommended（**须 `no-explicit-any: off`** 对齐 §7.3）+ Vue `flat/recommended` + `import/order`。
- `no-console` 用 `warn` 模式、排除 DEV-warn、引导走 logger。
- 配 husky + lint-staged（pre-commit 跑 `eslint --fix` + `prettier --check` 仅暂存文件）。
- P2：`commitlint` 强制提交规范；ESLint `no-restricted-imports` 强制 import 深度 ≤2；barrel 禁令落地为 rule。

### 3.4 构建（40/50 ⭐⭐⭐⭐）

**现状 / 证据**
- `frontend/vite.config.js` 基于 **Vite 8**：`manualChunks` 将 `vue-vendor` / `openlayers` / `cesium` / `echarts` / `ui-vendor` 拆包，利于长期缓存。
- **Cesium 处理是亮点**：自定义插件 `removeCesiumHtmlTags` 移除 5.7MB 同步 `<script>`，改为运行时切 3D 才动态加载——首屏不被 3D 引擎拖死，决策有注释支撑。
- `rollup-plugin-visualizer` + `build:analyze` 可做包体分析。`minify:true`、`sourcemap:false`（生产）合理。
- 📌 `manualChunks` 的 `cesium` 分支按文档意图**保留**（豁免清单 #1），不清理。

**真实风险**
1. **`target: 'es2015'` 偏旧**：`browserslist` 已要求 `Chrome>=89`，es2015 强制转译可选链/空值合并，**徒增大体积、丧失现代运行时优化**。建议 `es2020` 或 `'baseline-widely-available'`。
2. **`emptyOutDir: false`**：因 sandbox 冲突关闭自动清目录。CI/生产构建不会清理旧产物，**存在旧 chunk / 哈希文件名残留、被错误引用的风险**。→ P0：仅在真实 CI 强制 `true`（或构建前 `rm -rf dist`），本地 sandbox 维持 `false`。
3. **无性能预算**：`build:analyze` 手动，CI 无 `size-limit` 阈值卡点，Cesium chunk（~5MB）超 `chunkSizeWarningLimit:1000` 只告警不阻断。

**改进建议**
- `target` 升 `es2020`；CI 中强制 `emptyOutDir:true`（限定真实 CI）。
- 引入 `size-limit` 或在 CI 解析 `dist/stats.html` 设体积阈值。

### 3.5 性能（36/50 ⭐⭐⭐⭐）

**现状 / 证据**
- **架构级性能决策优秀**：2D（OL）首屏直出，3D（Cesium ~5MB）按需 `dynamic import` + 运行时懒加载。
- 大依赖拆分 + 生产关 sourcemap + 压缩开启，缓存策略合理。
- `core/map/__tests__` 中 `offsetWidth/Height` mock 说明已意识到 jsdom 尺寸问题。

**真实风险**
1. **首次进入 3D 仍有 ~5MB 加载延迟**（已知问题），未做 Cesium workers 进一步分包或 CDN 化。
2. **无客观性能度量**：没有 Lighthouse / Web Vitals 采集，无首屏 FCP/LCP 基线。
3. **22 处 `console.*` 生产日志**：⚠️ 部分（渲染器 DEV warn）为刻意设计（豁免 #2），其余业务日志有轻微开销与信息泄漏顾虑，应走 logger。
4. `es2015` target（§3.4）间接拖累运行时性能与体积。
5. 📌 **双引擎常驻 / Cesium 单例不销毁**：显式标注为有意性能取舍（豁免 #4），非资源泄漏，不计入缺陷。
6. 📌 **Element Plus 全量进首屏 / Cesium 非压缩版**：项目自列 P2（豁免 #5），非盲区，标注"待办"即可。

**改进建议**
- 建立首屏 FCP/LCP 基线（本地 Lighthouse 或 Vite 插件采集），写进 docs 作为"性能契约"。
- Cesium 进一步：Workers/Assets 走 CDN 或独立 chunk，缩短首次 3D 等待。
- 收口生产 `console.*` → `logger`（配合 lint `no-console`，排除 DEV-warn）。

### 3.6 部署（8/50 ⭐）

**现状 / 证据**
- **仓库内零部署配置**：全量检索无 `Dockerfile*` / `nginx.conf` / `docker-compose*` / `vercel.json` / `netlify.toml`（根与 frontend 均无）。
- `ci.yml` **没有 deploy 步骤**，构建产物不落盘、不发布。
- 前端有 env 分离（`frontend/.env` + `frontend/.env.production`），但**缺 `frontend/.env.example`**（后端有，前后端不一致）。
- 后端 `backend/package.json` 用 Express 5 + `helmet` + `cors` + `express-rate-limit` + `bcryptjs` + `jsonwebtoken`，安全基线不错，但同样无容器化。
- 📌 **`/api/forecast` 免认证 / Cookie 单通道 / 三套响应格式**：均为稳定架构决策（豁免 #6），非安全缺陷。
- 📌 **后端 JSON 文件存储**：刻意简化（豁免 #7），非架构缺失。

**真实风险**
1. **不可复现上线**：任何人拿到仓库无法"一条命令"跑起完整栈（前端 SPA + 后端 API），更无法演示部署。
2. **SPA + Cesium 静态资源对 nginx 有硬要求**：history 路由 fallback、Cesium 静态目录（`/cesium`）服务、`/api` 反代——没有 nginx.conf 极易踩 404。
3. **面试叙事断层**：能讲清架构，却讲不清"怎么上线"，工程闭环不完整。

**改进建议（P0）**
- 补 `Dockerfile`（多段构建：build 阶段 `npm ci && npm run build`，nginx 阶段 serve `dist/`）。
- 补 `frontend/nginx.conf`：`try_files $uri /index.html` 做 SPA fallback；`location /cesium { ... }` 服务 Cesium 静态；`location /api { proxy_pass http://backend:3000 }`。
- 可选 `docker-compose.yml` 串联 frontend + backend，本地一键联调。
- 补齐 `frontend/.env.example`，与后端对齐。

## 四、后端工程化补查（初版仅在部署顺带提及，此处展开）

后端结构本身不差：`backend/` 用 Express 5 + `helmet` + `cors` + `express-rate-limit` + `BusinessError` 统一错误码 + routes/controllers/services 三层分离（工程规范 §6）——**分层清晰**。

**真实缺口**
- **后端零 Lint 质量门**：`eslint.config.js` 仅给 `backend/**/*.js` 设了 `globals.node`，**未引入任何 JS 最佳实践规则**（无 `no-unused-vars` 强约束、无 `no-console`、无复杂度）。纯 `.js` 后端处于"无静态检查"状态。
- **后端零测试**：适配器 / 路由 / 服务层无单测，与前端"测试孤岛"同源。
- 后端无 Docker（部署整体缺失已列 P0）。

**改进建议（P1）**：后端补 ESLint（JS 最佳实践规则集）+ 至少路由/适配器单测。

## 五、正向工程实践补记（初版未单列，此处给正分）

1. **编辑器级一致性**：根 `.editorconfig` + 提交 `.vscode/settings.json`（`formatOnSave` + `source.fixAll.eslint`，工程规范 §8.1）→ 降低格式噪音。
2. **Node 版本硬锁**：新增 `.npmrc(engine-strict=true)` + `.nvmrc(22)` → 防协作者用 Node 20 静默偏离 `engines`。
3. **依赖可复现**：单根 `package-lock.json` + `npm ci` + `setup-node` cache → 优于多数学生项目。
4. **架构契约进 CI**：dependency-cruiser 自动证明 core/services/stores 不反向依赖 business。
5. **Cesium 懒加载是真决策**：vite 自定义插件摘掉 5.7MB 同步 script，运行时切 3D 才动态加载。

## 七、结论（面试视角）

这套工程底座**明显强于同阶段学生项目**：dependency-cruiser 架构契约进 CI、Cesium 懒加载的工程决策、Vite 分包策略、单根 lockfile + `.nvmrc`/`engines` 一致性、Node 版本硬锁（`.npmrc engine-strict`），都是能拿去讲"我怎么做工程化治理"的硬料。

**两块真实短板很清晰**：
1. **部署为零**——工程闭环断在"最后一公里"，优先级最高，半天就能补出 Dockerfile + nginx。
2. **测试是孤岛**——核心路径测了，但架构边界（adapter/store）没测，coverage 还没门槛，CI 测试环节形同虚设。
3. 叠加 **CI d.ts 隐患**（全新 clone 可能红 CI）与**后端零 Lint/零测试**，构成本轮最该立刻处理的清单。

**刻意设计不必改**：双引擎常驻、Cesium 单例、渲染器 DEV warn、manualChunks cesium 冗余分支、Element Plus 全量、JSON 存储、forecast 免认证——这些都能在面试时讲成"我主动做的工程决策"，反而加分。

把 P0 三件事 + P1 的 d.ts 托管落地后，工程化成熟度可从 ⭐⭐⭐ 拉到 ⭐⭐⭐⭐，且你能完整讲出"本地开发 → Lint/类型/架构契约卡点 → 测试 → 构建分包 → 容器化部署"的全链路。架构没有银弹，合适的才是最好的——上述建议均为经验性参考，不构成唯一正确决策。
