## 1. 数据真实吗？（🔴 最高危追问）

### 1.1 真相地图

| 模块 | 链路 | 数据性质 | 证据 |
|---|---|---|---|
| 选址 site-analysis | 前端 → `/api/site-analysis` → `backend/siteAnalysisService.js` 用 **turf.js 真算** buffer/intersect/评分 | **真功能 + 真实算法**；输入 POI 是真实钦州坐标 | `useSiteAnalysisApi.ts:24`；`项目根基.md §1` 技术栈含 Turf.js 7 |
| 预测 forecast | 前端 → `/api/forecast/*` → 后端读 `public/data/forecast/*.json` + `forecastEngine.js` 趋势外推 | **真后端链路，假数据**（静态 JSON + 部分 `Math.random()` 散射点） | `ForecastPage.vue:71`；`forecastEngine.js:116` |
| 浸没 flood | `floodAdapter` 直读 `public/data/flood-*.json`；`getDEM()` 返回**硬编码字符串** | **纯 fixture，无后端** | `floodAdapter.ts:140`；`getDEM` 直接 return 字面量 |
| 认证/方案/标注 | 后端 Express + `fileStore.js` 写 JSON 文件 | 真链路 | `backend/app.js:47-51` |

### 1.2 必须知道的矛盾（真实，但可防御）

- `forecastAdapter.ts` 全项目**零业务 import**（仅自身定义 + `mock/forecast/README.md` 引用）。预测实际直连后端 `/api/forecast`。
  → 但 **Adapter 模式本身是文档确认的刻意架构**（`项目根基.md §2.1` 列 `services/adapters/`，`§4` 整章讲 Renderer Adapter）。问题在于**这个具体实例没被接上**，不是模式错。
- `floodAdapter.ts` 所有 `'api'` 分支统一 `throw`（`:88/114/137/144`）。即 flood **没有真实后端路径**，"换 Adapter 接真实数据"对 flood 目前是空话。
- 选址模块**绕过 Adapter** 直接用 `useApiRequest('/site-analysis')`（`useSiteAnalysisApi.ts:7-27`）。

### 1.3 可防御讲法（强）

> "数据全部是示意性 mock，已在 `src/mock/` 三份 README、根 README、代码注释多层声明。mock 数据是真实北部湾地理坐标（港口名、钦州 POI 都是真实经纬度）。后端 Express 真在跑——选址用 turf.js 做了真实空间计算，这是真算法；预测/浸没的后端只是读静态 JSON + 简单外推，数据内容是 mock。Adapter 隔离是我们文档化的架构意图（Renderer Adapter 模式），目前 flood 真正走了 Adapter，forecast 当时直接走了后端、Adapter 实例没接上——这是实现不完整，不是架构错误。"

### 1.4 踩雷讲法（弱）

> ❌ "我们数据是真实的。" → 被要求看 DEM/吞吐量来源时露馅（`getDEM` 返回硬编码字符串）。
> ❌ "生产直接换 Adapter 就行。" → 被追问"forecast 的 Adapter 在哪被调用"答不上来（死代码）；被问 flood 的 api 分支实现也答不出（全 throw）。
> ❌ "后端是完整真实服务。" → 被问数据库，答出"JSON 文件持久化、无 DB"会显得措辞过度——但**这恰恰是文档确认的刻意简化**（`项目根基.md §12 反模式 6`："JSON 文件存储替代数据库是当前阶段的刻意简化"），所以正确答法是主动说"刻意简化"，而非回避。

## 2. 为什么这样设计？（设计合理性 + 追问预案）

> 以下每条都在 `docs/开工前必读/` 有**明确背书**，面试被问"是不是过度设计"时，直接引文档即可反杀。

### 2.1 双地图引擎（OL 2D 首屏 / Cesium 3D 动态 import）
**为什么**：渲染范式不同；Cesium 5.7MB 必须延迟加载。
**证据**：`renderers/index.js:55-67` 静态 OL + 动态 `import('./CesiumRenderer')`；`build2.log` 实证 CesiumRenderer chunk 13KB gzip 3.99KB，5.7MB 移出首屏。`项目根基.md §4.4` 明确"Cesium Viewer 首次创建后保留，离开 3D 只隐藏不销毁……任何设备都单例"。
**追问**："为什么不用 CSS Grid？" → 见 2.3。

### 2.2 BusinessLayerManager + 双图层读写分离（**初版误判已纠正**）
**为什么（文档原话）**：`项目根基.md §4.3` 明确——"`BusinessLayerManager` 是业务图层的**写入端**（注册/更新/移除，由业务页面用）；`useLayerManager()` 是 Shared 的 composable，封装对 `mapStore.layerCatalog` 的**读取端**（供 LayerControlPanel 消费）。两者操作同一数据源，**职责不重叠**。"
另：`§6.3` 区分 `registerToggleable`（可切换底图，LayerControlPanel 控制显隐）与 `registerBusinessLayer`（只记元数据，不做 toggle 的业务图层）。**这是职责划分，不是重复/迁移债。**
**初版错误**：我曾把"双图层机制并存"判为迁移债/过度工程——**错**。文档证明其是刻意读写分离。
**追问**："为啥不直接用 map 的 registerToggleable？" → 答："toggleable 管可切换底图，businessLayer 管只注册不切换的业务图层（如水面），读取端再由 useLayerManager 供通用面板消费，三者职责清晰。"

### 2.3 GCS Panel / PPS 布局（**初版误判已纠正**）
**为什么（文档原话）**：`项目根基.md §3` 设计哲学——"Canvas 是屏幕，Grid 是尺子，Cell 是单位，Panel 是一切"；不用 Header/Sidebar，所有元素浮在地图之上。`§3.4` 的 `panelPosition(w,h,anchor,offsetX,offsetY)` 即"PPS 定位"。
**80px 不是误称**：`config.js:2` `CELL_PIXEL=80` 是**默认值**；`getCellPixelByViewport`（`:11-16`）按视口返回 90/80/80/70/60，`§3.2` 表明确认"1024–1919 是默认区间，统一返回 80px"。响应式是**刻意设计**。
**追问**："为什么不用 CSS Grid / Element Plus 布局？" → 答："面板要叠加在 OL/Cesium canvas 上、且 2D/3D 切换时保持同一坐标系，CSS 栅格做不到跨引擎对齐；PPS 用 Cell 网格统一度量，是文档化的核心布局系统（`§9 硬约束`：GCS Panel 是刻意设计，不推翻）。"
**初版错误**：称"80px 栅格是误称""PPS 命名过度包装"——**错**。80px 是文档默认值，PPS 是文档术语。

### 2.4 Renderer 能力矩阵（**初版误判已纠正**）
**为什么（文档原话）**：`项目根基.md §4.2` 渲染器能力矩阵——热力图 **仅 OL**，水面 **仅 Cesium**，多边形/点/GeoJSON **双引擎都支持**。未实现的方法调用时返回 `false/undefined + DEV warn`，属"给框架加能力"（`§11.7`），不是不完整抽象。
**初版错误**：把"heatmap 在 3D 下 no-op + warn"判为"抽象契约不完整"——**错**，是文档规定的能力边界。
**追问**："Cesium 不支持热力图，抽象不统一？" → 答："`MapRenderer` 接口把引擎专属能力标为可选（`addWaterSurface?`），未实现的渲染器调用即 warn，新增能力走 §11.7 流程扩接口，不破坏框架。"

### 2.5 Pinia 状态管理
**为什么**：每业务模块独立 store，互不依赖；`gcsStore` 是聚合协调器（`§6.2` 规则 4 合法）。
**权威清单（`§6.1`）**：恰为 **8 个 store**——`mapStore / gcsStore / waterLevelStore / floodState / portImpactStore / profileStore / forecastState / siteSelectionState`。**"11 个"是旧记错误**，对外统一说 8 个。

## 3. 过度设计审计（v2 修订）

### 3.A 经文档确认为「刻意设计」——**不是过度工程**（初版误判，已剔除）

| 初版误判 | 文档背书 | 结论 |
|---|---|---|
| GCS "80px 栅格"是误称 | `§3.2` 表 + `config.js`：80 是默认区间值，响应式是设计 | ❌ 非误称 |
| PPS 命名过度包装 | `§3.4` PPS 是文档术语，整套布局系统有哲学 | ❌ 非过度 |
| 双图层机制 = 迁移债 | `§4.3`/`§6.3` 读写分离 + toggleable/businessLayer 职责划分 | ❌ 非债 |
| polygon 适配器 = YAGNI 死代码 | `§4.2` 渲染器矩阵：多边形双引擎✅；`layerAdapters.js` 注册与 `OLRenderer/CesiumRenderer` 的 `addPolygonLayer` 实现一致 | ❌ 是文档支持的框架能力（当前无业务注册，但属合理扩展点，不应删） |
| heatmap 3D no-op = 不完整抽象 | `§4.2`/`§11.7`：heatmap 仅 OL，3D 调用即 warn 是规定行为 | ❌ 非不完整 |
| GcsInspectionOverlay = dev-only 死重 | `工程规范.md §5.4 反模式4 例外`：inspection toggle 是开发调试工具色，可保留硬编码 | ❌ 非死重 |
| JSON 文件存储 = 后端缩水 | `§12 反模式 6`：JSON 替代 DB 是刻意简化 | ❌ 非缩水 |
| mapStore god-store = 坏味道 | `§6.2` 明确"analysisHandler 累积是已知设计取舍（见待解决问题 A02/A04）" | ❌ 已知取舍 |

> **关键教训（给 HappY）**：面试前**先读 `docs/开工前必读/`**。本项目有大量"看似过度、实为刻意"的设计，文档都写明了。把刻意设计当过度工程讲，反而暴露你没读文档。

### 3.B 仍为真实问题（代码现实 ≠ 文档意图/实现）

1. **🔴 `forecastAdapter.ts` 死代码**（零业务 import）
   虽 Adapter 模式是刻意架构，但这个**具体实例没被任何业务接上**，预测走后端直连。建议：要么在预测模块接入 `forecastAdapter`（让"mock/api 切换"叙事成立），要么从文档/代码移除该实例，避免"架构叙事与实现脱节"。

2. **🔴 `floodAdapter` 的 `api` 分支全 `throw`**（`:88/114/137/144`）
   flood 没有真实后端路径，"替换 Adapter 接真实数据"对 flood 是空话。建议：至少在文档注明"flood 当前仅 mock，无 api 实现"，别让面试官以为 api 分支可用。

3. **🟡 选址模块绕过 Adapter 直连 `useApiRequest`**（`useSiteAnalysisApi.ts:7-27`）
   三模块中仅 2 个用 Adapter，约定不一致。建议：统一接入或文档说明"选址走直连是因为它需要 POST 复杂参数体，Adapter 接口暂不适配"。

4. **🟡 `createPersistedState` 工厂仅 1/2 采用**（`siteSelectionState.ts:22` 用，`floodState.ts:72-115` 仍内联重复）
   半成品抽象，轻微重构债。建议：把 floodState 也收口到工厂，或删工厂回归内联（二选一，别半吊子）。

5. **🟡 Turf.js：文档意图 ≠ 前端代码现实**
   `项目根基.md §1` 把 Turf.js 7 列为技术栈、`工程规范.md §4.2` 给了前端 turf 示例，但前端 `src` 对 `turf` 的 import **零匹配**（仅后端 `siteAnalysisService` 真用）。属"文档领先代码"。
   讲法："`turf` 在后端 site-analysis 做真实 buffer/intersect 评分；前端当前用 rbush 视口裁剪 + 坐标校验，客户端 turf 精确过滤在规范里已规划、尚未安装"——诚实且成立。

6. **🟡 性能文档数字漂移**
   `工程规范.md §二` 仍写 `ui-vendor 320KB gzip`、首屏 `~1.9MB`；但 Element Plus 改按需后真实构建为 `ui-vendor 116KB gzip`、首屏 `~480KB`（见 `docs/首屏分包分析.md` 落地版）。文档未同步。
   讲法：直接报真实数字（116KB / ~480KB），并说明"工程规范文档的性能章节待更新"。

## 4. 性能是否证明？（性能证据审计）

### 4.1 ✅ 真实落地、有文档+日志双重佐证（构建体积维度）
| 优化 | 证据 |
|---|---|
| Cesium 5.7MB 懒加载 | `renderers/index.js:64` 动态 import；`工程规范.md §二/§五`：首屏 7.5MB→1.9MB（↓75%）；`build2.log` CesiumRenderer 13KB chunk |
| 路由级懒加载 | `router/index.js:8-35` 全部 `() => import()` |
| manualChunks 分包 | `vite.config.js:80-95`；`build2.log` 独立 chunk |
| R-tree 视口裁剪 | `OLRenderer.js:113-187` |
| echarts/core 按需 | 仅预测/浸没/选址路由加载 |

### 4.2 ❌ 完全缺失（运行时维度）
- 零运行时度量：grep 全仓 `lighthouse|web-vitals|LARGEST_CONTENTFUL|CLS|FID` 零匹配。`工程化审查报告-2026-07-28.md:128` 自述"无客观性能度量……'性能 OK'靠体感"。
- 无 CI 体积卡点：`build:analyze` 手动，Cesium chunk 超 `chunkSizeWarningLimit` 仅告警。
- 无图片优化（grep `webp|avif|loading="lazy"` 零匹配，影响有限，因以矢量/GeoJSON 为主）。
- 无 PWA / Service Worker（grep `service-worker|manifest` 零匹配）；Cesium 5.7MB 本可 SW 预缓存改善二次访问。

### 4.3 讲法
**强**："构建体积优化有文档和构建日志双重佐证——Cesium 懒加载把首屏从 7.5MB 降到 ~1.9MB（按需后实际 ~480KB gzip），分包和视口裁剪都有日志。但**运行时我没做 Lighthouse/Web Vitals 度量**，这是已知缺口，面试后补一个基线。"
**弱**：❌ "Lighthouse 95+"（现场跑不出）。

## 6. 给 HappY 的整改建议（按优先级）
