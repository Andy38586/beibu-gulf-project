## §1 项目身份与目标

**北部湾港智慧选址分析平台**——面向智慧港口场景的 WebGIS 业务应用，验证"可扩展的 GIS 系统架构"而不是可视化 Demo。

- **目标**：最终是**有交付能力的产品**。当前阶段是工程化搭壳；以毕业论文为节点注入真研究（新选址分析 + 学术因子），同时作为求职作品集。
- **四类业务**：选址分析（2D 空间运算）、预测分析（趋势可视化）、浸没分析（3D 淹没演算）、路径分析（路网最近路径）。现有业务为未来的**新选址分析**铺垫：浸没、吞吐量预测是前哨。
- **已知未完成板块**：预测真模型（当前为合成示意数据）、真实海底 DEM、航线密集度分析。
- **诚实性口径**：合成指标（确定性种子生成的示意数据）是当前阶段的已知妥协——已标注、面试主动讲，不回避也不自贬。
- **阶段判据**：演示可用；距产品化差**真实用户**与**真实业务**两大鸿沟。

## §3 系统架构

### 3.1 分层（L0-L8，单向依赖）

```
L0  types          纯类型声明（零运行时依赖）
L1  shared         通用工具 / composable / 常量 / 基础组件
L2  stores         Pinia 全局状态
L3  services       数据访问（adapter / API 封装）
L4  visualization  通用图表资产
L5  core           地图核心 + 布局基座
L6  business       业务模块（互不依赖，manifest 注册）
L7  views          页面装配
L8  入口            main / router / App
```

- 铁律：**低层不得依赖高层**；`types/` 零运行时依赖；业务模块之间禁止互引。依赖方向由 `npm run cruise` 强制守护。
- 已知的设计确认例外（core→stores、core→services 等）在 K2 登记；例外只能登记，不能默认。

### 3.2 双引擎（Renderer 抽象）

- 2D/3D 引擎 API 完全不同 ⇒ `MapRenderer` 抽象接口 + OL/Cesium 各一实现；业务只经接口操作地图，引擎切换业务零改动。
- 低功耗、低需求用 2D；有 3D 需求时优先 3D；Cesium 太重，不常驻。
- 单引擎专有能力（如水面）拆独立能力接口，调用方**能力检查后**使用；禁止空实现 stub。

### 3.3 请求路径（总览，细则见 K2/K3）

```
业务组件 → 取数入口（useApiRequest / loadStatic）
  ├─ 静态资源 → loadStatic（前端托管的真数据，不是 mock 契约桩）
  └─ 后端接口 → fetch → Nest /nest-api/*
后端：modules → controllers → services → repositories（PostGIS）
      + data-files.service（静态 JSON）
异步长任务：POST /nest-api/task → 后端 task 域排队计算 → 前端 taskStore + dock 槽位轮询/回收
```

- 数据源模式是**演进路径**而非平行实现：mock 契约桩 → Nest 单模式（当前）。栅格服务（GeoServer）待规模需要时引入。
- 前端取数规则（R1-R5）、后端响应规则（R6-R8）、各业务主流程细则在 K2，本文不复述。

## §4 目录职责地图

> 新代码去哪、哪儿不许放，以本表为准。三条禁则：**types 零运行时**、**core 不写业务**、**business 不互引**。

| 目录             | 负责                                                                                       | 禁止                                                           |
| ---------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `types/`         | 全局类型契约（业务模型 / 组件 Props / 渲染器接口）                                         | **零运行时代码**（函数、常量放 shared）                        |
| `shared/`        | 跨业务复用：通用组件 / composable / 工具 / GCS 布局基础设施                                | 依赖高层（core/stores/business）                               |
| `stores/`        | Pinia 全局状态（统一 Setup Store 语法，`useXxxStore`）                                     | 业务专属逻辑；页面内临时状态                                   |
| `services/`      | 数据访问：adapter / API 封装 / 静态数据服务                                                | 业务规则                                                       |
| `visualization/` | 通用图表资产                                                                               | 业务耦合                                                       |
| `core/`          | 地图引擎层 + 布局基座（renderers / BLM / GCS 面板）                                        | **写业务逻辑**（选址、预测、浸没一律进 business）              |
| `business/`      | 业务模块（互不依赖；模块集合由 `cruise-coverage` 守卫从目录派生，文档不抄清单）            | **模块互引**（经 manifest 注册，禁止直接 import 其他业务模块） |
| `views/`         | 通用页面装配（Home / Profile）                                                             | 业务实现                                                       |
| `backend/`       | NestJS 分层：`modules/<域>/{controllers,services,repositories,dto}` + `common/` + `infra/` | controller 写算法；DB 访问收口在 repositories                  |

## §5 工程红线（不变量）

- `npm run cruise`（含 backend）0 violation；前后端测试全绿；HTTP 边界 100% zod 校验。
- **禁止把会过时的信息写进规范文档**：具体清单 / 行号 / 覆盖率数字 / 版本 —— 规则进契约、状态进台账、数字进执行体。
- 改代码前必读 K1（技术规则集，源自 04）：它是从已归档问题归并出的"不要再犯"规则集；同类问题第 2 次出现时在 K1 追加规则（首次只修，不立规）。
- 任何"已 X"宣称必须同时给出产物级依据与**失效条件**（细则见 C2）。
- 面试口径：分层 / 数据流 / 类型安全是硬能力；合成指标是已定性的诚实项。
