# C3 · 信息源宪法（三层文档体系）

> **层级**：宪法（无时效、罕改、改动需用户批准）
> **定位**：规定"知识放在哪一层、谁是权威、什么时候读、什么时候回写、旧件怎么退役"。
> **拥有的权威事实**：三层定义 / 时间戳规则 / 权威切换规则 / 退役规则 / 读写矩阵规则 / 登记与守卫规则。
> **读者**：所有 agent 与维护者。
> **何时读**：按 `AGENTS.md` §二的矩阵进入任何任务之前；任何文档新增、改名、退役之前。
> **何时回写**：仅在本文件被用户批准修改时；变更记入文末变更记录，不写入正文日期散点。
> **最近复核**：2026-10-05

## §1 三层定义

| 层       | 性质                 | 判定问题                        | 变更规则                                                                   |
| -------- | -------------------- | ------------------------------- | -------------------------------------------------------------------------- |
| **宪法** | 无时效、罕改         | "推翻它 = 换项目方向？"         | 用户批准才可改；改动留决策记录；正文不写会过时的数字/清单/行号             |
| **契约** | 当前有效、随项目演进 | "改它 = 改现行规则/接口/流程？" | 允许改；**每次改必须追加当日变更记录**；被取代的版本全文快照进日志，不删除 |
| **日志** | 带时间戳、只增不改   | "它是当时发生了什么？"          | **禁止改写**；过时不是错误，是记录本身；新事实追加新条目/新文件            |

判定顺序：先问"它会不会随代码/时间变化"——会变且是**现行应然**的进契约；会变且是**当时事实**的进日志；不变的是宪法。

## §2 时间戳规则

- **契约**：头部必须有 `最近复核：YYYY-MM-DD` 与 `## 变更记录`；变更记录按 `YYYY-MM-DD 一句话` 追加。守卫按"最近一条变更记录日期 ≥ 该文件最后一次提交日"核对。
- **日志**：文件名或头部必须带日期（`YYYY-MM-DD`）；滚动档（如接力状态）允许用登记表 `ts` 字段承载时间戳。
- **宪法**：不强制正文日期；每次变更落一条决策记录即可。

## §3 权威切换（迁移期，按知识点）

1. 迁移期以 `tools/doc-system/kp-map.json` 为唯一口径：每条知识点（KP）标注 `authority = old | new` 与目标文档。
2. **被新文档覆盖的 KP 以新文档为准；未被覆盖的 KP 仍以旧文档为准**。同一 KP 不允许两个权威。
3. 旧文档在并行期**只读**（仅允许追加"并行期"横幅与路径映射）；内容冲突时以 kp-map 登记为准。
4. 未经用户批准，任何旧文档**不得删除、不得清空、不得隐式改名**。
5. KP 抽取的输入是基线快照 `tools/doc-system/baseline/<旧路径>.frozen`（基线 commit、逐件 sha256 见 `manifest.json`）。快照**只读、非权威**；以 `.frozen` 结尾＝冻结工具数据而非文档层 Markdown（故不参与"协议表头全仓唯一"扫描），得用 `git hash-object` 逐字节复核。旧文档在迁移期被加横幅/移动都不会改变 KP 表（表只认快照）。

## §4 退役规则

- 退役条件：某旧文档的全部 KP `authority=new` 且 `npm run docs:check` 绿。
- 退役流程：生成《可退役清单》→ 用户批准 → 旧文档整体移入 `docs/日志/退役/`（保留全文）→ 登记表翻 `retired`。
- 禁止：以"过时"为由直接删除；以"合并"为由覆盖旧内容；退役未经批准即从阅读入口摘除。

## §5 读写矩阵

- 人读入口 = `AGENTS.md` §二 的"任务→必读→回写"表；机读入口 = `tools/v3-guard/lib/doc-map.json` 的 `tasks[]`。
- 两处必须双向一致（任务码集合、必读/回写目标）；由 `doc-map-check` 守卫强制。
- 新增任务类型必须两处同时登记，否则视为流程未完成。

## §6 登记与守卫

- `docs/宪法/`、`docs/契约/`、`docs/日志/` 下**每个 tracked 文档**必须登记在 `doc-map.json`；未登记即红。
- 新文档先以 `planned`/`stub` 登记再创建/填充；迁移结束后 `stub` 与 `planned` 必须清零（由 `meta.migrationOpen` 闸门强制）。
- 守卫：`tools/v3-guard/doc-map-check.mjs`（挂 `guard:v3` 快集 + CI）；红样四类常驻：未登记文档 / 双权威 / KP 无目标 / 契约缺当日变更记录。
- 登记表 `facts[]` 记录"同一事实的当前权威 + 派生点 + 守卫"，是 RC1（单一事实源）的机器载体。

## §7 与其它权威件的关系

- `AGENTS.md` = 作业协议正本（纪律 + 矩阵）；本文件 = 文档体系宪法。冲突时：**纪律以 AGENTS 为准，文档归类与权威切换以本文件为准**。
- 技术规则以 `K1` 为准；审查标准库（`docs/根基文档/审查体系专项/`）是契约层的既有子域，本轮不改内容，只登记。
- `CLAUDE.md` 只是指向 AGENTS 的指针，不复制条文。
