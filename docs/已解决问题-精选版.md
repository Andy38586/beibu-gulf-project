## 1 · `a003+a013+a014+a022` — 双引擎业务图层生命周期治理链

**问题原因（溯源）**
项目采用 OpenLayers(2D)+Cesium(3D) 路由级切换的双引擎架构，但**图层生命周期管理的职责从第一天起就是分散的**，这是整条链的根因：
- 业务页（SiteSelectionPage）直接调 `renderer.addPointLayer / removeLayer / registerToggleable`，**绕过 BusinessLayerManager**（a014）——出现「业务页自己管一层、Manager 管一层」的双轨。
- 跨路由卸载时只清了局部图层，没清 `analysis-coverage / analysis-matched` 与设施 POI，**跨路由残留**（a013）。
- 最根本的设计缺陷（a003 埋下，a022 暴雷）：`reapplyAll` 依赖 `mapStore.layerCatalog` 找业务条目，而引擎切换时 `UnifiedMap.setupLayers→clearLayers→clearLayerCatalog()` 把整个 catalog 清空（`layerCatalog.value=[]`）；异步 watch 触发 `reapplyAll` 时目录已空 → `find` 找不到 → `continue` 跳过 → 业务图层**永久丢失**。`App.vue:99` 注释写着「修复 D06」实为未修的回归。
- 本质：**没有一个单一事实源记录「业务图层注册了什么、当前可见吗」**。状态散落在 renderer 私有字段、组件局部变量、可被清空的 catalog 三处，引擎/路由任一动作都让三者失同步。

**解决方法（详述）**
建立 **BusinessLayerManager 作为图层写端单一事实源**，引入 `_registry`（register 时存 `visible`，`setVisible` 时同步）：
- a022（2026-08-02）：`BusinessLayerManager.reapplyAll / setVisible / updateData` 全部改读 `_registry.visible`，**不再依赖会被清空的 `layerCatalog`**；补 2 个回归测试（catalog 清空后仍重绘 / 不可见图层不重绘）。前端 106 测试全绿。
- a014：`SiteSelectionPage` 的 `handleShow/HideFacilityLayer` 统一改走 `businessLayerManager.register/remove`，删除 `useLayerManager` 死引用，图层生命周期归一。
- a013：`SiteSelectionPage.vue:onUnmounted` 把 `handleHideFacilityLayer()` 换成 `clearAnalysisLayers()`（已含 analysis-coverage/matched 移除 + 设施 POI），零副作用。
- a003（早期）：`BusinessLayerManager.js:115` 持久化 data、`:142` 落地 `reapplyAll`、`App.vue:103` watch `currentRenderer` 调 `reapplyAll` 的框架在此奠定。
- 验证：前端 106 测试全绿。**业务场景**——2D↔3D 切换后业务图层不丢、跨路由往返无残留图层、组件卸载后零泄漏。

## 2 · `a016+a007+a005+a010+a011+a012+a018+z007` — 渲染器抽象与双引擎集成

**问题原因（溯源）**
渲染器层（`OLRenderer` / `CesiumRenderer` 继承 `MapRenderer` 基类）的缺陷源于**抽象边界不清 + 单测缺位**：
- `MapRenderer` 基类声明了 3D-only 方法，OLRenderer 不实现，约定靠文档口头说明（后来 z006 文档化，但仍非强制）——接口契约弱。
- `UnifiedMap.setupLayers` 直接读 `renderer._layers` **私有字段**（a007），破坏封装，渲染器内部改名即崩。
- Cesium 细节散雷：`addGeoJsonLayer` 给 `entity.properties.featureType` **未判空**（a005）；点图层 entity id 重复 `-undefined` 崩溃（a010）；`creditContainer` 隐藏版权隐患（a011）；直写外部单例私有 `_baseLayers`（a012）。
- **最隐蔽的根因（a016）**：OLRenderer 裁剪集成路径（`_addCulledPointLayer / _refreshCulledLayer / moveend` 增量刷新）**无专属单测**，补测时逮出 2 个潜伏真 bug——①`import Map from 'ol/Map'` **遮蔽全局 `Map`**，导致 `_cullLayers = new Map()` 误建 ol/Map 实例（moveend 遍历 `.keys()` 会崩）；②`_removeCullLayer` 定义了从不调用，`removeLayer` 不清理 `_cullLayers`、moveend 监听永不解除。
- 文档与代码对撞（a018+z007）：代码已落地 Cesium idle-destroy（30s 空闲 `viewer.destroy()`），但 `项目根基.md §4.2` 仍写「单例不销毁」，文档滞后于实现。

**解决方法（详述）**
- a016（2026-08-01）：①`OLRenderer.ts` 的 `import Map` 改名 `OlMap`，消除全局遮蔽；②覆盖基类 `removeLayer` 先清理 `_cullLayers` 并解除 moveend 监听。补 `__tests__/OLRenderer.culling.test.ts`（13 测试：阈值路由 / 初始裁剪 / moveend 增量 / 监听生命周期 / 空边界，mock ol/Map + 真实 rbush）。
- a007：`UnifiedMap.vue:195-201` `hasLayer` 优先用公开 `renderer.hasLayer(id)`，私有访问封装化。
- a005：`CesiumRenderer.js:642-643` 赋值前 `if (!entity.properties) entity.properties = {}`。
- a010：`CesiumRenderer.js:442` id 兜底 `` `${id}-${item.id ?? item.name ?? index}` ``。
- a011：移除 `creditContainer`，恢复默认 credit 容器（合规）。
- a012：`_baseLayers` 仅内部使用 + `renderers.d.ts` 已有公开 `setBaseLayers/getBaseLayers`，改用公开 API。
- a018+z007（2026-07-30）：更新 `项目根基.md §4.2` 为「Cesium Viewer 生命周期规则」、§4.4 引擎切换链路，写明 idle-destroy 机制 + trade-off，文档与代码对齐。
- 验证：前端 106 测试全绿。**业务场景**——2D 裁剪监听引擎切换后无残留回调、Cesium 版权合规无 attribution 缺失、3D 空闲 30s 后 WebGL 上下文自动释放。

## 3 · `b008+b021+b022+b024+b005+b011+b012+d013` — 数据层 Adapter 隔离与多源策略统一

**问题原因（溯源）**

- `floodAdapter` 模块顶层直接 `useApiRequest`（b008 反模式）——组合式函数在模块作用域误用。
- flood 的 api 分支仍 `throw('真实 API 尚未接入')`（b021），mock 改读 `/data/*.json` 但 api 模式未闭环，设计预留成了断头。
- 三模块数据源策略三套：forecast adapter 默认 `'api'`、flood 默认 `'mock'`、site-analysis 又一套（b022）；且无 `import.meta.env` 读取，全靠手动 `setDataSource`（b024）——dev 无后端时 Forecast 直接跑不通。

- **架构级反向依赖（d013）**：后端直接依赖前端静态目录（7 个预测 JSON 放前端），前后端数据边界颠倒。

**解决方法（详述）**
确立 **Data Adapter 隔离层 + env 驱动切换**为单一事实源：
- b008：移除 `floodAdapter` 顶层 `useApiRequest` 反模式。
- b021：`floodAdapter.ts:224-275` api 分支实装 `apiRequest('/flood/flood-areas?waterLevel=…')` + 影响评估 POST，不再是 throw，api 模式闭环。
- b022+b024：新增 `VITE_DATA_SOURCE`（默认 `mock`），`main.ts` bootstrap 读 env 调 `setDataSource`；两 adapter 统一 `setDataSource`，默认全 mock，dev 无后端也能跑。
- b005：`forecastState.ts:30` `dataCache: ShallowRef<Map>`、`:52-57` `cacheData` 正确 get/set。
- b011：`floodState.ts` 全量 `createPersistedState` 封装，`floodPolygons` 改 `shallowRef([])`。
- b012：`cacheData(time,data)` 入参收窄为 `ForecastSeries`，`dataCache` 改 `shallowRef(new Map())`。
- d013：7 个预测 JSON 迁至 `backend/data/forecast/`，前端 mock 夹具独立保留，前后端数据边界归位（解除反向依赖）。
- 验证：前端 106 / 后端 112 测试全绿。**业务场景**——无后端时前端一键 `npm run dev` 即跑通全模块；切换 `VITE_DATA_SOURCE=api` 后 forecast/flood/site-analysis 三模块数据源策略一致。

## 4 · `d020+d038+d048+d049+d033+d036+d022+d003+d010+d044+d008+d032+d037+d043` — 全链路安全加固

**问题原因（溯源）**
认证与接口安全是「边建边改」长出来的，漏洞成链，根因是**安全设计后置——先做功能可用，令牌/密钥/输入校验/审计全靠事后补**：
- **令牌无吊销**（d020）：logout/改密后旧 token 仍有效 7d——设计初未引入 `tokenVersion` 校验。
- **响应体回传 JWT**（d038）：登录/注册返回 `{token,user}`，削弱 HttpOnly Cookie 收益，XSS 可读响应拿 token 绕过 Cookie。
- **密钥泄露两连**（d048+d049）：`frontend/.env` 曾提交真实 `VITE_TIANDITU_KEY`（d048）；`.dockerignore` 未排除 `.env*`，Dockerfile `COPY backend/` 把含 `JWT_SECRET` 的 `.env` **烤进镜像**（d049）——密钥进 git 历史 / 进镜像即泄露。
- **认证恢复依赖 localStorage**（d033）：`restoreAuth` 仅当 localStorage 有 user 才调 `/auth/me`，与 HttpOnly Cookie 主通道不一致。
- **鉴权边界漂移**：`gcs` 路由全裸（后改名 `/flood`，d022）、双认证矛盾（同时发 Bearer+Cookie，d003）、路由守卫依赖内存 token（d010）、剖面面板直连 flood API 与免登录主页分裂（d036）。
- **公开路由暴露路径遍历**（d008→d032）：d008 决策移除 `forecast.js` 的 `authenticate`（与设计文档 4 处声明一致），但**公开路由 + 无输入白名单 + 路径拼接**的组合直接暴露路径遍历——`forecastService` `engineCache` 无上限，`ENOENT` 被当假成功，攻击者可用 `../` 遍历文件系统。这是 d008 决策的连锁安全债。
- **注册爆破 + 无审计**（d037+d043）：`/register` 仅吃全局限流无专属 limiter（登录有 max5），可被爆破；成功操作无审计日志，安全事件不可追溯。
- **git 历史残留**（d044）：users.json 明文测试/探针账号在 git 历史未清理。

**解决方法（详述）**
以「**HttpOnly Cookie 为唯一令牌通道 + 版本化吊销 + 密钥零落盘 + 公开路由输入加固 + 审计可追溯**」全链路重构：
- **令牌与密钥**：
  - d020：`users.json` 加 `tokenVersion`；`middleware/auth.js:53-70` 校验版本；`authController.js:105-106` logout 自增。
  - d038：`authController.js` 响应仅 `{user}`，token 仅 `Set-Cookie`（HttpOnly），响应体不再回传 JWT。
  - d048：`.env` 仅占位 `your_tianditu_key_here`，已 gitignored + 未跟踪，无真 key 入版本库。
  - d049（2026-08-01）：`.dockerignore:16-18` 排除 `backend/.env` + `backend/.env.*`；`Dockerfile:32` `ENV NODE_ENV=production`；`docker-compose.yml:15-16` `env_file` 运行时注入——三重防护。
- **认证通道统一**：
  - d033：`useAuth.ts` `restoreAuth` 始终调 `/auth/me`（Cookie 为权威），不再以 localStorage 前置。
  - d022：`/api/flood/*` 加 `router.use(authenticate)`。
  - d003：`useApiRequest.ts:56` 注释明确只发 HttpOnly Cookie（`credentials:'include'`），不发 Bearer；grep 无残留。
  - d010：路由全公开、后端为真网关，设计变更后内存 token 前置已不存在。
  - d036：`/flood/terrain-profiles` 注册在 `authenticate` 之前→公开，与 mock/d008 一致（只读数据默认开放）。
- **公开路由输入加固**（d008 决策的连锁债）：
  - d032（2026-07-30）：`forecastService.js` 加 `ALLOWED_INDICATORS` 白名单（throughput/berth/traffic/pressure/development）+ `..` 拒绝 + `validateIndicator()` + `MAX_CACHE_SIZE=100` + `ENOENT→BusinessError(NOT_FOUND)`；3 测试更新。
  - d037：`app.js:37-42` `registerLimiter` 挂 `/api/auth/register`，注册限流。
  - d043：`backend/utils/logger.js` 新增 `audit` 方法（生产保留）；`authController.js` register/login/logout 三处加 `logger.audit` 记 `userId+ip`。
- **git 历史清理**：
  - d044：建 `tools/git-clean-history.sh`（git filter-repo + 前置检查 + 确认交互），标注上线前手动执行、不可逆不自动跑。
- 验证：后端 112 测试全绿。**业务场景**——logout 后旧 token 立即失效（改密后其他设备被踢）；响应体无 token；`.env` 不在镜像 layer 里（`docker history` 可验）；`../` 路径遍历被白名单拒绝；注册接口受限流保护；关键操作有审计日志可追溯。

## 5 · `a004+d015+a006+d057+d056+b009` — GIS 空间数据正确性

**问题原因（溯源）**

- `markers` 坐标只查 `!== undefined`（d056），NaN/字符串/越界可入库，污染后续空间计算。
- 浸没分析 `AffectedFacility` 字段名未统一 `lng/lat`（b009）。

**解决方法（详述）**
建立 **坐标单一事实源 + 空间索引统一复用**：
- a004：`mapDataService.ts:5` 导入、`getPorts():63` 调 `isInBeibuGulf` 过滤越界港口。
- d015：`types/crs.ts` `normalizePoint` 统一 `lng/lat` + 兼容 `lon/longitude`。
- a006：`OLRenderer.js:17` 导入，`addHeatmapLayer:348 / updateHeatmapLayer:395` 改用 `normalizePoint`。
- d057（2026-08-02）：`filterFacilitiesInCoverage` 改用 `createSpatialIndex + queryByPolygon`（bbox 粗筛+精确判定），与 `filterMatchedXiaoqu` 对齐；新增 `filterFacilitiesInCoverage.test.js`（5 测试，含与逐点法等价性回归）。
- d056（2026-08-02）：`markersController` createOne/updateOne 补 `Number.isFinite(Number(lng/lat))` + 范围校验（lng∈[-180,180]、lat∈[-90,90]），字符串坐标转数值入库（M-01）；markersController 测试 5→9。
- b009：`floodAdapter.ts:164-165` 归一 `lng/lat`（兼容 `longitude/latitude`）。
- 验证：后端 112 / 前端 106 测试全绿。**业务场景**——越界港口被过滤不出图；热力图坐标不再错位；设施与小区筛选共用 rbush 路径结果等价；markers 非法坐标（NaN/字符串/越界）被 400 拒绝。

## 10 · `z001+z005+z019+c016+c022+a017` — GCS 设计系统统一

**问题原因（溯源）**
GCS（Global Component Style）是项目自研布局体系，其「不统一」根因是**设计系统早期缺失，样式随组件野蛮生长**：
- CSS 变量体系缺失（z001），`#409eff` 散落 19 文件；硬编码 hex ~71 行（z005）——无全局 Token，各组件自写颜色字面量。
- GCS 命名大小写不一（z019）：残留小写 `gcs` 标识符（`GcsFeature / .gcs-panel`），违反 GCS 全大写铁律——命名约定靠口头，无 typecheck/build 强制。
- `!important` 反杀（c016）：GCSPanel 内联写死定位，外部覆盖只能靠 `!important`——组件未输出 CSS 变量供外部定制。
- 变量层漏网（c022）：`GCSPanel.vue` CSS 变量用小写 `--gcs-panel-*`，违反 `--GCS-*` 全大写——z019 归一了标识符但漏了变量层。
- z-index 无刻度（a017）：各组件随意写数字导致遮挡混乱——无层级 Token，z-index 通胀。

**解决方法（详述）**
建立 **GCS Token + 全大写铁律 + 单一事实源**：
- z001+z005：建立 `--GCS-*` 全局 Token，核心/共享组件改用 `var()`；硬编码 hex 收敛至 `shared/constants/colors.ts`（RISK/FACILITY/CHART/LAYER_DEFAULTS/PROFILE/INSPECTION/FLOOD_RISK_COLORS）。
- z019（2026-07-30）：全量归一 `GCS`（9 文件 28 处），`typecheck` 0 错、`build` 通过。
- c016：GCSPanel 改输出 CSS 变量（`--gcs-panel-left/top/width/height`），scoped style 消费，外部 `:deep(.GCS-panel)` 覆盖变量即可，无需 `!important`。
- c022（2026-08-02）：6 个变量改名 `--GCS-panel-*`（声明+消费同步），typecheck 0 错。
- a017：`style.css :root` 新增 `--GCS-z-*` 刻度令牌（map/overlay/status/panel/float/drawer/modal/message）。
- 验证：代码 `(?i)gcs` 残留 0；CSS 变量全大写合规；typecheck 0 错。**业务场景**——全站配色改一处 Token 即生效；GCSPanel 定位可通过 CSS 变量覆盖无需 `!important`；z-index 按刻度令牌分配无遮挡混乱。
