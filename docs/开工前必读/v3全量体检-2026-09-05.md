## 一、P1 真 bug（1 项）

### 1. 航线分析里程显示放大 1000 倍（米当千米）
- **证据链**：`backend/algorithm-service/route/graph.py` find_path 返回 `"distanceM": round(distance_m, 1)`，distance_m 由 `weight_m`（= roads.length_m，米）累加；路由层 `route/__init__.py` mode 参数描述自证「distance=距离（米）」；`frontend/src/types/schemas.ts:352` `distanceM: z.number()` 无转换。
- **错误点**：`frontend/src/business/route-analysis/RouteAnalysisPage.vue:53` → `里程 ${distanceM.toFixed(1)} km`（113.9km 的钦州港→北海会显示 "里程 113900.0 km"）；`:60` totalDistanceText 同错（米+米标 km）。
- **为何测试没抓住**：useRouteApi/后端单测只校验形状，`durationMin`（分）恰好显示正确，量纲错误漏网。
- **修法**：展示层除以 1000（或后端改返回 km，二选一，注意 `snapDistanceM` 是米需同步）。

## 二、P2 功能性缺陷（1 项）

### 2. App.vue 的 DEM 暖机请求完全无效
- **证据链**：`frontend/src/App.vue:178-185` 启动 +6s 调 `/flood-online/api/flood/online?waterLevel=0`，注释宣称「触发 FastAPI load_dem 模块加载，首次真实演算免等」。
- 但 `backend/algorithm-service/flood.py` flood_online：`key = _level_key(0 - datum_offset())` = `_level_key(-2.5)` = **-2.5**，`key < 0` 走提前返回分支（「物理无淹没，直接回空，不触发 DEM 加载」）——**load_dem 永远不会被这次请求触发，暖机是空转**。
- **修法**：暖机请求改用 `waterLevel` 使 EGM96 键 ≥ 0（如 waterLevel=3 → 键 0.5，命中预计算表、且查表路径本身也不触发 load_dem——若目标是预热 DEM 引擎，需直接打会走 `_engine_module()` 的档位，或 FastAPI 侧提供显式 /warmup 端点）。

## 五、可接管性评估

**优（可放心交接的部分）**：

- 代码卫生：全仓生产代码 TODO 仅 1 处（OLRenderer.ts:705 且合法）；裸 `as any` 为 0，类型断言均带注释与理由。

**劣（交接前应补的坑）**：
- **本地启动链断裂**：`package.json:31-32` dev:all = vite+nest+algorithm，**不含 PostGIS**（在 docker-compose.v3.yml）；auth/plans/favorites 三模块启动即 ECONNREFUSED。新人按 README 直觉起服务会撞墙。建议 dev:all 前置 `docker compose -f docker-compose.v3.yml up -d postgis` 或 README 醒目声明。
- 第三节 8 项注释漂移会系统性误导新人（尤其 jwt.util 找不到 .env、flood_engine 内存差 14 倍）。
- `spatial-index.ts` 前后端同名不同语义（前端=视口裁剪/后端=多边形查点），文件头有自警注释，但 IDE 跳转会先踩坑。
- 施工「为什么」的日志在桌面目录（不进 git），仓库内只有结果（手册状态表）——新人能知道「做了什么」但难知道「为什么这么做」。

## 六、跨端语义差异（登记不修）

- 淹没判定边界点语义：Python `compute_impact` 用 shapely `poly.contains(pt)`（边界不算）vs Nest `flood.service` 用 `turf.booleanPointInPolygon`（边界算内）。设施点恰在淹没边界时双端结论可能相反；当前 25 个 curated 设施点实际风险极低，登记备查。
