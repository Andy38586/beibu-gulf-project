## 1. 核心原则

记住这三条，规范的其余部分是它们的展开：

```
1. 地理术语优先于通用术语
   lng/lat（不是 lon/lat） ｜ elevation（不是 altitude） ｜ feature（不是 item） ｜ crs（不是 coordSystem）

2. 代码自解释，注释写"为什么"和"地理背景"
   不写 "// 遍历数组"
   写 "// 北部湾区域存在大量凹多边形，turf.union 可能返回 MultiPolygon，需降级处理"

3. 双引擎思维渗透到命名
   凡是可能同时存在 2D/3D 两种实现的，必须用策略模式命名（Renderer / Adapter / Strategy）
```

## 3. 命名规范

### 3.1 地理术语词汇表

| 场景       | 使用                              | 弃用                 | 理由                                          |
| ---------- | --------------------------------- | -------------------- | --------------------------------------------- |
| 经纬度     | `lng`, `lat`                      | `lon`, `latitude`    | GIS 行业惯例；lon 易与 London 缩写混淆        |
| 海拔高程   | `elevation`                       | `altitude`, `height` | elevation = 大地水准面高程；height = 相对高度 |
| 坐标数组   | `coordinates`                     | `points`, `path`     | GeoJSON 规范术语                              |
| 单个要素   | `feature`                         | `item`, `data`       | GeoJSON Feature（geometry + properties）      |
| 要素集合   | `featureCollection`               | `list`, `array`      | GeoJSON FeatureCollection                     |
| 投影坐标   | `projectedX`, `projectedY`        | `x`, `y`             | 必须与地理坐标 `lng/lat` 区分                 |
| 缓冲区     | `bufferRadius` / `bufferDistance` | `range`, `distance`  | buffer 是 GIS 专有空间操作                    |
| 渲染器实例 | `olRenderer`, `csRenderer`        | `map1`, `map2`       | 一眼看出双引擎身份                            |

> **历史字段归一化**：`types/crs.ts` 的 `normalizePoint` 函数显式接受 `lon`/`longitude`/`latitude` 等历史字段名并归一化为 `lng`/`lat`。这是应对历史数据源的务实设计，**不是**鼓励新代码使用历史字段。新代码必须用 `lng`/`lat`，只有读取历史数据文件时才通过 `normalizePoint` 归一化。

### 3.6 GCS 缩写书写规范与坐标系豁免

**铁律：`GCS` 的唯一合法写法是全大写 `GCS`。**

`GCS` 是 **Global Component Style**（全局组件样式系统，本项目布局/样式基础设施）的缩写。指代它时**只允许全大写**；`Gcs` / `gcs`（含历史上出现的 `gcsStore` / `GcsPanel` / `--gcs-*`）一律视为**违规命名**，已于 2026-07-30 全量改正为 `GCSPanel` / `GCSButton` / `GCSInspectionOverlay` / `--GCS-*`。

**坐标系术语豁免**：`GCS` 按"独立词 / 词边界"判定。`CGCS2000`（国家 2000 大地坐标系，EPSG:4490，见 3.5 常量 `CRS.CGCS2000` 与 `src/types/crs.ts`）子串虽含 `GCS`，但含义是 "Geodetic Coordinate System"，与 Global Component Style 无关，**不算违规**，保留原样。

| 写法                                   | 判定            | 说明                   |
| -------------------------------------- | --------------- | ---------------------- |
| `GCS`、`GCSPanel`、`--GCS-*`、`useGCS` | ✅ 合法         | Global Component Style |
| `CGCS2000`、`CRS.CGCS2000`             | ✅ 合法（豁免） | 坐标系术语             |
| `Gcs`、`gcs`、`GcsPanel`、`--gcs-*`    | ❌ 违规         | 须改为全大写           |

```ts
// ✅ 写"为什么选这个坐标系"
// 北部湾区域横跨 108°E，处于 UTM 49N 和 50N 交界带。
// 前端展示统一用 WGS84(EPSG:4326)，投影到 Web Mercator 由 OL/Cesium 内部处理。

// ✅ 写"Turf.js 的已知坑"
// turf.union 在输入多边形存在共享边界时可能返回 MultiPolygon，
// 下游业务组件（SiteSelectionPage）只接受 Polygon，需做几何降级。
const merged = turf.union(featureA, featureB)
const normalized =
  merged.geometry.type === 'MultiPolygon'
    ? turf.convex(merged) // 退而求其次用凸包
    : merged

// ✅ 写"性能决策"
// xiaoqu.json 约 1200 个要素，全量遍历在移动端会掉帧。
// 第一步：rbush BBox 过滤（O(log n)）→ 第二步：turf.distance 精确计算（O(m), m << n）
const candidates = spatialIndex.search(bbox)
const matched = candidates.filter((f) => turf.distance(f, target) <= bufferRadius)

// ✅ 写"数据档位的设计意图"
// 洪涝浸没分析使用"向上取档"策略：请求 2.5m 水位时实际返回 3.0m 档位数据。
// 这是故意为之 —— 宁可高估风险（多返回淹没区域），不可低估（遗漏潜在受灾设施）。
// 前端通过对比 requestedWaterLevel / actualWaterLevel 感知档位差异。
```

### 4.5 注释卫生（2026-08-10 全仓注释大改定稿）

**读者画像**：未来的自己、AI、面试官、clone 仓库喂 AI 的人——**不预设读者已有项目上下文**。

**四条硬规则**：

1. **一句话原则**：能一句话说清，绝不用两句话。多行叙事注释压缩为一行"为什么"。
2. **禁内部编号**：注释里**禁止出现**问题台账编号（`a027`/`z083`/`d073` 等）——它们只对维护者有意义，外部读者（面试官/AI）看到的是一串无意义字符。设计决策的依据写"为什么"本身，不写编号。
3. **禁行号/文件路径引用**：`xxx.ts:123` 这类会随代码漂移，写了必过时。
4. **禁日期叙事**：`2026-08-XX 修复了 xxx` 的踩坑记录，压缩为一句"为什么这样写"；日期删掉。

**缩写首现解释**：项目专有缩写首次出现时给一句话解释（GCS=网格化布局系统、BLM=业务图层管理器、DEM=数字高程模型、CTB=地形金字塔切片工具）。后续出现可直接用缩写。

**保留清单**（这是项目注释的价值所在）：设计意图（为什么）、地理背景（坐标系/投影/凹多边形等）、工程约束（铁律）。

```js
  DUPLICATE_USERNAME: { code: 409001, status: 409, message: '用户名已存在' },
  DUPLICATE_RESOURCE: { code: 409002, status: 409, message: '资源已存在' },
  ANALYSIS_FAILED: { code: 422001, status: 422, message: '分析计算失败' },

class BusinessError extends Error {
  constructor(errorCode, detail = '') {
    super(detail || errorCode.message)
    this.name = 'BusinessError'
    this.code = errorCode.code
    this.status = errorCode.status
  }
}

// 使用
```

## 一、分包策略设计意图

### 1.1 manualChunks 分组原则

`frontend/vite.config.js` 的 `manualChunks` 函数按依赖来源分组：

| Chunk 名     | 包含依赖                         | 设计意图                                       |
| ------------ | -------------------------------- | ---------------------------------------------- |
| `vue-vendor` | `vue` / `vue-router` / `pinia`   | Vue 运行时核心，体积小、变动少，独立缓存收益高 |
| `openlayers` | `ol`                             | 2D 地图引擎，首屏核心依赖                      |
| `cesium`     | `cesium`                         | 3D 地图引擎，**实际不进 Vite chunk**（见 §二） |
| `echarts`    | `echarts`                        | 图表库，体积大，仅预测页面用                   |
| `ui-vendor`  | `element-plus` / `@element-plus` | UI 组件库，按需引入                            |

> **架构原则**：分包的目的不是"切得越细越好"，而是：(1) 让高频变动的业务代码与稳定的依赖分离，最大化浏览器缓存命中；(2) 让大体积依赖独立成块，便于按需加载与缓存。

### 1.2 Cesium 分包的特殊情况

`vite-plugin-cesium` 通过 `rollup-plugin-external-globals` 将 Cesium 标记为 external，**不会被打入 Vite chunk**。`manualChunks` 中的 `cesium` 规则在文档意图层面保留，但对构建产物无实际效果。

Cesium 的实际加载策略（架构层面）：

- 构建时：`vite-plugin-cesium` 复制 `node_modules/cesium/Build/Cesium/` → `dist/cesium/`
- 构建时：`removeCesiumHtmlTags()` post-plugin 移除 `vite-plugin-cesium` 自动注入的 HTML 标签
- 运行时：`renderers/index.ts` 中的 `ensureCesiumLoaded()` 在首次切 3D 时动态注入 `<script src="/cesium/Cesium.js">`
- `CesiumRenderer` 本身仍通过动态导入按需加载

> **设计原则**：Cesium 库体积大（MB 级）、3D 视图非首屏必需，故采用"构建时静态复制 + 运行时动态注入"的双阶段懒加载，避免 5.7MB 主库阻塞首帧。

## 二、动态导入与懒加载架构

| 模块           | 导入方式                               | 架构意图                                         |
| -------------- | -------------------------------------- | ------------------------------------------------ |
| CesiumRenderer | `await import('./CesiumRenderer')`     | 渲染器代码按需加载，2D-only 用户不下载 3D 渲染器 |
| Cesium 库      | `renderers/index.ts` 运行时注入 script | 5.7MB 主库仅在切 3D 时加载                       |
| ECharts        | 通过 ForecastPage 动态导入             | 仅预测页面加载图表库                             |
| OpenLayers     | 首屏静态导入                           | 2D 地图是首屏核心功能，预加载合理                |
| Turf.js        | —                                      | 前端未使用，仅后端依赖                           |

> **架构原则**：动态导入的判定标准是"是否首屏必需"。地图引擎、Vue 运行时、UI 框架属首屏必需；3D 引擎、图表库、路由级页面属按需加载。

# 第三部分：GCS 布局规范（原项目根基 §3,2026-08-04 移交）

> **定位**:GIS 浮动面板布局的**规则**(纯规则,不随 UI 演进)。实现方:
> `shared/layout/config.ts`(常量)、`shared/layout/useGCS.ts`(响应式布局)、
> `core/layout/components/GCSPanel.vue`(面板容器)。

## 1. 网格单元(Cell)

- `CELL_PIXEL = 80px`(按视口宽度分级 **90/80/70**——≥1920 为 90、≥960 为 80、<960 为 70;2026-08-10 更新,原 60 档已删)
- **所有面板尺寸 = 整数个 Cell**,禁止硬编码 px(`useGCS.cell(w, h)`)
- 基础间距 `GAP = 10px`;面板间距 `PANEL_SPACING = 2 × GAP = 20px`;
  安全边距 `SAFE_MARGIN = 20px`

## 2. 四条铁律

1. **尺寸整数 Cell**:面板宽高 = Cell 的整数倍
2. **锚点定位**:面板位置 = 锚点(top-left/top-right/bottom-center 等)+ offset,
   禁止绝对像素定位(`useGCS.panelPosition(w, h, anchor, offsetX, offsetY)`)
3. **禁止硬编码**:所有布局常量走 `config.ts`/CSS 变量(`--GCS-*`),禁止散落字面量
4. **间距统一**:面板间距/边距只用 GAP/PANEL_SPACING/SAFE_MARGIN

## 3. 面板交互契约

- 面板容器 `pointer-events: none`,面板内部 `pointer-events: auto`
  (防止全屏面板拦截地图拖拽/缩放)
- 面板分类:常驻面板(标题/图例)、业务面板(分析控制/结果)、临时面板(详情卡片);
  由业务页自行管理显隐,不叠放冲突

## 4. 响应式显隐

- 三档布局（2026-08-09 档位化，2026-08-10 更新断点数值）：
  - 档位 1（≥960px）：桌面等比例布局，面板原位显示（`showPanels`/`showTopArea`）
  - 档位 2（640~959px）：抽屉模式，面板收进抽屉（MobileDrawer），底部 nav 出现「菜单」键
  - 档位 3（<640px）：抽屉紧凑，底部 nav 收敛为 3 键（首页/个人中心/菜单），`navCompact`
- 断点判定在 `useGCS`（`showPanels`/`showTopArea`/`navCompact`），组件用 computed 消费，禁止组件内重复判定

## 5. CSS 变量体系

- 颜色/文本/间距全部走 `--GCS-*` 变量(`shared/constants/colors.ts` 等),禁止散落 hex/rgba
- 渲染层颜色(图层样式)走 `LAYER_DEFAULTS`/调色板,禁止散落 rgba 字面量

# 第四部分：分层契约（原 docs/分层契约.md，2026-08-10 并入）

> 定位:10 个顶层目录的依赖顺序与边界。`npm run cruise`(dependency-cruiser)守护
> 规则层,本契约守护语义层——规则没写到的,以本契约为准。
> 架构审查收口产物(2026-08-04):此前 dc 规则只防"谁都不许引 business"+ no-circular,
> 未定义 core/types/services 的层级顺序,导致反向依赖无规则可依。

## 1. 层级顺序(低 → 高)

| 层级 | 目录                               | 职责                              | 可依赖(低层)                          |
| ---- | ---------------------------------- | --------------------------------- | ------------------------------------- |
| L0   | `types/`                           | 纯类型声明                        | **零运行时依赖**(纯类型)              |
| L1   | `shared/`                          | 通用工具/composable/常量/基础组件 | types(type-only)                      |
| L2   | `stores/`                          | 全局状态(Pinia)                   | shared、types                         |
| L3   | `services/`                        | 数据访问(adapter/API 封装)        | shared、stores、types                 |
| L4   | `visualization/`                   | 通用图表资产                      | shared、types                         |
| L5   | `core/`                            | 地图核心 + 布局基座               | stores、services、shared、types       |
| L6   | `business/`                        | 业务模块(**互不依赖**)            | core、stores、services、shared、types |
| L7   | `views/`                           | 页面装配                          | business、core、shared、types         |
| L8   | 入口(`main.ts`/`router`/`App.vue`) | 应用装配                          | 全部                                  |

**核心铁律**:

- 低层**不得**依赖高层(如 shared 不得依赖 core/stores/business)
- `types/` 零运行时依赖(纯类型;运行时常量/工具放 shared)
- 业务模块之间禁止互引(manifest 驱动注册,非直接 import)

## 2. 已知的设计确认依赖(不禁,但必须知悉)

以下依赖**形式上"反向"**(低层引高层),但为架构有意设计,dc 不拦、本契约明示:

| 依赖                      | 位置                                                       | 理由                                                                                                                                         |
| ------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| core → stores             | `UnifiedMap.vue` / `useLayerManager.ts` / `provideKeys.ts` | mapStore 是跨层共享的地图状态,core 消费属设计使然                                                                                            |
| core → services           | `usePortLayer.ts` → mapDataService                         | core 需要数据服务加载 ports 等静态数据                                                                                                       |
| core → visualization      | `AppLayout.vue` → RadarChart                               | 布局基座展示图表组件                                                                                                                         |
| services → core(叶子例外) | `mapDataService.ts:7` → `core/config/map`                  | 仅取 MAP_CONFIG 叶子常量;走 `@/core` 会形成 core↔services 循环(no-circular),故深路径直引叶子;dc 规则 `services-not-import-core` 已豁免该叶子 |

> 若未来 core 希望完全独立,需将 mapStore 下沉或引入依赖注入;当前**明确接受**这些依赖,
> 代价是 core 不是零依赖内核,但每个依赖都有真实使用场景且方向稳定。

## 3. 已修复的反向依赖(2026-08-04)

| 原反向依赖                               | 修复                                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| types → shared(`types/crs.ts` 引 logger) | `normalizePoint`/`isInBeibuGulf`/`DEFAULT_CRS` 等运行时逻辑移入 `shared/utils/crs.ts`,`types/crs.ts` 只留纯类型;dc 新增 `types-not-import-shared`(error)守住 |

## 4. dc 规则清单(与契约对应)

- `shared-not-import-core` / `shared-not-import-stores` / `stores-not-import-business`(error)
- `core-imports-business` / `services-imports-business` / `visualization-should-not-import-business`(error)
- `types-not-import-shared`(error,2026-08-04 新增)
- `business-cross-import-*`(warn,模块互引)
- `no-circular`(error)
- cruise 覆盖范围: `frontend/src backend`(2026-08-04 起 backend 入守护)

## 5. 校验命令

```bash
npm run cruise   # frontend/src + backend 全量架构守护
```

# 第五部分：数据流契约（原 docs/数据流契约.md，2026-08-10 并入）

> 定位:项目数据流动的唯一规则文档。任何数据流动相关改动都必须遵守本契约。
> 违反规则的代码 = bug(即使功能暂时正常,也要修)。
> 本契约由 2026-08-04 数据流审查产出,已修复全部已发现的违规项。

## 1. 总览

```
业务组件 → 取数入口(useApiRequest / loadStatic)
  ├─ flood         → floodAdapter       (services/adapters/)
  ├─ forecast      → useForecastRequest (业务 composable,事务/竞态管理)
  ├─ site-analysis → useSiteAnalysisApi (业务 composable,直连 useApiRequest + zod 校验)
  └─ 数据源: mock → loadStatic(public/data 契约桩)
             api   → fetch → Express /api/*
             online→ fetch → FastAPI /flood-online
后端:routes → controllers(sendSuccess) → services(createReadCache) → backend/data/*.json
```

## 2. 前端请求规则

| 规则                | 内容                                                                                                                                                                            | 违反后果                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| **R1 请求唯一入口** | API 请求一律走 `useApiRequest`;静态资源一律走 `loadStatic`。**禁止裸 fetch/axios**。                                                                                            | 报错口径/重试/超时/解包全部失效 |
| **R1.1 跨服务例外** | FastAPI 返回裸 JSON(无信封)时,`apiRequest` 传 `envelope: false`,**仍在统一入口内**,禁止绕出入口裸 fetch                                                                         | 同 R1                           |
| **R2 信封统一**     | 响应契约 `{ code, data }`,前端解包**唯一**走 `unwrapEnvelope`。禁止手写 `res.data`/`.then(r=>r.data)`                                                                           | 解包逻辑重复、漂移              |
| **R3 静态资源**     | `loadStatic`(超时 10s / TTL 5min / in-flight 去重 / LRU 上限 100)                                                                                                               | 缓存/超时/校验缺失              |
| **R4 数据源归属**   | 数据源模式由 `dataSourceConfig` 统一管理(全局 `VITE_DATA_SOURCE` + adapter 覆盖)。业务组件**不得**直接调 `apiRequest`/判断数据源                                                | 数据源语义散落                  |
| **R5 取数统一收口** | 业务组件取数一律经 `useApiRequest`/`loadStatic` 统一入口;跨业务复用的取数封装放 `services/adapters/`(当前仅 floodAdapter);业务专属取数逻辑(事务/竞态/校验)放业务模块 composable | 中间层不一致/统一入口被绕过     |

## 3. 后端响应规则

| 规则              | 内容                                                                                                                   | 违反后果                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| **R6 成功出参**   | controller 一律 `sendSuccess(res, data)`,信封 `{ code, data }`                                                         | 前端解包失效            |
| **R7 错误出参**   | 错误抛 `BusinessError(code, message)` → 全局错误中间件统一映射 HTTP 状态码。禁止 controller 裸 `res.json`/`res.status` | 错误口径不一致          |
| **R8 读文件缓存** | 后端读 JSON 文件缓存统一 `createReadCache`(TTL + LRU 上限)。**禁止自研 cache Map**                                     | 缓存实现重复(曾经 4 套) |

## 4. 分层与入口规则

| 规则             | 内容                                                                                                                                       | 违反后果 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| **R9 跨层收口**  | 跨层 import 走 index 入口(`@/shared` / `@/core` / `@/stores` / `@/services` / `@/business`),禁止深层路径穿透(已由 dependency-cruiser 校验) |
| **R10 依赖方向** | shared ← stores/services/core ← business ← 应用层,单向(已由 dependency-cruiser 校验,0 violation)                                           |

## 5. 数据源与数据文件

| 数据源 | 位置                            | 定位                                                                                     |
| ------ | ------------------------------- | ---------------------------------------------------------------------------------------- |
| mock   | `frontend/public/data/*.json`   | 前端契约桩(数据文件带 `_contractVersion` 契约版本字段),给前端独立开发用,随真数据接入退役 |
| api    | `backend/data/*.json`           | Express 数据(过渡存储,最终归属空间数据库 PostGIS)                                        |
| online | FastAPI `backend/flood-service` | 真 DEM 演算(未来接数据库后成为唯一生产通路)                                              |

**mock 与 api 物理隔离**(不混放),但**契约必须一致**——原校验脚本已移除,靠人工保证,见 §8 历史。

## 6. 新增业务模块清单(z075 manifest)

```
1. business/manifest.ts 加一条(路径/引擎/标题/导航/组件)
2. 建 business/<name>/ 模块目录(页面 + components + composables + constants)
3. 取数层:业务专属取数 composable 放 business/<name>/composables(经 useApiRequest 统一入口);仅当取数逻辑跨业务复用才建 services/adapters/<name>Adapter.ts(规则 R5)
4. stores/<name>Store.ts(如需要跨页状态)
5. types/ 补充业务类型
```

路由/导航/meta 由 manifest 自动生成,不需改 router/App.vue。

## 7. 校验命令

```bash
npm test                # 前后端测试(含数据流相关用例)
# 注: 原契约校验脚本(check-mock-contract.cjs → check-static-contract.cjs)已移除, mock/api 契约一致性靠人工保证(见 §8 历史)
```
