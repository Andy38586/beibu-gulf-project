## 三、GCS Panel 布局系统（核心框架）

### 3.1 设计哲学

> Canvas 是屏幕，Grid 是尺子，Cell 是单位，Panel 是一切。

本项目不采用传统 Header/Sidebar/Content/Footer 布局，而采用 **iPad 桌面模型**：
- 屏幕上没有容器、没有区域、没有分区
- 所有可见元素都是 Panel
- Panel 浮于 Canvas 之上，Canvas 主体（地图）透过 Panel 间隙可见

### 3.2 四条铁律

| # | 铁律 | 说明 |
|---|---|---|
| R1 | 一切都是 Panel | 标题是 Panel，图表是 Panel，按钮是 Panel，Dock 是 Panel |
| R2 | 不存在容器 | 禁止 Zone、Area、Container 等任何中间层 |
| R3 | 度量单位是 Cell | Panel 的宽高用 Cell 定义，不用 px |
| R4 | 间距统一 2×GAP | Panel 到任何边缘/其他 Panel 的距离 = 2×GAP = 20px |

### 3.3 核心常量（config.js）

| 常量 | 值 | 含义 |
|---|---|---|
| `CELL_PIXEL` | 80 (默认) | Cell 最小逻辑像素单位 |
| `GAP` | 10 | 基础间距单位 |
| `PANEL_SPACING` | GAP × 2 = 20 | Panel 间距 |
| `SAFE_MARGIN` | PANEL_SPACING = 20 | Panel 到 Canvas 边缘距离 |
| `CELL_PADDING` | GAP = 10 | Panel 内部 padding |
| `GRID_SIZE` | 100 | Grid 参考线间距（仅检查模式） |

响应式断点映射 (`getCellPixelByViewport`)：
- ≥1920 → 90
- ≥1366 → 80
- ≥1024 → 80
- ≥768 → 70
- <768 → 60

### 3.4 PPS 定位系统

Panel 位置由 `useGCS().panelPosition(w, h, anchor, offsetX, offsetY)` 计算。

锚点 (anchor) 类型：
- `top-left` — 左上角，向右下偏移
- `top-right` — 右上角，向左下偏移
- `top-center` — 顶部居中
- `bottom-center` — 底部居中（BottomNavBar 使用）
- `bottom-left` / `bottom-right`

**使用方式（标准模板）：**
```vue
<GcsPanel :w="4" :h="4" anchor="top-left" :offset-x="0" :offset-y="1.25">
  <YourContent />
</GcsPanel>
```

- `w` / `h`：Cell 单位的宽高
- `offset-x` / `offset-y`：Cell 单位的偏移（可以是小数如 1.25）
- Panel 之间自动保持 PANEL_SPACING (20px) 间距

### 3.5 CSS 尺寸规范

**禁止在组件中硬编码 px 值。** 使用 `useGCS()` 的 CSS 工具：
```js
const { cell8px, cell16px, cell40px, fontSizeTitle, fontSizeBody, fontSizeSmall } = useGCS()
// 在 <style> 中: v-bind(cell8px)
```

字号固定规范（GCS_V2，与 Cell 网格解耦）：
| 用途 | 规范值 |
|---|---|
| 标题 | 16px |
| 正文 | 14px |
| 辅助文字 | 12px |

### 3.6 响应式显隐

```js
const { showPanels, showTopArea } = useGCS()
// showPanels: 视口 ≥768px 显示左右 Panel 组
// showTopArea: 视口 ≥768px 显示顶部 Title + 按钮
// BottomNavBar 始终显示
```

## 四、面板分类与交互契约

### 4.1 两类面板

| 类型 | 定义 | 交互模式 | 示例 |
|---|---|---|---|
| **数据末端 (Data Endpoint)** | 接收数据 → 可视化渲染 → 终点 | 只消费数据，不对外输出参数 | LineChart / BarChart / RadarChart / FloodAnalysisReportPanel / WaterLevelProfilePanel |
| **中间件 (Middleware Panel)** | 接收参数 → 展示 + 交互 → 传出参数 | 双向通信：既读又写 | LayerControlPanel / PaginatedListPanel / SiteAnalysisControlPanel |

### 4.2 中间件面板的交互契约（以 PaiginatedListPanel 为例）

**输入（props）：**
- `items` — 数据源数组
- `pageSize` — 每页条数
- `planType` — 方案类型 ('site-selection' | 'flood')

**输出（emits）：**
- `click-item` → 父组件接收，触发地图交互（如 `startBreathing`）+ 更新雷达图

**内部直接操作（不用 emit）：**
- 地图 flyTo / startBreathing — 通过 `useMapControls()`
- 收藏/取消收藏 — 通过 `usePlans()`
- 登录判断 — 通过 `useAuth().isAuthenticated`

**关键约束：**
- PaginatedListPanel 点击小区 → 地图呼吸效果必须保留
- 雷达图通过 `displayXiaoquForRadar` computed 响应 `selectedXiaoqu` 自动更新
- 浸没分析的 AffectedFacilityListPanel 也需要同样的设施点击呼吸效果（当前未实现，属已知遗漏）

### 4.3 图层控制面板的交互契约

LayerControlPanel 是纯展示型中间件：
- **输入**：通过 `useLayerManager().layerCatalog` 获取图层列表（来自 `mapStore.layerCatalog`）
- **输出**：通过 `mapStore.toggleLayer(key)` 控制图层显隐
- **不直接操作渲染器**：通过 store → `registerToggleable` 的 show/hide 回调间接操作

### 4.4 雷达图的数据流向

```
分析结果 → SiteSelectionPage.matchedXiaoqu
  → displayXiaoqu (切片 top 8)
  → PaginatedListPanel (列表展示)
     → click-item emit
        → selectedXiaoqu 更新
           → displayXiaoquForRadar (优先选中，否则第一名)
              → RadarChart props 更新
```

关键：雷达图的 `displayXiaoquForRadar = selectedXiaoqu || topXiaoqu`（`SiteSelectionPage.vue:80`）

## 五、Renderer Adapter 模式（地图引擎抽象）

### 5.1 抽象基类接口

`MapRenderer.js` 定义了所有渲染器必须实现的接口：

| 方法 | 用途 | 备注 |
|---|---|---|
| `addPointLayer(id, features, options)` | 添加点图层 | features 格式: `[{lon, lat, name}]` |
| `addPolygonLayer(id, features, options)` | 添加多边形图层 | |
| `addGeoJsonLayer(id, geojson, options)` | 添加 GeoJSON 图层 | |
| `setVisibility(id, visible)` | 设置图层可见性 | 支持 pending visibility（图层未注册时暂存） |
| `removeLayer(id)` | 移除图层 | |
| `flyTo(target, options)` | 飞行/缩放 | target: `{lng, lat}` 或 `[lng, lat]` 或 `{layerId}` |
| `exportState()` / `importState(state)` | 2D/3D 切换时的状态持久化 | |
| `on(event, handler)` / `emit(event, data)` | 事件总线 | |
| `addWaterSurface(id, coords, height, opts)` | 水面（仅 Cesium） | 基类默认返回 false + DEV warn |
| `updateWaterLevel(id, height)` | 更新水面高度 | 同上 |
| `startBreathing(lng, lat)` / `stopBreathing()` | 呼吸灯效果 | 同上 |

### 5.2 渲染器能力矩阵（2026-07-23 实际状态）

| 特性 | OLRenderer | CesiumRenderer | 备注 |
|---|---|---|---|
| addPointLayer 字段名 | `item.lon` | `item.lon` | ⚠️ 与部分业务代码的 `lng` 约定不一致（P3-01），但两个渲染器均已做 lon/lng 兼容（`target.lng ?? target.lon`） |
| flyTo duration | 毫秒 | 秒（✅ 已修正为 `duration: 1`） | `CesiumRenderer.js:610` |
| addGeoJsonLayer marker | ✅ Circle + Text | ✅ PointGraphics（✅ 已修正，支持 markerColor/markerSize） | `CesiumRenderer.js:533`, `OLRenderer.js:229` |
| addGeoJsonLayer heatmap | ❌ 不支持 | ❌ 不支持 | 预测分析的前置能力缺口，需在 OLRenderer 中新增 |
| camera.changed 清理 | ✅ destroy 时移除 | ✅ 已修正（保存引用，destroy 时 removeEventListener） | `CesiumRenderer.js:303,311,908` |
| destroy() 定义 | 1 个 | 2 个（P3-13，后者覆盖前者，332 行为死代码） | 低优先级技术债 |

### 5.3 引擎切换流程

```
App.vue 监听 route.meta.engine 变化
  → mapStore.setMapType('2d'|'3d')
    → UnifiedMap 接收 props.mapType
      → v-show 切换容器（OL 始终存在，Cesium 首次创建后保留）
      → exportState(旧引擎) → 切换 v-show → importState(新引擎)
      → 引擎切换时不触发相机重置（isEngineSwitch 保护）
```

### 5.4 Cesium Viewer 单例规则

- CesiumViewer 由 `CesiumRenderer` 内部管理，首次创建后复用，**不销毁**
- 离开 3D 路由只是 v-show 隐藏，不 destroy
- `camera.changed` 监听器已保存引用，`destroy()` 时移除（`CesiumRenderer.js:303,908`）

## 六、路由与页面结构

### 6.1 路由配置规则

`src/router/index.js` — 所有路由必须声明 `meta.engine`：

| 路由 | 引擎 | 页面组件位置 |
|---|---|---|
| `/` (Home) | 2d | `@/views/HomePage.vue` |
| `/site-selection` | 2d | `@/business/site-selection/SiteSelectionPage.vue` |
| `/heatmap` (Flood) | 3d | `@/business/flood-analysis/FloodAnalysisPage.vue` |
| `/profile` | 2d | `@/views/ProfilePage.vue` |

要求：
- 业务路由页面组件放在 `src/business/<业务名>/` 下
- 通用页面放在 `src/views/` 下
- **所有路由不需要 `requiresAuth`**：认证通过 AuthModal 弹窗实现，不阻断路由访问（P0-001 已移除）

### 6.2 页面标准结构

每个业务页面遵循统一模板：

```vue
<script setup>
import AppLayout from '@/core/layout/AppLayout.vue'
import GcsPanel from '@/core/layout/components/GcsPanel.vue'
// 业务组件 imports

// 状态管理
// 生命周期（onMounted / onUnmounted）
// 路由守卫（onBeforeRouteLeave → 保存/清除状态到 stateStore）
</script>

<template>
  <div class="xxx-page">
    <AppLayout>
      <template #left>
        <GcsPanel :w="4" :h="4" anchor="top-left" :offset-x="0" :offset-y="1.25">
          <!-- 左上内容 -->
        </GcsPanel>
        <GcsPanel :w="4" :h="4" anchor="top-left" :offset-x="0" :offset-y="5.5">
          <!-- 左下内容 -->
        </GcsPanel>
      </template>

      <template #right>
        <GcsPanel :w="4" :h="4" anchor="top-right" :offset-x="0" :offset-y="1.25">
          <!-- 右上内容 -->
        </GcsPanel>
        <GcsPanel :w="4" :h="4" anchor="top-right" :offset-x="0" :offset-y="5.5">
          <!-- 右下内容 -->
        </GcsPanel>
      </template>
    </AppLayout>
  </div>
</template>

<style scoped>
.xxx-page {
  width: 100%;
  height: 100%;
  pointer-events: none; /* 让鼠标事件穿透到地图 */
}
.xxx-page :deep(.gcs-panel) {
  pointer-events: auto;  /* 面板恢复鼠标事件 */
}
</style>
```

### 6.3 pointer-events 关键规则

页面根元素必须 `pointer-events: none`，否则会阻挡底层地图的鼠标事件（拖拽/缩放/旋转）。
- 通过 `:deep(.gcs-panel) { pointer-events: auto }` 恢复面板交互
- **禁止使用 `:deep(*) { pointer-events: none }` 通配符**：会覆盖 UnifiedMap 的 `.map-container` 样式
- 3D 路由（浸没分析）额外禁用 `backdrop-filter`：`backdrop-filter: none !important` 避免 WebGL 性能开销

## 七、状态管理约定

### 7.1 Pinia Store 职责划分

| Store | 文件 | 职责 | 持久化方式 |
|---|---|---|---|
| `map` | `stores/map.js` | 地图状态（2d/3d切换、选中港口、图层目录、分析结果、基础底图选择） | localStorage (mapType/baseLayer/selectedPort) + sessionStorage (analysisResult) |
| `gcs` | `stores/gcsStore.js` | GCS 分析聚合（综合水位、剖面、淹没、港口影响的 active 状态） | 无持久化（运行时） |
| `waterLevel` | `stores/waterLevelStore.js` | 水位高度 | 无 |
| `flood` | `stores/floodStore.js` | 淹没分析结果（统计、范围、风险等级） | 无 |
| `portImpact` | `stores/portImpactStore.js` | 港口影响评估（受影响设施、总损失） | 无 |
| `profile` | `stores/profileStore.js` | 剖面分析状态 | 无 |
| `siteSelectionState` | `stores/siteSelectionState.js` | 选址分析页面状态暂存（用于 /profile 返回恢复） | 内存（consumeState 一次性消费） |
| `floodState` | `stores/floodState.js` | 浸没分析页面状态暂存 | 内存 |

### 7.2 Store 设计原则

1. **map store 是唯一处理持久化的 store** — localStorage/sessionStorage 读写只在此处
2. **业务 store 不直接操作渲染器** — 通过 mapStore 或 composable 间接操作
3. **状态恢复使用 consumeState 模式** — `saveState` → 离开页面 → `onMounted` 时 `consumeState()` 一次性消费后清空
4. **store 之间的依赖通过 Pinia 的 `useXxxStore()` 调用** — 不通过 inject/provide

### 7.3 图层注册标准模式

```js
// 注册业务图层到 mapStore 的 layerCatalog
// 方式 1: 传 renderer，store 自动生成 setVisibility 回调
registerToggleable('gcs-flood-area', '淹没范围', renderer, undefined, true)

// 方式 2: 手动传 show/hide 回调
registerToggleable('gcs-water-surface', '水面', showFn, hideFn, true)
```

`registerToggleable` 内部对 renderer 参数的处理（`useLayerManager.js:35-41`）：
- 如果传的是 renderer 对象（有 `setVisibility` 方法）→ 自动生成回调
- 如果传的是函数 → 直接作为 show/hide 回调

## 八、组件分类与复用规则

### 8.1 组件层次

| 层次 | 位置 | 职责 | 可复用？ | 依赖方向 |
|---|---|---|---|---|
| Core Layout | `core/layout/components/` | GcsPanel / BottomNavBar / NavButton / GcsButton / GcsInspectionOverlay | 全项目 | → core only |
| Core Map | `core/map/` | UnifiedMap | 根级别挂载（App.vue） | → core only |
| Shared | `shared/components/` | LayerControlPanel / PaginatedListPanel / ErrorPopup / ErrorBoundary / LoginPanel / PanelTitle / PlanSaveModal | 跨业务 | → shared composables + stores |
| Visualization | `visualization/` | LineChart / BarChart / RadarChart / PortInfoPanel | 跨业务（纯展示） | → visualization composables only |
| Business | `business/<name>/components/` | SiteAnalysisControlPanel / FloodAnalysisReportPanel / WaterLevelProfilePanel / AffectedFacilityListPanel | 仅本业务 | → shared + stores + business composables |

### 8.2 何时抽取到 shared/

满足以下条件之一：
- 被 ≥2 个业务页面使用的组件 → shared/components/
- 被 ≥2 个业务页面使用的 composable → shared/composables/
- 纯工具函数（不依赖 Vue 响应式） → shared/utils/

**反例：** 不要过早抽象。只被一个业务使用的组件留在 business 目录下。

### 8.3 PaginatedListPanel 的命名说明

这个组件在你的描述中叫"列表展示面板"，代码中叫 `PaginatedListPanel`。命名历史：
- 曾用名 `FavoriteListPanel`（已废弃，因为功能不止收藏）
- 前端叫"收藏"是因为提供收藏按钮，但核心是一个**通用分页列表 + 地图交互**组件
- 后续浸没分析也可以复用它来展示受影响设施列表

## 十、API 调用约定

### 10.1 统一入口

前端 API 调用统一使用 `useApiRequest()` 的 `apiRequest(path, options)` 方法：

```js
const { apiRequest } = useApiRequest()
const data = await apiRequest('/site-analysis', {
  method: 'POST',
  body: JSON.stringify(payload),
})
```

**禁止直接使用裸 `fetch()`** — 需要经过统一的错误处理和 401 拦截。

### 10.2 响应格式

当前项目存在两套格式（这是已知的历史遗留问题，决策缺口）：

| 风格 | 格式 | 使用者 |
|---|---|---|
| RESTful | HTTP 状态码 + `{error}` | auth / plans / markers / site-analysis / facilities |
| GCS 系 | HTTP 200 + `{code, data, message}` | gcs/* |

**新增接口统一使用 RESTful 风格**（HTTP 状态码 + `{error}`），待后续统一迁移 GCS 系接口。

## 十五、新增业务的标准流程

以新增"预测分析"为例：

```
1. 创建 src/business/forecast-analysis/
```

## 十七、常见反模式（禁止清单）

以下是另一个 AI 最容易犯的错误，逐条列出并附实际后果：

### ✗ 反模式 1: 在页面根元素忘记 pointer-events: none

```vue
<!-- ❌ 错误 -->
<style scoped>
.forecast-page {
  width: 100%;
  height: 100%;
  /* 缺了 pointer-events: none */
}
</style>
```

**后果**: 整个页面成为全屏事件拦截层，地图拖拽/缩放/旋转全部失效。
**正确**: 参考 6.2 节模板，必须加 `pointer-events: none` + `:deep(.gcs-panel) { pointer-events: auto }`。

### ✗ 反模式 2: 用 :deep(*) 恢复 pointer-events

```css
/* ❌ 错误 — 会覆盖 .map-container 的 pointer-events: auto */
.flood-analysis-page :deep(*) {
  pointer-events: none; /* 或 auto */
}
```

**后果**: 选择器特异性高于 UnifiedMap 的 `.map-container`，导致 Cesium canvas 无鼠标事件。
**正确**: 只对 `.gcs-panel` 恢复：`.xxx-page :deep(.gcs-panel) { pointer-events: auto }`。

### ✗ 反模式 3: 在 onMounted 中直接操作渲染器

```js
// ❌ 错误
onMounted(() => {
  const renderer = mapStore.currentRenderer  // 可能为 null
  renderer.addPointLayer(...)                 // TypeError
})
```

**后果**: 渲染器初始化是异步的，onMounted 时大概率未就绪。
**正确**: 参考 FloodAnalysisPage.vue:175-185，用 watch currentRenderer 或在重试循环中等待。

### ✗ 反模式 4: 硬编码 px 值

```vue
<!-- ❌ 错误 -->
<div style="padding: 10px; font-size: 14px;">
```

**后果**: 无视口尺寸变化，在小屏/大屏下比例失调。
**正确**:
```js
const { cell8px, fontSizeBody } = useGCS()
// <div :style="{ padding: cell8px, fontSize: fontSizeBody }">
```

### ✗ 反模式 5: 跨层 import

```js
// ❌ 错误 — core 层 import business 层
// 文件: src/core/map/UnifiedMap.vue
import { useAnalysisLayer } from '@/business/site-selection/composables/useAnalysisLayer'
```

**后果**: 违反规则 1（core 不依赖 business），新增业务时必须改 core 层代码。
**正确**: 业务层自己 import，通过 mapStore.registerAnalysisHandler 注入（参考 SiteSelectionPage.vue:88-93）。

### ✗ 反模式 6: 把"当前阶段简化"当 bug 修

```js
// ❌ 错误 — 把 JSON 文件存储"升级"成 MongoDB
// 理由: "JSON 文件存储不是生产级方案"
```

**后果**: 引入不必要复杂度，违反当前阶段目标。JSON 存储是刻意简化（见第 11 节）。
**正确**: 先判断是否在第 11 节清单中，如果是 → 不改。

### ✗ 反模式 7: 修改 bug 时顺手重构

```js
// ❌ 错误 — 修 P1-07（字段名不一致）时顺手把 markers 整个模块重构成 TypeScript
```

**后果**: 单次改动量失控，引入新问题，无法独立验证。
**正确**: 每条规则 13.5 — 每次只修一个模块。重构放另一个 PR。

### ✗ 反模式 8: 不处理请求乱序

```js
// ❌ 错误 — 快速拖滑块时直接 setStore
watch(waterLevel, async (newLevel) => {
  const data = await apiRequest(`/gcs/flood-areas?waterLevel=${newLevel}`)
  floodStore.startFloodAnalysis(data)  // 旧响应可能覆盖新响应
})
```

**后果**: 用户在 2m→5m→3m 快速拖动后看到的是 5m 的数据（竞态）。
**正确**: 参考 FloodAnalysisPage.vue:262-291，用 `analysisSeq` 递增序号，只取最新响应。
