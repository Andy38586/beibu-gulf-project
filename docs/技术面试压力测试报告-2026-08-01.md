# 第一部分：项目真实性审查

## 1. 业务闭环 — 致命问题：自述与展示目的矛盾

**致命矛盾**：README.md:5 自述「本科 GIS 专业独立开发项目……目标是验证一套可扩展的 GIS 业务系统架构，而非单纯的地图可视化 Demo」；README.md:165 自述「这是一个**学习性质**的个人项目」；README.md:26 自述「业务部分目前数据规模有限，主要用于验证 GIS 业务流程与系统架构的可行性，**不追求覆盖完整业务闭环**」。

但你在面试中"展示给企业"。面试官第一句必然是：「既然是学习项目，为什么拿来面试？」——这是 README 自述与展示动作的**真实矛盾**，无需捏造其他证据。

### 业务闭环审查

| 模块 | 输入 | 数据来源 | 用户操作 | 输出价值 | 真实度 |
|------|------|----------|----------|----------|--------|

### 最致命的"为展示而设计"证据 — `backend/services/forecastEngine.js:101-140` `generateSpatialValues`

用 `Math.random()` 在 3 个真实港口坐标周围生成散射点（**每港 40 个，3 港合计 120 个**）填热力图。面试官看到这段会直接质疑「这热力图反映的是真实业务分布，还是纯随机噪声？」

> 注：该随机散射是**后端预测引擎**的示意性可视化（用散射点表达港口预测强度），并非前端代码。面试时应如实定位为"后端为热力图做的示意性填充"，而非否认其存在。

### README 文案与代码冲突

- README.md:13 宣称「基于水位与地形的三维淹没模拟（Cesium 3D）」
- `FloodAnalysisPage.vue:5` 注释：「使用 mock DEM 数据……待接入：真实 DEM 数据」
- README.md:12 宣称「根据历史数据预测」

# 第二部分：架构面试压力测试

## 模块设计追问

**Q1：为什么这样划分 core/business/shared？**
回答依据：项目根基.md §2.2 有明确依赖规则（core 不依赖 business、shared 不依赖 business、types 只能被 import）。这是项目的真实加分项——dependency-cruiser 在 CI 中自动校验。

**Q2：新增业务模块需修改哪些地方？**
1. `business/<name>/<Name>Page.vue`（套模板）
2. `router/index.ts` 加路由 + `meta.engine`
3. `core/layout/components/BottomNavBar.vue` 加 nav 项

关键：项目根基.md §10 自述"唯一需要在 core/layout 改的是 BottomNavBar 的 navItems 数组加一行"——这是真实可验证的扩展性。

**Q3：business 文件夹膨胀如何避免？**
当前只有 3 个业务，每个 4-7 个文件。文档无对应策略。面试官会追问：「如果 20 个业务呢？business/`<name>`/ 内部是否需要再分子模块？」

**Q4：两个业务共享能力怎么处理？**
项目根基.md §2.3 有明确规则："被 ≥2 个业务使用 → shared/"。`PaginatedListPanel` 是真实案例——被 `SiteSelectionPage` 和 `AffectedFacilityListPanel` 共用。

## 地图架构追问

**Q1：为什么不直接用 OpenLayers API？**
真实回答：业务代码（如 `FloodAnalysisPage.vue`）通过 `businessLayerManager.register(layerType: 'waterSurface'/'geojson'/'points')` 注册图层，完全不 import ol。换引擎时业务代码零改动。这是真实成立的解耦。

**Q2：Renderer 抽象解决什么问题？**
1. 2D/3D 路由级切换（`App.vue:55-95` 监听 `route.meta.engine`）
2. 引擎切换后图层重建（`App.vue:100-107` 监听 `currentRenderer` 调 `reapplyAll`）
3. 业务层不感知引擎差异

**Q3：换 Cesium 需要改多少代码？**
⚠️ 陷阱问题：README.md:59 自述"接入 OpenLayers（2D）与 Cesium（3D）"。实际两套都已接入——面试官如果问"换 MapboxGL"，答案是：新写一个 ~600 行的 `MapboxRenderer` 类，业务代码不动。但这种假设性扩展是否值得 2000 行抽象成本，是面试官会持续追问的点。

**Q4：抽象是否真减少成本？**
关键反例：`OLRenderer.ts:560-593` 重写了 6 个 3D-only 方法（`addWaterSurface`/`updateWaterLevel`/`removeWaterSurface`/`removeAllWaterSurfaces`/`setWaterSurfaceVisibility`），每个都只是 `if (import.meta.env.DEV) logger.debug(...); return false`。

但 `MapRenderer.ts:238-266` 基类已经默认实现了相同的 `logger.debug + return false`。OLRenderer 的这 6 个重写完全是冗余代码——典型的 AI 生成"看起来很完整但无价值"的代码。面试官看到这 30+ 行会直接质疑抽象的合理性。**（已实锤：功能与基类完全重合，可安全删除。）**

**Q5：地图实例生命周期管理？**
- OL：DOM 容器 `v-show` 切换，不销毁（项目根基.md §4.4）
- Cesium：单例 + 30s idle-destroy（`CesiumRenderer.ts:29-210` `CesiumViewerManager`，`IDLE_DESTROY_DELAY=30000`）
- destroy 链路完整：`CesiumRenderer.ts:1032-1063` 清理相机监听/屏幕事件/水面/防抖定时器/idle 定时器

这是真实加分项——面试官会认可"Cesium 显存管理 + idle destroy"是实战经验。

## 状态管理追问

**Q1：为什么用 Store？**
`mapStore.ts` 423 行——确实过重。包含：地图实例、渲染器、mapType、layerCatalog、baseLayerKey、analysisHandler、lastAnalysisResult、activePanel、selectedXiaoqu。

**Q2：哪些数据该进全局状态？**
- ✅ 应该全局：mapType、currentRenderer、layerCatalog、selectedPort
- ❌ 不应该全局：analysisHandler（`mapStore.ts:95` 注释自承"是已知的设计取舍"）、activePanel/selectedXiaoqu（这是组件 UI 状态）、lastAnalysisResult（这是业务数据）

**Q3：为什么不用组件内 ref？**
- selectedXiaoqu 跨 `PaginatedListPanel` + `RadarChart` + 地图呼吸灯共享，确需全局
- activePanel 仅 `LayerControlPanel` 和 `AppLayout` 用，可下沉

**Q4：Store 无限膨胀如何避免？**
项目自身已承认问题：项目根基.md §6.2 模式一 自述"此模式让 mapStore 累积了 analysisHandler 职责，是已知的设计取舍（详见 待解决问题.md A02/A04）"。面试官看到这段会问「为什么不重构？」

**Q5：多业务同时修改地图状态怎么办？**
未处理——currentRenderer 是 ShallowRef，多业务并发 setVisibility 会竞态。但单用户单页面场景下不暴露，可接受。

### 视口裁剪的隐藏问题 ⚠️
`CesiumRenderer._getViewportBBox:475-494` 用 `camera.positionCartographic` 的经纬度 + `height/111000*1.5` 估算视口范围——这是**以相机位置为中心的圆形/方形估算，不是真实视口四角投影**。当相机倾斜（pitch≠-90）时误差显著。面试官会追问：「倾斜视角下，边缘 POI 会被错误裁掉吗？」

# 第四部分：代码质量审查

## 1. AI 生成代码风险

### 严重冗余（必被面试官抓）
`OLRenderer.ts:560-593` 6 个 3D-only 方法重写：

基类 `MapRenderer.ts:238-266` 已实现相同逻辑。30 行纯冗余——AI 生成"看起来完整"的典型痕迹。**（已实锤：功能与基类完全重合。）**

### `@ts-nocheck` 大面积使用
- `OLRenderer.ts:1 // @ts-nocheck`
- `CesiumRenderer.ts:1 // @ts-nocheck`

核心地图层 2000+ 行无类型保护——面试官会问「TypeScript 迁移"渐进"了多久？什么时候移除 @ts-nocheck？」项目根基.md §7.3 自承"不在 TS 迁移范围"——这是技术债的公开承认。

### 命名不一致
- 文件命名：`floodStore.ts`（19 行）vs `floodState.ts`（143 行）——README 有解释但仍是混乱
- `mapStore.ts:83` 注释："map 存储地图引擎实例（OL Map / Cesium Viewer），非渲染器"——字段名 `map` 与 `currentRenderer` 同时存在，容易混淆

### 函数过长
- `CesiumRenderer.addPointLayer:394-434` + `_setupViewportListener:508-529` + `_updateCulledLayer:534-569` 视口裁剪逻辑分散在 3 个方法
- `floodAdapter.ts` 264 行单文件，包含 mock 映射+api 调用+fallback 逻辑

### 看似高级但无实际价值
- `logger.ts:19` transports 钩子 + `addLogTransport` 导出——全项目无人调用，是"预留扩展"
- `logger.js:31` backend audit 方法——grep 后仅在 authController 等少数地方调用
