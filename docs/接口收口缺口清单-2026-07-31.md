# 前端 × 后端 接口契约收口缺口清单

> 评审日期：2026-07-31
> 评审范围：`frontend/src` 请求层 + `backend/routes`、`backend/controllers`
> 目的：定位"请求方式 / 传参方式 / 后端接收 / 响应契约"中尚未统一之处，支撑阶段一架构收口。

## 0. TL;DR（直接结论）

| 维度 | 结论 |
|---|---|

## 1. 已收口（先肯定，避免只挑刺）

1. **统一传输 `apiRequest`**：`frontend/src/shared/composables/useApiRequest.ts:50` 用单例 `fetch` 封装了 Cookie 鉴权（`credentials:'include'`）、10s 超时、 abort、错误归一化（`ApiError` + `ErrorCode`）。所有后端调用方（`useSiteAnalysisApi`、`useForecastRequest`→`forecastAdapter`、`floodAdapter`、`usePlans`、`useAuth`、`WaterLevelProfilePanel`）都经它，无第二套"后端 API transport"。这是收口做得对的地方。
2. **错误.message 提取一致**：后端错误统一带 `{ error }`（手写或全局中间件），`useApiRequest.ts:97-104` 统一读 `data.error` 抛 `ApiError`，错误文案消费侧基本一致。
3. **鉴权通道统一**：前端不传 Bearer，统一靠 HttpOnly Cookie（`useApiRequest.ts:56-57`），后端 `authenticate` 中间件一致挂载。

## 2. 未收口清单（按严重度排序）

### 🔴 P1-1｜响应契约分裂：信封 vs 裸体（最该收口）

**现象**：后端成功响应有两种形状，前端被迫跟着分裂。

| 阵营 | 后端实现 | 前端消费方式 |
|---|---|---|
| 信封式 `{code,data}` | `forecastController.js:21,34,45,56,73`、`floodAnalysisController.js`（全文 `res.json({code:200,data,...})`） | `forecastAdapter.ts:211/244/300` 读 `resp.data`；`WaterLevelProfilePanel.vue:128-130` 自读 `result.code/result.data` |
| 裸体式 `res.json(data)` | `siteAnalysisController.js:74`、`plansController.js:7/25/62/94...`、`authController.js:52/94/124`、`facilitiesController.js`、`markersController.js` | `useSiteAnalysisApi.ts:39-44` 直接读 `result.coverage`；`usePlans.ts:19` 直接当数组；`useAuth.ts:61` 读 `data.user` |

**证据**：
- `useApiRequest` **不做信封解包**（`useApiRequest.ts:112` 直接 `return data as T`，返回整包）。
- 于是"解包责任"甩给每个调用方：forecast/flood 阵营要 `.data`，site-analysis/plans 阵营不要。新人给任一接口改阵营都会静默炸。

**风险**：调用方必须"记住每个接口属于哪一阵营"，契约无单一真相；新增接口极易复制错模板。

**收口建议（二选一，推荐全量信封化）**：
- 后端新增 `wrapResponse(data)` 工具（`backend/utils/response.js`），所有成功响应统一 `res.json({ code: 200, data })`；site-analysis/plans/auth/facilities/markers 补齐信封。
- 前端在 `useApiRequest` 内做**自动解包**：若返回体含 `code===200 && 'data' in body` 则 `return body.data`，调用方永远拿 `T`。`WaterLevelProfilePanel.vue:62` 那个本地 `ApiResponse<T>` 即可删掉。

**优先级**：P1 ｜ 预期收益：高 ｜ 估算工时：0.5–1 天（含全量回归）

---

### 🔴 P1-2｜同一概念两种传参姿势：`waterLevel` 的 query vs body

**现象**：flood 模块里同一个"水位"参数，前端两种传法、后端两种接法。

| 调用 | 前端传参 | 后端接收 |
|---|---|---|
| `floodAdapter.getFloodAnalysis` (`floodAdapter.ts:224-231`) | `GET /flood/flood-areas?waterLevel=${waterLevel}`（**query**） | `floodAnalysisController.js:72` `req.query.waterLevel` |
| `floodAdapter.getImpactAssessment` (`floodAdapter.ts:269-275`) | `POST /flood/analysis/disaster` body `{waterLevel}`（**body**） | `floodAnalysisController.js:211` `req.body.waterLevel` |

**风险**：同一语义字段在前端两套序列化、后端两套解析；后续接真实水位计算时，规则漂移风险高（比如一处 `parseFloat` 一处 JSON 已解析）。

**收口建议**：明确约定「查询类 GET 用 query、写/分析类 POST 用 body」，并把 `waterLevel` 在两侧统一为同一来源。getFloodAnalysis 是只读查询→保持 query；getImpactAssessment 是分析写操作→保持 body 合理，但**字段名与校验逻辑应抽到共享 `validateWaterLevel`**（后端已有 `floodAnalysisController.js:30` 的 `validateWaterLevel`，前端无对应，建议两端共用同一契约定义）。

**优先级**：P1 ｜ 预期收益：中 ｜ 估算工时：0.25 天

### 🟠 P2-1｜GET 参数手写模板字符串，无统一 query 构造

**现象**：所有 GET 查询参数都是字符串拼接，无 `URLSearchParams` / 编码处理。

- `forecastAdapter.ts:210` `` `/forecast/timeseries?indicator=${indicator}&granularity=${granularity}&confidence=${confidence}` ``
- `forecastAdapter.ts:243` `` `/forecast/indicator/${indicator}?time=${time}&confidence=${confidence}` ``
- `floodAdapter.ts:225` `` `/flood/flood-areas?waterLevel=${waterLevel}` ``

**证据**：全仓除 `spatialIndex.ts` 外无 `URLSearchParams` 使用（已 grep 确认）。

**风险**：参数含中文/空格/特殊字符会拼出错误 URL（当前都是英文 id，暂未爆，但属隐患）；且 body 用 `JSON.stringify`、query 用手写模板，两套序列化方式。

**收口建议**：给 `useApiRequest` 增加 `params` 选项，内部用 `URLSearchParams` 拼 query（`apiRequest(path, { params: { indicator, granularity, confidence } })`），调用方不再手写 `?`。

**优先级**：P2 ｜ 预期收益：中（健壮性+可读性）｜ 估算工时：0.25 天

---

### 🟠 P2-2｜后端缺统一入参校验层，且 site-analysis/auth 不走全局错误中间件

**现象**：
1. 各 controller 自写 `if (!x) throw BusinessError`（校验逻辑分散）。
2. `siteAnalysisController.js:9-11,19,32...` 与 `authController.js:30,33,36,41...` 直接 `res.status(400).json({ error })`，**绕过**全局中间件；而其他 controller 统一 `throw BusinessError → next(error)`（`forecast/flood/plans/facilities/markers`）。
3. 错误信封不统一：手写的是 `{ error }`，全局中间件返回 `{ code, error }`（`app.js:76`）。

**风险**：错误响应形状依赖"哪个 controller 写的"，前端可靠 `.error` 但 `.code` 缺失时不统一；校验规则散落易漂移。

**收口建议**：
- 引入轻量校验层（中间件或 service 内 `validateXxx` 函数），把"方案参数 schema"抽为共享模块——`siteAnalysisController.js`（校验 importance 1–5、radius>0、weights 0–10）与 `plansController.js`（仅校验 name）当前各写一套，规则可能漂移，应复用同一份。
- `siteAnalysis`/`auth` 改为 `throw new BusinessError(...)` 统一走 `app.js:73` 全局中间件，删除手写 `res.status(400)`。

**优先级**：P2 ｜ 预期收益：中 ｜ 估算工时：0.5 天

---

### 🟠 P2-3｜静态资源加载是"第二套 fetch"，且与 API 通道不互认

**现象**：以下均用裸 `fetch` 直连 `public/data` / `*.geojson`，各自实现超时/缓存/重试：

| 位置 | 用途 | 超时 | 缓存 |
|---|---|---|---|
| `mapDataService.ts:13` `fetchData` | 港口/边界 GeoJSON | 10s | Map TTL 5min |
| `useBoundaryLayer.ts:49` | 边界 GeoJSON | 10s + 重试3次 | sessionStorage 24h |
| `forecastAdapter.ts:127/135/264` `_fetchMock*` | forecast fixture | **无超时** | 无 |
| `floodAdapter.ts:37/65` `_fetchMock*` | flood fixture | 10s | 仅 waterArea 内存 |

**风险**：静态加载逻辑与 `apiRequest` 重复且**不一致**（forecast mock 甚至无超时）；没有"静态资源加载器"抽象，三套缓存策略（Map / sessionStorage / 内存）互不认。

**收口建议**：是否收口取决于你如何定义"数据源"——若把静态 fixture 也视作一种数据源，应抽一个 `loadStatic(path)`（统一超时 + 可选 cache），让 `mapDataService` / adapter mock 分支复用，而不是各自 `fetch`。属"一致性收敛"，非紧急 bug。

**优先级**：P2 ｜ 预期收益：低-中 ｜ 估算工时：0.5 天

---

### 🟡 P2-4｜数据源切换（mock/api）散落在各 adapter 的 `if (_dataSource==='mock')`

**现象**：`forecastAdapter.ts:123` 与 `floodAdapter.ts:14` 各自维护独立 `_dataSource` 变量，切换逻辑写在每个方法内；无统一开关、无 env 驱动、无 UI 切换（工作记忆已记）。

**收口建议**：把"数据源策略"提升为统一抽象（一个 `DataSourceSwitch` 或配置项 + 每 adapter 实现 `mock`/`api` 两策略），消除各 adapter 内部的 `if/else` 重复。

**优先级**：P2 ｜ 预期收益：低 ｜ 估算工时：0.5 天

## 4. 推荐收口顺序（贴合你已有的"阶段一 架构收口"纲领）

1. **先做 P1-1（响应契约）**：这是根因——`apiRequest` 不解包 + 后端两派响应，导致上层所有调用方都"半收口"。改完它，forecast/flood 的 `.data` 与 site-analysis/plans 的裸体能在前端统一。
2. **P1-2 + P2-1 一起做**：传参姿势统一（waterLevel 约定 + query 构造工具），前端传、后端接一次性对齐。
3. **P2-2**：把 site-analysis/auth 的错误返回并入全局中间件，并抽共享校验 schema，消除"方案参数"规则漂移。
4. **P2-3 / P2-4**：静态加载与数据源切换的一致性收敛，收益偏"整洁度"，可后置。

> 一句话：你现在的 `apiRequest` 把"传输"收口了，但"契约"（响应怎么包、参数怎么传、后端怎么接、错误怎么回）还停在"各模块自洽"阶段——这正是阶段一要补的 API Client / Error Handler 那一层。
