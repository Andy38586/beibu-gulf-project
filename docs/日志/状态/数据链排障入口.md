# 数据链故障定位手册（排障入口，2026-10-27 立 · W06）

> 本件即专项1 指标 7.1–7.4 要求的「排障手册」。治的失效：`git grep -lE '排障手册|故障定位手册|定位链路' -- docs ':!docs/archive' ':!docs/根基文档'`
> 长期 0 命中 ⇒ 「面板没数据」这类报障只能靠翻代码定位。
> 本文只给**入口与顺序**，不复述端点路径——路径一律取 `frontend/src/shared/constants/api.ts` 的 `ENDPOINTS`
> 与 `backend/src/routes.manifest.ts`（两处是权威，本文件抄一份就是第二份死数）。

## 一、面板没数据（先说清「请求发没发」）

1. **看前端有没有出站**：dev 控制台搜 `[apiRequest:<rid>]`（`useApiRequest.ts` 的 dev 日志）。
   没有该行 ⇒ 请求没发，问题在调用点/前置开关，不在后端。
2. **拿 rid 反查后端**：同一 rid 写在请求头 `x-request-id`（`useApiRequest.ts` 写入、
   `business-error.filter.ts` 读取）。`docker compose logs --tail=500 nest | grep '<rid>'`，
   有该 rid 的行 = 后端收到了；没有 = 卡在 nginx/前缀。
3. **绕开前端直打**：`curl -i -H 'x-request-id: probe-1' "http://127.0.0.1:3000/nest-api<ENDPOINTS 里的 path>"`
   （ENDPOINTS 的值就是相对路径）。200 但有数据 ⇒ 问题在前端渲染；4xx/5xx ⇒ 看响应信封的 `code`。

## 二、接口 200 但页面报错/空白（多半是契约不符）

1. `npm run types:check` —— schema 与 `@backend-contract` 注解的字段集合/可选性比对。
2. `npm run contract:check` —— Swagger 文档 ↔ 前端 `ENDPOINTS` 双向断言。
3. zod 拒绝时前端**不重试**（`useApiRequest.ts` 的「响应数据错误重试无意义」分支）⇒
   日志里只有 `schema 校验失败`，与「后端 bug」难区分：把该条响应的 `code`/`error` 一并带走。

## 三、数据更新了但 UI 不变（图层/响应式面）

1. `node tools/v3-guard/layer-keys.mjs` —— 图层 key 是否裸写（改了 key 而消费方没改）。
2. `node tools/v3-guard/owned-layers.mjs` —— 图层注册/注销是否成对（漏 unregister 会「旧图层盖住新数据」）。
3. `npm run cruise` —— 分层方向是否被新 import 破坏（0 违规才算过）。
4. 后端数据文件本身：`ls -l backend/data/flood/`（一次性迁移后 DB 是唯一真源，JSON 只剩只读残留）。

## 失效条件

- `useApiRequest.ts` 的 rid 日志与 `x-request-id` 头任一被改名/删除 ⇒ 第一条链断裂，本文需同笔改。
- 端点前缀再变（D1a 之后为单前缀 `/nest-api`）⇒ 第三条 curl 示例失效。
- 本文件与 `docs/根基文档/核心流程与数据流.md` 冲突时，以该文与 K2 契约为准（本文只是入口，不是权威）。
