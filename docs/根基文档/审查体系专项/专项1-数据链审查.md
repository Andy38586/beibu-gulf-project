# 数据链专项审查指标体系

> 版本：v1.0
> 定位：项目代码深度审查体系的数据链专项，可独立并行执行
> 与审查体系关系：见 `00-审查体系约定.md`（一级质量属性 #2 数据链完整性）
> 适用：AI 辅助代码审查、数据链故障根因定位、接口治理专项、上线前数据正确性体检
> 聚焦范围：数据从来源 → 传输 → 转换 → 消费 → 销毁的完整生命链，以及链路上的请求治理
> 原则约束：所有结论必须来自真实代码证据；每一跳必须可追溯；不依赖具体技术栈

---

## 0. 文档使用说明

### 0.1 文档定位

本文档是「数据链专项审查标准库」，是审查体系 8 专项之一（见 `00-审查体系约定.md` §3）。

本专项覆盖数据链全链路 51 个指标：
- 数据来源的每一个真实出处
- 数据传输链路的每一跳
- 数据转换的每一个字段
- 数据消费的每一次渲染
- 数据生命周期的每一次清理
- 数据一致性与污染的每一处隐患
- 典型数据问题的根因定位链路
- 请求与接口的治理细节

本专项可与生命周期专项、TS 专项、WebGIS 专项、工程化专项、架构耦合专项并行执行，互不依赖结论，但可交叉引用指标编号。

### 0.2 与其他专项的边界

本专项**只管数据链**：数据从哪来、怎么传、怎么转、怎么用、怎么清、是否被污染、典型问题如何定位、请求如何治理。

本专项**不管**以下内容（属于其他专项）：
- 类型覆盖率与 any 治理 → TS 专项（仅本专项 6.1 关注前后端类型定义一致性这一数据链层面）
- 变量作用域与对象销毁的工程细节 → 生命周期专项（本专项仅在 5.4/5.6 引用）
- 地图实例销毁、图层渲染性能 → WebGIS 专项
- 目录结构、模块边界、循环依赖 → 架构耦合专项
- 构建配置、CI、Docker → 工程化专项

当本专项审查中发现跨域问题时，会标注「转 XX 专项」（如「详见专项2 生命周期」）。

### 0.3 指标条目格式约定

每一个指标采用 `00-审查体系约定.md` §2 的 11 字段结构：

```
指标名称：该指标的唯一标识名
检查目标：这个指标要确认什么事实
为什么需要检查：不检查会带来什么风险
检查范围：该指标适用于哪些代码实体
检查方法：具体如何执行检查（步骤化）
需要查看：必须阅读哪些证据材料
正常标准：满足什么条件算通过
异常情况：出现什么现象算不通过
风险等级：P0 / P1 / P2 / P3
整改方向：发现问题后的修复路径
验收标准：整改完成后如何证明已修复
```

### 0.4 风险等级定义

见 `00-审查体系约定.md` §1（判据与处置），本专项不再重复定义，仅引用：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

本专项中以下情况直接判 P0：
- 数据来源不明（无法追溯数据真实出处）
- 坐标系错误（GIS 数据未做坐标转换直接渲染）
- 假数据混入正式路径（mock/fake/dummy 进入生产链路）
- 生产构建包含 mock 模块
- 接口字段与渲染字段错位导致数据展示错误

### 0.5 本专项核心原则

**原则 1：每一跳可追溯**
- 数据链路上每一跳都必须能定位到具体的文件、函数、行号
- 无法追溯的跳转视为链路黑盒，必须标记为风险点
- 严禁「数据不知道从哪里冒出来」的隐式来源

**原则 2：真数据优先**
- 任何审查结论必须基于真实接口、真实数据库、真实文件
- mock/假数据/测试数据必须显式隔离，禁止混入正式路径
- 静态数据文件必须能证明其与真实业务数据一致

**原则 3：链路完整性**
- 数据从来源到消费的链路必须能完整画出
- 缺失任一环节（如缺 adapter、缺 service）视为断链
- 多余环节（如反复转换）视为冗余链

**原则 4：消费对齐**
- 数据最终在 UI 的渲染必须与接口字段、单位、坐标系、时间格式严格对齐
- 字段名不一致、单位错误、坐标系错误均视为数据链断裂

**原则 5：生命周期闭环**
- 数据有创建就必须有清理，有写入就必须有失效
- 只 set 不 clear、只 add 不 remove 视为生命周期缺陷

**原则 6：可观测**
- 链路关键节点必须有日志或埋点
- 无可观测点的链路无法定位故障根因，视为诊断能力缺失

### 0.6 Agent 并行执行契约（2026-08-11 统一改造）

- **独立线程**：本专项可单独作为一条 agent 审查线程执行，与其余专项**零执行依赖**（支持 8 窗口并行）；跨专项交叉点见 0.2 边界表，仅在产出层面汇总，不在执行层面依赖。
- **输入**：本文档（可按「部分」切片，仅加载本子 agent 负责的部分）+ 对应代码范围 + 设计文档对应章节（见 `00-审查体系约定.md` §4「标准输入资产」，本专项映射：02 一/二 R1-R5/三 R6-R8/4.1-4.3；01 3.3/五.7；03 四 API 契约）。
- **输出**：发现清单（每条含：指标编号 / 证据 file:line / 风险等级 / 整改建议）→ 写入 `docs/audits/<日期>-<批次名>/专项1-数据链审查-问题副本.md`（产出统一规范见 `00-审查体系约定.md` §4；副本规则见 docs/待解决问题.md 头部），经用户裁决转正主台账；执行记录存同批次目录 `专项1-数据链审查-执行记录.md`（模板见 §0.7）。
- **子 agent 拆分**：按「第 X 部分」切分（拆分规则见 `00-审查体系约定.md` §4：① 1 部分=1 子 agent；② 相邻部分证据重叠>50% 可合并；③ 单专项上限 6；④ 禁止二次拆分）。
  - 本专项 8 部分共享 service/store 证据，建议 **4–5 个**子 agent（来源+传输 合 1、转换 1、消费+一致性 合 1、生命周期 1、诊断+请求治理 合 1）。
  - 每个子 agent 领 1 个切分单元独立执行（输入 = 该单元指标 + 对应代码），主 agent 汇总去重、合并同根因、统一定级。
- **格式约定**：结论必须来自真实代码证据（file:line）；指标编号用本文档编号（如 3.2）；跨专项引用写「专项N X.Y」；**禁止使用草稿/临时编号**（唯一合法编号 = 台账编号体系）。

## 第一部分：数据来源审查

> 目标：还原项目所有数据的真实出处，回答「每一类数据到底从哪里来」「真数据还是假数据」
> 本部分是整个数据链审查的起点，来源不清则后续全链路审查无意义

### 指标 1.1：前端数据获取入口全量清单

**指标名称**：前端数据获取入口全量清单
**检查目标**：确认前端所有数据获取入口都被识别并记录，不存在「游离的数据获取点」
**为什么需要检查**：游离的数据获取点是「数据来源不明」「绕过统一封装」「安全漏洞」的来源；若清单不全，则后续链路审查必然漏项
**检查范围**：前端所有源码文件，重点关注 `fetch`、`axios`、`XMLHttpRequest`、`import 静态 JSON`、`WebSocket`、`EventSource`、`postMessage`、`localStorage/sessionStorage 读取`
**检查方法**：
1. 全局搜索 `fetch(`、`axios`、`request(`、`http.` 等所有可能发起请求的关键字，输出调用点清单
2. 全局搜索 `import .* from .*\.json`，输出所有静态数据导入点
3. 全局搜索 `new WebSocket`、`new EventSource`、`postMessage`、`localStorage.getItem`、`sessionStorage.getItem`，识别非常规数据来源
4. 对每个调用点标注：所在文件、行号、获取的数据类别、是否经过 service 层封装
5. 检查是否存在直接在组件 / view 中调用而非经过 service 层的获取点
6. 汇总输出「前端数据获取入口清单」表格
**需要查看**：源码全量搜索结果、services 目录、dataSourceConfig、组件 / view 文件
**正常标准**：
- 所有数据获取入口均有清单记录，含文件路径、行号、数据类别
- 所有 HTTP 请求统一经过 service 层封装（无组件内直接 fetch / axios）
- 静态 JSON 导入集中在 dataSourceConfig 或 data 目录管理
- WebSocket / EventSource / postMessage 等非常规来源单独列出
**异常情况**：
- 组件内直接调用 `fetch` / `axios`（绕过 service 层）
- 存在清单外的数据获取点（搜索发现但清单未收录）
- 同一数据有多个获取入口且实现不一致
- 使用未封装的 `XMLHttpRequest` 或第三方请求库且未收口
**风险等级**：P1
**整改方向**：所有数据获取收口到 service 层；建立 dataSourceConfig 统一管理；游离获取点归并到统一入口
**验收标准**：前端数据获取入口清单完整且与代码搜索结果一致；无组件内直接请求；所有入口经 service 封装

### 指标 1.2：后端数据返回点全量清单

**指标名称**：后端数据返回点全量清单
**检查目标**：确认后端所有对外返回数据的接口都被识别并记录，不存在「未登记的对外接口」
**为什么需要检查**：未登记的接口是「前端调用了无文档接口」「接口被废弃但仍在用」「安全漏洞」的来源
**检查范围**：后端所有 controller / route / handler / view 函数，以及所有返回 JSON / 数据的端点
**检查方法**：
1. 列出所有 controller 类 / route 文件 / handler 模块
2. 对每个 controller 提取所有 `@GetMapping` / `@PostMapping` / `router.get` / `router.post` 等路由注解
3. 检查每个端点的返回类型与实际返回内容
4. 标注每个端点：路径、方法、返回数据类别、是否需要鉴权、是否有前端消费者
5. 检查是否存在「无前端消费者」的端点（可能是废弃接口或后门）
6. 检查是否存在「前端调用了但后端无对应路由」的情况
7. 汇总输出「后端数据返回点清单」并与前端入口清单对账
**需要查看**：后端 controller / route 文件、API 文档、路由配置、鉴权中间件
**正常标准**：
- 所有对外端点均有清单记录，含路径、方法、返回类型、鉴权要求
- 每个端点都有文档说明（至少在 API 契约文档中登记）
- 每个端点都有对应的前端消费者（或明确标注为内部接口）
- 前端调用清单与后端端点清单能对账
**异常情况**：
- 存在前端调用但后端无对应路由的端点
- 存在后端有路由但无前端消费者的端点（废弃或后门）
- 端点未在 API 文档登记
- 端点无鉴权但返回敏感数据
**风险等级**：P1
**整改方向**：废弃端点删除；未文档化端点补文档；前后端清单对账；缺失鉴权端点补鉴权
**验收标准**：后端端点清单完整；与前端调用清单对账一致；所有端点有文档；废弃端点已清理

### 指标 1.3：后端数据来源真实性

**指标名称**：后端数据来源真实性
**检查目标**：确认后端每个接口返回的数据真实来自数据库 / 文件 / 第三方接口，而非硬编码或 mock
**为什么需要检查**：后端返回硬编码数据但前端以为是数据库查询，会导致「上线后数据不更新」「数据永远相同」等严重问题；这是数据链最致命的来源错误
**检查范围**：后端所有 service / repository / handler 的返回逻辑
**检查方法**：
1. 对每个后端端点，追踪其调用链：controller → service → repository → 数据源
2. 检查 service 中是否存在直接 `return { ... }` 返回硬编码对象的情况
3. 检查 repository 是否真正查询数据库 / 读取文件 / 调用第三方
4. 检查返回数据是否含明显的「测试值」特征（如 `name: "测试"`、`value: 123`）
5. 检查是否存在 `// TODO: 替换为真实查询` 之类的注释
6. 对每条数据来源标注：数据库表 / 文件路径 / 第三方接口 URL / 硬编码 / mock
**需要查看**：后端 service 实现、repository 实现、数据源配置、数据库连接配置
**正常标准**：
- 每条业务数据都有真实数据源（数据库 / 文件 / 第三方）
- 无硬编码业务数据返回
- 无 `// TODO: 替换为真实数据` 残留
- 数据源有配置化管理（不硬编码连接串）
**异常情况**：
- service 直接返回硬编码对象（如 `return [{ id: 1, name: "测试站" }]`）
- repository 返回固定值而非真实查询
- 返回数据含「测试」「示例」「demo」字样
- 数据源连接串硬编码在代码中
**风险等级**：P0
**整改方向**：硬编码数据改为真实查询；TODO 替换为真实实现；连接串配置化
**验收标准**：每条数据可追溯至真实数据源；无硬编码业务数据；无 TODO 残留

### 指标 1.4：mock 数据隔离检查

**指标名称**：mock 数据隔离检查
**检查目标**：确认 mock 数据通过环境开关或构建配置严格隔离，不会进入生产路径
**为什么需要检查**：mock 未隔离是「上线后展示假数据」的直接原因，是数据链最严重的污染源
**检查范围**：mock 目录、mock 文件、mock 开关、构建配置（vite.config / webpack.config / tsconfig）
**检查方法**：
1. 列出所有 mock 相关文件与目录（`mock/`、`*.mock.ts`、`__mocks__/`）
2. 检查 mock 是否通过环境变量（如 `VITE_USE_MOCK`）或构建标志控制
3. 检查生产构建配置是否显式排除 mock 模块（如 `import.meta.env.DEV` 守卫、tree-shaking 配置）
4. 检查 mock 模块是否被业务代码直接 import（而非通过开关条件 import）
5. 检查 mock 与真实 service 是否实现同一接口（可替换性）
6. 在生产构建产物中搜索 mock 关键字，验证是否真的被排除
**需要查看**：mock 文件、构建配置、环境变量定义、service 实现、构建产物
**正常标准**：
- mock 数据通过环境开关或构建配置严格隔离
- 业务代码不直接 import mock 模块（通过开关条件引入）
- 生产构建产物中不含 mock 关键字
- mock 与真实 service 实现同一接口契约
- mock 开关默认关闭（生产环境）
**异常情况**：
- mock 模块被业务代码直接 import（无条件）
- mock 开关默认开启
- 生产构建产物中仍含 mock 代码
- mock 与真实 service 接口不一致（字段对不上）
- 无 mock 隔离机制
**风险等级**：P0
**整改方向**：mock 收口到独立目录；通过环境开关条件引入；生产构建显式排除；mock 与 service 对齐接口
**验收标准**：mock 通过开关隔离；生产构建无 mock；mock 与 service 接口一致

### 指标 1.5：静态数据文件与接口数据的切换机制

**指标名称**：静态数据文件与接口数据的切换机制
**检查目标**：确认项目中使用静态 JSON 文件作为数据源的部分有明确的切换机制，能在静态与接口之间切换
**为什么需要检查**：GIS 项目常使用静态 GeoJSON / 配置文件作为兜底数据源，若无切换机制则会导致「数据永远不更新」或「切换时字段对不上」
**检查范围**：所有静态 JSON / GeoJSON / 配置文件导入点、dataSourceConfig、service 中的静态数据兜底逻辑
**检查方法**：
1. 列出所有静态数据文件导入点
2. 对每个静态数据导入，检查是否有对应的接口数据获取逻辑
3. 检查是否存在「静态优先 / 接口兜底」或「接口优先 / 静态兜底」的切换逻辑
4. 检查切换开关是否配置化（环境变量 / 配置文件）
5. 检查静态数据与接口数据的结构是否一致（字段名 / 类型对齐）
6. 检查静态数据是否有过期标识或更新机制（避免长期不更新）
**需要查看**：静态数据文件、dataSourceConfig、service 实现、环境变量配置
**正常标准**：
- 静态数据与接口数据有明确的切换机制
- 切换开关配置化
- 静态数据结构与接口数据结构一致
- 静态数据有更新机制或过期标识
**异常情况**：
- 静态数据直接 import 且无接口切换机制
- 切换开关硬编码（无法配置）
- 静态数据与接口数据结构不一致（字段名 / 类型不同）
- 静态数据长期未更新且无更新机制
**风险等级**：P1
**整改方向**：建立切换机制；配置化开关；静态数据结构对齐接口；定期更新静态数据
**验收标准**：静态与接口有切换机制；开关配置化；结构一致；有更新机制

### 指标 1.6：数据来源环境差异

**指标名称**：数据来源环境差异
**检查目标**：确认开发环境与生产环境的数据来源配置差异明确，不会因环境切换导致数据来源错乱
**为什么需要检查**：开发用 mock / 本地数据，上线后切真实接口但配置不一致，会导致「开发好好的上线就崩」
**检查范围**：环境变量配置（.env.development / .env.production）、dataSourceConfig、API base URL 配置
**检查方法**：
1. 列出所有环境变量文件（.env.*）
2. 对比开发与生产的 API base URL、mock 开关、数据源配置
3. 检查是否存在「开发用 mock、生产用真实」但配置未对齐的情况
4. 检查是否存在硬编码的 `localhost` / 内网 IP 出现在生产配置中
5. 检查环境变量是否有 `.env.example` 模板
6. 检查是否有环境变量缺失时的默认值兜底逻辑
**需要查看**：.env 文件、构建配置、dataSourceConfig、API 配置
**正常标准**：
- 开发与生产环境配置明确分离
- 环境变量有 .env.example 模板
- 无硬编码的 localhost / 内网 IP 进入生产
- 环境变量缺失有默认值或明确报错
**异常情况**：
- 开发与生产共用一份配置
- 生产配置含 localhost / 内网 IP
- 无 .env.example 模板
- 环境变量缺失时静默使用错误默认值
**风险等级**：P1
**整改方向**：环境配置分离；补 .env.example；移除硬编码地址；缺失时明确报错
**验收标准**：环境配置分离；有模板；无硬编码地址；缺失有兜底

### 指标 1.7：数据来源文档化

**指标名称**：数据来源文档化
**检查目标**：确认每一类业务数据的来源都有文档记录，新人能通过文档快速理解数据出处
**为什么需要检查**：数据来源无文档会导致新人无法快速定位问题、交接困难、知识沉淀缺失
**检查范围**：API 契约文档、数据字典、项目根因文档、模块说明
**检查方法**：
1. 检查是否有 API 契约文档，并核对文档中的接口与代码中的实际接口是否一致
2. 检查是否有数据字典，列出所有业务实体及其字段含义
3. 检查关键模块是否有说明文档，标注数据来源
4. 检查文档与代码是否同步（文档落后于代码视为不同步）
5. 检查文档是否标注数据来源的责任人 / 维护方
**需要查看**：API 契约文档、数据字典、模块 README、项目根因文档
**正常标准**：
- 有 API 契约文档且与代码同步
- 有数据字典
- 关键模块有数据来源说明
- 文档标注维护责任人
**异常情况**：
- 无 API 契约文档或文档严重落后于代码
- 无数据字典
- 关键模块无数据来源说明
- 文档无维护责任人
**风险等级**：P2
**整改方向**：补全 API 契约文档；建立数据字典；模块补充数据来源说明；标注维护人
**验收标准**：有 API 契约文档且与代码同步；有数据字典；模块有来源说明

## 第二部分：数据传输链路审查

> 目标：还原数据从来源到消费的完整传输链路，回答「数据每一跳经过哪些环节」「是否有断链或冗余」
> 本部分是数据链审查的核心，链路完整性决定数据正确性

### 指标 2.1：完整数据链路可画出性

**指标名称**：完整数据链路可画出性
**检查目标**：确认对每条核心业务数据，都能画出从数据源到 UI 渲染的完整链路图
**为什么需要检查**：画不出链路就意味着链路不清晰，是「数据来源不明」「断链」「冗余跳转」的根因；链路图是数据链审查的基础产出
**检查范围**：所有核心业务数据（如地图图层、面板数据、列表数据、统计图表数据）
**检查方法**：
1. 选取每条核心业务数据
2. 从 UI 渲染组件反向追踪：组件 → store → adapter → service → HTTP 请求 → 后端 controller → service → repository → 数据源
3. 在每一跳标注：文件路径、函数名、行号、数据结构
4. 检查是否能完整画出（无「黑盒跳转」）
5. 输出链路图（文字版或图示）
6. 对每条链路标注是否完整、是否有断点
**需要查看**：组件模板、store 实现、adapter 实现、service 实现、后端代码、数据源
**正常标准**：
- 每条核心业务数据都有完整链路图
- 链路图含每一跳的文件路径与函数名
- 链路无黑盒跳转
- 链路图与代码实际调用关系一致
**异常情况**：
- 某条数据无法追溯到源头（链路画不完整）
- 链路中存在「数据凭空出现」的环节
- 链路图与实际代码不一致
- 多条数据共用一条链路但未在图中标注
**风险等级**：P1
**整改方向**：补全断链环节；建立链路图文档；定期与代码同步
**验收标准**：每条核心数据有完整链路图；链路图与代码一致；无黑盒跳转

### 指标 2.2：链路环节完整性（无断链）

**指标名称**：链路环节完整性（无断链）
**检查目标**：确认数据链路中每一跳都存在且符合分层规范，不存在跳过的环节
**为什么需要检查**：跳过环节是「接口成功但页面错误」「数据未经转换直接消费」的根因
**检查范围**：所有数据链路，重点检查是否跳过 service / adapter / store
**检查方法**：
1. 对每条链路，检查是否经过：service 层（数据获取）→ adapter 层（数据转换）→ store（状态管理）→ 组件（消费）
2. 检查组件是否直接调用 service 而绕过 store（应通过 store 管理状态）
3. 检查组件是否直接 fetch 绕过 service
4. 检查是否缺少 adapter（组件直接消费原始接口字段）
5. 检查后端是否缺少 service 层（controller 直接调 repository）
6. 对每个缺失环节评估：是合理的简化还是断链
**需要查看**：链路图、各层代码、组件 import 关系
**正常标准**：
- 链路环节完整：service → adapter → store → 组件
- 缺失环节有合理理由（如简单只读数据可省 store）
- 无组件直接 fetch 绕过 service
- 无组件直接消费原始接口字段（应经 adapter）
**异常情况**：
- 组件直接 fetch 后端接口
- 组件直接消费原始接口字段（无 adapter 转换）
- 后端 controller 直接调 repository 跳过 service
- store 被绕过（组件直接调 service 并本地管理状态）
**风险等级**：P1
**整改方向**：补全缺失环节；统一链路模式；简化需有合理理由
**验收标准**：链路环节完整；缺失环节有合理理由；无绕过

### 指标 2.3：链路环节无冗余（无多余转换）

**指标名称**：链路环节无冗余（无多余转换）
**检查目标**：确认数据链路中不存在多余的转换环节，数据未被反复转换
**为什么需要检查**：多余转换会增加性能开销、增加维护成本、增加 bug 风险（每次转换都可能出错）
**检查范围**：所有数据链路，重点检查 adapter / mapper / 转换函数的调用次数
**检查方法**：
1. 对每条链路，统计转换次数（adapter 调用、字段重命名、格式化）
2. 检查是否存在「adapter 转换后 store 又转换一次」
3. 检查是否存在「service 转换后 adapter 又转换一次」
4. 检查是否存在「同一字段在多处被重复格式化」
5. 检查是否存在「转换后又转回去」的来回转换
6. 对每个冗余转换评估是否可合并或移除
**需要查看**：链路图、adapter 实现、store 实现、service 实现
**正常标准**：
- 每条链路的转换次数合理（通常 1-2 次）
- 无反复转换
- 同一字段无重复格式化
- 转换有明确职责（如 adapter 负责字段映射，store 不再转换）
**异常情况**：
- adapter 转换后 store 又转换
- 同一字段在 service / adapter / store / 组件各格式化一次
- 转换后又转回去
- 转换职责重叠
**风险等级**：P2
**整改方向**：合并转换；明确转换职责；移除冗余转换
**验收标准**：链路无冗余转换；转换职责明确

### 指标 2.4：绕过 service 的直接调用

**指标名称**：绕过 service 的直接调用
**检查目标**：确认不存在组件 / view 直接调用 fetch / axios 或直接访问后端的情况
**为什么需要检查**：绕过 service 会导致请求逻辑散落、无法统一错误处理、无法统一鉴权、无法统一缓存
**检查范围**：所有组件 / view 文件
**检查方法**：
1. 在组件 / view 目录下搜索 `fetch(`、`axios`、`request(`、`http.`
2. 检查每个调用点是否在组件内（而非 service 内）
3. 检查是否有组件通过 `import` 直接引入 axios / fetch 工具
4. 检查是否有组件直接构造 URL 调用后端
5. 对每个绕过点评估：是合理简化还是违规
**需要查看**：组件 / view 源码、import 关系、service 目录
**正常标准**：
- 组件 / view 中无 fetch / axios 调用
- 所有请求经 service 层封装
- 组件不直接 import axios / fetch 工具
**异常情况**：
- 组件内直接调用 fetch / axios
- 组件直接构造 URL
- 组件直接 import 请求工具
**风险等级**：P1
**整改方向**：将请求逻辑迁移到 service 层；组件通过 service 获取数据
**验收标准**：组件 / view 中无直接请求调用；所有请求经 service 封装

### 指标 2.5：绕过 adapter 的字段直接消费

**指标名称**：绕过 adapter 的字段直接消费
**检查目标**：确认组件不直接消费接口原始字段，所有字段消费都经过 adapter 转换
**为什么需要检查**：直接消费原始字段会导致「接口字段变了组件就崩」「前后端字段耦合」「无法做字段映射」
**检查范围**：所有组件模板、组件 script 中的字段访问
**检查方法**：
1. 列出每个组件使用的字段名
2. 对比接口返回的字段名
3. 检查组件是否直接使用接口字段名（如 `data.station_name` 而非经 adapter 转换为 `data.stationName`）
4. 检查是否有 adapter 但组件绕过 adapter 直接使用原始字段
5. 检查接口字段命名风格（snake_case / camelCase）与组件使用风格是否一致
**需要查看**：组件模板、接口响应、adapter 实现、类型定义
**正常标准**：
- 组件消费的字段都经过 adapter 转换
- 组件不直接使用接口原始字段名
- 接口字段命名与组件字段命名风格一致（或经 adapter 转换）
**异常情况**：
- 组件直接使用 `data.station_name` 等接口原始字段
- 有 adapter 但组件绕过
- 接口用 snake_case 组件用 camelCase 且无 adapter 转换
**风险等级**：P1
**整改方向**：补全 adapter；组件消费经 adapter 转换后的字段；字段命名风格统一
**验收标准**：组件消费字段均经 adapter；无直接使用接口原始字段

### 指标 2.6：每一跳的类型契约

**指标名称**：每一跳的类型契约
**检查目标**：确认数据链路每一跳都有明确的类型定义，类型契约贯穿全链路
**为什么需要检查**：类型契约缺失会导致「字段对不上」「类型不匹配」「运行时报错」；类型是数据链路的第一道防线
**检查范围**：service 返回类型、adapter 输入输出类型、store state 类型、组件 props 类型
**检查方法**：
1. 对每一跳检查是否有 TypeScript 类型定义
2. 检查 service 函数返回值是否有类型标注
3. 检查 adapter 函数的输入类型与输出类型
4. 检查 store state 的类型定义
5. 检查组件 props 的类型定义
6. 检查相邻跳的类型是否一致（service 返回类型 = adapter 输入类型；adapter 输出类型 = store state 类型）
7. 检查是否有 `any` 类型断点
**需要查看**：类型定义文件、service / adapter / store / 组件的类型标注
**正常标准**：
- 每一跳都有类型定义
- 相邻跳的类型一致
- 无 any 类型断点
- 类型定义有单一来源（不重复定义）
**异常情况**：
- 某一跳无类型定义
- 相邻跳类型不一致（如 service 返回 `any`，adapter 输入 `Station`）
- 使用 any 类型断开类型链
- 同一类型在多处重复定义
**风险等级**：P1
**整改方向**：补全类型定义；对齐相邻跳类型；移除 any；类型单一来源
**验收标准**：每一跳有类型；相邻跳类型一致；无 any 断点

### 指标 2.7：链路可观测点（日志 / 埋点）

**指标名称**：链路可观测点（日志 / 埋点）
**检查目标**：确认数据链路关键节点有日志或埋点，能在故障时定位根因
**为什么需要检查**：无可观测点的链路在故障时无法定位是哪一跳出问题，导致排障时间漫长
**检查范围**：service 请求 / 响应日志、adapter 转换日志、store 状态变更日志、组件错误日志
**检查方法**：
1. 检查 service 是否记录请求 URL、参数、响应状态、响应时长
2. 检查 service 是否记录请求失败与错误详情
3. 检查 adapter 是否记录转换前后的数据（开发环境）
4. 检查 store 是否记录状态变更（可借助 devtools）
5. 检查组件是否有错误边界或错误捕获
6. 检查日志是否有级别（debug / info / warn / error）
7. 检查生产环境日志是否会泄露敏感信息
**需要查看**：service 实现、日志工具、错误处理、组件错误边界
**正常标准**：
- service 记录请求与响应（含状态、时长）
- 失败请求有错误日志
- adapter 在开发环境记录转换
- 组件有错误边界
- 日志有级别
- 生产日志不泄露敏感信息
**异常情况**：
- service 无任何日志
- 请求失败静默（无日志）
- 组件无错误边界
- 日志无级别
- 生产日志输出敏感信息（token / 密码）
**风险等级**：P1
**整改方向**：补全链路日志；加错误边界；日志分级；生产脱敏
**验收标准**：链路关键节点有日志；失败有记录；有错误边界；日志分级且脱敏

## 第三部分：数据转换审查

> 目标：审查数据在链路中每一处转换的正确性，回答「字段映射是否完整」「空值是否处理」「转换是否可逆」
> 本部分直接影响数据消费的正确性，转换错误是「接口成功但页面错误」的根因

### 指标 3.1：adapter / mapper / converter 全量清单

**指标名称**：adapter / mapper / converter 全量清单
**检查目标**：确认项目中所有数据转换函数都被识别并记录
**为什么需要检查**：游离的转换函数是「字段映射不一致」「转换逻辑散落」的来源；清单不全则转换审查必然漏项
**检查范围**：所有 adapter / mapper / converter / transformer / formatter 文件与函数
**检查方法**：
1. 搜索所有 `adapter`、`mapper`、`converter`、`transformer`、`formatter`、`toXxx`、`fromXxx` 命名的文件与函数
2. 搜索所有形如 `function xxx(data: ApiXxx): Xxx` 的转换签名
3. 检查 service / store 中是否有内联的转换逻辑（未抽取为独立函数）
4. 对每个转换函数标注：输入类型、输出类型、转换方向、所在文件
5. 检查是否存在「同一业务实体有多个 adapter」的情况
6. 汇总输出「转换函数清单」
**需要查看**：adapter 目录、service / store 中的转换逻辑、类型定义
**正常标准**：
- 所有转换函数有清单记录
- 转换函数集中在 adapter / mapper 目录
- 同一业务实体的转换函数单一（无多个 adapter 转换同一实体）
- 转换函数命名规范（如 `adaptXxx`、`mapXxx`、`toXxx`）
**异常情况**：
- 转换逻辑内联在 service / store 中未抽取
- 同一实体有多个 adapter 且实现不一致
- 转换函数命名不规范（如 `handleData`、`processInfo`）
- 清单外存在游离转换函数
**风险等级**：P2
**整改方向**：转换逻辑抽取为独立函数；集中到 adapter 目录；统一命名
**验收标准**：转换函数清单完整；集中在 adapter 目录；命名规范

### 指标 3.2：转换函数类型契约

**指标名称**：转换函数类型契约
**检查目标**：确认每个转换函数有明确的输入类型与输出类型，类型契约完整
**为什么需要检查**：转换函数是类型链的衔接点，类型缺失会导致类型链断裂，运行时报错
**检查范围**：所有转换函数的签名
**检查方法**：
1. 检查每个转换函数的参数是否有类型标注
2. 检查每个转换函数的返回值是否有类型标注
3. 检查输入类型是否对应接口返回类型（如 `ApiStation`）
4. 检查输出类型是否对应业务领域类型（如 `Station`）
5. 检查是否有 `any` 类型作为输入或输出
6. 检查类型定义是否在独立 types 文件中管理
**需要查看**：转换函数签名、类型定义文件
**正常标准**：
- 每个转换函数有完整的输入输出类型
- 输入类型对应接口返回类型
- 输出类型对应业务领域类型
- 无 any 类型
- 类型定义在独立文件管理
**异常情况**：
- 转换函数参数无类型标注
- 返回值无类型标注
- 使用 any 类型
- 类型定义散落在转换函数内
**风险等级**：P1
**整改方向**：补全类型标注；移除 any；类型定义独立管理
**验收标准**：每个转换函数有完整类型契约；无 any；类型独立管理

### 指标 3.3：转换字段映射完整性（无静默丢弃）

**指标名称**：转换字段映射完整性（无静默丢弃）
**检查目标**：确认转换函数覆盖所有字段，不存在字段被静默丢弃的情况
**为什么需要检查**：字段静默丢弃会导致「接口返回了但页面没显示」「数据丢失」等隐蔽问题
**检查范围**：所有转换函数的字段映射逻辑
**检查方法**：
1. 对每个转换函数，列出输入类型的所有字段
2. 列出输出类型的所有字段
3. 检查每个输入字段是否在输出中有对应（或显式忽略并注释说明）
4. 检查每个输出字段是否在输入中有来源
5. 检查是否有字段被静默丢弃（既未映射也未显式忽略）
6. 检查是否有字段被「忘记映射」（输出类型有但转换函数未赋值）
**需要查看**：转换函数实现、输入输出类型定义
**正常标准**：
- 每个输入字段都有对应输出（或显式忽略并注释）
- 每个输出字段都有来源
- 无静默丢弃字段
- 显式忽略的字段有注释说明原因
**异常情况**：
- 输入字段被静默丢弃（未映射、未忽略）
- 输出字段无来源（转换函数未赋值）
- 大量字段被丢弃但无注释说明
**风险等级**：P1
**整改方向**：补全字段映射；显式忽略并注释；建立字段映射文档
**验收标准**：所有字段有映射或显式忽略；无静默丢弃；有字段映射文档

### 指标 3.4：转换空值处理（null / undefined / 空数组）

**指标名称**：转换空值处理（null / undefined / 空数组）
**检查目标**：确认转换函数正确处理 null / undefined / 空数组 / 空对象等边界情况
**为什么需要检查**：空值未处理会导致下游 NaN / 报错 / 白屏；接口返回空值是常见情况
**检查范围**：所有转换函数对空值的处理逻辑
**检查方法**：
1. 检查转换函数对 `null` 输入的处理（是否返回默认值或抛错）
2. 检查转换函数对 `undefined` 输入的处理
3. 检查转换函数对空数组 `[]` 输入的处理（是否返回空数组而非 undefined）
4. 检查转换函数对空对象 `{}` 输入的处理
5. 检查转换函数对字段缺失的处理（如 `data.field` 为 undefined）
6. 检查转换后的字段是否可能为 NaN（如 `Number(null)` → 0 但 `Number(undefined)` → NaN）
**需要查看**：转换函数实现、空值处理逻辑
**正常标准**：
- 转换函数对 null / undefined 有处理（返回默认值或抛错）
- 空数组返回空数组
- 字段缺失有兜底
- 转换后无 NaN 风险
**异常情况**：
- 转换函数未处理 null / undefined
- 空数组转换为 undefined
- 字段缺失导致 NaN
- 转换后字段为 NaN 但未处理
**风险等级**：P1
**整改方向**：补全空值处理；提供默认值；防御性编程
**验收标准**：所有空值场景有处理；无 NaN 风险

### 指标 3.5：转换不可变性（不修改入参）

**指标名称**：转换不可变性（不修改入参）
**检查目标**：确认转换函数不修改入参对象，始终返回新对象
**为什么需要检查**：修改入参会导致「同一数据被多次转换后状态混乱」「原始数据被污染」「难以调试」
**检查范围**：所有转换函数的实现
**检查方法**：
1. 检查转换函数是否直接修改入参对象的属性（如 `data.field = xxx`）
2. 检查转换函数是否返回新对象（使用展开运算符 / Object.assign 创建新对象）
3. 检查转换函数是否对入参数组进行 push / pop / splice 等 mutating 操作
4. 检查转换函数是否调用了会修改入参的工具函数
5. 检查是否有 `JSON.parse(JSON.stringify(data))` 这种低效深拷贝
**需要查看**：转换函数实现
**正常标准**：
- 转换函数不修改入参
- 始终返回新对象
- 数组操作使用 map / filter / reduce 等非 mutating 方法
- 无低效深拷贝
**异常情况**：
- 转换函数直接修改入参属性
- 转换函数对入参数组进行 push / splice
- 使用 JSON.parse(JSON.stringify) 深拷贝
- 调用会修改入参的工具函数
**风险等级**：P1
**整改方向**：改为不可变转换；使用展开运算符创建新对象；避免低效深拷贝
**验收标准**：所有转换函数不可变；返回新对象；不修改入参

### 指标 3.6：转换方向单一性（无双向转换）

**指标名称**：转换方向单一性（无双向转换）
**检查目标**：确认每个转换函数只负责一个方向的转换，不存在「同一函数既正向又反向转换」
**为什么需要检查**：双向转换会导致「转换逻辑混乱」「难以维护」「方向不明易出错」
**检查范围**：所有转换函数
**检查方法**：
1. 检查每个转换函数的输入输出方向（如 `ApiXxx → Xxx` 是正向，`Xxx → ApiXxx` 是反向）
2. 检查是否存在同一函数同时处理正向与反向（如根据参数判断方向）
3. 检查是否存在两个方向相反的转换函数但实现高度相似（应合并）
4. 检查是否存在「转换后再转回去」的来回转换
5. 检查反向转换是否真的需要（如前端是否需要构造接口入参）
**需要查看**：转换函数清单、转换函数实现
**正常标准**：
- 每个转换函数单一方向
- 反向转换有合理业务需求（如提交表单时构造接口入参）
- 无来回转换
- 反向转换单独命名（如 `toApiXxx` 与 `fromApiXxx` 分离）
**异常情况**：
- 同一函数处理双向转换
- 存在来回转换
- 反向转换无业务需求（如只读数据却写了反向转换）
- 双向转换实现高度相似但未合并
**风险等级**：P2
**整改方向**：拆分双向转换；移除无需求的反向转换；统一命名
**验收标准**：每个转换函数单一方向；反向转换有需求；命名规范

### 指标 3.7：重复转换检测

**指标名称**：重复转换检测
**检查目标**：识别项目中重复实现的转换逻辑，确保同一转换只在一处实现
**为什么需要检查**：重复转换会导致「修改时需同步多处」「转换不一致」等维护问题
**检查范围**：所有转换函数
**检查方法**：
1. 列出所有转换函数的输入输出类型对
2. 检查是否存在多个转换函数处理相同的输入输出类型对
3. 对比这些转换函数的实现是否高度相似
4. 检查是否有转换逻辑散落在多个 service / store 中
5. 检查前后端是否有重复的转换逻辑（如前端做了字段映射，后端也做了）
**需要查看**：转换函数清单、转换函数实现
**正常标准**：
- 同一输入输出类型对只有一处转换实现
- 转换逻辑集中在 adapter 层
- 前后端转换职责明确（不重复）
**异常情况**：
- 多个转换函数处理相同类型对且实现相似
- 转换逻辑散落在 service / store / 组件
- 前后端都做了同一字段映射
**风险等级**：P2
**整改方向**：合并重复转换；集中到 adapter 层；明确前后端转换职责
**验收标准**：同一转换单一实现；集中在 adapter 层

## 第四部分：数据消费审查

> 目标：审查数据在 UI 层的消费是否正确，回答「渲染的字段对不对」「坐标系 / 单位 / 时间格式对不对」
> 本部分直接影响用户看到的数据正确性，是数据链的最后一道关口

### 指标 4.1：接口字段与组件使用字段对齐

**指标名称**：接口字段与组件使用字段对齐
**检查目标**：确认组件模板中使用的字段与接口返回（经 adapter 转换后）的字段完全对齐
**为什么需要检查**：字段不对齐会导致「数据有但显示不出来」「显示 undefined」等问题
**检查范围**：所有组件模板、组件 script 中的字段访问
**检查方法**：
1. 列出每个组件模板中使用的字段名（如 `{{ data.name }}`、`v-bind="data.id"`）
2. 列出接口返回并经 adapter 转换后的字段名
3. 对比两组字段名是否一致
4. 检查组件是否访问了接口不存在的字段
5. 检查字段类型是否匹配（如接口返回 string，组件当 number 用）
6. 检查嵌套字段访问是否安全（如 `data.user.name` 是否可能因 user 为 null 报错）
**需要查看**：组件模板、接口响应、adapter 输出类型、类型定义
**正常标准**：
- 组件使用的字段与接口字段（经 adapter）完全对齐
- 无组件访问接口不存在的字段
- 字段类型匹配
- 嵌套字段访问有可选链保护（`data?.user?.name`）
**异常情况**：
- 组件访问接口不存在的字段
- 字段类型不匹配
- 嵌套字段访问无保护导致报错
- 字段名拼写错误（如 `data.namme`）
**风险等级**：P0（关键字段错位） / P1（其他）
**整改方向**：字段对齐；加可选链；修正拼写
**验收标准**：组件字段与接口字段对齐；类型匹配；嵌套访问有保护

### 指标 4.2：坐标系转换检查（GIS 关键）

**指标名称**：坐标系转换检查（GIS 关键）
**检查目标**：确认所有地理坐标数据在渲染前都经过正确的坐标系转换
**为什么需要检查**：坐标系错误会导致「点位偏移几公里」「图层错位」等严重问题，是 GIS 项目最致命的数据错误
**检查范围**：所有地理坐标数据（经纬度、投影坐标）、地图图层渲染、坐标转换函数
**检查方法**：
1. 列出所有坐标数据来源及其原始坐标系（WGS84 / GCJ02 / BD09 / CGCS2000 / 投影坐标）
2. 检查地图底图使用的坐标系
3. 检查每个图层 / 点位的坐标是否与底图坐标系一致
4. 检查是否有显式的坐标转换函数（如 `wgs84togcj02`）
5. 检查坐标转换是否在 adapter 层完成（而非组件内临时转换）
6. 检查坐标转换函数的正确性（参考标准算法）
7. 检查是否有「未转换直接渲染」的坐标数据
**需要查看**：坐标数据、底图配置、坐标转换函数、adapter 实现
**正常标准**：
- 所有坐标数据有明确的坐标系标注
- 坐标数据与底图坐标系一致（或经显式转换）
- 坐标转换在 adapter 层完成
- 坐标转换函数正确（参考标准算法）
- 无未转换直接渲染的坐标
**异常情况**：
- 坐标数据未转换直接渲染
- 坐标系标注不明
- 坐标转换在组件内临时完成（散落）
- 坐标转换函数错误（偏差大）
- 同一地图混合不同坐标系未统一
**风险等级**：P0
**整改方向**：统一坐标系；转换收口到 adapter；使用标准转换算法
**验收标准**：所有坐标经正确转换；坐标系标注明确；转换在 adapter 层

### 指标 4.3：单位转换检查

**指标名称**：单位转换检查
**检查目标**：确认所有带单位的数据在渲染前经过正确的单位转换
**为什么需要检查**：单位错误会导致「数据放大 1000 倍或缩小 1000 倍」，严重影响业务判断
**检查范围**：所有带单位的数据（距离、面积、速度、温度、压力、流量等）
**检查方法**：
1. 列出所有带单位的数据字段
2. 标注接口返回的单位（如米 / 千米 / 毫米）
3. 标注组件渲染期望的单位（如显示千米但接口返回米）
4. 检查是否有显式的单位转换（如 `value / 1000`）
5. 检查单位转换是否在 adapter 层完成
6. 检查单位是否在 UI 上明确标注（如「距离：100 km」）
7. 检查单位转换的正确性（如 mm/d 与 m/s 的转换）
**需要查看**：接口数据、组件模板、adapter 实现、单位标注
**正常标准**：
- 所有带单位的数据有单位标注
- 接口单位与渲染单位一致或经显式转换
- 单位转换在 adapter 层完成
- UI 明确标注单位
- 单位转换正确
**异常情况**：
- 接口返回米但组件直接显示为千米
- 无单位标注导致用户误判
- 单位转换散落在组件内
- 单位转换错误（如把 mm/d 当 m/s）
**风险等级**：P0（关键业务单位） / P1（其他）
**整改方向**：统一单位；转换收口到 adapter；UI 标注单位
**验收标准**：所有单位数据有标注；转换在 adapter；UI 标注单位

### 指标 4.4：时间格式转换检查

**指标名称**：时间格式转换检查
**检查目标**：确认所有时间数据在渲染前经过正确的时间格式转换
**为什么需要检查**：时间格式错误会导致「显示 1970 年」「时区错乱」「无法解析」等问题
**检查范围**：所有时间数据字段（时间戳、ISO 字符串、自定义格式）
**检查方法**：
1. 列出所有时间数据字段
2. 标注接口返回的时间格式（如 Unix 时间戳、ISO 8601 字符串、自定义字符串）
3. 标注组件渲染期望的时间格式（如 `YYYY-MM-DD HH:mm:ss`）
4. 检查是否有显式的时间格式转换（使用 dayjs / date-fns 等）
5. 检查时区处理（接口返回 UTC，组件显示本地时间）
6. 检查时间戳单位（秒 vs 毫秒）
7. 检查时间转换是否在 adapter 层完成
**需要查看**：接口数据、组件模板、adapter 实现、时间格式化工具
**正常标准**：
- 所有时间数据有格式标注
- 接口格式与渲染格式一致或经显式转换
- 时区处理正确
- 时间戳单位明确（秒 / 毫秒）
- 时间转换在 adapter 层完成
**异常情况**：
- 时间戳单位混淆（秒当毫秒用）
- 时区未处理导致显示错误
- 时间格式化散落在组件内
- 时间数据为 null 时显示「Invalid Date」
**风险等级**：P1
**整改方向**：统一时间格式；转换收口到 adapter；处理时区；null 兜底
**验收标准**：时间格式统一；转换在 adapter；时区正确；null 有兜底

### 指标 4.5：列表渲染 key 稳定性

**指标名称**：列表渲染 key 稳定性
**检查目标**：确认列表渲染使用稳定且唯一的 key，而非 index
**为什么需要检查**：用 index 做 key 会导致「列表重排时渲染错乱」「组件状态错位」「性能下降」
**检查范围**：所有 `v-for` / `map` 列表渲染
**检查方法**：
1. 搜索所有 `v-for` 与 `map` 渲染
2. 检查每个列表的 key 来源
3. 检查 key 是否稳定（不随列表重排变化）
4. 检查 key 是否唯一（列表内无重复）
5. 检查列表是否会重排 / 插入 / 删除（若不会，index 风险较低）
6. 检查是否有「无合适字段做 key」的情况（应补 id 字段）
**需要查看**：组件模板、列表数据结构
**正常标准**：
- 所有列表使用稳定唯一的 key（如 id）
- 无用 index 做 key 的列表（除非列表永不重排）
- key 字段在数据中存在且唯一
**异常情况**：
- 用 index 做 key 且列表会重排
- key 字段不唯一（如多条数据 id 相同）
- key 字段可能为 null / undefined
- 无 key 字段
**风险等级**：P1
**整改方向**：使用稳定唯一字段做 key；补 id 字段
**验收标准**：所有列表有稳定唯一 key；无 index 做 key 的重排列表

### 指标 4.6：空数据兜底 UI（数据链视角）

**指标名称**：空数据兜底 UI（数据链视角）
**检查目标**：确认所有数据为空时有兜底 UI，而非白屏或报错
**为什么需要检查**：空数据白屏会让用户以为「系统崩了」，严重影响体验
**检查范围**：所有数据消费组件
**检查方法**：
1. 检查每个数据消费组件对空数据的处理
2. 检查列表为空时是否有「暂无数据」提示
3. 检查图表数据为空时是否有占位 UI
4. 检查地图图层无数据时是否有提示
5. 检查接口返回 null / 空数组时组件行为
6. 检查 loading / error / empty 三态是否都覆盖
**需要查看**：组件模板、空数据处理逻辑、loading / error 状态
**正常标准**：
- 列表空数据有「暂无数据」UI
- 图表空数据有占位
- 地图无数据有提示
- loading / error / empty 三态覆盖
- 空数据 UI 有统一组件
**异常情况**：
- 空数据白屏
- 空数据显示 undefined / null
- 无 loading 状态
- 无 error 状态
- 空数据 UI 不统一（每处自己实现）
**风险等级**：P1
**整改方向**：补全空数据 UI；统一空数据组件；覆盖三态
**验收标准**：所有空数据有兜底 UI；三态覆盖；有统一组件

### 指标 4.7：数据边界值渲染（0 / 负数 / 极大值）

**指标名称**：数据边界值渲染（0 / 负数 / 极大值）
**检查目标**：确认数据为 0、负数、极大值时渲染正确，不报错不显示异常
**为什么需要检查**：边界值是渲染 bug 的高发区，如「0 被当作 false」「负数显示为正」「极大值溢出」
**检查范围**：所有数值渲染、条件渲染（v-if / &&）
**检查方法**：
1. 检查 `v-if="data.value"` 是否会因 value 为 0 而不渲染（应 `v-if="data.value != null"`）
2. 检查 `{{ data.value || '--' }}` 是否会因 value 为 0 显示 `--`
3. 检查负数渲染（如温度 -5℃ 是否正确显示）
4. 检查极大值渲染（如超过 Number.MAX_SAFE_INTEGER）
5. 检查百分比 / 比例数据是否正确处理 0% 与 100%
6. 检查数值精度（如 0.1 + 0.2 !== 0.3）
**需要查看**：组件模板、数值渲染逻辑
**正常标准**：
- 0 值正确渲染（不被当作 false）
- 负数正确显示
- 极大值不溢出
- 数值精度有处理
- 边界值有兜底显示
**异常情况**：
- `v-if="value"` 导致 0 不渲染
- `value || '--'` 导致 0 显示 `--`
- 负数显示异常
- 极大值溢出显示 NaN / Infinity
- 精度问题导致显示 0.30000000000000004
**风险等级**：P1
**整改方向**：修正边界值判断；使用 `!= null` 而非真值判断；精度处理
**验收标准**：0 / 负数 / 极大值渲染正确；无边界值 bug

## 第五部分：数据生命周期审查

> 目标：审查数据从创建到销毁的完整生命周期，回答「数据何时创建、何时清理」「是否有泄漏」
> 本部分与生命周期专项有交叉，本专项聚焦数据本身的清理时机

### 指标 5.1：store 数据创建与清理时机

**指标名称**：store 数据创建与清理时机
**检查目标**：确认 store 中每类数据有明确的创建时机与清理时机
**为什么需要检查**：store 数据只 set 不 clear 会导致「切换页面后旧数据残留」「状态污染」
**检查范围**：所有 store 的 state、action、清理逻辑
**检查方法**：
1. 列出每个 store 的所有 state 字段
2. 对每个 state 字段，检查何时被赋值（创建 / 更新）
3. 检查每个 state 字段何时被清空（重置 / 清理）
4. 检查是否有 `$reset` 或显式清理 action
5. 检查路由切换时 store 是否被重置（若需要）
6. 检查登出 / 退出时 store 是否被清空
**需要查看**：store 实现、action、路由守卫、登出逻辑
**正常标准**：
- 每个 state 字段有赋值时机
- 每个 state 字段有清理时机（重置或登出时清空）
- 路由切换时需要重置的 store 有重置逻辑
- 登出时清空所有业务 store
**异常情况**：
- state 只 set 不 clear
- 路由切换后旧数据残留
- 登出后 store 仍保留业务数据
- 无 $reset 或清理 action
**风险等级**：P1
**整改方向**：补全清理 action；路由切换重置；登出清空
**验收标准**：每个 state 有清理时机；路由切换无残留；登出清空

### 指标 5.2：图层数据创建与清理时机

**指标名称**：图层数据创建与清理时机
**检查目标**：确认地图图层的创建、显隐、销毁时机明确，无图层泄漏
**为什么需要检查**：图层只 add 不 remove 会导致「内存泄漏」「图层叠加越来越乱」「性能下降」
**检查范围**：所有地图图层的 add / remove / show / hide 逻辑
**检查方法**：
1. 列出所有图层创建点
2. 检查每个图层是否有对应的 remove / destroy
3. 检查图层销毁时机（组件卸载 / 路由切换 / 业务切换）
4. 检查图层显隐是否正确管理（show / hide vs add / remove）
5. 检查是否有「创建多次但只销毁一次」的情况
6. 检查图层切换时旧图层是否被移除
**需要查看**：图层管理代码、组件卸载逻辑、地图实例管理
**正常标准**：
- 每个图层有创建与销毁配对
- 销毁在正确时机（卸载 / 路由切换）
- 图层显隐管理正确
- 创建与销毁次数匹配
- 图层切换时旧图层移除
**异常情况**：
- 图层只 add 不 remove
- 销毁时机错误（如未在卸载时销毁）
- 创建多次销毁一次
- 图层切换时旧图层残留
**风险等级**：P1
**整改方向**：补全图层销毁；统一图层管理；切换时清理
**验收标准**：每个图层有销毁配对；时机正确；创建销毁匹配

### 指标 5.3：缓存数据写入与失效

**指标名称**：缓存数据写入与失效
**检查目标**：确认缓存数据有写入策略与失效策略，不会无限增长或返回过期数据
**为什么需要检查**：缓存无失效策略会导致「数据过期但还在用」「内存无限增长」
**检查范围**：所有缓存实现（内存缓存、localStorage、IndexedDB、Map / WeakMap）
**检查方法**：
1. 列出所有缓存使用点
2. 检查每个缓存的写入策略（何时写、写什么）
3. 检查每个缓存的失效策略（TTL / LRU / 主动清除）
4. 检查缓存是否有大小限制
5. 检查缓存键的生成规则（是否唯一、是否可重复）
6. 检查缓存数据是否可能与接口数据不一致（脏数据）
**需要查看**：缓存实现、缓存配置、缓存使用点
**正常标准**：
- 每个缓存有写入与失效策略
- 缓存有大小限制
- 缓存键生成规则明确
- 缓存数据有版本控制或 TTL
**异常情况**：
- 缓存只写不清
- 无大小限制
- 缓存键冲突
- 缓存数据过期但仍在用
**风险等级**：P1
**整改方向**：补全失效策略；加大小限制；版本控制
**验收标准**：每个缓存有失效策略；有大小限制；无脏数据

### 指标 5.4：组件卸载数据清理

**指标名称**：组件卸载数据清理
**检查目标**：确认组件卸载时清理相关数据、监听、定时器、图层
**为什么需要检查**：组件卸载后未清理会导致「内存泄漏」「回调报错」「定时器持续运行」
**检查范围**：所有组件的 onUnmounted / onBeforeUnmount 钩子
**检查方法**：
1. 列出所有组件中创建的长生命周期对象（定时器、监听、WebSocket、图层、ECharts 实例）
2. 检查每个对象是否有对应的清理
3. 检查清理是否在 onUnmounted / onBeforeUnmount 中
4. 检查清理是否完整（监听是否全部移除、定时器是否全部清除）
5. 检查异步回调是否在卸载后被忽略（标志位或 AbortController）
**需要查看**：组件 setup、onUnmounted 钩子、清理逻辑
**正常标准**：
- 每个长生命周期对象有清理
- 清理在 onUnmounted / onBeforeUnmount 中
- 清理完整（无遗漏）
- 异步回调卸载后被忽略
**异常情况**：
- 定时器无 clearInterval
- 监听无 removeEventListener
- ECharts 无 dispose
- 卸载后异步回调仍执行
- 清理逻辑遗漏部分对象
**风险等级**：P1（详见专项2 生命周期，对象泄漏为 P0）
**整改方向**：补全清理逻辑；统一卸载钩子；异步回调加取消
**验收标准**：所有长生命周期对象有清理；清理完整；异步安全

### 指标 5.5：路由切换数据重置

**指标名称**：路由切换数据重置
**检查目标**：确认路由切换时需要重置的数据被重置，避免旧页面数据残留到新页面
**为什么需要检查**：路由切换后旧数据残留会导致「新页面显示旧数据」「状态错乱」
**检查范围**：路由守卫、store 重置逻辑、组件路由切换处理
**检查方法**：
1. 检查路由守卫（beforeEach / afterEach）是否重置相关 store
2. 检查组件 onBeforeRouteLeave 是否清理数据
3. 检查路由切换时图层是否被清理
4. 检查路由切换时定时器是否被清除
5. 检查路由切换时筛选条件是否被重置
6. 检查路由参数变化时数据是否重新加载
**需要查看**：路由配置、路由守卫、组件路由处理、store 重置
**正常标准**：
- 路由切换时重置相关 store
- 路由切换时清理图层 / 定时器
- 路由参数变化时数据重新加载
- 筛选条件按需重置
**异常情况**：
- 路由切换后旧数据残留
- 图层未清理
- 定时器未清除
- 路由参数变化但数据未刷新
**风险等级**：P1
**整改方向**：路由守卫加重置；组件清理；参数变化刷新
**验收标准**：路由切换无残留；参数变化刷新数据

### 指标 5.6：定时器数据清理

**指标名称**：定时器数据清理
**检查目标**：确认所有 setInterval / setTimeout 在不再需要时被清除
**为什么需要检查**：定时器未清除会导致「内存泄漏」「组件卸载后定时器仍执行」「回调报错」
**检查范围**：所有 setInterval / setTimeout 调用
**检查方法**：
1. 搜索所有 `setInterval` / `setTimeout`
2. 检查每个定时器是否有对应的 `clearInterval` / `clearTimeout`
3. 检查清除时机（组件卸载 / 业务结束 / 路由切换）
4. 检查定时器回调中是否访问了已卸载组件的状态
5. 检查定时器是否可能重复创建（如重复点击触发多个定时器）
**需要查看**：定时器代码、清除逻辑、组件卸载钩子
**正常标准**：
- 每个定时器有对应清除
- 清除时机正确
- 回调不访问已卸载状态
- 不会重复创建
**异常情况**：
- setInterval 无 clearInterval
- 清除时机错误
- 回调访问已卸载状态
- 重复创建多个定时器
**风险等级**：P1（详见专项2 生命周期）
**整改方向**：补全清除；统一管理；防重复创建
**验收标准**：所有定时器有清除；时机正确；无重复创建

## 第六部分：数据一致性与污染审查

> 目标：审查数据在多源之间的一致性，以及假数据是否污染正式路径
> 本部分是数据正确性的保障，多源不一致与假数据混入是高危风险

### 指标 6.1：前后端类型定义一致性

**指标名称**：前后端类型定义一致性
**检查目标**：确认同一业务实体在前端类型定义与后端类型定义一致
**为什么需要检查**：前后端类型不一致会导致「字段对不上」「类型不匹配」「运行时报错」
**检查范围**：前端 types 目录、后端 DTO / VO / Entity 定义
**检查方法**：
1. 列出前端所有业务实体类型定义
2. 列出后端对应实体类型定义
3. 对比字段名、字段类型、字段含义
4. 检查是否有「前端有字段但后端不返回」
5. 检查是否有「后端返回字段但前端类型没定义」
6. 检查字段命名风格（snake_case vs camelCase）是否有统一约定或自动转换
7. 检查是否有自动生成类型机制（如 OpenAPI / Swagger 生成）
**需要查看**：前端 types、后端 DTO / VO、API 文档、类型生成配置
**正常标准**：
- 前后端类型定义一致
- 字段名 / 类型 / 含义对齐
- 命名风格有约定或自动转换
- 有类型同步机制（自动生成或文档对账）
**异常情况**：
- 前端类型有字段但后端不返回
- 后端返回字段但前端类型没定义
- 字段类型不一致（如前端 string 后端 number）
- 命名风格不一致且无转换
- 无类型同步机制
**风险等级**：P1
**整改方向**：类型对齐；建立同步机制；考虑自动生成
**验收标准**：前后端类型一致；有同步机制

### 指标 6.2：静态数据与接口结构一致性

**指标名称**：静态数据与接口结构一致性
**检查目标**：确认静态数据文件（JSON / GeoJSON）的结构与接口返回结构一致
**为什么需要检查**：静态数据与接口结构不一致会导致「切换数据源时字段对不上」「渲染错误」
**检查范围**：所有静态数据文件、对应接口返回结构
**检查方法**：
1. 列出所有静态数据文件
2. 列出对应接口的返回结构
3. 对比字段名、字段类型、字段含义
4. 检查静态数据是否使用与接口相同的字段命名风格
5. 检查静态数据是否包含接口的所有必要字段
6. 检查静态数据是否有版本标识（与接口版本对应）
**需要查看**：静态数据文件、接口响应结构、类型定义
**正常标准**：
- 静态数据结构与接口结构一致
- 字段名 / 类型对齐
- 静态数据包含必要字段
- 有版本标识
**异常情况**：
- 静态数据字段名与接口不同
- 静态数据缺少必要字段
- 静态数据结构过期（与接口最新结构不一致）
- 无版本标识
**风险等级**：P1
**整改方向**：静态数据结构对齐接口；补全字段；加版本标识
**验收标准**：静态数据与接口结构一致；有版本标识

### 指标 6.3：同名不同义 / 同义不同名检查

**指标名称**：同名不同义 / 同义不同名检查
**检查目标**：识别项目中同名字段表达不同含义、或同义字段使用不同名称的情况
**为什么需要检查**：同名不同义会导致「误用字段」「数据错位」；同义不同名会导致「重复定义」「维护困难」
**检查范围**：所有类型定义、字段命名
**检查方法**：
1. 收集所有字段名
2. 检查同名字段在不同实体中是否表达同一含义
3. 检查同义字段是否使用了不同名称（如 `name` / `nm` / `title` 都表示名称）
4. 检查缩写是否一致（如 `id` / `ID` / `Id`）
5. 检查中英混合命名（如 `mingcheng` vs `name`）
6. 输出「同名不同义」与「同义不同名」清单
**需要查看**：所有类型定义、字段命名
**正常标准**：
- 同名字段表达同一含义
- 同义字段使用同一名称
- 命名风格统一（camelCase / snake_case）
- 无中英混合命名
**异常情况**：
- 同名字段不同含义（如 `type` 在不同实体中表示不同类型）
- 同义字段多个名称
- 命名风格不统一
- 中英混合命名
**风险等级**：P2
**整改方向**：统一命名；建立字段命名规范；消除同名不同义
**验收标准**：无同名不同义；无同义不同名；命名风格统一

### 指标 6.4：假数据关键字搜索（mock / fake / dummy / demo / test）

**指标名称**：假数据关键字搜索
**检查目标**：确认代码中不存在混入正式路径的假数据（通过关键字搜索识别）
**为什么需要检查**：假数据混入正式路径是上线后展示错误数据的直接原因
**检查范围**：所有源码文件（重点 service / store / 静态数据文件）
**检查方法**：
1. 全局搜索 `mock`、`fake`、`dummy`、`demo`、`test`、`示例`、`测试` 等关键字
2. 对每个搜索结果，判断是否在正式数据路径
3. 检查 service 中是否有返回假数据的逻辑
4. 检查静态数据文件是否含测试条目
5. 检查组件中是否有硬编码的假数据用于「演示」
6. 检查假数据是否通过环境开关隔离
7. 输出「假数据清单」并标注风险
**需要查看**：源码全量搜索结果、service / store / 静态数据文件
**正常标准**：
- 正式数据路径无 mock / fake / dummy / demo / test 关键字
- 假数据通过环境开关隔离
- 静态数据为真实业务数据
- 组件无硬编码假数据
**异常情况**：
- service 中返回假数据
- 静态数据文件含测试条目（如「测试站 1」）
- 组件硬编码假数据
- 假数据未通过开关隔离
**风险等级**：P0
**整改方向**：移除假数据；通过开关隔离；静态数据清洗
**验收标准**：正式路径无假数据关键字；静态数据为真实数据

### 指标 6.5：静态数据测试条目检查

**指标名称**：静态数据测试条目检查
**检查目标**：确认静态数据文件中不含测试条目（如「测试」「示例」「demo」数据）
**为什么需要检查**：静态数据含测试条目会导致「上线后显示测试数据」「数据污染」
**检查范围**：所有静态数据文件（JSON / GeoJSON / 配置文件）
**检查方法**：
1. 读取每个静态数据文件
2. 检查数据条目中是否含「测试」「test」「示例」「demo」「dummy」等关键字
3. 检查数据条目是否为明显非真实业务数据（如 `name: "张三测试"`、`value: 999999`）
4. 检查数据条目数量是否合理（如只有 2-3 条可能是测试数据）
5. 检查数据条目是否有明显规律（如递增的 id 1-10 可能是测试数据）
6. 对可疑条目标注并要求业务方确认
**需要查看**：静态数据文件内容
**正常标准**：
- 静态数据无测试条目
- 数据为真实业务数据
- 数据条目数量合理
- 无明显测试特征
**异常情况**：
- 含「测试」「示例」字样的条目
- 数据明显非真实（如极大值、规律性 id）
- 数据条目过少（疑似测试残留）
- 数据含明显占位符（如 `xxx`、`lorem`）
**风险等级**：P0
**整改方向**：清洗静态数据；移除测试条目；业务方确认数据真实性
**验收标准**：静态数据无测试条目；为真实业务数据

### 指标 6.6：生产构建 mock 排除

**指标名称**：生产构建 mock 排除
**检查目标**：确认生产构建产物中不包含 mock 模块代码
**为什么需要检查**：构建配置未排除 mock 会导致「生产包含 mock 代码」「体积增大」「潜在被调用风险」
**检查范围**：构建配置（vite.config / webpack.config）、生产构建产物
**检查方法**：
1. 检查构建配置是否有 mock 排除规则
2. 检查 mock 模块是否通过 `import.meta.env.DEV` 或 `process.env.NODE_ENV` 守卫
3. 执行生产构建，检查产物中是否含 mock 关键字
4. 检查 mock 模块是否在 tree-shaking 范围内
5. 检查 mock 模块是否被业务代码无条件 import（导致无法 tree-shake）
6. 检查构建产物体积是否异常（含 mock 可能增大体积）
**需要查看**：构建配置、mock 模块、生产构建产物、构建体积分析
**正常标准**：
- 构建配置显式排除 mock
- mock 通过环境守卫
- 生产产物无 mock 关键字
- mock 模块可被 tree-shake
**异常情况**：
- 构建配置未排除 mock
- mock 未通过环境守卫
- 生产产物含 mock 代码
- mock 被无条件 import 无法 tree-shake
**风险等级**：P0
**整改方向**：构建配置排除 mock；环境守卫；条件 import
**验收标准**：生产构建无 mock；体积正常

### 指标 6.7：TODO 标记的未替换假数据

**指标名称**：TODO 标记的未替换假数据
**检查目标**：确认代码中不存在 `// TODO: 替换为真实数据` 之类的未完成替换
**为什么需要检查**：TODO 标记的假数据是「上线后仍展示假数据」的高发区，常被遗忘
**检查范围**：所有源码文件中的 TODO / FIXME 注释
**检查方法**：
1. 全局搜索 `TODO`、`FIXME`、`HACK`、`XXX` 注释
2. 筛选与数据相关的 TODO（如「替换为真实数据」「接接口」「待对接」）
3. 检查每个 TODO 是否对应未替换的假数据
4. 检查 TODO 是否有责任人标注
5. 检查 TODO 是否有计划完成时间
6. 输出「数据相关 TODO 清单」
**需要查看**：源码 TODO 搜索结果
**正常标准**：
- 无数据相关的未替换 TODO
- TODO 有责任人标注
- TODO 有计划完成时间
- 上线前所有数据 TODO 已处理
**异常情况**：
- 存在「替换为真实数据」的 TODO 未处理
- TODO 无责任人
- TODO 无计划时间
- 上线前未处理
**风险等级**：P0
**整改方向**：处理所有数据 TODO；替换为真实实现；标注责任人
**验收标准**：无数据相关未处理 TODO；全部替换为真实实现

## 第七部分：典型数据问题诊断

> 目标：建立三类典型数据问题的根因定位链路，回答「面板没有数据是哪一跳出问题」「接口成功但页面错误是哪一跳出问题」
> 本部分是数据链审查的诊断能力验证，链路无可观测点则无法定位

### 指标 7.1：「面板没有数据」根因定位链路

**指标名称**：「面板没有数据」根因定位链路
**检查目标**：确认当面板没有数据时，能通过链路日志定位到具体环节
**为什么需要检查**：「面板没有数据」是最高频的故障，无法定位根因会导致排障时间漫长
**检查范围**：完整数据链路、链路日志、空数据兜底
**检查方法**：
1. 模拟「面板没有数据」场景，沿链路逐跳检查
2. 检查数据源是否有数据（数据库 / 接口是否返回）
3. 检查请求是否发出（service 是否被调用）
4. 检查请求是否成功（HTTP 状态、响应内容）
5. 检查响应数据是否为空（接口返回空数组 / null）
6. 检查 adapter 是否正确转换（是否吞掉了数据）
7. 检查 store 是否正确存储（是否被覆盖）
8. 检查组件是否正确消费（是否绑定了正确字段）
9. 检查空数据是否有兜底 UI（无兜底则白屏）
10. 确认每一跳是否有日志可观测
**需要查看**：链路图、链路日志、service / adapter / store / 组件实现
**正常标准**：
- 能沿链路逐跳定位「数据在哪一跳丢失」
- 每一跳有日志可观测
- 空数据有兜底 UI
- 能区分「无数据」与「出错」
**异常情况**：
- 无法定位数据在哪一跳丢失
- 链路无日志
- 空数据白屏无法区分是「无数据」还是「出错」
- 多跳无观测点
**风险等级**：P1
**整改方向**：补全链路日志；空数据兜底；区分无数据与出错
**验收标准**：能定位「面板没有数据」的根因环节；链路有日志；有兜底

### 指标 7.2：「接口成功但页面错误」根因定位链路

**指标名称**：「接口成功但页面错误」根因定位链路
**检查目标**：确认当接口成功返回但页面显示错误时，能定位到转换或消费环节的问题
**为什么需要检查**：接口成功但页面错误是数据链中段问题的典型表现，常源于转换 / 字段 / 坐标系错误
**检查范围**：adapter 转换、字段映射、坐标系 / 单位 / 时间格式转换、组件消费
**检查方法**：
1. 模拟「接口成功但页面错误」场景
2. 检查接口返回数据是否正确（数据本身是否有问题）
3. 检查 adapter 转换是否正确（字段映射是否完整、是否有静默丢弃）
4. 检查字段名是否对齐（接口字段 vs 组件使用字段）
5. 检查坐标系是否正确转换（GIS 关键）
6. 检查单位是否正确转换
7. 检查时间格式是否正确转换
8. 检查类型是否匹配（如 string 当 number）
9. 检查空值是否导致 NaN / undefined
10. 确认转换与消费环节有日志可观测
**需要查看**：adapter 实现、组件模板、接口响应、坐标系 / 单位 / 时间转换
**正常标准**：
- 能定位「接口成功但页面错误」的根因环节
- 转换环节有日志
- 字段映射有文档
- 坐标系 / 单位 / 时间有显式转换
**异常情况**：
- 无法定位是转换还是消费环节出错
- 转换无日志
- 字段映射无文档
- 坐标系 / 单位 / 时间未显式转换
**风险等级**：P1
**整改方向**：补全转换日志；字段映射文档化；显式转换
**验收标准**：能定位「接口成功但页面错误」根因；转换有日志；有文档

### 指标 7.3：「数据更新但 UI 不变化」根因定位链路

**指标名称**：「数据更新但 UI 不变化」根因定位链路
**检查目标**：确认当数据已更新但 UI 不变化时，能定位到响应式断链或状态同步问题
**为什么需要检查**：「数据更新但 UI 不变化」是 Vue 项目最隐蔽的 bug，常源于响应式断链
**检查范围**：store 响应式、组件响应式绑定、props 解构、computed 派生
**检查方法**：
1. 模拟「数据更新但 UI 不变化」场景
2. 检查 store 数据是否真的更新（devtools 查看 state）
3. 检查组件是否正确监听了 store（storeToRefs / computed）
4. 检查 reactive 对象是否被解构丢失响应式（应用 toRefs）
5. 检查 props 是否被解构丢失响应式
6. 检查 ref 是否在 script 中正确使用 .value
7. 检查是否有 Object.assign(reactive对象, ...) 导致的问题
8. 检查 reactive 数组的直接索引赋值
9. 检查 computed 依赖是否正确
10. 确认响应式链路有可观测点
**需要查看**：store 实现、组件响应式使用、props / reactive 解构、computed
**正常标准**：
- 能定位「数据更新但 UI 不变化」的响应式断点
- 响应式使用正确（storeToRefs / toRefs）
- 无响应式断链
- devtools 可观测 state 变化
**异常情况**：
- 无法定位响应式断点
- reactive 直接解构丢失响应式
- props 解构丢失响应式
- store 未用 storeToRefs 解构
- ref 忘 .value
**风险等级**：P0（响应式断链，详见专项2 生命周期）
**整改方向**：修复响应式断链；用 storeToRefs / toRefs；正确使用 ref
**验收标准**：能定位响应式断点；无响应式断链

### 指标 7.4：数据链路无观测点风险

**指标名称**：数据链路无观测点风险
**检查目标**：确认数据链路关键节点都有观测点，不存在「整段链路无任何日志」的黑盒段
**为什么需要检查**：无观测点的链路段在故障时完全无法定位，是诊断能力的致命缺陷
**检查范围**：完整数据链路的日志 / 埋点覆盖
**检查方法**：
1. 沿链路图标注每个节点的观测点（日志 / 埋点 / devtools）
2. 识别「连续多跳无观测点」的黑盒段
3. 评估黑盒段的故障概率与影响
4. 检查关键节点（请求 / 转换 / 状态变更 / 渲染）是否都有观测
5. 检查观测点是否能在生产环境使用（开发日志不计数）
6. 检查观测点是否有上下文信息（如请求 ID、数据 ID）
**需要查看**：链路图、日志实现、埋点配置
**正常标准**：
- 链路关键节点都有观测点
- 无连续多跳的黑盒段
- 观测点生产可用
- 观测点有上下文信息
**异常情况**：
- 连续多跳无观测点
- 观测点仅开发环境可用
- 观测点无上下文（无法关联）
- 关键节点（如 adapter）无观测
**风险等级**：P1
**整改方向**：补全观测点；生产可用；加上下文
**验收标准**：链路无黑盒段；关键节点有观测；生产可用

## 第八部分：请求与接口治理

> 目标：审查数据链路上的请求治理，回答「请求错误如何处理」「竞态如何处理」「卸载如何取消」
> 本部分是数据链传输环节的工程治理，直接影响数据正确性与稳定性

### 指标 8.1：请求错误处理链完整性（数据链视角）

**指标名称**：请求错误处理链完整性（数据链视角）
**检查目标**：确认每个请求都有完整的错误处理链：网络错误 / 服务端错误 / 业务错误 / 空数据
**为什么需要检查**：错误处理缺失会导致「请求失败静默」「白屏」「用户无法操作」
**检查范围**：所有请求封装、service 错误处理、组件错误处理
**检查方法**：
1. 检查请求封装（axios interceptor / fetch wrapper）是否统一处理网络错误
2. 检查 HTTP 状态码处理（4xx / 5xx 是否有区分）
3. 检查业务错误码处理（如 `code: 0` 为成功，其他为失败）
4. 检查请求失败是否有用户可见提示（message / notification）
5. 检查请求失败后 UI 状态（loading 是否复位、是否显示 error 状态）
6. 检查请求失败是否记录日志
7. 检查是否有全局错误边界兜底
**需要查看**：请求封装、interceptor、service 错误处理、组件错误处理、错误边界
**正常标准**：
- 请求封装统一处理网络错误与 HTTP 状态
- 业务错误码有处理
- 失败有用户提示
- loading 复位、显示 error 状态
- 失败有日志
- 有全局错误边界
**异常情况**：
- 请求失败静默（无提示、无日志）
- 业务错误码未处理
- 失败后 loading 不复位
- 无 error 状态显示
- 无全局错误边界
**风险等级**：P1
**整改方向**：统一错误处理；补全提示与状态；加错误边界
**验收标准**：所有请求有错误处理；有提示；有错误边界

### 指标 8.2：请求竞态处理

**指标名称**：请求竞态处理
**检查目标**：确认并发请求场景下有竞态处理，避免「先发的请求后返回覆盖正确结果」
**为什么需要检查**：竞态会导致「页面显示旧数据」「数据闪烁」，是异步逻辑最隐蔽的 bug
**检查范围**：所有可能并发的请求（如快速切换筛选、快速翻页、快速切换路由）
**检查方法**：
1. 识别可能并发的请求场景（如用户快速点击、路由快速切换）
2. 检查这些场景是否有竞态处理（AbortController / 标志位 / 请求 ID 比对）
3. 检查先发后返回的请求是否被忽略
4. 检查组件卸载后的请求回调是否被忽略
5. 检查是否有「最后一次请求生效」的逻辑
6. 检查竞态处理是否正确（如标志位是否在 finally 中复位）
**需要查看**：service 请求逻辑、竞态处理代码、组件卸载逻辑
**正常标准**：
- 可能并发的请求有竞态处理
- 先发后返回的请求被忽略
- 卸载后回调被忽略
- 标志位在 finally 中复位
**异常情况**：
- 快速切换导致旧数据覆盖新数据
- 卸载后回调仍执行
- 标志位未在 finally 复位导致后续请求被永久拦截
- 无竞态处理
**风险等级**：P0
**整改方向**：加 AbortController 或请求 ID 比对；卸载后忽略；标志位 finally 复位
**验收标准**：所有并发场景有竞态处理；无旧数据覆盖

### 指标 8.3：请求超时与重试

**指标名称**：请求超时与重试
**检查目标**：确认请求有超时设置与合理的重试机制
**为什么需要检查**：无超时会导致请求挂起、用户等待无尽；无重试会导致偶发失败影响体验
**检查范围**：请求封装、超时配置、重试逻辑
**检查方法**：
1. 检查请求封装是否设置 timeout
2. 检查 timeout 值是否合理（如 10s / 30s，视业务而定）
3. 检查超时后是否有用户提示
4. 检查是否有重试机制（如重试 3 次）
5. 检查重试是否有退避策略（如指数退避）
6. 检查重试是否区分可重试错误（网络错误可重试，业务错误不可重试）
7. 检查重试次数是否有上限
**需要查看**：请求封装、timeout 配置、重试逻辑
**正常标准**：
- 所有请求有 timeout
- timeout 值合理
- 超时有提示
- 可重试错误有重试
- 重试有退避与上限
**异常情况**：
- 无 timeout 设置
- timeout 值不合理（如 0 或过大）
- 超时无提示
- 无重试机制
- 重试无上限导致无限重试
**风险等级**：P1
**整改方向**：设置合理 timeout；加超时提示；可重试错误加退避重试
**验收标准**：所有请求有 timeout；有重试机制；重试有上限

### 指标 8.4：请求取消（组件卸载）

**指标名称**：请求取消（组件卸载）
**检查目标**：确认组件卸载时正在进行的请求被取消，避免卸载后回调执行
**为什么需要检查**：卸载后请求回调执行会导致「内存泄漏」「setState on unmounted 警告」「数据错乱」
**检查范围**：所有组件中的请求、组件卸载逻辑
**检查方法**：
1. 检查组件中的请求是否使用 AbortController
2. 检查组件卸载时是否调用 abort 取消请求
3. 检查卸载后回调是否有标志位忽略
4. 检查 axios 是否支持 CancelToken / AbortSignal
5. 检查请求封装是否暴露取消接口
6. 检查卸载后回调是否访问已卸载组件的状态
**需要查看**：组件请求代码、卸载钩子、请求封装
**正常标准**：
- 组件请求使用 AbortController
- 卸载时调用 abort
- 卸载后回调被忽略
- 请求封装支持取消
**异常情况**：
- 请求未使用 AbortController
- 卸载时未取消请求
- 卸载后回调仍执行
- 请求封装不支持取消
**风险等级**：P0
**整改方向**：使用 AbortController；卸载时取消；请求封装支持取消
**验收标准**：所有组件请求支持取消；卸载时取消

### 指标 8.5：API 版本管理

**指标名称**：API 版本管理
**检查目标**：确认 API 有版本管理机制，能在接口升级时平滑过渡
**为什么需要检查**：无版本管理会导致「后端升级接口前端就崩」「无法平滑迭代」
**检查范围**：API 路径、版本前缀、版本协商机制
**检查方法**：
1. 检查 API 路径是否含版本号（如 `/api/v1/xxx`）
2. 检查是否有多版本并存的情况
3. 检查版本升级时是否有兼容策略（如 v1 废弃前 v2 并存）
4. 检查是否有版本协商机制（header / query）
5. 检查废弃版本是否有明确的下线计划
6. 检查前端是否硬编码版本号（应配置化）
**需要查看**：API 路径配置、版本管理策略、前端 API 配置
**正常标准**：
- API 路径含版本号
- 多版本并存有兼容策略
- 版本号配置化
- 废弃版本有下线计划
**异常情况**：
- API 无版本号
- 多版本无兼容策略
- 版本号硬编码
- 无下线计划
**风险等级**：P2
**整改方向**：API 加版本号；建立版本管理策略；版本号配置化
**验收标准**：API 有版本管理；有兼容策略；版本号配置化

### 指标 8.6：接口数据脱敏

**指标名称**：接口数据脱敏
**检查目标**：确认接口返回的敏感数据（如手机号、身份证、密码、token）在传输与展示时脱敏
**为什么需要检查**：敏感数据未脱敏会导致「信息泄露」「合规风险」「安全漏洞」
**检查范围**：接口响应、日志输出、UI 展示
**检查方法**：
1. 列出所有可能含敏感数据的接口（用户信息、认证、财务等）
2. 检查后端返回是否对敏感字段脱敏（如手机号 `138****8888`）
3. 检查前端展示是否对敏感数据脱敏
4. 检查日志是否输出敏感数据（请求 / 响应日志）
5. 检查 localStorage / sessionStorage 是否存储敏感数据
6. 检查是否有脱敏工具函数与统一脱敏策略
**需要查看**：接口响应、日志实现、UI 展示、脱敏工具
**正常标准**：
- 敏感数据在传输与展示时脱敏
- 日志不输出敏感数据
- 不在 localStorage 存储敏感数据
- 有统一脱敏策略
**异常情况**：
- 接口返回明文敏感数据
- 日志输出敏感数据
- localStorage 存储 token / 密码
- 无脱敏策略
**风险等级**：P0
**整改方向**：后端脱敏；日志脱敏；不存储敏感数据；建立脱敏策略
**验收标准**：敏感数据全链路脱敏；日志无敏感信息；无敏感数据存储

## 附录 D：本专项审查执行流程建议

执行一次数据链专项审查的建议步骤：

1. **建立数据来源清单**（第一部分 1.1-1.7）：先看清所有数据从哪来，输出数据来源清单
2. **画出完整数据链路**（第二部分 2.1-2.7）：对每条核心数据画出从来源到消费的链路图
3. **审查转换正确性**（第三部分 3.1-3.7）：逐个转换函数审查字段映射、空值、不可变性
4. **审查消费正确性**（第四部分 4.1-4.7）：逐个组件审查字段对齐、坐标系、单位、时间、key、兜底
5. **审查生命周期**（第五部分 5.1-5.6）：逐类数据审查创建与清理时机
6. **审查一致性与污染**（第六部分 6.1-6.7）：审查前后端一致性、假数据混入、TODO 残留
7. **验证诊断能力**（第七部分 7.1-7.4）：模拟三类典型问题验证链路可观测性
8. **审查请求治理**（第八部分 8.1-8.6）：审查错误处理、竞态、超时、取消、脱敏
9. **汇总输出**：按 P0/P1/P2/P3 分级，给出整改清单与验收标准

每一步的输出都应能被下一步引用，形成「来源 → 链路 → 转换 → 消费 → 生命周期 → 一致性 → 诊断 → 请求」的完整证据链。
