# 生命周期专项审查指标体系

> 版本：v1.0
> 定位：可并行执行的专项审查之一（与审查体系关系见 `00-审查体系约定.md`，一级质量属性 #3 生命周期与资源管理）
> 聚焦：所有代码实体的「创建 → 使用 → 修改 → 销毁」完整生命周期深度审查
> 适用：AI 辅助代码审查、阶段性技术体检、大型项目重构前分析、项目交接分析、内存泄漏与状态污染排查
> 原则约束：本专项不依赖具体技术栈、不依赖具体项目，所有结论必须来自真实代码证据

---

## 0. 文档使用说明

### 0.1 文档定位

本文档是「生命周期专项审查标准」，是审查体系的并行子专项之一。

它回答的不是「这个项目现在有什么问题」，而是「审查一个项目的生命周期管理时应该检查什么、怎么检查、什么算正常、什么算异常」。

本专项可与以下专项并行执行，互不阻塞：
- 数据链专项（关注数据来源、传输、转换、消费）
- 类型安全专项（关注类型覆盖率与类型契约）
- WebGIS 专项（关注坐标系、图层、渲染）
- 工程化专项（关注构建、测试、安全、性能）
- 架构耦合专项（关注模块边界、依赖、循环）

### 0.2 与其他专项的边界

本专项管「生命周期」，不管以下领域，但会引用其他专项编号进行协作：

| 本专项负责 | 不负责（归属其他专项） |
|------------|------------------------|
| 变量作用域与生命周期 | 数据来源真伪（数据链专项 2.1） |
| 全局状态管理生命周期 | 数据传输链路完整性（数据链专项 2.2） |
| 对象实例创建与销毁 | 数据转换契约（数据链专项 2.3） |
| 状态同步一致性 | 数据消费字段对齐（数据链专项 2.4） |
| 内存风险 | 模块依赖方向（架构耦合专项 5.1） |
| 响应式正确性 | 类型覆盖率（工程化专项 6.1） |
| 异步生命周期 | 函数性能（工程化专项 3.6） |
| 组件与路由生命周期 | 安全审查（工程化专项 6.4） |

边界协作说明：当生命周期问题涉及数据链路时（如 store 数据未清理导致旧数据残留），本专项负责「清理时机」，数据链专项负责「数据本身是否正确」。

### 0.3 指标条目格式约定

每一个指标采用 `00-审查体系约定.md` §2 的 11 字段结构：

```
指标名称：该指标的唯一标识名
检查目标：这个指标要确认什么事实
为什么需要检查：不检查会带来什么风险
检查范围：该指标适用于哪些代码实体
检查方法：具体如何执行检查（步骤化）
需要查看：必须阅读哪些证据材料
正常标准：满足什么条件算通过
异常情况：出现什么现象算不通过
风险等级：P0 / P1 / P2 / P3
整改方向：发现问题后的修复路径
验收标准：整改完成后如何证明已修复
```

### 0.4 风险等级定义

风险等级判据见 `00-审查体系约定.md` §1：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

本专项 P0 触发场景：对象未销毁导致内存泄漏、响应式断链导致 UI 不更新、请求竞态导致数据覆盖、组件卸载后回调执行导致报错。

### 0.5 本专项核心原则

**原则 1：无主之物必有泄漏**
- 任何在代码中创建的实体（变量、对象、监听、定时器、连接），必须能追溯到「谁负责销毁它」
- 找不到销毁主体的实体，默认视为生命周期缺陷

**原则 2：创建必有销毁**
- 每一个 `create`/`new`/`init`/`connect`/`addEventListener`/`setInterval` 都必须有对应的 `destroy`/`close`/`dispose`/`removeEventListener`/`clearInterval`
- 销毁必须发生在正确的生命周期钩子中

**原则 3：注册必有注销**
- 每一个事件注册、watch、订阅、computed 都必须有对应的注销机制
- 自动注销机制（如 onScopeDispose、watchEffect 自动清理）算合规

**原则 4：四阶段可追溯**
- 任何实体的「创建 → 使用 → 修改 → 销毁」四个阶段都必须能在代码中找到证据
- 缺任一阶段都视为生命周期缺陷

**原则 5：销毁后不复用**
- 销毁后的对象、引用、回调不应再被访问
- 销毁后引用应置空，避免悬挂引用

### 0.6 Agent 并行执行契约（2026-08-11 统一改造）

- **独立线程**：本专项可单独作为一条 agent 审查线程执行，与其余专项**零执行依赖**（支持 8 窗口并行）；跨专项交叉点见 0.2 边界表，仅在产出层面汇总，不在执行层面依赖。
- **输入**：本文档（可按「部分」切片，仅加载本子 agent 负责的部分）+ 对应代码范围 + 设计文档对应章节（见 `00-审查体系约定.md` §4「标准输入资产」，本专项映射：02 4.4/5.1/5.2/5.5；01 五.5/五.6；03 1.4/2.3）。**先读预期机制，再查代码**——预期对照是深检第一步（见附录 D）。
- **输出**：发现清单（每条含：指标编号 / 证据 file:line / 风险等级 / 整改建议）→ 写入 `docs/audits/<日期>-<批次名>/专项2-生命周期审查-问题副本.md`（产出统一规范见 `00-审查体系约定.md` §4；副本规则见 docs/待解决问题.md 头部），经用户裁决转正主台账；执行记录存同批次目录 `专项2-生命周期审查-执行记录.md`（模板见 §0.7）。
- **子 agent 拆分**：按「第 X 部分」切分（拆分规则见 `00-审查体系约定.md` §4：① 1 部分=1 子 agent；② 相邻部分证据重叠>50% 可合并；③ 单专项上限 6；④ 禁止二次拆分）。
  - 本专项 8 部分共享组件/store 证据，建议 **4–5 个**子 agent（变量+全局状态 合 1、对象实例 1、状态同步 1、内存+响应式 合 1、异步+组件路由 合 1）。
  - 每个子 agent 领 1 个切分单元独立执行（输入 = 该单元指标 + 对应代码），主 agent 汇总去重、合并同根因、统一定级。
- **格式约定**：结论必须来自真实代码证据（file:line）；指标编号用本文档编号（如 3.2）；跨专项引用写「专项N X.Y」；**禁止使用草稿/临时编号**（唯一合法编号 = 台账编号体系）。

## 第一部分：变量作用域与生命周期

> 目标：建立项目变量全量地图，回答「每个变量活多久、谁负责它的生死」

### 指标 1.1：模块级变量全量清单

**指标名称**：模块级变量全量清单
**检查目标**：确认项目所有模块级（文件顶层）变量都被识别和登记，无遗漏、无隐式全局
**为什么需要检查**：模块级变量是「跨函数共享状态」的载体，也是最容易被忽视的生命周期盲区。未登记的模块级变量会导致「不知道谁在用、不知道何时清理、不知道何时被改」，是状态污染与并发问题的源头
**检查范围**：所有 `.js`、`.ts`、`.vue`、`.py` 源码文件的顶层声明
**检查方法**：
1. 逐文件扫描顶层（非函数内部）的 `let`、`const`、`var`、`export` 声明
2. 区分常量（全大写、不可变）与可变状态（小写、会被修改）
3. 对每个模块级变量标注：声明位置、类型、是否可变、被哪些函数读取、被哪些函数写入
4. 检查是否有未声明直接赋值的隐式全局（如 `foo = 1` 而非 `let foo`）
5. 检查是否使用 `window.xxx =` 或 `globalThis.xxx =` 创建全局变量
6. 输出模块级变量全量清单表（作为**审查执行产出**记入执行记录/台账，不写入规范文档——01 §六 红线禁止清单/行号进规范文档，防过时）
**需要查看**：所有源码文件顶层声明、ESLint 配置中的 no-undef / no-implicit-globals 规则
**正常标准**：
- 执行记录/台账含模块级变量全量清单（清单是执行产出而非规范文档内容，防过时）
- 每个模块级变量有明确用途说明
- 无隐式全局变量
- 无 `window.xxx =` 形式的全局赋值（除非有明确理由如 polyfill）
- 模块级可变变量数量受控（建议单文件不超过 2 个）
**异常情况**：
- 存在未声明的隐式全局变量
- 使用 `window.xxx =` 共享状态
- 模块级可变变量大量存在且无用途说明
- 同一变量在多个文件分别声明导致命名冲突
- 模块级变量既不导出也不在本文件使用（死变量）
**风险等级**：P2
**整改方向**：建立模块级变量清单（存执行记录/台账）；移除隐式全局；模块级可变变量收敛到 store 或 composable 内部
**验收标准**：模块级变量全量清单完整；无隐式全局；每个变量有用途说明

### 指标 1.2：模块级可变变量必要性

**指标名称**：模块级可变变量必要性
**检查目标**：确认每一个模块级可变变量（`let` 顶层变量、模块级 `reactive` 对象、模块级 `ref`）真的需要模块级作用域
**为什么需要检查**：模块级可变变量在 SPA 中是「单例状态」，会被所有使用该模块的组件共享，是「状态污染」「串数据」「测试隔离困难」的高发区。多数情况下模块级可变变量可以被 store、composable、组件内变量替代
**检查范围**：所有模块级 `let` 声明、模块级 `reactive()`、模块级 `ref()`、模块级普通对象赋值
**检查方法**：
1. 列出所有模块级可变变量
2. 对每个变量追问：为什么不能放到组件 setup 内？为什么不能放到 store？
3. 检查变量是否真的需要跨函数共享（若仅本文件内多函数共享，可考虑闭包或类）
4. 检查变量是否真的需要跨组件共享（若是，应进 store 而非模块级）
5. 检查模块级可变变量在测试中是否会导致用例间相互污染
6. 检查模块级可变变量是否在路由切换时被正确重置
**需要查看**：模块级可变变量声明、使用位置、测试文件
**正常标准**：
- 每个模块级可变变量有「为什么必须模块级」的注释说明
- 模块级可变变量仅用于真正的单例（如全局配置、单例服务、缓存实例）
- 跨组件共享状态走 store 而非模块级变量
- 测试中模块级可变变量有重置机制
**异常情况**：
- 业务状态使用模块级可变变量（如 `let currentSelected = null`）
- 模块级可变变量在路由切换后未重置，导致显示上一页数据
- 多个组件通过 import 同一模块级可变变量共享状态（绕过 store）
- 测试用例间因模块级可变变量相互污染
**风险等级**：P1
**整改方向**：业务状态迁移到 store；单文件内共享改用闭包或类；测试加 beforeEach 重置
**验收标准**：模块级可变变量仅用于真正单例；业务状态进 store；测试无污染

### 指标 1.3：const/let 使用正确性

**指标名称**：const/let 使用正确性
**检查目标**：确认 `const` 与 `let` 的选择符合「能 const 不 let」原则
**为什么需要检查**：`let` 声明的变量意味着「可被重新赋值」，扩大了变量的可变面。无谓使用 `let` 会让阅读者误以为变量会被重新赋值，增加认知负担，也容易引发意外覆盖。`const` 还能防止意外重赋值导致的 bug
**检查范围**：所有 `let` 声明
**检查方法**：
1. 列出所有 `let` 声明
2. 对每个 `let` 检查：变量是否在声明后被重新赋值（`=`, `+=`, `++` 等）
3. 从未被重新赋值的 `let` 应改为 `const`
4. 检查 `for` 循环中使用 `let i` 是否合理（合理）
5. 检查是否有 `var` 残留（应全部迁移到 let/const）
6. 检查 ESLint 是否启用 `prefer-const` 规则
**需要查看**：所有 let 声明、ESLint 配置
**正常标准**：
- 所有 `let` 变量确实会被重新赋值
- 无 `var` 残留
- ESLint 启用 `prefer-const`
- 临时变量、循环变量用 `let`，其余用 `const`
**异常情况**：
- `let` 变量声明后从未被重新赋值
- 残留 `var` 声明
- 未启用 `prefer-const` 规则
- 用 `let` 声明对象/数组但只修改属性不重赋值（应 const）
**风险等级**：P3
**整改方向**：let 改 const；移除 var；启用 prefer-const
**验收标准**：所有 let 变量确有重赋值；无 var；prefer-const 启用

### 指标 1.4：组件变量创建与清理配对

**指标名称**：组件变量创建与清理配对
**检查目标**：确认组件内创建的变量（特别是长生命周期对象引用、定时器、监听）都有对应的清理逻辑
**为什么需要检查**：组件在 SPA 中会被反复创建销毁，组件内创建的实体若不清理，会在每次组件卸载时泄漏一份，长时间运行后内存爆炸。这是 Vue/React 项目最典型的内存泄漏模式
**检查范围**：所有组件的 setup、onMounted、onBeforeUnmount、onUnmounted 钩子
**检查方法**：
1. 列出组件 setup 中创建的所有非响应式变量（实例引用、定时器 ID、订阅器）
2. 检查每个变量是否有对应的清理代码
3. 检查清理代码是否在 onUnmounted 或 onBeforeUnmount 中
4. 检查是否使用 onScopeDispose / tryOnScopeDispose 自动清理
5. 检查条件分支创建的变量是否在所有分支都有清理
6. 检查动态创建的变量（如循环内创建多个监听）是否有对应的批量清理
**需要查看**：组件 setup、生命周期钩子、composable 返回值
**正常标准**：
- 每个组件内创建的长生命周期变量都有清理
- 清理在 onUnmounted / onBeforeUnmount 中
- 优先使用 onScopeDispose / effectScope 自动清理
- 条件分支创建的实体在所有路径都有清理
- 动态创建的实体有批量清理机制
**异常情况**：
- onMounted 中创建实例但无 onUnmounted 销毁
- setup 中 new 了一个对象但无清理
- 条件分支创建了监听但只在某个分支清理
- 循环内创建多个定时器但只 clear 最后一个
**风险等级**：P0
**整改方向**：补全 onUnmounted 清理；优先用 onScopeDispose 自动清理；动态创建用数组收集后批量清理
**验收标准**：组件内创建的所有实体在卸载时被清理；无泄漏

### 指标 1.5：函数内临时变量泄漏

**指标名称**：函数内临时变量泄漏
**检查目标**：确认函数内的临时变量不会通过闭包、返回值、回调等方式泄漏到函数外部，导致本应回收的内存被长期持有
**为什么需要检查**：函数内临时变量本应在函数返回后被回收，但如果被闭包捕获、被异步回调持有、被赋值到外部引用，就会延长生命周期，造成「看起来是临时的实际是长期的」泄漏
**检查范围**：所有函数内的临时变量，特别是大对象、DOM 引用、长数组
**检查方法**：
1. 识别函数内创建的大对象（如解析后的 JSON、计算结果、查询结果）
2. 检查这些临时变量是否被闭包捕获（被内层函数引用）
3. 检查是否被异步回调持有（setTimeout/Promise 回调引用了临时大对象）
4. 检查是否被赋值到模块级变量或外部 ref
5. 检查是否被作为返回值返回但调用方未及时释放
6. 检查 DOM 引用是否在事件回调中长期持有
**需要查看**：函数实现、闭包、异步回调、返回值使用
**正常标准**：
- 函数内临时变量在函数返回后无外部引用
- 大对象不在闭包中长期持有
- 异步回调中引用的大对象在回调执行后释放
- DOM 引用不长期持有
**异常情况**：
- 闭包捕获了大对象导致内存无法回收
- setTimeout 回调持有大对象，定时器未清理则大对象一直不释放
- 临时变量被赋值到模块级 ref 导致长期持有
- 函数返回大对象但调用方长期持有引用
**风险等级**：P1
**整改方向**：避免闭包捕获大对象；异步回调中显式置空；不在临时函数中修改外部状态
**验收标准**：函数内临时变量在函数返回后无外部引用；无闭包泄漏

## 第二部分：全局状态管理生命周期

> 目标：建立 store 全量地图，回答「状态何时创建、何时修改、何时清理、何时重置」

### 指标 2.1：store 职责单一性

**指标名称**：store 职责单一性
**检查目标**：确认每个 store 只承担一个业务域的职责，不存在「万能 store」
**为什么需要检查**：万能 store 是状态管理的反模式，会导致单文件膨胀、修改牵连面过大、命名空间冲突、持久化策略难以制定。store 职责单一是状态可维护的基础
**检查范围**：所有 Pinia / Vuex / Redux store 定义文件
**检查方法**：
1. 列出所有 store
2. 为每个 store 用一句话描述职责
3. 若一句话描述不出或出现「和」「以及」「同时」，标记为可疑
4. 检查 store 的 state 是否跨多个业务域（如同时含用户信息和地图配置）
5. 检查 store 的 action 是否跨多个业务域
6. 检查 store 文件行数（超过 300 行需说明理由）
**需要查看**：store 定义文件、state、action、getter
**正常标准**：
- 每个 store 能用一句话描述职责
- state 与 action 都围绕同一业务域
- 单 store 文件行数合理（建议 < 300 行）
- 无「万能 store」
**异常情况**：
- 一个 store 同时管理用户、地图、配置、UI 状态
- store 文件超过 500 行
- store 命名为 `common`、`global`、`main` 等含糊词
- store 的 state 字段跨多个业务域
**风险等级**：P1
**整改方向**：按业务域拆分 store；万能 store 拆为多个职责单一的 store
**验收标准**：每个 store 单一职责；无万能 store；行数合理

### 指标 2.2：store state 修改入口收敛

**指标名称**：store state 修改入口收敛（只通过 action）
**检查目标**：确认 store 的 state 只能通过 action 修改，不存在组件直接修改 state 的情况
**为什么需要检查**：直接修改 state 会绕过 action 的日志、校验、副作用管理，让状态变化不可追溯，是「状态莫名其妙变化」的根因。Pinia 默认允许直接修改，更需人工约束
**检查范围**：所有组件、composable、service 中对 store state 的访问
**检查方法**：
1. 搜索所有 `store.xxx =` 形式的直接赋值（Pinia 默认允许）
2. 搜索所有 `store.$patch` 调用（应有限使用）
3. 检查组件是否通过解构后修改（`const { foo } = store; foo.bar = 1` 这种是修改原 state）
4. 检查 action 是否是修改 state 的唯一入口
5. 检查 Pinia 配置是否启用 `disabled: 'error'` 禁止直接修改
6. 检查 action 内是否有修改日志或可观测点
**需要查看**：store 定义、组件中的 store 使用、Pinia 配置
**正常标准**：
- state 修改只通过 action
- 无组件直接 `store.xxx =` 赋值
- `$patch` 仅用于批量更新且有合理理由
- action 是状态修改的唯一入口
- 修改入口有日志或可观测点
**异常情况**：
- 组件中存在 `store.xxx = yyy` 直接赋值
- 通过解构后修改原对象绕过 action
- 大量使用 `$patch` 替代 action
- 状态变化无日志无法追溯
**风险等级**：P1
**整改方向**：所有 state 修改收敛到 action；启用 Pinia 禁止直接修改；action 加日志
**验收标准**：无直接修改 state 的代码；所有修改走 action；修改有日志

### 指标 2.3：跨 store 数据冗余

**指标名称**：跨 store 数据冗余
**检查目标**：确认同一数据不会在多个 store 中各存一份，避免数据冗余
**为什么需要检查**：跨 store 数据冗余是「数据更新但 UI 不变化」的典型根因。一份在 store A 更新，另一份在 store B 没同步，消费方读到的就是旧值。冗余还会导致修改入口增多、一致性维护成本上升
**检查范围**：所有 store 的 state 字段
**检查方法**：
1. 列出所有 store 的 state 字段
2. 对比是否有同名字段出现在多个 store
3. 对比是否有同义不同名的字段（如 `userId` 与 `uid`）
4. 检查跨 store 引用是否通过 getter 派生而非复制
5. 检查 store A 是否在 action 中调用 store B 的 setter 同步数据（手动同步易漏）
6. 检查组件是否同时从多个 store 读取同一数据
**需要查看**：store state 定义、store 间调用、组件 store 使用
**正常标准**：
- 同一数据只在一个 store 中存储
- 跨 store 引用通过 getter 派生
- 无手动同步同义字段的代码
- 组件从单一 store 读取数据
**异常情况**：
- 用户 ID 同时存在 user store 和 auth store
- store A 的 action 调用 store B 的 setter 同步同一数据
- 组件同时从两个 store 读取「同一」数据
- 同义不同名字段在多个 store 重复
**风险等级**：P1
**整改方向**：单一来源；跨 store 通过 getter 派生；移除手动同步
**验收标准**：同一数据单一 store 存储；跨 store 通过 getter；无手动同步

### 指标 2.4：store 持久化策略合理性

**指标名称**：store 持久化策略合理性
**检查目标**：确认 store 的持久化策略合理：该持久化的持久化了，不该持久化的没持久化
**为什么需要检查**：持久化是 store 生命周期的延伸——本应在刷新后重置的状态如果被持久化，会导致「旧数据残留」「登出后还能看到旧用户数据」；本应持久化的状态如果没持久化，会导致「刷新后丢失登录态/筛选条件」
**检查范围**：所有 store 的持久化配置（pinia-plugin-persistedstate、手动 localStorage）
**检查方法**：
1. 列出所有启用持久化的 store
2. 检查每个持久化的 store：持久化字段是否合理（如 token 应持久化，临时筛选不应持久化）
3. 检查未持久化的 store：是否需要持久化（如用户偏好应持久化）
4. 检查持久化存储位置（localStorage vs sessionStorage vs cookie）
5. 检查登出时是否清除持久化数据
6. 检查持久化数据是否有版本号或迁移机制（schema 变化时不会崩）
7. 检查敏感数据是否加密存储
**需要查看**：持久化配置、登出逻辑、存储读写代码
**正常标准**：
- 持久化字段合理（登录态、用户偏好持久化；临时状态、UI 状态不持久化）
- 存储位置合理（登录态 cookie/httpOnly，偏好 localStorage）
- 登出时清除持久化数据
- 持久化有版本号或迁移机制
- 敏感数据加密
**异常情况**：
- 临时筛选状态被持久化导致下次进入仍是旧筛选
- 登录态未持久化导致刷新掉线
- 登出后持久化数据未清除导致看到旧用户数据
- 持久化数据 schema 变化后解析崩溃
- 敏感数据明文存 localStorage
**风险等级**：P1（敏感数据明文为 P0）
**整改方向**：调整持久化字段；登出清存储；加版本迁移；敏感数据加密或移至后端
**验收标准**：持久化字段合理；登出清除；有版本迁移；敏感数据不泄漏

### 指标 2.5：store 数据清理时机

**指标名称**：store 数据清理时机
**检查目标**：确认 store 中的业务数据在合适的时机被清理，不会无限残留
**为什么需要检查**：store 数据只 set 不 clear 会导致「切换业务模块后看到上一模块数据」「登出后仍能访问旧数据」「内存持续增长」。store 是全局状态，其清理时机必须显式定义
**检查范围**：所有 store 的 state 字段，特别是业务列表数据、详情数据、临时筛选
**检查方法**：
1. 列出每个 store 的 state 字段
2. 对每个字段追问：何时创建？何时更新？何时清理？
3. 检查业务模块切换时是否清理对应 store 数据
4. 检查登出时是否清理所有业务数据（保留登录态配置）
5. 检查详情类数据（如 `currentDetail`）在使用后是否清理
6. 检查列表类数据是否在切换筛选时清空旧数据
7. 检查是否有「只 set 不 clear」的字段
**需要查看**：store action、路由守卫、登出逻辑
**正常标准**：
- 每个字段有明确的清理时机
- 业务模块切换时清理对应数据
- 登出时清理业务数据
- 详情类数据使用后清理
- 无「只 set 不 clear」字段
**异常情况**：
- 切换业务模块后 store 仍残留上一模块数据
- 登出后 `currentDetail` 仍有上一用户数据
- 列表数据切换筛选时未清空导致混合显示
- 临时状态（loading、error）未在合适时机重置
**风险等级**：P1
**整改方向**：定义每类数据的清理时机；路由守卫中调用 store reset；登出时全量清理
**验收标准**：每个字段有清理时机；切换/登出时数据被清理；无残留

### 指标 2.6：store 重置机制

**指标名称**：store 重置机制（登出/切换业务）
**检查目标**：确认 store 有显式的重置机制，能在登出或切换业务时回到初始状态
**为什么需要检查**：没有重置机制的 store 在用户切换账号或业务时会残留前一账号数据，是数据泄漏与状态污染的高发场景。Pinia 提供了 `$reset` 但仅对 option store 有效，composition store 需自行实现
**检查范围**：所有 store 的 reset 实现、登出逻辑、路由切换守卫
**检查方法**：
1. 检查每个 store 是否有 `reset` action 或使用 `$reset`
2. 对 composition store 检查是否手动实现了 reset（$reset 不可用）
3. 检查登出流程是否调用所有 store 的 reset
4. 检查切换业务模块时是否 reset 对应 store
5. 检查 reset 是否真的能恢复到初始状态（测试验证）
6. 检查 reset 是否会误清持久化数据（应保留登录态配置）
**需要查看**：store reset 实现、登出代码、路由守卫
**正常标准**：
- 每个 store 有 reset 机制
- composition store 手动实现 reset
- 登出调用所有 store reset
- 切换业务模块 reset 对应 store
- reset 后状态与初始一致
- reset 不误清持久化配置
**异常情况**：
- store 无 reset 机制
- composition store 误用 $reset（不可用会报错）
- 登出时未调用 reset 导致旧数据残留
- reset 误清了登录态配置导致掉线
- reset 后状态与初始不一致（漏清某些字段）
**风险等级**：P1
**整改方向**：为每个 store 实现 reset；登出调用全量 reset；切换业务调用对应 reset
**验收标准**：所有 store 有可用 reset；登出与切换业务时正确 reset；reset 后状态与初始一致

## 第三部分：对象实例生命周期

> 目标：建立长生命周期对象全量地图，回答「每个对象何时创建、何时销毁、销毁是否彻底」

### 指标 3.1：地图实例（Cesium/OL）创建与销毁

**指标名称**：地图实例（Cesium/OL）创建与销毁
**检查目标**：确认所有 Cesium Viewer / Scene / OpenLayers Map 实例都有对应的 destroy / setTarget(null) 销毁
**为什么需要检查**：地图实例是 WebGIS 项目中最重的对象，单个实例占用数百 MB 内存，且持有 WebGL 上下文。不销毁会直接导致浏览器 WebGL 上下文耗尽（最多 16 个）和内存爆炸
**检查范围**：所有 `new Viewer`、`new Map`、`new Scene`、地图容器创建代码
**检查方法**：
1. 搜索所有 `new Viewer`、`new Map`（OL）、`new Scene` 调用
2. 为每个实例找到对应的 `viewer.destroy()`、`map.setTarget(null)`、`map.dispose()`
3. 检查销毁是否在 onUnmounted / onBeforeUnmount 中
4. 检查销毁前是否清理了所有图层、实体、影像提供者
5. 检查销毁前是否取消了所有事件监听（如 `screenSpaceEventHandler`）
6. 检查销毁后是否置空引用
7. 检查条件渲染场景下地图容器是否存在被重复 init 的可能
8. 检查 keep-alive 场景下是否使用 onActivated/onDeactivated 而非 onMounted/onUnmounted
**需要查看**：地图初始化代码、组件卸载钩子、地图管理器
**正常标准**：
- 每个地图实例有对应 destroy / dispose
- 销毁在 onUnmounted 中（keep-alive 用 onDeactivated）
- 销毁前清理图层、实体、监听
- 销毁后引用置空
- 无重复 init 风险
- WebGL 上下文数量受控
**异常情况**：
- `new Viewer` 但无 `viewer.destroy()`
- 销毁在普通函数中而非生命周期钩子
- 销毁前未清理图层导致 destroy 报错
- 销毁后仍访问 viewer 实例
- keep-alive 下用 onUnmounted 导致切换时被销毁
- 多次进入页面累积创建 Viewer 实例
**风险等级**：P0
**整改方向**：补全 destroy；在 onUnmounted 中销毁；keep-alive 用 onDeactivated；销毁前置空引用
**验收标准**：每个地图实例有销毁；销毁在正确钩子；销毁前清理依赖；无重复创建

### 指标 3.2：ECharts 实例创建与销毁

**指标名称**：ECharts 实例创建与销毁（dispose）
**检查目标**：确认所有 `echarts.init` 都有对应的 `chart.dispose()`，且在组件卸载时调用
**为什么需要检查**：ECharts 实例持有 DOM 引用、Canvas 上下文、内部定时器（动画、tooltip）。不 dispose 会导致 DOM 引用泄漏、Canvas 内存累积、定时器持续运行。多次 init 同一 DOM 还会触发 ECharts 警告
**检查范围**：所有 `echarts.init` 调用
**检查方法**：
1. 搜索所有 `echarts.init` 调用
2. 为每个 init 找到对应的 `chart.dispose()`
3. 检查 dispose 是否在 onUnmounted / onBeforeUnmount 中
4. 检查是否处理了 resize 监听的清理（window resize listener）
5. 检查是否复用实例（同一 DOM 多次 init 是反模式，应 init 一次后 setOption）
6. 检查条件渲染场景下 DOM 不存在时是否跳过 init
7. 检查 DOM 被销毁后是否还有代码访问 chart 实例
8. 检查是否有 `getInstanceByDom` 复用现有实例的逻辑
**需要查看**：echarts.init 代码、组件卸载钩子、resize 处理
**正常标准**：
- 每个 init 有对应 dispose
- dispose 在 onUnmounted 中
- resize 监听在卸载时移除
- 同一 DOM 只 init 一次（复用 setOption）
- 条件渲染下 DOM 不存在时跳过 init
- dispose 后引用置空
**异常情况**：
- `echarts.init` 但无 `dispose`
- 同一 DOM 多次 init 触发 ECharts 警告
- resize 监听未移除导致卸载后仍触发
- dispose 后仍调用 setOption 报错
- 条件渲染下 DOM 不存在仍 init 导致报错
**风险等级**：P0
**整改方向**：补全 dispose；resize 监听移除；复用实例；dispose 后置空
**验收标准**：每个 init 有 dispose；resize 监听移除；无重复 init；dispose 后无访问

### 指标 3.3：WebSocket 创建与关闭

**指标名称**：WebSocket 创建与关闭
**检查目标**：确认所有 `new WebSocket` 都有对应的 `close` 调用，且在不需要时关闭
**为什么需要检查**：WebSocket 是长连接，不关闭会持续占用连接资源、持续接收消息触发回调。组件卸载后未关闭的 WebSocket 还会触发回调访问已销毁组件的状态导致报错。EventSource（SSE）有同样问题
**检查范围**：所有 `new WebSocket`、`new EventSource`、socket.io 连接
**检查方法**：
1. 搜索所有 `new WebSocket`、`new EventSource`、`io.connect`
2. 为每个连接找到对应的 `close` / `disconnect`
3. 检查 close 是否在 onUnmounted 中
4. 检查是否清理了所有 message / open / error 监听
5. 检查重连机制是否会创建多个连接（重连前未 close 旧连接）
6. 检查路由切换时是否关闭连接
7. 检查 close 后是否还有代码发送消息
8. 检查连接状态是否有可观测点（连接/断开日志）
**需要查看**：WebSocket 创建代码、close 调用、监听注册、重连逻辑
**正常标准**：
- 每个连接有对应 close
- close 在 onUnmounted 中
- 所有监听在 close 前移除
- 重连前先 close 旧连接
- 路由切换时关闭连接
- close 后不再发送消息
**异常情况**：
- `new WebSocket` 但无 close
- 重连时未 close 旧连接导致连接数累积
- 组件卸载后 WebSocket 回调访问已销毁状态
- close 后仍调用 send 报错
- 路由切换后旧连接仍在接收消息
**风险等级**：P0
**整改方向**：补全 close；重连前先 close；卸载时移除监听并 close；路由切换关闭
**验收标准**：每个连接有 close；重连无累积；卸载后无回调；路由切换关闭

### 指标 3.4：setInterval/setTimeout 创建与清理

**指标名称**：setInterval/setTimeout 创建与清理
**检查目标**：确认所有 `setInterval` 和组件内的 `setTimeout` 都有对应的 `clearInterval` / `clearTimeout`
**为什么需要检查**：定时器是组件卸载后最容易残留的资源。setInterval 残留会持续触发回调访问已销毁组件状态；setTimeout 残留会在延迟后触发回调。这是 React/Vue 项目中最高频的内存泄漏模式之一
**检查范围**：所有 `setInterval`、`setTimeout` 调用（组件内）
**检查方法**：
1. 搜索所有 `setInterval`、`setTimeout`
2. 为每个返回的 ID 找到对应的 `clearInterval` / `clearTimeout`
3. 检查清理是否在 onUnmounted 中
4. 检查 setInterval 是否有「先 clear 再 set」的防重复机制
5. 检查 setTimeout 回调内是否访问了可能已销毁的组件状态
6. 检查定时器回调内是否有 try/catch（异常不应中断下一次执行）
7. 检查是否优先使用 VueUse 的 `useIntervalFn` / `useTimeoutFn`（自动清理）
8. 检查递归 setTimeout 模式是否有终止条件
**需要查看**：定时器创建代码、清理代码、回调实现
**正常标准**：
- 每个 setInterval 有 clearInterval
- 组件内 setTimeout 有 clearTimeout
- 清理在 onUnmounted 中
- setInterval 有防重复机制
- 回调有 try/catch
- 优先使用自动清理的 composable
**异常情况**：
- setInterval 无 clearInterval
- 组件卸载后定时器仍触发回调
- 多次进入页面累积创建 setInterval
- 回调内访问已销毁状态报错
- 回调异常导致后续不再执行（setInterval）
**风险等级**：P1
**整改方向**：补全 clearInterval/clearTimeout；优先用 useIntervalFn；回调加 try/catch
**验收标准**：所有定时器有清理；卸载后不触发；优先用自动清理 composable

### 指标 3.5：addEventListener 与 removeEventListener 配对

**指标名称**：addEventListener 与 removeEventListener 配对
**检查目标**：确认所有 `addEventListener` 都有对应的 `removeEventListener`，且参数（事件名、回调、选项）一致
**为什么需要检查**：事件监听未移除是内存泄漏的经典来源。更隐蔽的是：移除时回调不是同一引用（如使用了匿名函数或 bind 后未保存引用），会导致 removeEventListener 静默失败，监听其实并未移除
**检查范围**：所有 `addEventListener`、`emitter.on`、`bus.on` 调用
**检查方法**：
1. 搜索所有 `addEventListener`、`emitter.on`、`bus.$on`
2. 为每个 on 找到对应的 `removeEventListener`、`emitter.off`、`bus.$off`
3. 检查移除时的回调是否与注册时是同一引用（不能是匿名函数或新 bind）
4. 检查移除时的事件名、capture/passive 选项是否与注册一致
5. 检查移除是否在 onUnmounted 中
6. 检查条件注册的监听是否在所有路径都有移除
7. 检查 window / document 级监听是否在组件卸载时移除（最容易遗漏）
8. 检查是否优先使用 VueUse 的 `useEventListener`（自动移除）
**需要查看**：事件注册代码、移除代码、回调引用
**正常标准**：
- 每个 addEventListener 有对应 removeEventListener
- 移除时回调是同一引用（具名函数或保存的引用）
- 事件名、选项一致
- 移除在 onUnmounted 中
- window/document 级监听有移除
- 优先使用 useEventListener 自动移除
**异常情况**：
- addEventListener 但无 removeEventListener
- 移除时用了不同的回调引用（匿名函数、重新 bind）
- 移除时选项不一致导致静默失败
- window 监听在组件卸载时未移除
- 条件注册的监听漏移除
**风险等级**：P1
**整改方向**：保存回调引用用于移除；优先 useEventListener；window 监听必须在卸载移除
**验收标准**：所有监听有移除；回调同引用；选项一致；window 监听移除

### 指标 3.6：创建与销毁次数匹配

**指标名称**：创建与销毁次数匹配
**检查目标**：确认对象的创建次数与销毁次数在所有执行路径下都能匹配，不存在「创建多次只销毁一次」或「创建一次销毁多次」
**为什么需要检查**：动态创建场景下（如根据条件创建实例、循环创建监听），容易出现创建次数与销毁次数不匹配。多次创建只销毁一次会泄漏，多次销毁会报错或被静默忽略掩盖 bug
**检查范围**：动态创建对象的条件分支、循环创建、按需创建
**检查方法**：
1. 识别动态创建场景（条件创建、循环创建、列表渲染创建）
2. 追踪每个动态创建的实体是否被收集到容器（数组、Map）
3. 检查销毁时是否遍历容器批量销毁
4. 检查销毁后是否从容器移除（避免重复销毁）
5. 检查条件分支：路径 A 创建了实体，路径 B 是否也创建？销毁是否覆盖所有路径？
6. 检查销毁函数是否有「已销毁」守卫（防止重复销毁报错）
7. 检查异常路径：创建过程中抛错是否导致部分实体未销毁
**需要查看**：动态创建代码、容器管理、批量销毁逻辑
**正常标准**：
- 动态创建的实体被收集到容器
- 销毁时遍历容器批量销毁
- 销毁后从容器移除
- 所有创建路径都有对应销毁
- 销毁函数有「已销毁」守卫
- 异常路径有清理（try/finally）
**异常情况**：
- 循环内创建实例但只销毁最后一个
- 条件创建但销毁未覆盖所有路径
- 销毁后未从容器移除导致重复销毁
- 销毁函数重复调用报错
- 创建过程异常导致部分泄漏
**风险等级**：P1
**整改方向**：动态创建用容器收集；批量销毁；销毁后移除；加守卫；try/finally 清理
**验收标准**：创建与销毁次数匹配；批量销毁；无重复销毁；异常路径有清理

### 指标 3.7：销毁后引用置空

**指标名称**：销毁后引用置空
**检查目标**：确认对象销毁后，所有持有该对象引用的变量都被置空，避免悬挂引用
**为什么需要检查**：销毁对象但不置空引用，会导致后续代码误以为对象还有效而继续访问，触发「对象已销毁」报错或静默错误。置空引用还能让 GC 回收闭包中持有的对象
**检查范围**：所有持有长生命周期对象引用的变量（组件 ref、模块级变量、store state）
**检查方法**：
1. 识别所有持有长生命周期对象引用的变量
2. 检查销毁代码后是否将引用置空（`this.map = null`、`mapRef.value = null`）
3. 检查闭包中是否持有引用（销毁后闭包仍能访问到已销毁对象）
4. 检查 store state 中是否存储了对象引用（销毁后未置空）
5. 检查模块级变量是否在销毁后置空
6. 检查销毁后是否还有代码路径会访问该引用
**需要查看**：销毁代码、引用持有变量、闭包
**正常标准**：
- 销毁后引用置空
- 闭包不长期持有已销毁对象
- store state 中的对象引用在销毁后置空
- 模块级变量在销毁后置空
- 销毁后无代码路径访问该引用
**异常情况**：
- 销毁后引用未置空，后续访问报错
- 闭包持有引用导致对象无法 GC
- store state 残留已销毁对象引用
- 模块级变量残留已销毁对象
**风险等级**：P2
**整改方向**：销毁后置空引用；闭包避免长期持有；store state 清理引用
**验收标准**：销毁后引用置空；无悬挂引用；无闭包持有

### 指标 3.8：销毁顺序正确性

**指标名称**：销毁顺序正确性
**检查目标**：确认多个相关对象的销毁顺序正确，避免「先销毁依赖再销毁被依赖」导致报错
**为什么需要检查**：对象间存在依赖关系（如图层依赖地图、监听依赖事件源、子组件依赖父组件）。销毁顺序错误会导致「访问已销毁对象」报错，或销毁过程静默失败
**检查范围**：组件卸载时多个对象的销毁顺序、地图销毁前的清理顺序
**检查方法**：
1. 列出组件卸载时销毁的所有对象
2. 分析对象间依赖关系（A 依赖 B）
3. 检查销毁顺序是否为「先销毁依赖方再销毁被依赖方」（先 A 后 B）
4. 检查地图销毁前是否先移除所有图层、实体、监听
5. 检查 WebSocket 关闭前是否先移除所有 message 监听
6. 检查父组件销毁前是否先销毁子组件持有的资源
7. 检查销毁过程中是否有「已销毁」守卫防止顺序错误时报错
**需要查看**：卸载钩子中的销毁顺序、对象依赖关系
**正常标准**：
- 销毁顺序符合依赖关系（依赖方先销毁）
- 地图销毁前清理图层、实体、监听
- WebSocket 关闭前移除监听
- 销毁过程有守卫防止报错
- 销毁顺序在代码中有注释说明
**异常情况**：
- 先销毁地图再移除图层导致图层移除报错
- 先关闭 WebSocket 再移除监听导致监听移除失败
- 销毁顺序错误导致静默失败（资源未真正释放）
- 销毁过程抛错中断后续销毁
**风险等级**：P1
**整改方向**：调整销毁顺序；地图先清图层再 destroy；连接先移监听再 close；加 try/finally
**验收标准**：销毁顺序符合依赖关系；销毁过程不报错；资源彻底释放

## 第四部分：状态同步一致性

> 目标：建立状态副本地图，回答「同一状态在多处是否保持一致」

### 指标 4.1：props 复制到本地状态检查

**指标名称**：props 复制到本地状态检查
**检查目标**：确认组件没有将 props 复制到本地 ref / reactive 后再修改，导致 props 与本地状态不一致
**为什么需要检查**：props 复制到本地是 Vue 项目中最常见的状态同步陷阱。父组件更新 props 后，本地副本不会自动同步，导致「父组件改了但子组件显示旧值」。修改本地副本也不会通知父组件，破坏单向数据流
**检查范围**：所有组件的 props 使用，特别是 `const localX = ref(props.x)` 这类模式
**检查方法**：
1. 搜索所有 `ref(props.`、`reactive(props.`、`toRefs(props` 模式
2. 检查本地副本是否在 props 变化时同步（watch props 更新本地）
3. 检查本地副本是否被修改（若修改则破坏单向数据流）
4. 检查是否有「props 用于初始化」的合理场景（如组件内部独立状态，仅种子值来自 props）
5. 检查是否优先使用 computed 派生而非复制
6. 检查 v-model 双向绑定的实现是否符合规范
**需要查看**：组件 props 定义、setup 中 props 使用、watch
**正常标准**：
- props 不复制到本地（直接使用或 computed 派生）
- 若需「初始化用 props 后独立」的场景有明确注释
- 本地副本不被修改（修改通过 emit 通知父组件）
- 优先 computed 派生
- v-model 实现规范
**异常情况**：
- `const localValue = ref(props.value)` 后修改 localValue
- props 变化后本地副本不同步
- 本地修改不通知父组件
- 同一 props 既复制又 watch 同步（冗余）
**风险等级**：P1
**整改方向**：移除本地副本；用 computed 派生；修改通过 emit；v-model 规范化
**验收标准**：无 props 复制到本地；派生用 computed；修改通过 emit

### 指标 4.2：状态单一来源原则

**指标名称**：状态单一来源原则
**检查目标**：确认同一业务状态在系统中只有唯一来源，不存在多处副本
**为什么需要检查**：多处状态副本是「数据更新但 UI 不变化」的根因。一份更新了另一份没同步，消费方读到的就是旧值。单一来源是状态可维护的基础
**检查范围**：store 与组件本地状态、多个组件间的共享状态、store 间的关联状态
**检查方法**：
1. 列出所有业务状态
2. 对每个状态追问：唯一来源在哪里？
3. 检查同一状态是否在 store 和组件本地各存一份
4. 检查多个组件是否各自维护同一状态的副本
5. 检查 URL 参数与 store 状态是否冗余（如筛选条件同时存 URL 和 store）
6. 检查 localStorage 与 store 是否冗余
**需要查看**：store state、组件本地状态、URL 同步逻辑
**正常标准**：
- 每个状态有唯一来源
- store 与组件本地不存同一数据
- URL 参数与 store 有明确同步策略（单一方向）
- localStorage 与 store 不冗余
**异常情况**：
- 同一数据在 store 和组件本地各一份
- 多个组件各自维护同一状态
- URL 和 store 双向同步导致循环
- localStorage 与 store 各存一份且无同步
**风险等级**：P1
**整改方向**：状态收口到单一来源；派生用 computed；URL 与 store 单向同步
**验收标准**：每个状态单一来源；无冗余副本；URL 同步单向

### 指标 4.3：computed 派生 vs 手动 watch 同步

**指标名称**：computed 派生 vs 手动 watch 同步
**检查目标**：确认派生状态优先使用 computed 而非手动 watch 同步
**为什么需要检查**：手动 watch 同步派生状态是反模式——容易漏掉初始值、容易在异步场景下时序错乱、容易遗忘清理 watch。computed 是 Vue 提供的派生状态机制，自动追踪依赖、自动缓存、自动更新
**检查范围**：所有 watch 使用，特别是「watch A 然后 set B」的模式
**检查方法**：
1. 搜索所有 watch 调用
2. 识别「watch 源状态后 set 派生状态」的模式
3. 检查这些场景是否能用 computed 替代
4. 检查 watch 是否处理了 immediate（初始值）
5. 检查 watch 是否有副作用（发请求、修改外部状态）——若纯派生应改 computed
6. 检查 watch 是否在组件卸载时自动停止（Vue 3 默认自动，Vue 2 需手动）
**需要查看**：watch 使用、computed 使用、派生状态
**正常标准**：
- 派生状态用 computed
- watch 仅用于副作用（发请求、操作 DOM、修改外部状态）
- watch 处理了 immediate（需要时）
- watch 在组件卸载时自动停止
**异常情况**：
- 用 watch 同步派生状态而非 computed
- watch 漏掉初始值导致首次渲染错误
- watch 未在卸载时停止（Vue 2）
- 大量 watch 链式同步（A→B→C→D）
**风险等级**：P2
**整改方向**：派生状态改 computed；watch 仅用于副作用；处理 immediate
**验收标准**：派生用 computed；watch 仅副作用；无链式同步

### 指标 4.4：多 store 关联状态同步

**指标名称**：多 store 关联状态同步
**检查目标**：确认多个 store 间的关联状态有正确的同步机制，不会出现「A store 改了 B store 没同步」
**为什么需要检查**：跨 store 关联状态（如 user store 的 userId 关联 order store 的订单）若手动同步极易遗漏。应通过 getter 派生或显式的订阅机制同步
**检查范围**：跨 store 的状态访问、store 间调用
**检查方法**：
1. 识别跨 store 的关联状态（A store 的状态依赖 B store 的状态）
2. 检查同步方式：getter 派生（推荐）/ 订阅 / 手动 setter 同步
3. 检查手动同步是否有遗漏场景
4. 检查 store 间是否有循环依赖（A 依赖 B，B 依赖 A）
5. 检查 store 间调用是否在 action 中（不应在 state 定义时直接引用其他 store）
6. 检查关联状态变化时是否有可观测点
**需要查看**：store 间调用、getter 定义、action 实现
**正常标准**：
- 跨 store 关联状态通过 getter 派生
- 手动同步有完整覆盖
- 无 store 间循环依赖
- store 间调用在 action 中
- 关联状态变化有日志
**异常情况**：
- 跨 store 手动同步遗漏场景
- store 间循环依赖
- 在 state 定义时直接引用其他 store（初始化顺序问题）
- 关联状态变化无日志无法追溯
**风险等级**：P1
**整改方向**：关联状态用 getter 派生；移除循环依赖；store 间调用在 action 中
**验收标准**：跨 store 关联通过 getter；无循环依赖；调用在 action

### 指标 4.5：父子组件状态同步

**指标名称**：父子组件状态同步
**检查目标**：确认父子组件间的状态同步符合单向数据流，通过 props 向下、emit 向上
**为什么需要检查**：父子组件状态同步混乱会导致「父改了子不改」「子改了父不知道」「双向绑定循环」。单向数据流是 Vue 状态同步的基础规范
**检查范围**：所有父子组件的 props/emit 使用、v-model 实现
**检查方法**：
1. 检查父子组件的 props/emit 契约
2. 检查是否有子组件直接修改 props（违反单向数据流）
3. 检查 v-model 是否规范实现（modelValue + update:modelValue）
4. 检查多个 v-model 是否合理
5. 检查 sync 修饰符（Vue 2）是否迁移为 v-model（Vue 3）
6. 检查父子组件是否有「双向同步」导致循环更新
7. 检查 provide/inject 的响应性是否正确传递
**需要查看**：组件 props/emit 定义、v-model 使用、provide/inject
**正常标准**：
- 父子通过 props/emit 单向数据流
- 子组件不直接修改 props
- v-model 规范实现
- 无循环更新
- provide/inject 响应性正确
**异常情况**：
- 子组件直接修改 props 对象属性
- v-model 实现不规范
- 双向同步导致循环更新
- provide/inject 丢失响应性
- 多个 v-model 命名混乱
**风险等级**：P1
**整改方向**：单向数据流；v-model 规范；避免循环更新；provide/inject 用 ref/reactive
**验收标准**：单向数据流；v-model 规范；无循环；响应性正确

## 第五部分：内存风险

> 目标：识别内存泄漏与无限增长隐患，回答「长时间运行后是否会越来越卡」

### 指标 5.1：缓存大小限制与清理策略

**指标名称**：缓存大小限制与清理策略
**检查目标**：确认所有缓存（Map、对象缓存、请求缓存、计算缓存）都有大小限制和清理策略
**为什么需要检查**：缓存只写不清理会导致内存持续增长，长时间运行的 SPA 最终会 OOM。缓存没有大小限制时，单个缓存就可能耗尽内存
**检查范围**：所有缓存实现（Map、WeakMap、对象、lru-cache、自定义缓存）
**检查方法**：
1. 搜索所有缓存实现（Map、对象作为缓存、cache 关键字）
2. 检查每个缓存是否有大小上限
3. 检查缓存是否有清理策略（LRU、TTL、手动清理）
4. 检查缓存项是否有过期机制
5. 检查 WeakMap 使用是否合理（键为对象时可自动回收）
6. 检查请求缓存是否在路由切换或登出时清理
7. 检查计算缓存（memoize）是否有失效机制
**需要查看**：缓存实现、清理逻辑、缓存使用位置
**正常标准**：
- 每个缓存有大小上限
- 缓存有清理策略（LRU/TTL/手动）
- 缓存项有过期机制
- 请求缓存在路由切换/登出时清理
- WeakMap 用于对象键缓存
**异常情况**：
- Map 缓存只 set 不 delete
- 缓存无大小限制
- 请求缓存不清理导致旧数据残留
- memoize 无失效机制
- 缓存项永不过期
**风险等级**：P1
**整改方向**：缓存加 LRU/TTL；设大小上限；路由切换清理；memoize 加失效
**验收标准**：所有缓存有上限和清理；无只写不清的缓存

### 指标 5.2：闭包持有大对象引用

**指标名称**：闭包持有大对象引用
**检查目标**：确认闭包不会意外持有大对象引用，导致大对象无法被 GC 回收
**为什么需要检查**：闭包是 JavaScript 内存泄漏的隐蔽来源。闭包捕获的变量在其引用的函数存活期间不会被回收。如果闭包捕获了大对象（如解析后的数据、DOM 节点、地图实例），会导致大对象长期驻留内存
**检查范围**：所有闭包（内层函数引用外层变量），特别是回调、定时器回调、事件监听回调
**检查方法**：
1. 识别所有闭包（内层函数引用外层变量）
2. 检查闭包是否捕获了大对象（数据、DOM、实例）
3. 检查闭包的生命周期是否长于大对象的预期生命周期
4. 检查闭包是否在用完后释放（移除监听、clear 定时器）
5. 检查模块级闭包（如单例服务内的回调）是否长期持有大对象
6. 检查是否有「闭包链」（A 闭包持有 B 闭包持有 C 大对象）
**需要查看**：闭包实现、捕获的变量、闭包生命周期
**正常标准**：
- 闭包不捕获大对象
- 闭包生命周期与捕获对象生命周期匹配
- 闭包用完后释放（移除监听、clear 定时器）
- 模块级闭包不长期持有大对象
**异常情况**：
- 事件监听回调捕获大对象且未移除
- 定时器回调捕获大对象且未 clear
- 模块级闭包长期持有大对象
- 闭包链导致大对象无法回收
**风险等级**：P1
**整改方向**：闭包不捕获大对象；用完后释放；模块级闭包定期清理
**验收标准**：闭包不持有大对象；用完释放；无闭包链泄漏

### 指标 5.3：事件监听未移除

**指标名称**：事件监听未移除
**检查目标**：确认所有事件监听（DOM、window、document、EventBus、自定义 emitter）都有对应的移除
**为什么需要检查**：事件监听未移除是内存泄漏的经典来源。监听未移除会导致：1）回调持有的引用无法回收；2）回调持续触发浪费性能；3）回调访问已销毁组件状态报错
**检查范围**：所有 addEventListener、emitter.on、bus.$on、$on
**检查方法**：
1. 搜索所有事件注册（addEventListener、on、$on、subscribe）
2. 为每个注册找到对应的移除（removeEventListener、off、$off、unsubscribe）
3. 检查移除时的回调引用是否与注册时一致
4. 检查移除是否在 onUnmounted 中
5. 检查 window/document 级监听是否在组件卸载时移除
6. 检查 EventBus 监听是否在组件卸载时移除
7. 检查是否优先使用自动移除的 composable（useEventListener）
**需要查看**：事件注册代码、移除代码、回调引用
**正常标准**：
- 每个监听有对应移除
- 移除回调引用一致
- 移除在 onUnmounted 中
- window/document 监听移除
- EventBus 监听移除
- 优先 useEventListener
**异常情况**：
- 监听无移除
- 移除回调引用不一致导致静默失败
- window 监听未移除
- EventBus 监听未移除导致跨组件幽灵回调
**风险等级**：P1
**整改方向**：补全移除；保存回调引用；优先 useEventListener
**验收标准**：所有监听有移除；回调一致；无幽灵回调

### 指标 5.4：无限增长集合

**指标名称**：无限增长集合（只 push 不清理的数组/对象）
**检查目标**：确认所有数组、对象、Map、Set 集合都有边界控制，不会无限增长
**为什么需要检查**：只 push 不清理的集合是内存泄漏的隐蔽来源。日志数组、历史记录、消息列表、缓存对象等若不限制大小，长时间运行后会耗尽内存
**检查范围**：所有数组的 push、对象的属性添加、Map/Set 的添加
**检查方法**：
1. 搜索所有 `.push(`、`.set(`、`.add(` 调用
2. 识别「只增不减」的集合（无对应 pop/shift/delete/splice）
3. 检查日志/历史/消息类集合是否有大小限制
4. 检查是否有「环形缓冲区」或「最大长度截断」机制
5. 检查对象属性添加是否有删除机制
6. 检查 Map/Set 是否有清理
**需要查看**：集合操作代码、清理逻辑
**正常标准**：
- 集合有大小上限
- 日志/历史/消息有截断机制
- 对象属性有删除机制
- Map/Set 有清理
- 无「只 push 不清理」的集合
**异常情况**：
- 日志数组只 push 不截断
- 历史记录无上限
- 消息列表累积不清理
- 对象属性只添加不删除
- Map 只 set 不 delete
**风险等级**：P1
**整改方向**：集合加上限；日志/历史截断；定期清理；用环形缓冲区
**验收标准**：所有集合有上限；无无限增长；有清理机制

### 指标 5.5：WebSocket/EventSource 未关闭

**指标名称**：WebSocket/EventSource 未关闭
**检查目标**：确认所有 WebSocket、EventSource 连接在不需要时被关闭，不会长期占用资源
**为什么需要检查**：未关闭的连接会持续占用服务器资源、持续接收消息触发回调、持续消耗客户端内存。组件卸载后未关闭的连接还会触发回调访问已销毁状态
**检查范围**：所有 WebSocket、EventSource、socket.io 连接
**检查方法**：
1. 搜索所有 `new WebSocket`、`new EventSource`、`io.connect`
2. 为每个连接找到对应的 close 调用
3. 检查 close 是否在 onUnmounted 中
4. 检查路由切换时是否关闭连接
5. 检查登出时是否关闭所有连接
6. 检查重连机制是否会累积连接
7. 检查连接状态是否有可观测点
**需要查看**：连接创建代码、close 调用、重连逻辑
**正常标准**：
- 每个连接有 close
- close 在 onUnmounted 中
- 路由切换关闭连接
- 登出关闭所有连接
- 重连不累积
**异常情况**：
- 连接无 close
- 路由切换后旧连接仍存活
- 登出后连接仍接收消息
- 重连累积多个连接
**风险等级**：P0
**整改方向**：补全 close；路由切换关闭；登出关闭；重连先 close 旧连接
**验收标准**：所有连接有 close；路由切换关闭；登出关闭；无累积

### 指标 5.6：DOM 引用未释放

**指标名称**：DOM 引用未释放
**检查目标**：确认所有 DOM 节点引用（getElementById、querySelector、ref）在节点销毁后释放
**为什么需要检查**：DOM 节点引用若长期持有，会阻止 GC 回收 DOM 树，导致「DOM 已从页面移除但内存仍占用」。这是 SPA 路由切换后内存增长的常见原因
**检查范围**：所有 DOM 引用（document.getElementById、querySelector、$el、template ref）
**检查方法**：
1. 搜索所有 DOM 引用获取（getElementById、querySelector、document.querySelector）
2. 检查模块级变量是否持有 DOM 引用
3. 检查闭包是否持有 DOM 引用
4. 检查组件卸载后 DOM 引用是否置空
5. 检查 template ref 是否在卸载后自动置空（Vue 3 会自动）
6. 检查是否有「手动缓存 DOM 节点」的反模式
**需要查看**：DOM 引用代码、模块级变量、闭包
**正常标准**：
- 模块级变量不持有 DOM 引用
- 闭包不长期持有 DOM 引用
- 组件卸载后 DOM 引用置空
- template ref 由 Vue 自动管理
- 无手动缓存 DOM 节点的反模式
**异常情况**：
- 模块级变量持有 DOM 引用
- 闭包持有 DOM 引用且监听未移除
- 组件卸载后仍访问 DOM 引用
- 手动缓存 DOM 节点
**风险等级**：P1
**整改方向**：模块级不持有 DOM；闭包不长期持有；卸载后置空；用 template ref
**验收标准**：无模块级 DOM 引用；闭包不持有；卸载后置空

## 第六部分：响应式正确性

> 目标：确认 Vue 响应式被正确使用，回答「数据变了 UI 是否会更新」

### 指标 6.1：reactive 对象解构丢失响应式

**指标名称**：reactive 对象解构丢失响应式
**检查目标**：确认 reactive 对象没有被直接解构（应用 toRefs），避免丢失响应式
**为什么需要检查**：`const { a } = reactive({a:1})` 解构后 `a` 是普通值，不再是响应式。修改 `a` 不会触发 UI 更新，是 Vue 项目最隐蔽的 bug 之一
**检查范围**：所有 reactive 对象的解构使用
**检查方法**：
1. 搜索所有 `reactive(` 调用
2. 检查 reactive 对象是否被直接解构
3. 检查解构是否使用 toRefs / toRef
4. 检查 reactive 对象作为函数参数时是否被解构
5. 检查 reactive 对象属性赋值给普通变量是否丢失响应式
6. 检查 composable 返回 reactive 对象时是否用 toRefs 包裹
**需要查看**：reactive 使用、解构代码、composable 返回值
**正常标准**：
- reactive 对象不直接解构
- 解构使用 toRefs / toRef
- composable 返回 reactive 用 toRefs 包裹
- 作为函数参数时不解构
**异常情况**：
- `const { a } = reactive({a:1})` 丢失响应式
- composable 返回 reactive 后调用方解构丢失响应式
- reactive 属性赋值给普通变量
**风险等级**：P0
**整改方向**：用 toRefs / toRef 解构；composable 返回用 toRefs
**验收标准**：无 reactive 直接解构；都用 toRefs

### 指标 6.2：props 解构丢失响应式

**指标名称**：props 解构丢失响应式
**检查目标**：确认 props 解构后仍保持响应式（Vue 3.5+ 默认响应式，旧版本需 toRefs）
**为什么需要检查**：在 Vue 3.5 之前，`const { foo } = props` 解构后 `foo` 丢失响应式。Vue 3.5+ 虽然默认保持响应式，但仍需确认项目版本与配置
**检查范围**：所有组件的 props 解构
**检查方法**：
1. 确认 Vue 版本（3.5+ 默认响应式解构）
2. 搜索所有 props 解构
3. 检查解构后是否在 watch/computed 中使用（响应式生效）
4. 检查是否启用了 `propsDestructureTransform`（Vue 3.3-3.4 需手动启用）
5. 检查旧版本是否使用 toRefs 解构 props
6. 检查 props 解构是否有默认值（`withDefaults`）
**需要查看**：Vue 版本、props 解构代码、tsconfig/vite 配置
**正常标准**：
- Vue 3.5+ 或启用了响应式解构
- 旧版本用 toRefs 解构
- 解构后响应式生效
- 有默认值处理
**异常情况**：
- Vue 3.4 及以下未启用响应式解构却直接解构
- 解构后 props 变化不触发更新
- 无默认值处理
**风险等级**：P0
**整改方向**：升级 Vue 3.5+；或用 toRefs 解构；或启用 propsDestructureTransform
**验收标准**：props 解构保持响应式；版本与配置匹配

### 指标 6.3：store 未用 storeToRefs 解构

**指标名称**：store 未用 storeToRefs 解构
**检查目标**：确认 Pinia store 解构时使用 storeToRefs，避免 state 和 getter 丢失响应式
**为什么需要检查**：直接解构 store 会丢失响应式（`const { foo } = store` 中 `foo` 是普通值）。storeToRefs 是 Pinia 提供的解构工具，能保持 state 和 getter 的响应式
**检查范围**：所有 Pinia store 的解构使用
**检查方法**：
1. 搜索所有 store 解构
2. 检查是否使用 `storeToRefs(store)` 解构
3. 检查 action 是否也被 storeToRefs 解构（action 不需要响应式，可直接解构）
4. 检查 `$patch`、`$reset` 等特殊属性的处理
5. 检查解构后 state 变化是否触发更新
**需要查看**：store 解构代码、storeToRefs 使用
**正常标准**：
- store 解构使用 storeToRefs
- action 可直接解构（无需 storeToRefs）
- state 和 getter 保持响应式
**异常情况**：
- `const { foo } = store` 直接解构丢失响应式
- storeToRefs 中包含 action（action 不需要响应式）
- 解构后 state 变化不触发更新
**风险等级**：P0
**整改方向**：用 storeToRefs 解构 state/getter；action 直接解构
**验收标准**：store 解构用 storeToRefs；state/getter 响应式

### 指标 6.4：ref 在 script 中漏 .value

**指标名称**：ref 在 script 中漏 .value
**检查目标**：确认 ref 在 script 中访问时使用 .value（模板中自动解包不需要）
**为什么需要检查**：ref 在 script 中漏 .value 会导致：1）读到 RefImpl 对象而非值；2）比较/计算错误；3）TypeScript 类型不匹配。这是 TypeScript 项目中 ESLint 可拦截的高频问题
**检查范围**：所有 ref 在 script 中的访问
**检查方法**：
1. 搜索所有 ref 声明
2. 检查 script 中访问 ref 是否用 .value
3. 检查 ref 作为函数参数时是否需要 .value
4. 检查 ref 在 watch / computed 中是否用 .value
5. 检查 ref 在解构后是否需要 .value（toRefs 后是 ref，需要 .value）
6. 检查 reactive 内的 ref 是否自动解包（Vue 3 自动解包）
7. 检查 ESLint 是否启用相关规则
**需要查看**：ref 声明、script 中访问、ESLint 配置
**正常标准**：
- script 中访问 ref 用 .value
- 模板中自动解包不用 .value
- reactive 内 ref 自动解包
- ESLint 启用 vue/no-ref-as-operand 等规则
**异常情况**：
- script 中漏 .value 读到 RefImpl
- 比较时 `if (myRef === 1)` 永远 false
- TypeScript 类型不匹配
- toRefs 后忘记 .value
**风险等级**：P1
**整改方向**：补 .value；启用 ESLint 规则
**验收标准**：script 中 ref 都用 .value；ESLint 拦截

### 指标 6.5：Object.assign(reactive) 问题

**指标名称**：Object.assign(reactive) 问题
**检查目标**：确认使用 Object.assign 修改 reactive 对象时的行为符合预期
**为什么需要检查**：`Object.assign(reactiveObj, newObj)` 会触发响应式更新（合理用法），但 `Object.assign({}, reactiveObj)` 会丢失响应式（生成普通对象）。混用容易引发 bug
**检查范围**：所有 Object.assign 使用，涉及 reactive 对象
**检查方法**：
1. 搜索所有 Object.assign 调用
2. 检查目标对象是否为 reactive（`Object.assign(reactive, ...)` 触发更新，合理）
3. 检查是否生成了普通对象（`Object.assign({}, reactive)` 丢失响应式）
4. 检查 reactive 对象整体替换是否用 `Object.assign` 还是直接赋值
5. 检查 Object.assign 是否覆盖了原有属性导致数据丢失
**需要查看**：Object.assign 代码、reactive 使用
**正常标准**：
- `Object.assign(reactive, ...)` 用于更新多个属性（合理）
- 不用 `Object.assign({}, reactive)` 生成普通对象
- 整体替换用直接赋值（`obj.value = newObj`）
- 不误覆盖属性
**异常情况**：
- `Object.assign({}, reactive)` 丢失响应式
- 整体替换用 Object.assign 导致部分属性残留
- 误覆盖原有属性
**风险等级**：P1
**整改方向**：更新用 Object.assign(reactive, ...)；整体替换直接赋值；避免生成普通对象
**验收标准**：Object.assign 用法正确；无响应式丢失

### 指标 6.6：reactive 数组直接索引赋值/length 修改

**指标名称**：reactive 数组直接索引赋值/length 修改
**检查目标**：确认 reactive 数组的修改方式符合 Vue 3 响应式规范
**为什么需要检查**：Vue 3 的 reactive 数组支持直接索引赋值和 length 修改（与 Vue 2 不同），但仍需确认项目用法一致。Vue 2 的响应式数组有诸多限制，迁移项目需特别注意
**检查范围**：所有 reactive 数组的修改
**检查方法**：
1. 搜索所有 reactive 数组
2. 检查索引赋值（`arr[0] = x`）—— Vue 3 支持，Vue 2 不支持需 Vue.set
3. 检查 length 修改（`arr.length = 0`）—— Vue 3 支持
4. 检查是否混用 Vue 2 和 Vue 3 的数组修改方式
5. 检查数组替换（`arr.value = newArr`）是否触发更新
6. 检查 splice、push、pop 等方法的使用
**需要查看**：reactive 数组修改代码、Vue 版本
**正常标准**：
- Vue 3 项目：索引赋值、length 修改均支持
- 不混用 Vue 2 / Vue 3 修改方式
- 数组替换触发更新
- splice/push/pop 正常使用
**异常情况**：
- Vue 2 项目用 `arr[0] = x` 不触发更新
- 混用 Vue.set 和直接赋值
- 数组替换不触发更新
**风险等级**：P1
**整改方向**：确认 Vue 版本；统一数组修改方式；Vue 2 用 Vue.set
**验收标准**：数组修改符合 Vue 版本规范；不混用

### 指标 6.7：computed 中的副作用

**指标名称**：computed 中的副作用
**检查目标**：确认 computed 函数内没有副作用（修改状态、发请求、操作 DOM）
**为什么需要检查**：computed 应为纯函数，副作用会导致：1）多次求值产生不同结果；2）副作用时机不可控（computed 惰性求值）；3）难以调试。computed 中的副作用是 Vue 反模式
**检查范围**：所有 computed 的实现
**检查方法**：
1. 搜索所有 computed 调用
2. 检查 computed 函数内是否修改了外部状态（ref、reactive、store）
3. 检查 computed 函数内是否发请求
4. 检查 computed 函数内是否操作 DOM
5. 检查 computed 函数内是否调用有副作用的函数
6. 检查 computed 是否依赖了 Date.now() / Math.random() 等非响应式源
**需要查看**：computed 实现、依赖关系
**正常标准**：
- computed 为纯函数
- 不修改外部状态
- 不发请求
- 不操作 DOM
- 不依赖非响应式源
**异常情况**：
- computed 内修改 ref/reactive
- computed 内发请求
- computed 内操作 DOM
- computed 依赖 Date.now() 导致缓存失效
**风险等级**：P1
**整改方向**：computed 纯函数化；副作用移到 watch
**验收标准**：computed 无副作用；纯函数

## 第七部分：异步生命周期

> 目标：确认异步逻辑的正确性，回答「异步操作是否安全、是否会竞态、卸载后是否安全」

### 指标 7.1：async 函数 try/catch 完整性

**指标名称**：async 函数 try/catch 完整性
**检查目标**：确认所有 async 函数的 await 都有错误处理（try/catch 或 .catch）
**为什么需要检查**：未捕获的 Promise 拒绝会导致 unhandledrejection 事件，在浏览器中表现为控制台报错，严重时导致页面白屏。异步错误不会冒泡到同步代码的 try/catch，必须显式处理
**检查范围**：所有 async 函数、await 调用
**检查方法**：
1. 搜索所有 `async` 函数
2. 检查函数体内的 await 是否被 try/catch 包裹
3. 检查 catch 是否真正处理错误（而非空 catch 吞掉）
4. 检查 catch 是否有用户可见的提示（message.error 等）
5. 检查 finally 是否清理了 loading 状态
6. 检查是否有「部分 await 在 try 外」的情况
**需要查看**：async 函数实现、try/catch、错误提示
**正常标准**：
- 所有 await 在 try/catch 内
- catch 真正处理错误（非空 catch）
- 有用户可见提示
- finally 清理 loading
- 无遗漏的 await
**异常情况**：
- await 无 try/catch
- 空 catch 吞掉错误
- 无用户提示
- loading 未在 finally 清理
- 部分 await 在 try 外
**风险等级**：P1
**整改方向**：补全 try/catch；非空 catch；加用户提示；finally 清理 loading
**验收标准**：所有 await 有错误处理；有提示；loading 清理

### 指标 7.2：Promise 未 catch

**指标名称**：Promise 未 catch（unhandledrejection）
**检查目标**：确认所有 Promise 链都有 catch 或 await 后的错误处理，避免 unhandledrejection
**为什么需要检查**：Promise 未 catch 会导致 unhandledrejection 事件，浏览器控制台报错，Node.js 中可能导致进程退出。这是异步错误处理的底线
**检查范围**：所有 Promise 链、Promise 构造、.then 调用
**检查方法**：
1. 搜索所有 `.then(` 调用，检查是否有 `.catch`
2. 搜索所有 `new Promise(` 构造，检查 reject 是否被处理
3. 检查 `Promise.all` / `Promise.race` 的错误处理
4. 检查 `Promise.allSettled` 的 rejected 项处理
5. 检查是否有全局 unhandledrejection 监听
6. 检查浮动 Promise（未 await 也未 catch）
**需要查看**：Promise 链、.then/.catch、全局错误监听
**正常标准**：
- 所有 .then 有 .catch
- Promise.all 有 catch
- Promise.allSettled 处理 rejected
- 有全局 unhandledrejection 监听
- 无浮动 Promise
**异常情况**：
- .then 无 .catch
- Promise.all 未 catch 导致整体拒绝
- 浮动 Promise 导致 unhandledrejection
- 无全局错误监听
**风险等级**：P1
**整改方向**：补全 .catch；处理 allSettled rejected；加全局监听；消除浮动 Promise
**验收标准**：所有 Promise 有 catch；无 unhandledrejection

### 指标 7.3：请求竞态

**指标名称**：请求竞态（先发后到覆盖）
**检查目标**：确认并发请求场景下有竞态处理机制，避免「先发的请求后返回覆盖最新结果」
**为什么需要检查**：竞态是异步 bug 中最难复现的。用户快速操作（如连续切换筛选）时，先发的慢请求后返回会覆盖最新结果，导致「显示的不是当前选择的数据」。这是高频线上故障
**检查范围**：所有可并发触发的请求（搜索、筛选、切换 tab、分页）
**检查方法**：
1. 识别可并发触发的请求场景
2. 检查是否有竞态处理机制：
   - AbortController 取消旧请求
   - 标志位（lastRequestId）忽略过期响应
   - 防抖/节流减少触发频率
3. 检查机制是否真正生效（标志位更新时机正确）
4. 检查取消请求后是否会触发 catch（应忽略 AbortError）
5. 检查 UI loading 状态与竞态处理是否一致
6. 检查分页场景的竞态（快速翻页）
**需要查看**：请求封装、竞态处理代码、AbortController 使用
**正常标准**：
- 可并发请求有竞态处理
- 优先使用 AbortController
- 忽略 AbortError
- loading 状态与竞态一致
- 分页场景有竞态处理
**异常情况**：
- 无竞态处理，先发后到覆盖
- 标志位更新时机错误
- 未忽略 AbortError 导致报错
- 分页快速翻页显示错误页
**风险等级**：P0
**整改方向**：用 AbortController 取消旧请求；标志位忽略过期响应；忽略 AbortError
**验收标准**：可并发请求有竞态处理；无覆盖；AbortError 忽略

### 指标 7.4：组件卸载后异步回调执行

**指标名称**：组件卸载后异步回调执行
**检查目标**：确认组件卸载后，未完成的异步回调不会执行或不会访问已销毁状态
**为什么需要检查**：组件卸载后异步回调执行会：1）访问已销毁的 ref/reactive 报错；2）修改已销毁组件状态；3）触发 Vue 警告「无法在已卸载组件上更新」。这是 React/Vue 项目高频警告来源
**检查范围**：所有组件内的异步操作（请求、定时器、Promise）
**检查方法**：
1. 识别组件内的异步操作
2. 检查是否有「卸载标志位」（isUnmounted）在回调中检查
3. 检查是否使用 AbortController 在卸载时取消请求
4. 检查是否使用 onScopeDispose / tryOnScopeDispose 自动清理
5. 检查 VueUse 的 useFetch / useAsyncState 等是否自动处理卸载
6. 检查回调内是否访问了已销毁的 ref
**需要查看**：组件异步操作、卸载钩子、AbortController
**正常标准**：
- 异步回调有卸载检查
- 卸载时取消未完成请求（AbortController）
- 优先使用 VueUse 自动处理卸载的 composable
- 回调不访问已销毁状态
**异常情况**：
- 卸载后回调执行报错
- 卸载后修改状态触发 Vue 警告
- 无卸载检查
- 未取消未完成请求
**风险等级**：P0
**整改方向**：加卸载标志位；用 AbortController 取消；优先 VueUse composable
**验收标准**：卸载后回调不执行或不访问状态；无警告

### 指标 7.5：浮动 Promise

**指标名称**：浮动 Promise（未 await 也未 catch）
**检查目标**：确认没有「浮动 Promise」——调用了返回 Promise 的函数但既不 await 也不 .catch
**为什么需要检查**：浮动 Promise 的错误不会被捕获，导致 unhandledrejection。同时浮动 Promise 的执行时序不可控，可能在本不该执行时执行（如组件卸载后）
**检查范围**：所有返回 Promise 的函数调用
**检查方法**：
1. 搜索所有函数调用，识别返回 Promise 的
2. 检查调用是否被 await 或 .catch
3. 检查 ESLint 是否启用 `no-floating-promises` 规则
4. 检查 `void` 操作符的使用（显式标记浮动 Promise）
5. 检查 fire-and-forget 场景是否有明确注释
**需要查看**：函数调用、ESLint 配置
**正常标准**：
- 无浮动 Promise
- ESLint 启用 no-floating-promises
- 显式 fire-and-forget 用 void 标记且有注释
**异常情况**：
- 调用返回 Promise 的函数但未 await/catch
- ESLint 未启用 no-floating-promises
- 浮动 Promise 导致 unhandledrejection
**风险等级**：P1
**整改方向**：补 await/catch；启用 ESLint 规则；fire-and-forget 用 void 标记
**验收标准**：无浮动 Promise；ESLint 拦截

### 指标 7.6：async/await 错误冒泡

**指标名称**：async/await 错误冒泡
**检查目标**：确认 async 函数中的错误冒泡行为符合预期：要么在当前函数处理，要么向上冒泡被调用方处理
**为什么需要检查**：async 函数中的错误若既不在当前处理也不被调用方处理，就会变成 unhandledrejection。多层 async 调用链的错误冒泡需要明确策略
**检查范围**：多层 async 调用链
**检查方法**：
1. 识别多层 async 调用链（A async 调 B async 调 C async）
2. 检查每一层是否处理错误或向上冒泡
3. 检查最顶层是否有错误处理
4. 检查错误是否被「空 catch」吞掉
5. 检查错误信息是否丢失（catch 后重新抛出但未保留原始错误）
6. 检查是否有「部分处理部分冒泡」的混乱策略
**需要查看**：async 调用链、catch 实现
**正常标准**：
- 每层有明确的错误处理策略
- 最顶层有错误处理
- 无空 catch 吞错
- 错误信息保留
- 处理策略一致
**异常情况**：
- 错误既不处理也不冒泡
- 空 catch 吞掉错误
- 错误信息丢失
- 多层处理策略混乱
**风险等级**：P1
**整改方向**：明确每层错误策略；最顶层兜底；保留错误信息
**验收标准**：错误处理策略明确；最顶层兜底；无吞错

## 第八部分：组件与路由生命周期

> 目标：确认组件和路由的生命周期管理正确，回答「钩子是否配对、路由切换是否清理」

### 指标 8.1：onMounted/onUnmounted 钩子配对

**指标名称**：onMounted/onUnmounted 钩子配对
**检查目标**：确认 onMounted 中创建的资源都在 onUnmounted 中清理，钩子配对完整
**为什么需要检查**：onMounted 中创建的资源（DOM 监听、实例、定时器）若不在 onUnmounted 清理，会随组件反复挂载泄漏。这是 Vue 组件生命周期管理的基础
**检查范围**：所有组件的 onMounted 和 onUnmounted 钩子
**检查方法**：
1. 搜索所有 onMounted 调用
2. 列出 onMounted 中创建的资源
3. 为每个资源找到 onUnmounted 中的清理
4. 检查是否使用 onBeforeUnmount（DOM 还存在时清理）vs onUnmounted（DOM 已销毁）
5. 检查 onMounted 中条件创建的资源是否在所有路径都有清理
6. 检查是否有「onMounted 创建但无 onUnmounted」的组件
**需要查看**：组件生命周期钩子、资源创建与清理
**正常标准**：
- onMounted 创建的资源在 onUnmounted 清理
- 选择合适的钩子（onBeforeUnmount vs onUnmounted）
- 条件创建的资源在所有路径清理
- 无「有 onMounted 无 onUnmounted」的组件
**异常情况**：
- onMounted 创建资源但无 onUnmounted 清理
- 用错钩子（如需访问 DOM 却用 onUnmounted）
- 条件创建漏清理
- 组件只有 onMounted 无 onUnmounted
**风险等级**：P1
**整改方向**：补全 onUnmounted 清理；选择合适钩子；条件创建全覆盖
**验收标准**：onMounted 资源在 onUnmounted 清理；钩子配对完整

### 指标 8.2：onActivated/onDeactivated 配对

**指标名称**：onActivated/onDeactivated 配对（keep-alive）
**检查目标**：确认 keep-alive 缓存的组件使用 onActivated/onDeactivated 而非 onMounted/onUnmounted 管理资源
**为什么需要检查**：keep-alive 组件切换时不触发 onMounted/onUnmounted，而是触发 onActivated/onDeactivated。若仍用 onMounted/onUnmounted 管理资源，组件「切换出去」时资源不会被清理，导致泄漏和回调访问已销毁状态
**检查范围**：所有被 keep-alive 包裹的组件
**检查方法**：
1. 识别被 keep-alive 包裹的组件（路由配置、component 标签）
2. 检查这些组件是否使用 onActivated/onDeactivated
3. 检查 onActivated 中是否重新初始化资源（如重新加载数据、重连 WebSocket）
4. 检查 onDeactivated 中是否暂停/清理资源（如暂停定时器、关闭 WebSocket）
5. 检查是否有「onMounted 创建 + onDeactivated 清理」的错配
6. 检查 keep-alive 的 include/exclude 配置是否合理
**需要查看**：keep-alive 配置、组件生命周期钩子
**正常标准**：
- keep-alive 组件用 onActivated/onDeactivated
- onActivated 重新初始化
- onDeactivated 暂停/清理
- 无钩子错配
- include/exclude 合理
**异常情况**：
- keep-alive 组件用 onMounted/onUnmounted 导致切换不清理
- onActivated 未重新加载数据导致显示旧数据
- onDeactivated 未暂停定时器导致后台运行
- 钩子错配
**风险等级**：P1
**整改方向**：keep-alive 组件改用 onActivated/onDeactivated；onActivated 重载；onDeactivated 暂停
**验收标准**：keep-alive 组件用正确钩子；切换时资源管理正确

### 指标 8.3：路由切换状态清理

**指标名称**：路由切换状态清理
**检查目标**：确认路由切换时，旧路由相关的状态、数据、监听被正确清理
**为什么需要检查**：路由切换不清理会导致：1）旧页面数据残留显示在新页面；2）旧页面的监听/定时器继续运行；3）内存累积。这是 SPA 状态管理的核心场景
**检查范围**：路由守卫、组件卸载、store 重置
**检查方法**：
1. 检查全局路由守卫（beforeEach / afterEach）
2. 检查路由切换时是否清理 store 数据
3. 检查组件 onUnmounted 是否清理路由相关监听
4. 检查 URL 参数同步是否有清理（避免旧参数残留）
5. 检查路由切换时是否关闭 WebSocket / 取消请求
6. 检查 keep-alive 场景下的状态管理
7. 检查路由切换时是否有全局 loading 残留
**需要查看**：路由配置、路由守卫、组件卸载、store reset
**正常标准**：
- 路由切换清理 store 数据
- 组件卸载清理监听
- URL 参数同步有清理
- 切换时关闭连接 / 取消请求
- keep-alive 场景正确处理
- 无 loading 残留
**异常情况**：
- 切换路由后旧页面数据残留
- 旧页面监听继续运行
- URL 参数残留
- 切换后 WebSocket 仍接收旧页面消息
- loading 残留
**风险等级**：P1
**整改方向**：路由守卫清理 store；组件卸载清理监听；切换时关闭连接
**验收标准**：路由切换无残留；监听清理；连接关闭

### 指标 8.4：图层显隐生命周期

**指标名称**：图层显隐生命周期
**检查目标**：确认地图图层的显示/隐藏有正确的生命周期管理，不会累积或残留
**为什么需要检查**：图层显隐是 WebGIS 项目的核心交互。只 add 不 remove、显隐状态不重置、切换业务图层累积，都会导致地图渲染异常和内存增长
**检查范围**：所有地图图层的 add/remove/show/hide 操作
**检查方法**：
1. 搜索所有图层添加代码（addLayer、addVectorLayer、imageryLayers.addImageryProvider）
2. 检查每个图层是否有对应的 remove
3. 检查图层的 show/hide 是否合理（hide 而非 remove 适用于频繁切换）
4. 检查切换业务模块时旧图层是否被 remove
5. 检查图层是否在地图销毁前移除
6. 检查图层显隐状态是否有持久化（如 URL 参数同步）
7. 检查条件渲染的图层是否在条件变化时 remove
**需要查看**：图层管理代码、地图销毁、路由切换
**正常标准**：
- 每个图层 add 有对应 remove
- show/hide 用于频繁切换，remove 用于彻底清理
- 切换业务模块 remove 旧图层
- 地图销毁前移除所有图层
- 显隐状态有合理管理
**异常情况**：
- 图层 add 无 remove
- 切换业务模块后旧图层残留
- 地图销毁前未移除图层导致 destroy 报错
- 显隐状态混乱
**风险等级**：P1
**整改方向**：补全 remove；切换业务 remove 旧图层；销毁前移除图层
**验收标准**：图层 add 有 remove；切换清理；销毁前移除

### 指标 8.5：EventBus/mitt 注册与注销

**指标名称**：EventBus/mitt 注册与注销
**检查目标**：确认所有 EventBus / mitt 的 on 都有对应的 off，且注销时回调引用一致
**为什么需要检查**：EventBus 是全局事件总线，注册的监听若不注销会成为「幽灵监听」，持续触发并访问已销毁组件状态。mitt 的 on/off 同样要求回调引用一致
**检查范围**：所有 EventBus / mitt / 自定义 emitter 的使用
**检查方法**：
1. 搜索所有 `bus.on`、`emitter.on`、`$on`、`EventBus.on`
2. 为每个 on 找到对应的 off
3. 检查 off 时的回调是否与 on 时一致（具名函数或保存的引用）
4. 检查 off 是否在 onUnmounted 中
5. 检查是否有「注册多次只注销一次」
6. 检查是否有「全局 bus 监听跨组件残留」
7. 检查是否优先使用 VueUse 的 useEventBus（自动注销）
**需要查看**：EventBus 注册与注销代码、回调引用
**正常标准**：
- 每个 on 有对应 off
- off 回调引用一致
- off 在 onUnmounted 中
- 无重复注册
- 优先 useEventBus
**异常情况**：
- on 无 off
- off 回调引用不一致导致静默失败
- 全局 bus 监听跨组件残留
- 重复注册
**风险等级**：P1
**整改方向**：补全 off；保存回调引用；优先 useEventBus
**验收标准**：所有 on 有 off；回调一致；无幽灵监听

### 指标 8.6：watch/watchEffect 自动清理

**指标名称**：watch/watchEffect 自动清理
**检查目标**：确认 watch / watchEffect 在组件卸载时自动停止，且 onCleanup 被正确使用处理副作用清理
**为什么需要检查**：Vue 3 的 watch/watchEffect 在组件作用域内会自动停止，但若在组件作用域外（如模块级、setTimeout 内）创建则不会自动停止。watch 的 onCleanup 用于清理上一次副作用（如取消旧请求），遗漏会导致竞态
**检查范围**：所有 watch / watchEffect 调用
**检查方法**：
1. 搜索所有 watch / watchEffect 调用
2. 检查是否在组件作用域内（setup 或 composable 内）——自动停止
3. 检查组件作用域外的 watch 是否手动 stop
4. 检查 watch 的 onCleanup 是否用于清理上一次副作用
5. 检查 watchEffect 的 cleanup 函数是否返回并使用
6. 检查 watch 是否有 immediate 处理
7. 检查 watch 的 deep 选项是否合理（性能影响）
**需要查看**：watch/watchEffect 实现、onCleanup 使用
**正常标准**：
- 组件作用域内 watch 自动停止
- 组件作用域外 watch 手动 stop
- onCleanup 清理上一次副作用
- watchEffect 返回 cleanup
- immediate 处理正确
- deep 选项合理
**异常情况**：
- 模块级 watch 未 stop
- onCleanup 未用于清理导致竞态
- watchEffect 无 cleanup
- immediate 漏处理
- 滥用 deep 导致性能问题
**风险等级**：P1
**整改方向**：模块级 watch 手动 stop；用 onCleanup 清理；watchEffect 返回 cleanup
**验收标准**：watch 自动/手动停止；onCleanup 使用；无竞态

### 指标 8.7：组件间状态同步时序

**指标名称**：组件间状态同步时序
**检查目标**：确认组件间状态同步的时序正确，不会出现「A 改了 B 还没同步」的时序错乱
**为什么需要检查**：组件间状态同步（通过 props/emit/store/EventBus）存在时序问题。如果 A 修改状态后 B 立即读取，可能读到旧值（Vue 异步更新队列）。如果多个组件同时修改同一状态，时序错乱会导致数据不一致
**检查范围**：多组件状态同步、跨组件通信
**检查方法**：
1. 识别组件间状态同步场景
2. 检查同步方式：props/emit（同步）、store（同步）、EventBus（同步）、nextTick（异步）
3. 检查「A 修改后 B 立即读取」是否有时序问题（Vue 异步更新）
4. 检查多组件同时修改同一状态的时序
5. 检查是否需要 nextTick 等待 DOM 更新
6. 检查 watch 的触发时序是否符合预期
7. 检查父子组件挂载顺序（子先 mounted 还是父先 mounted）
**需要查看**：组件通信代码、状态同步逻辑、nextTick 使用
**正常标准**：
- 同步方式符合时序要求
- 异步场景用 nextTick
- 多组件修改有时序控制
- watch 触发时序符合预期
- 父子挂载顺序处理正确
**异常情况**：
- 「A 改了 B 立即读」读到旧值
- 多组件同时修改导致时序错乱
- 未用 nextTick 导致 DOM 未更新
- watch 触发时序错误
- 父子挂载顺序假设错误
**风险等级**：P1
**整改方向**：异步场景用 nextTick；多组件修改加时序控制；明确父子挂载顺序
**验收标准**：状态同步时序正确；无时序错乱

### 指标 8.8：Nest 生命周期钩子与资源闭环
**指标名称**：Nest 生命周期钩子与资源闭环
**检查目标**：确认连接池、请求级客户端、定时器等资源在模块销毁或请求结束时成对释放。
**为什么需要检查**：前端卸载清理已有成熟纪律，服务端同款问题更隐蔽——Pool 不 end 会拖住进程退出与滚动发布，请求级 client 不 release 会在并发下耗尽连接池（表现为偶发超时而非明确报错）。后端迁到 Nest 后，资源生命周期从中间件手写变为框架钩子，必须确认钩子真的接上而不是"看起来有 DI 就没问题"。
**检查范围**：`backend/nest/src/infra/db/`、各 `modules/*` 的 service/repository、定时任务与流式响应。
**检查方法**：
1. `grep -rn "onModuleDestroy\|beforeApplicationShutdown" backend/nest/src`——确认 Pool 有 end 且幂等。
2. `grep -rn "pool.connect\|client.release" backend/nest/src`——确认 try/finally 成对，异常分支也释放。
3. 查 `setInterval` / `setTimeout` 是否配对清理。
4. 起库、停库各一次：观察应用能否在数秒内干净退出（Pool 未 end 会挂住）。
**需要查看**：db provider、各 repository、定时/轮询注册处、应用关闭路径。
**正常标准**：Pool 在模块销毁时 end；请求级 client 在 finally 释放；定时器有清理；进程可干净退出。
**异常情况**：可 grep 的模式——`new Pool` 后无 `pool.end()`；`pool.connect()` 与 `client.release()` 不配对（尤其异常分支）；`setInterval` 无对应 `clearInterval`；控制器直接 `pool.query` 绕过 repository（同时违反分层）。
**风险等级**：P2
**整改方向**：Pool provider 实现销毁钩子；repository 统一 try/finally 释放；定时器挂到模块生命周期；查询收口 repository。
**验收标准**：□ Pool end 有钩子且有测试 □ client release 成对且覆盖异常分支 □ 定时器清理可达 □ 进程退出无挂起
