# TS类型专项审查指标体系

> 版本：v1.0
> 定位：可并行执行的专项审查之一，聚焦 TypeScript 类型安全全链路深度审查
> 适用：AI 辅助代码审查、阶段性类型治理、重构前类型债盘点、第三方库接入类型评估、跨端类型契约对齐
> 与审查体系关系：见 `00-审查体系约定.md`（一级质量属性 #4 类型安全与代码质量）
> 原则约束：所有结论必须来自真实代码证据（tsconfig、源码、类型定义、运行时响应），不依赖框架经验推断

---

## 0. 文档使用说明

### 0.1 文档定位

本文档是「TS 类型安全专项审查标准库」，不是某一次类型治理的报告。

它回答的不是「这个项目现在有什么类型问题」，而是「审查一个 TypeScript 项目的类型安全时应该检查什么、怎么检查、什么算正常、什么算异常」。

本专项可与数据链专项、生命周期专项、架构耦合专项、工程化专项并行执行，互不依赖，结论可交叉引用。

### 0.2 与其他专项的边界

本专项只管类型安全，不管以下事项（但会引用其他专项编号）：

- 数据从哪里来、如何流动 → 由「数据链专项」负责
- 变量、状态、对象的生命周期管理 → 由「生命周期专项」负责
- 模块边界、依赖方向、循环依赖 → 由「架构耦合专项」负责
- 函数职责单一性、副作用、性能 → 由「工程化专项」负责
- 错误处理、安全、构建、测试 → 由「工程化专项」负责

边界交叉点：

- 类型与运行时数据一致性：本专项 4.x 负责类型契约对齐，数据链专项 2.6 负责多数据源业务一致性
- composable 返回类型：本专项 3.4/5.5 负责类型层面，生命周期专项负责实例层面
- store 类型定义：本专项 5.4 负责类型契约，生命周期专项 4.2 负责状态管理

### 0.3 指标条目格式约定

采用 `00-审查体系约定.md` §2 的 11 字段结构：

```
指标名称：该指标的唯一标识名
检查目标：这个指标要确认什么事实
为什么需要检查：不检查会带来什么风险
检查范围：该指标适用于哪些代码实体
检查方法：具体如何执行检查（步骤化）
需要查看：必须阅读哪些证据材料
正常标准：满足什么条件算通过
异常情况：出现什么现象算不通过
风险等级：P0 / P1 / P2 / P3
整改方向：发现问题后的修复路径
验收标准：整改完成后如何证明已修复
```

### 0.4 风险等级定义

见 `00-审查体系约定.md` §2：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

类型安全专项的等级判定原则：

- 类型与运行时严重不一致、`@ts-nocheck` 整文件禁用、API 响应无运行时校验直接当类型用 → P0
- 大量 `any`/`as any`/`@ts-ignore`、strict 未开启、前后端类型契约断裂 → P1
- 隐式 any、未标注返回值、断言滥用 → P2
- interface/type 选择不一致、枚举与联合类型混用、工具类型未使用 → P3

### 0.5 本专项核心原则

**原则 1：类型即契约**
- 类型定义是函数、模块、接口之间的契约文档
- 契约一旦签订，调用方依赖它，被调用方必须遵守它
- 任何对契约的修改都必须显式同步所有调用方

**原则 2：any 是债**
- 每一个 `any` 都是一笔技术债，会在未来某天以运行时错误的形式偿还
- `any` 不是"暂时不用想类型"，而是"把问题推迟到运行时"
- 任何 `any` 都必须有注释说明原因和退出计划

**原则 3：类型与运行时必须一致**
- 类型定义说有这个字段，运行时就必须真的有
- 类型定义说这个字段是 `number`，运行时就不能是 `string`
- "类型说有但运行时没有"比"完全没类型"更危险，因为它给人虚假的安全感

**原则 4：边界处必须有运行时校验**
- 类型只在编译时有效，运行时类型不存在
- API 响应、用户输入、本地存储、postMessage 等外部数据进入系统时，必须有运行时校验
- 不能因为"类型已经定义了"就跳过边界校验

**原则 5：类型应当自文档化**
- 好的类型定义本身就是文档，不需要额外注释解释字段含义
- 类型应当能够回答"这个数据长什么样"的问题
- 命名清晰的类型胜过注释丰富的 `any`

## 第一部分：TS编译配置审查

> 目标：确认 TypeScript 编译配置是否开启了完整的类型安全检查，配置是类型安全的第一道防线
> 配置缺失会让所有源码层面的类型努力归零

### 指标 1.1：tsconfig strict 模式

**指标名称**：tsconfig strict 模式
**检查目标**：确认 `tsconfig.json` 是否开启 `strict: true`，以及该开关是否实际生效（未被局部覆盖）
**为什么需要检查**：`strict` 是 TypeScript 类型安全的总开关，包含 `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes`、`strictPropertyInitialization`、`noImplicitThis`、`alwaysStrict` 等子选项。未开启 strict 等于让一半以上的类型检查失效，源码层面的类型标注再认真也守不住
**检查范围**：项目根 `tsconfig.json`、所有继承的 `tsconfig.*.json`、各业务模块的 `tsconfig.json`、构建工具（vite/webpack）中的 TS 处理配置
**检查方法**：
1. 读取根 `tsconfig.json` 的 `compilerOptions.strict` 字段
2. 若未设置或为 `false`，标记为 P0
3. 若为 `true`，逐项检查 6 个子选项是否被局部关闭（`noImplicitAny: false` 等覆盖）
4. 检查 `extends` 链中是否有覆盖 strict 子选项的配置
5. 检查 vite.config / vue.config 中 `vue-tsc` 或 `fork-ts-checker` 是否启用了类型检查（构建时是否真的跑了类型检查）
6. 检查 CI 流水线是否在 build 前执行 `tsc --noEmit` 或 `vue-tsc --noEmit`
**需要查看**：`tsconfig.json`、`tsconfig.app.json`、`tsconfig.node.json`、`vite.config.ts`、CI 配置文件、`package.json` 的 scripts
**正常标准**：
- `strict: true` 在根配置中显式声明
- 6 个子选项无一处被关闭
- 构建工具启用了类型检查（vue-tsc / fork-ts-checker-webpack-plugin）
- CI 在 build 前执行类型检查命令
- 不存在 `// @ts-ignore` 整段绕过 strict 的现象
**异常情况**：
- `strict` 字段缺失或为 `false`
- `strict: true` 但 `noImplicitAny: false` 等子项被关闭
- 构建配置跳过类型检查（`transpileOnly: true` 且无独立类型检查步骤）
- CI 不跑 `tsc --noEmit`
- 多个 tsconfig 配置中 strict 状态不一致
**风险等级**：P0
**整改方向**：开启 `strict: true`；移除所有子项覆盖；构建管线加入类型检查；CI 加入 `tsc --noEmit` 步骤
**验收标准**：根 tsconfig 显式 `strict: true`；无子项覆盖；CI 类型检查步骤存在且通过；构建产物经过类型校验

### 指标 1.2：noImplicitAny 配置

**指标名称**：noImplicitAny 配置
**检查目标**：确认 `noImplicitAny` 是否开启，以及源码中是否存在隐式 any 参数/变量
**为什么需要检查**：`noImplicitAny` 关闭后，未标注类型的函数参数会默认为 `any`，这是类型漏洞的最大入口。一个隐式 any 参数会让该函数内部所有类型推断失效，错误沿着调用链向上传播
**检查范围**：`tsconfig.json`、所有 `.ts`/`.vue` 文件中的函数参数、箭头函数参数、回调参数
**检查方法**：
1. 读取 `tsconfig.json` 中 `noImplicitAny` 字段
2. 若 `strict: true` 则该字段默认开启，但仍需确认未被显式关闭
3. 全局搜索未标注类型的函数参数（包括方法参数、箭头函数参数、回调参数）
4. 重点检查事件处理器、Promise 回调、数组遍历方法的回调参数
5. 检查 `.vue` 文件中 `<script setup>` 的函数参数
**需要查看**：`tsconfig.json`、源码中所有函数签名、IDE 类型推断提示
**正常标准**：
- `noImplicitAny` 开启（或 strict 开启且未关闭此项）
- 所有函数参数有显式类型标注或能被正确推断
- 回调函数参数有类型（如 `(value: User) => void` 而非 `(value) => void`）
- 事件处理器参数使用 `Event` 或其子类型
**异常情况**：
- `noImplicitAny: false` 显式关闭
- 大量函数参数无类型标注（依赖隐式 any）
- `forEach(item => ...)` 中 `item` 实际为 any
- 事件回调参数无类型（`onClick` 处理器无 `MouseEvent` 标注）
**风险等级**：P0
**整改方向**：开启 `noImplicitAny`；逐个补全参数类型；事件处理器使用正确的 Event 子类型
**验收标准**：`noImplicitAny` 开启；编译无 implicit any 告警；所有参数有显式类型或正确推断

### 指标 1.3：strictNullChecks 配置

**指标名称**：strictNullChecks 配置
**检查目标**：确认 `strictNullChecks` 是否开启，源码中是否正确处理 `null`/`undefined`
**为什么需要检查**：未开启 `strictNullChecks` 时，`null` 和 `undefined` 可以赋值给任何类型，是空指针异常的根源。开启后才能强制开发者在类型层面处理空值
**检查范围**：`tsconfig.json`、所有可能返回 null/undefined 的函数、API 响应类型、可选属性
**检查方法**：
1. 读取 `tsconfig.json` 中 `strictNullChecks` 字段
2. 检查 API 响应类型中哪些字段可能为 null/undefined 但未标注
3. 检查函数返回值是否区分 `T` 和 `T | null`
4. 检查可选属性（`prop?: T`）的使用是否在访问前判断
5. 检查 DOM 查询（`document.getElementById`）返回是否做了 null 判断
6. 检查数组方法（`find`/`pop`）返回的 `T | undefined` 是否处理
**需要查看**：`tsconfig.json`、API 类型定义、函数返回类型、DOM 操作代码
**正常标准**：
- `strictNullChecks` 开启
- API 响应类型显式标注可能为 null 的字段（`field: string | null`）
- 函数返回类型显式区分 `T` 与 `T | null`
- 可选属性访问前有判断或使用可选链（`?.`）
- DOM 查询结果做 null 判断
**异常情况**：
- `strictNullChecks: false`
- API 类型字段全部非空但运行时实际可能为 null
- 函数返回 `User` 但实际可能返回 `null`
- 未使用可选链直接访问可能为空的属性
- `Array.find()` 结果未做 undefined 判断直接使用
**风险等级**：P1
**整改方向**：开启 `strictNullChecks`；API 类型显式标注可空字段；使用可选链和空值合并；函数返回类型显式标注 null 可能性
**验收标准**：`strictNullChecks` 开启；无空值未处理告警；API 类型与运行时 null 行为一致

### 指标 1.4：noUnusedLocals / noUnusedParameters

**指标名称**：noUnusedLocals / noUnusedParameters
**检查目标**：确认是否开启未使用变量/参数检查，以及源码中是否存在死变量
**为什么需要检查**：未使用的变量和参数是死代码的一种，会误导维护者，掩盖真实依赖关系，并增加类型检查的噪声
**检查范围**：`tsconfig.json`、所有 `.ts`/`.vue` 文件中的局部变量、函数参数、import
**检查方法**：
1. 读取 `tsconfig.json` 中 `noUnusedLocals` 和 `noUnusedParameters` 字段
2. 全局搜索声明后从未使用的变量（IDE 会标灰）
3. 检查函数参数中以下划线开头但仍被使用的参数（约定俗成的"故意不用"）
4. 检查 import 但未使用的模块
5. 检查解构后未使用的字段
**需要查看**：`tsconfig.json`、源码、IDE 未使用告警
**正常标准**：
- `noUnusedLocals: true` 和 `noUnusedParameters: true` 开启
- 无未使用的局部变量
- 故意不用的参数以下划线开头（`_unused`）
- import 全部被使用
**异常情况**：
- 配置未开启
- 存在大量声明后未使用的变量
- import 了模块但从未引用
- 解构出字段后未使用
**风险等级**：P2
**整改方向**：开启配置；删除未使用变量；用 ESLint 的 `no-unused-vars` 辅助
**验收标准**：配置开启；编译无未使用告警；ESLint 无 `no-unused-vars` 报错

### 指标 1.5：strictFunctionTypes

**指标名称**：strictFunctionTypes
**检查目标**：确认 `strictFunctionTypes` 开启，函数类型赋值时是否做了逆变检查
**为什么需要检查**：未开启时函数参数类型采用双变检查（不安全），会让 `(x: Animal) => void` 被赋值给 `(x: Dog) => void`，运行时可能传入 Cat 导致错误。开启后强制逆变，是函数类型安全的关键
**检查范围**：`tsconfig.json`、所有函数赋值场景（回调、事件处理器、高阶函数）
**检查方法**：
1. 读取 `tsconfig.json` 中 `strictFunctionTypes` 字段
2. 检查回调函数赋值时参数类型是否兼容
3. 检查事件处理器注册时类型是否匹配
4. 检查高阶函数（map/filter/reduce）的回调类型
5. 重点检查接口中定义的函数成员（接口方法不受 strictFunctionTypes 约束，需注意）
**需要查看**：`tsconfig.json`、回调使用、事件注册、高阶函数调用
**正常标准**：
- `strictFunctionTypes: true`
- 回调函数参数类型与被赋值位置兼容
- 事件处理器类型正确
- 无双变导致的类型不安全赋值
**异常情况**：
- `strictFunctionTypes: false`
- 回调参数类型宽于预期（如期望 `(e: MouseEvent)` 但传入 `(e: any)`）
- 事件处理器类型不匹配但被静默接受
**风险等级**：P2
**整改方向**：开启配置；修正不兼容的回调类型
**验收标准**：配置开启；无函数类型双变赋值；回调类型严格匹配

### 指标 1.6：路径别名配置一致性

**指标名称**：路径别名配置一致性
**检查目标**：确认 `tsconfig.json` 的 `paths` 与构建工具（vite/webpack）的别名配置一致，且类型解析正确
**为什么需要检查**：路径别名不一致会导致"TS 能解析但运行时报错"或"运行时能跑但 TS 报错"，是类型与运行时不一致的典型场景
**检查范围**：`tsconfig.json` 的 `paths`/`baseUrl`、`vite.config.ts` 的 `resolve.alias`、ESLint 的 `import/resolver`、`package.json` 的 `imports`
**检查方法**：
1. 读取 `tsconfig.json` 的 `baseUrl` 和 `paths`
2. 读取 `vite.config.ts` 的 `resolve.alias`
3. 逐项对比两个配置中的别名是否一致
4. 检查 ESLint 配置中 `eslint-import-resolver-typescript` 是否启用
5. 测试别名在 TS 类型解析和运行时都能正确工作
6. 检查是否存在相对路径与别名混用（同一模块一会儿 `@/utils` 一会儿 `../utils`）
**需要查看**：`tsconfig.json`、`vite.config.ts`、`.eslintrc`、源码中的 import 语句
**正常标准**：
- `tsconfig.json` 与构建工具的别名配置完全一致
- ESLint 解析器配置正确
- 项目内统一使用别名或统一使用相对路径（不混用）
- 别名指向的路径存在且正确
**异常情况**：
- `tsconfig.json` 有 `@/*` 但 `vite.config.ts` 没有对应配置
- 别名指向的路径不存在
- 同一模块在 import 中既用别名又用相对路径
- ESLint 无法解析别名导致大量告警
**风险等级**：P2
**整改方向**：对齐两边配置；统一 import 风格；启用 ESLint 别名解析
**验收标准**：tsconfig 与构建工具别名一致；无混用；ESLint 无解析告警

## 第二部分：any治理

> 目标：识别并治理项目中所有的 `any` 使用，将类型债降到最低
> any 是 TypeScript 的逃生舱，每用一个 any 就在类型安全网上开一个洞

### 指标 2.1：any 使用全量统计

**指标名称**：any 使用全量统计
**检查目标**：统计项目中所有显式 `any` 类型标注的位置、数量、上下文
**为什么需要检查**：无法度量就无法治理。any 的总数和分布是类型健康度的核心指标，必须先建立基线
**检查范围**：所有 `.ts`/`.vue` 文件中的类型标注、变量声明、函数参数、返回值、泛型参数
**检查方法**：
1. 全局搜索 `\bany\b` 关键字（注意排除注释和字符串）
2. 统计每个文件的 any 出现次数
3. 按文件、模块、类型（参数/返回值/变量/泛型）分类汇总
4. 标记 any 密集的文件和模块
5. 计算类型健康度指标：`any 总数 / 文件数`、`any 总数 / 代码行数`
**需要查看**：源码全量搜索结果、文件统计
**正常标准**：
- any 总数有基线并持续下降
- 单文件 any 数量 ≤ 3 个
- 核心业务模块（services/stores/types）零 any
- any 密度（any/千行）< 2
**异常情况**：
- 项目存在数百个 any
- 单文件 any 数量 > 10 个
- 类型定义文件（types.ts）中出现 any
- API 请求/响应类型使用 any
**风险等级**：P1
**整改方向**：建立 any 清单；按文件优先级逐个替换为具体类型；用 `unknown` 替代不确定类型
**验收标准**：any 清单建立；核心模块零 any；any 密度持续下降并达标

### 指标 2.2：as any 使用审查

**指标名称**：as any 使用审查
**检查目标**：识别所有 `as any` 类型断言，评估其必要性和可替代性
**为什么需要检查**：`as any` 是显式关闭类型检查，比隐式 any 更危险——它表示"我知道类型不对但我不想管"。每一个 `as any` 都是类型链上的断点
**检查范围**：所有 `.ts`/`.vue` 文件中的 `as any` 表达式
**检查方法**：
1. 全局搜索 `as any` 表达式
2. 对每个 `as any` 评估：是真实需要还是偷懒
3. 检查是否可以用更精确的类型替代（`as unknown as T`、`as Partial<T>`、`as Pick<T, K>`）
4. 检查 `as any` 后是否紧跟未类型安全的操作
5. 检查 `as any` 是否出现在 API 边界（最危险）
6. 检查是否有 `as any as T` 这种双重断言
**需要查看**：源码中的 `as any` 表达式、上下文
**正常标准**：
- `as any` 数量趋近于零
- 残留的 `as any` 有注释说明原因
- 不存在 `as any as T` 双重断言
- API 边界无 `as any`
**异常情况**：
- 大量 `as any` 散落各处
- `as any` 用于绕过本应修复的类型错误
- `as any` 出现在 API 请求/响应处理
- `as any` 后直接访问任意属性
- `as any as T` 双重断言
**风险等级**：P1
**整改方向**：用 `unknown` + 类型守卫替代；用精确类型断言（`as Partial<T>`）；修复底层类型错误而非绕过
**验收标准**：`as any` 数量趋零；残留项有注释和退出计划；无双重断言；API 边界无 `as any`

### 指标 2.3：@ts-ignore 使用审查

**指标名称**：@ts-ignore 使用审查
**检查目标**：识别所有 `@ts-ignore` 注释，评估其必要性和范围
**为什么需要检查**：`@ts-ignore` 会忽略下一行的所有错误，比 `as any` 更粗暴——它不仅关闭类型检查，还关闭所有其他检查。一个 `@ts-ignore` 可能掩盖真实 bug
**检查范围**：所有 `.ts`/`.vue` 文件中的 `@ts-ignore` 注释
**检查方法**：
1. 全局搜索 `@ts-ignore`
2. 对每个 `@ts-ignore` 检查被忽略的具体错误
3. 评估是否可以用 `@ts-expect-error` 替代（后者会验证错误是否真的存在）
4. 检查 `@ts-ignore` 是否有注释说明原因
5. 检查 `@ts-ignore` 是否掩盖了真实类型错误
**需要查看**：源码中的 `@ts-ignore`、被忽略的代码
**正常标准**：
- 无 `@ts-ignore`
- 若必须用，改为 `@ts-expect-error` 并附注释
- 每个 `@ts-expect-error` 有明确的原因说明
**异常情况**：
- 存在 `@ts-ignore`
- `@ts-ignore` 无注释说明原因
- `@ts-ignore` 掩盖了类型不匹配错误
- `@ts-ignore` 用于绕过 strict 检查
**风险等级**：P1
**整改方向**：移除 `@ts-ignore`；修复底层类型错误；改用 `@ts-expect-error` 并注释
**验收标准**：无 `@ts-ignore`；`@ts-expect-error` 有注释且验证有效

### 指标 2.4：@ts-nocheck 使用审查

**指标名称**：@ts-nocheck 使用审查
**检查目标**：识别所有 `@ts-nocheck` 注释，评估其必要性
**为什么需要检查**：`@ts-nocheck` 会禁用整个文件的类型检查，相当于把这个文件降级为 JavaScript。这是最严重的类型债务，必须零容忍
**检查范围**：所有 `.ts`/`.vue` 文件顶部的 `@ts-nocheck` 注释
**检查方法**：
1. 全局搜索 `@ts-nocheck`
2. 列出所有使用 `@ts-nocheck` 的文件
3. 评估每个文件的修复成本和优先级
4. 检查这些文件是否在核心业务路径上
5. 制定逐文件移除 `@ts-nocheck` 的计划
**需要查看**：源码中的 `@ts-nocheck`、文件内容
**正常标准**：
- 项目中无 `@ts-nocheck`
- 若历史遗留，有明确的移除计划和期限
**异常情况**：
- 存在任何 `@ts-nocheck`
- `@ts-nocheck` 出现在核心业务文件（services/stores/components）
- `@ts-nocheck` 文件数量多
- 新增文件使用 `@ts-nocheck`
**风险等级**：P0
**整改方向**：逐文件移除 `@ts-nocheck`；修复类型错误；优先处理核心业务文件
**验收标准**：项目中无 `@ts-nocheck`；所有文件接受完整类型检查

### 指标 2.5：隐式 any（未标注参数）

**指标名称**：隐式 any（未标注参数）
**检查目标**：识别所有未标注类型且被推断为 any 的函数参数
**为什么需要检查**：隐式 any 是"看不见的债"，开发者不知道哪里有 any，类型检查也不报错。它会让函数内部所有类型推断失效
**检查范围**：所有函数（包括方法、箭头函数、回调）的参数
**检查方法**：
1. 在 IDE 中将 `noImplicitAny` 开启并观察告警
2. 全局搜索未标注类型的函数参数（正则：`function\s+\w+\s*\([^:)]+\)` 等）
3. 重点检查回调函数参数：`forEach(item => ...)`、`.then(res => ...)`、`onClick(e => ...)`
4. 检查 Vue 组件的方法参数
5. 检查 composable 返回的函数参数
**需要查看**：源码、IDE 类型告警、tsconfig
**正常标准**：
- 所有函数参数有显式类型标注或能被正确推断
- 回调参数有类型（如 `(item: User) => void`）
- 事件处理器参数有 Event 子类型
- Promise.then 回调参数有类型
**异常情况**：
- 大量函数参数无类型标注
- 回调参数被推断为 any
- 事件处理器参数无类型
- API 响应回调参数为 any
**风险等级**：P1
**整改方向**：开启 `noImplicitAny`；逐个补全参数类型；为回调定义清晰的类型签名
**验收标准**：`noImplicitAny` 开启；编译无隐式 any 告警；所有参数有类型

### 指标 2.6：any 的合理使用场景

**指标名称**：any 的合理使用场景
**检查目标**：评估残留的 any 是否属于合理使用场景，是否附有注释说明
**为什么需要检查**：any 并非绝对不能用，但必须用于真正的合理场景（如第三方库类型缺失、动态代理、调试临时方案），且必须有注释说明原因和退出计划
**检查范围**：所有残留的 any 使用
**检查方法**：
1. 对每个 any 评估其场景是否属于：
   - 第三方库类型缺失（应配合 `declare module` 或 `.d.ts`）
   - 调试临时方案（应有 TODO 和退出计划）
   - 真正的动态类型（如序列化/反序列化边界，应用 `unknown`）
   - 元编程/代理对象（应用 `Proxy` 类型）
2. 检查每个 any 是否有注释说明原因
3. 检查是否有退出计划（何时移除、如何移除）
4. 评估是否能用 `unknown`、`Record<string, unknown>`、`object` 等更安全的类型替代
**需要查看**：残留 any 的上下文、注释
**正常标准**：
- 每个 any 有注释说明原因
- 场景确实属于合理使用
- 有明确的退出计划
- 已考虑 `unknown` 等替代方案但不适用
**异常情况**：
- any 无注释说明
- 场景不属于合理使用（如业务逻辑、API 边界）
- 无退出计划
- 本应用 `unknown` 却用了 `any`
**风险等级**：P2
**整改方向**：为残留 any 补注释；评估替代方案；制定退出计划
**验收标准**：残留 any 全部有注释和退出计划；无替代方案可用

## 第三部分：函数类型契约

> 目标：确保每个函数都有清晰的类型契约，函数是类型系统的基本单元
> （本部分为 TS 类型专项自身扩展）

### 指标 3.1：导出函数参数类型标注

**指标名称**：导出函数参数类型标注
**检查目标**：确认所有导出函数的参数都有显式类型标注
**为什么需要检查**：导出函数是模块对外的 API，其参数类型是契约的核心。无类型标注的参数会让调用方无法正确使用，且在重构时失去类型保护
**检查范围**：所有 `export` 的函数、composable 返回的函数、service 层函数、utils 工具函数
**检查方法**：
1. 全局搜索所有 `export function`、`export const xxx = (...) =>` 声明
2. 检查每个导出函数的参数是否有类型标注
3. 检查参数类型是否为 `any` 或无标注
4. 检查参数类型是否使用了项目内已定义的接口/类型
5. 检查可选参数是否用 `?` 标注
6. 检查剩余参数（rest params）是否有类型
**需要查看**：所有 export 函数声明、参数类型
**正常标准**：
- 所有导出函数的参数有显式类型标注
- 参数类型使用项目内定义的接口/类型而非原始类型重复定义
- 可选参数用 `?` 标注
- 剩余参数有类型（`...args: string[]`）
- 无 `any` 参数
**异常情况**：
- 导出函数参数无类型标注
- 参数类型为 `any`
- 参数类型重复定义而非引用公共类型
- 可选参数未用 `?` 标注
**风险等级**：P1
**整改方向**：补全参数类型；引用公共类型定义；规范可选参数标注
**验收标准**：所有导出函数参数有显式类型；无 any；引用公共类型

### 指标 3.2：导出函数返回值类型标注

**指标名称**：导出函数返回值类型标注
**检查目标**：确认所有导出函数都有显式返回值类型标注
**为什么需要检查**：依赖类型推断的返回值在函数内部实现变化时会悄悄改变对外契约，导致调用方在不知情下类型失效。显式返回值类型是稳定契约的保障
**检查范围**：所有 `export` 的函数、composable 返回、service 函数
**检查方法**：
1. 全局搜索所有 export 函数
2. 检查是否有 `: ReturnType` 显式标注
3. 检查返回 Promise 的函数是否标注 `Promise<T>`
4. 检查返回 void 的函数是否标注
5. 检查返回复杂对象的函数是否引用了定义好的接口
6. 检查异步函数的返回类型是否与 await 后的值一致
**需要查看**：export 函数声明、返回值类型
**正常标准**：
- 所有导出函数有显式返回值类型
- 异步函数返回 `Promise<T>`
- 返回复杂对象时引用接口定义
- 返回类型稳定（不依赖实现细节推断）
- 无 `Promise<any>` 或返回 `any`
**异常情况**：
- 导出函数无返回值类型标注
- 返回 `any` 或 `Promise<any>`
- 返回类型依赖推断且不稳定
- 异步函数返回类型与实际值不匹配
**风险等级**：P1
**整改方向**：补全返回值类型；定义返回值接口；避免返回 any
**验收标准**：所有导出函数有显式返回值类型；无 any 返回；返回类型稳定

### 指标 3.3：内部函数类型标注

**指标名称**：内部函数类型标注
**检查目标**：确认非导出的内部函数也有合理的类型标注
**为什么需要检查**：内部函数虽然不对外，但参数和返回值类型影响其调用方代码的类型安全。完全依赖推断会在重构时丢失保护
**检查范围**：所有未 export 的函数、组件内方法、闭包函数
**检查方法**：
1. 检查组件内的方法参数类型
2. 检查闭包函数参数类型
3. 检查内部工具函数的参数和返回值
4. 评估哪些可以依赖推断（简单函数）哪些必须显式标注（复杂函数）
5. 重点检查回调函数和事件处理器
**需要查看**：组件内部、模块内部函数
**正常标准**：
- 复杂内部函数有显式类型标注
- 简单函数可依赖推断但参数能被正确推断
- 回调函数参数有类型
- 事件处理器参数有 Event 子类型
- 无隐式 any
**异常情况**：
- 内部函数参数全部无类型
- 回调参数被推断为 any
- 事件处理器参数无类型
- 复杂函数返回值依赖推断且不稳定
**风险等级**：P2
**整改方向**：补全复杂函数类型；回调函数参数加类型；事件处理器加 Event 类型
**验收标准**：复杂内部函数有类型；回调参数有类型；无隐式 any

### 指标 3.4：composable 返回类型

**指标名称**：composable 返回类型
**检查目标**：确认所有 composable（`useXxx`）函数的返回类型清晰且稳定
**为什么需要检查**：composable 是 Vue 3 项目复用逻辑的核心单元，其返回类型被多个组件依赖。返回类型不稳定会导致所有使用方类型失效
**检查范围**：所有 `useXxx` 命名的 composable 函数
**检查方法**：
1. 列出所有 composable 函数
2. 检查返回值是对象还是 ref/数组
3. 检查返回值类型是否显式标注
4. 检查返回的 ref 类型是否清晰（`Ref<User>` 而非 `Ref<any>`）
5. 检查返回的函数类型是否清晰
6. 检查返回值是否使用 `Reactive<...>` 或 `Readonly<...>` 包装
7. 检查是否暴露了不该暴露的内部状态
**需要查看**：composable 实现、返回值类型
**正常标准**：
- composable 有显式返回类型或推断稳定
- 返回的 ref 类型清晰（`Ref<T>`）
- 返回的函数类型清晰
- 内部状态不被暴露（用 `readonly` 或不返回）
- 返回值结构与文档一致
**异常情况**：
- composable 返回值类型为 any
- 返回的 ref 类型为 `Ref<any>`
- 返回的函数参数/返回值无类型
- 暴露了内部可变状态
- 返回值结构不稳定（频繁变化）
**风险等级**：P1
**整改方向**：补全返回类型；用 `Ref<T>` 包装；用 `readonly` 保护内部状态
**验收标准**：所有 composable 返回类型清晰；ref 类型为 `Ref<T>`；无 any

### 指标 3.5：回调函数类型标注

**指标名称**：回调函数类型标注
**检查目标**：确认所有回调函数（事件、Promise、数组方法、自定义回调）都有清晰的参数类型
**为什么需要检查**：回调函数是类型推断最容易失效的地方，参数类型丢失会让回调内部所有操作失去类型保护
**检查范围**：所有回调函数使用场景
**检查方法**：
1. 检查 `Array.map/filter/reduce/forEach` 的回调参数类型
2. 检查 `Promise.then/catch/finally` 的回调参数类型
3. 检查事件监听器（`addEventListener`、Vue `@click`）的参数类型
4. 检查自定义回调函数（如 `onSuccess: (data) => void`）的参数类型
5. 检查 `setTimeout/setInterval` 的回调
6. 检查 `watch/watchEffect` 的回调参数类型
**需要查看**：回调使用代码、类型定义
**正常标准**：
- 数组方法回调参数有类型（`(item: User, index: number) => ...`）
- Promise 回调参数有类型（`(value: Response<T>) => ...`）
- 事件监听器参数有 Event 子类型
- 自定义回调参数类型清晰
- watch 回调参数有类型
**异常情况**：
- 回调参数无类型被推断为 any
- 数组方法回调参数为 any
- Promise 回调参数为 any
- 事件监听器参数无类型
- 自定义回调签名不清晰
**风险等级**：P1
**整改方向**：为所有回调参数补类型；定义清晰的回调类型签名
**验收标准**：所有回调参数有类型；无隐式 any；回调签名清晰

### 指标 3.6：函数重载合理性

**指标名称**：函数重载合理性
**检查目标**：确认使用函数重载的场景合理，重载签名与实现一致
**为什么需要检查**：重载是表达"同一函数多种调用形态"的方式，但误用会让类型与实现脱节。重载顺序错误会导致后面的签名永远匹配不到
**检查范围**：所有使用重载的函数
**检查方法**：
1. 全局搜索 function overloading 模式（多个同名 function 声明 + 一个 implementation）
2. 检查重载签名的顺序（更具体的在前）
3. 检查实现签名是否兼容所有重载签名
4. 检查是否有更简单的方案（联合类型、可选参数、泛型）能替代重载
5. 检查重载是否覆盖了所有调用场景
**需要查看**：重载函数声明、实现
**正常标准**：
- 重载用于真实需要的场景（如不同参数类型返回不同类型）
- 重载签名顺序正确（具体在前）
- 实现签名兼容所有重载
- 无可用更简单方案替代的重载
- 重载覆盖所有调用场景
**异常情况**：
- 重载顺序错误导致后面的签名匹配不到
- 实现签名不兼容某个重载
- 重载可以用联合类型或可选参数替代
- 重载遗漏某些调用场景
- 重载签名与实现行为不一致
**风险等级**：P2
**整改方向**：调整重载顺序；用联合类型/泛型替代简单重载；确保实现兼容所有重载
**验收标准**：重载场景合理；顺序正确；实现兼容；无更简单替代方案

## 第四部分：类型契约一致性

> 目标：确保类型定义与实际数据一致，类型不是装饰而是真实契约
> （本部分为 TS 类型专项自身扩展）

### 指标 4.1：前端API类型与后端响应一致性

**指标名称**：前端API类型与后端响应一致性
**检查目标**：确认前端定义的 API 响应类型与后端实际返回的数据结构完全一致
**为什么需要检查**：前后端类型不一致是"接口成功但页面错误"的根因。类型定义说有这个字段，但后端不返回，前端访问就是 undefined
**检查范围**：前端 API 类型定义、后端 controller 返回结构、后端 DTO/VO、API 文档
**检查方法**：
1. 列出前端所有 API 调用及其响应类型
2. 对每个 API 找到后端对应的 controller 和返回类型
3. 逐字段对比：字段名、字段类型、是否可空、是否可选
4. 检查字段命名风格一致（camelCase vs snake_case，是否有转换层）
5. 检查嵌套对象和数组的类型一致性
6. 检查枚举值是否一致（前端 `"active"` 后端 `1`）
7. 检查分页/包装结构是否一致（`{list, total}` vs `{data, count}`）
**需要查看**：前端 API 类型定义、后端 controller/DTO、API 文档、实际响应样本
**正常标准**：
- 前后端字段名一致（或有显式转换层）
- 字段类型一致
- 可空性一致
- 枚举值一致
- 包装结构一致
- 有文档记录字段含义
**异常情况**：
- 前端类型有字段但后端不返回
- 后端返回字段但前端类型没定义
- 同名字段类型不一致（前端 string 后端 number）
- 枚举值不一致
- 命名风格不一致且无转换层
- 包装结构不一致
**风险等级**：P0
**整改方向**：类型对齐；建立自动同步机制（OpenAPI 生成）；显式转换层；统一命名规范
**验收标准**：前后端类型逐字段一致；有自动同步机制或对齐验证流程

### 指标 4.2：类型定义与运行时数据一致性

**指标名称**：类型定义与运行时数据一致性
**检查目标**：确认类型定义与运行时实际数据结构吻合，不存在"类型说有但运行时没有"
**为什么需要检查**：类型只在编译时有效，运行时类型不存在。如果类型与运行时数据不一致，类型检查通过但运行时报错
**检查范围**：所有类型定义、API 响应、本地存储数据、用户输入、第三方接口返回
**检查方法**：
1. 对每个核心类型，对比类型定义与运行时实际数据（通过日志或断点）
2. 检查类型定义的字段是否在运行时真的存在
3. 检查运行时字段的类型是否与定义一致（`number` vs `string`）
4. 检查可空字段在运行时是否真的可能为空
5. 检查数组元素结构是否与定义一致
6. 检查嵌套对象的层级结构
**需要查看**：类型定义、运行时数据样本（接口返回、日志、断点）
**正常标准**：
- 类型定义与运行时数据结构一致
- 字段名、类型、可空性一致
- 嵌套结构一致
- 数组元素结构一致
- 枚举值与运行时一致
**异常情况**：
- 类型定义有字段但运行时没有
- 运行时有字段但类型没定义
- 字段类型不一致
- 可空性不一致
- 嵌套结构不一致
**风险等级**：P0
**整改方向**：根据运行时数据修正类型；建立运行时校验机制；定期对齐
**验收标准**：类型与运行时逐字段一致；有运行时校验机制保障

### 指标 4.3：静态数据与类型定义一致性

**指标名称**：静态数据与类型定义一致性
**检查目标**：确认项目内的静态数据（JSON 文件、常量配置、字典数据）与对应类型定义一致
**为什么需要检查**：静态数据是项目内的"小型数据库"，如果与类型定义不一致，消费方按类型访问会出错
**检查范围**：所有静态 JSON 文件、常量配置、字典数据、mock 数据
**检查方法**：
1. 列出所有静态数据文件
2. 为每个静态数据找到对应的类型定义
3. 逐条对比静态数据与类型定义
4. 检查字段名、类型、可空性
5. 检查枚举值是否在类型定义的范围内
6. 检查是否有类型断言（`as MyType`）掩盖不一致
**需要查看**：静态数据文件、类型定义、消费方代码
**正常标准**：
- 每个静态数据有对应类型定义
- 字段名、类型一致
- 枚举值在合法范围内
- 无 `as MyType` 掩盖不一致
- 静态数据有类型守卫或 as const 标注
**异常情况**：
- 静态数据无类型定义
- 字段不一致
- 枚举值超出类型定义范围
- 用 `as MyType` 强制断言掩盖问题
- 静态数据结构变化未同步类型
**风险等级**：P1
**整改方向**：为静态数据定义类型；用 `as const` 或类型守卫；移除强制断言
**验收标准**：静态数据有类型；字段一致；无强制断言掩盖问题

### 指标 4.4：类型字段多余/缺失检查

**指标名称**：类型字段多余/缺失检查
**检查目标**：识别类型定义中多余的字段（运行时不返回）和缺失的字段（运行时返回但类型没定义）
**为什么需要检查**：多余字段会让代码访问不存在的数据，缺失字段会让维护者不知道有这个数据可用。两者都是类型债
**检查范围**：所有 API 类型定义、核心业务类型
**检查方法**：
1. 对每个 API 类型，对比类型定义字段与运行时返回字段
2. 标记多余字段（类型有但运行时无）
3. 标记缺失字段（运行时有但类型无）
4. 评估多余字段是否应该删除或运行时应该补返回
5. 评估缺失字段是否应该加入类型
6. 检查是否有"历史遗留字段"（曾经返回现在不返回但类型还在）
**需要查看**：类型定义、运行时响应样本、API 文档
**正常标准**：
- 类型字段与运行时字段一一对应
- 无多余字段
- 无缺失字段
- 历史遗留字段已清理
- 字段变更同步更新类型
**异常情况**：
- 类型有 `createTime` 字段但运行时不返回
- 运行时返回 `createTime` 但类型没定义
- 大量历史遗留字段
- 字段变更未同步类型
**风险等级**：P1
**整改方向**：删除多余字段；补充缺失字段；建立类型变更同步流程
**验收标准**：类型字段与运行时一一对应；无多余无缺失

### 指标 4.5：同名字段跨源类型一致性

**指标名称**：同名字段跨源类型一致性
**检查目标**：确认同名字段在不同源（前端类型、后端类型、静态数据、运行时数据）中类型一致
**为什么需要检查**：同名字段在不同源中类型不一致会导致"在这个源里能用那个源里报错"的隐蔽 bug
**检查范围**：跨多个源使用的同名字段（如 `id`、`name`、`status`、`createTime`）
**检查方法**：
1. 提取所有类型定义中的字段名
2. 找出在多个源中出现的同名字段
3. 对比每个源中该字段的类型
4. 重点检查：`id`（string vs number）、`status`（string vs number vs enum）、`time`（string vs number vs Date）
5. 检查同名字段的语义是否一致（同名不同义是更大的问题）
6. 检查转换层是否处理了类型差异
**需要查看**：所有类型定义、字段使用
**正常标准**：
- 同名字段跨源类型一致
- 同名字段语义一致
- 如有差异，有显式转换层
- 转换层有文档说明
**异常情况**：
- `id` 在 A 源是 string 在 B 源是 number
- `status` 在 A 源是枚举在 B 源是 number
- `time` 在 A 源是时间戳在 B 源是字符串
- 同名字段同名不同义
- 无转换层直接混用
**风险等级**：P1
**整改方向**：统一字段类型；建立转换层；文档化字段语义
**验收标准**：同名字段跨源类型一致；有差异处有转换层；语义明确

### 指标 4.6：类型同步机制（手动/自动生成）

**指标名称**：类型同步机制（手动/自动生成）
**检查目标**：确认前后端类型同步有明确机制（手动同步、自动生成、契约测试），而非依赖人工记忆
**为什么需要检查**：纯手动同步必然遗漏，是类型契约漂移的根因。必须有机制保障同步
**检查范围**：类型同步流程、代码生成配置、契约测试、API 文档工具
**检查方法**：
1. 检查是否有 OpenAPI/Swagger 文档
2. 检查是否有自动生成前端类型的工具（openapi-typescript、swagger-typescript-api）
3. 检查是否有契约测试（Pact 等）
4. 检查手动同步的流程和责任人
5. 检查类型变更的评审流程
6. 检查是否有类型版本对齐的 CI 检查
**需要查看**：API 文档、代码生成配置、CI 配置、团队规范文档
**正常标准**：
- 有明确的类型同步机制（自动生成或文档化手动流程）
- 自动生成有配置和 CI 步骤
- 手动同步有责任人和评审流程
- 类型变更有通知机制
- 有契约测试或对齐验证
**异常情况**：
- 无任何同步机制，纯靠人工记忆
- 有 OpenAPI 但未用于生成类型
- 手动同步无流程无责任人
- 类型变更不通知前端
- 无对齐验证
**风险等级**：P1
**整改方向**：建立自动生成机制；若手动则文档化流程和责任人；加入 CI 对齐检查
**验收标准**：有明确同步机制；自动生成或文档化手动流程；CI 有对齐检查

## 第五部分：Vue生态类型安全

> 目标：确保 Vue 3 项目的 props/emit/store/composable 等核心机制有完整类型保护
> Vue 3 的类型支持强大但需要正确使用

### 指标 5.1：组件 props 类型定义

**指标名称**：组件 props 类型定义
**检查目标**：确认所有 Vue 组件的 props 有完整的类型定义
**为什么需要检查**：props 是组件的输入契约，无类型定义会让父组件传错 props 而无告警，重构时失去类型保护
**检查范围**：所有 `.vue` 组件、`defineProps` 使用
**检查方法**：
1. 全局搜索所有 `defineProps` 使用
2. 检查是否使用基于类型的声明（`defineProps<MyProps>()`）而非运行时声明
3. 检查 props 类型是否完整（每个 prop 有类型）
4. 检查必填/可选、默认值、validator
5. 检查 props 类型是否引用公共类型定义
6. 检查复杂 props（对象、数组）的内部类型
7. 检查 `withDefaults` 的使用
**需要查看**：组件 `defineProps`、props 类型定义
**正常标准**：
- 所有组件使用基于类型的 `defineProps<T>()`
- 每个 prop 有明确类型
- 必填/可选清晰
- 复杂 props 内部类型完整
- 默认值用 `withDefaults` 设置
- 引用公共类型定义
**异常情况**：
- 使用运行时声明（`defineProps({ prop: String })`）丢失精确类型
- props 类型为 `any`
- 复杂 props 内部类型缺失
- 无默认值设置
- 类型重复定义未引用公共类型
**风险等级**：P1
**整改方向**：改用基于类型的 `defineProps<T>()`；补全类型；引用公共类型
**验收标准**：所有组件使用 `defineProps<T>()`；类型完整；引用公共类型

### 指标 5.2：组件 emit 类型定义

**指标名称**：组件 emit 类型定义
**检查目标**：确认所有 Vue 组件的 emit 有完整的类型定义
**为什么需要检查**：emit 是组件的输出契约，无类型定义会让父组件监听错事件名或接收错参数类型
**检查范围**：所有 `.vue` 组件、`defineEmits` 使用
**检查方法**：
1. 全局搜索所有 `defineEmits` 使用
2. 检查是否使用基于类型的声明（`defineEmits<MyEmits>()`）
3. 检查每个 emit 事件的参数类型
4. 检查 emit 事件名是否规范
5. 检查是否有事件未在定义中却调用了 emit
6. 检查复杂 emit 参数（对象、数组）的类型
**需要查看**：组件 `defineEmits`、emit 调用
**正常标准**：
- 所有组件使用基于类型的 `defineEmits<T>()`
- 每个 emit 事件有参数类型
- 事件名规范（kebab-case）
- 复杂参数类型完整
- 无未定义却使用的事件
**异常情况**：
- 使用运行时声明
- emit 参数无类型
- 事件名不规范
- 复杂参数类型缺失
- 调用未定义的事件
**风险等级**：P1
**整改方向**：改用基于类型的 `defineEmits<T>()`；补全参数类型；规范事件名
**验收标准**：所有组件使用 `defineEmits<T>()`；参数类型完整；事件名规范

### 指标 5.3：defineModel 类型

**指标名称**：defineModel 类型
**检查目标**：确认使用 `defineModel` 的双向绑定有完整类型定义
**为什么需要检查**：`defineModel` 是 Vue 3.4+ 的双向绑定语法糖，无类型定义会让父组件传入错误类型而子组件接收时类型失效
**检查范围**：所有使用 `defineModel` 的组件
**检查方法**：
1. 全局搜索 `defineModel` 使用
2. 检查每个 `defineModel` 是否有类型参数（`defineModel<User>()`）
3. 检查 model 的默认值
4. 检查 model 的可空性
5. 检查父组件 `v-model` 传入的类型是否与子组件定义一致
**需要查看**：`defineModel` 调用、父组件 `v-model` 使用
**正常标准**：
- 所有 `defineModel` 有类型参数
- 默认值合理
- 可空性明确
- 父子组件类型一致
**异常情况**：
- `defineModel` 无类型参数（推断为 any）
- 默认值缺失
- 可空性不明确
- 父子组件类型不一致
**风险等级**：P2
**整改方向**：补全 `defineModel<T>()` 类型参数；统一父子组件类型
**验收标准**：所有 `defineModel` 有类型；父子组件类型一致

### 指标 5.4：store 类型定义（State/Getters/Actions）

**指标名称**：store 类型定义（State/Getters/Actions）
**检查目标**：确认 Pinia/Vuex store 的 State、Getters、Actions 都有完整类型定义
**为什么需要检查**：store 是全局状态的核心，类型缺失会让所有使用 store 的组件失去类型保护，且难以重构
**检查范围**：所有 Pinia store（`defineStore`）、Vuex store
**检查方法**：
1. 列出所有 store
2. 检查 State 的类型定义（接口定义 or 推断）
3. 检查 Getters 的返回类型
4. 检查 Actions 的参数和返回值类型
5. 检查 store 的整体类型是否能被正确推断
6. 检查组件中使用 `storeToRefs` 后的类型
7. 检查 store 间相互引用的类型
**需要查看**：store 定义、State/Getters/Actions 类型、组件使用
**正常标准**：
- State 有显式接口定义
- Getters 有返回类型
- Actions 参数和返回值有类型
- 组件使用 store 时类型正确推断
- store 间引用类型清晰
- 无 any
**异常情况**：
- State 无类型定义
- Getters 返回 any
- Actions 参数无类型
- 组件使用 store 时类型为 any
- store 间引用类型丢失
**风险等级**：P1
**整改方向**：为 State 定义接口；补全 Getters/Actions 类型；确保组件使用时类型正确
**验收标准**：State 有接口；Getters/Actions 有类型；组件使用类型正确；无 any

### 指标 5.5：composable 返回类型推断

**指标名称**：composable 返回类型推断
**检查目标**：确认 composable 返回类型在组件中使用时能被正确推断
**为什么需要检查**：composable 返回类型推断失败会让组件内使用 composable 的所有变量失去类型保护
**检查范围**：所有 composable 函数、组件中的使用
**检查方法**：
1. 列出所有 composable
2. 在组件中检查 `const { xxx } = useXxx()` 的类型推断
3. 检查返回的 ref 类型（`Ref<User>` vs `Ref<any>`）
4. 检查返回的函数类型
5. 检查返回的 computed 类型
6. 检查解构后是否丢失响应式（响应式问题由生命周期专项负责，此处只看类型）
**需要查看**：composable 实现、组件使用
**正常标准**：
- composable 返回值在组件中类型正确推断
- ref 类型为 `Ref<T>` 而非 `Ref<any>`
- 函数类型清晰
- computed 类型正确
- 无 any
**异常情况**：
- composable 返回类型为 any
- ref 类型为 `Ref<any>`
- 函数参数/返回值无类型
- computed 类型丢失
**风险等级**：P1
**整改方向**：补全 composable 返回类型；确保 ref 类型为 `Ref<T>`
**验收标准**：composable 返回类型在组件中正确推断；无 any

### 指标 5.6：模板引用（ref）类型

**指标名称**：模板引用（ref）类型
**检查目标**：确认组件模板引用（`ref`）有正确的类型标注
**为什么需要检查**：模板引用默认类型为 `any`，访问组件属性或 DOM 方法时无类型保护
**检查范围**：所有使用 `ref` 模板引用的组件
**检查方法**：
1. 全局搜索 `ref=""` 和 `useTemplateRef` 使用
2. 检查 `const myRef = ref<HTMLInputElement | null>(null)` 是否有类型
3. 检查组件引用是否使用 `InstanceType<typeof MyComponent>`
4. 检查访问 ref.value 时的类型推断
5. 检查第三方组件 ref 的类型（如 ECharts 实例）
**需要查看**：模板引用声明、使用位置
**正常标准**：
- 所有模板引用有类型标注
- DOM 引用使用对应 HTML 元素类型
- 组件引用使用 `InstanceType<typeof X>`
- 第三方组件引用有正确类型
- 无 any
**异常情况**：
- 模板引用无类型（默认 any）
- DOM 引用类型错误
- 组件引用无 `InstanceType` 包装
- 第三方组件引用为 any
**风险等级**：P2
**整改方向**：为模板引用补类型；使用 `InstanceType<typeof X>` 标注组件引用
**验收标准**：所有模板引用有类型；无 any；类型推断正确

### 指标 5.7：provide/inject 类型安全

**指标名称**：provide/inject 类型安全
**检查目标**：确认 `provide`/`inject` 使用了类型安全的 InjectionKey 而非字符串
**为什么需要检查**：基于字符串的 `inject` 返回 `any`，且无类型保护。基于 InjectionKey 的方式能保留类型信息
**检查范围**：所有 `provide`/`inject` 使用
**检查方法**：
1. 全局搜索 `provide` 和 `inject` 使用
2. 检查是否使用 `InjectionKey<T>` 而非字符串
3. 检查 inject 的默认值处理
4. 检查 provide 的值类型与 key 类型一致
5. 检查跨组件 inject 的类型推断
**需要查看**：provide/inject 调用、InjectionKey 定义
**正常标准**：
- 使用 `InjectionKey<T>` 而非字符串
- key 类型与 provide 值类型一致
- inject 有默认值或处理 undefined
- 类型在消费方正确推断
- 无 any
**异常情况**：
- 使用字符串作为 key
- inject 返回 any
- provide 值类型与 key 类型不一致
- inject 无默认值且未处理 undefined
**风险等级**：P2
**整改方向**：改用 `InjectionKey<T>`；统一 key 类型；处理 undefined
**验收标准**：所有 provide/inject 使用 InjectionKey；类型一致；无 any

## 第六部分：类型工程化

> 目标：确保类型系统的工程化质量，包括泛型、守卫、断言、导出等高级用法
> 类型工程化决定类型系统的可维护性

### 指标 6.1：类型断言（as）审查

**指标名称**：类型断言（as）审查
**检查目标**：识别所有类型断言（`as`）使用，评估其必要性和安全性
**为什么需要检查**：类型断言会绕过类型检查，是类型安全的隐患。不合理的断言会让"看起来对但运行时错"的代码通过编译
**检查范围**：所有 `.ts`/`.vue` 文件中的 `as` 表达式
**检查方法**：
1. 全局搜索 ` as ` 表达式（注意排除字符串中的 "as"）
2. 对每个断言评估：是真实需要还是偷懒
3. 检查是否有更安全的替代（类型守卫、类型谓词、unknown 中转）
4. 检查 `as` 是否用于"窄化"（合理）还是"宽化"（危险）
5. 检查 `as unknown as T` 双重断言（最危险）
6. 检查断言后的操作是否真的安全
**需要查看**：所有 `as` 表达式、上下文
**正常标准**：
- 断言数量最小化
- 断言用于合理的窄化场景
- 无 `as any`
- 无 `as unknown as T` 双重断言
- 断言有注释说明原因
- 能用类型守卫替代的优先用守卫
**异常情况**：
- 大量 `as` 断言
- `as any`
- `as unknown as T` 双重断言
- 断言用于宽化（把窄类型当宽类型）
- 断言后访问不存在的属性
- 无注释说明
**风险等级**：P2
**整改方向**：用类型守卫替代；用 unknown 中转；减少断言；补注释
**验收标准**：断言数量最小化；无 `as any`/双重断言；有注释；优先用守卫

### 指标 6.2：类型守卫使用合理性

**指标名称**：类型守卫使用合理性
**检查目标**：确认类型守卫（`is`、`in`、`typeof`、`instanceof`）使用合理，能在边界处正确收窄类型
**为什么需要检查**：类型守卫是处理联合类型和 unknown 类型的安全方式，合理使用能在边界处建立类型安全。误用会让守卫后的类型推断失效
**检查范围**：所有类型守卫使用、自定义类型谓词（`x is T`）
**检查方法**：
1. 全局搜索 `is` 类型谓词、`in` 操作符、`typeof`、`instanceof` 使用
2. 检查自定义类型谓词的实现是否正确（守卫逻辑与类型定义一致）
3. 检查是否在边界处（API 响应、外部数据）使用了守卫
4. 检查守卫后的类型是否正确收窄
5. 检查是否有该用守卫却用断言的地方
6. 检查 `in` 操作符的副作用（会触发类型收窄）
**需要查看**：类型守卫实现、使用位置
**正常标准**：
- 边界处（API、外部数据）使用守卫
- 自定义类型谓词实现正确
- 守卫后类型正确收窄
- 该用守卫的地方不用断言
- 守卫有清晰的类型边界
**异常情况**：
- 边界处用断言而非守卫
- 自定义类型谓词实现错误（守卫逻辑与类型不符）
- 守卫后类型未收窄
- 滥用 `in` 操作符
- 该用守卫却用断言
**风险等级**：P2
**整改方向**：边界处改用守卫；修正错误的类型谓词；优先用守卫替代断言
**验收标准**：边界处使用守卫；谓词实现正确；类型正确收窄

### 指标 6.3：泛型使用合理性

**指标名称**：泛型使用合理性
**检查目标**：确认泛型使用合理，避免过度泛化或欠泛化
**为什么需要检查**：泛型是类型系统的核心抽象能力，过度泛化会让类型难以理解，欠泛化会丢失类型信息
**检查范围**：所有泛型函数、泛型接口、泛型类
**检查方法**：
1. 全局搜索泛型声明（`<T>`、`<T extends U>`）
2. 检查泛型约束（`extends`）是否合理
3. 检查泛型是否被实际使用（避免无意义的泛型）
4. 检查泛型参数命名是否规范（T、K、V、U）
5. 检查是否有该用泛型却用 any 的地方
6. 检查泛型默认值的使用
7. 检查复杂泛型是否有注释说明
**需要查看**：泛型声明、使用
**正常标准**：
- 泛型用于真实需要的场景（如工具函数、容器类型）
- 泛型有合理约束（`extends`）
- 泛型参数被实际使用
- 命名规范
- 该用泛型的地方不用 any
- 复杂泛型有注释
**异常情况**：
- 过度泛化（简单逻辑用复杂泛型）
- 欠泛化（该用泛型却用 any）
- 泛型无约束导致类型不安全
- 泛型参数未被使用
- 命名混乱
**风险等级**：P3
**整改方向**：移除无意义泛型；为该用泛型的地方补泛型；加约束；规范命名
**验收标准**：泛型使用合理；有约束；命名规范；无该用泛型却用 any

### 指标 6.4：类型导出与复用

**指标名称**：类型导出与复用
**检查目标**：确认类型定义有合理的导出和复用机制，避免重复定义
**为什么需要检查**：重复定义的类型在变更时需要同步多处，遗漏任一处都会导致类型不一致
**检查范围**：所有类型定义文件（`types.ts`、`interfaces.ts`）、export 的类型
**检查方法**：
1. 列出所有类型定义文件
2. 检查类型是否集中管理还是分散定义
3. 检查是否有重复定义的类型（同名或同结构）
4. 检查类型的导出方式（`export interface` vs `export type`）
5. 检查类型是否被多处复用
6. 检查 barrel 文件（`index.ts`）的使用
7. 检查跨模块类型引用是否清晰
**需要查看**：类型定义文件、export 关系、import 关系
**正常标准**：
- 类型有集中管理位置（如 `types/` 目录）
- 无重复定义
- 复用合理（同一类型多处使用）
- 导出方式规范
- barrel 文件合理使用
- 跨模块引用清晰
**异常情况**：
- 同一类型在多处定义
- 类型散落各处无集中管理
- 该复用的类型重复定义
- 导出方式混乱
- 无 barrel 文件导致深层 import
**风险等级**：P2
**整改方向**：集中类型定义；移除重复；建立 barrel 文件；规范导出
**验收标准**：无重复类型；集中管理；导出规范；复用合理

### 指标 6.5：interface vs type 选择一致性

**指标名称**：interface vs type 选择一致性
**检查目标**：确认项目内 `interface` 和 `type` 的选择有一致规范
**为什么需要检查**：两者都能定义对象类型但语义不同（interface 可被 implements/extends，type 更灵活）。混用会让代码风格不一致
**检查范围**：所有 `interface` 和 `type` 声明
**检查方法**：
1. 统计 `interface` 和 `type` 的使用比例
2. 检查是否有项目规范（如对象用 interface，联合/交叉用 type）
3. 检查是否有混用（同一场景时而 interface 时而 type）
4. 检查是否有该用 interface 却用 type 的（可被扩展的对象类型）
5. 检查是否有该用 type 却用 interface 的（联合类型、映射类型）
**需要查看**：所有 interface 和 type 声明、项目规范
**正常标准**：
- 有明确的选择规范
- 对象类型用 interface（可扩展）
- 联合/交叉/工具类型用 type
- 风格一致
- 规范有文档记录
**异常情况**：
- 无规范，混用随意
- 对象类型用 type 而非 interface
- 联合类型用 interface（不允许）
- 同类场景时而 interface 时而 type
**风险等级**：P3
**整改方向**：制定规范并文档化；按规范统一调整
**验收标准**：有规范文档；使用一致；符合规范

### 指标 6.6：枚举 vs 联合类型选择

**指标名称**：枚举 vs 联合类型选择
**检查目标**：确认 `enum` 和联合类型的选择有一致规范
**为什么需要检查**：两者都能表示有限集合但行为不同（enum 是运行时对象，联合类型是编译时类型）。选择不当会影响类型安全和打包体积
**检查范围**：所有 `enum` 声明和联合类型使用
**检查方法**：
1. 统计 `enum` 和字符串/数字联合类型的使用
2. 检查是否有项目规范
3. 检查 enum 是否真的需要运行时对象（迭代、反向映射）
4. 检查该用联合类型却用 enum 的（只需类型约束）
5. 检查 enum 与后端值的一致性
6. 检查 `const enum` 的使用（编译时内联）
**需要查看**：enum 声明、联合类型、使用位置
**正常标准**：
- 有明确规范
- 需要运行时迭代的用 enum
- 只需类型约束的用联合类型
- enum 值与后端一致
- `const enum` 用于纯类型场景
- 风格一致
**异常情况**：
- 无规范，混用随意
- 只需类型约束却用 enum（增加运行时体积）
- 该用 enum 却用联合类型（需要迭代时）
- enum 值与后端不一致
**风险等级**：P3
**整改方向**：制定规范；按规范统一；确保 enum 值与后端一致
**验收标准**：有规范；使用一致；enum 值与后端对齐

### 指标 6.7：工具类型使用

**指标名称**：工具类型使用
**检查目标**：确认合理使用 TypeScript 内置工具类型（`Partial`/`Pick`/`Omit`/`Record`/`Readonly` 等）和自定义工具类型
**为什么需要检查**：工具类型能避免重复定义相似类型，提高类型可维护性。不用工具类型会导致大量重复且容易遗漏
**检查范围**：所有类型定义中的工具类型使用
**检查方法**：
1. 检查是否有该用 `Partial<T>` 却手动定义全可选版本
2. 检查是否有该用 `Pick<T, K>` 却手动挑选字段
3. 检查是否有该用 `Omit<T, K>` 却手动排除字段
4. 检查是否有该用 `Record<K, V>` 却用 `{ [key: string]: V }`
5. 检查是否有该用 `Readonly<T>` 却手动定义只读版本
6. 检查自定义工具类型的合理性和复用性
7. 检查 `ReturnType`/`Parameters`/`Awaited` 等元类型的使用
**需要查看**：类型定义、工具类型使用
**正常标准**：
- 合理使用内置工具类型
- 无重复定义相似类型
- 自定义工具类型有复用性
- 工具类型组合合理
**异常情况**：
- 手动定义 `Partial`/`Pick`/`Omit` 等价的类型
- 不用 `Record` 而用索引签名
- 重复定义只读版本
- 该用工具类型却复制粘贴
**风险等级**：P3
**整改方向**：用内置工具类型替代手动定义；提取自定义工具类型
**验收标准**：合理使用工具类型；无重复定义；自定义工具有复用

## 第七部分：运行时类型安全

> 目标：确保类型边界处有运行时校验，类型只在编译时有效，运行时需要额外保障
> 这是类型与运行时一致性的最后一道防线

### 指标 7.1：类型边界处的运行时校验

**指标名称**：类型边界处的运行时校验
**检查目标**：确认所有外部数据进入系统处（API 响应、用户输入、本地存储、postMessage）都有运行时校验
**为什么需要检查**：类型只在编译时有效，外部数据不保证符合类型定义。无运行时校验会让"类型说有但运行时没有"的错误直达业务逻辑
**检查范围**：API 响应处理、表单输入、localStorage/sessionStorage 读取、postMessage/onMessage、URL 参数
**检查方法**：
1. 列出所有 API 调用点
2. 检查每个 API 响应是否有运行时校验（zod、自定义校验函数、类型守卫）
3. 检查表单输入是否有校验
4. 检查 localStorage 读取是否有校验（可能被篡改或格式变化）
5. 检查 postMessage 数据是否有校验
6. 检查 URL 参数是否有校验
7. 检查校验失败的处理（默认值、错误提示、上报）
**需要查看**：API 调用、表单处理、localStorage 读取、postMessage、URL 参数解析
**正常标准**：
- 所有 API 响应有运行时校验
- 用户输入有校验
- 本地存储读取有校验
- postMessage 有校验
- URL 参数有校验
- 校验失败有明确处理
**异常情况**：
- API 响应直接当类型用无校验
- 表单输入无校验
- localStorage 读取无校验
- postMessage 无校验
- URL 参数无校验
- 校验失败静默或崩溃
**风险等级**：P0
**整改方向**：在边界处引入运行时校验库（zod 等）；自定义校验函数；处理校验失败
**验收标准**：所有边界处有运行时校验；校验失败有处理；无外部数据直达业务

### 指标 7.2：运行时校验库使用

**指标名称**：运行时校验库使用
**检查目标**：确认运行时校验使用了合适的库（zod、io-ts、class-validator、ajv）或自定义校验函数，且校验与类型定义同步
**为什么需要检查**：手写校验容易遗漏字段且与类型定义脱节。校验库能从校验逻辑自动推导类型，保证校验与类型一致
**检查范围**：校验库的使用、校验函数、类型定义与校验的同步
**检查方法**：
1. 检查项目是否引入运行时校验库
2. 若引入，检查使用范围（是否覆盖所有边界）
3. 检查校验 schema 是否与类型定义同步（如 zod 的 `z.infer<>`）
4. 检查校验失败的错误处理
5. 若未引入库，检查自定义校验函数的完整性
6. 检查校验是否覆盖所有字段（深层校验）
**需要查看**：package.json、校验库使用、校验 schema、错误处理
**正常标准**：
- 引入合适的校验库（推荐 zod）
- 校验 schema 覆盖所有边界
- 类型从 schema 推导（`z.infer<typeof schema>`）
- 校验失败有清晰错误信息
- 深层校验（嵌套对象、数组）
**异常情况**：
- 未引入校验库且无自定义校验
- 引入但使用范围不完整
- 校验 schema 与类型定义脱节
- 校验失败无错误处理
- 仅校验顶层字段
**风险等级**：P1
**整改方向**：引入校验库；从 schema 推导类型；覆盖所有边界；处理校验失败
**验收标准**：有校验库；schema 覆盖边界；类型从 schema 推导；失败有处理

### 指标 7.3：第三方库类型完整性

**指标名称**：第三方库类型完整性
**检查目标**：确认项目使用的第三方库都有完整的类型定义
**为什么需要检查**：第三方库类型缺失会让使用处的类型推断失效，是 any 的重要来源
**检查范围**：`package.json` 的 dependencies、所有 import 的第三方库
**检查方法**：
1. 列出 `package.json` 中所有 dependencies
2. 对每个库检查是否自带类型（`@types/xxx` 或库自身包含）
3. 检查 `@types/xxx` 是否在 devDependencies
4. 检查使用第三方库的代码处类型推断是否正常
5. 检查是否有 `declare module 'xxx'` 补丁
6. 检查无类型库的处理（自定义 `.d.ts` 或 `declare module`）
**需要查看**：`package.json`、`node_modules/@types`、自定义 `.d.ts`、使用代码
**正常标准**：
- 所有第三方库有完整类型
- `@types/xxx` 在 devDependencies
- 使用处类型推断正常
- 无类型库有自定义 `.d.ts`
- 无 `any` 来自第三方库
**异常情况**：
- 第三方库无类型且未补 `.d.ts`
- 使用处类型为 any
- `@types/xxx` 缺失
- 无 `declare module` 补丁
**风险等级**：P2
**整改方向**：安装 `@types/xxx`；为无类型库编写 `.d.ts`；优先选择有类型的库
**验收标准**：所有第三方库有类型；使用处类型正确推断；无 any

### 指标 7.4：类型定义文件（.d.ts）管理

**指标名称**：类型定义文件（.d.ts）管理
**检查目标**：确认项目的 `.d.ts` 文件管理规范，包括环境声明、模块声明、全局类型
**为什么需要检查**：`.d.ts` 文件管理混乱会导致类型冲突、全局污染、类型解析错误
**检查范围**：所有 `.d.ts` 文件、`tsconfig.json` 的 `include`/`exclude`、`env.d.ts`、`shims-vue.d.ts`
**检查方法**：
1. 列出所有 `.d.ts` 文件
2. 检查 `env.d.ts` 或 `shims-*.d.ts` 是否存在且合理
3. 检查 `declare module` 的使用（为无类型库补类型）
4. 检查全局声明（`declare global`）是否最小化
5. 检查 `tsconfig.json` 的 `include` 是否包含所有 `.d.ts`
6. 检查是否有重复的模块声明
7. 检查 Vue 的 `.vue` 文件类型声明（`shims-vue.d.ts`）
**需要查看**：所有 `.d.ts` 文件、`tsconfig.json`、`env.d.ts`
**正常标准**：
- 有 `env.d.ts` 或 `shims-vue.d.ts`
- `declare module` 用于无类型库
- 全局声明最小化
- tsconfig include 包含 `.d.ts`
- 无重复声明
- `.vue` 文件类型声明正确
**异常情况**：
- 缺少 `shims-vue.d.ts` 导致 `.vue` import 报错
- 全局声明泛滥
- tsconfig 未包含 `.d.ts`
- 重复模块声明冲突
- 无类型库未补 `declare module`
**风险等级**：P2
**整改方向**：补全 `shims-vue.d.ts`；收敛全局声明；修复重复声明；为无类型库补声明
**验收标准**：`.d.ts` 管理规范；无冲突；`.vue` 类型正确；全局声明最小化
