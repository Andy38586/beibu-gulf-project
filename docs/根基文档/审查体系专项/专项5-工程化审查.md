# 工程化专项审查指标体系

> 版本：v1.1（2026-08-29 增补指标——见 00 §4 指标演进口径）
> 定位：可并行执行的专项审查之一，聚焦工程质量与生产风险全链路深度审查
> 适用：AI 辅助代码审查、上线前工程体检、生产事故根因复盘、阶段性技术债治理、项目交接工程评估
> 与审查体系关系：见 `00-审查体系约定.md`（一级质量属性 #7 工程化与生产风险）
> 原则约束：所有结论必须来自真实代码证据（源码、配置、构建产物、测试报告、依赖清单、CI 日志），不依赖框架经验推断，不依赖"一般项目都这样"的常识判断

## 0. 文档使用说明

### 0.1 文档定位

本文档是「工程化专项审查标准库」，不是某一次工程治理的报告。

它回答的不是「这个项目现在能不能上线」，而是「审查一个项目的工程质量与生产风险时应该检查什么、怎么检查、什么算正常、什么算异常」。

本专项可与数据链专项、生命周期专项、TS 专项、架构耦合专项、WebGIS 专项并行执行，互不依赖，结论可交叉引用。本专项是距离"生产上线"最近的专项，附录 D 提供可直接使用的上线 Checklist。

### 0.2 与其他专项的边界

本专项负责工程质量与生产风险，专属管辖以下七个领域：

- 错误处理完整性（loading/error/empty 三态、错误边界、错误上报）
- 安全审查（认证、权限、密钥、后门、CORS、依赖漏洞）
- 性能审查（首屏、虚拟化、压缩、缓存、阻塞）
- 测试体系（覆盖率、断言质量、业务流程测试、回归机制）
- 构建与部署（build 成功性、环境变量、Dockerfile、CI、健康检查、回滚）
- 死代码与重复治理（未引用文件、未消费 export、注释代码、重复实现）
- 代码规范与可维护性（ESLint/Prettier、命名一致性、commit 规范、文档）

不管以下事项（但会引用其他专项编号）：

- 数据从哪里来、如何流动 → 由「数据链专项」负责
- 变量、状态、对象的生命周期管理 → 由「生命周期专项」负责，但本专项 5.5 日志轮转会涉及长生命周期对象
- TypeScript 类型覆盖率与类型契约 → 由「TS 专项」负责，但本专项 5.2 环境变量、5.1 build 成功性会涉及类型检查流程
- 模块边界、依赖方向、循环依赖 → 由「架构耦合专项」负责
- 地图图层按需加载、坐标系转换 → 由「WebGIS 专项」负责，本专项 3.3 图层按需加载引用 WebGIS 专项结论

边界交叉点：

- 错误处理与生命周期：本专项 1.6 未捕获 Promise rejection 与生命周期专项 3.5 异步逻辑正确性交叉，本专项负责全局兜底，生命周期专项负责单点处理
- 安全与数据链：本专项 2.4 日志敏感信息与数据链专项 2.7 数据污染交叉，本专项负责日志输出，数据链专项负责数据路径
- 性能与 WebGIS：本专项 3.3 图层按需加载只做"是否按需"判断，WebGIS 专项负责"按需加载的具体实现是否正确"
- 测试与 TS：本专项 4.1 测试覆盖率统计，TS 专项不负责测试但负责被测代码的类型质量
- 构建与 TS：本专项 5.1 build 成功性包含 `tsc --noEmit` 通过，TS 专项负责类型问题本身

### 0.3 指标条目格式约定

采用 `00-审查体系约定.md` §2 的 11 字段结构：

```
指标名称：该指标的唯一标识名
检查目标：这个指标要确认什么事实
为什么需要检查：不检查会带来什么风险
检查范围：该指标适用于哪些代码实体
检查方法：具体如何执行检查（步骤化）
需要查看：必须阅读哪些证据材料
正常标准：满足什么条件算通过
异常情况：出现什么现象算不通过
风险等级：P0 / P1 / P2 / P3
整改方向：发现问题后的修复路径
验收标准：整改完成后如何证明已修复
```

### 0.4 风险等级定义

见 `00-审查体系约定.md` §2：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

工程化专项的等级判定原则：

- 安全漏洞（硬编码密钥、开发后门、绕过认证）、生产构建不可重复、生产路径含 mock、无任何错误兜底导致白屏 → P0
- 错误处理缺失、核心逻辑无测试、build 失败、CI 不跑测试、性能隐患（无虚拟化、无懒加载）、依赖高危漏洞 → P1
- 大段注释代码、临时备份文件、命名不一致、文档缺失 → P2
- ESLint 规则微调、commit 规范细节、注释风格 → P3

### 0.5 本专项核心原则

**原则 1：生产优先**
- 所有检查以"能否上线、上线后是否稳定"为最终评判标准
- "开发环境能跑"不等于"能上线"，必须验证 build 产物、CI 流程、生产配置
- 任何"只在本地验证过"的结论都必须标注「未在生产环境验证」

**原则 2：安全无小事**
- 安全问题一律 P0 起步，不存在"低危安全漏洞"
- 硬编码密钥、开发后门、绕过认证接口是绝对红线，发现即阻断上线
- 安全审查不依赖"攻击者会不会发现"，而依赖"漏洞是否存在"

**原则 3：测试是护城河**
- 没有测试的代码不具备持续维护能力，改一处坏一片
- 测试不仅要"能跑"，还要"真的断言"，只跑不断的测试是虚假安全感
- 核心业务逻辑必须有测试，非核心逻辑至少要有业务流程级测试

**原则 4：构建必须可重复**
- 同一份代码在任何机器上 build 都应产出相同产物（除时间戳等不可避免差异）
- 依赖必须锁版本，环境变量必须有 example，构建步骤必须文档化
- "在我机器上能 build"不是有效结论

**原则 5：错误必须可见**
- 错误不能静默吞掉，必须要么给用户提示，要么上报到日志系统
- 用户看到的错误提示必须可理解，不能直接展示堆栈或错误码
- 白屏、卡死、无响应是错误处理的彻底失败

### 0.6 Agent 并行执行契约（2026-08-11 统一改造）

- **独立线程**：本专项可单独作为一条 agent 审查线程执行，与其余专项**零执行依赖**（支持 8 窗口并行）；跨专项交叉点见 0.2 边界表，仅在产出层面汇总，不在执行层面依赖。
- **输入**：本文档（可按「部分」切片，仅加载本子 agent 负责的部分）+ 对应代码范围 + 设计文档对应章节（见 `00-审查体系约定.md` §4「标准输入资产」，本专项映射：03 二/五/九；01 六）。
- **输出**：发现清单（每条含：指标编号 / 证据 file:line / 风险等级 / 整改建议）→ 写入 `docs/audits/<日期>-<批次名>/专项5-工程化审查-问题副本.md`（产出统一规范见 `00-审查体系约定.md` §4；副本规则见 docs/待解决问题.md 头部），经用户裁决转正主台账；执行记录存同批次目录 `专项5-工程化审查-执行记录.md`（模板见 §0.7）。
- **子 agent 拆分**：按「第 X 部分」切分（拆分规则见 `00-审查体系约定.md` §4：① 1 部分=1 子 agent；② 相邻部分证据重叠>50% 可合并；③ 单专项上限 6；④ 禁止二次拆分）。
  - 本专项 7 部分证据较独立，建议 **5–6 个**子 agent（各 1 部分各领 1 个，或错误处理+安全合 1、性能 1、测试 1、构建 1、死代码+规范合 1）。
  - 每个子 agent 领 1 个切分单元独立执行（输入 = 该单元指标 + 对应代码），主 agent 汇总去重、合并同根因、统一定级。
- **格式约定**：结论必须来自真实代码证据（file:line）；指标编号用本文档编号（如 3.2）；跨专项引用写「专项N X.Y」；**禁止使用草稿/临时编号**（唯一合法编号 = 台账编号体系）。

## 第一部分：错误处理完整性

> 目标：确认项目对"出错"这件事有完整应对，回答"请求失败、数据为空、组件崩溃时用户体验是什么"
> 错误处理是工程质量的底线，没有错误处理的项目不具备上线资格

### 指标 1.1：请求错误处理链完整性（错误可见性视角）

**指标名称**：请求错误处理链完整性（错误可见性视角）
**检查目标**：确认每一个网络请求从发起到结果消费的完整链路中，错误都被捕获、被处理、被用户感知，不存在静默失败的请求
**为什么需要检查**：网络请求是前端项目最高频的失败点，未处理的请求失败会导致"用户点了没反应""数据不显示但无提示""页面卡在 loading"等问题，是用户投诉的主要来源。静默失败的请求还会让开发者误以为功能正常，掩盖真实故障
**检查范围**：所有 HTTP 请求（fetch/axios/封装的 service 函数）、所有调用 service 的组件、所有请求拦截器与响应拦截器
**检查方法**：
1. 列出项目中所有发起网络请求的代码位置（搜索 `fetch(`、`axios`、`request(`、`http.` 等）
2. 对每个请求，检查是否有 `try/catch` 或 `.catch()` 包裹
3. 检查 axios/fetch 封装层是否统一处理了非 2xx 状态码（默认 fetch 不会对 4xx/5xx 抛错）
4. 检查拦截器是否对错误做了统一转换（如把 HTTP 错误转成业务错误对象）
5. 检查错误是否传递到组件层（不能在 service 层吞掉错误后返回 undefined）
6. 检查组件层是否消费了错误状态（设置 error 变量、显示错误提示）
**需要查看**：请求封装代码、service 层实现、组件中的请求调用、拦截器配置
**正常标准**：
- 所有请求有 try/catch 或 .catch 包裹
- fetch 封装层对非 2xx 响应主动抛错
- 拦截器统一转换错误格式
- 错误从 service 层传递到组件层，不被静默吞掉
- 组件层消费错误状态并展示给用户
- 网络错误（断网、超时）有专门处理
**异常情况**：
- 请求无任何错误处理，失败时 Promise rejection 无人接住
- fetch 封装未处理非 2xx，4xx/5xx 被当成成功
- service 层 catch 后返回 undefined/null，组件无法区分"无数据"和"出错"
- 拦截器吞掉错误只 console.log，用户无感知
- 组件层不消费 error 状态，错误时仍显示 loading
- 超时未配置，弱网下请求永远 pending
**风险等级**：P1
**整改方向**：统一请求封装层错误处理；拦截器转换错误格式；service 层不吞错误；组件层消费 error 状态；配置请求超时
**验收标准**：所有请求有错误处理；fetch 封装对非 2xx 抛错；组件层消费错误状态；超时有配置

### 指标 1.2：错误用户可见提示

**指标名称**：错误用户可见提示
**检查目标**：确认每一个被捕获的错误都有对用户可见的提示，且提示内容可理解、不暴露技术细节
**为什么需要检查**：错误被捕获但只 console.log 是最常见的"假错误处理"，用户依然不知道发生了什么。直接展示错误堆栈或错误码则会让非技术用户困惑。无提示的错误会让用户重复操作，加重服务端负担
**检查范围**：所有 catch 块、所有错误处理分支、所有错误提示组件（Message/Notification/Toast）
**检查方法**：
1. 搜索所有 `catch` 块，检查内部是否有用户可见的提示
2. 搜索 `console.log`、`console.error` 在 catch 块中的使用，标记"只 console 不提示"的情况
3. 检查错误提示内容是否为用户可理解的自然语言（而非 `error.stack`、`error.code`、`Request failed with status 500`）
4. 检查提示组件是否正确触发（Message.error / ElMessage.error / notification.error）
5. 检查不同错误类型是否有差异化提示（网络错误 vs 权限错误 vs 业务错误）
6. 检查错误提示是否会重复弹出（同一错误触发多次提示）
**需要查看**：catch 块实现、错误提示组件调用、错误信息转换逻辑
**正常标准**：
- 所有 catch 块有用户可见提示（除被上层统一处理的）
- 提示内容为自然语言（如"加载失败，请稍后重试"）
- 不展示 error.stack、error.code、技术错误信息
- 不同错误类型有差异化提示
- 错误提示不会重复弹出
- 网络错误提示"网络异常"，权限错误提示"无权限访问"
**异常情况**：
- catch 块只有 console.log，无用户提示
- 直接展示 `error.message` 或 `error.stack` 给用户
- 所有错误都提示"出错了"，无法区分错误类型
- 同一错误触发多次提示刷屏
- 错误提示用 alert() 阻塞页面
- 权限错误提示"服务器错误"误导用户
**风险等级**：P1
**整改方向**：catch 块加用户提示；提示内容自然语言化；错误分类差异化提示；防止重复弹出
**验收标准**：所有 catch 有用户提示；提示内容可理解；不暴露技术细节；无重复刷屏

### 指标 1.3：空数据兜底 UI（错误可见性视角）

**指标名称**：空数据兜底 UI（错误可见性视角）
**检查目标**：确认数据为空（空数组、空对象、null、undefined）时，UI 有明确的空状态展示，而非空白或报错
**为什么需要检查**：空数据是正常业务场景（如新用户无记录、筛选无结果），但未做兜底会导致页面空白、组件报错（访问 null 字段）、用户以为出 bug。空状态 UI 还能引导用户下一步操作（如"暂无数据，点击创建"）
**检查范围**：所有列表渲染、所有详情页、所有图表渲染、所有数据消费组件
**检查方法**：
1. 列出所有渲染列表的组件，检查 `v-if="list.length"` 或类似的空判断
2. 检查列表空时是否有空状态组件（Empty/Placeholder）
3. 检查详情页在数据为 null 时是否有兜底（而非访问 null.field 报错）
4. 检查图表组件在数据为空时是否有占位（而非渲染空白 canvas）
5. 检查空状态 UI 是否有引导操作（如"去创建""刷新"按钮）
6. 检查空状态 UI 的样式是否美观（而非一行"无数据"文字）
**需要查看**：组件模板、空状态组件、数据消费逻辑
**正常标准**：
- 所有列表有空状态展示
- 空状态有图标、文案、引导操作
- 详情页 null 数据有兜底
- 图表空数据有占位
- 空状态样式统一（项目内有 Empty 组件复用）
- 空状态文案符合业务场景（如"暂无站点数据"而非"无数据"）
**异常情况**：
- 列表为空时页面完全空白
- 列表为空时显示 `undefined` 或 `null` 字样
- 详情页访问 null 字段导致白屏
- 图表空数据渲染空白 canvas
- 空状态只有"无数据"三个字，无图标无引导
- 各处空状态 UI 风格不一致
**风险等级**：P1
**整改方向**：统一 Empty 组件；所有列表加空判断；详情页 null 兜底；图表空数据占位
**验收标准**：所有数据消费点有空状态 UI；空状态有引导；样式统一

### 指标 1.4：loading/error/empty三态覆盖

**指标名称**：loading/error/empty 三态覆盖
**检查目标**：确认每一个数据消费组件都覆盖了 loading（加载中）、error（加载失败）、empty（无数据）、success（有数据）四种状态，且状态切换正确
**为什么需要检查**：三态覆盖是数据驱动 UI 的基本要求。缺失任一状态都会导致用户体验断裂：无 loading 用户以为没点中、无 error 用户以为在加载、无 empty 用户以为出 bug。状态切换错误会导致"loading 永远不结束""error 后仍显示旧数据"等问题
**检查范围**：所有发起请求的组件、所有数据展示组件
**检查方法**：
1. 对每个数据消费组件，列出其可能的状态：loading、error、empty、success
2. 检查模板中是否对每种状态都有对应渲染分支
3. 检查状态切换逻辑：请求开始→loading、请求成功且有数据→success、请求成功但空→empty、请求失败→error
4. 检查重新请求时状态是否正确重置（从 error/empty 回到 loading）
5. 检查 loading 状态是否有视觉反馈（骨架屏/loading 图标）
6. 检查 error 状态是否有重试按钮
**需要查看**：组件模板、组件状态变量、请求调用逻辑
**正常标准**：
- 每个数据组件覆盖 loading/error/empty/success 四态
- 状态切换逻辑正确
- 重新请求时状态重置
- loading 有视觉反馈（骨架屏或 loading 图标）
- error 有重试按钮
- empty 有引导操作
**异常情况**：
- 只有 success 状态，其他三态缺失
- loading 永远不结束（请求完成未置 false）
- error 后仍显示旧数据（未清空）
- 重新请求时未重置 error/empty 状态
- loading 状态无视觉反馈（页面看似卡住）
- error 状态无重试按钮，用户无法恢复
**风险等级**：P1
**整改方向**：补全四态渲染；修正状态切换；加 loading 视觉反馈；error 加重试
**验收标准**：所有数据组件四态覆盖；状态切换正确；loading 有反馈；error 有重试

### 指标 1.5：全局错误边界（ErrorBoundary）

**指标名称**：全局错误边界（ErrorBoundary）
**检查目标**：确认项目配置了全局错误边界，能在组件渲染抛出异常时兜底，避免整个应用白屏
**为什么需要检查**：Vue/React 组件渲染时抛出未捕获异常会导致整个应用白屏，用户只能刷新页面。错误边界能捕获渲染异常，展示降级 UI，让用户继续使用其他功能。无错误边界的项目一次小 bug 就会让整页崩溃
**检查范围**：应用根组件、路由出口、关键页面组件
**检查方法**：
1. 检查 Vue 项目的 `app.config.errorHandler` 是否配置
2. 检查 React项目是否有 ErrorBoundary 组件包裹根组件
3. 检查 Vue 3 的 `onErrorCaptured` 是否在关键组件中使用
4. 检查路由出口是否有错误边界包裹
5. 检查错误边界的降级 UI 是否友好（而非"出错了"三个字）
6. 检查错误边界是否上报错误到日志系统
7. 检查错误边界是否能恢复（如提供"刷新"按钮）
**需要查看**：main.ts/main.js、app.config 配置、ErrorBoundary 组件、路由配置
**正常标准**：
- 配置了全局 errorHandler 或 ErrorBoundary
- 关键路由有错误边界包裹
- 降级 UI 友好（有图标、文案、刷新按钮）
- 错误上报到日志系统
- 错误边界可恢复（用户能点击刷新）
- 局部错误不影响全局（如某图表崩溃不影响整页）
**异常情况**：
- 无任何全局错误处理
- errorHandler 只 console.log 无降级 UI
- 降级 UI 只有"出错了"无刷新按钮
- 错误未上报到日志系统
- 局部组件崩溃导致整页白屏
- 路由切换后错误状态未清除
**风险等级**：P1
**整改方向**：配置全局 errorHandler；关键路由加 ErrorBoundary；降级 UI 友好；错误上报
**验收标准**：有全局错误边界；局部崩溃不白屏；降级 UI 有刷新；错误已上报

### 指标 1.6：未捕获Promise rejection处理

**指标名称**：未捕获 Promise rejection 处理
**检查目标**：确认项目对未捕获的 Promise rejection 有全局兜底处理，避免浮动 Promise 失败时无人感知
**为什么需要检查**：未 catch 的 Promise 失败会触发 unhandledrejection 事件，在浏览器控制台报警告，但用户无感知。这类错误最隐蔽，开发者不查控制台根本不知道。浮动 Promise（未 await 的 async 调用）是主要来源
**检查范围**：所有 Promise 链、所有 async 函数调用、window 的 unhandledrejection 事件监听
**检查方法**：
1. 搜索 `window.addEventListener('unhandledrejection', ...)` 检查是否有全局监听
2. 搜索所有 async 函数调用，检查是否被 await 或 .catch
3. 搜索"浮动 Promise"模式：`someAsyncFunc()` 未 await 也未 .catch
4. 检查 Vue 的 `app.config.errorHandler` 是否覆盖 Promise rejection
5. 检查全局监听是否上报错误到日志系统
6. 检查是否有 `process.on('unhandledRejection')` （Node.js 后端）
**需要查看**：main.ts、async 函数调用、全局事件监听、Node.js 入口文件
**正常标准**：
- 配置了 window 的 unhandledrejection 全局监听
- 全局监听上报错误到日志系统
- 无浮动 Promise（所有 async 调用被 await 或 .catch）
- Vue errorHandler 覆盖 Promise rejection
- Node.js 后端配置了 process.on('unhandledRejection')
- 开发环境下 unhandledrejection 有明显告警
**异常情况**：
- 无 unhandledrejection 全局监听
- 存在浮动 Promise（`doSomething()` 未 await 未 catch）
- 全局监听只 console.log 不上报
- Promise 链中某一段无 catch
- async 函数中 await 无 try/catch 且外层无 catch
- Node.js 后端无 unhandledRejection 处理
**风险等级**：P1
**整改方向**：配置全局 unhandledrejection 监听；上报到日志系统；消除浮动 Promise；async 加 try/catch
**验收标准**：有全局监听；无浮动 Promise；错误已上报

### 指标 1.7：错误日志上报

**指标名称**：错误日志上报
**检查目标**：确认项目配置了错误日志上报机制，能将前端错误上报到服务端日志系统，便于线上问题排查
**为什么需要检查**：线上错误用户不会主动反馈，若无上报机制，开发者根本不知道线上出了什么错。错误日志是线上问题排查的唯一线索来源。无上报的项目等于"上线即失明"
**检查范围**：错误上报 SDK（Sentry/Bugsnag/自研）、errorHandler、unhandledrejection 监听、resource 错误监听
**检查方法**：
1. 检查 package.json 是否引入错误上报 SDK（Sentry/Bugsnag/前端监控）
2. 检查 main.ts 是否初始化上报 SDK
3. 检查 errorHandler 是否调用了上报 SDK
4. 检查 unhandledrejection 监听是否调用了上报 SDK
5. 检查是否监听了 `window.addEventListener('error', ...)` 捕获资源加载错误
6. 检查上报是否携带用户信息（user id）、版本号（release）、环境标识
7. 检查上报是否做了采样（避免高并发下淹没日志系统）
8. 检查上报本身失败是否有兜底（不能因上报失败导致主流程崩溃）
**需要查看**：package.json、main.ts、上报 SDK 配置、errorHandler 实现
**正常标准**：
- 引入并初始化了错误上报 SDK
- errorHandler 调用上报 SDK
- unhandledrejection 调用上报 SDK
- 监听 window error 捕获资源错误
- 上报携带 user id、release、环境标识
- 上报有采样策略
- 上报失败不影响主流程
- 开发环境不上报（或上报到测试项目）
**异常情况**：
- 无任何错误上报 SDK
- 有 SDK 但未在 errorHandler 中调用
- 上报不携带版本号，无法定位是哪个版本出错
- 上报不区分环境，开发错误淹没线上日志
- 上报失败导致主流程崩溃
- 未监听资源加载错误（图片/css/js 加载失败）
- 上报无采样，高并发下淹没日志系统
**风险等级**：P1
**整改方向**：引入上报 SDK；errorHandler/unhandledrejection 调用 SDK；携带版本与环境；加采样；上报失败兜底
**验收标准**：有上报 SDK；错误已上报；携带版本环境；有采样；上报失败不影响主流程

### 指标 1.8：错误反馈通道唯一性（全局反馈层收编与内联禁令）

**指标名称**：错误反馈通道唯一性
**检查目标**：确认用户可见的错误/提示一律经全局反馈层（GCSModal/GCSToast 单例）呈现，组件内不内联渲染错误文本，不引入 Element Plus 反馈组件或原生 alert/confirm
**为什么需要检查**：错误提示散落在组件内部（内联 error 文本/自研弹窗）会挤占组件布局、样式随组件漂移、暗色主题失守；通道不唯一时「哪里弹什么」不可预测，同一错误还可能双通道重复提示
**检查范围**：全部 .vue 组件模板、shared 反馈层（gcsFeedback / errorHandler）、原生 API 使用
**检查方法**：
1. grep 组件模板中的内联错误节点（`error-text` 类 class、`v-if="xxxError"` 类渲染），核对是否为全局反馈层迁移残留
2. grep `alert(` / `window.confirm(` / `prompt(`，应零命中
3. grep `ElMessageBox` / `ElMessage`，应零命中（反馈统一 GCS 化）
4. 检查新增反馈是否走 gcsFeedback 的 `showToast` / `showModal` 或 errorHandler 的 `showError` / `showWarning`
5. 例外核对：弹窗组件内部的行内校验错误（表单场景贴字段展示）允许，但须注明属于弹窗自身 UI 而非全局提示
**需要查看**：shared/utils/gcsFeedback.ts、shared/utils/errorHandler.ts、全部组件模板
**正常标准**：
- 错误/成功/警告提示全部经 GCS 反馈层（toast 自动消失，modal 需用户确认）
- 组件模板无内联错误文本节点（弹窗内部贴字段校验除外）
- 无原生 alert/confirm/prompt、无 Element Plus 反馈组件
**异常情况**：
- 组件模板内出现 `{{ xxxError }}` 类内联错误渲染
- 引入 ElMessage/ElMessageBox 或原生弹窗
- 同一错误既内联又 toast（双通道重复提示）
**风险等级**：P2
**整改方向**：内联节点迁全局 toast/modal；删除重复通道；例外场景注释说明
**验收标准**：三类违禁模式 grep 零命中；全部反馈经 gcsFeedback 单例

### 指标 1.9：错误文案成因区分（不笼统化）

**指标名称**：错误文案成因区分
**检查目标**：确认用户可见错误文案按真实成因区分（网络不可达 / 服务器错误 / 业务失败 / 未登录各说各话），不存在「万物皆请先登录」式笼统兜底
**为什么需要检查**：笼统文案掩盖真实故障——后端宕机提示「请先登录」会把用户引向错误的自救动作（反复登录），也掩盖真正的服务器故障；文案是排查的第一现场
**检查范围**：shared/utils/errorHandler.ts（错误码→文案映射层）、useApiRequest（错误码抛出点与 HTTP 语义归口）、各业务 catch 的兜底文案、认证恢复逻辑
**检查方法**：
1. 检查是否存在集中的错误码→用户文案映射层，业务方不各自手写笼统 fallback
2. 核对语义分组：NETWORK_ERROR/TIMEOUT/网关 5xx →「服务器无响应」类；500 带可读中文 → 透传（描述具体情况）；UNAUTHORIZED → 透传后端归一文案（防枚举，不区分账号不存在/密码错误）；其余 → 调用方 fallback
3. 检查登录引导（login modal / 跳转登录）是否仅在真实 401 认证失效路径触发，网络错误不得触发
4. 检查认证恢复逻辑：后端不可达不得误判为「未登录」（保留临时态或明确降级），Cookie 失效才清态
5. 检查技术细节边界：错误码/堆栈/原始串只进日志不上屏；上屏文案经无害化（防技术串/HTML 外泄）
**需要查看**：shared/utils/errorHandler.ts（describeError/showError）、shared/composables/useApiRequest.ts（错误码抛出点）、shared/composables/useAuth.ts（restoreAuth）
**正常标准**：
- 存在集中式错误码→文案映射层；后端不可达/超时/网关 5xx 统一「服务器无响应」语义
- 后端可读中文错误透传，技术串/HTML 经无害化回退
- 网络失败不触发登录引导；401 才清登录态/触发引导
- 错误码与原始错误进日志（DEV 全量/生产采样），不上用户屏
**异常情况**：
- 网络错误/后端宕机被提示为「请先登录」类登录话术
- 所有错误共用一个笼统 fallback，服务器错误与网络不可达不可区分
- 错误码/堆栈直接上屏
- 认证校验失败与网络失败共用同一清态分支
**风险等级**：P1
**整改方向**：建立集中映射层；按码分组语义；认证与网络分支分离；原始错误进日志
**验收标准**：映射层存在且覆盖全部错误码；四类成因（无响应/服务器错误/业务失败/未登录）文案可区分；日志含错误码

## 第二部分：安全审查

> 目标：识别项目的安全风险，回答"这个项目上线后会不会被攻击、会不会泄露敏感信息"
> 安全是上线阻断项，本部分任何 P0 问题都必须修复后才能上线

### 指标 2.1：认证Token存储位置

**指标名称**：认证 Token 存储位置（localStorage vs httpOnly cookie）
**检查目标**：确认认证 Token（JWT/session token）存储在安全位置，不易被 XSS 攻击窃取
**为什么需要检查**：Token 存 localStorage 会被任何 JS 代码访问，一旦发生 XSS 攻击，攻击者能直接偷走 Token 冒充用户。httpOnly cookie 则无法被 JS 读取，是更安全的存储方式。Token 存储位置是认证安全的基础
**检查范围**：登录逻辑、Token 存储代码、请求拦截器（Token 注入）、登出逻辑
**检查方法**：
1. 搜索 `localStorage.setItem`、`sessionStorage.setItem`、`document.cookie` 查看 Token 存储位置
2. 检查登录成功后 Token 是存 localStorage 还是 httpOnly cookie（后端 set-cookie）
3. 检查请求拦截器如何注入 Token（从 localStorage 读 还是浏览器自动带 cookie）
4. 检查是否配置了 CSRF 防护（如果用 cookie 必须配 CSRF）
5. 检查 Token 是否有过期机制
6. 检查登出时是否清除 Token
7. 检查 Token 是否被持久化到 localStorage 导致关闭浏览器后仍有效
**需要查看**：登录代码、存储工具类、请求拦截器、后端 set-cookie 配置、登出代码
**正常标准**：
- Token 存 httpOnly cookie（后端 set-cookie，前端不接触 Token 值）
- 或 Token 存内存（刷新页面重新登录），仅 refresh token 存 httpOnly cookie
- 配置了 CSRF 防护（用 cookie 时）
- Token 有过期时间
- 登出时清除 Token
- 不在 localStorage 存敏感 Token
**异常情况**：
- JWT 存 localStorage，任何 XSS 都能偷走
- Token 存 sessionStorage 但无 CSRF 防护
- Token 无过期时间，永久有效
- 登出时未清除 Token
- Refresh token 存 localStorage
- Token 被写到全局变量或 window 对象
**风险等级**：P0
**整改方向**：改用 httpOnly cookie 存储；或前后端配合改用 refresh token 模式；配 CSRF 防护；加过期机制
**验收标准**：Token 不在 localStorage；用 httpOnly cookie 或内存存储；有 CSRF 防护；有过期机制

### 指标 2.2：接口权限校验中间件

**指标名称**：接口权限校验中间件
**检查目标**：确认后端每个接口都有权限校验中间件，不存在"前端隐藏按钮就以为安全"的情况
**为什么需要检查**：前端隐藏按钮只是 UI 层面的控制，攻击者能直接调用接口绕过。权限校验必须在后端中间件层做，且每个接口都要做。无后端校验的接口等于公开接口
**检查范围**：后端所有路由定义、所有中间件、所有控制器
**检查方法**：
1. 列出后端所有路由定义
2. 检查每个路由是否挂载了认证中间件（如 authMiddleware）
3. 检查是否有"白名单"接口绕过认证（如 /public、/login）
4. 检查白名单是否合理（不应包含业务接口）
5. 检查权限校验是否区分角色（admin/user/visitor）
6. 检查是否有资源级权限（如用户只能删自己的数据，不能删别人的）
7. 检查是否有"前端控制后端不校验"的接口（如前端隐藏删除按钮，但后端删除接口无校验）
**需要查看**：后端路由配置、中间件实现、控制器、白名单配置
**正常标准**：
- 每个业务接口都挂载认证中间件
- 白名单只含登录、注册、健康检查等公开接口
- 权限校验区分角色
- 资源级权限校验（用户只能操作自己的资源）
- 前端隐藏的功能后端也校验
- 中间件无法被绕过（如不能通过 URL 参数跳过）
**异常情况**：
- 业务接口未挂载认证中间件
- 白名单包含业务接口（如 /api/users 在白名单）
- 只有认证无权限校验（任何登录用户都能操作任何数据）
- 前端隐藏删除按钮，后端删除接口无校验
- 中间件可通过特殊参数绕过
- 资源级权限缺失（用户能删别人的数据）
**风险等级**：P0
**整改方向**：所有业务接口挂载认证中间件；清理白名单；加资源级权限校验；前后端权限对齐
**验收标准**：所有业务接口有认证；白名单合理；有资源级权限；无绕过路径

### 指标 2.3：硬编码密钥/密码/Token搜索

**指标名称**：硬编码密钥/密码/Token 搜索
**检查目标**：确认源码中不存在硬编码的密钥、密码、Token、API Key 等敏感凭证
**为什么需要检查**：硬编码密钥一旦提交到 git 仓库就永久泄露，即使后续删除也会留在 git 历史中。攻击者扫描 github 能轻松发现这些凭证。密钥泄露会导致数据库被入侵、第三方服务被盗用、生产环境被控制
**检查范围**：所有源码文件、所有配置文件、.env 文件、构建配置
**检查方法**：
1. 全局搜索 `password`、`secret`、`apiKey`、`api_key`、`token`、`accessKey`、`secretKey` 等关键字
2. 检查搜索结果是否有真实凭证（而非变量名、配置项名）
3. 检查是否有形如 `password = 'xxx'`、`apiKey: 'sk-xxx'` 的硬编码
4. 检查 .env 文件是否被提交到 git（.gitignore 是否包含 .env）
5. 检查 .env.example 是否含真实密钥（应只有占位符）
6. 检查测试文件中的密钥是否为真实密钥（应为 mock）
7. 检查 git 历史中是否曾提交过密钥（git log -p 搜索）
8. 检查构建产物中是否包含密钥（dist 目录搜索）
**需要查看**：源码全量搜索结果、.env 文件、.gitignore、.env.example、git 历史
**正常标准**：
- 源码中无硬编码密钥
- 所有密钥通过环境变量注入
- .env 在 .gitignore 中
- .env.example 只有占位符（如 `VITE_API_KEY=`）
- 测试文件用 mock 密钥
- git 历史中无密钥泄露
- 构建产物中无密钥
**异常情况**：
- 源码中找到真实密钥（数据库密码、API Key、JWT secret）
- .env 被提交到 git
- .env.example 含真实密钥值
- 测试文件用生产密钥
- git 历史中有密钥提交记录
- 构建产物中能搜到密钥
- 密钥写在注释里（如 `// 测试用密码 123456`）
**风险等级**：P0
**整改方向**：立即移除硬编码密钥；改用环境变量；轮换已泄露的密钥；清理 git 历史；.env 加入 .gitignore
**验收标准**：源码无硬编码密钥；密钥通过环境变量注入；.env 不入库；已泄露密钥已轮换

### 指标 2.4：日志敏感信息输出

**指标名称**：日志敏感信息输出
**检查目标**：确认日志输出不包含敏感信息（密码、Token、身份证号、手机号等）
**为什么需要检查**：日志文件通常权限较低、留存时间长、可能被运维、第三方日志服务查看。敏感信息进日志等于变相泄露。日志泄露难以发现，但一旦发生后果严重
**检查范围**：所有 console.log、所有日志库调用（winston/log4j/pino）、所有错误上报、所有请求日志
**检查方法**：
1. 搜索 `console.log`、`logger.info`、`logger.error` 等日志输出
2. 检查日志参数是否包含 password、token、secret、idCard、phone 等字段
3. 检查请求日志是否记录了完整请求体（可能含密码）
4. 检查错误日志是否记录了完整 error 对象（可能含敏感堆栈）
5. 检查响应日志是否记录了完整响应体（可能含用户信息）
6. 检查是否有日志脱敏中间件（自动脱敏敏感字段）
7. 检查前端上报是否携带完整请求/响应（可能含敏感信息）
**需要查看**：日志输出代码、日志配置、请求/响应日志中间件、前端上报配置
**正常标准**：
- 日志不输出 password、token、secret 等敏感字段
- 请求日志不记录完整请求体（或脱敏后记录）
- 响应日志不记录完整响应体
- 有日志脱敏中间件
- 错误日志记录 error.message 而非完整 error
- 前端上报不携带完整请求/响应
- 用户信息（手机号、身份证）脱敏后记录（如 138****1234）
**异常情况**：
- 日志直接输出 password 字段
- 请求日志记录完整请求体（含密码明文）
- 错误日志记录完整 error 对象（含敏感堆栈）
- 响应日志记录完整用户信息
- 无日志脱敏机制
- 前端上报携带完整请求体
- 手机号、身份证号未脱敏直接记录
**风险等级**：P0
**整改方向**：移除敏感信息输出；加日志脱敏中间件；请求/响应日志脱敏；用户信息脱敏
**验收标准**：日志无敏感信息；有脱敏中间件；用户信息脱敏记录

### 指标 2.5：开发后门（绕过认证接口）

**指标名称**：开发后门（绕过认证接口）
**检查目标**：确认源码中不存在开发阶段遗留的"后门"——如固定密码、万能 Token、跳过认证的调试接口、测试账号
**为什么需要检查**：开发时为了方便调试，开发者有时会留"后门"——如 `if (user === 'admin') skipAuth()`、固定测试 Token、`?debug=1` 跳过权限。这些后门一旦带到生产环境，攻击者能直接获取管理员权限，是最高危的安全漏洞
**检查范围**：认证逻辑、权限校验、调试接口、测试账号、环境判断逻辑
**检查方法**：
1. 搜索 `skipAuth`、`bypass`、`debug`、`test`、`admin`、`backdoor` 等关键字
2. 检查认证逻辑中是否有"跳过认证"的分支（如 `if (process.env.NODE_ENV !== 'production') skipAuth()`）
3. 检查是否有固定 Token/密码能绕过认证（如 `if (token === 'test-token')`）
4. 检查是否有 `?debug=1` 之类的查询参数跳过权限
5. 检查是否有硬编码的测试账号（如 `admin/admin123`）
6. 检查环境判断是否被误用（如 `if (dev) return true` 跳过校验）
7. 检查是否有未删除的调试接口（如 `/api/debug/xxx`）
8. 检查 git 历史中是否曾有过后门代码
**需要查看**：认证代码、权限校验、环境判断、路由配置、git 历史
**正常标准**：
- 无任何跳过认证的逻辑
- 无固定 Token/密码后门
- 无 debug 参数跳过权限
- 无硬编码测试账号
- 环境判断只用于配置，不用于跳过安全
- 无调试接口残留
- 开发环境的便利功能通过独立工具而非生产代码实现
**异常情况**：
- `if (NODE_ENV !== 'production') skipAuth()`
- 固定 Token `if (token === 'master-token')` 绕过认证
- `?debug=1` 跳过权限校验
- 硬编码 `admin/admin123` 测试账号
- 调试接口 `/api/debug/users` 未删除
- 环境判断被用于跳过安全检查
- 生产代码中留有 `// TODO: 上线前删除` 的后门
**风险等级**：P0
**整改方向**：立即移除所有后门；测试账号通过数据库而非代码；调试接口删除或加权限；环境判断只用于配置
**验收标准**：无后门代码；无固定 Token；无 debug 跳过；无硬编码测试账号

### 指标 2.6：CORS配置

**指标名称**：CORS 配置
**检查目标**：确认后端 CORS 配置收敛，不存在 `Access-Control-Allow-Origin: *` 配合凭证的危险组合
**为什么需要检查**：CORS 配置为 `*` 且允许凭证（credentials）时，任何网站都能携带用户凭证调用接口，等于完全放开认证。即使 CORS 只配 `*` 不允许凭证，也存在信息泄露风险。CORS 是浏览器同源策略的最后一道防线
**检查范围**：后端 CORS 中间件配置、nginx 配置、响应头设置
**检查方法**：
1. 搜索后端 CORS 配置（如 `cors()`、`Access-Control-Allow-Origin`）
2. 检查 `Access-Control-Allow-Origin` 是否为 `*`
3. 检查 `Access-Control-Allow-Credentials` 是否为 `true`
4. 检查 `*` 与 `credentials: true` 是否同时出现（危险组合）
5. 检查允许的方法是否收敛（不应包含 DELETE/PUT 等危险方法如果不需要）
6. 检查允许的来源是否为白名单（而非 `*`）
7. 检查 nginx 配置中的 add_header Access-Control-Allow-Origin
**需要查看**：CORS 中间件、nginx 配置、响应头、后端配置
**正常标准**：
- Allow-Origin 为白名单（如 `https://example.com`）
- 或动态读取请求 Origin 并校验白名单后返回
- Allow-Credentials 与 Allow-Origin 不冲突
- 允许的方法收敛（只用 GET/POST 等需要的）
- 允许的头部收敛
- 预检请求（OPTIONS）正确响应
**异常情况**：
- Allow-Origin: * 且 Allow-Credentials: true（危险组合）
- Allow-Origin: * 且接口需要凭证
- 允许所有方法（含 DELETE/PUT）
- 允许所有头部
- 动态回显 Origin 不做白名单校验
- nginx 与后端都配 CORS 导致重复
**风险等级**：P0（* + credentials 危险组合）/ P1（其他）
**整改方向**：改用白名单；移除危险组合；收敛方法与头部；统一一处配置 CORS
**验收标准**：CORS 白名单收敛；无危险组合；方法头部收敛

### 指标 2.7：SQL注入/XSS风险

**指标名称**：SQL 注入/XSS 风险
**检查目标**：确认后端无 SQL 注入风险，前端无 XSS 风险
**为什么需要检查**：SQL 注入能让攻击者直接操作数据库，XSS 能让攻击者在用户浏览器执行任意代码。两者都是 OWASP Top 10 的高危漏洞，一旦被利用后果极其严重
**检查范围**：后端所有数据库查询、后端 ORM 使用、前端所有 v-html、前端所有 innerHTML、用户输入处理
**检查方法**：
1. 搜索后端 SQL 拼接（如 `SELECT * FROM ${table}`、字符串拼接 SQL）
2. 检查 ORM 是否使用了原始查询（raw query）拼接用户输入
3. 检查参数化查询是否正确使用
4. 搜索前端 `v-html`、`innerHTML`、`dangerouslySetInnerHTML` 使用
5. 检查 v-html 的内容是否来自用户输入
6. 检查 URL 参数是否被直接渲染到页面
7. 检查后端是否对用户输入做了校验和转义
8. 检查是否有 CSP（Content-Security-Policy）配置
**需要查看**：后端数据库查询代码、ORM 使用、前端模板、用户输入处理
**正常标准**：
- 所有 SQL 使用参数化查询或 ORM 方法
- 无字符串拼接 SQL
- 前端无 v-html 渲染用户输入
- 用户输入有校验和转义
- 配置了 CSP 头
- 富文本输入用白名单过滤（如 DOMPurify）
**异常情况**：
- SQL 拼接用户输入 `WHERE id = ${req.query.id}`
- ORM raw query 拼接用户输入
- 前端 v-html 渲染用户输入
- innerHTML 设置用户输入
- URL 参数直接渲染到页面
- 无输入校验和转义
- 无 CSP 配置
**风险等级**：P0
**整改方向**：改用参数化查询；移除 v-html 或用 DOMPurify；加输入校验；配置 CSP
**验收标准**：无 SQL 注入；无 XSS；有输入校验；有 CSP

### 指标 2.8：依赖漏洞（npm audit）

**指标名称**：依赖漏洞（npm audit）
**检查目标**：确认项目依赖无已知高危漏洞，依赖版本保持更新
**为什么需要检查**：第三方依赖是现代项目的主要攻击面，npm 生态频繁爆出漏洞（如 lodash 原型污染、event-stream 后门）。不扫描依赖漏洞等于"自己写的代码再安全，依赖一塌糊涂"
**检查范围**：package.json、package-lock.json、npm audit 报告、后端 requirements.txt/pom.xml 等
**检查方法**：
1. 运行 `npm audit`（或 `yarn audit`、`pnpm audit`）扫描前端依赖
2. 检查报告中 high/critical 级别漏洞数量
3. 检查是否有漏洞修复版本可用
4. 检查 package-lock.json 是否锁版本（避免安装时被注入恶意版本）
5. 运行后端依赖扫描（`pip-audit`、`mvn dependency-check`、`snyk`）
6. 检查是否有依赖长期未更新（超过 1 年）
7. 检查 CI 是否集成了依赖扫描步骤
**需要查看**：npm audit 报告、package-lock.json、后端依赖清单、CI 配置
**正常标准**：
- npm audit 无 critical/high 漏洞
- package-lock.json 锁版本
- 依赖定期更新
- CI 集成依赖扫描
- 漏洞有修复计划或可接受的说明
- 无长期未更新的核心依赖
**异常情况**：
- npm audit 报告多个 critical/high 漏洞
- 无 package-lock.json（版本不锁）
- 依赖长期未更新
- CI 未集成依赖扫描
- 漏洞依赖无法升级（被其他依赖间接锁定）
- 使用了已废弃或有后门传闻的包
**风险等级**：P0（critical 漏洞）/ P1（high 漏洞）
**整改方向**：升级漏洞依赖；锁版本；CI 集成扫描；定期更新依赖
**验收标准**：npm audit 无 critical/high；锁版本；CI 集成扫描

## 第三部分：性能审查

> 目标：识别性能瓶颈，回答"项目在大数据量、弱网、长运行下会不会卡"
> 性能问题影响用户体验，GIS 项目尤甚

### 指标 3.1：首屏懒加载（路由+组件）

**指标名称**：首屏懒加载（路由+组件）
**检查目标**：确认首屏只加载必要资源，非首屏路由和重组件都做了懒加载
**为什么需要检查**：首屏加载速度直接影响用户留存，统计显示首屏超过 3 秒用户流失率显著上升。不懒加载会让首屏加载所有路由代码、所有重组件，首屏体积膨胀，弱网下尤其严重
**检查范围**：路由配置、组件 import、动态 import 使用、构建产物 chunk 划分
**检查方法**：
1. 检查路由配置是否使用动态 import（如 `() => import('./views/Home.vue')`）
2. 检查是否有静态 import 的非首屏路由组件
3. 检查重组件（如图表、地图、富文本编辑器）是否懒加载
4. 检查构建产物的 chunk 划分（vite/webpack 的 manualChunks 配置）
5. 检查首屏 chunk 体积（应 < 200KB gzip）
6. 检查是否有 preload/prefetch 优化首屏
7. 检查第三方库是否按需引入（如 lodash 按需 import 而非全量）
**需要查看**：路由配置、组件 import、构建配置、构建产物分析报告
**正常标准**：
- 所有路由懒加载（动态 import）
- 重组件懒加载
- 首屏 chunk < 200KB gzip
- 第三方库按需引入
- 有 chunk 分割策略
- 有 preload 优化关键资源
- 构建产物有分析报告
**异常情况**：
- 路由全部静态 import
- 首屏加载所有路由代码
- 重组件（地图/编辑器）在首屏加载
- 首屏 chunk > 500KB
- 第三方库全量引入（如 `import _ from 'lodash'`）
- 无 chunk 分割，所有代码打成一个 bundle
- 无 preload/prefetch 优化
**风险等级**：P1
**整改方向**：路由改动态 import；重组件懒加载；按需引入第三方库；配置 chunk 分割
**验收标准**：路由懒加载；首屏 chunk < 200KB；第三方库按需引入

### 指标 3.2：大数据列表虚拟化

**指标名称**：大数据列表虚拟化
**检查目标**：确认渲染大数据列表时使用了虚拟滚动，而非一次性渲染全部
**为什么需要检查**：DOM 节点数是前端性能的关键因素，超过 1000 个 DOM 节点会显著拖慢渲染和交互。万级数据一次性渲染会导致首屏卡死数秒、滚动卡顿、内存暴涨。虚拟滚动只渲染可视区域，能支撑十万级数据流畅滚动
**检查范围**：所有列表渲染、表格渲染、下拉选项渲染
**检查方法**：
1. 搜索 `v-for`、`map(` 列表渲染代码
2. 评估每个列表的潜在数据量（用户数据、日志、配置等）
3. 检查数据量可能超过 100 条的列表是否使用了虚拟滚动
4. 检查表格组件是否支持虚拟滚动（如 el-table-v2、vxe-table）
5. 检查下拉选项超过 100 条时是否用了虚拟化（如 el-select-v2）
6. 检查虚拟滚动实现是否正确（如固定行高、动态行高处理）
**需要查看**：列表渲染代码、表格组件、下拉组件、数据量评估
**正常标准**：
- 数据量可能超 100 条的列表用虚拟滚动
- 表格用支持虚拟滚动的组件
- 下拉选项超 100 条用虚拟化
- 虚拟滚动实现正确（行高处理、滚动同步）
- 大数据量有分页或懒加载
- 无一次性渲染万级数据的情况
**异常情况**：
- 万级数据一次性 v-for 渲染
- 表格不支持虚拟滚动但渲染千级数据
- 下拉选项 1000+ 条无虚拟化
- 虚拟滚动行高计算错误导致跳动
- 无分页直接渲染全部数据
- 列表渲染导致 DOM 节点超过 5000
**风险等级**：P1
**整改方向**：大数据列表改虚拟滚动；表格换支持虚拟滚动的组件；加 分页
**验收标准**：大数据列表虚拟化；无一次性渲染千级数据；DOM 节点可控

### 指标 3.3：图层按需加载（引用WebGIS专项）

**指标名称**：图层按需加载（引用 WebGIS 专项）
**检查目标**：确认地图图层按需加载、视口裁剪，而非一次性加载全部图层和全部要素
**为什么需要检查**：GIS 项目图层是性能大头，一次性加载所有图层和所有要素会导致地图卡死、内存暴涨。图层按需加载、视口裁剪是 GIS 性能的基本要求。具体实现细节由 WebGIS 专项审查，本指标只判断"是否按需"
**检查范围**：地图图层加载逻辑、图层显隐控制、要素加载策略
**检查方法**：
1. 检查地图初始化时是否一次性加载所有图层
2. 检查图层是否有按需加载机制（如用户切换显隐时才加载）
3. 检查要素是否按视口范围加载（bbox 过滤）
4. 检查大数据量图层是否用了矢量瓦片或聚合
5. 检查图层销毁时是否释放资源
6. 引用 WebGIS 专项结论判断按需加载的具体实现是否正确
**需要查看**：地图配置、图层加载代码、图层管理器、WebGIS 专项审查结论
**正常标准**：
- 图层按需加载（用户切换时才加载）
- 要素按视口范围加载
- 大数据量用矢量瓦片或聚合
- 图层销毁时释放资源
- 非首屏图层不立即加载
- 引用 WebGIS 专项结论确认实现正确
**异常情况**：
- 地图初始化加载所有图层
- 一次性加载全部要素无 bbox 过滤
- 大数据量图层无聚合无瓦片
- 图层只加载不释放
- 非首屏图层在首屏加载
- WebGIS 专项指出按需加载实现有缺陷
**风险等级**：P1
**整改方向**：图层按需加载；要素视口裁剪；大数据用瓦片或聚合；引用 WebGIS 专项修复
**验收标准**：图层按需加载；要素视口裁剪；引用 WebGIS 专项确认

### 指标 3.4：图表实例复用

**指标名称**：图表实例复用
**检查目标**：确认 ECharts/Chart.js 等图表实例被复用，而非每次更新都销毁重建
**为什么需要检查**：图表实例创建（init）开销大，包含 canvas 初始化、主题应用、事件绑定。每次数据更新都 dispose + init 会导致明显卡顿，尤其在频繁更新的场景。正确做法是 init 一次，后续用 setOption 更新
**检查范围**：所有图表组件、所有 ECharts/Chart.js init 调用、所有 setOption 调用
**检查方法**：
1. 搜索 `echarts.init`、`Chart(` 等图表初始化代码
2. 检查 init 是否在合适的生命周期（onMounted）只调用一次
3. 检查数据更新是否用 setOption 而非 dispose + init
4. 检查 dispose 是否在 onUnmounted 调用
5. 检查 resize 是否正确处理（窗口大小变化时 resize 而非重建）
6. 检查多个图表是否复用了相同配置
**需要查看**：图表组件实现、init/dispose/setOption 调用、生命周期钩子
**正常标准**：
- init 在 onMounted 只调用一次
- 数据更新用 setOption
- dispose 在 onUnmounted 调用
- resize 用 chart.resize() 而非重建
- 多图表复用配置
- 无重复 init 逻辑
**异常情况**：
- 每次数据更新都 dispose + init
- init 在 watch 或 computed 中调用
- 无 dispose 导致内存泄漏
- resize 通过重建实例实现
- 多图表重复初始化相同配置
- 切换图表类型时整个实例重建
**风险等级**：P1
**整改方向**：init 一次 + setOption 更新；onUnmounted dispose；resize 而非重建
**验收标准**：图表实例复用；setOption 更新；有 dispose；resize 正确

### 指标 3.5：静态资源压缩与体积

**指标名称**：静态资源压缩与体积
**检查目标**：确认静态资源（图片、字体、JS、CSS）经过压缩，体积合理
**为什么需要检查**：未压缩的大资源会拖慢首屏，尤其弱网环境。一张 5MB 的图片能让首屏多花数秒。静态资源体积是性能最直接的指标
**检查范围**：构建产物 dist 目录、public 目录、图片资源、字体文件
**检查方法**：
1. 检查构建产物 dist 目录的总体积
2. 检查单个 JS/CSS chunk 体积（应 < 500KB）
3. 检查图片资源是否压缩（单图应 < 200KB，除非必要大图）
4. 检查是否使用了 webp/avif 等现代格式
5. 检查字体文件是否只包含用到的字符（subset）
6. 检查是否启用了 gzip/brotli 压缩
7. 检查是否有不必要的资源被打入构建（如测试数据、mock 文件）
8. 检查大资源是否走了 CDN
**需要查看**：dist 目录、构建配置、public 目录、nginx 配置
**正常标准**：
- 构建产物总体积合理
- 单个 chunk < 500KB
- 图片单图 < 200KB
- 使用 webp/avif 现代格式
- 字体 subset
- 启用 gzip/brotli
- 大资源走 CDN
- 无测试数据被打入
**异常情况**：
- 构建产物 > 10MB
- 单个 chunk > 1MB
- 图片单图 > 1MB 未压缩
- 使用 bmp/tiff 等大格式
- 字体未 subset 包含全部字符
- 未启用 gzip/brotli
- 测试数据被打入构建
- 大资源走应用服务器而非 CDN
**风险等级**：P1
**整改方向**：压缩图片；用现代格式；字体 subset；启用 gzip/brotli；大资源走 CDN
**验收标准**：产物体积合理；图片压缩；启用 gzip；大资源走 CDN

### 指标 3.6：重复计算缓存

**指标名称**：重复计算缓存
**检查目标**：确认计算密集型逻辑的结果被缓存，而非每次重新计算
**为什么需要检查**：重复计算在数据量小时不显现，大数据量时会明显卡顿。如每次渲染都重新格式化日期、每次都重新排序大数组、每次都重新计算聚合值。缓存能显著提升性能
**检查范围**：computed 属性、计算函数、循环内计算、渲染相关计算
**检查方法**：
1. 检查 computed 属性是否有不必要的重复计算（依赖未变化却重算）
2. 检查循环内是否有可外提的计算（如 `list.map(i => format(i.date))` 中 format 应外提）
3. 检查大数组排序/过滤是否每次重新计算（应缓存或用 computed）
4. 检查日期格式化、数字格式化等是否重复执行相同输入
5. 检查是否有 memoize 机制（如 lodash.memoize）
6. 检查地图聚合、图表聚合等计算是否缓存
**需要查看**：computed 实现、循环代码、计算函数
**正常标准**：
- computed 依赖正确，无多余重算
- 循环内无可外提计算
- 大数组计算用 computed 缓存
- 重复输入的计算有 memoize
- 聚合计算有缓存
- 无明显重复计算模式
**异常情况**：
- computed 依赖错误导致每次重算
- 循环内重复计算（如 `list.filter().map().sort()` 每次渲染都执行）
- 大数组每次渲染都重新排序
- 相同输入的格式化重复执行
- 无 memoize 机制
- 聚合计算每次重新执行
**风险等级**：P2
**整改方向**：computed 修正依赖；循环计算外提；加 memoize；聚合缓存
**验收标准**：无重复计算；computed 依赖正确；有 memoize

### 指标 3.7：阻塞操作识别

**指标名称**：阻塞操作识别
**检查目标**：确认主线程无长时间阻塞操作，耗时操作已异步化或分块
**为什么需要检查**：浏览器主线程单线程，超过 50ms 的阻塞会让用户感到卡顿，超过 100ms 会让动画掉帧。同步大计算、同步 JSON 解析大文件、同步加密都会阻塞主线程
**检查范围**：所有同步计算密集代码、大文件处理、加密/解密、序列化/反序列化
**检查方法**：
1. 搜索同步的 JSON.parse 大文件、parseInt 大数据
2. 搜索同步加密/解密（如 crypto-js 同步调用）
3. 检查大数组遍历是否同步（超过 100ms 的遍历应分块）
4. 检查是否有 requestIdleCallback/setTimeout 分块处理
5. 检查是否有 Web Worker 处理重计算
6. 检查是否有同步的 DOM 操作（如大量 innerHTML 拼接）
7. 检查 Performance 火焰图中的长任务（> 50ms）
**需要查看**：同步计算代码、大文件处理、加密代码、Performance 分析
**正常标准**：
- 无长时间阻塞主线程的操作
- 大计算用 Web Worker 或分块
- 大文件用流式处理
- 加密用异步或 Web Worker
- 无大量同步 DOM 操作
- Performance 火焰图无长任务
**异常情况**：
- 同步解析 10MB+ JSON 文件
- 同步加密大数据
- 大数组同步遍历超过 100ms
- 无 Web Worker 或分块处理
- 大量同步 innerHTML 拼接
- Performance 火焰图有 > 100ms 长任务
**风险等级**：P1
**整改方向**：大计算用 Web Worker；大文件流式处理；分块处理；异步加密
**验收标准**：无阻塞操作；大计算异步化；无长任务

## 第四部分：测试体系

> 目标：确认项目有测试护城河，回答"改一处代码会不会坏一片"
> 测试是持续维护能力的核心指标

### 指标 4.1：测试文件覆盖率统计

**指标名称**：测试文件覆盖率统计
**检查目标**：确认项目有测试文件，且覆盖率统计可量化
**为什么需要检查**：没有测试文件的项目等于"裸奔"，任何修改都可能引入回归。覆盖率统计能量化测试质量，让测试改进可衡量。无覆盖率统计的项目无法判断测试是否充分
**检查范围**：测试文件目录、测试配置、覆盖率报告、package.json 的 test 脚本
**检查方法**：
1. 检查是否有测试目录（tests/、__tests__/、*.spec.ts、*.test.ts）
2. 统计测试文件数量与源码文件数量比例
3. 检查是否配置了覆盖率工具（jest --coverage、c8、istanbul）
4. 运行覆盖率报告，统计行覆盖率、分支覆盖率、函数覆盖率
5. 检查 package.json 是否有 test 脚本和 coverage 脚本
6. 检查 CI 是否执行覆盖率并设置阈值
7. 评估核心模块覆盖率是否高于非核心模块
**需要查看**：测试目录、测试配置、覆盖率报告、package.json、CI 配置
**正常标准**：
- 有测试目录和测试文件
- 测试文件与源码文件比例合理（> 30%）
- 配置了覆盖率工具
- 行覆盖率 > 60%
- 分支覆盖率 > 50%
- 有 test 和 coverage 脚本
- CI 设置覆盖率阈值
- 核心模块覆盖率 > 80%
**异常情况**：
- 无测试文件
- 测试文件极少（< 5 个）
- 无覆盖率工具配置
- 覆盖率 < 20%
- 无 test 脚本
- CI 不跑覆盖率
- 核心模块无测试
- 测试文件全在临时目录
**风险等级**：P1
**整改方向**：补核心模块测试；配置覆盖率工具；CI 加覆盖率阈值
**验收标准**：有测试文件；配置覆盖率；核心模块覆盖率 > 80%

### 指标 4.2：核心业务逻辑测试覆盖

**指标名称**：核心业务逻辑测试覆盖
**检查目标**：确认核心业务逻辑（数据转换、计算、规则、权限）有测试覆盖，而非只测工具函数
**为什么需要检查**：工具函数测试容易写但价值低，核心业务逻辑测试难写但价值高。测了 formatDate 但没测"洪水预警等级计算"等于本末倒置。核心逻辑无测试，改一处业务规则可能引发线上事故
**检查范围**：业务计算函数、数据转换函数、权限判断函数、核心业务规则
**检查方法**：
1. 列出项目核心业务逻辑清单（如预警计算、站点筛选、数据聚合）
2. 对每个核心逻辑，检查是否有对应测试文件
3. 检查测试是否覆盖正常路径、边界值、异常输入
4. 检查测试是否覆盖业务规则的所有分支
5. 评估核心逻辑覆盖率是否高于工具函数
6. 检查是否有"只测工具函数不测业务逻辑"的情况
**需要查看**：核心业务逻辑代码、测试文件、覆盖率报告（按模块）
**正常标准**：
- 每个核心业务逻辑有对应测试
- 测试覆盖正常路径、边界值、异常输入
- 业务规则所有分支有测试
- 核心逻辑覆盖率 > 80%
- 核心逻辑覆盖率高于工具函数
- 测试用例体现业务场景
**异常情况**：
- 核心业务逻辑无测试
- 只测正常路径不测边界和异常
- 业务规则分支未覆盖
- 只测工具函数（formatDate、debounce）不测业务
- 核心逻辑覆盖率 < 30%
- 测试用例与业务场景脱节
**风险等级**：P1
**整改方向**：补核心业务逻辑测试；覆盖边界和异常；测试体现业务场景
**验收标准**：核心逻辑有测试；覆盖边界异常；覆盖率 > 80%

### 指标 4.3：测试断言质量（不只跑不断言）

**指标名称**：测试断言质量（不只跑不断言）
**检查目标**：确认测试有有效断言，验证了行为正确性，而非"跑过就算通过"
**为什么需要检查**：只调用函数不断言的测试是虚假安全感——代码改坏了测试也"通过"。无断言的测试比没测试更危险，因为它让人误以为有保护。断言质量决定测试的真实价值
**检查范围**：所有测试用例的断言部分
**检查方法**：
1. 检查每个测试用例是否有 expect/assert 语句
2. 检查断言是否验证了关键行为（而非只验证 `expect(true).toBe(true)`）
3. 检查断言数量是否合理（每个测试至少 1 个有效断言）
4. 检查是否有"只验证不抛错就算通过"的测试（try/catch 包裹）
5. 检查断言是否验证了返回值、副作用、状态变化
6. 检查是否有"占位测试"（it.todo、it.skip 滥用）
**需要查看**：测试文件、断言语句、测试运行结果
**正常标准**：
- 每个测试有有效断言
- 断言验证关键行为
- 每个测试至少 1 个有效断言
- 断言验证返回值、副作用、状态
- 无 try/catch 假测试
- it.todo/it.skip 最小化
- 断言具体（如 `expect(result).toEqual({a:1})`）而非宽泛（`expect(result).toBeTruthy()`）
**异常情况**：
- 测试无断言，只调用函数
- 断言只验证 `expect(true).toBe(true)`
- try/catch 包裹"只要不抛错就通过"
- 大量 it.todo/it.skip
- 断言过于宽泛（toBeTruthy、toBeDefined 滥用）
- 断言不验证关键行为
- 测试只验证"函数存在"不验证"行为正确"
**风险等级**：P1
**整改方向**：每个测试加有效断言；断言验证关键行为；移除假测试；具体断言
**验收标准**：所有测试有有效断言；断言验证行为；无假测试

### 指标 4.4：业务流程级测试

**指标名称**：业务流程级测试
**检查目标**：确认有跨函数、跨模块的业务流程级测试，而非只有单元测试
**为什么需要检查**：单元测试只能验证单个函数正确，无法验证"多个函数组合后业务流程正确"。业务流程测试能发现集成问题、数据流问题、状态切换问题。只有单元测试的项目仍会出"每个函数都对，但整体流程错"的问题
**检查范围**：业务流程测试、集成测试、E2E 测试
**检查方法**：
1. 检查是否有集成测试目录（tests/integration/、e2e/）
2. 列出项目核心业务流程（如"查询站点→展示数据→切换图层→导出"）
3. 检查每个核心流程是否有对应流程测试
4. 检查流程测试是否覆盖完整链路（从入口到出口）
5. 检查是否有 E2E 测试框架（Cypress、Playwright）
6. 检查流程测试是否覆盖异常流程（如中途失败、网络错误）
**需要查看**：集成测试目录、E2E 测试、测试配置
**正常标准**：
- 有集成测试或 E2E 测试
- 核心业务流程有流程测试
- 流程测试覆盖完整链路
- 有 E2E 测试框架
- 覆盖异常流程
- 流程测试有可重复的测试数据
**异常情况**：
- 只有单元测试无流程测试
- 核心业务流程无流程测试
- 流程测试只覆盖部分链路
- 无 E2E 框架
- 不测试异常流程
- 流程测试依赖外部数据无法重复
**风险等级**：P2
**整改方向**：补核心流程测试；引入 E2E 框架；覆盖异常流程；准备测试数据
**验收标准**：核心流程有测试；覆盖完整链路；有 E2E 框架

### 指标 4.5：测试可执行性（npm test通过）

**指标名称**：测试可执行性（npm test 通过）
**检查目标**：确认测试能正常执行通过，而非"测试存在但跑不通"
**为什么需要检查**：测试存在但跑不通等于没有测试。常见问题：依赖缺失、环境配置错、测试数据过期、断言失效。跑不通的测试会被开发者忽略，最终成为摆设
**检查范围**：package.json 的 test 脚本、测试运行结果、测试依赖
**检查方法**：
1. 执行 `npm test` 或 `npm run test`
2. 检查是否所有测试通过
3. 检查失败的测试原因（依赖、配置、断言失效）
4. 检查测试是否有外部依赖（数据库、API）导致无法独立运行
5. 检查测试是否有超时问题
6. 检查 CI 中测试是否通过
7. 检查测试运行时间（应 < 5 分钟，过长会被跳过）
**需要查看**：测试运行结果、package.json、测试配置、CI 日志
**正常标准**：
- npm test 全部通过
- 无外部依赖（或外部依赖有 mock）
- 无超时问题
- 测试运行 < 5 分钟
- CI 中测试通过
- 失败测试有修复或明确标记
**异常情况**：
- npm test 失败
- 测试依赖数据库/真实 API 无法独立运行
- 测试超时
- 测试运行 > 10 分钟
- CI 中测试不通过
- 失败测试被忽略
- 测试配置错误无法运行
**风险等级**：P1
**整改方向**：修复失败测试；mock 外部依赖；优化测试性能；CI 保证通过
**验收标准**：npm test 通过；无外部依赖；运行 < 5 分钟

### 指标 4.6：临时测试与正式测试分离

**指标名称**：临时测试与正式测试分离
**检查目标**：确认临时测试（调试用、一次性）与正式测试（持续维护）分离，临时测试不污染正式测试体系
**为什么需要检查**：开发时为了调试写的临时测试如果混入正式测试，会让测试体系混乱——有的测试是该维护的，有的是一次性的，时间长了分不清。临时测试还会拖慢 CI、产生误报
**检查范围**：测试目录结构、临时测试文件、.skip/.only 使用
**检查方法**：
1. 检查测试目录是否有临时测试文件（如 test-temp.spec.ts、debug.test.ts）
2. 检查是否有 .only 或 .skip 的测试（可能导致 CI 跑不全）
3. 检查是否有测试文件名含 temp、debug、try、test-copy
4. 检查是否有测试在注释中标注"临时"
5. 检查正式测试与临时测试是否分目录（如 tests/unit/ vs tests/temp/）
6. 检查 CI 是否排除临时测试
**需要查看**：测试目录、测试文件名、.skip/.only 使用
**正常标准**：
- 临时测试与正式测试分目录
- 无 .only（会跳过其他测试）
- .skip 最小化且有说明
- 临时测试文件名清晰标识
- CI 排除临时测试
- 正式测试目录干净
**异常情况**：
- 临时测试混在正式测试目录
- 有 .only 导致 CI 只跑一个测试
- 大量 .skip 无说明
- 测试文件名含 temp/debug 但在正式目录
- CI 跑临时测试拖慢流水线
- 正式测试目录混乱
**风险等级**：P2
**整改方向**：临时测试移到独立目录；移除 .only；.skip 加说明；CI 排除临时测试
**验收标准**：临时测试分离；无 .only；.skip 有说明

### 指标 4.7：回归测试机制

**指标名称**：回归测试机制
**检查目标**：确认项目有回归测试机制，bug 修复后能补测试防止再次出现
**为什么需要检查**：bug 修复后不补测试，同样的问题可能再次出现。回归测试是"bug 修复闭环"的关键一环——发现 bug → 修复 → 补测试 → 防止回归。无回归测试机制的项目会反复出现相同 bug
**检查范围**：bug 修复记录、回归测试、CI 流程
**检查方法**：
1. 检查 git 历史中 bug 修复 commit 是否附带测试
2. 检查是否有"修复 bug 时必须补测试"的约定
3. 检查 CI 是否有回归测试集
4. 检查是否有 bug 跟踪系统关联测试
5. 检查是否有"先写失败测试再修复"的实践（TDD 风格）
6. 检查关键 bug 是否有对应的回归测试
**需要查看**：git 历史、bug 修复记录、测试文件、CI 配置
**正常标准**：
- bug 修复 commit 附带测试
- 有"修复即补测试"约定
- CI 有回归测试集
- 关键 bug 有对应回归测试
- 先写失败测试再修复的实践
- 回归测试持续累积
**异常情况**：
- bug 修复无测试
- 无"修复即补测试"约定
- 无回归测试集
- 同一 bug 反复出现
- 修复直接改代码不写测试
- 回归测试不随修复累积
**风险等级**：P2
**整改方向**：建立"修复即补测试"约定；CI 加回归测试集；先写失败测试
**验收标准**：bug 修复有测试；有回归测试集；同 bug 不再出现

## 第五部分：构建与部署

> 目标：确认构建部署流程健全，回答"项目能否可靠地上线、上线后能否运维"
> 构建部署问题会在上线时才暴露，是最被动的故障

### 指标 5.1：build成功性

**指标名称**：build 成功性
**检查目标**：确认 `npm run build` 能成功执行，产出可部署的产物
**为什么需要检查**：开发环境能跑不等于 build 能成功。TypeScript 类型错误、import 路径错误、tree-shaking 问题、环境变量缺失都会导致 build 失败。build 失败的项目无法上线
**检查范围**：package.json 的 build 脚本、构建配置、构建产物
**检查方法**：
1. 执行 `npm run build`
2. 检查是否成功产出 dist 目录
3. 检查是否有 TypeScript 错误（如开启 vue-tsc）
4. 检查是否有 build 警告（如 chunk 过大、未使用 import）
5. 检查构建产物结构是否合理（index.html、assets/、static/）
6. 检查构建产物能否在本地预览（npm run preview）
7. 检查不同环境（dev/staging/prod）的 build 是否都能成功
**需要查看**：构建结果、dist 目录、构建日志、package.json
**正常标准**：
- build 成功无错误
- 无 TypeScript 错误
- 无严重警告
- 产物结构合理
- 本地预览正常
- 不同环境 build 都成功
- 构建时间合理（< 5 分钟）
**异常情况**：
- build 失败
- 有 TypeScript 错误但被忽略
- 大量警告
- 产物结构混乱
- 本地预览异常
- 某环境 build 失败
- 构建时间过长（> 10 分钟）
**风险等级**：P0
**整改方向**：修复 build 错误；修复 TS 错误；清理警告；优化构建性能
**验收标准**：build 成功；无错误无警告；产物可预览

### 指标 5.2：环境变量管理（.env.example无密钥）

**指标名称**：环境变量管理（.env.example 无密钥）
**检查目标**：确认环境变量管理规范，有 .env.example，无真实密钥入库
**为什么需要检查**：环境变量混乱是常见问题——开发者本地能跑但别人不能跑、密钥硬编码在 .env 入库、生产环境变量缺失。规范的环境变量管理是可重复构建的前提
**检查范围**：.env 文件、.env.example、.gitignore、构建配置中的环境变量使用
**检查方法**：
1. 检查是否有 .env.example 文件
2. 检查 .env.example 是否只含占位符（如 `VITE_API_URL=`）而非真实值
3. 检查 .env 是否在 .gitignore 中
4. 检查 .env 是否被误提交到 git
5. 检查代码中环境变量的使用（`import.meta.env.VITE_XXX`）
6. 检查是否有 .env.development、.env.production 等多环境文件
7. 检查是否有环境变量缺失时的默认值或报错
8. 检查 CI 中环境变量如何注入
**需要查看**：.env、.env.example、.gitignore、源码中的环境变量使用、CI 配置
**正常标准**：
- 有 .env.example
- .env.example 只含占位符
- .env 在 .gitignore 中
- .env 未入库
- 多环境文件分离（.env.development 等）
- 环境变量缺失有报错或默认值
- CI 通过 secret 注入环境变量
- 前端环境变量以 VITE_ 前缀
**异常情况**：
- 无 .env.example
- .env.example 含真实密钥
- .env 被提交到 git
- 无多环境分离
- 环境变量缺失静默失败
- CI 中硬编码环境变量
- 前端用了非 VITE_ 前缀变量（构建时不注入）
- 环境变量名前后端不一致
**风险等级**：P0（密钥入库）/ P1（其他）
**整改方向**：创建 .env.example；.env 入 .gitignore；移除已泄露密钥；多环境分离；CI 用 secret
**验收标准**：有 .env.example；无密钥入库；多环境分离；CI 用 secret

### 指标 5.3：Dockerfile合理性（多阶段/最小镜像）

**指标名称**：Dockerfile 合理性（多阶段/最小镜像）
**检查目标**：确认 Dockerfile 使用多阶段构建，最终镜像最小化，无 unnecessary 依赖
**为什么需要检查**：单阶段构建会把开发依赖（node_modules 全部、源码、构建工具）都打进镜像，导致镜像体积巨大（> 1GB）、攻击面大、拉取慢。多阶段构建只把最终产物打入镜像，体积可控（< 200MB）
**检查范围**：Dockerfile、.dockerignore、镜像构建结果
**检查方法**：
1. 检查是否有 Dockerfile
2. 检查是否使用多阶段构建（FROM ... AS builder, FROM nginx/node:alpine）
3. 检查最终镜像是否基于 alpine 或 distroless
4. 检查是否有 .dockerignore（排除 node_modules、.git 等）
5. 检查镜像体积（`docker images` 查看大小）
6. 检查是否以非 root 用户运行
7. 检查是否有 HEALTHCHECK 指令
8. 检查是否利用了构建缓存（依赖安装层与代码拷贝层分离）
**需要查看**：Dockerfile、.dockerignore、镜像大小
**正常标准**：
- 使用多阶段构建
- 最终镜像基于 alpine 或 distroless
- 有 .dockerignore
- 镜像体积 < 200MB
- 以非 root 用户运行
- 有 HEALTHCHECK
- 构建缓存优化
- 无源码进入最终镜像
**异常情况**：
- 单阶段构建
- 基于 node:latest 等大镜像
- 无 .dockerignore
- 镜像体积 > 1GB
- 以 root 运行
- 无 HEALTHCHECK
- 源码进入最终镜像
- 每次构建都重装依赖（无缓存优化）
**风险等级**：P1
**整改方向**：改多阶段构建；用 alpine/distroless；加 .dockerignore；非 root 运行；加 HEALTHCHECK
**验收标准**：多阶段构建；镜像 < 200MB；非 root；有 HEALTHCHECK

### 指标 5.4：CI流程完整性（测试+构建）

**指标名称**：CI 流程完整性（测试+构建）
**检查目标**：确认 CI 流程包含 lint、测试、构建等必要步骤，且在 PR/MR 时执行
**为什么需要检查**：CI 是代码质量的自动门禁，无 CI 或 CI 不完整会让低质量代码进入主干。CI 必须包含测试和构建，否则"我本地能跑"的代码可能 break 主干。CI 在 PR 时执行能提前发现问题
**检查范围**：CI 配置文件（.github/workflows、.gitlab-ci.yml、Jenkinsfile）
**检查方法**：
1. 检查是否有 CI 配置文件
2. 检查 CI 流程包含哪些步骤（lint、test、build、deploy）
3. 检查是否在 PR/MR 时执行（而非只在 push 主干）
4. 检查是否跑测试（npm test）
5. 检查是否跑构建（npm run build）
6. 检查是否跑 lint（npm run lint）
7. 检查是否跑类型检查（tsc --noEmit）
8. 检查 CI 失败是否阻断合并
9. 检查 CI 是否有缓存优化（npm cache）
**需要查看**：CI 配置文件、CI 运行记录、分支保护设置
**正常标准**：
- 有 CI 配置
- CI 包含 lint、type-check、test、build
- PR/MR 时执行
- CI 失败阻断合并
- 有缓存优化
- CI 运行时间合理（< 10 分钟）
- 有多个环境（dev/staging/prod）的部署流程
**异常情况**：
- 无 CI 配置
- CI 只跑 build 不跑 test
- CI 只在 push 主干时跑
- CI 失败不阻断合并
- 无缓存优化
- CI 运行 > 30 分钟
- 无 lint 或类型检查
- 无部署流程
**风险等级**：P1
**整改方向**：完善 CI 步骤；PR 时执行；失败阻断合并；加缓存优化
**验收标准**：CI 包含 lint/test/build；PR 时执行；失败阻断合并

### 指标 5.5：日志级别与轮转

**指标名称**：日志级别与轮转
**检查目标**：确认后端日志有级别区分和轮转机制，避免日志文件无限增长
**为什么需要检查**：无级别日志会让排查问题困难（debug 日志淹没 error）。无轮转的日志会无限增长撑满磁盘，导致服务崩溃。日志轮转是后端服务的基本运维要求
**检查范围**：后端日志配置、日志库（winston/log4j/pino）、日志文件
**检查方法**：
1. 检查后端日志库配置（winston/log4j/pino）
2. 检查日志级别是否区分（debug/info/warn/error）
3. 检查生产环境日志级别是否合理（info 或 warn，不应是 debug）
4. 检查是否有日志轮转配置（如 winston-daily-rotate-file）
5. 检查轮转策略（按天、按大小）
6. 检查日志保留时长（如保留 30 天）
7. 检查日志是否输出到文件（而非只 console）
8. 检查是否有日志收集系统（ELK、Loki）
**需要查看**：日志配置、日志库使用、日志文件目录
**正常标准**：
- 日志级别区分（debug/info/warn/error）
- 生产环境级别为 info 或 warn
- 有日志轮转
- 轮转按天或按大小
- 日志保留 30 天以上
- 日志输出到文件
- 有日志收集系统
- 错误日志单独文件
**异常情况**：
- 无日志级别区分
- 生产环境用 debug 级别
- 无日志轮转
- 日志无限增长
- 只 console 不写文件
- 无日志收集系统
- 所有日志混在一起
- 日志保留时间过短或过长
**风险等级**：P1
**整改方向**：配置日志级别；加日志轮转；配置保留时长；接入日志收集系统
**验收标准**：有日志级别；有轮转；有保留时长；有收集系统

### 指标 5.6：健康检查

**指标名称**：健康检查
**检查目标**：确认服务有健康检查端点，容器编排系统能据此判断服务状态
**为什么需要检查**：无健康检查的容器在服务假死时不会被重启，导致用户持续访问故障实例。健康检查是容器编排（K8s、Docker Swarm）判断服务是否存活的基础
**检查范围**：后端健康检查端点、Dockerfile HEALTHCHECK、K8s liveness/readiness probe
**检查方法**：
1. 检查后端是否有 `/health` 或 `/healthz` 端点
2. 检查健康检查端点的返回（应返回 200 + 状态 JSON）
3. 检查健康检查是否检查关键依赖（数据库、Redis 连接）
4. 检查 Dockerfile 是否有 HEALTHCHECK 指令
5. 检查 K8s 配置是否有 livenessProbe 和 readinessProbe
6. 检查 probe 配置是否合理（间隔、超时、阈值）
7. 检查是否有 readiness 与 liveness 区分（readiness 检查能否接流量，liveness 检查是否存活）
**需要查看**：后端路由、Dockerfile、K8s 配置
**正常标准**：
- 有 /health 端点
- 返回 200 + 状态 JSON
- 检查关键依赖
- Dockerfile 有 HEALTHCHECK
- K8s 有 livenessProbe 和 readinessProbe
- probe 配置合理
- liveness 与 readiness 区分
**异常情况**：
- 无健康检查端点
- 健康检查只返回 200 不检查依赖
- Dockerfile 无 HEALTHCHECK
- K8s 无 probe 配置
- probe 配置不合理（间隔过短、阈值过低）
- liveness 与 readiness 不区分
- 健康检查端点需要认证（编排系统无法访问）
**风险等级**：P1
**整改方向**：加 /health 端点；检查关键依赖；Dockerfile 加 HEALTHCHECK；K8s 加 probe
**验收标准**：有 /health 端点；检查依赖；有 probe 配置

### 指标 5.7：回滚机制

**指标名称**：回滚机制
**检查目标**：确认部署系统支持快速回滚，且回滚流程有演练
**为什么需要检查**：上线出问题时分秒必争，无回滚机制只能"边修边炸"。回滚是上线失败的安全网，必须有预案且演练过。没演练过的回滚在真实故障时往往会失败
**检查范围**：部署系统配置、回滚脚本、版本管理、回滚演练记录
**检查方法**：
1. 检查部署系统是否支持回滚（K8s rollout undo、Docker 镜像回退）
2. 检查是否有回滚脚本或文档
3. 检查镜像是否保留多个版本（可回退到上一版本）
4. 检查数据库迁移是否支持回滚（migration down）
5. 检查是否有回滚演练记录
6. 检查回滚耗时（应 < 5 分钟）
7. 检查是否有蓝绿部署或金丝雀发布降低风险
**需要查看**：部署配置、回滚脚本、镜像仓库、迁移文件、演练记录
**正常标准**：
- 部署系统支持回滚
- 有回滚脚本/文档
- 镜像保留多版本
- 数据库迁移支持回滚
- 有回滚演练记录
- 回滚 < 5 分钟
- 有蓝绿或金丝雀发布
**异常情况**：
- 无回滚机制
- 无回滚脚本
- 镜像只保留最新版本
- 数据库迁移不支持回滚
- 无演练记录
- 回滚耗时 > 30 分钟
- 直接全量发布无灰度
**风险等级**：P1
**整改方向**：实现回滚机制；编写回滚脚本；保留多版本镜像；迁移支持回滚；定期演练
**验收标准**：有回滚机制；有脚本；有演练记录；回滚 < 5 分钟

## 第六部分：死代码与重复治理

> 目标：清理项目认知负担，回答"项目里哪些代码是死的、哪些是重复的"
> 死代码和重复代码增加维护成本，是技术债的主要成分

### 指标 6.1：未引用文件识别（工程化视角）

**指标名称**：未引用文件识别（工程化视角）
**检查目标**：识别项目中从未被任何地方引用的源码文件
**为什么需要检查**：未引用文件是死代码的主要形式，增加认知负担、误导维护者、掩盖真实结构。开发者不敢删怕"万一用到"，最终项目越来越臃肿
**检查范围**：所有源码文件（除入口、配置、测试）
**检查方法**：
1. 列出所有源码文件
2. 用 dependency-cruiser 或 ts-prune 扫描未引用文件
3. 全局搜索每个文件是否被 import
4. 排除入口文件（main.ts、index.html）、配置文件（vite.config）、测试文件
5. 对未引用文件，确认是否真的无用（而非被动态 import）
6. 检查是否有动态 import 字符串拼接（如 ``import(`./views/${name}`)``）导致静态分析遗漏
**需要查看**：文件清单、import 关系、dependency-cruiser/ts-prune 报告
**正常标准**：
- 所有源码文件都被引用
- 未引用文件已删除或归档
- 动态 import 有注释说明
- 入口文件、配置文件、测试文件单独标识
- 无"怕删不敢删"的文件
**异常情况**：
- 存在从未被引用的源码文件
- 未引用文件长期保留无人清理
- 动态 import 未注释导致分析遗漏
- 同名文件多处存在造成混淆
- 整个目录未被引用
**风险等级**：P2
**整改方向**：删除未引用文件；归档到独立目录；动态 import 加注释
**验收标准**：无未引用源码文件；动态 import 有注释

### 指标 6.2：未消费export识别

**指标名称**：未消费 export 识别
**检查目标**：识别文件中导出但从未被任何地方 import 的 export
**为什么需要检查**：未消费 export 是"文件级死代码"的细化，说明该函数/变量/类型对外暴露但无人使用。可能是历史遗留或过度设计，增加维护负担
**检查范围**：所有 export 语句
**检查方法**：
1. 用 ts-prune 或类似工具扫描未消费 export
2. 列出所有未被 import 的 export
3. 排除入口文件的 export（index.ts 的 export 可能用于对外 API）
4. 排除被动态访问的 export（如 `module[key]`）
5. 检查未消费 export 是否有保留理由
6. 检查是否是"导出后从未使用"还是"曾经使用现已废弃"
**需要查看**：export 清单、ts-prune 报告、import 关系
**正常标准**：
- 所有 export 都有消费者（除入口文件对外 API）
- 未消费 export 已删除
- 入口文件 export 有说明
- 无"导出备用"的过度设计
**异常情况**：
- 大量 export 无消费者
- 未消费 export 长期保留
- 入口文件 export 混乱
- 有"导出以防万一"的过度设计
- 同名 export 多处定义
**风险等级**：P2
**整改方向**：删除未消费 export；收敛入口文件 export
**验收标准**：无未消费 export；入口 export 清晰

### 指标 6.3：大段注释代码

**指标名称**：大段注释代码
**检查目标**：识别被注释掉的大段代码块，这些代码应该删除而非注释保留
**为什么需要检查**：注释代码是"墓碑代码"，增加认知负担、误导维护者（"这段是要的还是不要的"）、占用文件空间。git 已经保留历史，不需要用注释保留旧代码
**检查范围**：所有源码文件中的注释代码块
**检查方法**：
1. 搜索多行注释（`/* ... */`、`<!-- ... -->`）
2. 检查注释内容是否是代码（含 if/for/function/const 等）
3. 标记超过 10 行的注释代码块
4. 检查注释代码是否是"旧实现"或"备用方案"
5. 检查是否有"// TODO: 删除"标记的注释代码
6. 排除合法的注释（文档注释、说明性注释）
**需要查看**：源码文件、注释内容
**正常标准**：
- 无大段注释代码（> 10 行）
- 旧实现已删除（git 保留历史）
- 备用方案有独立文档而非注释
- 注释是说明性的而非代码
- 有"注释代码即删除"的约定
**异常情况**：
- 大段注释代码（> 10 行）
- 旧实现注释保留
- 备用方案注释在代码中
- "TODO 删除"标记长期未处理
- 注释代码与正常代码混杂
**风险等级**：P2
**整改方向**：删除注释代码；旧实现靠 git 历史；备用方案独立文档
**验收标准**：无大段注释代码；旧实现已删除

### 指标 6.4：临时/备份文件（_old/_v2/_backup）

**指标名称**：临时/备份文件（_old/_v2/_backup）
**检查目标**：识别源码中的临时文件、备份文件、版本副本
**为什么需要检查**：临时/备份文件是"墓碑代码"的另一形式，增加认知负担、可能被误 import、污染构建。这些文件应该删除或归档，不应留在源码区
**检查范围**：所有文件（含源码、配置、文档）
**检查方法**：
1. 搜索文件名含 `_old`、`_v2`、`_backup`、`_temp`、`_copy`、`-old`、`-backup` 的文件
2. 搜索文件名含 `test-`、`debug-`、`try-` 的文件
3. 搜索文件名含日期（如 `20240101`）的文件
4. 检查是否有 `.bak`、`.tmp`、`.orig` 后缀文件
5. 检查是否有 `copy of`、`复件` 开头的文件
6. 确认这些文件是否真的无用
**需要查看**：文件清单、文件名
**正常标准**：
- 无临时/备份文件
- 无 `.bak`、`.tmp`、`.orig` 文件
- 无日期后缀文件
- 无"复件"文件
- 有"临时文件不入源码"的约定
**异常情况**：
- 存在 `_old`、`_v2`、`_backup` 文件
- 存在 `.bak`、`.tmp` 文件
- 存在日期后缀文件
- 存在"复件"文件
- 临时文件被误 import
**风险等级**：P2
**整改方向**：删除临时/备份文件；归档到独立目录；约定不入源码
**验收标准**：无临时/备份文件；源码区干净

### 指标 6.5：重复工具函数

**指标名称**：重复工具函数
**检查目标**：识别多处实现的相同或高度相似的工具函数
**为什么需要检查**：重复工具函数意味着修改时需要同步多处，遗漏任一处都会产生 bug。如多个 `formatDate`、`parseTime`、`deepClone` 实现散落各处
**检查范围**：所有工具函数（format、parse、clone、validate 等）
**检查方法**：
1. 列出所有工具函数（搜索 utils 目录、helper 文件）
2. 按功能分类（格式化、校验、转换、克隆等）
3. 对比同类函数的实现是否高度相似
4. 检查是否有多个 `formatDate`、`parseTime` 实现
5. 检查是否有多个 `deepClone`、`debounce`、`throttle` 实现
6. 检查是否引用了 lodash 等库但又有自己的实现
**需要查看**：工具函数实现、utils 目录、import 关系
**正常标准**：
- 同一功能只有一处实现
- 工具函数有统一出处
- 无重复的 formatDate/parseTime 等
- 已用 lodash 等库的不重复实现
- 工具函数有清晰分类
**异常情况**：
- 多个 formatDate 实现
- 多个 deepClone 实现
- 已用 lodash 又自己实现 debounce
- 同一校验逻辑多处实现
- 工具函数散落多个文件无统一出处
**风险等级**：P2
**整改方向**：统一到 shared/utils；删除重复实现；优先用成熟库
**验收标准**：同一功能单一实现；统一出处；无重复

### 指标 6.6：前后端重复类型定义

**指标名称**：前后端重复类型定义
**检查目标**：确认前后端没有各自维护一份相同结构的类型定义
**为什么需要检查**：前后端各自维护类型定义会导致不一致——前端加了字段后端没加，或后端改了字段名前端没同步。这种不一致是"接口成功但页面错误"的常见原因
**检查范围**：前端 types 目录、后端类型定义/DTO/Schema
**检查方法**：
1. 列出前端类型定义（types/、interfaces/）
2. 列出后端类型定义（DTO、Schema、Model）
3. 对比同一业务实体在前后端的定义
4. 检查字段名、类型、可空性是否一致
5. 检查是否有自动同步机制（如 OpenAPI 生成前端类型）
6. 检查不一致的定义是否有转换层
**需要查看**：前端 types、后端 DTO/Schema、API 文档
**正常标准**：
- 同一实体前后端类型一致
- 或有自动同步机制（OpenAPI 生成）
- 不一致处有转换层
- 类型定义单一来源
- 字段名、类型、可空性对齐
**异常情况**：
- 前后端各自维护一份相同结构
- 字段名不一致（如前端 userName 后端 user_name）无转换
- 类型不一致（如前端 string 后端 number）
- 无自动同步机制
- 同一实体多处定义
**风险等级**：P1
**整改方向**：单一来源或自动同步；不一致处加转换层；字段对齐
**验收标准**：前后端类型一致；有同步机制或转换层

### 指标 6.7：重复业务逻辑

**指标名称**：重复业务逻辑
**检查目标**：识别多处实现的相同业务逻辑（如计算规则、过滤规则、权限判断）
**为什么需要检查**：重复业务逻辑比重复工具函数更危险——业务规则变化时需要同步修改多处，遗漏会导致业务错误。如"预警等级计算"在前端和后端各实现一遍
**检查范围**：业务计算函数、过滤规则、权限判断、状态转换
**检查方法**：
1. 列出核心业务逻辑（计算、规则、判断）
2. 检查同一业务逻辑是否在多处实现
3. 重点检查前后端是否各实现一遍相同业务规则
4. 检查多个组件是否各自实现相同的过滤/排序逻辑
5. 检查多个 composable 是否有相似的业务逻辑未抽公共
6. 评估重复实现的同步风险
**需要查看**：业务逻辑实现、前后端代码、composable
**正常标准**：
- 同一业务逻辑单一实现
- 前后端不重复实现业务规则（后端为权威）
- 多组件公共逻辑抽取
- composable 公共逻辑抽取
- 业务逻辑有文档
**异常情况**：
- 同一业务规则前后端各实现一遍
- 多个组件各自实现相同过滤
- 多个 composable 有相似业务逻辑
- 业务逻辑散落多处无统一出处
- 修改一处业务规则需同步多处
**风险等级**：P1
**整改方向**：业务逻辑后端权威；前端不重复实现；公共逻辑抽取
**验收标准**：业务逻辑单一实现；前后端不重复

## 第七部分：代码规范与可维护性

> 目标：评估项目的可维护性，回答"项目能否长期演进、新人能否快速接手"
> 可维护性决定项目生命周期

### 指标 7.1：ESLint/Prettier配置与执行

**指标名称**：ESLint/Prettier 配置与执行
**检查目标**：确认项目配置了 ESLint 和 Prettier，且通过工具强制执行（如 git hook、CI）
**为什么需要检查**：无 ESLint 的项目代码风格依赖开发者自觉，必然逐渐混乱。无 Prettier 的项目格式不统一，diff 噪音大。仅配置不强制等于没配——开发者可以忽略警告
**检查范围**：ESLint 配置、Prettier 配置、package.json 的 lint 脚本、git hook（husky）、CI
**检查方法**：
1. 检查是否有 .eslintrc / eslint.config.js
2. 检查是否有 .prettierrc
3. 检查 ESLint 规则是否合理（无大量 off 或 warn）
4. 检查 package.json 是否有 lint 脚本
5. 检查是否有 husky + lint-staged 在 commit 时强制执行
6. 检查 CI 是否跑 lint 并阻断失败
7. 执行 `npm run lint` 检查是否有错误
8. 检查是否有 `eslint-disable` 滥用
**需要查看**：ESLint 配置、Prettier 配置、package.json、husky 配置、CI 配置
**正常标准**：
- 有 ESLint 和 Prettier 配置
- 规则合理（无大量 off）
- 有 lint 脚本
- husky + lint-staged 强制执行
- CI 跑 lint 阻断失败
- npm run lint 无错误
- eslint-disable 最小化且有说明
**异常情况**：
- 无 ESLint 或 Prettier 配置
- 规则大量关闭
- 无 lint 脚本
- 无 husky 强制执行
- CI 不跑 lint
- npm run lint 大量错误
- eslint-disable 滥用
**风险等级**：P2
**整改方向**：配置 ESLint/Prettier；husky 强制执行；CI 阻断；清理 eslint-disable
**验收标准**：有配置；husky 强制；CI 阻断；lint 无错误

### 指标 7.2：命名一致性（同概念多命名）

**指标名称**：命名一致性（同概念多命名）
**检查目标**：确认同一概念在项目中使用统一命名，不存在"一个东西多个名字"
**为什么需要检查**：命名不一致增加认知负担，新人不知道"userName"和"username"是不是一个东西。还可能导致 bug（如大小写不一致导致字段访问失败）
**检查范围**：变量命名、函数命名、文件命名、字段命名
**检查方法**：
1. 列出核心业务概念（如 user、site、station、layer）
2. 搜索每个概念的不同命名形式（如 userName/username/user_name/User）
3. 检查同一概念是否有多个命名
4. 检查文件命名风格是否统一（kebab-case vs camelCase vs PascalCase）
5. 检查前后端字段命名是否一致
6. 检查变量、函数、类型命名风格是否统一
**需要查看**：源码全量搜索、命名风格、前后端字段
**正常标准**：
- 同一概念统一命名
- 文件命名风格统一
- 前后端字段命名一致
- 变量/函数/类型命名风格统一
- 有命名约定文档
**异常情况**：
- 同一概念多个命名（userName/username/user_name）
- 文件命名风格混乱（kebab-case 与 camelCase 混用）
- 前后端字段命名不一致
- 变量/函数/类型风格不统一
- 无命名约定
**风险等级**：P2
**整改方向**：统一命名；建立命名约定；前后端对齐
**验收标准**：同一概念单一命名；风格统一；前后端对齐

### 指标 7.3：commit规范与工具化

**指标名称**：commit 规范与工具化
**检查目标**：确认项目有 commit 规范（如 Conventional Commits）且通过工具强制执行
**为什么需要检查**：无规范的 commit 历史难以阅读，无法自动生成 changelog，无法回溯某类变更。规范的 commit 是项目演进的可追溯记录
**检查范围**：commitlint 配置、commitizen、git 历史
**检查方法**：
1. 检查是否有 commitlint 配置（.commitlintrc）
2. 检查是否有 commitizen 或类似工具
3. 检查 husky 是否在 commit-msg 时校验
4. 检查 git 历史中 commit 是否符合规范（feat/fix/docs/chore 等）
5. 检查是否有自动生成 changelog 的机制
6. 检查 commit message 是否有 scope 和 description
**需要查看**：commitlint 配置、husky 配置、git 历史
**正常标准**：
- 有 commitlint 配置
- husky 校验 commit-msg
- git 历史符合 Conventional Commits
- 有自动 changelog 机制
- commit 有 type/scope/description
- 无"update"、"fix bug"等模糊 commit
**异常情况**：
- 无 commitlint
- husky 不校验 commit-msg
- git 历史混乱（"update"、"修改"等）
- 无 changelog 机制
- commit 无 type
- 大量"杂项"commit
**风险等级**：P3
**整改方向**：配置 commitlint；husky 校验；用 Conventional Commits；自动 changelog
**验收标准**：有 commitlint；husky 校验；历史规范

### 指标 7.4：项目文档完整性（根因文档/API契约）

**指标名称**：项目文档完整性（根因文档/API 契约）
**检查目标**：确认项目有根因文档、API 契约文档、架构文档等关键文档
**为什么需要检查**：无文档的项目只能靠口口相传，新人接手困难，关键人员离职后知识断层。根因文档说明"为什么这么做"，API 契约说明"接口长什么样"，是项目传承的基础
**检查范围**：docs 目录、README、API 文档、架构文档
**检查方法**：
1. 检查是否有 README 且内容完整（项目介绍、启动方式、构建方式）
2. 检查是否有根因文档（说明项目背景、为什么选某些技术、关键决策）
3. 检查是否有 API 契约文档（OpenAPI/Swagger 或 markdown）
4. 检查是否有架构文档（模块划分、依赖关系）
5. 检查文档是否与代码同步（过期文档比无文档更糟）
6. 检查关键模块是否有说明文档
**需要查看**：README、docs 目录、API 文档、架构文档
**正常标准**：
- README 完整
- 有根因文档
- 有 API 契约文档
- 有架构文档
- 文档与代码同步
- 关键模块有说明
- 文档有维护责任人
**异常情况**：
- 无 README 或内容简陋
- 无根因文档
- 无 API 文档
- 无架构文档
- 文档严重过期
- 关键模块无说明
- 无文档维护人
**风险等级**：P2
**整改方向**：补全 README；写根因文档；生成 API 文档；写架构文档；定期更新
**验收标准**：有 README；有根因文档；有 API 文档；文档同步

### 指标 7.5：关键模块说明文档

**指标名称**：关键模块说明文档
**检查目标**：确认关键模块（core、shared、业务核心）有说明文档，解释其职责、用法、注意事项
**为什么需要检查**：关键模块是项目核心，无文档只能靠读代码理解，新人接手慢、修改易出错。关键模块文档应说明"做什么、怎么做、不能做什么"
**检查范围**：core 模块、shared 模块、业务核心模块、地图模块
**检查方法**：
1. 列出关键模块清单
2. 对每个关键模块，检查是否有 README 或说明文档
3. 检查文档是否说明模块职责
4. 检查文档是否说明用法（API、示例）
5. 检查文档是否说明注意事项（不能做什么、已知限制）
6. 检查文档是否与代码同步
**需要查看**：模块目录、README、文档
**正常标准**：
- 每个关键模块有说明文档
- 文档说明职责、用法、注意事项
- 文档有示例
- 文档与代码同步
- 文档有维护人
**异常情况**：
- 关键模块无文档
- 文档只说职责不说用法
- 无示例
- 文档过期
- 无维护人
**风险等级**：P2
**整改方向**：为关键模块补文档；说明职责、用法、注意事项；加示例
**验收标准**：关键模块有文档；文档完整；有示例

### 指标 7.6：代码注释质量

**指标名称**：代码注释质量
**检查目标**：确认代码注释质量合理——关键逻辑有注释，无明显代码有冗余注释
**为什么需要检查**：注释是代码的补充说明，好的注释解释"为什么"，坏的注释只重复"是什么"。无注释的关键逻辑难以理解，过度注释的简单代码增加阅读负担
**检查范围**：源码中的注释
**检查方法**：
1. 检查关键业务逻辑是否有注释（解释为什么这么做）
2. 检查复杂算法是否有注释
3. 检查 hack/workaround 是否有注释说明原因
4. 检查是否有"重复代码"式注释（如 `// 设置 name 为 xxx` 后跟 `name = xxx`）
5. 检查是否有过期注释（注释与代码不符）
6. 检查 TODO 是否有负责人和计划
**需要查看**：源码注释
**正常标准**：
- 关键逻辑有注释解释为什么
- 复杂算法有注释
- hack 有注释说明原因
- 无重复代码式注释
- 注释与代码一致
- TODO 有负责人
**异常情况**：
- 关键逻辑无注释
- 复杂算法无注释
- hack 无说明
- 大量"重复代码"式注释
- 注释与代码不符
- TODO 无负责人无计划
**风险等级**：P3
**整改方向**：关键逻辑加注释；移除冗余注释；修正过期注释；TODO 加负责人
**验收标准**：关键逻辑有注释；无冗余注释；注释与代码一致

## 第八部分：v3 迁移新增指标（2026-09-01 增补，见 00 §4 指标演进口径）

> 背景：v3 迁移引入 Docker Compose 多服务栈（postgis/nest/algorithm-service）、数据库迁移脚本与新后端工程。以下指标覆盖这一新机制的可审查语义。

### 指标 8.1：compose 服务健康检查与启动依赖

**指标名称**：compose 服务健康检查与启动依赖
**检查目标**：确认 v3 栈中每个有依赖关系的服务都配置了 healthcheck，且依赖方使用 `depends_on` 的 `condition: service_healthy` 而非裸列表
**为什么需要检查**：Nest/FastAPI 启动时若 Postgres 尚未就绪，连接池初始化失败会导致服务反复崩溃重启；裸 `depends_on` 只保证容器启动顺序，不保证服务可用
**检查范围**：`docker-compose.yml`、`docker-compose.v3.yml` 及后续合并产物中全部服务定义
**检查方法**：
1. 逐服务检查 `healthcheck` 字段是否存在且探针命令有意义（如 `pg_isready`）
2. 检查依赖数据库的服务是否声明 `depends_on` 且带 `condition: service_healthy`
3. 实际验证：`docker compose -f <file> up -d` 后观察依赖方是否等待健康再启动
**需要查看**：compose 文件全文、容器启动日志
**正常标准**：数据类服务有 healthcheck；依赖方带 condition 等待；全栈冷启动一次成功
**异常情况**：依赖方无 condition（裸列表或缺失）；healthcheck 缺失或探针恒真；冷启动需手工按序起容器
**风险等级**：P2
**整改方向**：补 healthcheck + condition；本地实测冷启动
**验收标准**：全栈一条命令冷启动成功，依赖方无连接失败重试日志

### 指标 8.2：迁移/导入脚本幂等性

**指标名称**：迁移/导入脚本幂等性
**检查目标**：确认数据迁移与导入脚本重复执行结果一致，不产生重复数据、不因中间态崩溃留下半成品
**为什么需要检查**：迁移脚本会在开发期反复重跑（数据更新、表结构调整）；非幂等脚本重跑即产生重复行或脏数据，且问题往往在消费端才暴露
**检查范围**：`tools/db-import.mjs`、`tools/gis-import/` 及后续新增的迁移脚本
**检查方法**：
1. 通读脚本确认写入策略（TRUNCATE 重灌 / `ON CONFLICT` / 裸 INSERT）
2. 连续执行两遍，比对每表行数与抽查行内容
3. 构造中途失败场景（如断言失败退出）后重跑，确认可恢复
**需要查看**：脚本源码、两次执行的行数输出、失败恢复日志
**正常标准**：两遍执行行数一致；含对账输出（源条数/写入条数/过滤条数）；中途失败后重跑可完整恢复
**异常情况**：裸 INSERT 无去重重跑翻倍；无对账输出无法判断成功；失败后留下部分数据且重跑不清理
**风险等级**：P1
**整改方向**：改为重灌或冲突忽略语义；补对账报告；失败路径先清理再重灌
**验收标准**：连跑两遍结果一致；对账报告全 PASS

### 指标 8.3：数据库凭据与环境配置管理

**指标名称**：数据库凭据与环境配置管理
**检查目标**：确认数据库连接凭据不硬编码进仓库，开发默认值与生产配置分离，敏感项走 .env/Secrets
**为什么需要检查**：v3 引入 PG 后新增 `PG_PASSWORD` 等敏感配置；开发 compose 里的默认口令若被原样搬进生产配置或前端可见处，即为 P0 安全问题
**检查范围**：compose 文件、`backend/nest` 配置模块、`.env*` 文件、`.gitignore`、CI Secrets 清单
**检查方法**：
1. grep 仓库确认无真实口令/密钥入库（`password\s*=` 模式 + gitleaks）
2. 确认 `.env` 在 `.gitignore` 且提供 `.env.example` 占位模板
3. 检查 Nest 配置模块从环境注入而非默认值硬编码
4. 确认开发默认口令（如 compose 里的 postgres/postgres）不出现在生产部署配置中
**需要查看**：compose 文件、配置模块、.env.example、gitleaks.toml
**正常标准**：仓库零真实凭据；.env.example 仅占位符；生产凭据走服务器 .env 或 CI Secrets；开发默认口令仅存在于开发 compose
**异常情况**：真实口令入库；生产配置复用开发默认口令；前端 bundle 出现数据库配置
**风险等级**：P0
**整改方向**：立即移出仓库并轮换；补 .env.example；生产凭据走环境注入
**验收标准**：gitleaks 通过；.env.example 齐全；生产配置无默认口令

### 指标 8.4：服务端口分配与冲突

**指标名称**：服务端口分配与冲突
**检查目标**：确认 v3 栈各服务端口分配有明确约定（Express 3000 / Nest 3100 / FastAPI 8000 / PG 5432 / Vite 5173），并存期无冲突，切换完成后按约定回收
**为什么需要检查**：strangler 迁移期新旧后端并存，端口冲突会导致服务起不来或"改了新后端却测的旧后端"的错觉排障
**检查范围**：compose 文件、各服务启动配置、Vite proxy 配置、根 package.json dev 脚本
**检查方法**：
1. 列出全部服务及其端口声明，确认无重复
2. 检查 Vite proxy 目标端口与实际服务端口一致
3. 本机实测：全栈启动后逐端口探活
**需要查看**：compose 端口映射、vite.config proxy、各服务 main/bootstrap 文件
**正常标准**：端口矩阵与约定一致；proxy 指向正确；全栈启动无端口占用报错
**异常情况**：两个服务同端口；proxy 指向已停用端口；脚本硬编码与 compose 声明不一致
**风险等级**：P2
**整改方向**：端口矩阵写入手册；冲突处改配置；proxy 对齐
**验收标准**：端口矩阵唯一权威出处且全栈实测无冲突

### 指标 8.5：CI 门禁对新后端的覆盖

**指标名称**：CI 门禁对新后端的覆盖
**检查目标**：确认 backend/nest 与 backend/algorithm-service 的 lint/test/typecheck 不游离于本地门禁（ci:local）与 CI 流水线之外
**为什么需要检查**：新工程若不在门禁内，质量约束只靠自觉，回归问题会在合并期集中爆发；与"跳过的那项就会在 CI 挂"的既有教训同源
**检查范围**：根 package.json `ci:local` 脚本、`.github/workflows/ci.yml`、nest/algorithm-service 各自的 lint/test 配置
**检查方法**：
1. 检查 `ci:local` 是否包含 nest 测试与 lint 步骤
2. 检查 ci.yml 是否有对应 job 或步骤（algorithm-service 走 pytest）
3. 故意注入一个 lint error / 失败测试，验证门禁确实拦截
**需要查看**：package.json scripts、ci.yml、各工程 eslint/vitest/pytest 配置
**正常标准**：新工程的 lint/test 均在 ci:local 与 CI 链中；破坏性改动必红
**异常情况**：新工程测试仅能手动跑；CI 只覆盖老 backend；lint 规则对新目录静默跳过
**风险等级**：P1
**整改方向**：ci:local 追加步骤；ci.yml 补 job；验证拦截有效性
**验收标准**：注入坏改动后本地与 CI 双双变红
