# 架构耦合专项审查指标体系

> 版本：v1.0
> 定位：项目代码深度审查体系的架构耦合专项，可独立并行执行
> 与审查体系关系：见 `00-审查体系约定.md`（一级质量属性 #1 架构与模块边界）
> 适用：AI 辅助代码审查、架构腐化诊断、模块边界治理、重构前结构分析、项目交接架构评估
> 聚焦范围：项目目录结构、文件职责、模块边界、依赖关系、分层架构、隐式通信与多入口、代码资产
> 原则约束：所有结论必须来自真实代码证据；依赖关系必须可画出；不依赖具体技术栈

## 0. 文档使用说明

### 0.1 文档定位

本文档是「架构耦合专项审查标准库」，是审查体系 8 专项之一（见 `00-审查体系约定.md` §3）。

本专项覆盖结构与耦合审查 45 个指标：
- 项目目录的每一层职责划分与归位
- 文件的职责单一性、跨层混杂、命名一致性
- 模块入口、公开 API、内部泄漏、可独立理解性
- 依赖关系图、循环依赖、跨层依赖、反向依赖、深层依赖链
- 分层架构定义、依赖方向、核心层污染、跨层调用绕过
- 隐式通信（window/EventBus/localStorage/DOM dataset）与多入口（数据/状态/图层/路由）
- 代码资产（死代码、未消费 export、注释代码、重复实现、伪 shared）

本专项可与数据链专项、生命周期专项、TS 专项、WebGIS 专项、工程化专项并行执行，互不依赖结论，但可交叉引用指标编号。

### 0.2 与其他专项的边界

本专项**只管结构与耦合**：目录怎么分、文件职责清不清、模块边界明不明、依赖怎么连、分合不合、隐式通信、多入口、代码资产。

本专项**不管**以下内容（属于其他专项）：
- 类型覆盖率、any 治理、类型契约 → TS 专项（本专项仅在 2.5 关注命名与内容一致性这一结构层面）
- 变量作用域、对象销毁、响应式断链 → 生命周期专项（本专项仅在 6.6 关注状态修改入口是否收口）
- 数据来源真实性、数据转换链路、坐标系 → 数据链专项（本专项仅在 6.5 关注数据获取入口是否单一）
- 地图实例销毁、图层渲染性能 → WebGIS 专项（本专项仅在 6.7 关注图层控制入口是否收口）
- 构建配置、CI、Docker、安全 → 工程化专项

当本专项审查中发现跨域问题时，会标注「转 XX 专项」并标注目标专项（如「详见专项1 数据链」「详见专项2 生命周期」）。

**本专项专属领域**（其他专项不重复审查）：
- 目录与文件职责划分
- 模块边界与公开 API
- 文件级 / 模块级依赖图
- 循环依赖、跨层依赖、反向依赖、深层依赖链
- 分层架构定义与依赖方向
- core / shared 业务污染
- 隐式通信（window / EventBus / localStorage / DOM dataset）
- 多入口（数据获取 / 状态修改 / 图层控制 / 路由跳转）
- 死代码、未消费 export、重复实现、伪 shared

### 0.3 指标条目格式约定

每一个指标采用 `00-审查体系约定.md` §2 的 11 字段结构：

```
指标名称：该指标的唯一标识名
检查目标：这个指标要确认什么事实
为什么需要检查：不检查会带来什么风险
检查范围：该指标适用于哪些代码实体
检查方法：具体如何执行检查（步骤化）
需要查看：必须阅读哪些证据材料
正常标准：满足什么条件算通过
异常情况：出现什么现象算不通过
风险等级：P0 / P1 / P2 / P3
整改方向：发现问题后的修复路径
验收标准：整改完成后如何证明已修复
```

### 0.4 风险等级定义

见 `00-审查体系约定.md` §2，本专项不再重复定义，仅引用：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

本专项中以下情况直接判 P0：
- 文件级或模块级循环依赖（A→B→A）
- 循环依赖导致运行时 undefined 或初始化顺序错误
- 分层架构被破坏且已造成功能错误

本专项中以下情况直接判 P1：
- 跨层依赖（views 直连 utils 内部、views 直接 fetch）
- 反向依赖（core/shared 依赖 business）
- core/shared 层业务污染
- 组件直接改 store.state 绕过 action
- 隐式通信（window/EventBus/localStorage 跨模块）
- 多入口导致同一逻辑多头控制

### 0.5 本专项核心原则

**原则 1：结构即架构**
- 目录结构是项目架构的物理映射，目录混乱必然意味着架构混乱
- 任何架构问题最终都会在目录与文件职责上留下痕迹
- 审查架构必先审查结构

**原则 2：依赖单向流**
- 依赖方向必须单向向下（高层 → 低层，业务 → core → shared → utils）
- 任何反向依赖、循环依赖都是架构腐化的标志
- 同层模块之间不直接互依赖，应通过上层编排或 shared 抽取

**原则 3：核心不污染**
- core / shared / utils 层不得包含任何业务特定逻辑、业务字段名、业务规则
- 核心层被业务污染后丧失复用性，每次业务变更都要改核心
- 业务逻辑必须沉淀在业务层，核心层通过配置 / 插槽 / 注入接收业务

**原则 4：同层不互依**
- 同一抽象层的模块之间不应直接 import，避免形成同层依赖链 A→B→C→D
- 同层协作应通过上层编排或下沉公共能力到 shared
- 同层互依赖是「拔出一个模块带出一串」的根因

**原则 5：入口单一可追溯**
- 同一业务逻辑（数据获取、状态修改、图层控制、路由跳转）必须有单一控制入口
- 多入口必然导致「改了 A 入口 B 入口还在用旧逻辑」
- 跨模块通信必须通过显式机制（props / store / 事件总线文档化），禁止隐式通信

**原则 6：依赖可画出**
- 项目所有文件级与模块级依赖关系必须能用工具生成完整依赖图
- 无法画出依赖图的项目无法判断循环 / 跨层 / 反向依赖
- dependency-cruiser 等工具应作为架构守护的常态化配置

### 0.6 Agent 并行执行契约（2026-08-11 统一改造）

- **独立线程**：本专项可单独作为一条 agent 审查线程执行，与其余专项**零执行依赖**（支持 8 窗口并行）；跨专项交叉点见 0.2 边界表，仅在产出层面汇总，不在执行层面依赖。
- **输入**：本文档（可按「部分」切片，仅加载本子 agent 负责的部分）+ 对应代码范围 + 设计文档对应章节（见 `00-审查体系约定.md` §4「标准输入资产」，本专项映射：01 三.1/四/五.10/六；02 六）。
- **输出**：发现清单（每条含：指标编号 / 证据 file:line / 风险等级 / 整改建议）→ 写入 `docs/audits/<日期>-<批次名>/专项6-架构耦合审查-问题副本.md`（产出统一规范见 `00-审查体系约定.md` §4；副本规则见 docs/待解决问题.md 头部），经用户裁决转正主台账；执行记录存同批次目录 `专项6-架构耦合审查-执行记录.md`（模板见 §0.7）。
- **子 agent 拆分**：按「第 X 部分」切分（拆分规则见 `00-审查体系约定.md` §4：① 1 部分=1 子 agent；② 相邻部分证据重叠>50% 可合并；③ 单专项上限 6；④ 禁止二次拆分）。
  - 本专项 7 部分证据较独立，建议 **5–6 个**子 agent（目录+文件 合 1、模块边界 1、依赖 1、分层 1、隐式通信+代码资产 合 1）。
  - 每个子 agent 领 1 个切分单元独立执行（输入 = 该单元指标 + 对应代码），主 agent 汇总去重、合并同根因、统一定级。
- **格式约定**：结论必须来自真实代码证据（file:line）；指标编号用本文档编号（如 3.2）；跨专项引用写「专项N X.Y」；**禁止使用草稿/临时编号**（唯一合法编号 = 台账编号体系）。

## 第一部分：项目目录结构审查

> 目标：建立项目结构地图，回答「项目由哪些目录组成」「每个目录的真实职责是什么」「是否存在结构污染」
> 本部分是架构耦合审查的起点，结构不清则后续依赖与边界审查无意义

### 指标 1.1：顶层目录职责划分

**指标名称**：顶层目录职责划分
**检查目标**：确认项目顶层目录的划分符合清晰的职责边界，每个顶层目录都能用一句话说明职责，不存在职责交叉或混乱目录
**为什么需要检查**：顶层目录是项目认知的第一入口，混乱的顶层目录会让新人无法快速定位代码，也会让模块边界从源头模糊，最终导致「同一类功能散落在多处」「同一目录承载多种职责」；顶层混乱往往向下传染到子目录
**检查范围**：项目根目录、前端 src 顶层、后端源码顶层、配置目录、工具脚本目录、文档目录
**检查方法**：
1. 列出项目根目录与 src 目录的全部顶层目录
2. 为每个顶层目录标注「声明职责」（从目录名推断）与「实际职责」（从内部文件内容推断）
3. 对比声明职责与实际职责是否一致，标注不一致项
4. 检查是否存在以下反模式：临时目录混入源码区、备份目录与业务目录平级、配置散落在多个顶层目录
5. 检查顶层目录数量是否合理（过少=万能目录，过多=职责过度拆分）
6. 输出「顶层目录职责对照表」
**需要查看**：项目根目录树、src 目录树、各顶层目录下的文件清单、README、构建配置中的路径别名
**正常标准**：
- 每个顶层目录都能用一句话说清楚职责
- 目录命名与内部文件内容一致
- 业务代码、测试代码、mock 数据、工具脚本、配置文件各自归位到独立顶层目录
- 顶层目录数量在合理范围（前端 src 通常 5-12 个，过多过少都需说明）
- 不存在职责重叠的顶层目录（如同时有 utils 和 helpers）
**异常情况**：
- 一个顶层目录同时承载控制器、服务、数据、工具类（万能目录）
- 存在职责重叠的目录（utils 与 helpers 并存且职责模糊）
- 业务代码与配置文件混在同一顶层目录
- 顶层目录数量异常（src 下超过 20 个或仅 1-2 个）
- 顶层目录命名含 `_backup`、`_tmp`、`_old`、`copy` 等临时后缀
**风险等级**：P2
**整改方向**：按职责重新归位顶层目录；合并职责重叠目录；临时/备份目录迁移至项目外或归档目录
**验收标准**：顶层目录职责对照表完整；每个顶层目录职责唯一且与内容一致；无职责重叠目录

### 指标 1.2：子目录职责单一性

**指标名称**：子目录职责单一性
**检查目标**：确认每个子目录只承载单一职责，不存在「子目录承载多种不相关职责」的情况
**为什么需要检查**：子目录是模块的物理边界，子目录职责混杂意味着模块边界从源头就模糊；一个子目录同时放 service、组件、utils 会让该目录无法被独立理解和复用
**检查范围**：所有顶层目录下的直接子目录、业务模块目录、core 目录下的子模块
**检查方法**：
1. 对每个顶层目录，列出其全部子目录
2. 为每个子目录标注职责（从内部文件类型与内容推断）
3. 检查子目录内是否存在多种不相关类型的文件（如 components 目录里混入 service 文件）
4. 检查子目录是否可以被一句话描述职责
5. 检查子目录命名与内部文件是否一致
6. 重点检查业务模块目录：是否同时混入其他模块的文件
**需要查看**：各子目录文件清单、子目录命名、文件类型分布
**正常标准**：
- 每个子目录能被一句话描述职责
- 子目录内文件类型一致（components 目录只有组件，services 目录只有 service）
- 子目录命名与内部文件内容一致
- 业务模块子目录不混入其他模块文件
**异常情况**：
- components 子目录里混入 api 请求文件
- services 子目录里混入 UI 组件
- 某子目录内同时有 .vue、.ts 工具、.json 数据、配置文件
- 业务模块 A 的子目录里出现业务模块 B 的文件
- 子目录命名含 `_misc`、`_others`、`_etc` 等模糊后缀
**风险等级**：P2
**整改方向**：按文件类型与职责重新归位子目录内容；混入文件迁回所属模块
**验收标准**：每个子目录职责单一；文件类型一致；无跨模块文件混入

### 指标 1.3：临时/备份目录污染检查

**指标名称**：临时/备份目录污染检查
**检查目标**：确认源码区不存在 `_backup`、`_tmp`、`_old`、`copy`、`_v2`、`_bak` 等临时/备份目录污染
**为什么需要检查**：临时/备份目录是「墓碑代码」的主要藏身处，它们会被构建工具打包进产物、被 IDE 索引、被新人误以为是有效代码；这些目录还会在搜索时产生大量噪音，干扰真实代码定位
**检查范围**：整个项目目录树，重点搜索源码区（src、server、app 等）
**检查方法**：
1. 全局搜索目录名匹配以下模式的目录：`_backup`、`_tmp`、`_old`、`copy`、`_v2`、`_bak`、`backup`、`tmp`、`old`、`_archive`、`_deprecated`、`_unused`
2. 检查每个匹配目录的位置：是否在源码区内（src 下、server 下）
3. 检查匹配目录的内容：是否包含 .ts/.js/.vue/.py 等源码文件
4. 检查构建配置（webpack/vite/tsconfig）是否将这些目录排除在编译范围外
5. 检查 .gitignore 是否忽略了这些目录
6. 检查文件名是否含 `_old`、`_v2`、`_backup`、`_bak`、`_copy`、`_deprecated`、`_unused` 后缀
**需要查看**：目录树、构建配置的 include/exclude、.gitignore、文件名清单
**正常标准**：
- 源码区内无任何 `_backup`、`_tmp`、`_old`、`copy` 等临时/备份目录
- 源码区内无任何带 `_old`、`_v2`、`_backup`、`_bak`、`_copy` 后缀的文件
- 历史代码通过 git 历史保留而非通过备份目录保留
- 构建配置明确排除非源码目录
**异常情况**：
- src 下存在 `components_backup/`、`utils_old/`、`api_v2/` 等目录
- 源码文件名含 `_old.ts`、`_v2.vue`、`_backup.js` 后缀
- 备份目录被构建工具纳入编译范围（未排除）
- 备份目录被 git 跟踪并提交
- 同一文件存在 `xxx.ts` 与 `xxx_old.ts` 两个版本
**风险等级**：P2
**整改方向**：删除所有临时/备份目录与文件；历史代码通过 git 历史或分支保留；构建配置明确排除非源码区
**验收标准**：源码区无临时/备份目录与文件；构建产物不含备份代码；git 已清理跟踪

### 指标 1.4：mock 数据归位检查

**指标名称**：mock 数据归位检查
**检查目标**：确认 mock 数据、fixture 数据、测试数据统一归位到独立的 mock / fixtures 目录，未散落在业务源码目录
**为什么需要检查**：mock 数据散落在业务目录会让维护者误以为是真实数据，导致「以为是真数据其实是 mock」「上线后数据消失」；散落的 mock 还会污染构建产物与搜索结果
**检查范围**：所有源码目录，重点检查业务模块目录、components、services、utils
**检查方法**：
1. 全局搜索文件名含 `mock`、`fake`、`dummy`、`fixture`、`test-data`、`sample`、`demo` 的文件
2. 全局搜索代码内含 `mock`、`fake`、`dummy`、`测试数据`、`示例数据` 等关键字的文件
3. 检查每个匹配文件的位置：是否在业务源码目录而非独立 mock / fixtures 目录
4. 检查项目是否有统一的 mock 目录（如 `src/mock/`、`__mocks__/`、`fixtures/`）
5. 检查 mock 数据是否通过环境开关隔离（开发环境启用、生产环境排除）
6. 检查静态 JSON 数据文件是否含测试条目（如 name 字段为「测试」「test」「示例」）
**需要查看**：文件清单、文件内容、mock 目录结构、构建配置的环境隔离、.env 配置
**正常标准**：
- mock / fixture 数据统一收口到独立 mock 目录
- 业务源码目录无 mock 数据文件
- mock 数据通过环境开关隔离，生产构建排除
- 静态数据文件为真实业务数据，无测试条目
- mock 与真实 service 接口签名一致（便于切换）
**异常情况**：
- 业务模块目录下存在 `mockData.ts`、`fakeResponse.json` 等文件
- components 目录下有 `demoData.ts`
- mock 数据未通过环境隔离，生产构建仍包含
- 静态 JSON 含「测试」「test」「示例」「demo」字样
- 同一数据有 mock 版本与真实版本且无切换机制
**风险等级**：P1
**整改方向**：mock 数据统一收口到 mock 目录；通过环境开关隔离；静态数据清洗测试条目；mock 与真实接口对齐
**验收标准**：业务源码目录无 mock 文件；mock 统一归位且环境隔离；静态数据为真实数据

### 指标 1.5：文档与代码目录混杂检查

**指标名称**：文档与代码目录混杂检查
**检查目标**：确认文档（md、txt、doc）与源码目录分离，不存在文档混入源码目录污染结构
**为什么需要检查**：文档混入源码目录会让目录结构变混乱，IDE 索引与搜索时产生噪音；文档与代码混在一起也意味着文档随代码一起被构建工具扫描，影响构建性能
**检查范围**：所有源码目录，重点检查 src、server、app 下的文档文件
**检查方法**：
1. 全局搜索源码目录下的 `.md`、`.txt`、`.doc`、`.docx`、`.pdf` 文件
2. 检查每个文档文件的位置：是否在源码目录内而非独立 docs 目录
3. 检查文档内容：是设计文档、临时笔记、还是说明文档
4. 检查项目是否有独立的 docs 目录
5. 检查 README 文件是否合理放置（根目录与各模块根目录可放 README）
6. 检查构建配置是否将文档排除在编译范围外
**需要查看**：文件清单、文档内容、docs 目录结构、构建配置
**正常标准**：
- 设计文档、需求文档、说明文档统一归位到独立 docs 目录
- 源码目录内仅允许 README.md 作为模块说明
- 文档不进入构建产物
- 文档目录与代码目录物理分离
**异常情况**：
- src 下存在 `设计文档.md`、`需求.txt`、`说明.docx`
- 业务模块目录混入非 README 文档
- 文档被构建工具纳入扫描范围
- 同一项目有多个散落的文档目录无统一管理
**风险等级**：P3
**整改方向**：文档统一迁移到 docs 目录；源码目录仅保留 README；构建配置排除文档
**验收标准**：源码目录无非 README 文档；文档统一归位；构建不扫描文档

### 指标 1.6：配置文件归位检查

**指标名称**：配置文件归位检查
**检查目标**：确认配置文件（环境配置、构建配置、运行时配置）归位合理，不存在配置散落在多个目录或混入源码目录
**为什么需要检查**：配置散落会让「修改一个配置需要找遍全项目」；配置混入源码会让目录职责不清；环境配置不一致会导致开发与生产行为差异
**检查范围**：所有配置文件，包括 `.env`、`config.*`、`*.config.*`、构建配置、运行时配置
**检查方法**：
1. 全局搜索配置文件：`.env*`、`config.ts`、`config.js`、`*.config.ts`、`*.config.js`、`config.json`
2. 检查每个配置文件的位置：是否在合理位置（根目录或独立 config 目录）
3. 检查是否存在多份环境配置（.env.development、.env.production）且无 example 模板
4. 检查业务模块目录内是否混入配置文件
5. 检查配置项是否硬编码在源码中（应配置化的项却写死在代码里）
6. 检查是否有 .env.example 作为环境配置模板
**需要查看**：配置文件清单、配置文件位置、.env.example、构建配置、源码中的硬编码配置
**正常标准**：
- 环境配置统一在根目录或 config 目录
- 有 .env.example 模板且不含真实密钥
- 业务模块目录无配置文件
- 配置项不硬编码在源码中
- 不同环境配置分离且通过环境变量切换
**异常情况**：
- 业务模块目录内存在 config.ts
- 多个目录各有一份 config 文件且无统一管理
- 配置项硬编码在源码中（如 API base URL 写死在 service 里）
- 无 .env.example 模板
- 真实密钥硬编码在配置文件中并提交到 git
**风险等级**：P2
**整改方向**：配置统一归位到 config 目录；建立 .env.example；硬编码配置提取到配置文件；密钥移除并改用环境变量
**验收标准**：配置统一归位；有 example 模板；无硬编码配置；无密钥入库

## 第二部分：文件职责审查

> 目标：建立文件级职责数据库，回答「每个文件到底干什么」「是否存在万能文件」「文件是否跨层混杂」
> 本部分承接第一部分目录结构，深入到文件级别

### 指标 2.1：文件职责单一性

**指标名称**：文件职责单一性
**检查目标**：确认每个源码文件只承担一个明确职责，不存在「万能文件」或「职责混杂文件」
**为什么需要检查**：一个文件承担多个职责会导致修改牵连面扩大、测试困难、复用困难，是架构腐化的最常见起点；职责混杂的文件往往是「改一处坏一片」的高发区
**检查范围**：所有 `.js`、`.ts`、`.vue`、`.py`、`.java` 源码文件
**检查方法**：
1. 读取每个文件的顶部声明与导出列表
2. 用一句话描述该文件职责
3. 若无法用一句话描述，或一句话里出现「和」「以及」「同时」「并且」等连接词，标记为可疑
4. 检查文件是否同时包含：数据获取 + 业务计算 + UI 渲染 + 状态管理中的多项
5. 检查文件导出是否包含多个不相关的功能（如同时导出格式化函数与请求函数）
6. 对可疑文件输出「职责混杂文件清单」
**需要查看**：文件内容、导出列表、import 关系、文件行数
**正常标准**：
- 每个文件能被一句话描述职责
- 单文件不跨越「数据层 / 逻辑层 / 表现层 / 状态层」中的两个以上
- 文件导出围绕单一主题
- 文件行数控制在合理范围（建议 < 400 行，超过需说明理由）
**异常情况**：
- 文件同时处理 API 请求、数据转换、UI 渲染
- 文件既是路由定义又是控制器实现又是业务逻辑
- 文件导出包含多个不相关功能（如同时导出 `formatDate` 与 `fetchUser`）
- 一句话描述需用「和」「以及」连接多个动作
- 单文件超过 800 行且无明显单一主题
**风险等级**：P1
**整改方向**：按职责拆分文件；提取公共逻辑到独立模块；万能文件按主题拆分
**验收标准**：每个文件能用一句话描述职责；不跨层；导出围绕单一主题

### 指标 2.2：超大文件识别

**指标名称**：超大文件识别
**检查目标**：识别行数异常的文件，这些文件通常是职责膨胀或维护负担的集中点
**为什么需要检查**：超大文件几乎必然承担过多职责，难以测试、难以复用、难以修改，是技术债的高发区；超过 1000 行的非配置文件几乎都有拆分空间
**检查范围**：所有源码文件（不含配置文件、类型定义文件、测试文件、自动生成文件）
**检查方法**：
1. 统计每个源码文件行数（排除空行与注释行可选）
2. 按行数降序排列，输出 Top 30 大文件清单
3. 标记超过阈值的文件：500 行（关注）、800 行（警告）、1000 行（严重）
4. 对每个超大文件判断：是合理的单一职责大文件（如配置表、类型定义、测试用例），还是职责膨胀
5. 对职责膨胀的大文件，标注其包含的职责数量
6. 重点关注 Vue 单文件组件（template + script + style 合计）
**需要查看**：文件行数统计、文件内容、文件类型
**正常标准**：
- 超过 500 行的文件有合理理由（如类型定义、配置常量、测试用例）
- 业务逻辑文件普遍在 400 行以内
- 不存在超过 1000 行的非配置/非类型文件
- Vue 单文件组件普遍在 400 行以内（含 template + script + style）
**异常情况**：
- 业务逻辑文件超过 800 行
- 单个 Vue 组件超过 600 行（template + script + style）
- 超大文件且职责混杂（配合 2.1 判断）
- Top 10 大文件中有多个业务逻辑文件
- 存在超过 1500 行的文件且非自动生成
**风险等级**：P2
**整改方向**：拆分为多个职责单一的文件；大组件拆分为子组件 + composable；配置表拆分为多个常量文件
**验收标准**：超大文件清单有处置结论；保留的大文件有合理理由说明；业务逻辑文件普遍 < 400 行

### 指标 2.3：万能文件识别

**指标名称**：万能文件识别（utils/helper/common/index 职责混杂）
**检查目标**：识别命名为 `utils`、`helper`、`common`、`index`、`misc`、`tools` 但内部职责混杂的「万能文件」
**为什么需要检查**：万能文件是「什么都往里塞」的垃圾桶，随时间推移会膨胀到无法维护；这类文件往往成为整个项目的耦合中心，被几十处 import，修改风险极高
**检查范围**：所有命名为 `utils.*`、`helper.*`、`helpers.*`、`common.*`、`index.*`、`misc.*`、`tools.*` 的文件
**检查方法**：
1. 全局搜索命名为 utils、helper、helpers、common、index、misc、tools 的文件
2. 统计每个万能文件的行数、导出数量、被引用次数
3. 检查导出内容是否围绕多个不相关主题（如同时有日期格式化、金额计算、深拷贝、防抖）
4. 检查导出函数的归属领域：是否属于同一领域（如都是日期工具）还是跨领域混杂
5. 检查万能文件是否被全项目广泛 import（被引用次数 > 10 标记为高风险耦合中心）
6. 对每个万能文件输出「职责拆分建议」
**需要查看**：万能文件内容、导出清单、被引用次数、import 关系
**正常标准**：
- 万能文件已按主题拆分（如 `dateUtils.ts`、`mathUtils.ts`、`domUtils.ts`）
- 或 utils 目录下有多个职责单一的子文件，index 仅做聚合导出
- 单个 utils 文件不超过 200 行
- 导出内容围绕单一主题
**异常情况**：
- 存在 `utils.ts` 同时导出日期、金额、深拷贝、防抖、节流等不相关函数
- `common.ts` 行数超过 300 行且导出超过 20 个不相关函数
- `index.ts` 既做聚合导出又包含具体实现
- 万能文件被全项目几十处 import（耦合中心风险）
- 同一功能在多个 utils 文件中重复实现
**风险等级**：P2
**整改方向**：按主题拆分万能文件为多个职责单一的文件；index 仅做聚合导出不含实现；高频引用的函数考虑下沉到 shared
**验收标准**：无职责混杂的万能文件；utils 按主题拆分；单文件不超过 200 行；index 仅聚合

### 指标 2.4：文件跨层检查

**指标名称**：文件跨层检查（单文件跨数据/逻辑/表现/状态层）
**检查目标**：确认单个文件不跨越多个架构层（数据层、逻辑层、表现层、状态层），不存在「一个文件干完所有层的事」
**为什么需要检查**：文件跨层是分层架构被破坏的最小单元；一个文件同时处理请求、状态、渲染会让该文件无法被独立测试与复用，也使分层形同虚设
**检查范围**：所有源码文件，重点检查 Vue 组件、composable、service 文件
**检查方法**：
1. 定义项目的架构层（如：数据层 service / 逻辑层 utils / 表现层 components / 状态层 store）
2. 对每个文件，标注其所属层（从文件类型与内容推断）
3. 检查文件内是否同时包含多层的代码：
   - 数据层代码：fetch、axios、API 调用
   - 逻辑层代码：业务计算、转换、校验
   - 表现层代码：模板、样式、DOM 操作
   - 状态层代码：store 读写、state 修改
4. 对跨层文件标注其跨越的层组合
5. 重点关注 Vue 组件：是否在组件内直接发请求 + 改 store + 做业务计算
**需要查看**：文件内容、文件类型、import 关系、架构层定义
**正常标准**：
- 单文件只属于一个架构层
- Vue 组件不包含数据获取与业务计算（通过 composable / service 委托）
- service 文件不包含 UI 逻辑
- store 文件不包含请求实现（请求在 service，store 调用 service）
**异常情况**：
- Vue 组件内同时有 fetch、store 修改、业务计算、模板渲染
- service 文件内包含 DOM 操作或 UI 逻辑
- store 文件内直接实现 fetch 而非调用 service
- 一个 composable 同时管理请求、状态、路由跳转
**风险等级**：P1
**整改方向**：按层拆分文件；数据获取移到 service；业务计算移到 composable 或 utils；状态管理移到 store
**验收标准**：单文件不跨层；Vue 组件仅含表现层；service 仅含数据层；store 仅含状态层

### 指标 2.5：文件命名与内容一致性

**指标名称**：文件命名与内容一致性
**检查目标**：确认文件名能准确反映文件内容，不存在「文件名与内容不符」的情况
**为什么需要检查**：文件名是定位代码的主要线索，名实不符会让维护者被误导；如 `userUtils.ts` 实际包含订单逻辑，会让人在找用户工具时错过、找订单逻辑时找不到
**检查范围**：所有源码文件
**检查方法**：
1. 列出所有源码文件名
2. 对每个文件，对比文件名暗示的职责与实际内容
3. 检查是否存在以下反模式：
   - 文件名含 `utils` 但实际是业务逻辑
   - 文件名含 `service` 但实际是 UI 组件
   - 文件名含 `component` 但实际是工具函数
   - 文件名含 `model` 但实际是视图
4. 检查文件名拼写是否规范（驼峰、短横线、下划线是否统一）
5. 检查同一类文件命名是否一致（如所有 service 文件都是 `xxxService.ts` 或都是 `xxx.service.ts`）
**需要查看**：文件名清单、文件内容、命名约定文档
**正常标准**：
- 文件名准确反映内容
- 命名风格统一（全项目同一类文件命名规则一致）
- 文件名不含误导性词汇
- 文件名与导出主实体名称对应
**异常情况**：
- `userUtils.ts` 实际包含订单业务逻辑
- `userService.ts` 实际是 Vue 组件
- `dataModel.ts` 实际是 API 请求函数
- 同一项目 service 文件有的叫 `userService.ts` 有的叫 `user-service.ts` 有的叫 `UserApi.ts`
- 文件名拼写风格不统一（驼峰与短横线混用）
**风险等级**：P3
**整改方向**：重命名名实不符的文件；统一命名约定；建立命名规范文档
**验收标准**：文件名与内容一致；命名风格统一；有名实不符清单的处置结论

## 第三部分：模块边界审查

> 目标：判断每个模块是否有清晰边界，回答「模块的入口在哪」「公开 API 是什么」「内部实现是否泄漏」「能否独立理解」
> 本部分承接文件职责，上升到模块级别

### 指标 3.1：模块入口文件存在性

**指标名称**：模块入口文件存在性
**检查目标**：确认每个模块（业务模块、core 模块、shared 模块）都有明确的入口文件（index.ts / mod.ts / __init__.py）
**为什么需要检查**：模块没有入口文件意味着外部可以直接深入到模块内部任意路径 import，模块边界形同虚设；入口文件是模块封装的第一道防线
**检查范围**：所有业务模块目录、core 模块目录、shared 模块目录、services 目录
**检查方法**：
1. 列出所有模块目录（含业务模块、core、shared、services）
2. 检查每个模块目录是否有入口文件（index.ts、index.js、mod.ts、__init__.py）
3. 检查入口文件是否做了聚合导出（re-export 模块对外公开的 API）
4. 检查外部是否通过入口文件 import 还是直接深入模块内部路径 import
5. 全局搜索 `from '.*/modules/[^/]*/[^/]*'` 这类跨过 index 的深路径 import
6. 对无入口的模块标注「无入口」并记录外部直接深入 import 的次数
**需要查看**：模块目录结构、入口文件内容、外部 import 语句、构建配置的路径别名
**正常标准**：
- 每个模块都有入口文件
- 入口文件聚合导出模块公开 API
- 外部 import 通过入口文件而非深入内部路径
- 路径别名指向模块入口而非内部文件
**异常情况**：
- 模块目录无 index.ts / 入口文件
- 外部直接 import `modules/user/components/UserPanel.vue` 这类深路径
- 入口文件存在但为空或未聚合导出
- 路径别名直接指向模块内部文件
- 同一模块有多个入口且职责不清
**风险等级**：P1
**整改方向**：为无入口模块建立 index.ts；聚合导出公开 API；外部 import 收口到入口；路径别名指向入口
**验收标准**：每个模块有入口；外部 import 经入口；无深路径 import

### 指标 3.2：模块公开 API 清晰性

**指标名称**：模块公开 API 清晰性
**检查目标**：确认每个模块的公开 API（export）清晰、最小化、有文档说明，不存在「导出过多内部细节」
**为什么需要检查**：公开 API 是模块与外部的契约，导出过多内部细节会让外部依赖内部实现，模块重构时牵连面巨大；清晰的公开 API 是模块可维护性的基础
**检查范围**：所有模块的入口文件与导出清单
**检查方法**：
1. 列出每个模块入口文件的导出（export）清单
2. 检查每个导出是否属于「公开 API」还是「内部实现泄漏」
3. 判断标准：导出的函数/类型/常量是否被外部模块使用，是否属于模块核心职责
4. 检查公开 API 是否有类型标注与文档说明
5. 检查公开 API 数量是否合理（过多=未做收敛，过少=可能内部实现被直接深入访问）
6. 检查是否有「导出了但无外部消费者」的项（未消费 export，详见 7.2）
**需要查看**：模块入口文件、导出清单、外部 import 关系、类型定义、文档
**正常标准**：
- 公开 API 清晰且最小化（仅导出外部需要的）
- 每个公开 API 有类型标注
- 公开 API 有文档说明（JSDoc 或 README）
- 无内部实现细节泄漏到公开 API
- 公开 API 都有外部消费者
**异常情况**：
- 模块导出几十个函数/类型（未做收敛）
- 导出的函数明显是内部工具（如 `__internalHelper`）
- 公开 API 无类型标注
- 导出的项无任何外部消费者
- 公开 API 与内部实现混在同一文件无分离
**风险等级**：P2
**整改方向**：收敛公开 API 到最小集；内部实现不导出或导出到 internal 子目录；补全类型与文档
**验收标准**：公开 API 最小化；有类型与文档；无内部泄漏；所有公开 API 有消费者

### 指标 3.3：模块内部实现泄漏

**指标名称**：模块内部实现泄漏
**检查目标**：确认模块内部实现细节（私有函数、内部工具、内部类型）没有被外部模块直接 import
**为什么需要检查**：内部实现泄漏会让外部模块依赖内部细节，模块重构时外部会因依赖内部而破坏；这是模块封装失效的核心标志
**检查范围**：所有模块的内部文件、内部导出、外部 import 关系
**检查方法**：
1. 列出每个模块的内部文件（非入口文件）
2. 全局搜索是否有外部模块直接 import 这些内部文件
3. 检查模块内部文件是否有 export 被外部使用（应通过入口聚合而非直接访问）
4. 检查是否有「内部工具函数」被外部模块使用（如模块内的 `utils.ts` 被外部 import）
5. 检查是否有「内部类型」被外部直接 import（应通过入口 re-export）
6. 输出「内部实现泄漏清单」
**需要查看**：模块内部文件清单、外部 import 语句、入口文件导出
**正常标准**：
- 外部模块不直接 import 模块内部文件
- 内部实现通过入口聚合导出（如需对外）
- 内部工具函数不对外暴露
- 内部类型通过入口 re-export（如需对外）
**异常情况**：
- 外部直接 import `modules/user/utils/formatName`（绕过入口）
- 模块内 `helpers.ts` 被多个外部模块使用
- 内部类型被外部直接 import 而非通过入口
- 模块内组件被外部直接深入访问而非通过入口
**风险等级**：P1
**整改方向**：外部 import 收口到入口；内部实现如需对外则通过入口 re-export；纯内部的不导出
**验收标准**：无外部直接 import 内部文件；内部实现对封装；如需对外经入口

### 指标 3.4：模块可独立理解性

**指标名称**：模块可独立理解性
**检查目标**：确认每个模块可以被独立理解——只看模块的公开 API 与依赖，能否说清楚它做什么、不依赖理解其他模块的内部细节
**为什么需要检查**：模块无法独立理解意味着修改一个功能需要先理解整个系统，维护成本指数级上升；可独立理解是模块化的核心价值
**检查范围**：所有业务模块、core 模块、shared 模块
**检查方法**：
1. 对每个模块，仅阅读其入口文件、公开 API、依赖列表
2. 尝试用一段话描述模块的职责、输入、输出
3. 检查描述是否需要引用其他模块的内部细节
4. 检查模块是否有 README 或文档说明
5. 检查模块的依赖是否清晰（依赖哪些外部模块、core、shared）
6. 检查模块是否有隐式依赖（通过 window、EventBus、localStorage 等隐式通信，详见第六部分）
**需要查看**：模块入口、公开 API、依赖列表、README、隐式通信使用
**正常标准**：
- 每个模块能被一段话独立描述
- 描述不需要引用其他模块内部细节
- 模块有 README 或入口注释说明
- 依赖清晰且显式（无隐式依赖）
- 模块可被「拔出」单独理解
**异常情况**：
- 描述模块职责必须先解释另一模块的内部实现
- 模块无文档且入口无注释
- 模块有隐式依赖（通过 window/EventBus 通信）
- 模块依赖链过深导致无法独立理解（A 依赖 B 依赖 C 依赖 D）
- 模块职责描述需要超过 3 句话
**风险等级**：P2
**整改方向**：补全模块文档；显式化隐式依赖；收敛依赖链；模块入口加注释说明职责
**验收标准**：每个模块有文档或入口注释；能被独立描述；依赖显式

### 指标 3.5：同层模块互依赖

**指标名称**：同层模块互依赖
**检查目标**：确认同一抽象层的业务模块之间不直接互依赖（业务模块 A 不直接 import 业务模块 B）
**为什么需要检查**：同层模块互依赖会形成同层依赖链 A→B→C→D，导致「拔出一个模块带出一串」；同层互依赖还容易演变为循环依赖 A→B→A
**检查范围**：所有业务模块之间的 import 关系、所有 core 模块之间的 import 关系
**检查方法**：
1. 列出所有业务模块（如 flood-analysis、forecast、site-selection）
2. 对每个业务模块，检查其是否 import 其他业务模块
3. 全局搜索业务模块间的 import 语句
4. 检查是否形成同层依赖链（A→B→C→D）
5. 检查是否有「互相依赖」的苗头（A import B，B import A 的子集）
6. 对同层依赖，判断是否可通过上层编排或 shared 抽取解决
**需要查看**：业务模块 import 关系、依赖图、shared 模块清单
**正常标准**：
- 业务模块之间不直接互依赖
- 同层协作通过上层编排（页面/路由层调用多个业务模块）
- 公共能力下沉到 shared 层
- 无同层依赖链 A→B→C→D
**异常情况**：
- 业务模块 A 直接 import 业务模块 B 的组件/工具/类型
- 多个业务模块互相 import 形成同层依赖链
- 业务模块 A import B，B import A（循环依赖苗头）
- 同层模块通过 shared 之外的隐式方式协作
**风险等级**：P1
**整改方向**：同层协作改为上层编排；公共能力下沉到 shared；如必须依赖则合并模块或显式声明依赖关系
**验收标准**：业务模块间无直接 import；同层协作经上层编排；无同层依赖链

### 指标 3.6：模块依赖链深度

**指标名称**：模块依赖链深度
**检查目标**：确认模块的依赖链深度合理，不存在 A→B→C→D→E 这种过深的依赖链
**为什么需要检查**：依赖链过深意味着修改底层模块会影响整条链，影响面难以预估；深层依赖也是「理解一个模块要先理解一长串模块」的根因
**检查范围**：所有模块的依赖链
**检查方法**：
1. 基于依赖图，计算每个模块的最长依赖链长度
2. 标记依赖链深度超过 4 的模块
3. 检查深层依赖链的每一跳是否合理（是否可简化）
4. 检查是否存在「中间层无意义」的情况（A→B→C 但 B 只是转发）
5. 检查深层依赖是否因同层互依赖导致（与 3.5 关联）
6. 输出「模块依赖链深度排行」
**需要查看**：依赖图、模块依赖关系、最长依赖链路径
**正常标准**：
- 模块依赖链深度普遍 ≤ 4
- 业务模块依赖链：业务 → core → shared → utils（深度 3-4）
- 无过深的依赖链（深度 > 5）
- 每一跳依赖都有明确意义（非无意义转发）
**异常情况**：
- 存在深度 > 5 的依赖链
- 依赖链中有「无意义中间层」（B 只转发 A 到 C）
- 业务模块依赖链穿过多个业务模块
- 依赖链中有环（与 4.2 循环依赖关联）
**风险等级**：P2
**整改方向**：简化依赖链；移除无意义中间层；深层依赖通过接口抽象或依赖倒置解决
**验收标准**：依赖链深度普遍 ≤ 4；无无意义中间层；有深度排行与处置结论

## 第四部分：依赖关系审查

> 目标：还原项目真实依赖图，回答「文件之间怎么连」「有没有环」「有没有跨层」「有没有反向」
> 本部分是架构耦合审查的核心，依赖关系是架构的骨架

### 指标 4.1：文件级依赖图生成

**指标名称**：文件级依赖图生成
**检查目标**：确认项目能够生成完整的文件级依赖图，所有 import 关系都被可视化
**为什么需要检查**：依赖图是判断循环依赖、跨层依赖、反向依赖的基础；无法生成依赖图意味着无法系统性分析架构，只能靠人工抽查
**检查范围**：所有源码文件的 import / require 关系
**检查方法**：
1. 选择依赖分析工具（dependency-cruiser、madge、dependency-tree）
2. 配置工具扫描项目全部源码文件
3. 生成依赖图（DOT 格式或可视化图）
4. 检查依赖图是否覆盖全部源码文件（无遗漏）
5. 检查依赖图是否正确解析路径别名（@/、~/ 等）
6. 检查依赖图是否包含动态 import（import()）与静态 import
7. 输出依赖图文件与统计信息（文件数、依赖边数、平均依赖数）
**需要查看**：依赖分析工具配置、生成的依赖图、路径别名配置、import 语句
**正常标准**：
- 能生成覆盖全部源码文件的依赖图
- 依赖图正确解析路径别名
- 依赖图包含静态与动态 import
- 依赖图无遗漏文件
- 有依赖统计信息（文件数、边数、平均依赖数）
**异常情况**：
- 无法生成依赖图（工具未配置或失败）
- 依赖图遗漏部分文件（路径别名未解析）
- 依赖图未包含动态 import
- 依赖图与实际 import 关系不一致
- 无依赖分析工具配置
**风险等级**：P1
**整改方向**：配置 dependency-cruiser 或同类工具；正确解析路径别名；纳入动态 import；定期生成依赖图
**验收标准**：依赖图覆盖全部源码文件；路径别名解析正确；有依赖统计

### 指标 4.2：循环依赖检测

**指标名称**：循环依赖检测（A→B→A）
**检查目标**：确认项目无任何文件级或模块级循环依赖
**为什么需要检查**：循环依赖导致初始化顺序问题、打包问题、运行时 undefined；这是架构耦合中最严重的问题，会直接导致功能错误
**检查范围**：所有源码文件的 import 关系
**检查方法**：
1. 用 dependency-cruiser 的 `circular` 规则检测循环依赖
2. 检查文件级循环（A.ts → B.ts → A.ts）
3. 检查模块级循环（业务模块 A 的入口 import 业务模块 B 的入口，反之亦然）
4. 检查间接循环（A→B→C→A）
5. 对每个循环依赖，标注循环路径与涉及的文件
6. 检查循环依赖是否导致运行时问题（运行时 undefined、初始化失败）
7. 检查是否有「自我依赖」（A.ts import A.ts）
**需要查看**：dependency-cruiser 报告、依赖图、循环路径、运行时错误日志
**正常标准**：
- 无任何文件级循环依赖
- 无任何模块级循环依赖
- 无间接循环（A→B→C→A）
- 无自我依赖
- dependency-cruiser circular 规则通过
**异常情况**：
- 存在文件级循环 A→B→A
- 存在模块级循环（业务模块互相 import 入口）
- 存在间接循环 A→B→C→A
- 循环依赖导致运行时 undefined
- 循环依赖导致打包警告或失败
- 存在自我依赖（A import A）
**风险等级**：P0
**整改方向**：通过接口抽取打破循环（A 和 B 都依赖接口 I 而非互依赖）；通过依赖倒置（高层定义接口，低层实现）；通过公共层下沉（A 和 B 的公共部分下沉到 shared）；通过事件解耦（A 不直接调 B，改用事件通知）
**验收标准**：dependency-cruiser circular 规则零告警；无运行时循环相关问题；依赖图无环

### 指标 4.3：跨层依赖检测

**指标名称**：跨层依赖检测
**检查目标**：确认不存在绕过中间层的跨层调用（如 views 直接 import utils 内部、views 直接调 store 内部实现）
**为什么需要检查**：跨层调用破坏分层架构，让中间层形同虚设；跨层调用还会让修改底层直接影响高层，影响面失控
**检查范围**：所有跨层 import 关系，重点检查 views → utils、views → store 内部、components → repository
**检查方法**：
1. 定义项目分层（如 views → services → core → shared → utils）
2. 检查每一层的 import 是否只指向直接下层（或同层合规范围）
3. 检查是否有「跨多层」import（如 views 直接 import utils 内部，绕过 services 与 shared）
4. 检查 views 是否直接 import store 的内部实现（应通过 store 的公开 API）
5. 检查 components 是否直接 import repository（应通过 service）
6. 输出「跨层依赖清单」
**需要查看**：分层定义、import 关系、依赖图、各层入口
**正常标准**：
- 调用遵循分层，不跨层
- views 通过 service 获取数据
- views 通过 store 公开 API 访问状态
- components 通过 service / composable 获取数据
- 无跨多层 import
**异常情况**：
- views 直接 import utils 内部工具（绕过 services/shared）
- views 直接 import store 的内部 mutation（绕过 action）
- components 直接 import repository（绕过 service）
- 存在跨多层 import（views → utils，跨过 services、shared）
- 跨层 import 涉及内部实现而非公开 API
**风险等级**：P1
**整改方向**：补全中间层；跨层调用收口到分层入口；通过公开 API 访问
**验收标准**：无跨层 import；调用遵循分层；通过公开 API 访问

### 指标 4.4：反向依赖检测

**指标名称**：反向依赖检测（下层依赖上层）
**检查目标**：确认依赖方向单向向下，不存在下层依赖上层的反向依赖（如 core import business、shared import business、utils import store）
**为什么需要检查**：反向依赖是分层架构被破坏的严重标志，意味着底层模块耦合了上层业务，底层无法复用；反向依赖还容易演变为循环依赖
**检查范围**：所有 import 关系，重点检查 core/shared/utils 是否 import business/views/services
**检查方法**：
1. 定义项目分层与依赖方向（高层 → 低层，业务 → core → shared → utils）
2. 检查 core 模块是否 import business 模块
3. 检查 shared 模块是否 import business 模块
4. 检查 utils 模块是否 import store / services / business
5. 检查 services 是否 import views / components
6. 对每个反向依赖，标注反向路径与原因
7. 检查反向依赖是否可通过依赖倒置解决
**需要查看**：分层定义、import 关系、依赖图、core/shared/utils 文件内容
**正常标准**：
- 依赖方向单向向下
- core 不 import business
- shared 不 import business
- utils 不 import store / services / business
- services 不 import views / components
- 无反向依赖
**异常情况**：
- core 模块 import 业务模块
- shared 模块 import 业务模块
- utils 模块 import store
- services import views / components
- 反向依赖已导致循环（与 4.2 关联）
**风险等级**：P1
**整改方向**：依赖倒置（底层定义接口，上层实现并注入）；上层逻辑下沉到下层；反向依赖部分移回上层；通过事件解耦
**验收标准**：依赖方向单向；core/shared/utils 无业务依赖；无反向 import

### 指标 4.5：深层依赖链检测

**指标名称**：深层依赖链检测（A→B→C→D→E）
**检查目标**：识别过深的文件级依赖链，深度过大的依赖链意味着修改影响面难以预估
**为什么需要检查**：深层依赖链让「改一个底层文件影响一长串文件」，影响面呈指数传播；深层依赖也是理解成本高的根因
**检查范围**：所有文件级依赖链
**检查方法**：
1. 基于依赖图，计算每个文件的最长依赖链长度
2. 标记依赖链深度超过 5 的文件
3. 对每个深层依赖链，输出完整路径
4. 检查深层依赖链中是否有可简化的环节（无意义转发、可合并的中间层）
5. 检查深层依赖链是否因跨层或反向依赖导致
6. 检查深层依赖链是否包含循环（与 4.2 关联）
7. 输出「深层依赖链清单」按深度降序
**需要查看**：依赖图、依赖链路径、文件依赖关系
**正常标准**：
- 文件级依赖链深度普遍 ≤ 4
- 无深度 > 5 的依赖链
- 每一跳依赖都有明确意义
- 深层依赖链无循环
**异常情况**：
- 存在深度 > 5 的依赖链
- 依赖链中有无意义转发环节
- 深层依赖链包含循环
- 单个文件被深层依赖链多次引用（耦合中心）
- 依赖链穿越多个不相关的模块
**风险等级**：P2
**整改方向**：简化依赖链；移除无意义中间层；深层依赖通过接口抽象；耦合中心拆分
**验收标准**：依赖链深度普遍 ≤ 4；无无意义转发；有深度排行与处置结论

### 指标 4.6：dependency-cruiser 配置与执行

**指标名称**：dependency-cruiser 配置与执行
**检查目标**：确认项目已配置 dependency-cruiser（或同类工具）作为架构守护，且规则覆盖循环、跨层、反向依赖
**为什么需要检查**：架构守护工具能防止架构腐化在日常开发中复发；没有架构守护的项目，本次审查修复后问题会再次出现
**检查范围**：dependency-cruiser 配置文件（.dependency-cruiser.js）、CI 集成、规则定义
**检查方法**：
1. 检查项目是否有 .dependency-cruiser.js 或同类配置文件
2. 检查配置是否定义了以下规则：
   - circular（循环依赖）
   - no-circular（禁止循环）
   - 层级规则（如 views 不允许 import utils 内部）
   - 反向依赖规则（core 不允许 import business）
3. 检查规则是否在 CI 中执行（PR 检查 / pre-commit）
4. 执行 `depcruise` 命令并检查输出
5. 检查规则是否覆盖路径别名
6. 检查是否有依赖规则文档说明
**需要查看**：.dependency-cruiser.js、CI 配置、package.json scripts、规则执行输出
**正常标准**：
- 有 .dependency-cruiser.js 配置
- 规则覆盖循环、跨层、反向依赖
- 规则在 CI 中执行
- depcruise 执行零告警
- 规则有文档说明
- 路径别名正确配置
**异常情况**：
- 无 dependency-cruiser 配置
- 配置存在但规则不全（只查循环不查跨层）
- 规则未在 CI 执行
- depcruise 执行有告警未处理
- 路径别名未配置导致规则失效
- 配置存在但已过时（与当前项目结构不符）
**风险等级**：P2
**整改方向**：配置 dependency-cruiser；补全循环/跨层/反向规则；纳入 CI；修复现有告警；配置路径别名
**验收标准**：有完整 dependency-cruiser 配置；规则覆盖核心耦合问题；CI 执行零告警

## 第五部分：分层架构审查

> 目标：判断项目分层是否清晰、依赖方向是否单向、核心层是否被污染、是否存在跨层绕过
> 本部分承接依赖关系，聚焦分层架构的合规性

### 指标 5.1：项目分层定义清晰性

**指标名称**：项目分层定义清晰性
**检查目标**：确认项目有明确的分层定义（文档化或代码化），每一层的职责、依赖方向、边界都有说明
**为什么需要检查**：没有明确的分层定义，开发者会按各自理解组织代码，导致分层混乱；分层定义不清是跨层依赖、反向依赖的根源
**检查范围**：项目文档、README、架构说明、目录结构、dependency-cruiser 配置
**检查方法**：
1. 检查项目是否有架构 / 分层说明文档
2. 检查 README 是否说明项目分层
3. 检查目录结构是否体现了分层（如 views/services/core/shared/utils 分目录）
4. 检查 dependency-cruiser 配置是否定义了分层规则
5. 检查路径别名是否对应分层（@views、@services、@core、@shared）
6. 检查是否有「未归层」的目录（既不是 views 也不是 services 也不是 core）
7. 输出「项目分层定义」清单
**需要查看**：架构文档、README、目录结构、dependency-cruiser 配置、路径别名配置
**正常标准**：
- 有明确的分层定义文档
- 目录结构体现分层
- 路径别名对应分层
- 每一层有职责说明
- 无「未归层」目录
- dependency-cruiser 配置体现分层规则
**异常情况**：
- 无分层定义文档
- 目录结构未体现分层（业务与工具混在一个目录）
- 无路径别名或别名不对应分层
- 存在「未归层」目录（不知道该归 views 还是 services）
- 分层定义与实际代码不符
**风险等级**：P2
**整改方向**：建立分层定义文档；目录结构按分层重组；配置路径别名；dependency-cruiser 体现分层
**验收标准**：有分层定义文档；目录体现分层；路径别名对应；无未归层目录

### 指标 5.2：依赖方向单向性

**指标名称**：依赖方向单向性
**检查目标**：确认项目依赖方向严格单向向下，无反向依赖、无循环依赖
**为什么需要检查**：依赖方向混乱是架构腐化的核心标志；反向依赖让底层耦合上层，循环依赖导致运行时错误
**检查范围**：所有跨层 import 关系
**检查方法**：
1. 定义项目分层与依赖方向（如 views → services → core → shared → utils）
2. 检查每一层的 import 是否只指向下层
3. 检查是否有反向依赖（下层 import 上层）
4. 检查是否有循环依赖（A→B→A）
5. 检查同层跨模块依赖是否合理（与 3.5 关联）
6. 用 dependency-cruiser 生成依赖方向报告
7. 输出「依赖方向违规清单」
**需要查看**：分层定义、import 关系、依赖图、dependency-cruiser 报告
**正常标准**：
- 依赖方向单向向下
- 无反向依赖
- 无循环依赖
- 同层跨模块通过上层编排
- dependency-cruiser 方向规则通过
**异常情况**：
- 存在反向依赖（core import business）
- 存在循环依赖
- 同层模块直接互依赖
- 依赖方向与分层定义不符
- dependency-cruiser 方向规则有告警
**风险等级**：P1（循环依赖为 P0）
**整改方向**：依赖倒置；上层编排；公共层下沉；接口抽取打破循环
**验收标准**：依赖方向单向；无反向依赖；无循环依赖；dependency-cruiser 方向规则零告警

### 指标 5.3：core/shared 业务污染检查

**指标名称**：core/shared 业务污染检查
**检查目标**：确认 core / shared 层不包含业务特定逻辑、业务字段名、业务规则、业务模块 import
**为什么需要检查**：核心层被业务污染后无法复用，每次业务变更都要改核心；核心层污染是「shared 不 shared」「core 不 core」的根因
**检查范围**：core 模块、shared 模块、utils 模块的所有文件
**检查方法**：
1. 列出 core / shared / utils 目录下所有文件
2. 检查文件内容是否出现业务字段名（如某业务特有的字段 code、业务实体名）
3. 检查文件内容是否包含业务规则（如某业务的计算公式、校验规则）
4. 检查 core / shared 是否 import 业务模块
5. 检查 core 组件是否硬编码业务配置（如某业务的颜色、路径、URL）
6. 检查 shared utils 是否包含业务计算逻辑
7. 检查 core 组件是否通过 props / 配置 / 插槽接收业务（而非硬编码）
**需要查看**：core/shared 文件内容、import 关系、组件 props、配置
**正常标准**：
- core/shared 无业务逻辑
- 无业务字段硬编码
- 无业务模块 import
- core 组件通过 props / 配置 / 插槽接收业务
- shared utils 为通用工具（非业务计算）
**异常情况**：
- core 组件含某业务字段名
- shared utils 含业务计算规则
- core import business 模块
- core 组件硬编码某业务的 URL / 颜色 / 路径
- shared 组件只服务单一业务（伪 shared，详见 7.7）
**风险等级**：P1
**整改方向**：业务逻辑移出核心层；核心层通过 props / 配置 / 插槽接收业务；伪 shared 组件移回业务模块
**验收标准**：core/shared 无业务污染；通过配置接收业务；无业务模块 import

### 指标 5.4：业务字段硬编码检查（核心层）

**指标名称**：业务字段硬编码检查（核心层）
**检查目标**：确认 core / shared / utils 层不硬编码业务字段名、业务常量、业务 URL
**为什么需要检查**：核心层硬编码业务字段会让核心层无法复用于其他业务；业务字段变更需要改核心层，违反开闭原则
**检查范围**：core / shared / utils 层的所有源码文件
**检查方法**：
1. 全局搜索 core / shared / utils 文件中的字符串字面量
2. 检查字符串字面量是否为业务字段名（如 `'userName'`、`'orderStatus'`）
3. 检查是否硬编码业务 URL（如 `/api/flood/analysis`）
4. 检查是否硬编码业务常量（如某业务的颜色值、阈值）
5. 检查是否硬编码业务实体名（如 `'flood-station'`）
6. 对每个硬编码，判断是否应通过 props / 配置 / 注入接收
**需要查看**：core/shared/utils 文件内容、字符串字面量、组件 props
**正常标准**：
- 核心层无业务字段名硬编码
- 无业务 URL 硬编码
- 无业务常量硬编码
- 业务相关内容通过 props / 配置 / 注入接收
- 核心层常量为通用常量（如颜色调色板、通用枚举）
**异常情况**：
- core 组件硬编码 `'floodLevel'` 字段名
- shared utils 硬编码 `/api/order/list` URL
- core 组件硬编码某业务颜色 `'#ff0000'`
- utils 硬编码某业务阈值 `0.5`
- 核心层出现业务实体名
**风险等级**：P1
**整改方向**：业务字段通过 props / 配置接收；URL 移到 service 层；业务常量移到业务模块；核心层仅保留通用常量
**验收标准**：核心层无业务硬编码；业务内容通过配置接收；核心层常量均为通用

### 指标 5.5：views 直接调 utils 检查（绕过 service）

**指标名称**：views 直接调 utils 检查（绕过 service）
**检查目标**：确认 views / components 不直接 import utils 内部工具绕过 services / shared
**为什么需要检查**：views 直接调 utils 绕过 service 破坏分层，让 utils 成为业务逻辑的实际承载点；这还会让 service 层形同虚设
**检查范围**：所有 views / components 文件的 import 关系
**检查方法**：
1. 列出所有 views / components 文件
2. 检查这些文件是否直接 import utils 目录的内部文件（非通过 shared 入口）
3. 检查是否绕过 services 直接调用数据加工函数
4. 检查是否绕过 shared 直接调用工具函数
5. 检查 views 是否直接 import repository / dao 层
6. 输出「views 直接调 utils 清单」
**需要查看**：views/components 的 import 语句、utils 目录结构、shared 入口
**正常标准**：
- views 通过 service 获取数据
- views 通过 shared 入口使用工具
- views 不直接 import utils 内部文件
- views 不直接 import repository / dao
- 工具函数经 shared 聚合导出后供 views 使用
**异常情况**：
- views 直接 import `utils/formatDate`（绕过 shared 入口）
- views 直接 import `utils/deepClone`
- views 直接调用数据加工函数而非经 service
- views 直接 import repository / dao 层
- 同一工具在 views 与 services 中分别 import 不同路径
**风险等级**：P1
**整改方向**：views 通过 shared 入口使用工具；数据加工移到 service；views 不直接访问 repository
**验收标准**：views 不直接 import utils 内部；经 shared 入口；经 service 获取数据

### 指标 5.6：views 直接 fetch 检查（绕过 service）

**指标名称**：views 直接 fetch 检查（绕过 service）
**检查目标**：确认 views / components 不直接调用 fetch / axios 绕过 service 层
**为什么需要检查**：views 直接 fetch 绕过 service 会破坏数据链路的统一性，导致请求散落各处、错误处理不一致、难以统一拦截与鉴权
**检查范围**：所有 views / components 文件
**检查方法**：
1. 全局搜索 views / components 文件中的 `fetch(`、`axios`、`request(`、`http.`、`XMLHttpRequest`
2. 检查每个调用点是否在 views / components 中（应在 service 中）
3. 检查是否有 views 直接调用第三方请求库
4. 检查是否有 views 直接操作 WebSocket / EventSource
5. 对每个违规调用，标注所在文件与行号
6. 检查 service 层是否覆盖了所有数据获取需求（如 service 缺失则 views 被迫直接 fetch）
**需要查看**：views/components 文件内容、fetch/axios 调用点、service 层覆盖
**正常标准**：
- views / components 无直接 fetch / axios 调用
- 所有数据获取经 service 层
- service 层覆盖所有数据获取需求
- WebSocket / EventSource 经 service 封装
- 无 views 内直接 XMLHttpRequest
**异常情况**：
- views 内有 `fetch('/api/...')` 调用
- components 内有 `axios.get(...)` 调用
- views 内直接 `new WebSocket(...)`
- service 层缺失导致 views 被迫直接 fetch
- 同一数据 views 直接 fetch 与 service 封装并存（多入口，详见 6.5）
**风险等级**：P1
**整改方向**：所有数据获取收口到 service 层；补全 service 缺失的封装；移除 views 内的直接请求
**验收标准**：views/components 无直接请求；所有获取经 service；service 覆盖完整

### 指标 5.7：组件直接改 store.state 检查（绕过 action）

**指标名称**：组件直接改 store.state 检查（绕过 action）
**检查目标**：确认组件不直接修改 store.state，所有状态修改通过 action / mutation
**为什么需要检查**：直接改 store.state 绕过 action 让状态变更不可追溯，是「莫名其妙的状态变化」的根因；还破坏 store 的单向数据流
**检查范围**：所有组件文件、所有 store.state 访问点
**检查方法**：
1. 全局搜索组件文件中的 `store.state.xxx =`、`store.state[xxx] =`、`store.xxx =` 赋值
2. 检查是否有 `store.state` 的直接赋值（非通过 action / mutation / commit / dispatch）
3. 检查是否有 `store.$patch` 直接修改（如 Pinia 的直接 patch 也应受控）
4. 检查 reactive store 是否被组件直接修改属性
5. 检查是否有组件通过 `Object.assign(store.state, ...)` 修改
6. 对每个违规，标注所在组件与修改的字段
**需要查看**：组件文件、store 定义、state 访问点
**正常标准**：
- 组件不直接修改 store.state
- 所有状态修改通过 action / mutation / commit / dispatch
- Pinia store 通过定义的 action 修改
- 无组件内 `store.state.xxx = yyy`
- 无组件内 `Object.assign(store.state, ...)`
**异常情况**：
- 组件内有 `store.state.user = {...}` 赋值
- 组件内有 `store.state.loading = true` 赋值
- 组件直接修改 reactive store 属性
- 组件通过 `Object.assign` 批量改 state
- 组件直接调用 mutation 而非 action（取决于框架约定）
**风险等级**：P1
**整改方向**：所有状态修改通过 action；组件调用 action 而非直接改 state；Pinia store 补全 action
**验收标准**：组件无直接改 state；所有修改经 action；状态变更可追溯

## 第六部分：隐式通信与多入口审查

> 目标：识别模块间的隐式通信与同一逻辑的多入口控制，回答「模块之间有没有看不见的通信」「同一逻辑是不是有多个控制点」
> 本部分是架构耦合的隐蔽高发区

### 指标 6.1：window 全局变量通信检查

**指标名称**：window 全局变量通信检查
**检查目标**：确认模块间不通过 window 全局变量进行隐式通信
**为什么需要检查**：window 全局变量通信让数据流不可追溯，是「莫名其妙的状态变化」根因；全局变量还容易命名冲突、被覆盖、难以调试
**检查范围**：所有源码文件，重点检查 `window.xxx =`、`window.xxx` 读取
**检查方法**：
1. 全局搜索 `window.` 赋值（`window.xxx =`、`window['xxx'] =`）
2. 全局搜索 `window.` 读取（`window.xxx`、`window['xxx']`）
3. 检查每个 window 变量的写入点与读取点是否跨模块
4. 检查是否有 window 变量被用作模块间状态传递
5. 检查是否有 window 变量被第三方库使用（区分业务用与库用）
6. 检查是否有 `globalThis.xxx`、`global.xxx` 等变体
7. 输出「window 全局变量通信清单」
**需要查看**：源码全量搜索结果、window 赋值与读取点
**正常标准**：
- 无 window 全局变量用于模块间通信
- window 仅用于第三方库挂载或环境检测
- 跨模块通信通过 props / store / 事件总线
- 无 `globalThis.xxx` 业务通信
**异常情况**：
- 模块 A 写 `window.sharedData = xxx`，模块 B 读 `window.sharedData`
- 通过 window 传递业务状态
- window 变量命名易冲突（如 `window.data`、`window.config`）
- window 变量无文档说明
**风险等级**：P1
**整改方向**：window 通信收口到 store / props；第三方库挂载加命名空间；文档化必要的 window 使用
**验收标准**：无 window 业务通信；window 仅用于库挂载；通信可追溯

### 指标 6.2：EventBus/mitt 使用审查

**指标名称**：EventBus/mitt 使用审查
**检查目标**：确认 EventBus / mitt / eventEmitter 的使用最小化、有文档、有清理
**为什么需要检查**：EventBus 满天飞会让事件流不可追溯，是「不知道谁触发了什么」的根因；事件监听不清理还会导致内存泄漏与重复触发
**检查范围**：所有 EventBus / mitt / eventEmitter / 自定义事件总线的使用
**检查方法**：
1. 全局搜索 `EventBus`、`mitt`、`eventEmitter`、`$emit`、`$on`、`$off`、`eventBus.emit`、`eventBus.on`
2. 列出所有事件名称与触发点 / 监听点
3. 检查每个事件是否有文档说明（事件名、payload、触发时机、监听者）
4. 检查每个监听是否有对应的取消监听（off / removeAllListeners）
5. 检查监听是否在组件卸载时清理
6. 检查是否有「事件替代 props/store」的反模式（应通过 props 传递的却用事件）
7. 检查事件命名是否规范（无冲突、易理解）
**需要查看**：EventBus 定义、事件触发点、事件监听点、组件卸载逻辑
**正常标准**：
- EventBus 使用最小化（仅用于跨层级 / 跨模块解耦）
- 每个事件有文档说明
- 每个监听有对应的取消监听
- 监听在组件卸载时清理
- 事件命名规范且无冲突
- 不用事件替代 props / store
**异常情况**：
- EventBus 被几十处使用且无文档
- 事件监听无对应的 off
- 组件卸载后监听未清理（内存泄漏 + 重复触发）
- 用事件传递本应通过 props 传递的数据
- 事件名冲突或命名混乱（如多个 `update` 事件含义不同）
- 全局 EventBus 与局部 EventBus 混用无区分
**风险等级**：P1
**整改方向**：事件收口到文档化；补全取消监听；卸载时清理；props 能传的不用事件；事件命名规范化
**验收标准**：EventBus 最小化且有文档；监听有清理；卸载安全；不替代 props

### 指标 6.3：localStorage 跨模块通信检查

**指标名称**：localStorage 跨模块通信检查
**检查目标**：确认 localStorage / sessionStorage 不被用作跨模块状态通信通道
**为什么需要检查**：localStorage 当状态管理用会让状态变更不可追溯、不响应式、跨标签页混乱；localStorage 还有大小限制、序列化开销、同步 IO 阻塞
**检查范围**：所有 localStorage / sessionStorage 的读写
**检查方法**：
1. 全局搜索 `localStorage.setItem`、`localStorage.getItem`、`sessionStorage.setItem`、`sessionStorage.getItem`
2. 列出所有 storage 的 key 与读写点
3. 检查是否有模块 A 写、模块 B 读的跨模块通信模式
4. 检查是否有 storage 被用作状态管理（频繁读写、依赖其响应式）
5. 检查 storage 是否存储敏感数据（token、密码）
6. 检查 storage key 是否有命名空间（避免冲突）
7. 检查 storage 是否有清理策略（避免无限增长）
**需要查看**：localStorage/sessionStorage 读写点、storage key 清单、敏感数据检查
**正常标准**：
- localStorage 仅用于持久化（如用户偏好、token）
- 不用作跨模块状态通信
- storage key 有命名空间
- 不存储敏感数据明文
- 有清理策略
- 跨模块状态通过 store 管理
**异常情况**：
- 模块 A `localStorage.setItem('data', ...)`，模块 B `localStorage.getItem('data')`
- 用 localStorage 当响应式状态（手动 watch storage 事件）
- 存储 token / 密码明文
- storage key 无命名空间易冲突
- storage 只写不清理
- 频繁读写 localStorage 当状态用
**风险等级**：P1
**整改方向**：跨模块状态收口到 store；localStorage 仅持久化；敏感数据加密或不存；key 加命名空间；补清理策略
**验收标准**：localStorage 不作状态通信；仅持久化；无敏感明文；key 有命名空间

### 指标 6.4：DOM dataset 跨组件通信检查

**指标名称**：DOM dataset 跨组件通信检查
**检查目标**：确认组件间不通过 DOM dataset（data-* 属性）进行隐式通信
**为什么需要检查**：DOM dataset 通信让数据流绕过组件树，不可追溯、不响应式、难以测试；这是「组件间偷偷传值」的反模式
**检查范围**：所有组件文件，重点检查 `dataset`、`getAttribute('data-`、`setAttribute('data-`
**检查方法**：
1. 全局搜索 `dataset.`、`getAttribute('data-`、`setAttribute('data-`、`data-*=`（模板中）
2. 列出所有 dataset 的读写点
3. 检查是否有组件 A 写 dataset、组件 B 读 dataset 的跨组件通信
4. 检查是否有通过 DOM 传递本应通过 props 传递的数据
5. 检查是否有通过 dataset 传递业务状态
6. 检查 dataset 是否用于与第三方库交互（区分业务用与库用）
**需要查看**：组件文件、dataset 读写点、模板中的 data-* 属性
**正常标准**：
- 组件间不通过 dataset 通信
- dataset 仅用于与第三方库交互或无障碍属性
- 跨组件数据通过 props / provide / inject / store
- 无业务状态通过 dataset 传递
**异常情况**：
- 组件 A `el.dataset.userId = ...`，组件 B `el.dataset.userId` 读取
- 通过 data-* 传递本应通过 props 传递的数据
- 通过 dataset 传递业务状态
- dataset 命名混乱无规范
**风险等级**：P2
**整改方向**：跨组件数据通过 props / store；dataset 仅用于库交互；移除业务 dataset 通信
**验收标准**：组件间无 dataset 通信；dataset 仅用于库交互；数据通过 props/store

### 指标 6.5：数据获取多入口检查

**指标名称**：数据获取多入口检查
**检查目标**：确认同一数据只有单一获取入口，不存在多个获取函数实现不同
**为什么需要检查**：多入口会导致「改了 A 入口 B 入口还在用旧逻辑」；多入口还会导致缓存不一致、错误处理不一致、鉴权不一致
**检查范围**：所有 service 函数、所有数据获取入口
**检查方法**：
1. 列出所有 service 函数及其获取的数据类别
2. 检查同一数据是否有多个获取函数（如 `getUserA` 与 `getUserB` 都获取用户）
3. 检查多个获取函数的实现是否一致（URL、参数、转换、错误处理）
4. 检查是否有 service 与组件直接 fetch 并存（service 有封装但组件绕过）
5. 检查同一数据是否有静态 JSON 与接口两个来源且无切换机制
6. 检查是否有「废弃入口未删除」（旧函数还在但已不应被调用）
**需要查看**：service 函数清单、fetch 调用点、静态数据导入、数据来源配置
**正常标准**：
- 同一数据单一获取入口
- 多入口已收口或明确分工（如分页 vs 详情）
- service 与组件不并存获取同一数据
- 静态与接口有切换机制
- 无废弃入口残留
**异常情况**：
- 两个函数都能获取同一数据且实现不同
- service 有封装但组件绕过直接 fetch
- 同一数据有静态 JSON 与接口两个来源无切换
- 废弃的获取函数未删除
- 同一数据不同入口的参数 / 错误处理不一致
**风险等级**：P1
**整改方向**：收口单一入口；废弃入口删除；多入口明确分工并文档化；静态与接口配置化切换
**验收标准**：同一数据单一入口；无废弃入口；多入口有分工文档

### 指标 6.6：状态修改多入口检查

**指标名称**：状态修改多入口检查
**检查目标**：确认同一状态只有单一修改路径，不存在多个 action / 多个直接修改并存
**为什么需要检查**：状态修改多入口会导致「改了 A 入口 B 入口还在用旧逻辑」；还会让状态变更不可追溯、难以调试
**检查范围**：所有 store action、所有 state 修改点
**检查方法**：
1. 列出所有 store 的 action 及其修改的 state 字段
2. 检查同一 state 字段是否有多个 action 修改
3. 检查是否有 action 与组件直接修改并存（action 有但组件绕过）
4. 检查是否有「通过 reset 整体覆盖」与「通过字段更新」两种修改路径并存
5. 检查跨 store 的状态修改（store A 修改 store B 的状态）
6. 检查是否有废弃的修改路径未删除
**需要查看**：store 定义、action 清单、组件 state 修改点
**正常标准**：
- 同一 state 字段单一修改路径
- 多 action 修改同一字段时有明确分工（如 init vs update）
- 无组件直接修改 state（与 5.7 关联）
- 无跨 store 修改
- 无废弃修改路径
**异常情况**：
- 同一 state 字段被多个 action 修改且无分工
- action 与组件直接修改并存
- 跨 store 修改（store A 改 store B 的 state）
- 废弃的修改路径未删除
- 通过 reset 与字段更新两种路径并存且无规范
**风险等级**：P1
**整改方向**：收口单一修改路径；废弃路径删除；跨 store 修改改为通过各自的 action；多路径明确分工
**验收标准**：同一 state 单一修改路径；无组件直接改；无跨 store 修改

### 指标 6.7：图层控制多入口检查（架构视角）

**指标名称**：图层控制多入口检查（架构视角）
**检查目标**：确认同一地图图层只有单一控制入口（显隐、样式、数据更新），不存在多个组件独立控制
**为什么需要检查**：图层多入口控制会导致「组件 A 显示图层，组件 B 隐藏图层，最终状态不可预测」；还会导致图层状态不一致、重复加载、清理遗漏
**检查范围**：所有地图图层控制点（显隐、样式、数据、过滤）
**检查方法**：
1. 列出所有地图图层及其控制点（显隐、样式、数据更新、过滤）
2. 检查同一图层是否有多个组件控制显隐
3. 检查同一图层是否有多个组件控制样式
4. 检查同一图层是否有多个数据更新入口
5. 检查图层控制是否有统一的管理器（如 LayerManager）
6. 检查图层状态是否有单一来源（store 或 manager）
7. 检查多入口控制是否导致冲突（如 A 显示后 B 隐藏）
**需要查看**：图层控制代码、LayerManager、图层相关 store、组件
**正常标准**：
- 同一图层单一控制入口
- 图层控制通过统一 LayerManager 或 store
- 图层状态单一来源
- 多组件协作时有明确的主从关系
- 无多入口冲突
**异常情况**：
- 多个组件都能显隐同一图层
- 图层样式被多个组件独立修改
- 图层数据有多个更新入口
- 无统一 LayerManager
- 多入口控制导致图层状态不可预测
**风险等级**：P1
**整改方向**：图层控制收口到 LayerManager 或 store；多组件协作明确主从；移除冗余控制入口
**验收标准**：同一图层单一控制入口；有统一管理器；状态单一来源

### 指标 6.8：路由跳转多入口检查

**指标名称**：路由跳转多入口检查
**检查目标**：确认同一业务跳转只有单一入口或多个入口行为一致，不存在「同一跳转多个入口行为不一致」
**为什么需要检查**：跳转多入口行为不一致会导致「从 A 入口跳带参数，从 B 入口跳不带参数」，用户体验不一致；还会让跳转逻辑难以维护
**检查范围**：所有路由跳转点（router.push、router.replace、router-link、window.location）
**检查方法**：
1. 全局搜索 `router.push`、`router.replace`、`<router-link`、`window.location`、`location.href`
2. 列出所有跳转目标与跳转点
3. 检查同一目标是否有多个跳转入口
4. 检查多入口的跳转参数是否一致（query、params）
5. 检查多入口的跳转方式是否一致（push vs replace）
6. 检查是否有硬编码 URL 跳转与路由跳转并存
7. 检查跳转是否有统一封装（如 navigateTo 函数）
**需要查看**：路由配置、跳转点清单、跳转参数
**正常标准**：
- 同一跳转多入口行为一致
- 跳转有统一封装或约定
- 跳转参数一致
- 无硬编码 URL 与路由跳转并存
- 跳转目标有命名常量
**异常情况**：
- 同一跳转多个入口参数不一致
- 有的 push 有的 replace 无规范
- 硬编码 URL 跳转与路由跳转并存
- 跳转目标字符串散落各处无常量
- 跳转前无权限校验或校验不一致
**风险等级**：P2
**整改方向**：跳转统一封装；多入口行为对齐；跳转目标常量化；跳转前统一鉴权
**验收标准**：同一跳转多入口行为一致；有统一封装；目标常量化

## 第七部分：代码资产审查

> 目标：识别死代码、未消费 export、注释代码、重复实现、伪 shared，回答「项目有多少无效资产」「有多少重复资产」
> 本部分是架构耦合的资产层清理

### 指标 7.1：未引用文件识别（架构视角）

**指标名称**：未引用文件识别（架构视角）
**检查目标**：识别从未被任何地方 import 的源码文件（死文件）
**为什么需要检查**：死文件增加认知负担、误导维护者、掩盖真实结构；它们还会被 IDE 索引、被构建工具扫描，影响性能
**检查范围**：所有源码文件（除入口文件、配置文件、测试文件）
**检查方法**：
1. 列出所有源码文件
2. 对每个文件，全局搜索是否被其他文件 import
3. 检查未被任何地方 import 的文件
4. 排除合法的未引用文件：入口文件（main.ts、app.ts）、配置文件、测试文件、类型定义文件（可能被 tsconfig include）
5. 检查未引用文件是否为废弃代码（有 `_old`、`_v2`、`_backup` 后缀）
6. 检查未引用文件是否被动态 import（`import()` 字符串）
7. 输出「未引用文件清单」
**需要查看**：文件清单、import 关系、动态 import 字符串、tsconfig include
**正常标准**：
- 无未被引用的源码文件（除入口、配置、测试、类型定义）
- 未引用文件有明确标注（如已废弃待删除）
- 动态 import 的文件被正确识别
**异常情况**：
- 存在未被任何地方 import 的源码文件
- 未引用文件无标注
- 未引用文件含 `_old`、`_v2`、`_backup` 后缀
- 动态 import 未被识别导致误判
- 大量未引用文件堆积
**风险等级**：P2
**整改方向**：删除死文件；废弃文件如需保留迁移到归档目录；动态 import 显式标注
**验收标准**：无未引用源码文件；废弃文件已清理或标注；动态 import 已识别

### 指标 7.2：未消费 export 识别

**指标名称**：未消费 export 识别
**检查目标**：识别从未被任何地方 import 的 export（死导出）
**为什么需要检查**：未消费 export 增加模块公开 API 的噪音，误导维护者以为某功能在使用；还会让模块公开 API 难以收敛
**检查范围**：所有源码文件的 export
**检查方法**：
1. 列出所有文件的 export（named export、default export）
2. 对每个 export，全局搜索是否被其他文件 import
3. 检查未被任何地方 import 的 export
4. 排除合法的未消费 export：库的公开 API、被动态引用的 export、类型 re-export
5. 检查未消费 export 是否为废弃功能
6. 检查未消费 export 是否导致模块公开 API 膨胀
7. 输出「未消费 export 清单」
**需要查看**：export 清单、import 关系、动态 import
**正常标准**：
- 无未消费 export（除库公开 API、类型 re-export）
- 未消费 export 有明确标注
- 模块公开 API 最小化
**异常情况**：
- 存在未被任何地方 import 的 export
- 未消费 export 无标注
- 模块导出几十个但多数无消费者
- 未消费 export 导致公开 API 膨胀
**风险等级**：P2
**整改方向**：删除未消费 export；废弃 export 如需保留加标注；模块公开 API 收敛
**验收标准**：无未消费 export；公开 API 最小化；废弃 export 已清理

### 指标 7.3：大段注释代码检查

**指标名称**：大段注释代码检查
**检查目标**：识别被注释掉的大段代码块（超过 10 行的注释代码）
**为什么需要检查**：注释代码是「墓碑代码」的主要成分，增加认知负担、误导维护者、掩盖真实结构；历史代码应通过 git 历史保留而非注释保留
**检查范围**：所有源码文件
**检查方法**：
1. 全局搜索连续多行注释（`//` 或 `/* */`）
2. 检查注释内容是否为代码（含 `function`、`const`、`return`、`if` 等关键字）
3. 标记超过 10 行的注释代码块
4. 检查注释代码是否为旧实现（与新实现并存）
5. 检查注释代码是否为「临时禁用」未清理
6. 检查是否有 `// TODO`、`// FIXME` 标记的注释代码
**需要查看**：源码全量搜索结果、注释代码块
**正常标准**：
- 无超过 10 行的注释代码块
- 注释为说明性注释而非代码
- 历史代码通过 git 历史保留
- 临时禁用的代码有清理计划
**异常情况**：
- 存在超过 10 行的注释代码块
- 注释代码为旧实现与新实现并存
- 注释代码为「临时禁用」无清理计划
- 大量 `// TODO` 标记的注释代码
- 注释代码含业务逻辑
**风险等级**：P3
**整改方向**：删除注释代码；历史代码通过 git 历史保留；临时禁用代码加清理计划
**验收标准**：无大段注释代码；注释为说明性；历史代码在 git

### 指标 7.4：重复工具函数检查

**指标名称**：重复工具函数检查
**检查目标**：识别多处实现的相同或高度相似的工具函数
**为什么需要检查**：重复工具函数意味着修改时需要同步多处，遗漏任一处都会产生隐蔽 bug；重复还会让工具函数的「单一来源」失效
**检查范围**：所有工具函数（格式化、校验、转换、计算）
**检查方法**：
1. 识别功能相似的工具函数（如多个 `formatXxx`、`parseXxx`、`deepClone`、`debounce`）
2. 对比实现是否高度相似（函数签名、逻辑、返回值）
3. 检查同一工具是否在多个 utils 文件中各实现一遍
4. 检查是否在多个业务模块中各自实现了相同工具
5. 检查是否有「复制粘贴」的痕迹（注释、命名一致但位置不同）
6. 输出「重复工具函数清单」并标注实现位置
**需要查看**：工具函数实现、utils 目录、业务模块内的工具函数
**正常标准**：
- 同一工具函数单一实现
- 工具函数有统一出处（如 shared/utils）
- 业务模块不重复实现通用工具
- 工具函数被多处引用而非多处实现
**异常情况**：
- 同一格式化函数存在 2 处以上实现
- 多个业务模块各自实现 deepClone / debounce
- 同一工具在 utils 与业务模块中各一份
- 复制粘贴的工具函数（命名、注释都一致）
- 工具函数实现略有差异（潜伏 bug）
**风险等级**：P2
**整改方向**：重复工具收口到 shared/utils；业务模块移除重复实现；统一引用单一来源
**验收标准**：同一工具单一实现；统一出处；业务模块无重复实现

### 指标 7.5：重复业务逻辑检查

**指标名称**：重复业务逻辑检查
**检查目标**：识别多处实现的相同或高度相似的业务逻辑（非工具函数）
**为什么需要检查**：重复业务逻辑意味着业务规则变更时需要同步多处，遗漏任一处都会导致业务行为不一致；这是「同一规则多处实现」的高发区
**检查范围**：业务计算逻辑、数据转换逻辑、校验逻辑、业务流程
**检查方法**：
1. 识别功能相似的业务逻辑（如多个模块的「计算水位等级」「校验站点」）
2. 对比实现是否高度相似
3. 检查同一业务逻辑是否在 service 与 controller 各实现一遍
4. 检查同一业务逻辑是否在多个组件中重复实现
5. 检查是否有「复制粘贴」的业务逻辑
6. 输出「重复业务逻辑清单」并标注实现位置
**需要查看**：service 实现、组件实现、业务逻辑代码
**正常标准**：
- 同一业务逻辑单一实现
- 业务逻辑沉淀在 service 或 composable
- 组件不重复实现业务计算
- 业务逻辑有统一出处
**异常情况**：
- 同一业务计算存在 2 处以上实现
- service 与 controller 各实现一遍
- 多个组件重复实现同一校验逻辑
- 复制粘贴的业务逻辑
- 业务逻辑实现略有差异（潜伏 bug）
**风险等级**：P2
**整改方向**：重复业务逻辑收口到 service / composable；组件移除重复实现；统一引用单一来源
**验收标准**：同一业务逻辑单一实现；沉淀在 service/composable；组件无重复

### 指标 7.6：前后端重复定义检查

**指标名称**：前后端重复定义检查
**检查目标**：识别前后端各自维护且无自动同步的重复类型定义、常量定义、枚举定义
**为什么需要检查**：前后端各维护一份相同结构定义且无自动同步，会导致「后端加了字段前端不知道」「前端类型与后端实际返回不一致」；这是类型契约失效的根因
**检查范围**：前端类型定义、后端类型定义、常量定义、枚举定义
**检查方法**：
1. 列出前端所有类型定义 / 常量定义 / 枚举定义
2. 列出后端所有类型定义 / 常量定义 / 枚举定义
3. 对比同一业务实体在前端与后端的定义
4. 检查字段名、类型、含义是否一致
5. 检查是否有自动同步机制（如 OpenAPI 生成、protobuf、code-gen）
6. 检查是否有「同名不同义」或「同义不同名」
7. 输出「前后端重复定义清单」与不一致项
**需要查看**：前端 types、后端类型/响应、常量定义、枚举定义、code-gen 配置
**正常标准**：
- 同一实体前后端定义一致
- 有自动同步机制（OpenAPI / protobuf / code-gen）
- 字段名、类型、含义对齐
- 无「同名不同义」或「同义不同名」
**异常情况**：
- 前后端各维护一份相同结构定义且无同步
- 前端类型有字段但后端不返回
- 后端返回字段但前端类型没定义
- 同名字段前后端类型不同
- 无自动同步机制纯靠人工维护
**风险等级**：P2
**整改方向**：类型定义单一来源或自动生成；前后端定义对齐；建立 code-gen 机制
**验收标准**：前后端定义一致；有自动同步机制；无不一致项

### 指标 7.7：模块复用性检查（伪 shared 组件）

**指标名称**：模块复用性检查（伪 shared 组件）
**检查目标**：判断 shared 目录下的组件 / composable / 工具是否真正被复用，还是只服务单一业务的「伪 shared」
**为什么需要检查**：伪 shared 组件占着 shared 的位置却不具备复用性，会让 shared 目录膨胀、职责模糊；伪 shared 还会硬编码业务参数，进一步丧失复用性
**检查范围**：shared 目录下的所有组件、composable、工具
**检查方法**：
1. 列出 shared 目录下所有组件 / composable / 工具
2. 对每个 shared 项，统计其被引用的次数与位置
3. 检查是否只被 1 个业务模块使用（伪 shared）
4. 检查 shared 组件是否硬编码业务参数（字段名、颜色、路径、URL）
5. 检查 shared 组件是否依赖业务模块（反向依赖，详见 4.4）
6. 检查 shared 组件是否能被「拔出」用于其他项目
7. 输出「伪 shared 清单」
**需要查看**：shared 目录内容、被引用次数、组件 props、依赖关系
**正常标准**：
- shared 目录下的项被至少 2 处使用，或明确设计为可复用
- shared 组件不硬编码业务参数
- shared 组件不依赖业务模块
- shared 组件能被「拔出」用于其他项目
- 无伪 shared
**异常情况**：
- shared 组件只被 1 个业务模块使用
- shared 组件硬编码某业务的字段名 / 颜色 / 路径
- shared 组件依赖业务模块
- 业务组件被放进 shared 目录
- shared 组件无法被「拔出」复用
**风险等级**：P3
**整改方向**：伪 shared 组件移回业务模块；真正需要复用的组件去除硬编码；shared 组件通过 props / 配置接收业务
**验收标准**：shared 目录均为真复用；无硬编码业务参数；无业务模块依赖

## 第八部分：v3 迁移新增指标（2026-09-01 增补，见 00 §4 指标演进口径）

> 背景：v3 采用 strangler 模式迁移——老 Express 冻结、Nest 新建、PG 引入。迁移期的架构风险集中在"新旧边界失守"与"DB 访问散落"。

### 指标 8.1：Express 冻结边界泄漏

**指标名称**：Express 冻结边界泄漏
**检查目标**：确认迁移冻结期内 `backend/`（老 Express）除声明过的 fix 外无新增功能/重构 diff
**为什么需要检查**：冻结的意义是保证切换基线可预期；老代码若持续被改，双后端行为对照（等价性验收）失去稳定基准，切换验证全部作废
**检查范围**：`backend/` 全部源码（`backend/nest/`、`backend/algorithm-service/` 除外）
**检查方法**：
1. `git log --oneline -- backend/` 列出冻结期全部提交
2. 核对每条是否为 `fix:` 且附回归测试（03 §1.6 既有规则）
3. 发现非 fix 改动 → 核对施工手册状态总表是否有对应声明
**需要查看**：git log、施工手册状态总表、commit message
**正常标准**：冻结期 backend/ 提交均为带测试的 fix 或施工手册声明的例外
**异常情况**：feat:/refactor: 提交改老后端；无测试的 fix；静默的数据文件手改
**风险等级**：P1
**整改方向**：非 fix 改动移回 nest/algorithm-service 实现；确属老后端 bug 的补测试转正
**验收标准**：冻结期 backend/ 提交链全部合规可追溯

### 指标 8.2：Nest feature 模块边界

**指标名称**：Nest feature 模块边界
**检查目标**：确认 backend/nest 按功能域分模块（auth/favorites/plans/forecast/flood/site-analysis 等），模块间不深引用（只经模块导出入口或公共 infra）
**为什么需要检查**：Nest 的模块系统是架构契约的落点；跨 feature 深引用会让"切换单元=功能域"的迁移策略失效，也会重演前端业务互引的老问题（专项6 既有一级质量属性）
**检查范围**：`backend/nest/src/modules/**`、`backend/nest/src/infra/**`
**检查方法**：
1. 列出 modules/ 下各 feature 目录及其 module/controller/service/repository 构成
2. 检查 feature 之间 import 是否只走对方 module exports 或公共 infra
3. `npm run cruise` 后确认 Nest 专属规则（若已配置）0 violation
**需要查看**：modules 目录结构、import 语句、cruise 配置与输出
**正常标准**：feature 互不深引用；共享能力全部下沉 infra；cruise 0 violation
**异常情况**：A 模块 import B 模块的 service 文件路径；业务逻辑放 infra；cruise 对 nest 无规则覆盖
**风险等级**：P2
**整改方向**：深引用改为经 module exports 注入；业务逻辑移回 feature；补 cruise 规则
**验收标准**：cruise 0 violation；模块间只经公共口交互

### 指标 8.3：DB 访问收口（repository 层唯一）

**指标名称**：DB 访问收口（repository 层唯一）
**检查目标**：确认 `pg` 的连接池与 SQL 查询只出现在 repository 层（或专门 data-access 模块），service/controller 不直接持有 pool 或执行裸 SQL
**为什么需要检查**：DB 访问散落是"迁移数据库时替换 repositories 层即可"这一既有设计决策（03 §七 ADR6）的直接违反；散落点会让 SQL 注入面、连接泄漏、事务边界失控同时放大
**检查范围**：`backend/nest/src/**`（排除测试）
**检查方法**：
1. grep `from 'pg'` / `new Pool` / `.query(` 的全部出现位置
2. 核对每处是否位于 repository 层（或注入型 data-access provider）
3. 检查 cruise 是否有对应禁止规则（service/controller → pg）
**需要查看**：import 扫描结果、目录分层、cruise 配置
**正常标准**：pg import 与 .query 调用仅在 repository 层；cruise 规则强制；service 经 repository 接口取数
**异常情况**：controller/service 直接 pool.query；多服务各自 new Pool；无规则守护
**风险等级**：P1
**整改方向**：散落查询下沉 repository；pool 收敛单例 provider；补 cruise 规则
**验收标准**：pg 相关 import 全量收口；cruise 守护生效

### 指标 8.4：架构守护工具覆盖新目录

**指标名称**：架构守护工具覆盖新目录
**检查目标**：确认 dependency-cruiser、eslint 的规则与扫描范围显式覆盖 backend/nest（与后续 algorithm-service），不存在"新目录游离于守护之外"
**为什么需要检查**：cruise 的 includeOnly 与 eslint 的 parserOptions 均按既有目录设计（frontend tsconfig）；新 TS 工程不显式适配会出现两类静默失败——规则不扫描（守护失效）或 tsconfig 错配（lint 崩溃，参照 z127 同类机理）
**检查范围**：`.dependency-cruiser.cjs`、`eslint.config.js`、各新工程 tsconfig
**检查方法**：
1. 确认 cruise includeOnly 覆盖 nest 且 Nest 专属规则存在
2. 确认 eslint 对 `backend/nest/**/*.ts` 有独立 parserOptions 块（指向 nest 自身 tsconfig）
3. 在 nest 内注入一条违反规则（如跨层 import）与一条格式违规，验证工具双双拦截
**需要查看**：cruise 配置、eslint 配置、nest tsconfig、拦截实验输出
**正常标准**：新目录在守护范围内；注入违规必被拦截；lint 无 TSConfig 失配报错
**异常情况**：cruise 输出不含 nest 文件；eslint 对 nest 文件报 TSConfig does not include 或直接跳过
**风险等级**：P1
**整改方向**：补配置块；注入实验验证；回归全绿
**验收标准**：拦截实验通过；`npm run lint` + `npm run cruise` 全绿且真实覆盖新目录

## 附录 D：分层架构参考模型

> 本附录给出推荐的分层架构模型，供项目对照与整改参考

### D.1 推荐分层模式（前端 Vue/React 项目）

```
views / pages          ← 表现层：页面级组件，编排业务模块，不含数据获取与业务计算
  ↓
components / modules    ← 业务层：业务模块，含业务组件与 composable，通过 service 获取数据
  ↓
services / api          ← 数据层：封装所有 HTTP 请求，统一错误处理与拦截
  ↓
store                   ← 状态层：全局状态管理，通过 action 修改，调用 service 获取数据
  ↓
core                    ← 核心层：项目级核心能力（如 map、layout），不含业务逻辑
  ↓
shared                  ← 共享层：跨业务复用的组件、composable、工具
  ↓
utils                   ← 工具层：纯函数工具，无副作用，无业务逻辑
```

### D.2 依赖方向规则

- 依赖方向严格单向向下：上层 → 下层
- views → modules → services → store → core → shared → utils
- 禁止反向：utils 不依赖 shared，shared 不依赖 core，core 不依赖 store
- 禁止跨层：views 不直接 import utils 内部（经 shared 入口）
- 禁止同层互依赖：业务模块 A 不 import 业务模块 B

### D.3 各层职责定义

| 层 | 职责 | 允许依赖 | 禁止内容 |
|----|------|----------|----------|
| views/pages | 页面编排、路由、页面级布局 | modules、services、store、shared | 数据获取实现、业务计算、utils 内部 |
| components/modules | 业务组件、composable、业务逻辑 | services、store、shared、core | 直接 fetch、utils 内部、跨模块 import |
| services/api | HTTP 请求封装、错误处理、拦截 | utils、shared | UI 逻辑、store 修改、业务计算 |
| store | 全局状态、action、getter | services、utils | 直接 fetch、UI 逻辑、业务计算 |
| core | 项目级核心能力（map、layout） | shared、utils | 业务逻辑、业务字段、业务模块 import |
| shared | 跨业务复用组件、composable、工具 | utils | 业务逻辑、业务字段、业务模块 import |
| utils | 纯函数工具 | （无依赖或仅依赖其他 utils） | 副作用、业务逻辑、store、services |

### D.4 路径别名建议

```
@views      → src/views
@modules    → src/modules
@services   → src/services
@store      → src/store
@core       → src/core
@shared     → src/shared
@utils      → src/utils
```

路径别名应指向各层根目录，外部通过别名访问各层入口而非内部文件。

### D.5 dependency-cruiser 规则建议

```js
// .dependency-cruiser.js 推荐规则
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment: '禁止循环依赖',
      from: {},
      to: { circular: true }
    },
    {
      name: 'no-reverse-core-to-business',
      severity: 'error',
      comment: 'core 不允许依赖 business',
      from: { path: '^src/core/' },
      to: { path: '^src/modules/' }
    },
    {
      name: 'no-reverse-shared-to-business',
      severity: 'error',
      comment: 'shared 不允许依赖 business',
      from: { path: '^src/shared/' },
      to: { path: '^src/modules/' }
    },
    {
      name: 'no-reverse-utils-to-store',
      severity: 'error',
      comment: 'utils 不允许依赖 store',
      from: { path: '^src/utils/' },
      to: { path: '^src/store/' }
    },
    {
      name: 'no-views-to-utils-internal',
      severity: 'error',
      comment: 'views 不允许直接访问 utils 内部',
      from: { path: '^src/views/' },
      to: { path: '^src/utils/[^/]+$' }
    },
    {
      name: 'no-views-to-fetch',
      severity: 'error',
      comment: 'views 不允许直接 fetch',
      from: { path: '^src/views/' },
      to: { path: '^src/services/' }
    }
  ]
};
```

### D.6 整改优先级建议
