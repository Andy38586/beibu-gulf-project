## 0. 文档使用说明

### 0.1 文档定位
本文档是「前端设计 token 一致性专项审查标准库」，填补审查体系对**视觉层一致性**的零覆盖。

其余专项都不管：CSS 变量守约、色值硬编码、间距/圆角/阴影/字体 token 一致性、暗色模式正确性、token 治理流程。
架构耦合专项 5.4「业务字段硬编码检查」只查逻辑层硬编码（写死业务字段名），**不查样式硬编码**——本专项是唯一覆盖视觉层的标准库。

本项目 GCS 设计系统（Global Component Style）是核心资产：布局基座 `shared/layout/`（config.ts 常量 + useGCS 计算）+ 面板组件 `core/layout/components/`（GCSPanel/GCSButton/BottomNavBar/MobileDrawer）+ 主题体系 `shared/constants/colors.ts` + 全局 CSS 的 `--GCS-*` 变量。token 体系是 GCS 的灵魂：改一处、全站生效；散落一处、全站漂移。

本专项 44 个指标分 5 个部分：色值 token 管理（9）、间距/圆角/阴影/字体（10）、组件级样式一致性（10）、主题切换与暗色模式（10）、token 工程与治理（5）。每部分可独立执行。

### 0.2 与其他专项的边界
- 本专项**只管前端样式 / 设计 token 一致性**（视觉层）。
- 业务逻辑硬编码（写死端口、字段名）→ 架构耦合专项 5.4，不归本专项。
- 布局算法（useGCS 网格计算逻辑）→ 不在本专项（那是逻辑，不是 token）。
- 但发现「某组件未用 GCS 布局引擎而手搓样式」→ 本专项 3.1（组件级样式一致性）。
- 图表库（ECharts）option 内色值 → 本专项 1.8/4.8 管「色板是否 token 化」，图表渲染正确性归专项4 WebGIS / 专项8 算法正确性。
- 样式相关的 TS 类型（CSS 变量类型声明、样式模块类型）→ 专项3 TS类型。
- 组件拆分粒度（是否该抽组件）→ 根基文档 03 §1.4 组件拆分标准，本专项只查"拆出来的组件样式是否一致"。

### 0.3 指标条目格式约定
每个指标严格采用 11 字段结构（见 `00-审查体系约定.md` §2）：指标名称/检查目标/为什么需要检查/检查范围/检查方法/需要查看/正常标准/异常情况/风险等级/整改方向/验收标准。

### 0.4 风险等级定义

见 `00-审查体系约定.md` §1（判据与处置），本专项不再重复定义，仅引用：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

本专项整体偏 P2–P3（一致性问题，非功能错误）；但「硬编码色值导致主题切换/暗色模式失效」「暗色下大面积不可读」升 P1。

### 0.5 本专项核心原则
1. **设计 token 单一来源**：所有视觉常量来自 `colors.ts` + CSS `:root` 的 `--GCS-*`，禁止散落字面量。
2. **var() 引用优先**：组件样式用 `var(--GCS-*)`，不直接写 hex/rgb。
3. **可验收**：每条不一致都能定位到 file:line，并能自动化扫描（grep / stylelint）。
4. **主题可切换即正确性**：样式是否支持暗色/主题切换是验收项，不只是美观问题。
5. **治理闭环**：token 不是一次定义永久不动——变更有影响面评估、废弃有清理、使用有统计。

## 第一部分：色值 token 管理（可独立执行）

### 指标 1.1：设计 token 单一来源
**指标名称**：设计 token 单一来源
**检查目标**：确认所有色值集中定义在一处（前端 `colors.ts` + CSS `:root` 的 `--GCS-*`），无第二套色值源。
**为什么需要检查**：多套色值源必然漂移——改一处另一处不变，主题不一致；新人在两套源之间不知道该改谁。
**检查范围**：`shared/constants/colors.ts`、全局 CSS（`:root` / `@theme` / data-theme 块）、各 `.vue` `<style>`、`.ts/.js` 中色值定义。
**检查方法**：
1. 列出 `colors.ts` 导出的全部色值常量（按语义分组：primary/success/warning/danger/text/bg/border/chart）。
2. 列出 CSS `:root` 与各主题块的 `--GCS-*` 变量，与 `colors.ts` 做一一映射核对（同名同值或明确分工）。
3. 搜索是否另有 `theme.ts` / `palette.ts` / 散落 `const color = '#xxx'` / `new Map` 色值表。
4. 检查组件内是否重新定义色值常量（`<style>` 内 `$primary` 或 script 内 `const RED = ...`）。
5. 检查第三方库覆写文件（如 element-plus 变量覆写）是否纳入 token 体系。
**需要查看**：`colors.ts`、`style.css`、全局样式文件、主题覆写文件。
**正常标准**：色值只有 `colors.ts` + CSS `--GCS-*` 两套且对齐；无散落色值常量；第三方覆写有映射注释。
**异常情况**：
- 存在第二个色值定义文件（如 `theme-dark.ts` 独立定义一套 hex）。
- `colors.ts` 与 `--GCS-*` 命名/值不对齐（同名不同值）。
- 组件 `<style>` 内 `--local-primary: #3b82f6` 局部重定义。
**风险等级**：P2（发现多套源且实际漂移时为 P1）
**整改方向**：合并到单一来源；`colors.ts` 与 `--GCS-*` 建立映射表；第三方覆写走注入。
**验收标准**：全项目色值来源唯一且对齐；映射表有文档。

### 指标 1.2：硬编码色值扫描
**指标名称**：硬编码色值扫描
**检查目标**：扫描所有样式/脚本中的字面色值（hex / rgb / hsl / 具名色），确认无业务样式写死颜色字面量。
**为什么需要检查**：硬编码色值是 GCS 设计系统违约的实锤表现，且破坏主题切换——暗色模式下硬编码浅色直接刺眼。
**检查范围**：所有 `.vue` 的 `<style>`、`.css`、`.ts/.js` 中出现的颜色字面量（排除测试与 mock）。
**检查方法**：
1. grep 正则：`#([0-9a-fA-F]{3}|[0-9a-fA-F]{6})\b` / `rgb\(` / `rgba\(` / `hsl\(` / `hsla\(` / 具名色（`white|black|red|blue|green|orange|purple|gray|grey|transparent|currentColor` 等）。
2. 对每个命中，判断是否可用 `var(--GCS-*)` 替代（排除：动画关键帧临时插值、第三方库强制值、canvas/svg 渲染数据色）。
3. 按文件分组统计命中，标注已知违约与新增违约。
4. 检查 `colors.ts` 内部定义（那里是允许的字面量来源）与业务代码的边界。
5. 检查是否误用 `currentColor`/`transparent`（它们是合法但需确认语义）。
**需要查看**：grep 命中清单、对应 file:line、豁免清单。
**正常标准**：业务样式无色值字面量；全部走 `var(--GCS-*)`；豁免项有注释。
**异常情况**：
- 全局 CSS / 组件 `<style>` / script 中散落 hex/rgb/hsl/具名色字面量（grep 定位：`#([0-9a-fA-F]{3}|[0-9a-fA-F]{6})\b`、`rgb\(`、`rgba\(`；历史反例 `style.css:102/108`、`PortInfoPanel.vue:54` 已随代码演进失效——2026-08-14 复核为空行/token 定义/flex 声明，不再作锚点）。
- `.vue` 内 `background: #fff` 浅色硬编码（暗色下失效）。
- ECharts option 内直接写 hex 而非引用图表 token。
**风险等级**：P2（若导致主题/暗色失效升 P1）
**整改方向**：字面量替换为 `var(--GCS-*)`；补对应 token 到 `colors.ts`；豁免项加 `// token 豁免：原因` 注释。
**验收标准**：grep 色值字面量仅剩豁免项；已知违约已修复；豁免清单可审计。

### 指标 1.3：语义变量命名一致性
**指标名称**：语义变量命名一致性
**检查目标**：确认 `--GCS-*` 命名语义统一（如 `--GCS-primary` / `--GCS-bg` / `--GCS-text`），无同义异名、无风格混用。
**为什么需要检查**：命名混乱导致同一语义多处命名，使用者不知道该引用哪个；历史上有 `Gcs`/`gcs` 大小写违规教训（已全量改正为全大写）。
**检查范围**：CSS `:root` 与主题块全部 `--GCS-*` 变量定义、组件引用。
**检查方法**：
1. 列出全部 `--GCS-*` 变量名，按前缀聚类（`--GCS-bg*` / `--GCS-text*` / `--GCS-border*` / `--GCS-primary*`）。
2. 检测同义异名（`--GCS-bg` vs `--GCS-background`、`--GCS-primary` vs `--GCS-main`）。
3. 检测风格混用（驼峰 `--GCS-primaryColor` vs 中划线 `--GCS-primary-color`、大小写违规 `--gcs-*`/`--Gcs-*`）。
4. 检测语义重叠（两个变量值相同但名字不同且都被引用——可能是废弃残留）。
5. 检查命名是否反映层级（`--GCS-bg` vs `--GCS-bg-hover` 的派生关系）。
**需要查看**：CSS 全部 `--GCS-*` 定义、grep 变量引用。
**正常标准**：每个语义唯一变量名；命名全中划线小写（`--GCS-` 前缀全大写）；派生变量有明确后缀约定（-hover/-active/-disabled/-50/-dark）。
**异常情况**：
- `--GCS-bg` 与 `--GCS-background` 并存且值不同。
- 出现 `--gcs-text`（小写前缀）或 `--GcsPanel-bg`（驼峰组件级）。
- `--GCS-primary-color` 与 `--GCS-primaryColor` 混用。
**风险等级**：P3（违规但历史已改正，新代码再犯升 P2）
**整改方向**：统一命名规范（见附录 D token 速查）；废弃别名；补命名检查到 stylelint。
**验收标准**：变量名语义唯一；grep 无风格违规。

### 指标 1.4：透明度与衍生色
**指标名称**：透明度与衍生色
**检查目标**：确认半透明/衍生色基于 token（如 `rgb(var(--GCS-primary) / 0.5)` 或 `--GCS-primary-50`），不写死 `rgba(#,0.x)`。
**为什么需要检查**：写死 `rgba(固定hex, 0.5)` 在主题切换时会与 token 主色脱钩——主色变了，衍生色还是旧主色。
**检查范围**：所有 `rgba(` / `hsla(` / `color-mix(` / `opacity` 叠加色、`--GCS-*-50` 类预定义衍生 token。
**检查方法**：
1. grep `rgba\(|hsla\(|color-mix\(` 命中，逐一判断：基于 token 透明（`rgb(var(--GCS-x) / a)`）→ 通过；固定 hex → 违约。
2. 检查衍生 token 命名（`--GCS-primary-50` 等）是否有定义且被引用。
3. 检查 `opacity` 属性使用：整元素透明度是否本可用 token 解决。
4. 检查 `color-mix` 使用（现代浏览器）是否基于 token。
5. 检查遮罩/蒙层色（overlay）是否有独立 token（`--GCS-overlay`）。
**需要查看**：grep 命中、CSS 定义、`colors.ts` 衍生色。
**正常标准**：衍生色基于 token 透明通道或预定义衍生 token；无固定 hex 衍生。
**异常情况**：
- `rgba(37, 99, 235, 0.5)` 写死（主色变暗色主题时不变）。
- `--GCS-primary-50` 定义但值写死为 rgba 而非派生计算。
- 多个组件各自写 `opacity: 0.6` 做遮罩（语义不一）。
**风险等级**：P3（暗色/主题切换下衍生色脱钩升 P2）
**整改方向**：改用 token 透明通道或预定义衍生 token；遮罩统一 `--GCS-overlay`。
**验收标准**：衍生色均基于 token；主题切换下衍生色随主色变化。

### 指标 1.5：色值语义层级完整性
**指标名称**：色值语义层级完整性
**检查目标**：确认 token 体系覆盖全部语义角色（primary/success/warning/danger/info、text 多级、bg 多级、border 多级），无"业务自造语义色"。
**为什么需要检查**：语义缺失会迫使组件用语义外的字面量（如"成功就用绿色"→ 散落 `#22c55e`）；语义完整则任何业务状态都有 token 可用。
**检查范围**：`colors.ts` 全部语义分组；业务组件中状态色（成功/警告/错误/信息/禁用/选中）引用。
**检查方法**：
1. 列出 `colors.ts` 语义角色清单（functional/text/bg/border/chart/overlay 六类是否齐）。
2. grep 业务中状态相关样式（`.success` / `.error` / `.warning` / `.active` / `.disabled`），检查引用的是 token 还是字面量。
3. 检查 text 层级（primary/secondary/muted/placeholder/disabled）是否齐全。
4. 检查 bg 层级（page/panel/elevated/hover/active/selected）是否齐全。
5. 检查 chart 色板（多分类色）是否成体系（≥6 色且可扩展）。
**需要查看**：`colors.ts`、业务组件状态样式。
**正常标准**：语义角色齐全；业务状态样式全部走 token；无"自造语义色"。
**异常情况**：
- 业务组件写 `.err { color: #ef4444 }` 而 token 无 `--GCS-danger`。
- text 只有一级，muted/placeholder 用 opacity 硬凑。
- chart 色板散落各图表组件。
**风险等级**：P2
**整改方向**：补齐语义 token；业务状态色迁移到 token；chart 色板收敛到 `colors.ts`。
**验收标准**：六类语义 token 齐全；业务状态零自造色。

### 指标 1.6：token 值出处与注释（可解释性）
**指标名称**：token 值出处与注释（可解释性）
**检查目标**：确认每个 token 值有出处（设计稿/品牌规范/推导公式），关键 token 有注释，无"魔法值 token"。
**为什么需要检查**：token 值无法解释 = 无法评审、无法演进；面试问"主色为什么是这个蓝"必须能答。
**检查范围**：`colors.ts` 全部值、CSS `:root` 定义。
**检查方法**：
1. 逐 token 检查是否有注释（品牌色出处/派生公式/历史决策）。
2. 检查数值是否为常见推导（如 50 档衍生、对比度计算而来）。
3. 检查是否有"抄来的但不知含义"的值（如随机 hex）。
**需要查看**：`colors.ts`、设计文档。
**正常标准**：关键 token 有出处注释；衍生色有公式说明；无不可解释值。
**异常情况**：`--GCS-primary: #2f5b8f` 无任何注释且设计稿查无此色。
**风险等级**：P3
**整改方向**：补注释（来源/公式/决策日期）；无法解释的值走评审。
**验收标准**：关键 token 注释覆盖率 100%。

### 指标 1.7：主题变量覆盖结构
**指标名称**：主题变量覆盖结构
**检查目标**：确认明暗主题通过「:root 基线 + 主题块覆盖」结构实现，无散落主题判断。
**为什么需要检查**：覆盖结构混乱（组件各自判断主题）会导致"只换一半"的中间态，且新主题（高对比度等）无法接入。
**检查范围**：CSS 主题块定义（`:root` / `[data-theme='dark']` / `.dark`）、组件内主题判断。
**检查方法**：
1. 定位主题入口：根元素 class/属性切换（`document.documentElement.dataset.theme` 或 classList）。
2. 检查 dark 块是否覆盖全部 `--GCS-*`（用 grep 对比两块的变量 key 集合）。
3. 检查组件内是否有 `[data-theme='dark']` 局部选择器或 JS 主题判断。
4. 检查基线变量（两主题相同的）是否合理放在 `:root`。
5. 检查新增 token 时是否两主题同步补（可通过 key 集合 diff 检测）。
**需要查看**：全局 CSS、主题切换入口（App.vue / main.ts / composable）。
**正常标准**：主题 = 根元素属性变化 + 对应覆盖块；无组件级主题判断；两主题 key 集合一致。
**异常情况**：
- dark 块缺 `--GCS-bg-elevated`（组件在暗色下用回基线浅色）。
- 组件内 `if (isDark) ...` 散落颜色判断。
- 新增 token 只加了 `:root` 没加 dark 块。
**风险等级**：P1（覆盖缺失直接导致暗色错误）
**整改方向**：统一覆盖结构；补 key 集合校验（脚本 diff 两主题块）。
**验收标准**：两主题 key 集合 diff = 空；组件级主题判断归零。

### 指标 1.8：图表色板 token 化
**指标名称**：图表色板 token 化
**检查目标**：确认 ECharts 等图表色板来自 `colors.ts` chart 分组，不散落各图表组件。
**为什么需要检查**：图表散落色板导致跨图表配色不一致，且主题切换时图表色板不同步（深色主题下浅色图表刺眼）。
**检查范围**：所有图表组件（RadarChart/LineChart/BarChart/剖面图/热力图色带）的色板来源。
**检查方法**：
1. grep 图表组件 option 中 `color:` 数组/`series.color`，检查来源。
2. 检查是否引用 `colors.ts` chart token（或通过 theme composable 注入）。
3. 检查热力图色带（gradient）是否 token 化。
4. 检查主题切换后图表是否重渲染（见 4.8 联动）。
**需要查看**：`visualization/charts/`、`colors.ts` chart 分组。
**正常标准**：图表色板单一来源（chart token）；跨图表配色一致。
**异常情况**：RadarChart 用一套 hex、LineChart 用另一套；option 内 `color: ['#5470c6', ...]` 抄自 ECharts 默认。
**风险等级**：P2
**整改方向**：色板收敛到 `colors.ts` chart 分组；图表组件消费 token。
**验收标准**：图表色板引用单一来源；grep 图表组件零散落 hex。

### 指标 1.9：信息色与装饰色区分
**指标名称**：信息色与装饰色区分
**检查目标**：确认语义色（信息/状态）走 token 且含义受控；装饰色（渐变、点缀）有边界不失控。
**为什么需要检查**：装饰色与语义色混用会导致"红色按钮"无法判断是危险操作还是装饰。
**检查范围**：业务中红/黄/绿/蓝的使用场景分类。
**检查方法**：
1. 按用途分类色值使用：状态语义（成功/警告/错误）vs 装饰（图标点缀/渐变）。
2. 检查装饰色是否成体系（有 token 或明确豁免）。
3. 检查语义色是否被误用为装饰（如 danger 色做按钮渐变）。
**需要查看**：业务组件色值引用。
**正常标准**：语义色用途受控；装饰色有边界与豁免注释。
**异常情况**：危险操作按钮用 success 绿；装饰渐变写死 5 个 hex 无 token。
**风险等级**：P3
**整改方向**：语义色用途清单化；装饰色收敛或豁免注释。
**验收标准**：语义/装饰分类清单可审计。

## 第二部分：间距 / 圆角 / 阴影 / 字体 token（可独立执行）

### 指标 2.1：间距刻度守约
**指标名称**：间距刻度守约
**检查目标**：确认 padding/margin/gap 使用间距 token（`--GCS-space-*` / `var(--GCS-gap)` 或 config.ts 常量），不用魔法数字。
**为什么需要检查**：魔法间距导致布局不统一，违背 GCS 网格布局引擎的设计意图（网格单元 80px、GAP 10px、PANEL_SPACING 20px）。
**检查范围**：所有 `.vue` `<style>`、`.css` 中的 `padding/margin/gap/inset/left/top/right/bottom` 数值。
**检查方法**：
1. grep `padding|margin|gap` 命中，提取全部数值。
2. 判断数值是否来自间距刻度（4/8/10/12/16/20/24/32 或 token 引用）。
3. 排除豁免：0、100%、auto、calc 布局占位、第三方组件内部。
4. 检查负间距（margin 负数 hack）是否有注释与用途。
5. 检查组件间间距是否用 PANEL_SPACING 而非各自 margin。
**需要查看**：grep 命中、`shared/layout/config.ts`、GCS 间距 token。
**正常标准**：间距全部走 token 刻度；负间距零或全注释。
**异常情况**：
- `padding: 13px` / `gap: 7px` 非刻度魔法数。
- 组件间用 `margin-right: 15px` 而体系是 20px。
- `margin-left: -5px` 无注释的 hack。
**风险等级**：P3
**整改方向**：替换为最近刻度 token；负间距改布局结构或加注释。
**验收标准**：间距无魔法数字；grep 命中仅豁免。

### 指标 2.2：圆角连续性（Apple 式连续圆角）
**指标名称**：圆角连续性（Apple 式连续圆角）
**检查目标**：确认圆角使用 radius token，且符合「连续圆角」设计哲学（嵌套元素圆角递减而非突变）。
**为什么需要检查**：设计明确要求 Apple 式连续圆角细节美学；散落 `border-radius` 破坏一致性；父子圆角相等产生视觉割裂。
**检查范围**：所有 `border-radius`、嵌套组件圆角关系。
**检查方法**：
1. grep `border-radius` 命中，提取数值。
2. 判断是否用 radius token（`--GCS-radius-*`，如 4/6/8/12/16 档）。
3. 对嵌套场景（Panel 内 Button、Card 内 Tag）检查圆角递减关系（外层大内层小）。
4. 检查圆形元素（`border-radius: 50%`）使用是否合理（按钮圆形/头像）。
5. 检查小组件（Tag/Badge）圆角是否过大会刺眼。
**需要查看**：grep 命中、GCS radius token、组件嵌套结构。
**正常标准**：圆角走 token；嵌套递减连续；50% 仅用于圆形元素。
**异常情况**：
- `border-radius: 6px` 散落而体系是 4/8。
- 外层 Panel 圆角 8 内层按钮圆角 12（突变）。
- 长矩形按钮 `border-radius: 50%`（畸形）。
**风险等级**：P3
**整改方向**：统一 radius token；调整嵌套递减；补 token 档位表（附录 D）。
**验收标准**：圆角 token 化且连续；grep 命中仅豁免。

### 指标 2.3：阴影与层级 token
**指标名称**：阴影与层级 token
**检查目标**：确认 box-shadow / 层级使用 elevation token，不写死 `box-shadow: 0 2px 8px #000`。
**为什么需要检查**：写死阴影在暗色模式下会过曝或不可见；层级无体系则"谁浮在上面"无法控制。
**检查范围**：所有 `box-shadow`、`z-index`。
**检查方法**：
1. grep `box-shadow` 命中，判断是否基于 elevation token（`--GCS-elevation-*` 或 `--GCS-shadow-*`）。
2. 检查阴影颜色是否含透明度且暗色下可接受（写死黑色阴影暗色下消失）。
3. 检查 `z-index` 使用是否有层级常量（panel/nav/overlay/modal/toast 分级）。
4. 检查 hover 阴影变化（浮起效果）是否走 token 档位切换。
**需要查看**：grep 命中、elevation token 定义。
**正常标准**：阴影走 elevation token；z-index 走层级常量；hover 阴影用档位切换。
**异常情况**：
- `box-shadow: 0 2px 8px rgba(0,0,0,.2)` 写死。
- `z-index: 9999` 散落。
- 暗色下阴影不可见（无暗色阴影 token）。
**风险等级**：P3（暗色下阴影失效升 P2）
**整改方向**：替换为 elevation token；z-index 收敛到层级常量；补暗色阴影。
**验收标准**：阴影无写死；z-index 无 9999 级散落。

### 指标 2.4：字体 / 字号 / 字重 token
**指标名称**：字体 / 字号 / 字重 token
**检查目标**：确认 font-family / font-size / font-weight / line-height 使用排版 token。
**为什么需要检查**：散落字号导致文字层级混乱；字号体系（12/13/14/16/20/24）缺失则标题与正文无法区分层级。
**检查范围**：所有 `font-size` / `font-weight` / `font-family` / `line-height` / `letter-spacing`。
**检查方法**：
1. grep `font-size` 命中，提取数值，判断是否来自排版 token（`--GCS-font-*` / `--GCS-text-*` / rem 刻度）。
2. grep `font-weight`，判断是否用 token 或标准化值（400/500/600/700，禁 550 之类）。
3. 检查 `font-family` 是否只出现在全局（组件内不重复定义字体栈）。
4. 检查 line-height 是否随字号成体系（1.2/1.4/1.6 档）。
5. 检查标题层级（h1-h4/面板标题）是否有统一字号映射。
**需要查看**：grep 命中、排版 token 定义、全局字体栈。
**正常标准**：排版走 token；字体栈全局单一定义；字重标准化。
**异常情况**：
- `font-size: 15px` / `font-weight: 500` 散落。
- 组件内重复定义 `font-family: 'PingFang SC', ...`。
- 标题字号每个页面各写各的（无层级映射）。
**风险等级**：P3
**整改方向**：归到排版 token；字体栈收敛全局；补标题层级映射。
**验收标准**：排版无魔法数字；字体栈全局唯一。

### 指标 2.5：行高与字距 token
**指标名称**：行高与字距 token
**检查目标**：确认 line-height / letter-spacing 使用排版 token，行高随字号缩放正确。
**为什么需要检查**：行高写死（如 `line-height: 20px`）在字号变化时文字截断或拥挤；字距（letter-spacing）散落导致标题/正文间距不统一。
**检查范围**：所有 `line-height` / `letter-spacing`。
**检查方法**：
1. grep `line-height` 命中：数值型（px）vs 比例型（1.4）vs token。
2. 检查小字号（12px）行高是否足够（≥1.4 避免截断）。
3. grep `letter-spacing`：标题加宽（0.5px 级）与正文默认是否有约定。
**需要查看**：grep 命中、排版 token。
**正常标准**：行高走 token/比例；字距有语义约定（标题/正文）。
**异常情况**：`line-height: 20px` 固定；标题字距各写各的。
**风险等级**：P3
**整改方向**：行高 token 化（按字号档）；字距约定化。
**验收标准**：行高/字距无散落魔法值。

### 指标 2.6：间距组合规则与负间距治理
**指标名称**：间距组合规则与负间距治理
**检查目标**：确认组件间距用「容器 padding + 子项 gap」组合而非「每个子项各自 margin」；负间距有明确治理。
**为什么需要检查**：各自 margin 的间距无法被容器统一控制（换行/缩放时错位）；负间距是布局 hack，数量一多必然失控。
**检查范围**：列表/网格/按钮组/面板内容的间距实现方式。
**检查方法**：
1. 对重复结构（按钮组、列表项、面板内多块），检查是容器 gap 还是逐子 margin。
2. 统计负 margin/负 inset 出现次数，检查每处用途注释。
3. 检查 `:last-child { margin-right: 0 }` 类修复是否被 gap 替代。
**需要查看**：业务组件布局代码。
**正常标准**：间距组合统一走 gap/padding；负间距零或全注释且可解释。
**异常情况**：按钮组 `button + button { margin-left: 10px }` 而非 gap；`margin-right: -10px` 无注释。
**风险等级**：P3
**整改方向**：改 gap 布局；负间距注释化或重构。
**验收标准**：重复结构间距单一实现；负间距 ≤ 3 处且有注释。

### 指标 2.7：边框与分割线 token
**指标名称**：边框与分割线 token
**检查目标**：确认 border-width / border-color / 分割线使用 token，无散落 `border: 1px solid #e5e7eb`。
**为什么需要检查**：分割线颜色是暗色模式最容易漏的地方（浅灰线暗色下不可见或过亮）。
**检查范围**：所有 `border` / `outline` / `box-shadow` 模拟分割线。
**检查方法**：
1. grep `border` 命中：宽度是否用 token（1px 统一或 `--GCS-border-width-*`）；颜色是否 `--GCS-border*`。
2. 检查分割线（border-bottom 等）颜色在暗色下可见。
3. 检查 outline（聚焦环）是否有独立 token（`--GCS-focus-ring`）。
**需要查看**：grep 命中、border token 定义。
**正常标准**：边框颜色全 token；聚焦环有独立 token；暗色下分割线可见。
**异常情况**：`border-bottom: 1px solid #e5e7eb` 写死；聚焦环用默认 outline 无样式。
**风险等级**：P3（暗色分割线失效升 P2）
**整改方向**：边框 token 化；聚焦环 token 化。
**验收标准**：边框零散落色值；聚焦环可见且统一。

### 指标 2.8：z-index 层级管理
**指标名称**：z-index 层级管理
**检查目标**：确认 z-index 使用层级常量体系（panel/nav/drawer/overlay/modal/toast），无 9999 散落。
**为什么需要检查**：z-index 无体系则弹窗被面板盖住、toast 被 modal 盖住——交互不可用。
**检查范围**：全部 `z-index`。
**检查方法**：
1. grep `z-index` 命中，提取全部数值。
2. 对照层级约定（GCS 面板 base / 抽屉 / 导航 / 遮罩 / 弹窗 / toast）检查是否有常量（如 `shared/constants/ui.ts` 的 Z_* 或 CSS 变量）。
3. 检查 Modal/Drawer/Toast 的挂载层级与 z-index 关系。
**需要查看**：grep 命中、层级常量定义。
**正常标准**：z-index 全部走常量；层级关系正确（toast > modal > overlay > drawer > panel）。
**异常情况**：`z-index: 9999` 散落；toast 与 modal 同层竞争。
**风险等级**：P2（层级错乱导致交互失效升 P1）
**整改方向**：收敛到层级常量；补层级表（附录 D）。
**验收标准**：z-index 零散落；层级关系测试通过（打开全组件叠加）。

### 指标 2.9：尺寸与比例 token
**指标名称**：尺寸与比例 token
**检查目标**：确认组件尺寸（宽/高/最小尺寸）、图标尺寸、比例走 token，无散落尺寸魔法值。
**为什么需要检查**：按钮高度 32/36/40 应成体系；图标 16/20/24 应成体系；散落尺寸导致组件视觉不齐。
**检查范围**：`width/height/min-width/min-height` 数值、图标 `font-size`/尺寸属性、按钮/输入框高度。
**检查方法**：
1. grep 尺寸数值，聚类（按钮高、输入框高、图标尺寸、面板宽）。
2. 对照尺寸 token（`--GCS-size-*` 或 config 常量）判断是否成体系。
3. 检查大尺寸（面板宽）是否走 Cell 网格（80 倍数）。
**需要查看**：grep 命中、尺寸 token、`config.ts`（CELL_PIXEL）。
**正常标准**：小尺寸（按钮/图标/输入框）成体系；大尺寸（面板）走 Cell 网格。
**异常情况**：按钮高度 33px（体系外）；面板宽 340px（非 80 倍数）。
**风险等级**：P3
**整改方向**：尺寸 token 化；面板宽改 `useGCS.cell(n)`。
**验收标准**：尺寸聚类全部落入体系档位。

### 指标 2.10：动画时长与缓动 token
**指标名称**：动画时长与缓动 token
**检查目标**：确认 transition/animation 的时长与缓动函数走 token，无散落 `transition: all 0.3s`。
**为什么需要检查**：动画节奏不统一导致界面"忽快忽慢"；`transition: all` 会拖慢性能且触发意外动画。
**检查范围**：全部 `transition` / `animation` / `transition-duration`。
**检查方法**：
1. grep `transition|animation` 命中：时长是否来自 token（`--GCS-duration-fast/medium/slow`）；缓动是否 token（`--GCS-ease-*`）。
2. 检查 `transition: all` 使用（应禁止，除非豁免）。
3. 检查暗色模式切换的过渡动画（theme 切换本身是否平滑）。
**需要查看**：grep 命中、动画 token 定义。
**正常标准**：时长/缓动走 token；无 `transition: all`；主题切换有过渡。
**异常情况**：`transition: all 0.3s` 散落；时长短中快无体系。
**风险等级**：P3
**整改方向**：动画 token 化；`all` 改具体属性。
**验收标准**：动画属性零散落；时长档位表可审计。

## 第三部分：组件级样式一致性（可独立执行）

### 指标 3.1：组件使用 GCS 布局引擎而非手搓布局
**指标名称**：组件使用 GCS 布局引擎而非手搓布局
**检查目标**：确认业务组件布局走 GCS 体系（`useGCS` 网格 / `GCSPanel` 容器），无手搓 flex/absolute 布局绕过。
**为什么需要检查**：GCS 的核心价值是"布局是网格约定不是组件库"——手搓布局是体系外的第一类违约，且不受响应式三档（≥960/640-959/<640）约束；手写 `position: absolute; left: 123px` 在抽屉/移动端直接错位。
**检查范围**：所有业务 `.vue` 的模板与 `<style>`；布局相关 composable 调用（`useGCS`/`useSliderFocus` 等）。
**检查方法**：
1. 列出业务页/面板组件的根元素布局方式（`position: absolute` / `display: flex` + 手写偏移 / `fixed`）。
2. 对每个手搓布局，判断是否应使用 `GCSPanel`（`:w :h anchor`）或 `useGCS` 计算值。
3. 豁免清单核对：页面级骨架（AppLayout 自身）、单行小部件（按钮内 flex 居中）、第三方组件内部。
4. 检查手写偏移数值是否可换算为 Cell/GAP 倍数（若是，说明该用引擎）。
5. 检查响应式行为：手搓布局在抽屉模式（640-959）与紧凑模式（<640）是否断裂。
**需要查看**：业务组件模板、`shared/layout/useGCS.ts`、`core/layout/components/GCSPanel.vue`、`AppLayout.vue`。
**正常标准**：面板级组件全部经 GCS 布局；手搓布局仅存在于豁免清单；偏移可换算为网格倍数。
**异常情况**：
- 业务面板手写 `position: absolute; left: 123px; top: 45px`（非网格、非锚点）。
- 业务组件手写 flex 布局模拟面板（重复实现 GCSPanel 能力）。
- 手搓布局在 <640px 下溢出屏幕。
**风险等级**：P2（移动端断裂升 P1）
**整改方向**：迁移到 GCSPanel + 锚点定位；布局常量走 `config.ts`；豁免清单更新。
**验收标准**：业务面板零手搓定位（豁免清单除外）；三档响应式下布局正确。

### 指标 3.2：GCS 标准组件复用率（伪 GCS 组件识别）
**指标名称**：GCS 标准组件复用率（伪 GCS 组件识别）
**检查目标**：识别"长得像 GCS、实为自绘"的伪组件，确认标准组件（GCSPanel / GCSButton / NavButton / BottomNavBar / MobileDrawer / TitlePanel）被正确复用。
**为什么需要检查**：伪 GCS 组件导致同一交互在多处有不同实现，样式维护双倍成本；暗色模式适配需要多处重复；新组件演进（如 GCSPanel 加动画）无法惠及伪组件。
**检查范围**：`core/layout/components/` 标准组件清单 vs 业务组件内相似实现。
**检查方法**：
1. 列出现有标准组件清单（GCSPanel/GCSButton/NavButton/BottomNavBar/MobileDrawer/TitlePanel/DebugToggle 等）。
2. 在业务组件中搜索手写同类结构（手写圆形按钮+悬浮定位、手写面板容器、手写导航条）。
3. 计算复用覆盖率：标准组件被引用次数 / 应使用场景数。
4. 检查新组件立项路径：是否评估过"进 core/layout/components/"（对照根基文档 03 §1.4 组件拆分标准）。
5. 检查 shared/components 与 core/layout/components 的边界（通用 vs 布局）。
**需要查看**：`core/layout/components/`、`shared/components/`、业务组件模板。
**正常标准**：同类交互复用标准组件；新组件需求先评估归属；复用覆盖率可量化。
**异常情况**：
- 业务组件内重复实现 GCSPanel 风格的面板容器（同样式两处维护）。
- 三处按钮实现（GCSButton/业务自绘/Element Plus 裸用）视觉不一。
**风险等级**：P2
**整改方向**：抽公共组件进 `core/layout/components/`（或 shared/components/），按 03 §1.4 拆分标准判定；伪组件迁移。
**验收标准**：标准组件清单与实际使用对齐；伪组件归零或列入迁移计划。

### 指标 3.3：组件 `<style>` 作用域与全局污染
**指标名称**：组件 `<style>` 作用域与全局污染
**检查目标**：确认组件样式使用 `scoped`，无全局选择器污染其他组件。
**为什么需要检查**：非 scoped 样式会泄漏到全应用——`.title { color: red }` 写一次全站标题变红；主题切换时出现"幽灵样式"难以排查。
**检查范围**：所有 `.vue` 的 `<style>` 块（scoped 属性、`:deep()` 使用、非 scoped 清单）。
**检查方法**：
1. grep `<style` 命中，检查是否带 `scoped`。
2. 对非 scoped 样式，判断是否故意（全局变量/重置类/reset 文件除外），并检查选择器宽度。
3. 检查 `:deep()` 使用是否必要（覆盖第三方组件内部）且选择器有前缀限定。
4. 检查 `v-html` 内容的样式作用域（scoped 下 `v-html` 内容不受 scoped 影响——需注意）。
5. 检查全局样式文件（style.css）的职责边界（变量/reset/基础元素样式 vs 组件样式）。
**需要查看**：grep 命中、组件样式、全局样式文件。
**正常标准**：业务组件全部 scoped；非 scoped 仅存在于全局样式文件与明确 reset；`:deep()` 有前缀限定。
**异常情况**：
- 业务组件非 scoped 且选择器过宽（直接写 `.panel` 而非 `.xxx-panel`）。
- `:deep(.el-input)` 无前缀（影响所有 el-input）。
- 全局样式文件里混入组件级样式。
**风险等级**：P3（实际污染事故升 P2）
**整改方向**：加 scoped；`:deep()` 加前缀；全局文件职责清理。
**验收标准**：业务组件 scoped 覆盖率 100%；非 scoped 清单可审计。

### 指标 3.4：响应式断点一致性
**指标名称**：响应式断点一致性
**检查目标**：确认组件响应式行为只依赖 GCS 三档断点（≥960 / 640-959 / <640），无自造断点。
**为什么需要检查**：自造断点（如 `@media (max-width: 768px)`）与 GCS 三档判定不一致会导致抽屉/面板行为错乱——历史实锤：MobileDrawer 注释与代码断点曾漂移（注释 768 vs 代码 960）。
**检查范围**：所有 `@media` 查询、`windowWidth`/`useGCS` 消费、断点常量引用（LAYOUT_DESKTOP_MIN=960 / LAYOUT_DRAWER_MIN=640）。
**检查方法**：
1. grep `@media` 命中，检查数值是否与常量一致（960/640 或 1920 cell 档）。
2. 检查组件是否通过 `useGCS()` 的 computed（showPanels/showTopArea/navCompact）消费断点，而非自算 `window.innerWidth`。
3. 检查注释/文档中的断点数字与代码常量一致（防漂移）。
4. 检查 960 边界附近（959/960/961）行为连续性（抽屉 ↔ 桌面切换无撕裂）。
5. 检查 640 边界附近（抽屉紧凑切换）。
**需要查看**：grep 命中、`shared/layout/config.ts`、`useGCS.ts`。
**正常标准**：断点全部来自常量；组件消费 computed；注释与代码一致；边界连续。
**异常情况**：
- 组件内 `window.innerWidth < 768` 自判。
- 注释写 768 代码用 960。
- 960px 处面板与抽屉同时渲染或同时消失。
**风险等级**：P2（自造断点导致抽屉行为错乱时为 P1）
**整改方向**：改走 `useGCS` computed；注释与代码对齐；边界测试。
**验收标准**：全项目断点引用仅剩常量源；960/640 边界行为测试通过。

### 指标 3.5：布局常量守约（CELL / GAP 不散落）
**指标名称**：布局常量守约（CELL / GAP 不散落）
**检查目标**：确认面板尺寸/间距/边距全部来自 `config.ts` 常量（CELL_PIXEL/GAP/PANEL_SPACING/SAFE_MARGIN/GRID_SIZE），无散落数值。
**为什么需要检查**：散落数值（如 `width: 320px` 手写）绕过网格体系，网格档位调整（90/80/70）时不同步；GAP 变化时散落间距纹丝不动。
**检查范围**：业务组件中的尺寸/间距字面量、`useGCS` 调用点。
**检查方法**：
1. grep `px` 命中，对面板类组件判断宽高是否 80 的整数倍（Cell 倍数）。
2. 判断间距是否 GAP(10)/PANEL_SPACING(20) 倍数。
3. 检查是否引用常量或 `useGCS.cell()`/`useGCS.gap()`。
4. 检查 SAFE_MARGIN 使用（贴边面板的安全边距）。
**需要查看**：grep 命中、`config.ts`、`useGCS.ts`。
**正常标准**：面板尺寸 = 整数 Cell；间距 = GAP 倍数；引用常量或引擎计算。
**异常情况**：
- `width: 340px`（非 80 倍数）手写。
- `margin: 15px`（非 GAP 倍数）。
- 面板贴边无 SAFE_MARGIN（贴屏）。
**风险等级**：P3
**整改方向**：改为 `useGCS.cell(n)`/`gap()` 或常量引用。
**验收标准**：业务面板尺寸/间距零散落字面量。

### 指标 3.6：组件状态样式完整性（hover/active/disabled/focus）
**指标名称**：组件状态样式完整性（hover/active/disabled/focus）
**检查目标**：确认交互组件四态（默认/hover/active/disabled/focus）样式齐全且走 token，无遗漏状态。
**为什么需要检查**：状态遗漏（如按钮无 disabled 样式）导致用户无法感知可操作性；focus 环缺失影响键盘可达性（a11y）。
**检查范围**：按钮/输入框/滑块/开关/列表项/标签等交互组件的状态样式。
**检查方法**：
1. 对每个交互组件，检查 :hover/:active/:disabled/:focus-visible 样式。
2. 检查 disabled 是否降低对比度（不透明度或灰化 token）。
3. 检查 focus-visible 环（键盘导航可见，鼠标点击不显示环）。
4. 检查状态色是否走 token（hover 用 `--GCS-*-hover`）。
**需要查看**：交互组件样式、状态 token。
**正常标准**：四态齐全；disabled 有视觉降级；focus 环可见且 token 化。
**异常情况**：按钮无 disabled 样式（禁用后仍可点击视觉）；focus 环被 `outline: none` 去掉且无替代。
**风险等级**：P2（a11y 缺失升 P1）
**整改方向**：补状态样式；focus 环 token 化；禁用态统一。
**验收标准**：全交互组件四态验收清单通过。

### 指标 3.7：组件内部 class 命名规范
**指标名称**：组件内部 class 命名规范
**检查目标**：确认组件内部 class 命名语义化（BEM 或统一前缀），无语义不明缩写与层级混乱。
**为什么需要检查**：`class="a1 b2"` 无法维护；命名无规范则样式覆盖链不可控。
**检查范围**：业务组件模板 class、`:deep()` 目标 class。
**检查方法**：
1. 抽查组件模板 class 命名：是否语义化（`panel-header` vs `ph`）。
2. 检查是否有前缀约定（组件名缩写前缀或 BEM 块）。
3. 检查 `:deep()` 引用的第三方 class 与自有 class 的区分。
**需要查看**：业务组件模板。
**正常标准**：class 语义化可读；命名风格全项目一致。
**异常情况**：`class="w"` 缩写；同语义两个命名（`panel-title`/`title`）。
**风险等级**：P3
**整改方向**：命名规范化；样式覆盖链走 BEM 或统一前缀。
**验收标准**：组件 class 命名抽查合格。

### 指标 3.8：图标与图片处理
**指标名称**：图标与图片处理
**检查目标**：确认图标统一走图标体系（icon 组件/图标字体），图片有主题适配与加载占位。
**为什么需要检查**：图标散落（emoji/手写 SVG/图片混用）视觉不统一；图片无占位导致布局抖动；暗色模式图片过亮刺眼。
**检查范围**：图标使用（icon 组件/emoji/SVG 内联）、`<img>`/背景图、加载占位。
**检查方法**：
1. 统计图标使用方式分布（icon 体系 vs emoji vs 内联 SVG vs 图片）。
2. 检查图标尺寸/颜色是否可被 token 控制（stroke/fill 用 currentColor）。
3. 检查图片加载失败/加载中占位。
4. 检查暗色下图片处理（亮度/遮罩/替换源）。
**需要查看**：图标组件、业务图标使用、图片组件。
**正常标准**：图标单一体系且颜色随 token；图片有占位与失败态；暗色适配。
**异常情况**：emoji 与 icon 混用；SVG fill 写死色值；图片加载白屏。
**风险等级**：P3
**整改方向**：图标收敛体系；SVG 用 currentColor；补图片占位。
**验收标准**：图标体系单一；图片三态（加载/成功/失败）齐全。

### 指标 3.9：滚动条与溢出处理
**指标名称**：滚动条与溢出处理
**检查目标**：确认滚动条样式统一（自定义滚动条 token），溢出场景有明确策略（滚动/省略/截断）。
**为什么需要检查**：默认滚动条在暗色下刺眼；溢出无策略导致内容截断不可见。
**检查范围**：滚动容器、文本溢出（省略号）、表格/列表溢出。
**检查方法**：
1. grep 滚动容器样式（overflow/::-webkit-scrollbar），检查是否统一。
2. 检查长文本溢出处理（ellipsis 使用）。
3. 检查列表/面板内容溢出策略（滚动 vs 分页）。
**需要查看**：滚动容器样式、文本组件。
**正常标准**：滚动条统一 token；溢出策略明确；无内容不可达。
**异常情况**：滚动条样式只在一处自定义；长文本硬截断无省略号。
**风险等级**：P3
**整改方向**：滚动条 token 化；溢出统一策略。
**验收标准**：滚动条全站统一；溢出场景无内容丢失。

### 指标 3.10：表单控件一致性
**指标名称**：表单控件一致性
**检查目标**：确认输入框/滑块/开关/单选/复选视觉统一（同尺寸/同边框/同聚焦环），禁用态统一。
**为什么需要检查**：表单控件散落实现（部分 Element Plus、部分自绘）导致视觉分裂；尺寸不一在并排时对不齐。
**检查范围**：全部表单控件实现与尺寸。
**检查方法**：
1. 列出表单控件实现来源（Element Plus/自绘/混合）。
2. 检查控件高度/边框/圆角/聚焦环一致性。
3. 检查禁用态统一（灰化方式一致）。
**需要查看**：表单组件、Element Plus 主题覆写。
**正常标准**：控件视觉体系统一；禁用态一致。
**异常情况**：输入框 32px 高、自绘滑块 28px 高并排错位；禁用态一半透明度一半灰色。
**风险等级**：P2
**整改方向**：统一尺寸 token；禁用态统一实现。
**验收标准**：表单控件并排对齐；禁用态视觉一致。

## 第四部分：主题切换与暗色模式（可独立执行）

### 指标 4.1：暗色模式色值全部经 token
**指标名称**：暗色模式色值全部经 token
**检查目标**：确认暗色模式下所有色值经 token 切换，无硬编码色导致暗色下不可读/刺眼。
**为什么需要检查**：暗色模式是全站能力（🌙/☀️ 切换，深蓝+橙主题），硬编码色值是暗色失效的头号原因——白底黑字在暗色下直接刺眼。
**检查范围**：全部样式 + `colors.ts` 的暗色分支定义 + 1.2 硬编码扫描结果交叉核对。
**检查方法**：
1. 开启暗色模式，逐页（首页/选址/预测/浸没/个人中心）检查文字/背景/边框对比度。
2. 对照 1.2 的硬编码扫描结果：命中项在暗色下是否仍可读。
3. 检查 `colors.ts` 是否提供暗色 token（如 `--GCS-bg-dark` 或主题对象双份定义）。
4. 检查 ECharts/地图在暗色下的表现（图表背景/文字）。
5. 检查暗色下图片/图标（见 3.8）。
**需要查看**：`colors.ts`、暗色模式实现（主题切换入口）、全站页面。
**正常标准**：暗色下全部文字/背景/边框走 token；无不可读区域；图表适配。
**异常情况**：
- 某组件暗色下白底黑字（硬编码未走 token）。
- 图表文字暗色下不可见（ECharts textStyle 未适配）。
- 暗色下分割线消失（border token 未覆盖）。
**风险等级**：P1（暗色失效直接影响用户体验与作品集展示）
**整改方向**：硬编码替换为 token；`colors.ts` 补暗色定义；图表适配。
**验收标准**：暗色模式逐页验收通过，无硬编码残留。

### 指标 4.2：主题切换时 CSS 变量整体替换
**指标名称**：主题切换时 CSS 变量整体替换
**检查目标**：确认主题切换（明/暗）通过 CSS 变量整体替换实现，无"只换一半"的中间态。
**为什么需要检查**：部分组件用 JS 状态判断颜色、部分用 CSS 变量，切换时出现混合状态——切换瞬间"半明半暗"。
**检查范围**：主题切换入口（App 层）、`colors.ts`、组件内 `isDark` 类判断。
**检查方法**：
1. 定位主题切换实现（class 切换 / data-theme / 变量覆写）。
2. 检查是否所有颜色消费点都走同一变量体系（无组件内 `isDark ? '#fff' : '#000'` 分支）。
3. 检查 ECharts 等图表实例是否随主题重建/更新（图表色板与主题同步）。
4. 检查切换瞬间的过渡（无闪烁，见 4.10）。
**需要查看**：主题切换入口、`colors.ts`、图表初始化代码。
**正常标准**：切换 = 一个根元素 class/属性变化，全部颜色随之变化；图表色板同步。
**异常情况**：
- 组件内 `isDark` 分支手写颜色。
- 图表在主题切换后色板不变（保持亮色）。
- 切换后部分区域延迟变色（transition 不齐）。
**风险等级**：P1
**整改方向**：统一走变量体系；图表监听主题变化更新 option。
**验收标准**：切换瞬间全站颜色一致变化，无中间态。

### 指标 4.3：明暗对比度达标（WCAG AA）
**指标名称**：明暗对比度达标（WCAG AA）
**检查目标**：确认明暗两套主题的文字/背景对比度满足 WCAG AA（正文 ≥ 4.5:1，大文本 ≥ 3:1）。
**为什么需要检查**：对比度不足在暗色模式尤其常见（深蓝底 + 低饱和文字），影响可读性与面试展示质量。
**检查范围**：主题 token 对（primary/bg/text/secondary/muted/border 等组合）。
**检查方法**：
1. 对 token 组合计算对比度：`(L1+0.05)/(L2+0.05)`，L = 相对亮度（sRGB 线性化）。
2. 标注 AA/AAA 达标情况（正文 4.5:1 / 大文本 3:1 / AAA 7:1）。
3. 重点检查 muted/placeholder 文字与背景的组合。
4. 检查暗色下 success/warning/danger 语义色的对比度（低饱和在暗色下可能不足）。
**需要查看**：`colors.ts` 全部 token 对。
**正常标准**：正文组合 ≥ 4.5:1；大文本 ≥ 3:1；禁用态可豁免但须有区分。
**异常情况**：
- muted 文字在暗色下对比度 < 3:1。
- 警告色文字在暗色背景上 < 2:1（不可读）。
**风险等级**：P2
**整改方向**：调整 token 亮度/饱和度；补充对比度达标表到 `colors.ts` 注释。
**验收标准**：明暗主题 token 对对比度表全部达标（附计算值）。

### 指标 4.4：主题偏好记忆与跟随系统
**指标名称**：主题偏好记忆与跟随系统
**检查目标**：确认主题偏好持久化（localStorage）+ 跟随系统（prefers-color-scheme）行为正确，刷新/重进不丢失。
**为什么需要检查**：偏好记忆是已声明能力（"偏好本地记忆 + 跟随系统"），失效即功能缺陷；首屏闪白（FOUC）是常见翻车点。
**检查范围**：主题初始化逻辑、存储键、系统监听（matchMedia）。
**检查方法**：
1. 检查主题初始化顺序：localStorage → 无则系统偏好 → 默认亮色。
2. 检查 `matchMedia('(prefers-color-scheme: dark)')` change 监听是否生效。
3. 检查首屏闪白：初始化脚本是否在渲染前执行（index.html 内联或 main.ts 前置）。
4. 检查存储键命名与清理（登出是否清主题偏好——应保留）。
5. 检查跟随系统模式下手动切换后的优先级（手动选择应覆盖系统并记忆）。
**需要查看**：主题入口、App.vue、main.ts、index.html。
**正常标准**：刷新保持偏好；系统切换实时跟随；首屏无闪白；手动选择优先且记忆。
**异常情况**：
- 刷新后主题重置为默认（未读 localStorage）。
- 系统暗色切换不响应（无监听）。
- 首屏白闪（FOUC）。
- 登出清除了主题偏好（不该清）。
**风险等级**：P2
**整改方向**：补初始化逻辑/监听；首屏内联样式防 FOUC；存储键分离用户态。
**验收标准**：偏好记忆 + 系统跟随 + 无闪白三项验收通过。

### 指标 4.5：主题 token 双份定义完整性
**指标名称**：主题 token 双份定义完整性
**检查目标**：确认 light/dark 两主题的 token key 集合完全一致（无缺失、无多余）。
**为什么需要检查**：dark 块缺失某 key 时，组件在暗色下回退到基线（可能是亮色值）——最隐蔽的暗色 bug。
**检查范围**：`:root`（light 基线）与 `[data-theme='dark']`（或 .dark）块的变量 key 集合。
**检查方法**：
1. 用脚本提取两块的 `--GCS-*` key 集合，做 diff。
2. 对 dark 独有 key（暗色专属如 `--GCS-overlay-dark`）确认是有意设计。
3. 检查 light 独有 key 是否被 dark 继承（基线语义）。
**需要查看**：全局 CSS 主题块、脚本 diff 结果。
**正常标准**：两主题 key 集合 diff 为空（或差异全注释说明）。
**异常情况**：dark 缺 `--GCS-border-subtle`（暗色下边框用回基线浅色）。
**风险等级**：P1
**整改方向**：补缺失 key；diff 脚本接入 CI 或执行清单。
**验收标准**：key 集合 diff 为空；diff 脚本可用。

### 指标 4.6：组件局部主题覆写受控
**指标名称**：组件局部主题覆写受控
**检查目标**：确认组件内 `data-theme`/class 局部覆写受控（有注释/有清单），不散落。
**为什么需要检查**：局部覆写散落会导致"这个组件在暗色下是另一个样子"且无人知道为什么。
**检查范围**：组件内主题判断、局部 class 切换、`:global([data-theme])` 选择器。
**检查方法**：
1. grep 组件内 `data-theme` / `.dark` / `isDark` / `theme ===` 使用。
2. 对每处判断用途分类：受控设计（如代码块保持亮色）vs 临时 hack。
3. 检查受控覆写是否有注释说明。
**需要查看**：grep 命中。
**正常标准**：局部覆写零或全注释且语义合理。
**异常情况**：3 处以上无注释的 `isDark ? ... : ...`。
**风险等级**：P2
**整改方向**：覆写收敛（token 化或组件级主题块）；补注释。
**验收标准**：局部覆写清单可审计。

### 指标 4.7：第三方组件主题适配
**指标名称**：第三方组件主题适配
**检查目标**：确认第三方库（Element Plus 等）组件在明暗两主题下视觉一致（通过变量覆写而非样式补丁）。
**为什么需要检查**：第三方组件默认亮色样式在暗色下刺眼；用样式补丁（!important 覆盖）会脆弱。
**检查范围**：Element Plus 变量覆写文件、第三方组件在暗色下的表现。
**检查方法**：
1. 检查是否通过 Element Plus CSS 变量覆写（--el-color-primary 等映射到 --GCS-*）。
2. 检查覆写是否双主题各一份。
3. 检查补丁式覆盖（`!important`）数量。
**需要查看**：样式覆写文件、全局样式。
**正常标准**：第三方组件走变量覆写；双主题映射完整；`!important` 补丁 ≤ 3。
**异常情况**：Element Plus 暗色下弹窗白底；`!important` 覆盖 10+ 处。
**风险等级**：P2
**整改方向**：变量覆写映射表；补丁收敛。
**验收标准**：第三方组件双主题验收通过。

### 指标 4.8：图表/地图主题联动
**指标名称**：图表/地图主题联动
**检查目标**：确认图表（ECharts）与地图（底图/图层）随主题联动，无"页面暗色、图表亮色"分裂。
**为什么需要检查**：图表与地图是大面积视觉区域，主题不同步直接破坏整体观感；演示时被一眼看穿。
**检查范围**：ECharts 实例（雷达/折线/柱状/剖面）、地图底图（天地图影像/矢量明暗）、图层样式。
**检查方法**：
1. 检查 ECharts 主题切换：option 是否随主题重建（textStyle/backgroundColor/color 数组）。
2. 检查地图底图在暗色下的选择（矢量底图暗色样式或影像变暗）。
3. 检查业务图层（热力图/POI）颜色在暗色下可见。
**需要查看**：图表 composable、地图底图配置、图层样式。
**正常标准**：图表随主题联动；地图底图可选暗色；图层可见。
**异常情况**：暗色下雷达图背景白；热力图色带不可见。
**风险等级**：P1（大面积视觉分裂）
**整改方向**：图表主题化封装（一个 composable 管理）；底图/图层主题映射。
**验收标准**：全站（页面+图表+地图）主题一致。

### 指标 4.9：暗色下的语义色调整
**指标名称**：暗色下的语义色调整
**检查目标**：确认暗色下语义色（success/warning/danger）饱和度与亮度经过调整（非原样搬运）。
**为什么需要检查**：亮色主题的高饱和语义色在暗色背景下刺眼且对比度不足。
**检查范围**：暗色主题块的语义色 token。
**检查方法**：
1. 对比 light/dark 的语义色 token 值（是否刻意调整）。
2. 检查暗色下 warning 文字可读性（黄字深底 vs 深黄字）。
3. 检查暗色下 danger 按钮（红色按钮在暗色下的亮度）。
**需要查看**：`colors.ts` 暗色分支。
**正常标准**：语义色在暗色下有专门调整（变亮或降饱和）；可读性达标。
**异常情况**：暗色直接复用亮色语义色（刺眼/不可读）。
**风险等级**：P2
**整改方向**：暗色语义色单独定义；对比度验证。
**验收标准**：暗色语义色清单与对比度表。

### 指标 4.10：主题切换性能与过渡
**指标名称**：主题切换性能与过渡
**检查目标**：确认主题切换流畅（无闪烁/无布局抖动/无卡顿），切换过渡（如有）平滑。
**为什么需要检查**：切换卡顿或闪烁 = 直接可感知的体验缺陷；`transition: all` 在主题切换时会触发大量动画。
**检查范围**：主题切换触发路径、全局 transition 配置。
**检查方法**：
1. 实测切换耗时（Performance 面板，无 longtask）。
2. 检查是否有 `transition: all` 导致主题切换动画风暴。
3. 检查切换是否触发布局抖动（宽度/高度变化）。
4. 检查切换瞬间是否白屏/黑屏闪烁。
**需要查看**：主题入口、全局样式、Performance 实测。
**正常标准**：切换 < 100ms 无卡顿；无闪烁；无布局抖动。
**异常情况**：切换卡顿（大量组件重排）；白闪；`transition: all` 动画风暴。
**风险等级**：P2
**整改方向**：过渡属性精确化；闪烁加防 FOUC 样式。
**验收标准**：切换实测报告（Performance 数据）。

## 第五部分：token 工程与治理（可独立执行）

### 指标 5.1：token 变更影响面评估
**指标名称**：token 变更影响面评估
**检查目标**：确认改 token 前有影响面评估（谁在用、改哪里），变更后有验证。
**为什么需要检查**：改 `--GCS-primary` 影响全站按钮/选中态/图表；无影响面评估 = 改完 UI 崩。
**检查范围**：token 变更流程、grep 引用能力。
**检查方法**：
1. 检查是否有变更 SOP（改前 grep 引用 → 评估影响 → 改 → 双主题验证 → 截图对比）。
2. 检查 token 引用统计方式（grep 可查）。
3. 检查历史变更是否有遗留（改了一半的 token）。
**需要查看**：变更记录、grep 实践。
**正常标准**：变更 SOP 文档化；每次变更走全流程。
**异常情况**：直接改 `colors.ts` 无影响评估，某页面颜色错乱才发现。
**风险等级**：P2
**整改方向**：变更 SOP 写入 03 或本专项附录；grep 引用命令固定。
**验收标准**：变更 SOP 可用且被执行。

### 指标 5.2：stylelint 自动化守约
**指标名称**：stylelint 自动化守约
**检查目标**：确认 stylelint（或等价）配置拦截硬编码色值/魔法间距/非法 z-index，而非仅靠人工。
**为什么需要检查**：人工 grep 会漏；stylelint 自动化是"可验收"原则的落地。
**检查范围**：stylelint 配置、CI 集成。
**检查方法**：
1. 检查 stylelint 是否存在及规则配置（color-no-hex / 自定义规则）。
2. 检查是否接入 lint 流程（package.json scripts + CI）。
3. 检查违规处理流程（新增违规是否被拦截）。
**需要查看**：stylelint 配置、package.json、CI。
**正常标准**：stylelint 拦截硬编码色值/魔法值；CI 阻断。
**异常情况**：无 stylelint；有配置但未接入 CI。
**风险等级**：P2
**整改方向**：补/启用 stylelint 规则；接入 CI。
**验收标准**：硬编码色值在 CI 被拦截。

### 指标 5.3：token 使用统计与覆盖率
**指标名称**：token 使用统计与覆盖率
**检查目标**：确认 token 有使用统计（未使用 token 检测、引用覆盖率），无"死 token"。
**为什么需要检查**：死 token 积累导致新人不知道该用哪个；覆盖率报告是 token 体系健康的晴雨表。
**检查范围**：`--GCS-*` 定义与引用统计。
**检查方法**：
1. 脚本统计：定义数 vs 被引用数（定义未引用 = 死 token）。
2. 检查引用覆盖率（业务样式使用 token 的比例）。
3. 检查同值重复 token（值相同名字不同）。
**需要查看**：grep 统计脚本、token 定义。
**正常标准**：死 token ≤ 5%；覆盖率报告可生成。
**异常情况**：20% token 未被引用；同值 token 3 个。
**风险等级**：P3
**整改方向**：清理死 token；重复合并。
**验收标准**：死 token 清零；统计脚本留档。

### 指标 5.4：CSS 变量作用域管理
**指标名称**：CSS 变量作用域管理
**检查目标**：确认 `--GCS-*` 变量定义只在全局（:root/主题块），组件内不定义 `--GCS-*` 前缀变量。
**为什么需要检查**：组件内定义 `--GCS-*` 会污染全局语义（scoped 不保护 CSS 变量穿透）。
**检查范围**：组件 `<style>` 内变量定义。
**检查方法**：grep 组件内 `--GCS-` 定义（非引用）。
**需要查看**：grep 命中。
**正常标准**：`--GCS-*` 仅全局定义；组件内用 `--local-*` 或直接 var 引用。
**异常情况**：组件内 `--GCS-panel-bg: xxx` 定义（穿透污染）。
**风险等级**：P2
**整改方向**：组件内变量改 `--local-*` 前缀。
**验收标准**：组件内 `--GCS-` 定义为零。

### 指标 5.5：废弃 token 清理
**指标名称**：废弃 token 清理
**检查目标**：确认废弃/改名 token 有清理机制（改名留映射过渡期、废弃删引用再删定义）。
**为什么需要检查**：改名不留映射 → 旧引用静默失效；废弃不清理 → 死 token 累积。
**检查范围**：token 改名历史、废弃定义。
**检查方法**：
1. 检查改名是否两步走（先加新名+映射 → 迁移引用 → 删旧名）。
2. 检查废弃 token 是否仍在定义中。
3. 检查别名映射文档。
**需要查看**：token 定义、迁移记录。
**正常标准**：改名有映射过渡；废弃已清理。
**异常情况**：旧名删除后引用 grep 仍命中（静默失效）；废弃 token 停留 2 个版本以上。
**风险等级**：P3
**整改方向**：补映射；清理废弃。
**验收标准**：废弃 token 清单为空。

## 附录 F：样式反例模式库（审查对照用）

> 每个反例 = 一个真实发生或高风险的模式。审查时按模式 grep 定位；命中即记入发现清单（对照 0.6 输出格式）。

### 反例 F.1：硬编码色值穿透主题
- **错误形态**：`.vue` 内 `background: #fff` / `color: #333` 直写。
- **为什么错**：暗色模式下白底刺眼；主题切换时纹丝不动——"页面一半跟着主题走、一半不动"。
- **如何发现**：grep `#([0-9a-fA-F]{3}|[0-9a-fA-F]{6})\b` 排除 `colors.ts` 与豁免清单。
- **修复**：替换为 `var(--GCS-bg)` / `var(--GCS-text-primary)`；语义缺失先补 token。
- **示例**：`PortInfoPanel.vue:54` 写死色值（已知违约，2026-08 在案）。

### 反例 F.2：组件内定义 --GCS-* 变量污染
- **错误形态**：组件 `<style>` 内 `--GCS-panel-bg: #1e293b`。
- **为什么错**：scoped 不保护 CSS 变量——定义穿透到全应用，其他组件意外继承。
- **如何发现**：grep 组件内 `--GCS-` 定义（`<style>` 块内非 `:root`/主题块）。
- **修复**：组件内变量用 `--local-*` 前缀；`--GCS-*` 只全局定义。

### 反例 F.3：rgba 固定色衍生脱钩
- **错误形态**：`rgba(37, 99, 235, 0.5)`（主色的固定衍生）。
- **为什么错**：主色 token 变（主题切换），衍生色不变——选中态/遮罩颜色错乱。
- **如何发现**：grep `rgba\(`，判断参数是否为固定 hex。
- **修复**：`rgb(var(--GCS-primary) / 0.5)` 或预定义 `--GCS-primary-50`。

### 反例 F.4：非 scoped 样式全局泄漏
- **错误形态**：业务组件 `<style>` 无 `scoped`，`.title { color: red }`。
- **为什么错**：全站同名 class 被污染；暗色排查时"幽灵样式"找不到来源。
- **如何发现**：grep `<style` 无 scoped 的组件（排除全局样式/reset 文件）。
- **修复**：加 `scoped`；全局样式只留变量/reset。

### 反例 F.5：transition: all 动画风暴
- **错误形态**：`transition: all 0.3s`。
- **为什么错**：主题切换时全站元素同时过渡（卡顿）；hover 触发无关属性动画。
- **如何发现**：grep `transition: all`。
- **修复**：精确属性（`transition: background-color 0.2s var(--GCS-ease)`）。

### 反例 F.6：自造断点魔数
- **错误形态**：组件内 `window.innerWidth < 768` 或 `@media (max-width: 768px)`。
- **为什么错**：与 GCS 三档（960/640）判定不一致——抽屉在 800px 时和面板打架。
- **如何发现**：grep `768|innerWidth`；对照 `config.ts` 断点常量。
- **修复**：消费 `useGCS()` computed（showPanels/showTopArea/navCompact）。
- **示例**：MobileDrawer 注释曾写 <768px 而代码 <960px（2026-08 实测漂移，已修）。

### 反例 F.7：手搓 absolute 定位面板
- **错误形态**：业务面板 `position: absolute; left: 123px; top: 45px`。
- **为什么错**：绕过 GCS 网格（80px Cell + 锚点）；抽屉/移动端直接错位。
- **如何发现**：grep 业务组件 `position: absolute` + 数值偏移。
- **修复**：`GCSPanel :w :h anchor` + offset；尺寸走 `useGCS.cell()`。

### 反例 F.8：z-index 9999 散落
- **错误形态**：组件 `z-index: 9999`。
- **为什么错**：层级无体系——新弹窗盖不住旧 toast；无法预判谁在上。
- **如何发现**：grep `z-index: 9+`。
- **修复**：层级常量（panel/nav/drawer/overlay/modal/toast 分级）。

### 反例 F.9：魔法间距/尺寸
- **错误形态**：`padding: 13px` / `gap: 7px` / `width: 340px`。
- **为什么错**：非刻度（4/8/10/20）间距视觉不齐；面板宽非 Cell 倍数网格失效。
- **如何发现**：grep `padding|margin|gap|width` 提取数值聚类。
- **修复**：间距走 GAP 倍数；面板宽 `useGCS.cell(n)`。

### 反例 F.10：伪 GCS 组件重复实现
- **错误形态**：业务组件内手写"面板容器"（同 GCSPanel 结构）。
- **为什么错**：同交互两处实现——改一处另一处不同步；暗色适配要重复改。
- **如何发现**：对照标准组件清单找相似结构；grep 重复的定位/圆角样式块。
- **修复**：复用标准组件；新需求先评估归属（03 §1.4）。

### 反例 F.11：isDark 分支手写颜色
- **错误形态**：组件内 `isDark ? '#fff' : '#000'`。
- **为什么错**：JS 分支颜色不走 CSS 变量——主题切换瞬间两态并存；新主题（高对比）无法接入。
- **如何发现**：grep `isDark|dark ?` 颜色三元。
- **修复**：颜色全走变量；组件不做主题判断。

### 反例 F.12：dark 块缺 key（双主题 diff）
- **错误形态**：`:root` 有 `--GCS-border-subtle`，dark 块没有。
- **为什么错**：暗色下该属性回退基线（可能是浅色）——最隐蔽的暗色 bug。
- **如何发现**：脚本提取两主题 key 集合 diff（见 4.5）。
- **修复**：补缺失 key；diff 脚本接入执行清单。

### 反例 F.13：图标 SVG fill 写死
- **错误形态**：内联 SVG `fill="#64748b"`。
- **为什么错**：图标颜色不随主题/状态（hover/禁用）变化。
- **如何发现**：grep SVG `fill=|stroke=` 色值。
- **修复**：`fill="currentColor"` + 父元素 color 走 token。

### 反例 F.14：字号/字重散落
- **错误形态**：`font-size: 15px` / `font-weight: 500` 各处。
- **为什么错**：文字层级无体系——标题与正文分不清；暗色下层级更乱。
- **如何发现**：grep `font-size|font-weight` 数值聚类。
- **修复**：字号档位 token（12/13/14/16/20/24）；字重标准化（400/500/600/700）。

### 反例 F.15：主题切换 FOUC 闪白
- **错误形态**：刷新页面先白屏再变暗色。
- **为什么错**：主题初始化在渲染后执行；暗色用户每次刷新被闪一下。
- **如何发现**：暗色模式下刷新观察；检查 index.html/main.ts 初始化顺序。
- **修复**：首屏内联脚本前置设置主题（防 FOUC）。

### M.6 误判案例（已发生）

1. **把 colors.ts 当违约**：`colors.ts` 是 token 定义处，不是违约——违约判定只针对业务代码。
2. **把 ECharts 默认色板当业务违约**：抄 ECharts 默认 `['#5470c6',...]` 是违约（1.8），但 ECharts 库内部色不是。
3. **把 scoped 组件内的 :deep 当污染**：`:deep` 有前缀限定时是合法穿透，不是全局污染（3.3）。
4. **把受控暗色覆写当散落**：有注释的组件级主题块（如代码块保持亮色）是设计，不是违约（4.6）。
