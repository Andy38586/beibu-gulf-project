## 0. 文档使用说明

### 0.1 文档定位
本文档是「算法与结果正确性专项审查标准库」，填补审查体系对**计算结果正确性**的零覆盖。

现有专项（数据链/生命周期/TS/WebGIS/工程化/架构耦合/设计Token）查的是工程侧——数据是否流动、生命周期是否完整、类型是否安全、是否硬编码。
**它们都不查**：算出来的数对不对——单位是否一致、除零兜底是否生效、防御分支是否真的能触发、评分算法语义是否与设计一致、结果是否可复现、缓存是否串数据。

本专项聚焦「数值结果」而非「入参校验」：入参校验（半径 0/负值/缺键）已有测试覆盖，不是盲点；盲点是**正常参数下算错**与**防御分支静默失效**。

三条奠基实锤（首份执行记录的开篇素材，均在 `backend/services/scoringService.js`）——**已全部修复（commit 45df38a，2026-08）**，保留为「防御分支可触发」的判例教学与回归复验基线，不再作为在案问题：
1. **`:83` 防御分支永久失效（已修）**：`facilityIndex.isEmpty?.()`——RBush 没有 `isEmpty()` 方法（.d.ts 与全库 grep 已验证），`?.()` 静默返回 undefined，分支永不触发；换指数衰减时周边零设施小区立刻拿 36.8 分。**修复**：改 `all().length === 0` 判空。
2. **`:79` 除零兜底是死代码（已修）**：`km / (111 * Math.cos(...) || 1)`——`||` 优先级低于 `*`，实际是 `(km / (111 * Math.cos(lat))) || 1`；而 `Math.cos(π/2) = 6.12e-17` 不是 0，兜底永不生效；lat=90 时 lngOffset ≈ 1.5e15 度，rbush 粗筛退化成 O(n)。**修复**：分母显式守卫（`Number.isFinite` + `> 1e-6` 才用，否则保守值）。
3. **评分核心零单测（已补）**：`__tests__/` 6 个测试文件里没有 `scoringService.test.js`。**修复**：`45df38a` 新增 `scoringService.test.js`（8 用例，锁定分数"值"而非仅字段存在）。

### 0.2 与其他专项的边界
- 本专项**只管算法与数值结果正确性**（计算层）。
- 数据是否流动/断链 → 专项1 数据链，不归本专项。
- 复杂度优化（rbush 引入、缓存）的实现质量 → 专项5 工程化（性能）+ 专项6 架构耦合（模块边界）；本专项只查「复杂度是否导致结果错误或退化」。
- 类型不匹配/数值类型漂移（number vs string）→ 专项3 TS类型。
- 坐标系/投影错误 → 专项4 WebGIS（坐标系链路归它）；本专项查**同一坐标系内的数值计算**（量纲、精度、防御）。
- 图层渲染结果 → 专项4；本专项查**分析结果数值**（评分、面积、档位、预测值）。
- 样式/视觉 → 专项7 设计Token。

### 0.4 风险等级定义

见 `00-审查体系约定.md` §1（判据与处置），本专项不再重复定义，仅引用：

| 等级 | 含义 | 触发条件 | 处置要求 |
|------|------|----------|----------|
| P0 | 阻断级 | 直接导致功能错误、数据错误、崩溃、安全漏洞 | 必须立即修复，不允许带病上线 |
| P1 | 高危 | 高概率引发故障、维护困难、性能问题 | 本轮审查必须修复 |
| P2 | 中危 | 存在隐患，特定场景下会出问题 | 计划修复，限期完成 |
| P3 | 低危 | 规范性、可读性、轻度冗余 | 择机优化，不阻断 |

本专项特殊性：**防御分支失效、量纲错误、除零兜底死代码**这类"看起来有防护、实际没有"的问题，一律 P1 起评（比没有防御更危险——隐蔽且面试可深挖）；导致排名/评分/淹没结果错误时为 P0。

### 0.5 本专项核心原则
1. **算得对优先**：先验证结果正确性，再谈测试覆盖——一个"有测试但算错"的算法比"没测试"更危险。
2. **防御分支必须可触发**：任何防御代码必须证明其触发条件在真实输入下可达；`?.()` 对不存在的方法、`|| 兜底` 被优先级/非零常量绕过 = 失效防御，P1。
3. **结果可复现**：同一输入必须同一输出（确定性）；随机性必须显式种子并诚实标注。
4. **证据可执行**：每条结论给 file:line + 最小复现输入，能跑出错误结果才算实锤。
5. **退化即错**：性能退化（如粗筛退化 O(n)）若导致超时/结果错误，与算错同等级。

## 第一部分：数值与量纲（1.1-1.8）

### 指标 1.1：单位换算一致性
**指标名称**：单位换算一致性
**检查目标**：确认距离/面积/坐标等数值在整条计算链上单位一致（米/千米/度），无混用。
**为什么需要检查**：单位混用是最隐蔽的算错方式——"看起来对了，量纲错"。历史风险：`kmToDegreeOffset` 类换算函数若在地理坐标（度）与投影距离（米）间混算，粗筛范围错 100 倍仍"正常"返回。
**检查范围**：所有涉及单位换算的函数（buffer 半径、距离计算、bbox 偏移、面积）、调用链上的单位来源、常量命名（`_KM`/`_M`/`_DEG` 后缀）。
**检查方法**：
1. 列出换算函数（km→度、度→km、米↔千米）及其系数推导。
2. 沿调用链验证单位流：buffer 半径单位 → turf 调用单位 → 结果单位 → 前端展示单位。
3. 用已知距离验证：如钦州-北海约 120km，换算后应得合理度数（≈1.1°）。
4. 检查常量命名是否带单位后缀（`DEFAULT_BUFFER_RADIUS = 3000 // 米` 有注释）。
5. 检查接口参数单位（前端传 km 还是 m）与后端期望一致。
**需要查看**：`scoringService.js`、`spatialIndex.js`、选址/浸没/预测的数值常量定义、接口契约。
**正常标准**：整链单位单一且可追溯；换算系数有注释推导；常量带单位注释。
**异常情况**：
- 米/千米混用（前端传 3000 米、后端当 3000 千米用）。
- 换算系数无推导来源。
- 展示单位与计算单位不一致（算的是米展示成千米）。
- `kmToDegreeOffset` 系数与纬度无关（忽略 cos 修正）。
**风险等级**：P1（量纲错 = 结果系统性错误）
**整改方向**：统一单位常量；换算函数加推导注释；补单位测试。
**验收标准**：全链单位可追溯；已知距离验证通过。

### 指标 1.2：除零与 NaN/Infinity 防御有效性
**指标名称**：除零与 NaN/Infinity 防御有效性
**检查目标**：确认所有除法有**真正生效**的零分母兜底，且分母不可能静默变成 NaN/Infinity。
**为什么需要检查**：历史实锤（`scoringService.js:79`）：`km / (111 * Math.cos(lat) || 1)`——`||` 优先级低于 `*`，实际是 `(km / (111 * Math.cos(lat))) || 1`，而 `Math.cos(π/2) = 6.12e-17` 不是 0，兜底**永不生效**；lat=90 时 lngOffset ≈ 1.5e15 度，rbush 粗筛退化成 O(n)。
**检查范围**：全部 `Math.cos/sin/tan`、除法表达式、`||`/`??` 兜底、`toFixed`/`parseFloat` 链、分母为表达式的地方。
**检查方法**：
1. 逐条检查除法分母表达式：是否可能为 0 / 极小值 / NaN。
2. 检查 `||`/`??` 兜底位置：兜底作用域是否覆盖整个分母表达式（括号优先级——`a / (b || 1)` 与 `a / b || 1` 语义完全不同）。
3. 代入极端输入（lat=±90、半径为 0、极大/极小值）验证兜底是否真的触发。
4. 检查 `Math.cos`/`Math.sin` 参数为 NaN 时的传播（cos(NaN)=NaN，分母 NaN 时兜底是否覆盖）。
5. 检查 0/0 与 Infinity/Infinity 场景（`0/0 = NaN`，`Infinity/Infinity = NaN`）。
**需要查看**：`scoringService.js:79` 及全库除法/三角函数点。
**正常标准**：分母兜底括号正确且对真实极端值生效；无 NaN 传播路径；兜底值语义正确（非"假装有值"）。
**异常情况**：
- `|| 1` 兜底被优先级绕过（实锤）。
- cos 极小值当 0 处理（`Math.cos(π/2)` 实为 6.12e-17）。
- lat=90 产生天文数字偏移。
- 兜底值为 1 但语义上应是 0（静默改结果）。
**风险等级**：P1（防御失效 = 静默错误，可升 P0 当结果错误）
**整改方向**：兜底改为显式判断（`if (!Number.isFinite(x)) x = fallback`）；补极端输入测试。
**验收标准**：极端输入下无 NaN/Infinity 传播；兜底均实际生效且语义正确。

### 指标 1.3：比例系数与权重量纲
**指标名称**：比例系数与权重量纲
**检查目标**：确认评分权重、衰减系数、情景系数等比例值的量纲与语义正确（和为 1 / 归一化 / 范围约束）。
**为什么需要检查**：权重未归一化或系数量纲错会导致排名失真——"每个数都对，总和不对"。
**检查范围**：`DEFAULT_WEIGHTS`、`importanceToRadius` 系数表、`linearDecay`、预测情景系数、置信度映射。
**检查方法**：
1. 检查权重归一化逻辑（除以总权重是否在正确位置、除零处理——见 1.2）。
2. 验证 `importanceToRadius` 系数表（1:0.4 … 5:2.2）的语义：是否单调、是否与需求档位一致。
3. 检查 `linearDecay` 的衰减范围：距离 > bufferRadius 时是否严格归零。
4. 检查置信度（0.8-1.2）到系数的映射：是否单调、边界是否闭合。
5. 检查情景系数（预测）与置信度的叠加是否超范围（1.2 × 1.2 = 1.44 是否允许）。
**需要查看**：`scoringService.js`（DEFAULT_WEIGHTS / importanceToRadius / linearDecay）、`forecastEngine.js`（情景系数）。
**正常标准**：权重归一化数学正确；系数表单调且符合需求；衰减在边界外归零；置信度映射单调有界。
**异常情况**：
- 权重除零无兜底。
- 系数表非单调（importance=4 半径小于 importance=3）。
- 衰减在界外返回非零。
- 置信度映射在 0.8/1.2 边界外不截断。
**风险等级**：P1
**整改方向**：修正归一化/兜底；系数表来源注释化；边界截断。
**验收标准**：任意输入下权重和 = 1（或等价语义）；边界外衰减 = 0；置信度映射边界闭合。

### 指标 1.4：舍入与精度
**指标名称**：舍入与精度
**检查目标**：确认四舍五入/截断位置正确（展示层舍入不进入计算链），浮点误差不累积到结果失真。
**为什么需要检查**：`toFixed` 在计算中途使用会污染后续计算；浮点累加（大量点面积/距离求和）误差会随规模放大。
**检查范围**：`toFixed`/`Math.round`/`parseFloat`/`Number.toPrecision` 使用点、累加循环、坐标精度。
**检查方法**：
1. grep `toFixed|Math.round|parseFloat|toPrecision`，判断使用位置（计算链 vs 展示层）。
2. 检查累加循环是否可能溢出/误差累积（如 983 POI 逐点 buffer 的面积和）。
3. 检查经纬度保留位数是否足够（5 位 ≈ 1m 精度，6 位 ≈ 0.1m）。
4. 检查浮点比较（`x === 0` / `x === y`）是否改为 epsilon 比较。
5. 检查展示层舍入是否统一（分数 1 位小数、面积 2 位、坐标 5 位）。
**需要查看**：计算结果到展示的转换点、聚合函数、比较逻辑。
**正常标准**：计算链无舍入；展示层舍入统一；坐标精度 ≥ 5 位小数；浮点比较用 epsilon。
**异常情况**：
- `toFixed(2)` 在计算中途（结果被二次使用）。
- 坐标 2 位小数（≈1km 误差）。
- `if (x === 0)` 直接比较浮点。
- 面积累加 1000 次后误差 > 1%。
**风险等级**：P2
**整改方向**：舍入下沉到展示层；浮点比较改 epsilon；累加改用分块或高精度。
**验收标准**：计算链零舍入；聚合误差在可接受范围；浮点比较审计通过。

### 指标 1.5：坐标精度与表示
**指标名称**：坐标精度与表示
**检查目标**：确认坐标存储/传输/计算的精度一致（经纬度小数位、类型 number、无字符串坐标）。
**为什么需要检查**：字符串坐标（"108.6"）在算术运算中静默转 number 但比较/排序行为异常；小数位不足导致点位偏移。
**检查范围**：坐标数据结构（`[lng, lat]` 元组）、接口传输、存储（JSON）、计算。
**检查方法**：
1. 检查坐标类型（number[] vs string[]）——grep 字符串坐标。
2. 检查坐标精度（源数据小数位 ≥ 5）。
3. 检查元组顺序约定（[lng, lat] vs [lat, lng]）是否全链一致。
4. 检查坐标是否被字符串拼接/模板使用（精度损失）。
**需要查看**：数据类型定义、adapter 数据映射、接口响应。
**正常标准**：坐标全链 number 类型；精度 ≥ 5 位；[lng, lat] 顺序统一。
**异常情况**：接口返回字符串坐标；某处 `[lat, lng]` 混入。
**风险等级**：P2（顺序混用 = 点位错误，升 P1）
**整改方向**：类型强制 number；顺序校验；补契约测试。
**验收标准**：坐标精度与顺序全链一致。

### 指标 1.6：面积/距离计算口径
**指标名称**：面积/距离计算口径
**检查目标**：确认面积/距离计算的几何口径（地理 vs 投影、turf 单位）一致且与用途匹配。
**为什么需要检查**：turf 面积默认返回平方米（球面），若展示为 km² 未除 1e6 则差 6 个数量级；距离用 `turf.distance`（米）与 `haversine` 混用产生不一致。
**检查范围**：`turf.area`/`turf.distance`/`turf.length` 调用点、面积/距离展示。
**检查方法**：
1. 列出面积/距离计算点及单位（turf 默认米/平方米）。
2. 检查展示层单位换算（km² = m²/1e6）。
3. 检查距离算法是否统一（turf.distance vs 自算 haversine 不应并存）。
4. 检查球面 vs 平面假设（小范围平面近似误差可接受需注释）。
**需要查看**：空间计算代码、展示组件。
**正常标准**：计算单位统一；展示换算正确；距离算法单一。
**异常情况**：面积展示差 1e6 倍；两处距离算法结果不一致。
**风险等级**：P1
**整改方向**：统一口径；换算集中一处；补单位测试。
**验收标准**：面积/距离口径全链一致。

### 指标 1.7：百分比与比例值语义
**指标名称**：百分比与比例值语义
**检查目标**：确认 0-1 与 0-100 比例值语义不混用（置信度、权重、增长率、覆盖率）。

**风险等级**：P1（换算错 = 展示全错）

**验收标准**：全链比例值语义对照表正确。

### 指标 1.8：时间序列单位与时区
**指标名称**：时间序列单位与时区

## 第三部分：算法实现正确性（3.1-3.12）

### 指标 3.1：几何降级处理（MultiPolygon / 退化几何）

**检查范围**：`buildTypeCoverage`（buffer+union）、`intersectCoverages`、几何消费方（渲染/过滤）。
**检查方法**：

3. 构造共享边界多边形验证。
4. 检查空几何（union 结果为 null）处理。
5. 检查自相交多边形（turf 行为）处理。
**需要查看**：`siteAnalysisService.js`（buildTypeCoverage/intersectCoverages）。
**正常标准**：MultiPolygon 有明确降级路径；降级语义在注释中说明（如"退而求其次用凸包"）；空几何有处理。
**异常情况**：
- union 结果直接当 Polygon 用（类型断言跳过）。
- 降级无注释（"为什么用凸包"不可解释）。
- 空几何导致后续面积计算 NaN。
**风险等级**：P1
**整改方向**：补几何类型分支 + 降级注释；加共享边界测试。
**验收标准**：共享边界输入跑通且降级语义可解释。

### 指标 3.2：空间索引正确性（粗筛不丢结果）
**指标名称**：空间索引正确性（粗筛不丢结果）
**检查目标**：确认 RBush BBox 粗筛 + 精确判定的组合**不漏匹配**（粗筛是超集，精确过滤不引入新误判）。
**为什么需要检查**：粗筛 bbox 过大 → 性能退化；粗筛 bbox 过小 → **漏匹配**（比慢更严重）。历史风险：`kmToDegreeOffset` 换算错误会让 bbox 缩小，命中缺失。
**检查范围**：`spatialIndex.js`（queryByPolygon）、`kmToDegreeOffset`、`booleanPointInPolygon` 二次过滤、`distanceScore` 的 bbox 粗筛。
**检查方法**：
1. 验证 bbox 计算 ≥ 真实范围（粗筛必须保守）。
2. 对凹多边形顶点做边界测试：顶点附近点应被粗筛命中。
3. 对比全量遍历结果：随机采样点，粗筛+精确 = 全量精确。
4. 检查 bbox 偏移换算（kmToDegreeOffset）在纬度 18-25 范围正确。
5. 检查 buffer 半径换算（km→度）与纬度相关修正。
**需要查看**：`spatialIndex.js`、`scoringService.js`（distanceScore 的 bbox 粗筛）。
**正常标准**：粗筛零漏配（可用全量对照验证）；精确过滤与粗筛无逻辑冲突。
**异常情况**：
- bbox 偏移导致边缘点漏配。
- 粗筛结果 ≠ 全量精确结果。
- kmToDegreeOffset 用固定系数忽略纬度（高纬度误差）。
**风险等级**：P1
**整改方向**：修正偏移换算；补"粗筛=全量"对照测试。
**验收标准**：随机采样对照零差异。

### 指标 3.3：评分算法语义与设计一致
**指标名称**：评分算法语义与设计一致
**检查目标**：确认评分公式与设计意图一致（可达性衰减、权重生效、TOP N 排序正确）。
**为什么需要检查**：评分是选址模块的核心产出，公式写错 = 整个分析结论错；且面试必问"评分怎么算的"。
**检查范围**：`scoreXiaoqu`、`distanceScore`、`linearDecay`、`rankXiaoqu`（TOP 10 截断）、权重乘法位置。
**检查方法**：
1. 用 3 个手工可算的用例验证评分值（距离=0 → 满分；距离=bufferRadius → 0；权重=0 → 不贡献）。
2. 验证权重 0 时该因子不参与（而非乘 0 仍显示有分）。
3. 验证 TOP 10 排序稳定（同分时顺序确定）。
4. 验证多因子合成（加权平均）数学正确。
5. 验证自定义 decayFn 场景（防御失效实锤的触发条件）。
**需要查看**：`scoringService.js` 全部评分函数。
**正常标准**：手工用例全部符合设计语义；同分排序确定；权重 0 不贡献。
**异常情况**：
- 距离 0 不得满分。
- 权重 0 仍影响总分。
- 排序不稳定（同分随机）。
- 自定义 decayFn 下零设施小区得分失真（实锤触发场景）。
**风险等级**：P0（评分错 = 选址结论错）
**整改方向**：修正公式；补 3+ 手工用例测试。
**验收标准**：手工用例与公式推导一致。

**异常情况**：README 声称"真预测"而代码合成；标注缺失；版本说明夸大。
**风险等级**：P1（面试诚信）
**整改方向**：叙事对齐代码；补/修标注。
**验收标准**：README 与代码行为逐条对照通过。

### 指标 4.3：前后端口径一致
**指标名称**：前后端口径一致
**检查目标**：确认同一语义参数在前后端的命名/单位/格式一致（无同语义多套传参）。
**为什么需要检查**：历史实锤：`waterLevel` 在 api 模式用 `params`、body 两套，online 模式用 `level`——三套参数名并存，前后端易漂移（待解决 b044 已在案）。
**检查范围**：前后端参数名/单位对照（水位、半径、权重、置信度、时间）。
**检查方法**：
1. 列出同一语义参数的所有命名，检查是否唯一。
2. 检查单位一致性（前端 km vs 后端 m）。
3. 检查格式一致性（时间字符串、数字类型）。
4. 检查 envelope 字段（code/data）前后端一致。
**需要查看**：`floodAdapter.ts`、`forecastController.js`、路由定义、契约文档。
**正常标准**：同语义同命名同单位；跨服务差异有映射注释。
**异常情况**：waterLevel/level 并存；米/千米混传；时间格式两套。
**风险等级**：P2
**整改方向**：统一命名；差异处加映射。
**验收标准**：同语义参数全局唯一。

### 指标 4.4：错误与空结果可区分
**指标名称**：错误与空结果可区分
**检查目标**：确认接口返回的"错误"与"业务空结果"语义分离（error 字段 vs 合法空数据）。
**为什么需要检查**：前端把空结果当错误弹窗、或把错误当空结果静默，都是演示现场事故。
**检查范围**：信封 `{code,data}` 的语义、各业务空结果形态（无重叠区域/无匹配/空档位）。
**检查方法**：
1. 检查"无重叠区域""无匹配小区"是否走 data 而非 error。
2. 检查错误信封（BusinessError）与业务空结果的区别。
3. 检查前端对两类响应的 UI 表现。
**需要查看**：`siteAnalysisService.js` 返回结构、前端判断逻辑。
**正常标准**：空结果 = data 内明确标记；错误 = error 字段 + 状态码。
**异常情况**：空结果抛 422；前端把 error 当空结果。
**风险等级**：P2
**整改方向**：语义分离；补空结果用例。
**验收标准**：错误/空结果两态 UI 表现正确。

### 指标 4.5：缓存与重算一致
**指标名称**：缓存与重算一致
**检查目标**：确认缓存命中结果 = 重新计算结果（缓存不引入陈旧值）。
**为什么需要检查**：缓存 key 缺维度、TTL 过期策略错会导致"缓存的值"与"现在该算的值"不一致。
**检查范围**：`createReadCache`、预测 LRU（ts/cmp/map）、online 查表、FastAPI LRU。
**检查方法**：
1. 对同一参数：缓存命中结果 vs 清缓存重算结果，对比一致。
2. 检查 TTL 语义（静态数据长 TTL、动态数据短 TTL）。
3. 检查 key 完整性（同参数不同值应不同 key）。
**需要查看**：缓存实现、调用方。
**正常标准**：缓存命中 = 重算；TTL 语义正确；key 全覆盖。
**异常情况**：缓存返回旧值；key 缺维度串数据。
**风险等级**：P1（串数据 = 结果错误）
**整改方向**：key 补全；缓存失效策略修正。
**验收标准**：缓存/重算对照一致。

### 指标 4.6：快照恢复一致性
**指标名称**：快照恢复一致性
**检查目标**：确认状态快照（saveState/consumeState）恢复后与保存前一致（控件状态、结果、图层）。
**为什么需要检查**：跳个人中心往返恢复是已声明能力；恢复错位（滑块值与图表不符）是隐蔽缺陷。
**检查范围**：三个业务页的快照（siteSelectionPersisted/floodStore/forecastStore）、`createPersistedState`。
**检查方法**：
1. 保存状态 → 跳转 → 返回，对比控件状态与结果。
2. 检查快照字段完整性（缺字段恢复默认 vs 恢复错误值）。
3. 检查一次性消费（consumeState 二次调用返回 null）行为。
**需要查看**：快照工厂、业务页 onBeforeRouteLeave/onMounted。
**正常标准**：往返恢复与保存一致；缺字段有默认；二次消费安全。
**异常情况**：恢复后滑块 5m 但图表是 2m 档；恢复字段缺失变 undefined。
**风险等级**：P2
**整改方向**：快照字段校验；补往返测试。
**验收标准**：往返恢复用例一致。

### 指标 4.7：展示格式化一致性
**指标名称**：展示格式化一致性
**检查目标**：确认展示层格式化（单位/小数位/千分位/百分比）统一，无同值不同显示。
**为什么需要检查**：同一个小分数值在列表 85 分、雷达图 85.0、详情 85.00——显示不一致让用户怀疑数据错。
**检查范围**：评分/面积/水位/预测值/时间的展示格式化。
**检查方法**：
1. 列出各展示点的格式化规则（小数位、单位、百分比）。
2. 检查同语义值是否同格式。
3. 检查格式化函数是否集中（shared/utils）而非散落。
**需要查看**：展示组件、格式化工具。
**正常标准**：同语义同格式；格式化集中。
**异常情况**：分数一处 1 位一处 2 位；面积一处 km² 一处 m²。
**风险等级**：P3
**整改方向**：格式化集中封装。
**验收标准**：展示格式对照表一致。

### 指标 4.8：多请求交叉一致性
**指标名称**：多请求交叉一致性
**检查目标**：确认同参数的多个请求（预测 timeseries/comparison/map）返回的数值互相一致。
**为什么需要检查**：三请求独立计算，若口径不一（折线图 100 万吨、柱状图 98 万吨、热力图 105）用户立即发现矛盾。
**检查范围**：预测三请求同参数下的值、图表与地图联动。
**检查方法**：
1. 同参数（指标+时间+置信度）对比三请求同点位数值。
2. 检查年/月粒度换算是否一致。
3. 检查置信度应用是否一致（三请求用同一系数）。
**需要查看**：`forecastService.js` 三个 getter、前端三渲染。
**正常标准**：同参数跨请求数值一致；粒度/置信度口径统一。
**异常情况**：折线与柱状图同月数值不一致。
**风险等级**：P1
**整改方向**：统一计算入口（共享 service 函数）；补对照测试。
**验收标准**：三请求同参数对照一致。

## 第五部分：复杂度与性能（5.1-5.5）

### 指标 5.1：复杂度实锤（O(n²) 与规模增长）
**指标名称**：复杂度实锤（O(n²) 与规模增长）
**检查目标**：确认核心算法复杂度与数据规模匹配，且有量化基线（不做无据优化，也不忽视已知退化）。
**为什么需要检查**：历史实锤（待解决 b044）：`buildTypeCoverage` 逐 POI buffer + 全量 union，O(n²)，6 类全选 983 POI 耗时 1.55s（核心计算 95% 在此）——当前规模可接受，数据翻倍前需 rbush/聚类。
**检查范围**：`siteAnalysisService.js`（union 热路径）、`spatialIndex.js`、预测/浸没循环。
**检查方法**：
1. 识别 O(n²) 热路径并测量（或引用性能基线）。
2. 判断当前数据规模是否安全（983 POI / 557 小区 / 251 档）。
3. 检查是否有"退化即错"的隐藏路径（如 lat=90 粗筛退化 O(n)）。
4. 检查复杂度注释是否随规模变化更新。
**需要查看**：`siteAnalysisService.js`、性能基线（根基文档 03 §2.3）。
**正常标准**：复杂度有标注；规模增长有阈值预警；无"退化即错"路径。
**异常情况**：O(n²) 无标注；退化路径导致超时/内存暴涨。
**风险等级**：P2
**整改方向**：标注复杂度与阈值；按 b044 方案优化。
**验收标准**：性能基线数字可复现；退化路径已消除或显式接受。

### 指标 5.2：大输入退化
**指标名称**：大输入退化
**检查目标**：确认输入规模放大（POI 翻倍、水位档位全量、预测全指标）时无崩溃/超时/内存失控。
**为什么需要检查**：演示现场数据量翻倍（新选址分析接入真实数据）是必然方向，退化行为要预先知道。
**检查范围**：大数据入口（全量分析、251 档全量、10 年预测）。
**检查方法**：
1. 构造 2 倍规模输入测耗时与内存。
2. 检查是否有超时保护（接口超时、前端超时 10s）。
3. 检查内存峰值（大 JSON 解析、演算进程）。
**需要查看**：分析服务、缓存层、超时配置。
**正常标准**：规模翻倍耗时近似线性（有索引）或已知上限；有超时保护。
**异常情况**：规模翻倍耗时 ×4（O(n²) 无缓解）；OOM；超时无兜底。
**风险等级**：P2
**整改方向**：索引/聚类；或显式限制并提示；超时兜底。
**验收标准**：2 倍规模实测报告。

### 指标 5.3：缓存正确性（不串数据/不失效）
**指标名称**：缓存正确性（不串数据/不失效）
**检查目标**：确认缓存（LRU/TTL/预计算表）key 完整、不串数据、失效及时。
**为什么需要检查**：缓存 key 缺维度（如缺 confidence）会把不同参数的结果串给用户——比无缓存更糟。
**检查范围**：`createReadCache`（TTL+LRU）、预测 LRU（ts/cmp/map key）、online 查表（251 档）、FastAPI LRU。
**检查方法**：
1. 检查缓存 key 是否含全部参数维度（indicator/time/confidence/waterLevel）。
2. 检查 TTL 是否合理（静态数据长 TTL、动态数据短 TTL）。
3. 检查 LRU 上限与淘汰策略（FIFO vs LRU 语义）。
4. 构造同 key 不同参数用例验证不串。
**需要查看**：`createReadCache.js`、`useForecastLayer.ts`（mapCacheKey）、`main.py`（_cached_level）。
**正常标准**：key 全覆盖；TTL 语义正确；无串数据路径。
**异常情况**：key 缺维度；相同 key 不同参数返回旧值。
**风险等级**：P1（串数据 = 结果错误）
**整改方向**：key 补全维度；补缓存命中对照测试。
**验收标准**：构造同 key 不同参数用例验证不串。

### 指标 5.4：内存与资源释放
**指标名称**：内存与资源释放
**检查目标**：确认大计算（DEM 解析、大 JSON、长循环）的内存使用受控且释放及时。
**为什么需要检查**：小内存服务器（1.6Gi）上 DEM 解析（169MB tif）或全量分析内存失控会 OOM 崩溃。
**检查范围**：大文件解析（readStaticJson、DEM）、分析进程内存、FastAPI 演算。
**检查方法**：
1. 测量大文件解析内存峰值。
2. 检查是否流式/分块处理大文件。
3. 检查计算完成后对象释放（缓存上限防无限增长）。
4. 检查 FastAPI LRU 上限（64 档）防内存膨胀。
**需要查看**：`readStaticJson.js`、`flood_engine.py`、缓存实现。
**正常标准**：内存峰值可控；大文件有处理策略；缓存有上限。
**异常情况**：DEM 解析内存 ×5 文件大小；缓存无上限无限增长。
**风险等级**：P2（OOM 时 P1）
**整改方向**：流式/降采样；缓存上限；内存测量留档。
**验收标准**：内存峰值实测报告。

### 指标 5.5：递归与深循环
**指标名称**：递归与深循环
**检查目标**：确认无失控递归（几何递归、深度嵌套）与无限循环风险。
**为什么需要检查**：递归深度失控 = 栈溢出崩溃；循环条件错 = 死循环卡死服务。
**检查范围**：递归函数、while 循环、几何处理。
**检查方法**：
1. grep 递归调用（自调用函数），检查退出条件与深度上限。
2. 检查 while 循环的终止条件（计数器/上限）。
3. 检查 turf 递归处理（几何嵌套）深度。
**需要查看**：递归/循环代码。
**正常标准**：递归有深度上限或迭代替代；循环有终止保护。
**异常情况**：无上限递归；while(true) 无 break 条件。
**风险等级**：P2
**整改方向**：递归改迭代/加深度限制；循环加保护。
**验收标准**：递归/循环审计通过。

**需要查看**：核心模块测试文件。
**正常标准**：核心路径有性质/对照测试。
**异常情况**：无任何性质测试。
**风险等级**：P3
**整改方向**：补粗筛=全量对照、单调性、确定性三类测试。
**验收标准**：性质测试清单齐备。

## 第七部分：路径与图算法（7.1-7.4）

> 立项背景：最短路径是 v3 阶段新机制（路网表入库 → networkx 构图 → 路径 API），
> 按 00 §4 指标演进口径尾部追加，不重排既有编号。此部分指标的"应然"基准是
> 02 §5.6 不变量（1 确定性 / 4 缓存=重算 / 8 空与错误分离）在图算法上的具体化。

### 指标 7.1：路径权重口径一致（distance / time 不混算）
**指标名称**：路径权重口径一致
**检查目标**：路径权重的两套口径（距离米 / 时间分）字段分离、单位一致，限速系数表有出处；边长不依赖投影分带。
**为什么需要检查**：路网边的 `length_m` 与限速推算的时长量纲不同，一旦同一字段被两种口径复用（或时长用距离数值再乘系数），结果"看起来合理"但量级错误。且路网 bbox 横跨 UTM 48N/49N 两带，边长若按投影计算会随分带选择漂移（实测两带差约 0.13%）——路径里程的权威口径已定为大地线（geography），任何一处改回分带投影即引入静默偏差。
**检查范围**：`backend/algorithm-service/route/`（构图与权重）、读边 SQL、`roads.length_m` 上游计算（`tools/gis-import/import-gis.ps1`）。
**检查方法**：
1. `grep -rn "length_m\|weight\|minutes\|duration" backend/algorithm-service/route/`——确认距离与时长是两个独立字段，无互相赋值。
2. 确认限速系数表（class → km/h）是显式常量表且带出处注释，不是散落在计算式里的魔法数字。
3. 确认 `length_m` 由 `ST_Length(geom::geography)` 计算，不含 `ST_Transform(geom, 326xx)` 分带投影。
4. 抽验 5 条基准 OD 对，人工核对里程量级（如钦州港→北海港直线约 90km，路径里程应大于直线距离）。
**需要查看**：构图模块、权重计算函数、限速系数常量、边读取 SQL、OD 基准对实测记录。
**正常标准**：distance 与 time 字段分离且命名可区分单位；权重常量集中有出处；边长为大地线口径；OD 里程量级与地理直觉一致。
**异常情况**：可 grep 的模式——同一个 `weight` 变量先赋米再赋秒；限速系数以字面数字内联在计算表达式中；`ST_Transform(geom, 32648)` 或 `32649` 参与长度计算；`length_m` 与 `minutes` 字段互相派生。
**风险等级**：P0
**整改方向**：字段按单位命名（distanceM / durationMin）；限速系数收口为带出处的常量表；边长统一走 geography。
**验收标准**：□ 两口径字段在类型层面可区分 □ 限速系数表单点可改 □ 长度计算不含分带投影 □ 5 条 OD 里程量级记录入日志

### 指标 7.2：拓扑断链与不可达语义
**指标名称**：拓扑断链与不可达语义
**检查目标**：起终点 snap 容差显式；不可达返回合法空结果而非错误；孤立子图不被静默吞掉。
**为什么需要检查**：路网是 OSM 派生数据，必然存在断链与孤岛。若不可达抛 5xx，前端会当故障处理；若静默返回空路径而不说明原因，用户会当成"算法没算出来"。02 §5.6 不变量 8（空与错误分离）在路径场景的新落点。
**检查范围**：`backend/algorithm-service/route/` 的 snap 与查询路径、API 响应结构、前端 RouteAnalysis 空态 UI。
**检查方法**：
1. 确认 snap 容差是具名常量并带单位注释（如 `SNAP_TOLERANCE_M = 200 // 米`），不是内联数字。
2. 构造三组用例：起点/终点均在主图 → 有路径；起点在图外（远海）→ 空结果信封；终点在孤立子图 → 空结果信封。
3. 确认空结果携带可区分原因（如 `reason: 'unreachable'`），与"参数非法"走不同分支、不同响应码。
4. 确认构图输出孤岛规模统计（子图数/最大子图边数），不是静默丢弃。
**需要查看**：snap 实现、最短路径调用处、响应模型、构图日志、前端空态分支。
**正常标准**：不可达 = HTTP 200 + 空结果 + 显式原因；容差常量具名；孤岛规模有统计。
**异常情况**：可 grep 的模式——`NetworkXNoPath` 异常未捕获直接冒泡；snap 容差为内联字面量；不可达与参数错误返回同一错误码；构图时对小于阈值的子图直接 `continue` 且无计数。
**风险等级**：P1
**整改方向**：捕获不可达异常转合法空信封；容差常量化；构图输出子图规模；前端空态与错误态两套 UI。
**验收标准**：□ 三组用例均有测试 □ 不可达走空信封不抛错 □ 容差常量带单位注释 □ 孤岛规模入构建日志

### 指标 7.3：路网图缓存失效与一致性
**指标名称**：路网图缓存失效（版本戳）
**检查目标**：进程内图缓存的失效条件显式；路网数据变更能触发重建；缓存命中结果等于重建后结果。
**为什么需要检查**：路网静态故缓存是正确优化，但"静态"是开发期假设——roads 表一旦重灌（如裁剪范围调整、长度口径修正），进程内图不会自知。命中陈旧图 = 路径基于旧数据，且因"重算"一侧从未被触发，缺陷被缓存掩盖（02 §5.6 不变量 4 的图算法特化）。
**检查范围**：`backend/algorithm-service/route/` 的图构建与缓存、roads 表变更途径（`tools/gis-import/import-gis.ps1`）。
**检查方法**：
1. 确认缓存 key/版本戳覆盖路网数据版本（行数 + 内容摘要或变更时间戳），不只按 bbox/类型。
2. 确认有显式失效入口（重建函数/版本戳比对），失效后重新构图。
3. 一致性对照：清缓存重建后的路径结果 == 缓存命中结果（同一 OD）。
4. 确认图构建耗时与内存被记录（03 §2.3 性能基线纪律）。
**需要查看**：图构建函数、缓存容器与 key 构造、失效触发点、构建日志。
**正常标准**：版本戳覆盖数据版本；失效入口可达；命中 = 重建；构建耗时/内存有记录。
**异常情况**：可 grep 的模式——缓存 key 只含 bbox/类型不含数据版本；模块级 `_graph` 变量无任何失效路径；重建与查询走两份不同构图代码；构建过程无日志无法对照耗时。
**风险等级**：P1
**整改方向**：版本戳并入缓存 key；提供显式 rebuild 入口；构图单一实现；构建指标入日志。
**验收标准**：□ key 含数据版本戳 □ 失效入口有测试 □ 命中=重建对照用例存在 □ 耗时内存入日志

### 指标 7.4：路径确定性与平局规则
**指标名称**：路径确定性与平局规则（tie-breaking）
**检查目标**：同一 OD 重复查询结果完全一致；等长路径的选取规则显式，不依赖节点插入序/边遍历序。
**为什么需要检查**：图算法结果依赖遍历顺序；不显式 tie-breaking 时，重建图（顺序变化）后同一 OD 可能给出不同路径——02 §5.6 不变量 1（确定性）在图算法上的具体化。路径不确定则"缓存=重算"无从断言。
**检查范围**：`backend/algorithm-service/route/` 的路径查询与结果序列化、图构建的边/节点插入顺序。
**检查方法**：
1. 同一 OD 连续查询 ≥3 次，断言响应完全一致（含折线点顺序）。
2. 重启服务重建图后再查同一 OD，断言结果一致。
3. 确认 tie-breaking 规则显式（如"等长取节点 id 字典序最小"或"取边数最少"）并有注释说明取舍。
4. 确认构图 SQL/迭代带稳定排序（`ORDER BY` 或按稳定键），不依赖数据库返回顺序。
**需要查看**：最短路径调用与结果序列化、构图 SQL、图数据结构构造处。
**正常标准**：同 OD 同结果（进程内与跨重建均一致）；tie-breaking 有显式规则；构图顺序确定。
**异常情况**：可 grep 的模式——构图 SQL 无 `ORDER BY` 且直接消费结果集；路径结果未按稳定键归一直接返回；`dict`/`set` 迭代序参与结果构造且无排序；无跨重建一致性断言。
**风险等级**：P1
**整改方向**：构图 SQL 加稳定排序；结果序列化前按稳定键归一；tie-breaking 规则显式化并补确定性测试。
**验收标准**：□ 三次查询结果一致有测试 □ 重建后一致有测试或人工记录 □ tie-breaking 规则入注释 □ 构图顺序确定

## 附录 F：数值反例模式库（审查对照用）

> 每个反例 = 一个真实发生或高风险的模式。审查时按模式定位；命中即记入发现清单（对照 0.6 输出格式）。★ = 本项目已实锤。

### 反例 F.1：`||` 兜底被优先级绕过（历史实锤，已修复 45df38a）
- **错误形态**：`km / (111 * Math.cos(lat) || 1)`——期望"cos 为 0 时兜底"，实际 `||` 优先级低于 `*`，作用于整个商。
- **为什么错**：兜底永不生效（除非整个商为 0）；极端输入产生天文数字（lat=90 → lngOffset ≈ 1.5e15）。
- **如何发现**：grep `||` 出现在除法/乘法表达式内；代入极端值验证。
- **修复**：显式判断（`const denom = 111 * Math.cos(lat); const safe = Number.isFinite(denom) && denom > 1e-6 ? denom : 1e-6`）。
- **示例**：`scoringService.js:79`（2026-08 实锤，45df38a 已修——复验：确认未回退）。

### 反例 F.2：`?.()` 调用不存在的方法（历史实锤，已修复 45df38a）
- **错误形态**：`facilityIndex.isEmpty?.()`——RBush 没有 `isEmpty()` 方法。
- **为什么错**：`?.()` 对不存在的方法静默返回 undefined，防御分支永不触发；"看似有防御、实际裸奔"。
- **如何发现**：对每个 `?.()` 验证方法存在于类型定义与原型（grep 定义）。
- **修复**：换真实 API（`all().length === 0`）或删分支。
- **示例**：`scoringService.js:83`（2026-08 实锤，45df38a 已修——换指数衰减时零设施小区拿 36.8 分的历史风险已消除）。

### 反例 F.3：cos(π/2) ≠ 0 兜底失效
- **错误形态**：用 `Math.cos(x) || 0` 做零保护——`Math.cos(π/2) = 6.12e-17`。
- **为什么错**：浮点下三角函数几乎不精确等于 0，`||` 兜底恒不触发。
- **如何发现**：`node -e "console.log(Math.cos(Math.PI/2))"` → 6.12e-17。
- **修复**：epsilon 判断（`Math.abs(cos) < 1e-12`）或 `Number.isFinite` 链。

### 反例 F.4：parseFloat || 0 坏数据变 0
- **错误形态**：`parseFloat(x) || 0`——x 为 undefined/NaN 时静默变 0。
- **为什么错**：数据坏了伪装成"值是 0"——0 参与计算产生合法但错误的结果。
- **如何发现**：grep `parseFloat.*||` / `Number(.*||`。
- **修复**：显式校验 + 报错/跳过；0 值语义需注释。

### 反例 F.5：浮点直接 === 比较
- **错误形态**：`if (score === 100)` / `if (area === 0)`。
- **为什么错**：浮点运算结果几乎不精确等于字面量；0.1+0.2 ≠ 0.3。
- **如何发现**：grep `=== 0|=== 100|!== 0` 在计算后。
- **修复**：epsilon 比较封装（`abs(a-b) < 1e-9`）。

### 反例 F.6：[0,0] 坐标污染计算 ★
- **错误形态**：数据含 [0,0]（几内亚湾）进入 buffer 计算。
- **为什么错**：0,0 点的 buffer 在非洲，union 结果污染覆盖范围；渲染时飞到非洲。
- **如何发现**：grep 坐标过滤逻辑（BEIBU_GULF_BBOX）；构造 [0,0] 输入。
- **修复**：计算前范围过滤（lng 105-115, lat 18-25）+ 过滤计数日志。
- **示例**：选址数据曾含 [0,0]，2026-08 已加前置过滤。

### 反例 F.7：toFixed 在计算链中途
- **错误形态**：`const radius = (x * 1.5).toFixed(2)` 后继续参与计算。
- **为什么错**：舍入误差进入后续计算；结果系统性偏移。
- **如何发现**：grep `toFixed` 位置，判断是否在计算链。
- **修复**：计算链不舍入；展示层统一格式化。

### 反例 F.8：单位混用（米/千米）★
- **错误形态**：前端传 3000（米）、后端按 3000（千米）buffer。
- **为什么错**：buffer 范围差 1000 倍——覆盖范围荒谬但"能跑"。
- **如何发现**：沿调用链核对单位（常量注释、接口字段）。
- **修复**：单位常量 + 注释；契约测试。
- **示例**：`DEFAULT_BUFFER_RADIUS = 3000 // 米`（有注释但需验证调用链）。

### 反例 F.9：粗筛 bbox 缩小漏匹配 ★
- **错误形态**：`kmToDegreeOffset` 换算错误导致 rbush 粗筛 bbox 小于真实范围。
- **为什么错**：粗筛漏配 = 结果缺失（比慢更严重）；"看起来正常"。
- **如何发现**：粗筛结果 vs 全量精确结果对照（随机采样）。
- **修复**：bbox 保守化（≥ 真实范围）；对照测试。

### 反例 F.10：union 结果未降级（MultiPolygon）★
- **错误形态**：`turf.union` 返回 MultiPolygon 直接当 Polygon 消费。
- **为什么错**：共享边界输入（北部湾凹多边形高频）返回 MultiPolygon；渲染/过滤报错。
- **如何发现**：构造共享边界多边形；检查 union 结果类型分支。
- **修复**：类型分支 + 降级（convex 或取最大部件）+ 注释。

### 反例 F.11：缓存 key 缺维度串数据 ★
- **错误形态**：预测缓存 key `ts:{indicator}:{granularity}` 缺 confidence。
- **为什么错**：不同置信度拿到同一份数据——参数变了结果不变。
- **如何发现**：构造同 key 不同参数；检查 key 拼接。
- **修复**：key 补全维度；缓存命中对照测试。

### 反例 F.12：权重未归一化
- **错误形态**：多因子评分直接 `Σ(score × weight)` 不除总权重。
- **为什么错**：权重绝对值影响总分尺度；权重"1,2,3"与"10,20,30"结果不可比。
- **如何发现**：手工计算 3 因子用例；检查公式。
- **修复**：除以 Σweight（含零兜底）。

### 反例 F.13：排序方向错（升序当降序）
- **错误形态**：`sort((a,b) => a.score - b.score)`（升序）展示"最差小区第一"。
- **为什么错**：方向错不报错——用户看到明显错误的排名却无人察觉。
- **如何发现**：构造已知分数用例验证排序方向。
- **修复**：`b.score - a.score`（降序）；补方向断言测试。

### 反例 F.14：NaN 传播到展示
- **错误形态**：中间某步 NaN，UI 显示"NaN 分"。
- **为什么错**：NaN 传播链无人拦截；展示无兜底。
- **如何发现**：构造 NaN 输入追踪；grep 展示层 NaN 检测。
- **修复**：入口 `Number.isFinite` 守卫；展示 `Number.isNaN → '--'`。

### 反例 F.15：确定性缺失（无种子随机）★
- **错误形态**：`Math.random()` 直接用于业务数值（预测/评分扰动）。
- **为什么错**：同输入不同输出——演示重跑结果变；无法复现 bug。
- **如何发现**：grep `Math.random` 业务使用；3 次重跑对比。
- **修复**：seededRandom 确定性种子（本项目 forecastEngine 已修）；诚实标注。
- **示例**：forecastEngine 原用 Math.random 已改 seededRandom（2026-08 已修）。

### N.7 误判案例（已发生）

1. **把 lat=90 场景当业务 bug**：北部湾纬度 18-25，lat=90 不真实发生——但兜底失效仍是要修的防御缺陷（面试深挖点），等级 P1 成立，理由要写清楚"防御失效而非业务影响"。
2. **把 b044 O(n²) 当 P0**：当前规模 1.55s 可接受（已定性 P2/限期），翻倍前不是阻断。
3. **把缓存 TTL 长当串数据**：TTL 长 ≠ 串数据；串数据是 key 缺维度——判定要区分。
4. **把展示 toFixed 当计算链舍入**：1.4 只禁计算链中途舍入；展示层舍入是验收项。
