# 03 · 开发指南与决策（Development Guide）

> **定位**：项目宪法第三篇——怎么继续开发。编码规范、构建性能、布局规则、API 契约、部署运维、决策记录、AI 规则。
> **写作纪律**：规则即现状（不写日期与历史，历史进台账）；配置以 `package.json` / `.github/workflows` 为准（本文档只写意图）；性能数字标注测量日与环境，改动者同步更新。

## 一、编码规范

### 1.1 核心原则

```
1. 地理术语优先于通用术语
   lng/lat（不是 lon/lat）｜ elevation（不是 altitude）｜ feature（不是 item）｜ crs（不是 coordSystem）

2. 代码自解释，注释写"为什么"和"地理背景"
   不写 "// 遍历数组"
   写 "// 北部湾区域存在大量凹多边形，turf.union 可能返回 MultiPolygon，需降级处理"

3. 双引擎思维渗透到命名
   凡是可能同时存在 2D/3D 两种实现的，必须用策略模式命名（Renderer / Adapter / Strategy）
```

### 1.2 命名规范

**地理术语词汇表**（节选，全表见各业务 types 定义）：

| 场景       | 使用                       | 弃用                 |
| ---------- | -------------------------- | -------------------- |
| 经纬度     | `lng`, `lat`               | `lon`, `latitude`    |
| 海拔高程   | `elevation`                | `altitude`, `height` |
| 坐标数组   | `coordinates`              | `points`, `path`     |
| 单个要素   | `feature`                  | `item`, `data`       |
| 要素集合   | `featureCollection`        | `list`, `array`      |
| 渲染器实例 | `olRenderer`, `csRenderer` | `map1`, `map2`       |

**文件命名**：Vue 页面 `XxxPage.vue`、面板 `XxxPanel.vue`、组件 `Xxx.vue`；TS 模块 `camelCase.ts`；Store `xxxStore.ts` + 导出 `useXxxStore`；类型 `camelCase.ts`；测试 `原文件名.test.ts`。

**函数命名**：`动词 + 地理对象 + 动作细节`（`queryFacilitiesByPolygon`、`flyToCoordinate`）。

**类型与接口**：无 I/T 前缀，业务语义优先（`MapRenderer`、`SiteSelectionParams`）。

**常量**：模块级 + 语义分组 + `as const`；带单位注释（`DEFAULT_BUFFER_RADIUS = 3000 // 米`）。

**GCS 书写铁律**：`GCS`（Global Component Style）只允许全大写；`Gcs`/`gcs` 一律违规。`CGCS2000`（坐标系术语）豁免。

### 1.3 注释规范

- **不写**"做什么"（代码自解释）。
- **要写**"为什么"：坐标系选择、Turf.js 已知坑、性能决策、数据档位设计意图。
- **标记约定**：`FIX:`（Bug）、`TODO:`（计划功能）、`@arch-note`（架构有意为之，与 TODO 同级）。
- 不写 JSDoc 八股文（`@param`/`@returns` 重复类型信息）。

### 1.4 Vue 组件规范

- `<script setup lang="ts">`，顺序：类型导入 → 组件导入 → composable → Props/Emits → 响应式 → 方法 → 生命周期。
- Props 用 `withDefaults` + 泛型 + 元组坐标（`[lng, lat]`）；Emits 用类型化 `defineEmits<{...}>`。
- 禁止 `v-for` 与 `v-if` 同级；禁止 `$refs`（用模板 ref）。
- 样式全部走 `var(--GCS-*)`，禁止硬编码色值；尺寸经 `useGCS` 的 `v-bind()` 计算。
- `pointer-events: none` 在页面根元素 → `:deep(.GCS-panel) { pointer-events: auto }` 恢复面板交互。

**组件拆分标准（2026-08-10 定稿）**——目标不是让文件变小，而是**让变化被隔离**：

- **核心判断**：这个东西未来修改，我希望它影响其他地方吗？**不希望 → 拆**；它只是某组件内部实现细节（永远不单独存在）→ 不拆。
- **按"业务单位"拆，不按 HTML 标签拆**：UserCard 是一个整体；只有当某片段成为独立能力（多处出现：首页/评论/聊天头像）才抽成 Avatar。
- **有独立状态/生命周期/事件 → 拆**；纯展示无状态（如 PanelTitle）→ 不拆。
- **复用等级**：强复用（Button/Modal/Input）与业务复用（LayerControl 多页使用）→ 拆；页面私有但降低复杂度 → 可拆；一次性小片段 → 不拆。
- **行数经验值**：<100 行通常不拆 / 100-300 看职责 / 300-500 大概率拆 / 500+ 基本拆（地图等复杂模块例外——千行地图组件可能合理）。
- **修改测试法**：需求变更只需改一个文件 = 拆对了；需连带改多个页面 = 耦合了。
- **拆太细的代价**：文件爆炸、props 多层穿透（为显示一个数字传 5 层）、新人找不到业务入口——200 个碎片文件比一个 500 行文件更糟。
- **GCS 视角**：按"功能模块 + 状态管理 + 业务职责"拆，不按"div + css 块"拆。
- **口诀**：能独立描述功能 / 有独立状态 / 未来可能复用 → 拆；只为减少行数 → 不拆。

### 1.5 后端规范

- **三层严格分离**：routes 只注册路由；controllers 只做请求解析 + 响应组装；services 写业务逻辑。
- **错误统一**：`throw new BusinessError(ErrorCode.XXX, detail)`，错误码表见 03 §四；禁止裸 `throw new Error`。
- **缓存统一** `createReadCache`，禁止自研 cache Map。
- 后端计划迁移 NestJS：routes→`@Controller`、controllers→Controller 方法、services→`@Injectable()`、middleware→Guard/Interceptor/Pipe，保持三层分离语义。

### 1.6 Git 提交规范

```
格式：<type>: <正文>

正文写清"做了什么 + 为什么"；精简，不当日志用。
禁止 <type>(<scope>): 括号写法（scope 不值得单独突出时强制括号很难看）。
```

| Type       | 使用场景         |
| ---------- | ---------------- |
| `feat`     | 新增业务功能     |
| `fix`      | 修复 bug         |
| `refactor` | 重构，不新增功能 |
| `perf`     | 性能优化         |
| `docs`     | 文档             |
| `style`    | 纯格式调整       |
| `chore`    | 工程化杂项       |

commitlint + husky 强制；lint-staged 对暂存文件跑 eslint + prettier。

**fix 提交必须附测试**（副-27 定）：修复类提交（`fix:`/`refactor:`）必须同时提交或说明对应的回归测试（单测/集成）；纯文档/配置/样式修复可豁免并在提交说明注明。抽查历史 15 个 fix 仅 2 个带测试，此约定收口。

### 1.7 提交前自检表（五问）

| #   | 检查项           | 标准                                                  |
| --- | ---------------- | ----------------------------------------------------- |
| 1   | 坐标变量叫什么？ | `lng` / `lat` / `elevation`                           |
| 2   | 空间对象叫什么？ | `feature` / `featureCollection` / `geometry`          |
| 3   | 注释写了什么？   | "为什么这样设计" + "地理/业务背景"                    |

## 二、构建与性能

### 2.1 分包策略（设计意图）

- `manualChunks` 按依赖来源分组：vue-vendor / openlayers / cesium / echarts / ui-vendor。
- 目的不是"切得越细越好"：① 高频业务代码与稳定依赖分离，最大化缓存命中；② 大体积依赖独立成块便于按需加载。
- 具体配置以 `frontend/vite.config.js` 为准（本文档不抄）。

### 2.2 懒加载架构（原则）

| 模块           | 策略                                   | 意图                              |
| -------------- | -------------------------------------- | --------------------------------- |
| Cesium 库      | 构建时静态复制 + 运行时动态注入 script | MB 级主库不进首屏，仅切 3D 时加载 |
| CesiumRenderer | `await import()` 动态导入              | 2D-only 用户不下载 3D 渲染器      |
| ECharts        | 页面级异步化                           | 仅预测页加载                      |
| OpenLayers     | 首屏静态导入                           | 2D 地图是首屏核心                 |

判定标准：**是否首屏必需**。

### 2.3 性能基线（实测 · 数据采集日 2026-08-09 · Windows 本机 Node v25，数据已入 OS 页缓存；2026-08-16 816 复核第 1 项体积）

> 纪律：**改性能代码的人必须同步更新本表**（新数字 + 新采集日）。浏览器三项由人工验收时记录。

| #   | 基线项              | 数值                                  | 说明                                                             |
| --- | ------------------- | ------------------------------------- | ---------------------------------------------------------------- |
| 1   | floodArea.json 解析 | 读盘 ~1ms + JSON.parse 6.3ms（1.35MB） | 浏览器量级相同；816 复核实测文件 1381KB（原 3.0MB 口径过期）      |
| 2   | 选址核心计算        | 1.55s                                 | 6 类设施全选 983 POI + 557 小区，默认参数                        |
| 3   | 选址 HTTP 端到端    | 4.5s                                  | 含会话 + 序列化；核心计算为大头（已知瓶颈 b044）                 |
| 4   | 选址 union 分段     | buildTypeCoverage 占 95%+             | bus_station + primary_school union 最重；数据翻倍前需 rbush/聚类 |

**结论**：预测/地图/洪涝秒级响应；选址 2-5s（演示前预热一次接口）。未做：十万级假点、WebWorker、矢量瓦片、PostGIS 压测（明确不做，见 v2 边界清单）。

## 三、GCS 布局规范

> GCS（Global Component Style）设计系统是本项目视觉层的单一事实源：规则（§三.1）+ 资产清单（§三.2）+ 组件规格书（§三.3）。审查体系专项7 以此为"应然"基准，专项7 不再承载设计内容。

### 三.1 布局规则

- **网格单元**：`CELL_PIXEL` 按视口分级（≥1920 → 90 / ≥960 → 80 / <960 → 70）；所有面板尺寸 = 整数个 Cell，禁止硬编码 px。
- **间距**：`GAP = 10px`；面板间距 `PANEL_SPACING = 2×GAP`；安全边距 `SAFE_MARGIN`。常量在 `shared/layout/config.ts`。
- **四条铁律**：① 尺寸整数 Cell；② 锚点定位（禁绝对像素）；③ 禁止硬编码（走 `config.ts` / `--GCS-*` 变量）；④ 间距统一只用 GAP/PANEL_SPACING/SAFE_MARGIN。
- **交互契约**：容器 `pointer-events: none`、面板内 `auto`；面板分常驻/业务/临时三类，由业务页自行管理显隐。
- **响应式**：三档断点见 02 §5.4；断点判定只在 `useGCS`，组件消费 computed，禁止重复判定。
- **颜色体系**：全部 `--GCS-*` 变量（`shared/constants/colors.ts` 等）；渲染层颜色走 `LAYER_DEFAULTS`/调色板。

### 三.2 GCS 资产清单（审查定位用）

**布局常量**（`shared/layout/config.ts`）：
- CELL_PIXEL = 80（档位：≥1920 → 90 / ≥960 → 80 / <960 → 70）
- GAP = 10 / PANEL_SPACING = 20 / SAFE_MARGIN = 20 / GRID_SIZE = 100
- LAYOUT_DESKTOP_MIN = 960 / LAYOUT_DRAWER_MIN = 640

**布局 composable**（`shared/layout/useGCS.ts`）：
- useGCS()：showPanels / showTopArea / navCompact / cellPixel / panelPosition（模块级单例 + resize 150ms 防抖）

**标准组件**（`core/layout/components/`）：
- GCSPanel：面板容器（w/h/anchor/offset，pointer-events 契约）
- GCSButton：悬浮按钮（定位 + 图标）
- NavButton：导航按钮
- BottomNavBar：底部导航（三档：7 键 / 3 键）
- MobileDrawer：抽屉容器（<960px 渲染）
- TitlePanel：标题面板
- DebugToggle / GCSDebugOverlay：调试开关与覆盖层

**颜色语义分组**（`shared/constants/colors.ts`）：

**已知违约点**（状态以台账为准，此处仅审查定位）：

### 三.3 GCS 标准组件规格书（审查对照基准）

> 每个标准组件的职责、样式契约、常见误用。审查时以本表为基准判断"复用 vs 伪实现"（专项7 指标 3.2）。

**GCSPanel（面板容器）**
- **职责**：GIS 浮动面板的容器——尺寸（Cell 整数倍）+ 锚点定位 + 内容插槽。
- **Props**：`w`（Cell 宽）/ `h`（Cell 高）/ `anchor`（top-left/top-right/bottom-center 等）/ `offsetX` / `offsetY` / `title?`。
- **样式契约**：背景 `var(--GCS-bg-panel)`；圆角 `var(--GCS-radius-lg)`；阴影 `var(--GCS-elevation-2)`；`pointer-events: none` 容器 + `:deep(.GCS-panel) { pointer-events: auto }`。
- **常见误用**：业务组件手写同结构面板（伪实现）；`w` 传非整数（`w="3.5"` 绕过网格）；面板内再套 absolute 定位（应使用锚点 offset）。

**GCSButton（悬浮按钮）**
- **职责**：地图上的圆形悬浮操作按钮（定位 + 图标 + 点击）。
- **样式契约**：圆形（radius pill）；背景 `var(--GCS-bg-elevated)`；图标 `currentColor`；hover/active 状态走 token；z-index 走层级常量。
- **常见误用**：手写圆形按钮（重复实现）；按钮内 SVG fill 写死；多个悬浮按钮手工排布（应组件内管理间距）。

**NavButton（导航按钮）**
- **职责**：顶部/底部导航的按钮（label + icon + active 态）。
- **样式契约**：active 态 `var(--GCS-primary)` 高亮；禁用态灰化；尺寸 token。
- **常见误用**：业务页自绘导航按钮（active 态各写各的）。

**BottomNavBar（底部导航）**
- **职责**：底部导航栏，三档行为（≥960 隐藏 / 640-959 7 键含菜单 / <640 3 键紧凑）。
- **样式契约**：背景 `var(--GCS-bg-panel)`；顶部 border `var(--GCS-border-subtle)`；z-index 层级常量。
- **常见误用**：业务组件自绘底部导航；在组件内重复判定断点（应消费 useGCS navCompact/showPanels）。

**MobileDrawer（抽屉容器）**
- **职责**：档位 2/3 下面板收进抽屉（<960px 渲染）。
- **样式契约**：宽度 token；滑入动画（duration-medium + ease）；遮罩 `var(--GCS-overlay)`；z-index 高于面板低于 modal。
- **常见误用**：断点判断漂移（注释与代码不一致——历史事故）；抽屉内面板脱离 GCS 布局。

**TitlePanel（标题面板）**
- **职责**：顶部标题/城市切换区域（showTopArea 控制）。
- **样式契约**：字号 `var(--GCS-font-20)`；text-primary；背景透明或 panel。
- **常见误用**：标题字号散落（页面各自定义标题样式）。

**DebugToggle / GCSDebugOverlay（调试开关与覆盖层）**
- **职责**：开发调试（网格叠加层、开关）。
- **样式契约**：仅 dev 构建加载；z-index 最高层（调试覆盖）。
- **常见误用**：生产构建误打包；覆盖层 z-index 污染正常层级。

### 三.4 组件复用判定流程（对应专项7 指标 3.2）

```
发现疑似伪实现（手写面板/按钮/导航）
  → 对照 §三.3 规格书：职责是否与标准组件重叠？
  → 是 → 检查能否直接复用（props 是否覆盖需求）
  → 能 → 迁移复用，伪实现删除
  → 不能 → 评估：扩展标准组件（加 props）还是新组件立项（03 §1.4 判定）
  → 新组件 → 进 core/layout/components/ 或 shared/components/
```

### 三.5 Token 变更 SOP（S7-10 定）

1. **改前先查**：新增/改色前 `grep -rn -- '--GCS-' frontend/src` 确认现有引用与同值 token（防重复与撞名）。
2. **改名留映射**：token 改名必须留映射注释（旧名 → 新名）至少一个版本，同步更新 §三.2 资产清单。
3. **双份同步**：`shared/constants/colors.ts` 与 `style.css` 同值色（如 #409eff）属渲染/DOM 双通道，改一边必须同步另一边（S7-01/11 绑定规则）。
4. **删除先验**：删 token 前跑 `node tools/token-stats.mjs` 确认无真实引用；仅注释提及视为未消费。
5. **验收**：`npm run stylelint` + `node tools/token-stats.mjs` 死 token ≤5%、硬编码清零后合入。

## 四、API 契约

> **完整契约**：`docs/开工前必读/API契约文档.md` 是本契约的**活文档**（与本文档并存，非历史档案）——信封格式、错误码表、认证、限流、接口清单的完整细节都在那里，接口索引以代码（backend/routes/）为准。
> 本节只保留最核心的格式约定，细节一律看上面那份：

- **信封**：`{ code, data }`；成功 `code=同 HTTP 状态`（200/201，权威口径见 API契约文档 §1.1）；错误码双轨制 `<HTTP status><业务序号>`（如 `400001` = 400 + 0001）。
- **错误码表**（7 项）：`INVALID_PARAMS 400001` / `UNAUTHORIZED 401001` / `FORBIDDEN 403001` / `NOT_FOUND 404001` / `DUPLICATE_USERNAME 409001` / `DUPLICATE_RESOURCE 409002` / `ANALYSIS_FAILED 422001`。新增按此规则扩展，不复用已存在 code。
- **认证**：HttpOnly Cookie 会话（JWT）；仅"收藏"相关接口要求登录（期望方向，见 02 §4.5）。
- **接口族**：auth（登录/注册）、site-analysis（选址，POST）、forecast（timeseries / indicator / map）、flood（water-area / flood-areas / flood-statistics / terrain-profiles / analysis）、flood-online（FastAPI 裸 JSON，`envelope: false`）。
- 接口索引以代码（backend/routes/）为准；HTTP 边界 100% zod 校验是红线。

## 五、部署与运维

### 5.1 当前部署形态

- 阿里云轻量应用服务器（1.6Gi 内存 / 40G 磁盘 / Ubuntu 24.04），Docker Compose 单容器 `beibu-gulf-webgis`。
- 容器内 nginx（80/443）→ 前端 dist + 反代 `/api`→Express:3000、`/flood-online`→FastAPI:8000、`/static/` 直发后端静态、`/tianditu/` 天地图同源代理。
- 部署目录 `/opt/beibu-gulf/`（git 仓库 = CI 部署目标）：compose / Dockerfile / entrypoint / nginx.conf / .env / backend（data + static：dem、terrain）/ frontend / certs / scripts。
- 数据卷：backend/data、static/dem、static/terrain、certs 均为 volume，构建不覆盖。

### 5.2 自动化链路

- CI（GitHub Actions）：audit（npm audit 高危阻断）→ lint-and-build（format/lint/cruise/typecheck/gitleaks/.env 检查/测试/build）→ backend-tests → deploy（仅 main，SSH 部署：`git pull --ff-only` + `docker compose up --build -d`）。
- 密钥走仓库 Secrets（TIANDITU_KEY / SERVER_SSH_KEY / SERVER_HOST / SERVER_USER）。

### 5.3 HTTPS 与证书

- Let's Encrypt + duckdns DNS-01，**自动续期**两条链路已验证：certbot.timer 每天检查（到期前 30 天自动续期）+ deploy hook 自动同步新证书到容器并 reload。
- 唯一前提：**duckdns token 不要动**。排查命令：`sudo systemctl list-timers | grep certbot`。

### 5.4 排雷要点

- 小内存机器：CI 增量构建没问题，全量 `--no-cache` 构建注意内存。
- 生产 3D 真地形依赖镜像内 dist 与 terrain volume 同步（历史教训：镜像旧 dist 导致 3D 无真地形）。
- 详见台账中部署相关条目；历史部署历程文档保留在 `docs/开工前必读/` 供回溯。

## 七、决策记录（ADR）

> **格式**：背景（为什么有这个问题）→ 决策（选了哪个）→ 代价（放弃了什么）。
> **注释与 ADR 分工**：注释回答"这行为什么这样写"（局部实现）；ADR 回答"这个设计为什么存在"（全局结构），互不重叠。同一"为什么"被问到第 3 次 → 从注释升级进 ADR。

**已实证决策**（从代码与历史文档提炼）：

1. **双引擎（OL + Cesium）**：低功耗 2D、需求时 3D；业务经 MapRenderer 接口不绑死引擎。代价：双实现维护成本。
2. **数据源三态演进（mock → api → online → PostGIS）**：mock 契约桩给前端独立开发，api JSON 过渡，online 真演算；adapter 隔离保证演进时业务零改动。代价：三套数据源并存期的语义管理成本。
3. **Express + FastAPI 并存**：重计算（真 DEM 演算）走 Python，业务 API 走 Node。代价：两个后端两套部署/测试。
4. **分层收口 + index 入口**：跨层 import 只走入口，防依赖失控（dependency-cruiser 强制）。代价：新增导出必须维护入口。
5. **暂不用数据库（JSON 文件 + createReadCache）**：当前数据量有限，主要验证业务流程。**必上路线**：PostgreSQL + GeoServer（否则停留在玩具级）。
6. **不用 ORM**：repositories 直接读 JSON（readStaticJson 统一缓存）。迁移数据库时替换 repositories 层即可。
7. **siteSelectionStore 保留 Pinia（816 修订）**：原「去 Pinia：模块级单例 + 快照工厂」决策已随 b047 修订——现为 Pinia setup store（`defineStore('site-selection')`），快照恢复仍走内存级快照工厂；代价：保留 Pinia 响应式全局态（选址结果需被 AppLayout 全局雷达跨组件消费）。
8. **竞态收敛到 useLatestRequest 单实现**：原四处手写 AbortController 收敛为一个 composable（`shared/composables/useLatestRequest`，业务方各自实例化），新请求优先、旧请求取消。代价：`useApiRequest` 基础层仍自持 AbortController（超时/外部 signal 基础能力，与竞态层分工，非重复实现）；路由级全局取消未做（z071）。
9. **快照只做内存级**：刷新即失是设计不是缺陷（跳个人中心往返保留，刷新重新开始）。

**历史决策补充**：⏳ 占位符（用户后续补充：项目早期决策，如技术栈选型过程、为什么不用 QGIS Server、为什么不用 vuex 等——按上述格式记录）。
