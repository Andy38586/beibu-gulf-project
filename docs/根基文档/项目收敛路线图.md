# 项目收敛路线图（细粒度 · 防偏移）

> **目标**：把项目从「每轮审查发现同一批问题」变成「老债单调递减、新债不再产生，最终可恢复业务开发」。
> **本文定位**：可交接的执行路线。每一步都有**机器可检查的出口条件**，不靠记忆、不靠"做完了"这种自述。

## 二、防偏移机制（六条，不可省）

1. **出口条件是命令，不是描述。** 每步的"完成"必须是一条能跑的命令 + 预期输出；跑不出来就是没完成。
2. **每类债有基线文件。** 量化出来的数字落成 baseline（如 `dead-code-baseline.json`）；后续任何一轮改动，它**只许下降或持平**，上涨即红。
3. **窗口预算。** 一个窗口最多碰 **3 个模块**、最多 **5 笔提交**（沿用 AGENTS 的批次上限）。超了就开新窗口。
4. **偏离即停。** 若某步产出与计划不符（死物数没降 / 出现新的失败测试 / 基线被迫上调），**立刻停**，把原因写进台账，不许"顺手绕过去"。
5. **交接靠台账，不靠记忆。** 每步完成即回写台账（状态词 + 行内钩子按新 HEAD 重写）。下一轮从台账接手，不读上一轮的对话。
6. **禁止大提交。** 任何单笔提交若涉及 >10 文件或 >3 个模块，拆开再提。格式类改动**严禁**与逻辑改动同笔（会破坏行号锚）。

### S2 · 清老债（按模块，N 窗口；**风格统一并入本步**）

**每模块一轮，一轮一笔或几笔提交**，固定动作序列：

```
for 模块 in 按死物数降序:
  1. 清死物（删或接线；废弃要成文 + 能红守卫）
  2. 统一风格（格式/命名/结构；与上一步分开提交）
  3. 补/加严判据（该模块的断言补变异四式）
  4. 基线下调（dead-code-baseline 与覆盖率基线同步）
  5. 整链自检（typecheck×2 / 全量测试 / stylelint / guard:v3）
```

| 出口条件            | 判据                                |
| ------------------- | ----------------------------------- |
| 死物数单调下降      | `dead-code` 报总数 ≤ 上一轮         |
| 每笔提交可单退      | 单笔 ≤10 文件、≤3 模块              |
| 57 条 open 逐条处置 | 台账每行有状态词 + 跑得通的行内钩子 |

## 四、窗口边界（关于"能不能一个窗口全做完"）

**不能，也不应该。**

- **能**：S0 全量 + S1 的一到两项（本窗口计划）
- **不能**：S2（清 57 条老债 + 风格统一）—— 那是按模块分批的 N 轮工作，且必须分批才能"要退只退一笔"
- **判据**：如果某一步的产出会形成一个「要退只能整块退」的提交，那这一步就切错了，拆开重来
