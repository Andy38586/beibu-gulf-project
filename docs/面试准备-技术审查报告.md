## 第一部分：项目真实性审查

### 1. 业务闭环

**项目定位**：北部湾港口设施选址分析 + 浸没风险评估 + 吞吐量预测。

**业务闭环真实性**：基本成立，但存在"为技术而设计"的痕迹。

| 业务模块 | 真实性 | 质疑点 |
|---------|-------|-------|
| 选址分析 (site-selection) | 中等 | 候选小区数据来源为静态 JSON，实际的"选址"是设施 POI 缓冲区叠加打分，不是真实规划业务中的多维度用地评估 |
| 浸没分析 (flood-analysis) | 较弱 | 水位数据硬编码 7 档（1-7m），不是真实 DEM 地形计算；水面坐标存在 hardcoded 兜底值 |
| 预测分析 (forecast) | 较弱 | 数据来源是 mock JSON，无真实预测模型，本质是时间序列数据的可视化展示 |

**"为展示技术而设计功能"的嫌疑点**：

- **浸没分析的"水面效果"**：用 Cesium entity 动画实现视觉效果，但水位数据来源是前端硬编码 7 档，业务层面是假的
- **预测分析的"播放"功能**：500ms/帧的动画效果，但数据是静态 JSON 循环，没有真实预测算法
- **三套 API 响应格式并存**：RESTful / GCS / 混合三种格式同时存在，总共约 30 个端点，完全可以统一——本质是"为了兼容历史"而非"业务需要"

### 2. 架构是否服务业务

| 抽象 | 真实使用场景 | 面试官追问风险 |
|------|-------------|--------------|
| **Renderer** | OLRenderer + CesiumRenderer 双实现 | ⚠️ "除了切换引擎，这个抽象还解决了什么？" |
| **GCS** | 19 个组件使用 useGCS() | ✅ 真实高频使用，可回答 |
| **BusinessLayerManager** | 3 个业务页面使用 | ⚠️ "直接调 renderer.registerLayer 不行吗？为什么需要这一层？" |
| **DataAdapter** | floodAdapter + forecastAdapter | ⚠️ mock 模式从未真正切换过，"这个抽象验证过吗？" |
| **Store 设计** | 8 个 Store/State | ⚠️ floodState 和 siteSelectionState 结构一致（文档 §D03 已承认），是重复而非抽象 |

**容易被追问"为什么需要这个"的设计**：

1. **BusinessLayerManager**：只有 3 个使用者，且 register / updateData / remove 三个方法可以直接在 mapStore 里实现。需要准备好具体的"如果没有这一层会出什么问题"的回答。
2. **DataAdapter**：mock 模式从未真正切换过，适配器本质只是一个中转层。"切换能力"是理论上的。
3. **Cesium 单例保留**："低端设备也保留"是性能取舍，但面试官会追问"你测过低端设备吗？内存占用多少？"

## 第二部分：架构面试压力测试

### 模块设计

**Q1: 为什么这样划分 core / business / shared？**

- **合理的回答**：依赖方向单向——core 不知道业务模块的存在，业务可以依赖 core 和 shared。这使得新业务模块独立开发、独立卸载，不会影响核心引擎。
- **风险回答**：如果回答"为了分层而分层"，会被追问"build 配置里的 A05 —— visualization 反向依赖 business 是怎么回事？"——这是一个已知的架构违规。

**Q2: 新增业务模块需要修改哪些地方？**

- 参考文档 §10 的 7 步流程：注册路由 → 创建 Store → 创建 Adapter → 注册 Adapter → 创建业务页面 → 创建视图组件 → 如需新图层类型则在 MapRenderer 添加方法。
- **风险点**：Step 5 "在 MapRenderer 接口添加方法"——如果新业务不需要新图层类型呢？流程中应该是"如需"才做。面试官可能会问"如果不需要新图层类型，流程是 6 步还是 7 步？"

**Q3: business 文件夹膨胀怎么办？**

- 当前只有 3 个业务模块，未到膨胀阈值。
- **真实风险**：如果业务到达 10+ 个，business 平铺结构会有维护问题。文档中没有给出"业务内子模块划分"的指引（如按领域划分子目录）。

**Q4: 两个业务共享能力怎么处理？**

- 文档 §2.3 明确：被 ≥2 个业务使用 → 抽到 shared。
- **缺失**：visualization 层的抽取规则没有明确——如果两个业务都需要同一种新图表类型，应该放到 visualization 的哪里？

### 地图架构

**Q1: 为什么不直接用 OpenLayers API？**

- 标准回答：项目需要支持 2D/3D 双引擎切换（OpenLayers + Cesium），Renderer 抽象隔离了两个引擎的 API 差异。
- **压力追问**："除了切换引擎，还有什么场景需要这个抽象？"��—可以回答"测试时可以 mock renderer，不需要真实地图环境"；如果能补充"未来换其他引擎只需要改 renderer 实现"，会更强。

**Q2: Renderer 抽象解决什么问题？**

- 隔离 OL / Cesium API 差异，业务代码不直接接触底层地图 API。
- **压力追问**："你的 OLRenderer 约 381 行，CesiumRenderer 多少行？维护两个渲染器的成本 vs 直接用 OL API 的成本，算过吗？"——这是一个成本收益分析问题，需要有数据支撑。

**Q3: 未来换 Cesium 需要改多少代码？**

- 理论上只改 core/map/renderers/ 下的渲染器实现。
- **压力追问**："业务代码真的不依赖 OL 特有概念吗？比如 turf.buffer 的坐标系？"——答案是：turf.buffer 的计算不经过 Renderer 抽象，确实可能存在隐式依赖，需要诚实回答。

**Q4: 抽象是否真的减少成本？**

- **这是最危险的追问**。当前抽象成本：MapRenderer interface + 2 个渲染器实现 + BusinessLayerManager + useMapRenderer composable。收益：路由切换时 2D/3D。
- 如果面试官认为"2D/3D 切换可以用两个路由组件分别实现，不需要抽象"，需要回答："两个组件各自维护图层逻辑会导致代码重复；Renderer 抽象使将来增加新引擎、测试 mock 成为可能。"

**Q5: 地图实例生命周期？**

- Cesium 使用单例保留——"为什么不销毁？内存占用多少？测过吗？"
- OL 容器 v-show 不销毁 DOM——"两个引擎同时占用 DOM，低端设备卡吗？"
- 这两个问题需要有实测数据，否则会被追问。

### 状态管理

**Q1: 为什么用 Store 不用 ref？**

- 跨组件共享的需要——比如 mapStore.currentRenderer 需要被多个业务模块访问。
- **压力追问**："floodState 只在 FloodAnalysisPage 使用，为什么是全局 Store 而不是组件内 ref？"——这个问题需要回答：是为了支持状态跨引擎生命周期保持（2D/3D 切换时状态不丢失）。

**Q2: 哪些数据该进全局状态？**

- 文档 §6.2 给了 3 种模式，但缺少一个明确的"判断标准"（如：跨组件共享 → Store，页面内私有的 → 组件内 ref）。
- **风险**：新人开发时可能把页面私有数据塞进 Store。

**Q3: 如何避免 Store 无限膨胀？**

- 文档 §6.2 模式一已承认"mapStore 累积职责"——这是已知问题。
- **压力追问**："mapStore 现在约 8 个职责（引擎 / 图层目录 / 分析结果 / 注册器 / 相机状态...），你怎么控制它不继续膨胀？"——需要给出具体的拆分策略（如按职责拆分为 mapEngineStore、layerCatalogStore、cameraStore）。

**Q4: 多业务同时修改地图状态怎么办？**

- 当前没有并发控制机制。
- **压力追问**："两个业务同时 registerBusinessLayer，layerCatalog 的顺序怎么保证？"——诚实回答：当前是单用户操作，不涉及并发写入。如果是面试场景，可以补充"需要加锁机制"的意识。

## 第三部分：工程能力审查

### 性能

**数据量现状**：

| 数据文件 | 大小 | Feature 数量级 |
|---------|------|-------------|
| xiaoqu.json | 75 KB | 数百个小区 |
| qz_bus_station.json | 54 KB | 数百个 POI |
| forecast/*.json | 48 KB | 时间序列点 |

**致命问题：数据量太小，空间索引 (rbush) 是过度设计**

项目实现了 rbush 空间索引（spatialIndex.ts），但最大数据文件只有 75 KB / 数百个 Feature。rbush 的价值通常在 10000+ 要素时才体现。

**面试官必问**：
- "你的空间索引阈值是 1000，但数据量只有几百，这个索引有什么用？"
- "如果数据量增加 10 倍到 750 KB，需要空间索引吗？100 倍到 7.5 MB 呢？"
- "你有 WebWorker 吗？为什么没有？"

**渲染方式**：
- OpenLayers：Canvas 渲染（OL 默认）✅
- Cesium：WebGL ✅
- 但缺少：矢量瓦片、clustering（聚合）、LOD

**大数据应对能力评估**：

| 优化手段 | 是否具备 | 风险 |
|---------|-------|------|
| 空间索引 (rbush) | ✅ 有但数据量不匹配 | 过度设计 |
| WebWorker | ❌ | 数据量小时不需要，但面试中需要解释为什么没有 |
| 矢量瓦片 | ❌ | 数据量小时不需要 |
| 后端空间查询 | ❌ | 后端只读 JSON 文件 |
| 聚合 (cluster) | ❌ | POI 多了会重叠 |
| 性能测试数据 | ❌ | 没有任何实测渲染帧率数据 |

### 前端工程化

| 检查项 | 状态 | 面试风险 |
|------|------|---------|
| 统一错误处理 | ⚠️ useApiRequest 部分统一 | 三套响应格式，错误处理逻辑不统一 |
| 日志体系 | ⚠️ 有 logger 模块 | 需确认是否区分环境、是否有上报机制 |
| 环境区分 | ⚠️ 有 VITE_ 环境变量 | mock/API 切换从未真正用过 |
| 代码规范 | ✅ 有 ESLint + Prettier | 良好 |
| 自动化测试 | ❌ **仅 4 个测试文件** | **最大短板** |
| 构建优化 | ⚠️ Vite 默认配置 | 无 chunk 分割、无懒加载优化 |

**致命问题：测试覆盖率几乎为零**

现有 4 个测试文件：
- `MapRenderer.interface.test.ts`（接口测试）
- `UnifiedMap.test.ts`（骨架测试）
- `useChartBase.test.ts`（图表基础）
- `spatialIndex.test.js`（空间索引）

业务逻辑零测试，Store 零测试，API 调用零测试。

## 第四部分：代码质量审查

### 1. AI 生成代码风险

**疑似 AI 生成的痕迹**：
- 文档极其详尽（§1-§12 共 1000+ 行），但代码只有约 123 个源文件——文档量 > 代码量，AI 生成文档的典型特征
- 三套响应格式并存——真实项目不会这样设计，是"为了展示而设计"
- BusinessLayerManager 只有 3 个使用者但做了完整抽象——过度设计
- spatialIndex.ts 实现了但数据量不需要——"为未来设计"但未来未到

**重复代码模式**：
- `floodState` 和 `siteSelectionState` 结构一致（saveState / consumeState 模式重复）
- 三个业务页面的 `watch renderer → registerGcsLayers` 模式重复

**无意义封装**：
- DataAdapter 模式——mock 模式从未切换过，适配器只是一个中转层

### 2. 维护风险

**原作者离职后的维护难度**：
- 文档详细，但文档与代码已有偏差（如 UnifiedMap 文档某处说 550+ 行，实际约 381 行）
- 三套响应格式——新人不知道该用什么格式
- mapStore 职责过重——改一处可能影响全局
- **CI typecheck 是 `continue-on-error: true`**：类型检查允许失败，意味着 TS 类型可能不完整

## 第七部分：技术债优先级

### P0 — 面试一定会暴露

**问题 1：测试覆盖率几乎为零**

- **为什么危险**：面试官必问测试。4 个测试文件（且多为骨架/接口测试）无法过关。
- **面试官会问**："你的核心业务逻辑（选址打分、浸没分析）有测试吗？"
- **修复方案**：至少为选址打分算法、crs.ts、floodState 写单元测试，把核心逻辑覆盖率提到可展示的水平。
- **需改代码**：是

**问题 2：CI typecheck 允许失败**

- **为什么危险**：`continue-on-error: true` 意味着类型检查形同虚设。
- **面试官会问**："你的 CI 真的保证类型安全吗？"
- **修复方案**：清理所有类型错误，移除 `continue-on-error`，让 typecheck 回归阻断位。
- **需改代码**：是

**问题 3：业务数据是 mock / 硬编码**

- **为什么危险**：面试官追问业务真实性会暴露。
- **面试官会问**："水位数据从哪来？预测算法是什么？"
- **修复方案**：诚实说明项目处于"架构验证阶段"，有接入真实数据的适配器接口设计（DataAdapter），待真实 API 就绪即可切换。同时调整简历措辞，不夸大。
- **需改文档**：是（简历描述）

### P1 — 深入追问可能暴露

**问题 4：三套响应格式无统一计划**

- **面试官会问**："为什么不统一？什么时候统一？"
- **修复方案**：给出迁移时间表，或明确"新接口统一使用 RESTful 格式"的约定。

**问题 5：空间索引是过度设计**

- **面试官会问**："数据量这么小为什么用 rbush？"
- **修复方案**：
  - 诚实回答：架构验证阶段预留的扩展能力，当前数据量下索引开销为零（阈值判断），不影响性能。
  - 备选回答：如果面试官不买账，直接承认"这个阶段确实不需要，是设计上的提前量"。

**问题 6：DataAdapter 从未真正切换**

- **面试官会问**："mock 模式切换验证过吗？"
- **修复方案**：诚实说明"适配器接口已定义，两套实现（mock / api）并存，切换只需改一行导入。待真实 API 就绪后即可验证。"

**问题 7：mapStore 职责过重**

- **面试官会问**："8 个职责在一个 Store，怎么维护？"
- **修复方案**：准备拆分思路——按职责拆为 mapEngineStore / layerCatalogStore / cameraStore，并说明当前阶段 3 个业务模块未触发拆分必要性。
