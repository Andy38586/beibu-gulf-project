## 一、项目一句话叙事与数据叙事（背诵稿）

### 1.1 一句话叙事模板（doc1 一，背诵）

> 「一个面向北部湾港的港口选址情景推演与多准则决策支持平台：基于真实 DEM（ESA GLO-30 + UCSD SRTM15+）与 OSM 路网，用连通性演算、空间 SQL、图路由做浸没风险、可达性和多准则选址分析；前端 Vue3+TypeScript 双引擎（OpenLayers/Cesium）热插拔架构，后端 NestJS + FastAPI 双后端 + PostGIS。全部数据来自免费公开源，处理链可复现（GDAL/pyosmium 脚本），每份数据有校验。」

> doc5 Q1 逐字版（更贴合当前代码）：
> 「这是一个面向北部湾港（钦州）的智慧港口空间分析平台，解决三类真实问题：第一，港口配套选址——6 类设施（医院、学校、公园、公交站、商场）的覆盖范围叠加与距离加权评分，输出候选小区排名和雷达图；第二，吞吐量预测——4 项指标的趋势可视化，其中 cargo/container 是真实历史数据；第三，浸没分析——基于真实 ASTER 30 米 DEM 的连通性淹没演算，水位 0 到 25 米任意档位查表秒回，输出淹没范围、受影响设施和损失评估。数据方面：983 个真实 POI、557 个小区、3 个港口、83 个港口设施、真实 DEM 流水线。整个平台是『数据 → 后端空间计算 → 前端可视化 → 方案收藏』的完整闭环。需要说明的是，项目定位是验证一套可扩展的 GIS 业务系统架构，数据规模是中小的——全仓约 1.8MB，我把真实规模主动说清楚。」

### 1.2 数据叙事（doc1 二，背诵）

> 「全免费公开数据：陆地 DEM 用 ESA GLO-30（30m）和 UCSD SRTM15+（15弧秒陆海一体），路网/海岸线从 OSM 提取（165k 公路 + 9.5k 铁路 + 16k 海岸线），红树林用 GMW v3、保护区用 WDPA，吞吐量用公开统计。每份数据有校验（官方 MD5/文件魔数/全量读取统计/语义范围检查）。规模诚实口径：原始 20GB、处理后入库约 100-200MB，属小到中型；选 PostGIS 是功能驱动（pgRouting 最短路径、空间 SQL、外键约束——迁移时它当场暴露了 7 条孤儿方案数据）。」

### 1.3 最危险的叙事断层（doc4 独有核心发现，综合版最高优先防守位，以最新代码复核）

**一句话**：项目最能打的技术点——「基于 DEM 的连通性淹没算法（scipy.ndimage.label + 海域种子点）」——**写了、跑得通、但线上演示时默认不在执行**；同时三维叠加因未处理椭球高而垂直错位。

**事实链（doc4 四条独立证据互相咬合）**：
1. `main.ts:46` 数据源默认 `'api'`，`frontend/.env.production` 只有 `VITE_API_BASE=/api`、没有 `VITE_DATA_SOURCE=online` → 生产构建走 api 分支。
2. api 分支的洪涝 = `floodAnalysisController.js:42` `data.floodZones.find(zone => zone.waterLevel >= level)` —— 6 档静态 GeoJSON 向上取档（注：与 251 档预计算表是**两套数据**）。
3. api 分支的灾害评估 = `floodService.js:26-31` `facility.elevation <= level` —— 纯高程阈值筛选，**无连通性判断**，内陆封闭洼地会误判为"被淹"（Python 侧 `flood_engine.py:96,101` 正确处理了 8 连通 + 海面种子）。
4. `Dockerfile` / `docker-compose.yml` 零 python/uvicorn/fastapi，flood-service 不在容器编排里。

**面试官追问路径**：
> 「你现在演示的这个水位滑块，请求打到哪个接口？」→ 打开 Network 看到 `/api/flood/flood-areas` → 「那 FastAPI 那个服务呢？」→ 当场解释不清就是重伤。

**处置 A/B 方案（二选一，面试前做完）**：
- **A（推荐，成本低）**：把 flood-service 加进 docker-compose（多一个 service + uvicorn 命令），生产 env 设 `VITE_DATA_SOURCE=online`，线上真跑连通性演算。nginx 的 `/flood-online/` 反代已写好，只差把服务拉起来。
- **B（保底）**：主动承认并讲成设计决策——「预计算 251 档 gz（2.88MB）覆盖 0~25m 全量水位，线上默认走预计算表以保证响应确定性；FastAPI 在线演算作为 miss 时的 fallback 与算法验证通道」。**但前提是 api 分支得真的读 flood_levels.json.gz（251 档），而不是现在的 floodArea.json（6 档）**——否则讲不圆。

**Cesium 椭球高 vs 海拔高（doc4 独有，GIS 面试官一击必杀）**：全仓零 `heightReference`/`CLAMP_TO_GROUND`/`sampleTerrain`，`CesiumRenderer.ts:1341` polygon.height=0.5 绝对高；接了真实 terrain（`:504` CesiumTerrainProvider）后，业务图层与地形垂直方向错位——北部湾 geoid 分离约 **-30~-70m**。最小修复 = 点位加 `heightReference: CLAMP_TO_GROUND`、面加 `classificationType: TERRAIN`；能解释 geoid 分离更好。

**最大短板一句话（doc1）**：**架构复杂度与数据规模倒挂**（557 小区配视口裁剪——裁剪从未被真实数据触发，阈值 1000 vs 最大图层 372）。

### 模块与架构（Q1–Q9）

#### Q1. 项目解决什么真实问题？
**为什么问**：怕「为炫技而做」。
**逐字脚本**：见 1.1 节 doc5 Q1 逐字版。
**追问分支**：若被问「预测和损失是真实的吗」→ 按 Q18(13)/Q15 脚本，主动坦白演示级模型。
**防守/加分点**：三个业务闭环 + 数据来源真伪清单（含合成部分主动坦白）。坦承「架构验证」不是「交付系统」（doc4 README 已定调）。doc2 实录「业务闭环真，不是纯炫技；但『大规模』是后端算、前端只收结果」。
**故事弹药**：—（见 Q6/Q18 链）。
**取证位置**：`docs/性能实测-2026-08-13.md`；`backend/services/scoringService.js`、`siteAnalysisService.js`；`forecastEngine.js`（合成标注）；`flood-engine.py`。

**模块设计补充防守位（doc3 Q「业务膨胀怎么办」，非 Top30 编号题）**：若被问「business 越来越多怎么不膨胀」——答项目规约「单模块内只放 Page+composables+constants，禁止跨文件新抽象；能力复用走 shared」。**防守点（b045 已立案）**：当前三个模块结构并不一致——flood 有 `constants/` 无 composables、forecast 两者都有、site-selection 无 constants——面试官会说「你说的规约自己都没遵守」。诚实答：这是已知技术债（b045），正在统一模板。doc2 同题 `Q4` 另提醒：共享能力走 shared 这条路已经走歪（见 `shared/constants/forecast.ts:3-7` 假共享，Q29/六章）。

#### Q2. 数据量多大？浏览器扛得住吗？
**为什么问**：验证是否虚报「大规模」。
**逐字脚本**：
> 全仓 21 个 JSON 数据文件，raw 1.81MB、gzip 217KB；最大业务点图层是公交站 372 个要素；最大 GeoJSON 是行政区划边界约 303KB。前端只渲染分析结果，重计算（选址评分、连通性演算）都在后端。这个规模对浏览器毫无压力，实测选址全选 6 类设施后端计算 2.4 秒，洪涝查表小于 10 毫秒。所以我不说「支持大规模空间分析」——当前是千级要素规模。为大数据做的基建（视口裁剪、空间索引）有，但真实数据还没触发过，这一点我如实说明（Q22 详述）。
**追问分支**（doc4 C 组）：「最大 GeoJSON 多大？多少要素？」→ 1.4MB/121 Polygon/31902 顶点（历史口径 doc4，accepted 当额外素材但以 1.81MB 为口径）；「Canvas 还是 DOM？」→ OL/Cesium 均 Canvas，前端只画结果、重算在后端。

#### Q3. 为什么用双引擎 OL + Cesium？
**为什么问**：架构决策是否拍脑袋。
**逐字脚本**：
> 两个引擎解决不同的展示需求：2D（OpenLayers）适合选址、预测这类以图层叠加和平面分析为主的操作，交互轻、加载快；3D（Cesium）用于浸没分析，需要真实地形起伏来展示淹没范围——水面要贴地形、淹没多边形要沿地形裁剪，这是 2D 平面图表达不了的。所以我在业务注册清单里给每个模块声明 engine 字段：选址和预测是 2d，洪涝是 3d，路由切换自动带起引擎切换。选择 OL 而不是 Leaflet，是因为 OL 的投影体系、矢量渲染和后续 3D 化的路径更成熟；Cesium 是 3D 地形的行业标准，两者组合是 WebGIS 的常见搭配。
**追问分支**（doc3 Q1 防守）：「为什么不直接统一用一个引擎？」→ 2D/3D 需求确实不同；能力接口（Water3D/GeoTIFF/Heatmap）收敛避免 2D 背负 3D 契约。
**防守/加分点**：能讲出「能力接口」设计 + manifest 每模块声明 engine（doc3）。真实需求驱动（洪涝页 3D、其余 2D），不是炫技。
**取证位置**：`business/manifest.ts` 每模块 engine 字段；`docs/根基文档/项目全景.md`。

#### Q4. Renderer 抽象解决什么问题？
**为什么问**：抽象是否有真实价值。
**逐字脚本**：
> 核心是让业务层不感知引擎差异。业务代码只面向 MapRenderer 契约操作：加图层、设显隐、flyTo、导出导入相机状态，不碰 OL 或 Cesium 的 API。引擎切换时，UnifiedMap 把当前渲染器的相机状态 exportState 出来，新引擎 importState 恢复，业务图层由 BusinessLayerManager 的 reapplyAll 统一重绘。实测 2D↔3D 切换约 55 毫秒。还有一个细节：2D 和 3D 能力不是对等的——水面只有 Cesium 有、热力图只有 OL 有。我没有把这些塞进基类，而是收敛成三个能力接口（Water3D/GeoTIFF/Heatmap），调用方先做能力检查再调用，避免 2D 背负 3D 的契约。

#### Q6. 你的抽象是减少成本还是增加复杂度？
**为什么问**：这是「过度设计」与否的终极拷问。（doc3：本报告判定的最危险问题之一。）
**逐字脚本（诚实版，先承认再辩护）**：
> 诚实的答案是：对当前 3 个业务、2 个引擎的规模，抽象有净成本。支撑双引擎切换，我付出了：渲染器抽象基类、能力接口和类型守卫、业务图层管理器（BLM）的双状态源（注册表 + 图层目录）、pending visibility 队列、引擎切换时的手工状态同步。这些复杂度只为一个需求服务——2D/3D 无感切换。
> 我的辩护有三点：第一，双引擎不是炫技，洪涝页真的需要 3D 地形，这是需求驱动的；第二，抽象换来了业务层免疫引擎变化——manifest 里加一个模块、engine 字段改成 3d，业务代码零改动；第三，ROI 的完全兑现需要第三个引擎或第五个业务，我承认现在还没到那个点。
> 另外，这套抽象倒逼我修掉了一整条生命周期 bug 链——最早图层生命周期职责分散在三处（页面直调渲染器、Manager、可被清空的图层目录），导致引擎切换后图层永久丢失。我把它收敛成「BLM 注册表作为单一事实源」，这是抽象带来的真实收益。
**追问分支（doc3 与 doc4）**：doc4：`UnifiedMap.vue:519` `r.unmount?.()` 用 `as {unmount?}` 断言绕过类型系统——因为 `unmount` 只存在于 `CesiumViewerManager` 不在 Renderer 接口上，**抽象没覆盖生命周期，这里破了个洞**。doc3：pending visibility 队列（`MapRenderer.ts:79-93`）、`as unknown as` 桥接。
**防守/加分点**：**不要嘴硬说「绝对值得」**。ROI 分析把「净成本可能为负」讲成坦诚的架构师，打分反而高。
**故事弹药**：已解决链 1（a003+a013+a014+a022，双引擎业务图层生命周期治理）、链 12（a050–a053，卸载/切换清理职责收口）。

#### Q7. 地图实例生命周期如何管理？
**为什么问**：资源泄漏是 WebGIS 面试高频雷。
**逐字脚本**：
> 两条线。OL 渲染器跟随组件生命周期：创建时 new，组件卸载时销毁并 dispose 地图。Cesium 是全局单例 + 按需挂载：首次进 3D 创建 Viewer，离开页面只 unmount 不销毁（保留状态），30 秒空闲后自动销毁释放 WebGL 上下文；再进 3D 时检查单例是否被空闲销毁，失效就重建，复用就 mount 回新容器。Cesium 脚本本身 5.7MB，首屏后用 requestIdleCallback 空闲预热，首次进 3D 不再现场下载。
> 销毁路径有三层：组件 onUnmounted 解绑事件、取消 rAF、清 store 引用；渲染器 destroy 清理水面、监听、定时器；Viewer 空闲销毁兜底。这三层谁负责什么，我在代码里都写清楚了，也配了测试。
> 这里有个实战坑值得说：早期卸载 Cesium 时调了一个不存在的 unmount 方法，导致 destroy 永不执行、事件监听和水面全部泄漏——是测试逮出来的。
**追问分支**：「复用前检查 viewer 是否被 idle destroy」实战坑（`UnifiedMap.vue:166-172`）；「谁负责销毁？顺序是什么？」要能背出三层。
**防守/加分点（doc4 最加分一问）**：Cesium 单例 + 30s 空闲自动 destroy（`CesiumRenderer.ts:196-202`）；`camera.changed`(1048/1107)、viewport listener(1630/1526)、OL moveend/pointermove(750)、UnifiedMap click+ResizeObserver+rAF(487-536) **全部有对应解绑**——这是真做过功课的地方，主动讲。
**故事弹药**：已解决链 12（a050：不存在的 unmount 导致 destroy 永不执行）。
**取证位置**：`CesiumRenderer.ts:52-228`（Viewer 单例/30s idle）；`UnifiedMap.vue:166-172,469-516`。

#### Q8. Cesium 资源泄漏怎么防？
**为什么问**：3D 引擎的典型翻车点。

#### Q9. 为什么两个后端（Node + Python）？
**为什么问**：架构是否过度拆分。
**逐字脚本**：
> 职责不同：Express 承担 Web API——认证、选址评分、预测、查表服务，和前端是同一套 JS 生态；FastAPI 承担科学计算——连通性淹没演算依赖 scipy 的 ndimage 连通域标注和 rasterio 的栅格处理，这是 Python 生态的强项，Node 里没有等价物。演算服务独立容器部署，经 nginx 内网反代，不暴露公网。
> 两个服务共用同一份 251 档预计算表：查表优先，命中零演算；表缺失或越界档位才走 FastAPI 实时演算，带 64 档 LRU 缓存兜底。
> 代价我也清楚：两套部署、两套依赖管理，测试也要跑两份。这是为「scipy 不可替代」这个真实需求付的成本。
**追问分支**（doc3 Q9 需讲「为什么不全用 Python」）：
> 不全用 Python 的理由：前端与 Web API 是 JS 生态，Express 承载认证/选址/预测/查表与前端共用类型心智与构建链；Python 只承担 Node 没有等价物的 scipy/rasterio 科学计算。这是「按生态强项拆分」，不是为微服务而微服务。
**防守/加分点**：讲清边界 + 承认运维成本。doc4：可安慰地说「拆了一个 Python 计算服务」，**别说「微服务架构」**（不在容器编排、生产未启用，见第七章）。
**取证位置**：`backend/flood-service/`（`flood_engine.py`、`main.py`）；`vite.config.js`。

#### Q10. 为什么用 Pinia？哪些数据进全局状态？
**为什么问**：状态管理基本功与「什么不进 store」的边界意识。
**逐字脚本**：
> 核心原因是地图是跨路由单例——UnifiedMap 常驻，业务页面是它的兄弟节点，组件内 ref 无法共享。另外分析结果要跨页面恢复：从洪涝页跳到个人中心再返回，水位和结果要还原，这需要全局状态。
> 我给自己定了规约：只有「跨页面共享、多组件消费、需要统一重置」的数据进 store——地图引擎状态、图层目录、分析结果、收藏方案。UI 显隐、面板开关、剖面选择这些组件局部状态留在 ref 里。目前按业务域拆了 4 个 store（map/flood/forecast/siteSelection），不堆一个巨型 store。

#### Q12. 跨页面状态恢复怎么做的？

#### Q13. 多个业务同时修改地图状态怎么办？
**为什么问**：并发协调与单一事实源。
**逐字脚本**：

### GIS 专业（Q14–Q19）

#### Q14. 洪涝算法原理是什么？
**为什么问**：WebGIS 专业度压舱石，最可能被深挖的题。
**逐字脚本**：
> 这是海平面抬升模型，不是上游来水模型。思路：DEM 低于水位的高程区是候选淹没区，但只有与海域 8 连通的低洼区才会被淹——内陆洼地即使低于水位也不会淹。
> 实现：mask = (DEM ≤ 水位)，把 mask 和海域 NoData 区域合并做连通域标注（scipy ndimage.label，8 连通结构含对角），取与海域同一分量的像素，再与 mask 求交。结果是每个档位的淹没多边形，经 Douglas-Peucker 简化（UTM 系按米做容差，再转 4326，避免纬度畸变）、过滤小于 0.25 平方公里的碎片。
> 为什么不用 Priority Flood（richdem）？那个模型是「上游来水沿高程路径蔓延」，需要先填洼；而海平面抬升是全局水平面升高，连通域过滤就是标准解，不需要 richdem——而且它在 Windows 上编译也是坑。
> 两个工程细节：一是 DEM 降采样 4 倍（30m→120m）换演算速度，预计算表是全分辨率下的产物，online 实时演算才是 120m——精度和延迟的权衡我如实说；二是预计算了 251 档（0~25m、0.1m 步长），查表小于 10 毫秒，滑块拖动零卡顿。
**追问分支（doc4 A 组 Q6「淹没为什么不是简单 DEM<水位」）**：要讲连通性（内陆洼地不淹）+ 海面种子 + 8 邻域 label；**Python 侧做对了，但要说明 api 侧没做**（见 1.3 叙事断层）。
**防守/加分点**：`flood_engine.py:1-17` 注释就是现成答案（与 Priority Flood 区别）。doc4 Q22 加分：面积在 UTM 下算（`flood_engine.py:246` UTM 像元面积 0.0144km²，避开墨卡托畸变）；doc4 Q21 坐标系：DEM 用 UTM48N 算面积再转 4326 输出。

#### Q16. 251 档预计算表怎么生成的？miss 了怎么办？
**为什么问**：工程与算法的结合深度。
**逐字脚本**：
> precompute_levels.py 用多进程对 0~25 米、0.1 米步长的每个水位跑一遍连通性演算，生成 251 档的淹没多边形表，gzip 压缩后 2.88MB，Express 和 FastAPI 共用这份表。
> 请求流程是三级：先查预计算表（命中小于 10 毫秒）；miss 走 FastAPI 实时演算；演算结果进 64 档 LRU 缓存，滑块拖动时重复档位秒回。表加载是懒加载只读一次，进程内缓存。
> 为什么选查表而不是全实时？因为滑块是无极调节，实时演算约 1 秒，拖动会打爆服务；预计算把延迟从秒级压到毫秒级，这是「空间换时间」的经典取舍。
**防守/加分点**：doc4 工程数据——`flood_levels.json.gz` 2.88MB（解压 10.16MB），251 档 / 累计 548 features / 427093 顶点；`main.py:135-151` LRU 64 档；`precompute_levels.py` 251 档 ProcessPoolExecutor(8)。
**取证位置**：`tool.../precompute_levels.py`；`backend/flood-service/main.py:135-151`。

#### Q17. 前端空间计算（选址评分）怎么做的？
**为什么问**：空间索引与算法复杂度。
**逐字脚本**：
> 选址在后端 Express：对每个选中的设施类型，逐 POI 做 turf.buffer 生成缓冲区，同类型 union 合并，不同类型再 intersect 取交集，得到「同时覆盖所有选中设施类型」的区域；然后从 557 个小区里筛出落在该区域内的，用 rbush 空间索引做 bbox 粗筛加精确点面判定，避免全量遍历；最后评分——每类设施预构建 rbush 索引，只查半径内的候选点算最近距离，按距离线性衰减加权打分，取前 10。
> 实测：983 个 POI 全选，核心计算 2.4 秒，瓶颈是 turf.union 的 O(n²) 多边形合并——代码和文档里都标注了这个，数据翻倍前需要聚类或网格化分组优化。这是诚实的技术判断，不是美化过的「毫秒级」。
**追问分支（doc4 C 组「数据 ×10 怎么优化」）**：POI 5570 仍在 rbush 可控区（O(log n) 粗筛）；真瓶颈是 `siteAnalysisService.js:99` 的 turf.union 链最坏 O(n²)，**先改成分治两两合并或 dissolve**；前端 Cesium 侧从 Entity 换 PointPrimitiveCollection；再网上才谈矢量瓦片/PostGIS。**这么答比背「上矢量瓦片」高一个层级。**
**防守/加分点**：doc4/d3——rbush 真用（前端 `OLRenderer.ts:229` moveend；后端 `spatialIndex.js:6,31,37` bbox 粗筛+点面精筛）。
