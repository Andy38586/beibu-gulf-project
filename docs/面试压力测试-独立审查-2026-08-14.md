## 第一部分：项目真实性审查

### 1.1 业务闭环判定：**有真实闭环，但闭环浅、数据小、含合成成分**

| 环节 | 选址分析 | 预测分析 | 浸没分析 |
|---|---|---|---|
| 解决什么问题 | 港口配套选址评分 | 吞吐量趋势预测 | 海平面抬升淹没范围+设施损失 |
| 输入 | 6 类设施 POI + 557 小区 | 历史吞吐量 JSON | 水位滑块 0~25m |
| 数据来源 | 高德 POI 抓取（真） | cargo/container 真，berth/traffic 合成 | ASTER GDEM 30m 真 DEM（演算降采样至 120m） |
| 用户操作 | 勾选设施类型→评分→收藏 | 拖时间轴→看趋势+热力 | 拖水位→看淹没+影响评估 |
| 输出价值 | 评分雷达图+方案收藏 | 趋势图+地图热力 | 淹没多边形+受影响设施+损失 |

**真实性证据**：
- 选址：`backend/data/site-selection/*.json` 为真实 POI 数据（557 小区、983 POI 总量，实测记录见 `docs/性能实测-2026-08-13.md`）。
- 浸没：真 DEM 流水线（`tools/dem-pipeline/01~05`）+ scipy 8 连通演算（`flood_engine.py:76-102`），251 档预计算表真实存在（`flood_levels.json.gz` 2.88MB）。
- **但存在合成/示意成分（代码自述，面试前必须主动坦白）**：
  - `forecastEngine.js:3`：预测引擎"**当前为模拟实现**，架构预留接入 ARIMA/XGBoost"——即趋势外推公式，不是统计模型。
  - `forecastEngine.js:94,117-158`：地图热力散射点"**示意性合成数据**"（seededRandom 确定性生成，每港 40 点 × 3 港）。
  - `flood_engine.py:183`：损失模型 `loss = value × damageRate`，"value/damageRate 为合理假设的估算值"，代码注释自承"**可接受为'合理造假'**"。

**判定**：不是纯炫技 Demo，有完整"数据→计算→可视化→收藏"链路；但它是**单机演示级数据规模**（全仓数据 1.81MB raw / 217KB gzip），且预测与损失两个环节是"诚实标注的合成"，这是面试叙事上最需要防守的两处。

### 1.2 是否存在"为了展示技术而设计功能"：**是，有 3 处明显痕迹**

1. `manifest.ts:56-66` 预留模块 **"航线分析"**（`navDisabled: true`，组件为 null）——底部导航有一个点了没反应的占位按钮。面试官看到会问："这个没实现的导航为什么上线？"回答不好会显得项目是"攒功能"。
2. **性能基建与数据规模倒挂**（详见第三部分）：视口裁剪阈值 1000（`spatialIndex.ts:10`），而真实最大点图层仅 372 要素（bus_station）——**裁剪/空间索引代码在真实数据上从未触发**。面试官问"这个优化有没有实测过？"时，诚实答案是"没有在真实数据上触发过"。
3. `CesiumViewerManager` 30s 空闲销毁、`preloadCesium` 空闲预热、`perfReporter` 等工程资产，真实使用但部分无 UI 入口（如 `z105`：`setTerrainEnabled` 无调用方，死代码）。

### 1.3 架构是否服务业务

**能解释的设计（面试可讲）**：
- `core/business/shared` 三层 + `manifest.ts` 业务注册清单：新增模块只改清单一处（已验证 `router/index.ts:14` 由 manifest 生成路由）。
- `MapRenderer` 抽象 + `layerAdapters` 适配器 + `BusinessLayerManager`（BLM）：业务层不碰引擎 API，2D/3D 切换时 `reapplyAll` 重绘（`BusinessLayerManager.ts:211-267`）——**抽象有真实使用场景**（洪涝页 3D、其余 2D，`manifest.ts` 每模块声明 engine）。
- 能力接口收敛（`Water3DCapability/GeoTIFFCapability/HeatmapCapability`，`types/renderer.ts:98-124`）+ 类型守卫（`layerAdapters.ts:69-81`）：避免 2D 背负 3D 契约，这是面试中可以讲出设计权衡的点。
- 双后端（Express + FastAPI）：scipy 科学计算用 Python、Web API 用 Node，理由站得住。

**容易被问"为什么需要这个"的设计（防守位）**：
1. **`MapRenderer` 抽象类 vs `MapRenderer` 接口——同名双类型**（`core/map/renderers/MapRenderer.ts` 抽象类 + `types/renderer.ts` 接口）。面试官翻代码会直接困惑："这两个是什么关系？"你需要能立刻解释：类承载公共状态（`_layers`/`_eventBus`），接口是业务层依赖的契约。
2. **`createRenderer` 的 `as unknown as MapRenderer` 契约桥接**（`renderers/index.ts:93,104`）：子类**没有** `implements` 接口，靠运行时约定 + 类型断言。且 `types/renderer.ts:169` 声明 `addGeoJsonLayer` 返回 `void`，而 `CesiumRenderer.ts:494` 实现为 `async Promise<void>`——**接口与实现不一致被断言掩盖**。面试官追问"你的类型安全在哪个边界断了"时，答案就在这两行。
3. **BLM 双状态源**：`_registry`（App 级持久）+ `mapStore.layerCatalog`（引擎切换时清空重建，`UnifiedMap.vue:226`）。两套状态靠 `reapplyAll`/`removeAllFromRenderer`（`App.vue:155-165` flush:'sync' watch）手工同步——复杂，但注释和测试覆盖了主要坑。
4. **GCS 布局体系**：4 个业务页在用，不是摆设；但 8px 网格被多处违反且注释自认（`UnifiedMap.vue:576,600-604` "12px 非8的整数倍，保留"）——体系刚性 vs 现实妥协，面试官可能问"token 体系为什么守不住"。

## 第二部分：架构面试压力测试（模拟追问）

### 模块设计

**Q1：为什么这样划分 core/business/shared？**
答：core=与业务无关的地图/布局能力；business=业务模块（Page+composables+constants）；shared=跨业务复用。依赖单向（core 禁引 business，已由 dependency-cruiser 守护，`package.json:20` cruise 脚本 + `.dependency-cruiser.cjs`）。
**防守点**：`shared` 与 `core` 的边界模糊（如 `shared/utils/spatialIndex.ts` 是地图能力却放 shared）。准备好解释"core 放有状态的地图能力，shared 放无状态工具/组件"。

**Q2：新增一个业务模块，需要修改哪些地方？**
答：`business/<name>/` 建目录 + `manifest.ts` 追加一条（路径/引擎/导航一处声明）。路由由 `buildBusinessRoutes()` 生成。若需要新图层类型，在 `layerAdapters.ts` 加 adapter。**核心层零改动**。这是该架构最漂亮的卖点，答案要背熟。

**Q3：业务越来越多，如何避免 business 文件夹膨胀？**
答：项目规约"单模块内只放 Page+composables+constants，禁止跨文件新抽象"；能力复用走 shared。**防守点**：当前三个模块结构并不一致（`b045` 已记录：flood 有 constants/ 无 composables，forecast 两者都有，site-selection 无 constants）——面试官会说"你说的规约自己都没遵守"。诚实回答：这是已知技术债（b045），正在统一模板。

**Q4：两个业务需要共享能力，应该怎么处理？**
答：抽到 shared/ 或 core/，禁止 business→business 互引（已 grep 验证零违规）。**实例**：`useLatestRequest`（竞态守卫）从三个页面手写逻辑收敛为共享 composable（`useLatestRequest.ts:1-36`）——这是可以讲的真实案例。

### 地图架构

**Q1：为什么不直接使用 OpenLayers API？**
答：双引擎（OL 2D + Cesium 3D）需要统一契约；业务层只依赖 `MapRenderer` 接口 + `layerAdapters`。**加分点**：能讲出"能力接口"设计（3D 水面/GeoTIFF 是 Cesium 专属，不塞进基类）。

**Q2：Renderer 抽象解决什么问题？**
答：引擎切换（`exportState/importState` 相机状态传递）、图层生命周期统一、业务不感知引擎差异。**扣分点**：如果面试官深挖"抽象泄漏"，要承认：`LayerOptions.style: unknown`（`types/renderer.ts:74`）、`getMap()/getViewer()` 返回 `unknown`（`MapRenderer.ts:48-56`）——业务层拿到底层对象时类型全丢。这是"抽象必然泄漏"的诚实回答，比硬撑强。

**Q3：如果未来不用 OpenLayers 换 Cesium（或反之），需要修改多少代码？**
答：换引擎只改 `renderers/` 下对应子类 + 相关 adapter；业务层零改动。**但面试官会追问**："那 CesiumRenderer 本身 1653 行、OLRenderer 813 行，你确定'只改一个文件'吗？"——诚实答：新增一个渲染器子类的成本约等于重写 1600+ 行 + 配套测试，抽象降低的是**业务层**的耦合成本，不是**引擎适配本身**的成本。

**Q4：你的抽象是否真的减少成本，还是增加复杂度？**
**这是本报告判断的最危险问题之一**。诚实答案：对当前 3 个业务、2 个引擎，抽象净成本可能为负——双状态源（registry/catalog）、能力守卫、pending visibility 队列（`MapRenderer.ts:79-93`）、`as unknown as` 桥接，这些复杂度只为支撑"2D/3D 切换"一个需求。**准备的说辞**：① 洪涝页 3D、其余 2D 是真实需求（manifest engine 字段）；② 若未来接 MapLibre 或 Cesium 版本升级，业务层免疫；③ 承认 ROI 需要"第三个引擎或第五个业务"才能完全兑现。**不要嘴硬说"绝对值得"**。

**Q5：地图实例生命周期如何管理？**
答：OL 渲染器随组件创建/销毁；Cesium Viewer 全局单例（`CesiumViewerManager`，`CesiumRenderer.ts:52-228`）+ 30s 空闲自动销毁 + 按需 mount/unmount + `preloadCesium` 空闲预热（`renderers/index.ts:18-45`）。`UnifiedMap.vue` 卸载时解绑事件、取消 rAF、清 store 引用（`UnifiedMap.vue:469-516`）。**加分点**：能讲出"复用前检查 viewer 是否被 idle destroy"（`UnifiedMap.vue:166-172`）这种实战坑。**防守点**：销毁路径有三层（组件 onUnmounted / 渲染器 destroy / viewer 空闲销毁），面试官问"谁负责销毁？顺序是什么？"要能背出来。

### 状态管理

**Q1：为什么使用 Store？**
答：地图是跨路由单例（`UnifiedMap` 常驻 + `RouterView` 业务页是兄弟节点，`App.vue:48-51`），组件内 ref 无法跨页面共享；分析结果跨页面恢复（`floodStore.saveState/consumeState`）。

**Q2：哪些数据应该进入全局状态？**
答：当前 4 个 domain store（map/flood/forecast/siteSelection）+ 分域原则；UI 显隐、剖面选择等留在组件本地 ref（`floodStore.ts:17` 注释明确此规约）。这是面试加分项——"什么不进 store"和"什么进 store"同样重要。

**Q3：为什么不用组件内部 ref？**
答：同上 + 登出时全局重置（`App.vue:59-77`）需要统一入口。

**Q4：如何避免 Store 无限膨胀？**
答：分域 + 规约。**防守点**：
- `useAuth.ts:46` 的 user/token 是**模块级单例变量，没进 store**（b040 已立案）——面试官会问"你的全局状态到底在 store 里还是模块顶层？"答案是"两者都有"，需要解释为什么（历史包袱，已列入技术债）。
- `createPersistedState` 是**内存级快照，刷新即失**（z104）——"跨页面持久化"说成"跨刷新持久化"会被当场拆穿。

**Q5：多个业务同时修改地图状态怎么办？**
答：业务层只改自己的 store + 通过 BLM 注册图层（store 存意图，渲染器是唯一写方）；引擎切换时 `App.vue` 的 sync watcher 先清旧渲染器再 `reapplyAll`（顺序敏感，注释已写明 `UnifiedMap.vue:186-189`）。**防守点**：`layerCatalog` key 无业务命名空间（a066）——两个业务若定义同名图层 key 会互相覆盖，面试官问"冲突怎么办"时承认这是已知风险。

**实测数据（`docs/性能实测-2026-08-13.md`，可复现）**：

| 指标 | 值 |
|---|---|

**面试必被问的四连**：
1. **"GeoJSON 多大？Feature 多少？"** → 全仓 1.81MB；最大业务图层 372 点。**必须主动说"小"**，不要含糊。
2. **"Canvas 还是 DOM？"** → OL/Cesium 均为 Canvas 渲染；前端只画分析结果，重计算在后端。
3. **"图层数量增加怎么办？"** → 渲染器按 layerId 注册/复用，增量更新（`updateGeoJsonLayer` 复用 source/dataSource 避免重建闪烁，`OLRenderer.ts:477-503`、`CesiumRenderer.ts:1171-1208`）；zIndex 分档（`OLRenderer.ts:109-116`）。
4. **"数据量增加 10 倍如何优化？"** → 准备三条路线：① 后端空间查询（当前 turf 全内存，无数据库）；② 矢量瓦片/后端切片；③ WebWorker 解析 + 前端分页渲染。**并诚实说明**：当前项目的裁剪/索引基建（rbush）在真实数据上从未触发（见下）。

**⚠️ 最重要的性能叙事风险——"性能优化是空中楼阁"**：
- `VIEWPORT_CULL_THRESHOLD = 1000`（`spatialIndex.ts:10`），真实最大点图层 372 → **视口裁剪、R-tree 查询、Cluster 聚合从未在真实数据上启动**。代码是为"可能的大数据"写的，但没有一个真实场景验证过它。
- `MAX_FEATURES = 500_000` 守卫（`layerAdapters.ts:26`）同理。
- 面试官问"你的裁剪方案实测过吗？10 万点多少 FPS？"——目前没有答案。**建议面试前做一个 10 万点合成数据压测**（用现有 `tools/perf-bench` 思路），把实测数字写进简历背书，这是把最大短板变加分项的唯一路径。

**其他性能观察**：
- 预测时间轴一轮播放发 **400+ 请求**（`app.js:62,72` 注释自认 ~432 请求/轮）——面试官会问"为什么不做一次拉全量再本地播放？"答：数据已本地缓存、接口只读、限流已豁免；但**这个设计本身是扣分点**，应承认批量接口更优。
- Cesium 首屏空闲下载 55MB（双份清单，`性能实测` 4.1 节）——有实测辩护（不阻塞 FCP，FCP 68ms），但"55MB"这个数字要自己先说，别等面试官算出来。
- 洪涝 online 演算降采样 4x（120m 分辨率）：面试官问"120m 对港口级分析够吗？"——诚实答：视觉演示够，工程决策不够；预计算表是 30m 全分辨率下生成的（`precompute_levels.py`），online 模式才是 120m。

## 第四部分：代码质量审查

### 4.1 AI 生成代码风险

| 检查项 | 结论 | 证据 |
|---|---|---|
| 重复代码 | ⚠️ 中等 | 双引擎固有重复（多边形校验/闭合逻辑 OL 与 Cesium 各写一份：`OLRenderer.ts:404-475` vs `CesiumRenderer.ts:1004-1068`）；`addGeoJsonLayer` 的 token 竞态保护在 add/update 各写一遍（`CesiumRenderer.ts:1104-1208`） |
| 无意义封装 | ⚠️ 少量 | `MapRenderer` 基类大量 `throw 未实现` 模板方法（`MapRenderer.ts:44-66`）；`useBusinessLayers` 的 no-op 桩（`useBusinessLayers.ts:38-51`）——有测试价值但业务价值存疑 |
| 函数过长 | ✅ 健康 | 业务函数普遍 <50 行；但**文件过长**是主问题：CesiumRenderer 1653 行、OLRenderer 813 行、UnifiedMap 629 行、GCSDebugOverlay 728 行 |
| 命名不一致 | ⚠️ 有 | `waterLevel`/`level` 参数名三套并存（b027）；`_layers`/`_cullLayers`/`_waterSurfaces` 三套"图层表"语义相近 |
| 看似高级无价值 | ⚠️ 少量 | `setTerrainEnabled` 无调用方（z105）；`perfReporter` 生产无消费者（只有 dev 面板） |
