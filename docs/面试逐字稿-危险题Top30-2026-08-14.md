## 模块与架构（Q1–Q9）

### Q1. 项目解决什么真实问题？
**为什么问**：怕"为炫技而做"。
**脚本**：
> 这是一个面向北部湾港（钦州）的智慧港口空间分析平台，解决三类真实问题：第一，港口配套选址——6 类设施（医院、学校、公园、公交站、商场）的覆盖范围叠加与距离加权评分，输出候选小区排名和雷达图；第二，吞吐量预测——4 项指标的趋势可视化，其中 cargo/container 是真实历史数据；第三，浸没分析——基于真实 ASTER 30 米 DEM 的连通性淹没演算，水位 0 到 25 米任意档位查表秒回，输出淹没范围、受影响设施和损失评估。数据方面：983 个真实 POI、557 个小区、3 个港口、83 个港口设施、真实 DEM 流水线。整个平台是"数据 → 后端空间计算 → 前端可视化 → 方案收藏"的完整闭环。
> 需要说明的是，项目定位是验证一套可扩展的 GIS 业务系统架构，数据规模是中小的——全仓约 1.8MB，我把真实规模主动说清楚。

**追问防守**：若被问"预测和损失是真实的吗"→ 按 Q13/Q15 脚本，主动坦白演示级模型。

### Q2. 数据量多大？浏览器扛得住吗？
**为什么问**：验证是否虚报"大规模"。
**脚本**：
> 全仓 21 个 JSON 数据文件，raw 1.81MB、gzip 217KB；最大业务点图层是公交站 372 个要素；最大 GeoJSON 是行政区划边界约 303KB。前端只渲染分析结果，重计算（选址评分、连通性演算）都在后端。这个规模对浏览器毫无压力，实测选址全选 6 类设施后端计算 2.4 秒，洪涝查表小于 10 毫秒。
> 所以我不说"支持大规模空间分析"——当前是千级要素规模。为大数据做的基建（视口裁剪、空间索引）有，但真实数据还没触发过，这一点我如实说明（Q27 详述）。

### Q3. 为什么用双引擎 OL + Cesium？
**为什么问**：架构决策是否拍脑袋。
**脚本**：
> 两个引擎解决不同的展示需求：2D（OpenLayers）适合选址、预测这类以图层叠加和平面分析为主的操作，交互轻、加载快；3D（Cesium）用于浸没分析，需要真实地形起伏来展示淹没范围——水面要贴地形、淹没多边形要沿地形裁剪，这是 2D 平面图表达不了的。所以我在业务注册清单里给每个模块声明 engine 字段：选址和预测是 2d，洪涝是 3d，路由切换自动带起引擎切换。
> 选择 OL 而不是 Leaflet，是因为 OL 的投影体系、矢量渲染和后续 3D 化的路径更成熟；Cesium 是 3D 地形的行业标准，两者组合是 WebGIS 的常见搭配。

### Q4. Renderer 抽象解决什么问题？
**为什么问**：抽象是否有真实价值。
**脚本**：
> 核心是让业务层不感知引擎差异。业务代码只面向 MapRenderer 契约操作：加图层、设显隐、flyTo、导出导入相机状态，不碰 OL 或 Cesium 的 API。引擎切换时，UnifiedMap 把当前渲染器的相机状态 exportState 出来，新引擎 importState 恢复，业务图层由 BusinessLayerManager 的 reapplyAll 统一重绘。实测 2D↔3D 切换约 55 毫秒。
> 还有一个细节：2D 和 3D 能力不是对等的——水面只有 Cesium 有、热力图只有 OL 有。我没有把这些塞进基类，而是收敛成三个能力接口（Water3D/GeoTIFF/Heatmap），调用方先做能力检查再调用，避免 2D 背负 3D 的契约。

【追问】"那这个抽象有没有泄漏？"：
> 有，我承认。LayerOptions 里样式回调是 unknown 类型；getMap/getViewer 返回 unknown，业务层要拿底层对象时类型会丢。另外创建渲染器时用了 `as unknown as MapRenderer` 的桥接——子类没有显式 implements 接口，这是运行时契约加类型断言的双轨，是我知道的技术债，统一接口签名是计划项。

### Q5. 换掉 OpenLayers 需要改多少代码？
**为什么问**：抽象价值的量化。
**脚本**：
> 业务层零改动。改动集中在渲染器目录：写一个新的 MapRenderer 子类（参照 OLRenderer 813 行的工作量）+ 在 layerAdapters 里补对应适配。因为业务层只依赖契约和 6 种图层类型（points/polygon/geojson/heatmap/geotiff/waterSurface）。
> 但我要诚实：新增一个引擎适配本身的成本不是零——CesiumRenderer 有 1653 行，重写一个 3D 适配器是上千行加配套测试的量级。抽象降低的是业务层的耦合成本，不是引擎适配本身的成本。这个区分面试里我会主动讲。

### Q6. 你的抽象是减少成本还是增加复杂度？
**为什么问**：这是"过度设计"与否的终极拷问。
**脚本**（核心防守题，先承认再辩护）：
> 诚实的答案是：对当前 3 个业务、2 个引擎的规模，抽象有净成本。支撑双引擎切换，我付出了：渲染器抽象基类、能力接口和类型守卫、业务图层管理器（BLM）的双状态源（注册表 + 图层目录）、pending visibility 队列、引擎切换时的手工状态同步。这些复杂度只为一个需求服务——2D/3D 无感切换。
> 我的辩护有三点：第一，双引擎不是炫技，洪涝页真的需要 3D 地形，这是需求驱动的；第二，抽象换来了业务层免疫引擎变化——manifest 里加一个模块、engine 字段改成 3d，业务代码零改动；第三，ROI 的完全兑现需要第三个引擎或第五个业务，我承认现在还没到那个点。
> 另外，这套抽象倒逼我修掉了一整条生命周期 bug 链——最早图层生命周期职责分散在三处（页面直调渲染器、Manager、可被清空的图层目录），导致引擎切换后图层永久丢失。我把它收敛成"BLM 注册表作为单一事实源"，这是抽象带来的真实收益。

**故事弹药**：已解决链 1（a003+a013+a014+a022，双引擎业务图层生命周期治理）、链 12（a050–a053，卸载/切换清理职责收口）。

### Q7. 地图实例生命周期如何管理？
**为什么问**：资源泄漏是 WebGIS 面试高频雷。
**脚本**：
> 两条线。OL 渲染器跟随组件生命周期：创建时 new，组件卸载时销毁并 dispose 地图。Cesium 是全局单例 + 按需挂载：首次进 3D 创建 Viewer，离开页面只 unmount 不销毁（保留状态），30 秒空闲后自动销毁释放 WebGL 上下文；再进 3D 时检查单例是否被空闲销毁，失效就重建，复用就 mount 回新容器。Cesium 脚本本身 5.7MB，首屏后用 requestIdleCallback 空闲预热，首次进 3D 不再现场下载。
> 销毁路径有三层：组件 onUnmounted 解绑事件、取消 rAF、清 store 引用；渲染器 destroy 清理水面、监听、定时器；Viewer 空闲销毁兜底。这三层谁负责什么，我在代码里都写清楚了，也配了测试。
> 这里有个实战坑值得说：早期卸载 Cesium 时调了一个不存在的 unmount 方法，导致 destroy 永不执行、事件监听和水面全部泄漏——是测试逮出来的。

**故事弹药**：已解决链 12（a050：不存在的 unmount 导致 destroy 永不执行）。

### Q8. Cesium 资源泄漏怎么防？
**为什么问**：3D 引擎的典型翻车点。
**脚本**：
> 四个方面：第一，事件监听配对注销——click、pointer-move、camera-changed 都用具名处理器保存引用，destroy 时逐一解绑；第二，相机变化监听和防抖定时器随图层条目保存，图层移除时一并 cancel；第三，30 秒空闲自动销毁 Viewer，释放 GPU 上下文和显存；第四，图层实例按类型清理——Entity 数组逐个 remove、dataSource 带 destroy 参数移除、影像图层显式释放。水面 Primitive 单独管理。
> 每类清理都有对应测试，比如空闲销毁后重建的用例。

### Q9. 为什么两个后端（Node + Python）？
**为什么问**：架构是否过度拆分。
**脚本**：
> 职责不同：Express 承担 Web API——认证、选址评分、预测、查表服务，和前端是同一套 JS 生态；FastAPI 承担科学计算——连通性淹没演算依赖 scipy 的 ndimage 连通域标注和 rasterio 的栅格处理，这是 Python 生态的强项，Node 里没有等价物。演算服务独立容器部署，经 nginx 内网反代，不暴露公网。
> 两个服务共用同一份 251 档预计算表：查表优先，命中零演算；表缺失或越界档位才走 FastAPI 实时演算，带 64 档 LRU 缓存兜底。
> 代价我也清楚：两套部署、两套依赖管理，测试也要跑两份。这是为"scipy 不可替代"这个真实需求付的成本。

## 状态管理（Q10–Q13）

### Q10. 为什么用 Pinia？哪些数据进全局状态？
**为什么问**：状态管理的基本功与"什么不进 store"的边界意识。
**脚本**：
> 核心原因是地图是跨路由单例——UnifiedMap 常驻，业务页面是它的兄弟节点，组件内 ref 无法共享。另外分析结果要跨页面恢复：从洪涝页跳到个人中心再返回，水位和结果要还原，这需要全局状态。
> 我给自己定了规约：只有"跨页面共享、多组件消费、需要统一重置"的数据进 store——地图引擎状态、图层目录、分析结果、收藏方案。UI 显隐、面板开关、剖面选择这些组件局部状态留在 ref 里。目前按业务域拆了 4 个 store（map/flood/forecast/siteSelection），不堆一个巨型 store。
> 坦白一个已知债：登录用户状态 user/token 还在模块顶层单例变量里，没进 store，这是历史遗留，已列入技术债台账。

**故事弹药**：已解决链 8（d019 直改 catalog 绕过 Pinia action、d017 shallowRef、d055 原地变异幽灵用户）。

### Q11. Store 怎么防膨胀？
**为什么问**：工程纪律。
**脚本**：
> 三层：一是按业务域拆分，一个业务一个 store，mapStore 只放地图相关；二是"不进去的就不进去"的规约——UI 状态不进 store；三是登出时统一 reset，所有 store 有 clearState/reset 入口，由 App 层一个函数批量调用。
> 反面教材也有：早期 forecastState 里 dataCache 写了没人读、类型是 unknown 宽松槽，后来收窄成具体类型并把请求缓存迁进 store——这种漂移就是膨胀的前兆。

### Q12. 跨页面状态恢复怎么做的？
**为什么问**：细节真实性。
**脚本**：
> floodStore 提供 saveState/consumeState：离开页面到个人中心时保存快照，返回时恢复水位、分析结果、受影响设施，并重新渲染图层。恢复时有个标志位防止 watch 触发重复的 API 请求。
> 要说明的是，这个快照是内存级的——页面刷新会丢，只有跨路由往返能恢复。我没把它做成 localStorage 持久化，这是已知债，面试前我不夸大成"刷新恢复"。

### Q13. 多个业务同时修改地图状态怎么办？
**为什么问**：并发协调与单一事实源。
**脚本**：
> 原则是"store 只存意图，渲染器是唯一写方"，中间层是 BusinessLayerManager（BLM）。业务注册图层到 BLM，BLM 维护注册表（App 级持久），再把元数据同步到 mapStore 的图层目录供面板展示。引擎切换时：先清空旧渲染器上的视觉实例（App 层 sync watcher，顺序敏感），再 reapplyAll 按注册表重绘到新引擎——注册表是唯一权威，目录被清空也不丢图层。
> 这里有个我踩过的深坑：早期 reapplyAll 依赖会被清空的图层目录找条目，引擎切换时目录一空，业务图层永久丢失。后来改成注册表为单一事实源，补了回归测试。这段历史也是"为什么要单一事实源"的最好注脚。

**故事弹药**：已解决链 1（catalog 清空 → 图层永久丢失）。

## GIS 专业（Q14–Q19）

### Q14. 洪涝算法原理是什么？
**为什么问**：WebGIS 专业度压舱石，最可能被深挖的题。
**脚本**：
> 这是海平面抬升模型，不是上游来水模型。思路：DEM 低于水位的高程区是候选淹没区，但只有与海域 8 连通的低洼区才会被淹——内陆洼地即使低于水位也不会淹。
> 实现：mask = (DEM ≤ 水位)，把 mask 和海域 NoData 区域合并做连通域标注（scipy ndimage.label，8 连通结构含对角），取与海域同一分量的像素，再与 mask 求交。结果是每个档位的淹没多边形，经 Douglas-Peucker 简化（UTM 系按米做容差，再转 4326，避免纬度畸变）、过滤小于 0.25 平方公里的碎片。
> 为什么不用 Priority Flood（richdem）？那个模型是"上游来水沿高程路径蔓延"，需要先填洼；而海平面抬升是全局水平面升高，连通域过滤就是标准解，不需要 richdem——而且它在 Windows 上编译也是坑。
> 两个工程细节：一是 DEM 降采样 4 倍（30m→120m）换演算速度，预计算表是全分辨率下的产物，online 实时演算才是 120m——精度和延迟的权衡我如实说；二是预计算了 251 档（0~25m、0.1m 步长），查表小于 10 毫秒，滑块拖动零卡顿。

**故事弹药**：已解决链 6（b019 mock 忽略水位参数、b020 向上取档不透明）。

### Q15. DEM 哪来的？分辨率多少？
**为什么问**：数据真实性。
**脚本**：
> ASTER GDEM 30 米真实栅格，覆盖钦北防范围。流水线：01 镶嵌 → 02 填洼（sink fill，防止洼地被误判为可淹没）→ 03 重投影到 UTM48N 并裁切 → 04 生成洪涝数据 → 05 修正设施高程。填洼版 30 米 DEM 约 169MB。
> 3D 展示用的地形瓦片是自己切的：CTB 工具从 DEM 生成 z0–z12 共 3847 个 heightmap 瓦片，走 CesiumTerrainProvider 按需 LOD 加载。有个细节：这些 .terrain 文件是 gzip 压缩流，服务器必须声明 Content-Encoding: gzip，否则 Cesium 解压直接报错——部署时踩过。
> 诚实说明：online 实时演算为了速度降采样到 120 米，这个分辨率做视觉演示没问题，做工程决策精度不够，所以我默认走全分辨率预计算表。

### Q16. 251 档预计算表怎么生成的？miss 了怎么办？
**为什么问**：工程与算法的结合深度。
**脚本**：
> precompute_levels.py 用多进程对 0~25 米、0.1 米步长的每个水位跑一遍连通性演算，生成 251 档的淹没多边形表，gzip 压缩后 2.88MB，Express 和 FastAPI 共用这份表。
> 请求流程是三级：先查预计算表（命中小于 10 毫秒）；miss 走 FastAPI 实时演算；演算结果进 64 档 LRU 缓存，滑块拖动时重复档位秒回。表加载是懒加载只读一次，进程内缓存。
> 为什么选查表而不是全实时？因为滑块是无极调节，实时演算约 1 秒，拖动会打爆服务；预计算把延迟从秒级压到毫秒级，这是"空间换时间"的经典取舍。

### Q17. 前端空间计算（选址评分）怎么做的？
**为什么问**：空间索引与算法复杂度。
**脚本**：
> 选址在后端 Express：对每个选中的设施类型，逐 POI 做 turf.buffer 生成缓冲区，同类型 union 合并，不同类型再 intersect 取交集，得到"同时覆盖所有选中设施类型"的区域；然后从 557 个小区里筛出落在该区域内的，用 rbush 空间索引做 bbox 粗筛加精确点面判定，避免全量遍历；最后评分——每类设施预构建 rbush 索引，只查半径内的候选点算最近距离，按距离线性衰减加权打分，取前 10。
> 实测：983 个 POI 全选，核心计算 2.4 秒，瓶颈是 turf.union 的 O(n²) 多边形合并——代码和文档里都标注了这个，数据翻倍前需要聚类或网格化分组优化。这是诚实的技术判断，不是美化过的"毫秒级"。

**故事弹药**：已解决链 5（d057 双策略统一）、链 7（d047 rbush 接入评分）、链 17（d076 判空死代码、d079 极点 bbox 爆炸）。

### Q18. 预测模型是什么？准确性怎么验证？
**为什么问**：⚠️ 危险题——模型是"模拟实现"，必须主动坦白。
**脚本**：
> 我先把话说清楚：预测模块是**趋势外推的演示级模型，不是统计模型**。公式是历史 5 年增长率的年化均值 × 情景系数（0.8~1.2）做复利外推，再乘一个按月均值比例的季节性因子；可信度随预测年限线性衰减。代码注释里明确写了"当前为模拟实现，架构预留接入 ARIMA/XGBoost"。
> 真实的部分：cargo/container 两项指标的历史数据是真的；berth/traffic 两项以及地图热力散射点是明确标注的合成示意数据（确定性种子生成，可缓存）。
> 所以我简历和介绍里不会把"预测"说成"AI 预测"或"准确预测"，它演示的是趋势可视化和交互链路，模型本身是占位。如果面试官问"为什么不用真实模型"——答案是个人项目的时间预算，这是诚实的工程取舍。

### Q19. 热力图数据是真的吗？
**为什么问**：数据诚信。
**脚本**：

## 性能（Q20–Q24）

### Q20. 有测试吗？覆盖率多少？
**为什么问**：工程素养。⚠️ 数字面试前必须本机重跑替换。
**脚本**：
> 有，前后端共 35 个测试文件（README 记录 416 个用例），覆盖 store、渲染器、adapter、组件和算法服务，CI 里强制跑。我举两个有代表性的：OLRenderer 的视口裁剪测试（阈值路由、moveend 增量、监听生命周期），和选址评分测试（rbush 判空防御复活、极端纬度 bbox 不退化）——这两个都是先有 bug 后有测试的回归。
> 覆盖率目前 30% 上下，阈值设得低（25/20/15/25），我承认这是短板：现在覆盖率定位是回归基线，目标是 60%，这个数字我敢报是因为我知道差在哪——渲染器 mock 和部分页面组件覆盖不足。
> 没有 E2E，核心流程回归靠单测加人工，Playwright 是计划项。

**故事弹药**：已解决链 2（a016 补测逮出 import Map 遮蔽 bug）、链 17（d076+d079）。

### Q21. 构建和加载性能怎么优化的？
**为什么问**：性能意识。
**脚本**：
> 四条线：一是分包——manualChunks 把 vue/ol/cesium/echarts/ui 拆成独立 chunk，Element Plus 按需引入，首屏 gzip 从 720KB 压到 480KB；二是 Cesium 懒加载——5.7MB 脚本不随首屏，requestIdleCallback 空闲预热，首屏 FCP 实测 68 毫秒；三是静态资源缓存——nginx 一年 immutable + brotli 压缩；四是天地图预连接——preconnect 三个瓦片子域，还做了同源代理消除跨域 preflight。
> 渲染层也有：GeoJSON 图层增量更新复用 source/dataSource，避免重建闪烁；大数量点图层有 rbush 视口裁剪。
> 这套优化的每项都有实测背书，记录在性能实测文档里。

**故事弹药**：已解决链 7（c001 首屏 720→480KB、d030 nginx 缓存、d031 preconnect、z022 同源代理）。

### Q22. 视口裁剪实测过吗？10 万点能扛吗？
**为什么问**：⚠️ 本项目最危险的一题——裁剪从未被真实数据触发。
**脚本**（当前诚实版，做完压测后替换）：
> 我先把现状说清楚：裁剪阈值是 1000 个要素，真实数据最大的点图层是公交站 372 个，所以裁剪在真实数据上还没触发过——这套基建是为数据增长预留的，我承认它目前是"未被验证的优化"。
> 设计是这样的：超过阈值时构建 rbush 空间索引（投影坐标），moveend 时只查询视口 extent 内的要素增量更新 source；Cesium 侧相机移动时按视口 bbox 查索引，增量增删 Entity。单次索引查询是毫秒级。
> 10 万点实测我还没做——这是我面试前要补的作业：用合成数据压测，把"开启裁剪 vs 全量渲染"的 FPS 和内存对比数字跑出来。目前我能保证的是设计正确性，不能保证实测数字。
> （压测完成后替换为：10 万点下裁剪开启 FPS 从 X 提到 Y、内存降 Z%，单次索引查询 2ms——有实测背书。）

### Q23. 数据量增加 10 倍怎么优化？
**为什么问**：扩展性思维。
**脚本**：
> 三条路线，按成本排序：第一，后端空间化——现在选址计算是全内存 turf，数据 10 倍后应该把空间查询下沉到 PostGIS/空间数据库，前端只收结果；第二，数据切片——GeoJSON 转矢量瓦片（当前 boundary 303KB 是全量加载未切片），按视口拉取；第三，前端渲染层——10 万点以上用 WebGL 批量渲染（Cesium 的 Primitive/3D Tiles 或 OL 的 WebGL 点图层），加上 WebWorker 解析数据避免主线程卡顿。
> 我的判断：当前规模（千级）不需要这些，架构里已经预留了裁剪和索引的接缝，真到那一步改造面是可控的——渲染器抽象保证换渲染方案不动业务层。

### Q24. 预测时间轴一轮播放要发多少请求？
**为什么问**：⚠️ 高频请求的设计缺陷，面试官算得出来。
**脚本**：
> 这是我承认的设计缺陷。时间轴播放按时间点逐个请求，一轮约 400+ 请求。现状的缓解是：接口只读、有专属宽松限流、前端有结果缓存。但正确做法是一次批量接口拉全量、前端本地播放，或者前端插值——这是已知债，列入待办。
> 这个缺陷也说明我的限流设计是认真做的：全局限流 1000 次/15 分钟、登录 50 次、注册 50 次，forecast 单独豁免并配专属 limiter——因为如果我没有意识到 400+ 请求的问题，就不会单独给它开口子。

## 工程化（Q25–Q30）

### Q25. 错误处理体系怎么设计的？
**为什么问**：健壮性。
**脚本**：
> 三层。前端：全局 errorHandler（app.config.errorHandler + window.onerror + unhandledrejection 兜底）保证不白屏；请求层 useApiRequest 统一抛 ApiError、统一文案映射，页面不再手写 switch；组件层 ErrorBoundary 兜渲染错误，生产不暴露技术细节。后端：BusinessError 业务错误类带 code + status，全局错误中间件统一返回，生产不泄露堆栈。
> 竞态也统一处理：useLatestRequest 收口了三个页面手写的 AbortController 逻辑，新请求优先、过期响应丢弃、卸载取消。
> 已知缺口：生产环境没有错误上报 SDK（Sentry 未接入），日志只落控制台和文件——这是计划项。

**故事弹药**：已解决链 9（z028 白屏无痕、z030 口径分裂、z024 超时泄漏）。

### Q26. 日志体系怎么做的？生产开吗？
**为什么问**：安全与可观测。
**脚本**：
> logger 是结构化日志：{level, module, action, message, timestamp}，debug/info 用 import.meta.env.DEV 编译期门控，生产不输出；warn/error 生产保留但脱敏。后端请求日志做了 sanitize 脱敏（密码字段打码），认证关键操作有 audit 审计日志（记 userId + IP）。生产还加了 1% 采样日志和贯穿请求链的 requestId，故障时能把同一请求的日志串起来。
> 声明一下：main.ts 里有一行注释说"logger 已预留 addLogTransport 钩子，Sentry 就绪后一行接入"——这个钩子实际被删掉了，注释与代码不符，是文档债，我面试前会修掉，现在如实说明。

### Q27. 密钥和 .env 怎么管理的？
**为什么问**：安全红线。
**脚本**：
> 三条防线。一是 CI 硬检查：gitleaks 扫工作树、.env 类文件禁止入库（允许 .env.example），这条在 CI 里是硬性阻断。二是构建注入：天地图 key 走 GitHub Secrets 在构建期注入，本地开发用 .env 占位符。三是 Docker 镜像隔离：.dockerignore 排除 .env*，JWT_SECRET 通过 compose env_file 运行时注入，不进镜像层。
> 这段历史有教训：早期真实天地图 key 和 JWT_SECRET 都进过 git 历史，后来用 filter-repo 清理并写了清理脚本。令牌本身是 HttpOnly Cookie + tokenVersion 吊销——登出后旧令牌立即失效。

**故事弹药**：已解决链 4（d020 令牌无吊销、d038 响应体回传 JWT、d048+d049 密钥进镜像、d044 git 历史残留）。

### Q28. 有没有 E2E？API 契约怎么保证？
**为什么问**：工程完整性。❌ 只能承认，但要有补救计划。
**脚本**：
> 没有 E2E，这是当前最大工程短板之一。现状是：前端 35 个测试文件覆盖单元层，后端接口有 controller 测试，但"登录→选址→洪涝→预测"的跨模块链路没有自动化回归，靠人工。
> 补救计划：Playwright 覆盖核心链路，CI 加 job。
> API 契约：前端用 zod 在 HTTP 边界 100% 校验响应，但前后端之间没有 OpenAPI 单一事实源，字段对齐靠人工——有个反面案例：waterLevel 参数名在 adapter 里三套并存（waterLevel/level），后来统一了 online 分支，但"契约靠人"的风险还在。计划是 zod-to-openapi 生成契约。

### Q29. 项目最大的技术债是什么？
**为什么问**：自我认知——主动列清单是加分项。
**脚本**：
> 按严重度排：一是 CesiumRenderer 1653 行 + 模块级函数全是 any 类型，改 3D 任何一处都要通读千行，这是维护性最大的雷；二是无 API 契约、无 E2E、覆盖率阈值 25% 形同虚设；三是性能基建未被真实数据验证（Q22）；四是预测/损失模型是演示级，需要定性升级；五是引擎切换的相机 pitch 硬编码等小债。我维护了一个问题台账，13 项 open、315 项已闭环，每项带编号、发现日期、解决记录——这个台账本身就是项目的一部分。

### Q30. 这个项目你最大的教训是什么？
**为什么问**：成长性与复盘能力。这是把"已解决问题台账"变成故事的最佳机会。
**脚本**：
> 三个教训。
> 第一个是"约定必须靠工具强制"：早期分层红线（core 不能引 business）靠口头约定，结果出现反向依赖；后来接 dependency-cruiser 硬性阻断，问题清零。状态管理也是——早期有人绕过 Pinia action 直接改 catalog 条目，后来全部收口。
> 第二个是"性能优化必须有数据基线"：我为大数量图层写了裁剪和索引，但真实数据只有几百个点，优化从未被触发——这让我明白，没有基线数据的优化是空中楼阁，我现在的实测文档就是补这一课。
> 第三个是一次 Git 仓库事故：8 个并行编辑导致 index 损坏、自动 gc 补刀、激进自修把仓库搞成 not a git repository，最后靠手写 packed-refs 和整树备份救回来。这件事让我彻底理解了 worktree 隔离、gc 配置和"遇 git 异常只报告不激进自修"的原则——我把复盘写成了文档，成了团队的 agent 红线。
> 如果只留一条：**先跑通正确性，再谈优化；所有优化都要有实测背书。**

**故事弹药**：已解决链 11（Git 事故完整复盘，细节丰富最适合讲故事）。
