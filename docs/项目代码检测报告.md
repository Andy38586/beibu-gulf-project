## 一、架构设计

**评分**: 6/10  
**核心问题**: 分层意图清晰，但边界已被突破

---

### 1.1 Core 层逆向依赖 Business 层

**严重等级**: 🔴 阻断级

**文件**: `src/core/map/UnifiedMap.vue:22`

```js
import { useAnalysisLayer } from '@/business/site-selection/composables/useAnalysisLayer'
```

**问题描述**:
架构设计上 `core/` 应独立于 `business/`（core 是框架，business 是业务），此处却反过来。UnifiedMap（核心地图组件）直接引入了选址分析（业务模块）的 composable。这意味着：

- 你不能单独复用 UnifiedMap 作为一个独立的地图组件——它强依赖 `business/site-selection` 存在
- 新增第三个业务模块时，UnifiedMap 需要再加一个 import
- core 层的单元测试需要 mock business 层，增加了测试复杂度
- 违反了"依赖倒置原则"：抽象不应依赖具体实现

**影响范围**:
- `src/core/map/UnifiedMap.vue` — 第 22 行 import，第 62 行 `createUpdateHandler` 调用
- 所有依赖 UnifiedMap 的页面和测试

**期望行为**: UnifiedMap 不应直接 import 任何 `@/business/` 下的模块。业务逻辑应通过事件系统、store 回调或依赖注入注册到 core 层。

**修复方向**: 
- 将 `useAnalysisLayer` 的集成逻辑移到 `stores/map.js` 或新增 `core/composables/useRendererIntegration.js`
- 通过 `provide/inject` 允许业务模块向 core 层注册分析结果回调
- UnifiedMap 只关心"有一个分析结果处理器"，不关心它来自哪个业务模块

### 1.2 渲染器抽象接口不完整

**严重等级**: 🔴 阻断级

**文件**: 
- `src/core/map/renderers/MapRenderer.js` — 抽象基类
- `src/core/map/renderers/CesiumRenderer.js` — 实现

**问题描述**:
`MapRenderer` 抽象基类定义了 `addPointLayer` / `addPolygonLayer` / `addGeoJsonLayer` 等核心方法。但 `CesiumRenderer` 额外实现了 **5 个不在基类接口中的方法**：

| 方法 | 所在行 (CesiumRenderer.js) | 用途 | OLRenderer 有无 |
|---|---|---|---|
| `addWaterSurface(id, coords, height, opts)` | 783 | 创建 3D 水面 Primitive | ❌ |
| `updateWaterLevel(id, newHeight)` | 847 | 更新水面高度 | ❌ |
| `removeWaterSurface(id)` | 864 | 移除水面 | ❌ |
| `setWaterSurfaceVisibility(id, visible)` | 887 | 设置水面可见性 | ❌ |
| `removeAllWaterSurfaces()` | 876 | 移除所有水面 | ❌ |

**后果**:
业务代码（`FloodAnalysisPage.vue`）只能通过类型嗅探来使用这些方法：

```js
// src/business/flood-analysis/FloodAnalysisPage.vue:85, 276, 398, 414
const renderer = mapStore.currentRenderer?.value
if (renderer && renderer.getType() === 'cesium') {
  renderer.addWaterSurface(WATER_SURFACE_ID, coordinates, height)
}
```

这导致：
- 每新增一个渲染引擎（Mapbox、Deck.gl），都需要判断它是否支持水面
- 编译期无法检查方法是否存在（全是 JS）
- 代码中 `getType() === 'cesium'` 出现 6 次

**期望行为**: `MapRenderer` 应声明所有渲染器可能用到的方法。对不支持的方法，默认实现为 `throw new Error('not supported')`。业务代码通过 `try/catch` 而非 `getType()` 嗅探来判断能力。

**修复方向**:
在 `MapRenderer.js` 中增加以下抽象或默认方法：

```
addWaterSurface(id, coords, height, opts) → throw 'not supported'
updateWaterLevel(id, newHeight) → throw 'not supported'
removeWaterSurface(id) → 空实现
setWaterSurfaceVisibility(id, visible) → 空实现
removeAllWaterSurfaces() → 空实现
addHeatmapLayer(id, geojson, opts) → throw 'not supported' (预测分析需要)
startBreathing(lng, lat) → 空实现 (当前只在OL上有)
stopBreathing() → 空实现
setBaseLayer(type) → throw 'not supported'
getViewer() → throw 'not supported' (Cesium 特有)
getMap() → throw 'not supported' (OL 特有，但已有)
```

`OLRenderer` 对 `addWaterSurface` 等 3D 方法给出空实现或 `throw`。
`CesiumRenderer` 正常实现。
业务代码改为：

```js
try {
  renderer.addWaterSurface(id, coords, height)
} catch (e) {
  // 当前引擎不支持水面，fallback 逻辑
}
```

### 1.3 业务层直接操控渲染器实例

**严重等级**: 🟡 严重级

**文件**: `src/business/flood-analysis/FloodAnalysisPage.vue`

**问题描述**:
业务页面通过 `mapStore.currentRenderer?.value` 直接获取渲染器实例，然后直接调用渲染器的内部方法。绕过了一切中间隔离层。

具体表现：
- `FloodAnalysisPage.vue:85` — `mapStore.currentRenderer?.value` 访问
- `FloodAnalysisPage.vue:276` — `renderer.removeLayer(FLOOD_LAYER_ID)` 直接调用
- `FloodAnalysisPage.vue:301` — `renderer.addGeoJsonLayer(...)` 直接调用
- `FloodAnalysisPage.vue:403` — `renderer.updateWaterLevel(...)` 直接调用
- `FloodAnalysisPage.vue:414` — `renderer.removeWaterSurface(...)` 直接调用

**影响**:
- 业务页面与渲染引擎实现细节耦合
- 如果要替换渲染引擎实现（例如从 Cesium 切换到 Deck.gl 做 3D），所有业务页面都要改
- `mapStore.currentRenderer` 的 `.value` 双重解引用暗示 store 结构可能有问题（ref 套 ref）

**期望行为**: 业务页面不应直接持有渲染器引用。应通过 `useMapControls` 或专门的 composable 暴露"意图级别"的方法（如 `addLayerToMap` / `removeLayerFromMap` / `animateWaterLevel`），内部由这些 composable 决定具体调用哪个渲染器。

**修复方向**:

```
当前:   FloodAnalysisPage → renderer.addGeoJsonLayer(...)
期望:   FloodAnalysisPage → useMapControls().addLayer('flood', geojson, style)
                            → useMapControls 内部调用 renderer.addGeoJsonLayer(...)
```

### 1.4 Layout 层依赖 Visualization 具体组件

**严重等级**: 🟡 严重级

**文件**: `src/core/layout/AppLayout.vue:30-32`

```js
import LineChart from '@/visualization/charts/LineChart.vue'
import BarChart from '@/visualization/charts/BarChart.vue'
import RadarChart from '@/visualization/charts/RadarChart.vue'
```

**问题描述**:
`AppLayout.vue` 是布局基座（Layout Base），属于 core 层。但它直接 import 了三个具体的图表组件。这意味着：

- 如果未来有新的可视化库（如 Chart.js、D3），不能在 AppLayout 中插拔
- 布局层和可视化层耦合
- AppLayout 中的 chartData、barData 是硬编码的示例数据，不应该出现在布局组件中

**影响**: 所有继承 AppLayout 的路由页面都会加载这三个图表组件（即使业务页面通过 slot 替换了它们）。

**期望行为**: 图表组件应通过 slot 的默认内容注入，而非在 AppLayout 中静态 import。或者 AppLayout 完全不关心默认内容是什么，由 HomePage 作为"根业务路由"来提供默认图表。

**修复方向**:
- AppLayout 移除所有图表 import，只提供 slot 架构
- HomePage.vue 作为"首页"具体实现，在 slot 中放入图表
- 其他业务路由（SiteSelectionPage、FloodAnalysisPage）通过 slot 替换

### 1.5 UnifiedMap 职责过重

**严重等级**: 🟡 严重级

**文件**: `src/core/map/UnifiedMap.vue` (550 行)

**问题描述**:
UnifiedMap 同时承担了以下职责：

1. **地图容器管理** — OL 和 Cesium 两个容器的 v-show 切换
2. **渲染器生命周期** — 初始化/复用/销毁
3. **数据加载** — `loadPorts()`、`loadBoundaryGeoJson()`
4. **图层注册** — `setupLayers()` 同时处理底图 + 业务图层 + 分析图层
5. **相机状态同步** — 2D/3D 切换时 export/import 相机状态
6. **事件处理** — click 事件转发到 store
7. **加载状态管理** — loading/error/boundaryWarning 三态
8. **引擎切换** — `switchMapType` 含回滚逻辑
9. **超时控制** — `withTimeout` 有自己的超时机制

这些职责分散在 550 行的单个组件中。未来新增功能（如新引擎、新图层类型、新事件）都会让这个文件继续膨胀。

**期望行为**: 按单一职责原则拆分为：
- `UnifiedMapContainer.vue` — 只管理容器和 v-show
- `useRendererLifecycle.js` — 渲染器初始化/切换/销毁
- `useCameraSync.js` — 2D/3D 相机状态同步
- `useMapDataLoader.js` — 港口/边界数据加载

## 二、代码质量

### 2.1 API 调用方式三种并存

**严重等级**: 🟡 严重级

项目存在三种 API 调用方式，无统一策略：

| 方式 | 使用位置 | 特点 |
|---|---|---|
| **裸 `fetch()`** | `FloodAnalysisPage.vue:203,241`，`HomePage.vue` | 无超时、无统一错误处理、无 base URL 封装 |
| **`useApiRequest.ts`** | `src/shared/composables/useApiRequest.ts` | 有泛型、AbortController、ErrorCode 枚举，但**零调用** |
| **自定义包装** | 部分 composable 自己封装 fetch | 不一致 |

**具体位置**:
- `src/business/flood-analysis/FloodAnalysisPage.vue:203`:
  ```js
  const [floodAreasRes, statisticsRes] = await Promise.all([
    fetch(`/api/gcs/flood-areas?waterLevel=${waterLevel}`),
    fetch(`/api/gcs/flood-statistics?waterLevel=${waterLevel}`),
  ])
  ```
  没有超时、没有错误处理、没有 base URL 统一管理。

**期望行为**:
- 废弃裸 `fetch`，全部统一使用 `useApiRequest.ts`
- `useApiRequest.ts` 需要增加拦截器机制（token 刷新、错误上报）

### 2.3 错误处理不统一

**严重等级**: 🟡 严重级

**问题描述**:

## 三、可扩展性

**评分**: 4/10  
**核心问题**: 加新引擎需要改 UnifiedMap + 类型嗅探，加新模块需要改 store

---

### 3.1 引擎切换模型不支持"同页面多引擎共存"

**严重等级**: 🔴 阻断级

**当前机制**:
`App.vue` 监听 `route.meta.engine`，全局切换 mapType（`'2d'` 或 `'3d'`）。整个页面一次只能有一个引擎。

**限制**:
- 不能在一个页面上同时显示 2D 地图和 3D 小窗（如预测分析需要）
- 不能在 2D 底图上叠加 3D 可视化浮窗
- 引擎切换是"全有或全无"

**期望**: 设计应支持"主引擎 + 子渲染器"模式，2D 地图上可以嵌入 Cesium 3D 浮窗。

---

### 3.2 新引擎接入需要改 3 个文件

**严重等级**: 🟡 严重级

要接入第三个引擎（如 Mapbox），需要修改：

1. `src/core/map/renderers/index.js` — 在工厂函数加 `case 'mapbox'`
2. `UnifiedMap.vue` — 可能需要在 setupLayers 中加条件判断
3. 如果新引擎不支持部分方法，所有业务代码中新增 `getType() === 'mapbox'` 嗅探

**设计文档承诺"添加 Mapbox 只需 4 步"**，但实际上因为 MapRenderer 接口不完整，第 2-3 步会涉及大量业务代码改动。

---

### 3.3 gcsStore 有成为"上帝 Store"的趋势

**严重等级**: 🟡 严重级

**文件**: `src/stores/gcsStore.js` (197 行)

gcsStore 目前已管理 4 个子模块的状态：

| 模块 | 状态组 | 变量数 |
|---|---|---|
| 水位模拟 | `waterLevel`, `waterLevelActive` | 2 |
| 剖面分析 | `selectedProfileId`, `profileActive` | 2 |
| 淹没分析 | `floodActive`, `showFloodArea`, `showFloodPOI`, `floodStatistics`, `floodFeatures`, `floodRiskLevel` | 6 |
| 港口影响 | `portImpactActive`, `affectedFacilities`, `totalLoss` | 3 |
| 全局 | `activeModule`, `hasActiveAnalysis` | 2 |

**总共 15 个响应式变量**。

如果再增加预测分析（Forecast），有两种选择：
- 继续往 gcsStore 里加 → 变成 20+ 变量，难以维护
- 新建 forecastState.js → 分散但一致性问题

**期望**: 建立 Store 拆分规范。每个业务模块有独立的 store，通过组合式 API 在页面层组合。

## 四、类型安全

**评分**: 3/10  
**核心问题**: `src/types/` 完备但零使用，类型定义与实现分离

---

### 4.1 类型定义未被任何实际代码引用

**严重等级**: 🔴 阻断级

**文件**: 
- `src/types/index.ts` — 导出入口
- `src/types/analysis.ts` — `AnalysisParams`, `AnalysisResult`, `AnalysisState`
- `src/types/api.ts` — `User`, `AuthResponse`, `ApiError`
- `src/types/facility.ts` — `FacilityType`, `FacilityPoint`, `TypeSetting`
- `src/types/map.ts` — `Port`, `LayerEntry`, `MapType`
- `src/types/plan.ts` — `Plan`
- `src/types/xiaoqu.ts` — `Xiaoqu`, `ScoredXiaoqu`

这些文件定义了完整的类型体系，包括：

```typescript
// src/types/analysis.ts
export interface AnalysisParams {
  selectedKeys: FacilityType[]
  typeSettings: Record<string, TypeSetting>
  weights?: Record<string, number>
}

export interface AnalysisResult {
  error: string | null
  coverage: Feature<Geometry> | null
  matchedXiaoqu: ScoredXiaoqu[]

```

**但**: 没有任何 `.js` 或 `.vue` 文件 `import` 这些类型。`tsconfig.json` 配置了但只报告 lib 错误，不检查应用代码（因为应用代码是 `.js`）。

**影响**:
- 无法在编译期捕获类型错误
- 修改数据结构（如 `AnalysisResult` 新增字段）时，IDE 不会提示哪些文件需要更新
- 新开发者无法通过类型定义理解数据流

**期望**: 逐步将核心文件迁移到 `<script setup lang="ts">` 或 `.ts`，先从 stores 和 composables 开始。

```typescript
  }

```

但 `grep -r "useApiRequest" src/` 返回 **零结果**（除了定义文件自身）。所有页面仍然在使用裸 `fetch`。

### 4.3 tsconfig 已配置但未生效

**文件**: `tsconfig.json`, `tsconfig.app.json`, `tsconfig.node.json`

**问题**:
三个 tsconfig 文件都已创建且配置正确（`module: "ESNext"`, `moduleResolution: "bundler"`, `"include"` 包含 `src/**/*.ts` 和 `src/**/*.vue`）。

### 4.4 JSDoc 注释与类型定义重复

**严重等级**: 🟢 警告级

核心文件（`map.js` store、renderers、UnifiedMap）使用大量 JSDoc 注释：

```js
/**
 * @param {'2d'|'3d'} type - 渲染器类型

```

但 `src/types/map.ts` 中已经定义了 `type MapType = '2d' | '3d'`。JSDoc 的 `@param {'2d'|'3d'}` 与 TS 类型定义重复，且不受编译器保护（写错 JSDoc Vite 不会报错）。

## 六、UI/UX 与布局一致性

**评分**: 7/10  
**核心问题**: GCS 布局系统设计优秀，但与设计文档存在偏差

---

### 6.1 面板尺寸与设计规范不一致

**严重等级**: 🟡 严重级

**设计规范** (`docs/GCS_V2_设计规范.md`)：
- GCS 分析页面面板应为 **4×2 Cell**（4 列宽，2 行高）
- 4 个面板垂直堆叠共占 **8 行**（4 × 2 = 8 行）

**实际实现** (`src/business/flood-analysis/FloodAnalysisPage.vue`)：
- 所有面板为 **4×4 Cell**（4 列宽，4 行高）
- 4 个面板垂直堆叠共占 **16 行**

**影响**:
- 布局验收检查（Inspection Mode）会标记为不合格
- 未来新增面板时屏幕空间不足
- 如果遵循规范，需要重新计算所有 offsetY 参数

**期望**: 对齐规范。明确决定要么规范（4×2）要么实现（4×4），并更新另一份文档。

---

### 6.2 间距是否完全遵循 2×GAP 规则

**严重等级**: 🟢 警告级

GCS V2 规范要求所有 Panel 间距为 `2×GAP = 20px`。

需要检查（未逐一验证）：
- `AppLayout.vue` 中 offsetY 计算是否准确产生 20px 间距
- 是否有组件使用 CSS margin 绕过布局引擎
- `GcsPanel.vue` 的 `panelPosition` 函数是否正确实现 PPS 公式

---

### 6.3 Panel 内部硬编码 px 值

**严重等级**: 🟢 警告级

规范要求所有像素值来自 `config.js`，禁止硬编码。

但代码中存在：
- `AppLayout.vue` 中的间距值（如 `gap: 10px`）
- 各面板组件中的 padding/margin 值
- `CELL_PIXEL` 以外的像素常数

**规范约束 C07**: "所有像素值必须来自 config.js，禁止硬编码"
