### 动机

选址分析涉及 6 个因子的加权叠加与空间计算（缓冲区、衰减函数、评分矩阵），前端 JS 计算 500+ POI 点 → 页面 freeze 2-3 秒。需要将计算逻辑搬到服务端，同时为多用户提供持久化存储（方案保存/加载）。

### 方案

Express 分层架构（Controller → Service → Repository → Data），JWT 用户认证，CRUD 接口。

## 阶段 2：地图解耦 + 策略模式

| | 提交 | 日期 | 说明 |
|---|---|---|---|
| **Before** | `16fff04` | 2026-05-20 | "备份,准备给 mapContainer 解耦" |
| **After（过渡）** | `6d745fc` | 2026-06-30 | "拆分 mapcontainer，状态通过 pinia store 管理" |
| **After（完成）** | `02c1919` | 2026-07-02 | "新增 renderers，业务图层与渲染器解耦" |

### 动机

MapContainer 承担了 6 类职责，违反单一职责原则：
1. 底图切换（BaseLayerSwitcher）
2. 业务图层管理（6 个因子图层）
3. 缓冲区绘制与交互
4. 覆盖区渲染与动画
5. 点击/悬停交互
6. 结果面板联动

同时，未来需要支持 Cesium 3D 引擎，MapContainer 必须拆分为可替换的渲染器。

### 方案

1. **MapContainer → OlMap（纯 2D 渲染）+ 独立 composables**
2. **Pinia store（map.js）托管地图状态，组件只负责渲染**
3. **Strategy Pattern：MapRenderer（抽象基类）→ OLRenderer / CesiumRenderer**
4. **业务图层与渲染器解耦：图层只需提供数据和渲染方式（type + props），由 renderer 执行**

## 阶段 3：GCS 布局系统（Cell + Panel）

| | 提交 | 日期 | 说明 |
|---|---|---|---|
| **Before** | `8e44a90` | 2026-07-14 | "全屏布局 + ScreenLayout 路由" |
| **After** | `9edeead` | 2026-07-18 | "完整 GCS 面板设计系统" |

中间经历 12 个 GCS 阶段提交（32d8c99 → ff09e47 → ... → 9edeead）。

### 动机

阶段 2 后的架构中，地图在路由组件内初始化，导致：
1. 路由切换 → 地图重建 → 白屏闪烁
2. 多个业务入口散落在各页面，难以统一管理
3. 响应式布局依赖手写 CSS，不同设备表现不一致

GCS V2 提出 Cell 概念：屏幕被划分为 4×4 / 6×6 / 8×8 的不可见网格，每个 Panel 占据整数个 Cell，像 iPad 图标一样排列。

### 方案

1. **地图移至 App.vue 根级**：UnifiedMap 常驻，路由切换不销毁
2. **CELL_PIXEL 查找表**：根据屏幕宽度确定 Cell 大小，所有 Panel 以此为基准
3. **AppLayout + Panel 系统**：BottomNavBar（底部导航）+ GcsPanel（悬浮面板）+ NavButton
4. **目录模块化**：`src/core/`（核心逻辑）、`src/business/`（业务）、`src/shared/`（共享）、`src/visualization/`（可视化）

## 阶段 4：性能优化（路由绑定引擎）

| | 提交 | 日期 | 说明 |
|---|---|---|---|
| **引入** | `9edeead` | 2026-07-18 | meta.engine 随 GCS V2 引入 |
| **稳定** | `b37083c` | 2026-07-18 | "GCS 体系完成对旧页面的适配" |

### 动机

阶段 3 前，2D/3D 切换依赖用户手动点击 MapSwitcher，导致：
- **首屏加载 12s**：必须同时加载 OL（~2MB）和 Cesium（~8MB）
- **引擎与业务解耦不彻底**：业务组件可随意修改 mapStore.mapType
- **无法进行路由级代码分割**：Cesium 代码在首次访问就被打包

### 方案

1. **`route.meta.engine` 声明式绑定**：路由定义时声明使用 '2d'（OL）或 '3d'（Cesium）
2. **App.vue watch → mapStore.setMapType()**：禁止业务组件手动切换
3. **动态导入**：`() => import('@/business/gcs-analysis/GCSAnalysisPage.vue')` 配合 `meta.engine: '3d'`
4. **代码分割**：不再需要 import 'cesium' 到主包，仅在访问 3D 路由时加载

### 架构变化

```
Before:
  用户首次访问首页 → 加载主包（含 OL + Cesium）
                  → 树摇不充分（Cesium 未拆出）
                  → 点 MapSwitcher 切换 3D

After:
  用户首次访问 / → 加载主包（仅 OL）
               → 路由守卫检查 meta.engine

  用户点击"三维港口分析" → 动态加载 GCSAnalysisPage.vue
                        → meta.engine: '3d'

                        → 3D 引擎代码按需加载
```

## 阶段 5：TypeScript + 文档 + 规范

| | 提交 | 日期 | 说明 |
|---|---|---|---|
| **初始** | `88b5ba9` | 2026-07-01 | "新增 ElementPlus, TypeScript" |
| **过渡** | `133c144` | 2026-07-19 | composables 迁移 .ts，新增类型定义 |
| **当前** | `430e5fc` | 2026-07-20 | "新增浸没分析 + 预测分析，AI 日志" |

### 动机

项目从原型阶段进入长期维护阶段，面临的问题：
1. **JS 无类型**：重构时大量 `Uncaught TypeError: xxx is undefined`（如 Cesium 渲染器参数类型不匹配）
2. **知识流失**：每 3-5 天只有一个 commit，间隔期间上下文完全丢失
3. **AI 交互低效**：每次遍历全部源文件 → token 消耗大 → 回答不准
4. **缺乏组件复用目录**：开发者不知道 ErrorBoundary / LoginPanel 已存在 → 重复造轮子

### 方案

1. **渐进式 TS 迁移**：先类型定义 → composables 迁移 → 组件迁移
2. **设计文档先行**：`GCS_V2_设计规范.md` → `GCS三维港口分析实施文档.md` → AI 分阶段实施
3. **AI 日志系统**：`docs/日志/项目开发日志.md`，记录每次修改的 context 与决策
4. **组件复用目录**：`src/shared/` 集中管理可复用组件
5. **测试基础设施**：`src/core/map/__tests__/` + `src/core/map/renderers/__tests__/`
