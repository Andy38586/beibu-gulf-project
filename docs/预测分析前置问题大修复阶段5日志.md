## 二、排查过程（按提交记录叙述）

### 2.1 第一轮：怀疑异步竞态

**提交** `2809686`

针对 Bug 2，怀疑是 S3-08 把 `registerGcsLayers` 改成 async ��，`await loadWaterAreaCoordinates()` 期间组件卸载导致竞态。

改动：
- `registerGcsLayers` 加 `unmounted` 守卫标志，`gcsLayersRegistered` 移到 await 之后
- `onUnmounted` 补 `clearTimeout(analysisTimer)` + `unmounted = true`
- CesiumRenderer/OLRenderer flyTo 加 `target.lng ?? target.lon` 兼容 ports.json 的 lon 字段

**结果**：Bug 2 依旧。lon/lng 兼容对两个 Bug 都无影响（Bug 1 的根因不在这里）。

---

### 2.2 第二轮：怀疑 Cesium 后台渲染争 GPU

**提交** `56da45e`

怀疑 Cesium Viewer 单例在隐藏后仍在跑 render loop，与 OL 渲染争 GPU 导致卡顿/冻结。

改动：
- `CesiumViewerManager.unmount()` 加 `useDefaultRenderLoop = false`（彻底停 render loop）
- `CesiumViewerManager.mount()` 两处加 `useDefaultRenderLoop = true`（恢复）

**结果**：Bug 2 不仅没修好，**反而恶化**了——OL 页面连挂载都不完成了。`useDefaultRenderLoop = false` 触发了 Cesium 内部的同步清理操作，阻塞了 Vue 的 `<transition mode="out-in">` 生命周期。

---

### 2.3 第三轮：怀疑 exportState 坐标偏移

**提交** `71e3417`

针对 Bug 1，怀疑切换引擎时 Cesium 导出给 OL 的相机状态中心点偏移。Cesium 的 `_getCameraState` 用 `pickEllipsoid`（屏幕中心射线打地面），这个交点受相机 tilt 影响。

改动：
- `_getCameraState` 从 `pickEllipsoid` 切换为 `positionCartographic`（相机正下方直投，不受 tilt 影响）
- 同时导出 `pitch`，供 `_setCameraState` 恢复用

**结果**：Bug 1 没修好。Bug 2 **严重恶化**——`positionCartographic` 在高空相机时返回的是相机物理位置而非用户注视点，OL 导入后定位到错误坐标，所有 OL 页面地图也异常了。`4550e37` 紧急回退。

---

### 2.4 第四轮：GLM 多模态诊断介入

用户用视频多模态分析后，GLM 给出了精准的竞态条件诊断：

**触发链**：
```
用户进入 /flood-analysis
  → UnifiedMap switchMapType('3d')
  → watch(waterLevel, {immediate:true}) → 500ms 后 triggerFloodAnalysis
  → await Promise.all([/gcs/flood-areas, /gcs/flood-statistics])
  → 用户在此期间切回 2D 页面
  → switchMapType('cesium→2d') 执行
  → API 响应回来，renderFloodAreas(features)
  → mapStore.currentRenderer 已切换为 OL（或 null）
  → renderFloodAreas 操作错误渲染器
```

**提交** `cc53b73`

改动：
1. `triggerFloodAnalysis` / `triggerImpactAssessment` 加 `shouldRenderForCurrentRoute()` 守卫——路由不再是 3D 时直接丢弃响应
2. `renderFloodAreas` / `renderAffectedFacilities` 改为渲染器就绪重试模式（100ms 间隔，最多 10s）
3. 移除 `registerGcsLayers` 中的重复 500ms 分析触发（waterLevel watch 已覆盖）

**结果**：GLM 的竞态诊断是正确的，`shouldRenderForCurrentRoute` 确实堵住了一条真实的竞态路径。但它不是 Bug 2 的根因——Bug 2 依旧存在。

---

### 2.5 第五轮：怀疑 GCS 单例 cellPixel 异常

**提交** `d055331` / `8091e9a` / `e727785`

用户反馈"切换到所有的 OL 页面，面板都加载不出来"，说明问题出在所有 OL 页面共享的基础设施上。S4-07 把 `useGCS` 改成了模块级单例，如果模块级 ref（`cellPixel` / `windowWidth`）在引擎切换后被污染，所有面板的 CSS 尺寸都会异常。

改动（三层防线）：
1. `useGCS()` 入口：`cellPixel <= 0` 或 `NaN` → 强制 `updateCellPixel()` + 硬兜底 80/1920
2. `panelPosition()`：C/W/H 逐一检查回退
3. `GcsPanel.vue`：`minWidth`/`minHeight` + parseFloat 兜底
4. DEV 下 `showPanels`/`showTopArea` 强制 true（诊断性）→ `e727785`

**结果**：`e727785` 的 `showPanels=true` 强制后，**Bug 2 依旧**。排除了 `windowWidth < 768` 导致 `v-show=false` 的假设。三层兜底虽然无害，但没有命中根因。

---

### 2.6 第六轮：发现 transition 阻塞

**提交** `0b1442a`

关键线索：用户日志显示 `switchMapType cesium→2d` 完成后，**OL 页面的组件从未挂载**——store 没安装、onMounted 没触发。说明 `<transition mode="out-in">` 卡在了"旧组件离开"阶段。

回退了 `56da45e` 的 `useDefaultRenderLoop = false`——它导致 Cesium 内部同步清理阻塞了 Vue transition 钩子。

**结果**：修好了页面挂载——OL 页面开始有 store 安装日志了。但 Panel 仍然不渲染。推断 `useDefaultRenderLoop` 只是加重了阻塞，根因在 transition 本身。

---

### 2.7 第七轮：最终修复（第三个 AI）

**提交** `b2e90cc`

| Bug | 根因 | 修复 | 行数 |
|------|------|------|:--:|
| Bug 1 视角倾斜 | `_setCameraState` 用了导出的 `state.pitch`（用户交互后的倾斜值），恢复后视角倾斜累积 | pitch 硬设 `-90`，不读导出值 | 1 行 |
| Bug 2 Panel 不渲染 | Cesium 的 DOM 操作（`viewer.container` 移动）干扰了 Vue `<transition mode="out-in">`，新组件 `<script setup>` 从未执行 | 移除 `mode="out-in"` | 1 属性 |
