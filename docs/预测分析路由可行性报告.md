## 一、结论先行

**可行，且架构地基是好的，但不能照着设计文档直接开工。**

- 架构层面：AppLayout 插槽继承、GcsPanel 定位、`route.meta.engine` 引擎切换、`useLayerManager` 图层注册、`provide('unifiedMap')` 渲染器注入——这些预测分析需要的基础设施**全部真实存在且可用**，设计文档的继承模式与现状吻合。
- 但有 **1 个 P0 前置阻断**、**2 处耦合重灾区**、**8 处设计文档与真实代码的偏差**，不处理就动手，做出来的会是一个"图表不更新、图层画不出、面板显示 `--`"的半成品。

**建议路线**：先修 P0（图表快照 bug，约 20 行改动）→ 扩展渲染器样式能力（约 1 天）→ 再按修正后的设计落地（设计文档本身完成度约 85%，剩余 15% 是与现实的偏差）。

## 四、耦合特别重的部分（按重量排序）

### 4.1 重灾区一：渲染器样式能力单一（核心层）

`OLRenderer` 的三个 add 方法全部是"一种图层一种固定样式"：点图层全层同圆点、面图层全层同样式、GeoJSON 图层硬编码 `_createPolygonStyle`。预测分析 5 个指标需要 4 种视觉形态（热力/渐变点/流线/分级填色），**现有抽象一个都表达不了**。这是整个预测模块最大的技术缺口，且动的是刚完成解耦的 MapRenderer 核心层——扩展时要守住"基类加方法、OL 实现、Cesium 给桩"的既有模式，不要再引入 `getType()` 嗅探（项目里刚清掉 6 处）。

### 4.2 重灾区二：图表组件的 props 响应链断裂（可视化资产层）

见 3.2-1。`useECharts` 的 watch 链是通的（`watch(watchSources, updateChart)`，浅监听，引用替换可触发），但 `useChartBase` 把 option 做成了死快照，等于在最后一环断掉。修复成本低，但它横在预测分析**每一个图表**的必经之路上。RadarChart 不受影响（`useRadarChart.renderRadar` 每次现取 props，RadarChart.vue:121-131 驱动正常）。

### 4.3 中等耦合：图层目录的生命周期归 UnifiedMap 管

`UnifiedMap.setupLayers()`（UnifiedMap.vue:222-263）在每次引擎切换时 `clearLayers()` 清空图层目录，只重建 base/boundary/ports 三个。业务图层（含未来的 forecast-layer）被清掉后**由业务页面自己负责重建**。预测路由是 2D，从 3D 的 `/heatmap` 切回来会触发这个清空——好在 ForecastPage 会重新 mount。另外 `mapStore.registerLayer`（map.js:174-192）对已存在的 key 是**追加** show/hide 闭包，设计文档的 `updateForecastLayer` 每次更新都调 `registerToggleable` 会导致闭包数组无限膨胀（每次 toggle 触发 N 个失效闭包）。**实现时必须在 onMounted 注册一次、onUnmounted 注销，不能每次数据更新都注册。**

### 4.4 轻度耦合（需要知道但不用改）

- **App.vue 路由 watcher 硬编码路由名**（App.vue:76-81）：只有 Home/SiteSelection 有相机复位。Forecast 进页面不会自动 zoom——这恰好是想要的行为（保持当前视角），不用改，但要知道加路由不用动 App.vue。
- **BottomNavBar 导航项硬编码**（BottomNavBar.vue:54-61）：加一个按钮要改配置数组，Dock 宽度 `navItems.length + 1` 自动适应。
- **经纬度字段双轨制**：`addPointLayer` 读 `item.lon`（OLRenderer.js:104），`flyTo`/`startBreathing` 用 `lng`，SiteSelectionPage:125-129 和 162-167 被迫做 `lon/lng` 互转。预测数据文件如果坐标字段命名不统一，会静默画不出点。建议 forecast 数据统一用 `lng/lat` 并在 layer composable 里显式映射。
- **状态store 已 7 个**：map/gcsStore/siteSelectionState/floodState/floodStore/waterLevelStore/portImpactStore/profileStore。forecastState 是第 8 个。不阻断，但 ProfilePage 以后要做"预测方案"时，方案模型又得扩一次字段（`plan.ts` 已被 flood 扩过一次）。

### 4.5 已经不耦合的部分（历史问题已修复，设计文档可放心依赖）

- ✅ UnifiedMap 不再 import business（P0-2 已修）
- ✅ MapRenderer 基类已含 7 个水面方法，OL 有桩，`getType()` 嗅探已清除（P0-1 已修）
- ✅ `provide('unifiedMap')` 在 App.vue:22 提供，设计文档的 `inject('unifiedMap')` 可用
- ✅ `route.meta.engine` 自动引擎切换链路完整

## 五、设计文档与真实代码的偏差清单（落地前必须校准）

| # | 设计文档写的 | 真实代码 | 处置 |
|---|---|---|---|
| 1 | `const { request } = useApiRequest()`；`request({url, params})` | 导出的是 `apiRequest(path, options)`，无 params 序列化 | 用 `apiRequest` + 手拼 query，或给客户端补 params |
| 2 | "客户端 API 路径不带 /api 前缀"，但 ForecastPage 示例却写 `url: '/api/forecast/timeseries'` | `API_BASE = VITE_API_BASE \|\| '/api'`（useApiRequest.ts:30），path 不应再带 /api | 统一不带 /api |
| 3 | `addGeoJsonLayer(key, geojson, {type:'heatmap', weight, radius, blur})` 和 style 函数 | OLRenderer 全部静默忽略，统一套固定面样式 | 先扩展渲染器（3.2-2） |
| 4 | `ForecastPanel.currentValue` 读 `forecastState.currentData`（dataCache） | 设计文档全文**没有任何代码往 dataCache 写数据**，面板会永远显示 `--` | `updateForecastLayer` 成功后写 `cacheData(time, response.data)` |
| 5 | `onMounted` 立即 `updateForecastLayer()` | UnifiedMap 在 App 级异步初始化，直接访问 `/forecast` 刷新页面时渲染器大概率未就绪，`getRenderer()` 返回 null → **静默不画图，无重试** | 复用 App.vue:31-38 的 `waitForRenderer` 轮询模式 |
| 6 | 每次更新时间/指标都 `registerToggleable(...)` | mapStore.registerLayer 对已有 key 追加闭包，无限累积 | 注册一次，更新只换数据 |
| 7 | 播放 500ms/帧，每帧发 API 请求 | useApiRequest 超时 10s、无取消；慢网络下请求堆积、**响应乱序覆盖**（旧响应后到，覆盖新图层） | dataCache 前置 + 请求序号/AbortController 丢弃过期响应 |
| 8 | 数据文件放 `public/data/forecast/`，后端 `readFile('../../public/data/forecast/...')` | 后端既有约定是 `server/data/`（flood 数据就在 server/data/flood）；README 的部署方案前后端分离部署，后端读前端 public 目录在生产上会断 | 改放 `server/data/forecast/` |

另有两个**决策缺口**（文档没提，实现者必须拍板）：

- **认证策略**：`/api/site-analysis`、`/api/facilities`、`/api/plans` 全部要登录；`/api/gcs` 完全裸奔（gcs.js 无 authenticate）。forecast 跟哪一派？建议跟随 gcs 裸奔（演示数据）或全站统一，不要不声不响地选。
- **返回格式**：全站两套并存——主流是"成功裸数据/失败 `{error}`+HTTP 状态码"，gcs 系是 `{code, data}` 恒 200。设计文档跟的是 gcs 系。建议新模块统一一种并在文档里写明。
