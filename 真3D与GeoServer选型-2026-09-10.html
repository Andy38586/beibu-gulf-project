真 3D 现状 & GeoServer / FastAPI 选型（2026-09-10）
结论先行：① "真 3D 消失"= 服务器地形根瓦片 404（功能没删，数据没铺好，刚才页面变平是我诊断时的临时实验，刷新即还原，但线上真地形本身仍未立起来）；② 地形这类图层不适合上 GeoServer，现有"离线切片 + nginx 静态托管"方向正确，坏在部署制品管理；③ GeoServer 不能替换 FastAPI——一个是空间数据"发布/出图"，一个是洪涝/航线"数值演算"，职责正交，应并存而非二选一。
① "怎么没有真 3D 了"——时间线还原
诊断阶段：我在该标签页把 terrainProvider 临时换成平坦椭球（Ellipsoid）做反证 → 画面变平、无 z 起伏，这是我的实验动作，不是系统状态。
↓ 刷新页面后还原
还原后实测：terrainProvider = CesiumTerrainProvider（真地形在尝试工作），但控制台持续报 Failed to obtain terrain tile X:0/X:1 Level:0 → 404。根瓦片缺失 → 地形 mesh 建不起来 → 线上"真 3D"本来就没真正生效，同时拖黑影像底图。
↓ 修复方式
用 07-heightmap-reslice.py 重切并把 layer.json + 全部瓦片整体重新同步到服务器（补 0/0/0、0/1/0、1/3/1），根瓦片 200 后 z 起伏的真 3D 即恢复；无需改前端。

③ GeoServer 能不能换 FastAPI？——职责正交，不能互替
GeoServer ＝ 空间数据"发布/出图"
把 PostGIS / 文件里的空间数据按标准接口发出去：WMS（图片）、WMTS/TMS（瓦片缓存，内置 GWC）、WFS（矢量）、WCS（栅格）；SLD 配图、按需重投影、多源融合。
不擅长：跑自定义洪涝数值演算、最短路径算法、实时业务逻辑。
你们的 FastAPI ＝ 算法"计算"
任意水位 → 连通性淹没多边形（251 档预计算 + LRU 动态演算，毫秒级）；航线最短路径（路网构图预热约 40s）。
本质是计算服务：输入参数、输出结果 GeoJSON，不是把一份固定数据"发布"出去。
互相替代的代价：用 GeoServer 替 FastAPI = 用 WPS 把 flood_engine / 路径算法重写一遍，性能与可控性更差；用 FastAPI 替 GeoServer = 自己造 WMTS 瓦片缓存、SLD 样式、OGC 标准接口的轮子。两者并存才是常规架构。
